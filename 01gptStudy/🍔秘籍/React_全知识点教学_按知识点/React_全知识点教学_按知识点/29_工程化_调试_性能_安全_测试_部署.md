# 29. 工程化、调试、性能、安全、测试与部署

## 29.1 本章要解决什么问题

当你会写页面之后，下一个问题不是“能不能跑”，而是：

- 代码能不能长期维护；
- 出问题时能不能快速找到原因；
- 页面能不能更快；
- 有没有安全风险；
- 能不能测试；
- 最后能不能部署上线。

这些内容合在一起，叫工程化与项目质量。

---

## 29.2 工程化是什么

工程化不是某一个库，而是一整套让项目更稳定的做法。

它通常包括：

- 代码规范；
- 格式统一；
- 目录清楚；
- 提交前检查；
- 调试工具；
- 构建部署；
- 测试；
- 性能优化；
- 安全处理。

你可以把它理解成：

```text
写得出来，只是开始。
写得干净、稳定、可维护，才是工程化。
```

---

## 29.3 ESLint 和 Prettier

### ESLint

ESLint 用来检查代码问题，比如：

- 没有使用的变量；
- 错误的 Hook 调用；
- 语法风格问题；
- 可能出错的写法。

### Prettier

Prettier 用来统一代码格式，比如：

- 缩进；
- 引号；
- 换行；
- 空格。

### 它们的区别

| 工具 | 作用 |
|---|---|
| ESLint | 检查代码问题 |
| Prettier | 统一代码格式 |

很多项目会把它们一起用。

---

## 29.4 React 开发中的调试方法

### 1）看浏览器控制台

最基础的方法是：

```jsx
console.log(value);
console.error(error);
```

不要嫌它简单。很多问题第一眼就能在控制台看出来。

### 2）用 React DevTools

React DevTools 可以帮助你看：

- 组件树；
- props；
- state；
- Hook 状态；
- 组件是否重复渲染。

如果你发现页面不对，先看：

```text
数据有没有传对？
state 有没有变？
组件有没有重新渲染？
```

### 3）拆小问题

调试时不要一次看整个应用。  
先把问题缩小：

- 是按钮没点到？
- 是状态没更新？
- 是请求没回来？
- 是数据格式不对？
- 是样式问题？

---

## 29.5 常见调试思路

### 1）先看数据

```jsx
console.log(form);
console.log(list);
console.log(user);
```

### 2）再看条件

```jsx
if (!user) {
  return <p>没有数据</p>;
}
```

### 3）再看事件有没有触发

```jsx
function handleClick() {
  console.log('按钮被点击了');
}
```

### 4）再看接口返回什么

```jsx
const response = await fetch('/api/users');
const data = await response.json();
console.log(data);
```

很多 bug 不是 React 的问题，而是数据本身不对。

## 29.6 性能优化先从“少做无用功”开始

性能优化不是一开始就上高级技巧。  
最先做的事情是：

- 不要重复计算；
- 不要无意义渲染；
- 列表不要一次渲染太多；
- 大组件按需加载；
- 只在真正需要时再优化。

---

## 29.7 常见性能手段

### 1）合理拆组件

把大页面拆成小组件，React 更容易管理。

### 2）React.memo

适合 props 比较稳定、子组件较重的场景。

### 3）useMemo

适合缓存计算结果。

### 4）useCallback

适合缓存函数引用，常和 `memo` 一起使用。

### 5）lazy + Suspense

适合路由页面或大组件懒加载。

### 6）列表虚拟化

如果列表特别长，可以只渲染可见部分。  
这通常要借助专门库，比如虚拟列表方案。

---

## 29.8 不要过早优化

一个很重要的原则：

```text
没有明显慢，不要先优化。
```

因为过早优化会带来：

- 代码更复杂；
- 理解成本更高；
- 维护更难；
- 结果可能没变快多少。

先写对，再写稳，最后再优化。

---

## 29.9 XSS 安全基础

XSS 是一种常见安全问题。简单说：

```text
如果用户输入的内容被当成代码执行，就可能出问题。
```

React 默认把字符串当普通文本渲染，这其实已经帮你避免了很多 XSS 风险。

例如：

```jsx
const text = '<img src=x onerror=alert(1) />';
return <p>{text}</p>;
```

React 会把它当成字符串显示，不会直接执行成 HTML。

---

## 29.10 dangerouslySetInnerHTML 要小心

如果你真的需要渲染 HTML，可以用：

```jsx
<div dangerouslySetInnerHTML={{ __html: html }} />
```

但这很危险。

只有在这些条件都满足时才考虑：

- HTML 来源可信；
- 已经做过清洗或过滤；
- 你明确知道风险；
- 确实需要渲染富文本。

如果内容来自用户输入，先清洗，再渲染。  
不要直接把不可信字符串塞进去。

---

## 29.11 本地存储也要注意

很多人喜欢把 token、表单草稿、主题设置放到 localStorage。

这可以做，但要知道：

- localStorage 方便；
- 但它不是安全保险箱；
- 如果页面有 XSS 风险，本地存储也可能被读取。

所以敏感数据要谨慎设计。

---

## 29.12 测试是什么

测试的目的不是“炫技”，而是提前发现问题。

常见测试层次：

- **单元测试**：测一个函数、一个小逻辑；
- **组件测试**：测一个组件是否正常显示和交互；
- **端到端测试**：测完整用户流程。

对于初学者，先理解两件事就够了：

1. 纯函数很好测；
2. 用户交互也可以测试。

---

## 29.13 先从纯函数测试开始

例如你的校验函数：

```jsx
function validate(form) {
  const errors = {};

  if (!form.name.trim()) {
    errors.name = '姓名不能为空';
  }

  return errors;
}
```

这种函数很好测，因为它只依赖输入，不依赖页面。

测试思路：

```text
输入空姓名 → 应该返回 name 错误
输入正常姓名 → 应该返回空对象
```

先学会测这种逻辑，比一开始就上复杂组件测试更容易。

---

## 29.14 组件测试的基本思路

组件测试一般会检查：

- 有没有渲染出文字；
- 按钮能不能点；
- 输入框能不能输入；
- 点击后状态有没有变化。

常见测试组合会使用 Vitest、React Testing Library 等工具。  
如果你现在还没做测试项目，先知道“React 组件可以被自动测试”就够了。

---

## 29.15 调试与测试的关系

调试是你自己在开发时找问题。  
测试是你把“应该怎样”写成规则，让工具帮你反复检查。

简单说：

```text
调试 = 人来找问题
测试 = 机器帮你守规则
```

## 29.16 Vite 项目的构建与部署

Vite 项目常用命令：

```bash
npm run dev
npm run build
npm run preview
```

含义：

- `dev`：开发模式；
- `build`：打包生产代码；
- `preview`：本地预览打包结果。

打包后输出目录通常是 `dist`。

部署时，最常见的方式是把 `dist` 上传到静态托管平台。

---

## 29.17 环境变量

Vite 中，前端可用环境变量通常要以 `VITE_` 开头。

例如：

```env
VITE_API_BASE_URL=https://api.example.com
```

代码中读取：

```jsx
const baseUrl = import.meta.env.VITE_API_BASE_URL;
```

注意：

- 不要把真正敏感的服务器密钥直接放进前端；
- 前端环境变量会被打包到浏览器里；
- `VITE_` 前缀是为了明确哪些变量会暴露给前端。

---

## 29.18 部署前检查清单

上线前可以检查：

- 有没有未处理的报错；
- 接口地址是否正确；
- 生产环境变量是否配置；
- 图片、字体、静态资源路径是否正确；
- 路由刷新是否会 404；
- 是否已经压缩和分包；
- 是否还有明显性能问题；
- 是否有安全隐患。

---

## 29.19 常见错误

- 只会写功能，不做检查；
- 控制台报错却不看；
- 该用 DevTools 却不用；
- 过早写复杂优化代码；
- 直接渲染不可信 HTML；
- 把敏感信息当成普通前端变量；
- 不知道 `build` 和 `preview` 的区别；
- 上线前没有检查路由和环境变量。

---

## 29.20 小结与练习

本章重点：

- 工程化让项目更稳定、更好维护；
- ESLint 查问题，Prettier 管格式；
- React DevTools 和 console 是最基础的调试工具；
- 性能优化先从少做无用功开始；
- `dangerouslySetInnerHTML` 有 XSS 风险，要谨慎；
- 测试可以先从纯函数和简单交互开始；
- Vite 部署前要先 `build`，必要时用 `preview` 检查。

练习：

1. 给一个表单校验函数写一组手工测试用例。
2. 打开 React DevTools，观察一个组件的 props 和 state。
3. 找一个可以懒加载的页面，尝试加入 `lazy`。
4. 写一个带 `dangerouslySetInnerHTML` 的示例，并思考风险。
5. 用 Vite 执行一次 `npm run build`，看看输出目录是什么。
