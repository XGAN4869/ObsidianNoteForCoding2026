# 30. 项目结构与最佳实践

## 30.1 本章要解决什么问题

当你写完几个组件之后，就会发现一个很现实的问题：

```text
文件越来越多，
代码越来越长，
项目越来越乱。
```

如果没有清楚的项目结构，后面会出现：

- 找文件很慢；
- 组件到处乱放；
- API 请求写在页面里；
- 状态逻辑和 UI 混在一起；
- 想改一个功能，结果影响一堆地方。

本章学习的重点不是“某一种唯一正确目录”，而是：

```text
怎样把 React 项目整理得更清楚、更好维护。
```

---

## 30.2 先记住一个原则

项目结构没有唯一标准，但有几个稳定原则：

1. **按职责分开**；
2. **相近的东西放在一起**；
3. **常复用的提出来**；
4. **不要把所有东西都堆在 App.jsx**；
5. **先简单，后升级**。

---

## 30.3 一个新手友好的目录结构

最基础、最容易理解的结构可以这样：

```text
src/
  assets/
  components/
  pages/
  hooks/
  api/
  store/
  styles/
  utils/
  App.jsx
  main.jsx
```

解释：

| 目录 | 放什么 |
|---|---|
| `assets/` | 图片、图标、静态资源 |
| `components/` | 可复用组件 |
| `pages/` | 页面级组件 |
| `hooks/` | 自定义 Hooks |
| `api/` | 接口请求函数 |
| `store/` | 全局状态 |
| `styles/` | 全局样式、主题样式 |
| `utils/` | 工具函数 |

这个结构适合刚开始学 React 的人。

---

## 30.4 组件和页面要分开

### 页面组件

页面组件一般对应路由：

- 首页；
- 用户页；
- 详情页；
- 登录页；
- 404 页。

### 普通组件

普通组件是页面里可复用的小块：

- 按钮；
- 卡片；
- 搜索框；
- 列表项；
- 弹窗；
- 表单字段。

不要混着放。

例如：

```text
pages/HomePage.jsx
components/UserCard.jsx
```

这样一看就知道哪个是页面，哪个是组件。

---

## 30.5 推荐的组件拆分思路

当页面很大时，可以按“区域”拆：

```text
页面
  ├── 顶部区域
  ├── 搜索区域
  ├── 筛选区域
  ├── 列表区域
  └── 底部区域
```

例如任务管理页：

```text
TaskPage
  ├── TaskForm
  ├── TaskFilter
  ├── TaskList
  └── TaskStats
```

这样父组件负责“组合”，子组件负责“各自的事”。

---

## 30.6 一个好的组件应该尽量单一职责

单一职责的意思是：

```text
一个组件尽量只做好一件事。
```

比如：

- `TaskForm` 只负责编辑表单；
- `TaskList` 只负责显示列表；
- `TaskItem` 只负责一条任务的显示；
- `TaskFilter` 只负责筛选条件；
- `TaskPage` 只负责把它们拼起来。

不要把表单、列表、统计、请求、样式全塞到一个组件里。

---

## 30.7 feature-based 结构是什么

除了按类型分目录，还有一种常见做法叫按功能分目录。

例如：

```text
src/
  features/
    tasks/
      components/
      hooks/
      api.js
      taskSlice.js
      TaskPage.jsx
    auth/
      components/
      api.js
      authSlice.js
```

这叫按功能拆分。

它的好处是：

- 一个业务模块的代码放得比较集中；
- 找功能更快；
- 项目大时更清楚。

对于新手来说，你可以先用“按类型分目录”。
项目更大时，再逐步转到“按功能分目录”。

---

## 30.8 什么时候该提取组件

你可以在这些情况下提取组件：

- 同样的 UI 复用了 2 次以上；
- 一个组件太长，已经看不懂；
- 某个区域有独立逻辑；
- 某块 UI 以后大概率会复用；
- 需要单独测试。

不要为了拆而拆。

如果一个组件只会用一次，而且拆开后反而更绕，那就先不拆。

---

## 30.9 组件命名建议

命名要简单、清楚、一看就懂。

### 好名字

- `UserCard`
- `TaskForm`
- `SearchBar`
- `LoginPage`
- `Sidebar`
- `Header`

### 不太好的名字

- `A1`
- `Box2`
- `DataComponent`
- `NewThing`
- `CommonPart`

名字最好表达“它是什么”，而不是“它多酷”。

---

## 30.10 文件命名建议

React 文件常见命名方式：

- 页面：`HomePage.jsx`
- 组件：`TaskList.jsx`
- Hooks：`useTasks.js`
- 工具：`formatDate.js`
- 接口：`taskApi.js`

建议保持统一。

如果项目里已经规定了驼峰命名，就尽量不要混用太多风格。

---

## 30.11 把请求和 UI 分开

页面组件里不要塞太多接口代码。

不好：

```jsx
function TaskPage() {
  // 这里一堆 fetch
  // 这里一堆 setState
  // 这里一堆 JSX
}
```

更好：

```jsx
function TaskPage() {
  const { tasks, loading, error, reload } = useTasks();

  return <TaskList tasks={tasks} />;
}
```

请求逻辑放进：

- `api/`；
- 或 `hooks/`；
- 或状态库。

UI 组件只关心显示。

---

## 30.12 把重复逻辑抽成 Hook

如果很多组件都要做同一件事，可以提成自定义 Hook。

例如：

- 获取任务列表；
- 监听窗口宽度；
- 读 localStorage；
- 处理表单输入；
- 管理分页状态。

自定义 Hook 的名字要以 `use` 开头：

```jsx
useTasks
useWindowSize
useLocalStorage
useForm
```

这能让逻辑复用，又不把 UI 混进来。

---

## 30.13 不要把状态乱放

状态应该放在最合适的位置：

- 一个组件自己用 → `useState`；
- 父子共享 → 提到父组件；
- 多层共享 → `Context`；
- 多页面共享且复杂 → 状态库；
- 只是页面数据缓存 → 可能放在 Hook 里。

这条原则能帮你减少很多乱七八糟的状态。

---

## 30.14 数据流要清楚

React 数据流通常是：

```text
父组件 → 子组件
```

也就是单向数据流。

建议你在项目里总是问自己：

- 这个数据是谁拥有的？
- 谁修改它？
- 谁只负责显示？
- 谁负责提交？

只要这四个问题想明白，很多项目就不会乱。

---

## 30.15 样式管理建议

样式常见做法有：

- 全局样式；
- CSS Modules；
- 组件样式文件；
- CSS-in-JS；
- 原子化 CSS。

初学阶段建议：

- 全局基础样式放 `index.css`；
- 组件样式尽量跟组件放一起；
- 避免一个巨大的全局 CSS 文件越来越乱。

比如：

```text
components/
  TaskCard.jsx
  TaskCard.module.css
```

这样对应关系很清楚。

---

## 30.16 不要过度抽象

新手最容易犯的错误之一就是：

```text
什么都想提前抽象。
```

例如：

- 现在只有一个按钮，就先做一个超复杂通用按钮；
- 现在只有一个弹窗，就先做一套超级配置系统；
- 现在只有一个接口，就先做一层特别厚的封装。

结果就是：

- 代码更难懂；
- 调试更麻烦；
- 真正改需求时反而更慢。

正确做法：

```text
先写出最简单、最清楚的版本。
真的重复了，再抽象。
```

---

## 30.17 版本控制和提交习惯

虽然这不是 React 特有知识，但很重要。

建议：

- 每完成一个小功能就提交一次；
- 提交信息写清楚；
- 不要堆很多功能一起提交；
- 有问题时，能回退到上一个稳定版本。

例如：

```text
feat: add task form validation
fix: handle empty search result
refactor: split task list components
```

---

## 30.18 一个简单的最佳实践清单

你可以每次写组件时问自己：

- 这个组件是不是太长了？
- 这个逻辑是不是能提取成 Hook？
- 这个请求是不是该放到 api 文件？
- 这个状态是不是放错地方了？
- 这个名字清楚吗？
- 这个功能是不是已经可以复用？

只要经常问这些问题，代码质量会越来越好。

---

## 30.19 常见错误

- 所有逻辑都写在 App.jsx；
- 页面和组件不分；
- 文件命名混乱；
- 一个组件负责太多事情；
- 过早抽象；
- 状态放错地方；
- 请求和展示逻辑混在一起；
- 目录很多，但没有规则。

---

## 30.20 小结与练习

本章重点：

- 项目结构没有唯一答案，但有稳定原则；
- 页面、组件、Hook、API、Store 最好分开；
- 组件尽量单一职责；
- 先按类型分目录，项目大了再按功能分；
- 不要过度抽象；
- 状态和请求都要放在合适位置。

练习：

1. 把一个大页面拆成 `TaskForm`、`TaskList`、`TaskFilter` 三个组件。
2. 给你的项目整理出 `components`、`pages`、`hooks`、`api` 目录。
3. 找出一个可以变成自定义 Hook 的重复逻辑。
4. 思考：什么状态应该留在组件里，什么状态应该提到更上层？
