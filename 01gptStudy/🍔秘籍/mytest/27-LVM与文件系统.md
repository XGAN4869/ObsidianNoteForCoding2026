## 1. 概述

### 1.1 从"固定分区"到"弹性存储"

第 26 章你学会了传统磁盘管理——用 `fdisk`/`gdisk` 分区，用 `mkfs` 格式化，用 `mount` 挂载。这套方法从 1980 年代沿用至今，简单可靠，但它有一个根本性的限制：

**分区大小是固定的，一旦划定就很难改变。**

想象以下场景：

- "`/home` 分区满了，但 `/var` 分区还有 200G 空闲——能不能把空间挪过去？"
- "数据库需要 500G 空间，但服务器上三块磁盘分别是 200G、200G、100G——怎么合并？"
- "半夜 2 点磁盘满了，用户已经在投诉——能不能不停机、不重启就完成扩容？"
- "在升级软件之前，需要给系统分区做一个完整快照——这样升级失败可以秒级回滚。"

传统分区对这些需求束手无策（或只能停机操作），而 **LVM（Logical Volume Manager，逻辑卷管理器）** 就是为解决这些问题而生的。

LVM 是 Linux 企业级存储管理的基石。从 Ubuntu Server 到 RHEL/CentOS，从物理机部署到云环境，LVM 几乎是所有生产服务器的默认存储配置。

```
传统分区方式：                     LVM 方式：
┌────────────────┐              ┌─────────────────────────────────┐
│  /dev/sda      │              │  物理卷 PV（Physical Volume）    │
│  └─/dev/sda1   │              │  /dev/sda1  /dev/sdb1           │
│      ext4      │              │       │          │               │
│      50G       │              │       └────┬─────┘               │
│       │        │              │            ▼                     │
│       ▼        │              │  卷组 VG（Volume Group）          │
│    /data       │              │  vg_data（合并所有 PV 的空间）     │
│                │              │       │                          │
│  固定 50G      │              │       ├── 逻辑卷 LV1: lv_home 200G│
│  无法扩容      │              │       ├── 逻辑卷 LV2: lv_data 500G │
│  换磁盘=       │              │       └── 逻辑卷 LV3: lv_logs 100G │
│  换挂载点      │              │            ▼                       │
└────────────────┘              │       mkfs.ext4 + mount           │
                                特点：                               │
                                │  - 可以随时在线扩容 LV              │
                                │  - 可以将多块物理磁盘合并到一个 VG   │
                                │  - 可以添加新磁盘到 VG 并分配给 LV   │
                                │  - 支持快照（Snapshot）             │
                                └─────────────────────────────────┘
```

## 2. 核心概念

### 2.1 为什么需要 LVM？——传统分区的四大痛点

在动手操作 LVM 之前，先理解它解决了什么问题。传统分区方式的四个核心痛点：

```
+------------------------------------------------------------------+
|                    传统分区的四大痛点                               |
|                                                                  |
|  痛点 1：大小固定，难以扩展                                        |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  /home 分区 50G → 满了 → 怎么办？                             │ |
|  │  - 备份数据 → 删除分区 → 重新创建更大的分区 → 恢复数据         │ |
|  │  - 或者：添加一块磁盘 → 新建分区 → 挂载到 /home2              │ |
|  │  - 都需要停机！                                               │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                                                  |
|  痛点 2：不能跨磁盘                                                |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  有三块磁盘：200G + 200G + 100G → 想要一个 500G 的 /data      │ |
|  │  传统分区：每块磁盘独立分区，无法组合成一个大的文件系统          │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                                                  |
|  痛点 3：调整需要卸载                                              |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  传统分区扩容/缩减必须 umount，意味着服务中断                   │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                                                  |
|  痛点 4：快照功能缺失                                              |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  想给系统做快照再升级？传统分区做不到                           │ |
|  │  只能靠备份——但备份耗时且恢复到某个时间点很麻烦                  │ |
|  └──────────────────────────────────────────────────────────────┘ |
+------------------------------------------------------------------+
```

LVM 通过在物理磁盘和文件系统之间增加一层抽象，一举解决了上述所有问题。

### 2.2 LVM 三层架构：PV → VG → LV

LVM 的核心思想是**在物理磁盘之上加一层逻辑抽象**，让存储管理从"跟硬件绑定"变为"与硬件解耦"。这层抽象分为三个层次：

```
+------------------------------------------------------------------+
|                    LVM 三层架构详解                                 |
|                                                                  |
|  ┌──────────┐  ┌──────────┐  ┌──────────┐                       |
|  │  LV       │  │  LV       │  │  LV       │  ← 逻辑卷层          |
|  │  lv_home  │  │  lv_data  │  │  lv_mysql │     (Logical Volume) |
|  │  200G     │  │  500G     │  │  300G     │     ext4 / xfs /... |
|  │  /home    │  │  /data    │  │  /mysql   │     挂载后用户可见    |
|  └─────┬─────┘  └─────┬─────┘  └─────┬─────┘                       |
|        │              │              │                             |
|        └──────────────┼──────────────┘                             |
|                       │                                            |
|              ┌────────┴────────┐                                   |
|              │   VG（卷组）     │  ← 卷组层                         |
|              │   vg_system     │     (Volume Group)                |
|              │   总容量：1000G  │     合并所有 PV 的空间             |
|              │   已分配：1000G  │     形成一个大的存储池             |
|              └────────┬────────┘                                   |
|                       │                                            |
|        ┌──────────────┼──────────────┐                             |
|        │              │              │                             |
|  ┌─────┴─────┐  ┌─────┴─────┐  ┌─────┴─────┐                       |
|  │  PV        │  │  PV        │  │  PV        │  ← 物理卷层        |
|  │  /dev/sda1 │  │  /dev/sdb1 │  │  /dev/sdc1 │     (Physical Vol) |
|  │  300G      │  │  400G      │  │  300G      │     实际的磁盘/分区  |
|  └───────────┘  └───────────┘  └───────────┘                       |
|                                                                  |
|  关键概念：                                                        |
|  - PE（Physical Extent，物理扩展块）：PV 的最小分配单元，默认 4 MiB   |
|  - LE（Logical Extent，逻辑扩展块）：LV 的最小分配单元               |
|  - LE 和 PE 的大小相同（默认 4 MiB），LV 由 LE 组成，LE 映射到 PE    |
+------------------------------------------------------------------+
```

**三层各自的角色：**

| 层级 | 全称 | 中文 | 角色 | 类比 |
|------|------|------|------|------|
| **PV** | Physical Volume | 物理卷 | 被 LVM 管理的磁盘或分区，是存储的"原材料" | 砖块 |
| **VG** | Volume Group | 卷组 | 由一个或多个 PV 组成的存储池（Storage Pool），集中管理所有可用空间 | 仓库 |
| **LV** | Logical Volume | 逻辑卷 | 从 VG 中划分出的"虚拟分区"，可以像普通分区一样格式化和挂载，且支持在线调整大小 | 房间 |

**数据流向**：应用程序 → 文件系统（ext4/xfs）→ 逻辑卷（LV）→ 卷组（VG）→ 物理卷（PV）→ 物理磁盘（/dev/sda）

### 2.3 PE 与 LE：LVM 的"原子"单位

理解 PE（Physical Extent）和 LE（Logical Extent）对于掌握 LVM 的空间管理至关重要。

```
+------------------------------------------------------------------+
|                    PE 与 LE 的关系                                 |
|                                                                  |
|  LV：逻辑卷                                                        |
|  ┌────┬────┬────┬────┬────┬────┬────┬────┐                       |
|  │ LE0│ LE1│ LE2│ LE3│ LE4│ LE5│ LE6│ LE7│  ← LE = Logical Extent|
|  └──┬─┴──┬─┴──┬─┴──┬─┴──┬─┴──┬─┴──┬─┴──┬─┘                       |
|     │    │    │    │    │    │    │    │                           |
|     │    │    │    │    │    │    │    │    映射（Mapping）          |
|     ▼    ▼    ▼    ▼    ▼    ▼    ▼    ▼                           |
|  ┌────┬────┬────┬────┬────┬────┬────┬────┐                       |
|  │ PE0│ PE1│ PE2│ PE3│ PE4│ PE5│ PE6│ PE7│  ← PE = Physical Extent|
|  └──┬─┴────┴────┴──┬─┴──┬─┴────┴────┴──┬─┘                       |
|     │               │    │               │                        |
|     ▼               ▼    ▼               ▼                        |
|  ┌──────┐       ┌──────┐            ┌──────┐                      |
|  │ PV1  │       │ PV2  │            │ PV3  │                      |
|  │/sda1 │       │/sdb1 │            │/sdc1 │                      |
|  └──────┘       └──────┘            └──────┘                      |
|                                                                  |
|  关键特性：                                                        |
|  - PE 是 PV 的最小分配单位，默认大小 4 MiB（创建 VG 时可指定 -s）    |
|  - LE 是 LV 的最小分配单位，与 PE 一一对应                          |
|  - 一个 LV 的 LE 可以分布在不同 PV 的 PE 上（数据条带化）           |
|  - PE 大小在创建 VG 时确定，之后不可更改                            |
|  - 运行 `vgdisplay vg_name` 可以查看 PE Size 和 Free PE 数量        |
+------------------------------------------------------------------+
```

**PE 大小的影响**：

| PE 大小 | 最大 LV 容量（32 位系统） | 最大 PE 数量 | 优点 | 缺点 |
|---------|------------------------|-------------|------|------|
| 4 MiB（默认） | 256 GiB | ~65,536 | 平衡 | - |
| 8 MiB | 512 GiB | ~65,536 | 适合大容量卷 | 空间浪费更多 |
| 16 MiB | 1 TiB | ~65,536 | 适合超大卷 | 浪费最多 |
| 1 MiB | 64 GiB | ~65,536 | 空间利用率高 | PE 数量多，管理开销大 |

对于 Ubuntu 24.04 LTS（64 位系统），默认 4 MiB PE 足以支持最大 8 EiB 的 LV 容量（64 位下 PE 数量限制极高）。

### 2.4 Device Mapper：LVM 的内核引擎

LVM 的用户态工具（`pvcreate`、`lvcreate` 等）最终通过 **Device Mapper（设备映射器）**——一个 Linux 内核子系统——来创建虚拟块设备。

```
+------------------------------------------------------------------+
|                    LVM 与 Device Mapper                           |
|                                                                  |
|  用户态：                                                         |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  pvcreate / vgcreate / lvcreate / lvextend ...              │ |
|  │  LVM 工具包（lvm2）—— 用户态命令行工具                         │ |
|  └─────────────────────────────────────┬────────────────────────┘ |
|                                        │ ioctl 系统调用             |
|                                        ▼                           |
|  内核态：                                                         |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  Device Mapper（dm）—— 内核的块设备映射框架                     │ |
|  │  ┌────────────────────────────────────────────────────────┐  │ |
|  │  │  dm-linear：线性映射 —— LE 与 PE 一一对应               │  │ |
|  │  │  dm-snapshot：快照 —— 写时复制（Copy-on-Write）          │  │ |
|  │  │  dm-stripe：条带化 —— 数据分散到多个 PV                 │  │ |
|  │  │  dm-mirror：镜像 —— 数据复制到多个 PV                  │  │ |
|  │  │  dm-crypt：加密 —— LUKS 全盘加密的基础                  │  │ |
|  │  └────────────────────────────────────────────────────────┘  │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                        │                           |
|                                        ▼                           |
|  /dev/mapper/vg_system-lv_home  ← LV 的设备路径                     |
|  /dev/vg_system/lv_home         ← 符号链接（Ubuntu 常用）            |
+------------------------------------------------------------------+
```

创建 LV 后，可以通过 `/dev/<vg_name>/<lv_name>` 或 `/dev/mapper/<vg_name>-<lv_name>` 访问它：

```bash
# 查看 LVM 设备映射
ls -l /dev/mapper/
# 输出示例：
# lrwxrwxrwx 1 root root  7 Jul 30 10:00 vg_system-lv_home -> ../dm-0
# lrwxrwxrwx 1 root root  7 Jul 30 10:00 vg_system-lv_data -> ../dm-1

# 查看 Device Mapper 设备
sudo dmsetup ls
# 输出示例：
# vg_system-lv_home (253:0)
# vg_system-lv_data  (253:1)

# 查看映射关系
sudo dmsetup table
# 输出每个 dm 设备背后的物理块设备信息
```

### 2.5 LVM 快照：写时复制的秒级备份

LVM 快照（Snapshot）是 LVM 最强大的特性之一。它的核心机制是 **CoW（Copy-on-Write，写时复制）**。

```
+------------------------------------------------------------------+
|                    LVM 快照原理                                    |
|                                                                  |
|  正常状态（快照刚创建时）：                                        |
|  ┌────────────────────────────────────────────┐                  |
|  │  原始 LV（lv_data，100G）                    │                  |
|  │  ┌───┬───┬───┬───┬───┬───┬───┬───┐        │                  |
|  │  │ A │ B │ C │ D │ E │ F │ G │ H │  ← 数据块│                  |
|  │  └───┴───┴───┴───┴───┴───┴───┴───┘        │                  |
|  └────────────────────────────────────────────┘                  |
|  ┌──────────────────────────┐                                    |
|  │  快照卷（snap_data，10G） │  ← 快照异常区域，初始为空            │
|  │  （空的 COW 表）          │                                     │
|  └──────────────────────────┘                                    |
|                                                                  |
|  写操作发生时（块 C 被修改）：                                      |
|  ┌────────────────────────────────────────────┐                  |
|  │  原始 LV                                      │                  |
|  │  ┌───┬───┬───┬───┬───┬───┬───┬───┐        │                  |
|  │  │ A │ B │ C'│ D │ E │ F │ G │ H │  ← C→C'│                  |
|  │  └───┴───┴───┴───┴───┴───┴───┴───┘        │                  |
|  └────────────────────────────────────────────┘                  |
|  ┌──────────────────────────┐                                    |
|  │  快照卷（snap_data，10G） │  写入前先复制旧数据 C 到快照卷       |
|  │  ┌───┐                   │                                     |
|  │  │ C │  ← 旧数据副本      │                                     |
|  │  └───┘                   │                                     |
|  └──────────────────────────┘                                    |
|                                                                  |
|  读取快照时：                                                      |
|  - 如果块未被修改（A、B、D、E...）：从原始 LV 直接读取               |
|  - 如果块已被修改（C）：从快照卷中的旧副本读取                       |
|  - 对用户来说，快照始终呈现为"创建时的原始状态"                      |
+------------------------------------------------------------------+
```

**快照的关键特性**：

| 特性 | 说明 |
|------|------|
| **创建速度** | 秒级创建（只需创建元数据，无需复制数据） |
| **空间占用** | 初始几乎为 0，随原始卷的写入逐渐增长 |
| **快照大小** | 决定能在原始卷上写入多少"新数据"而不耗尽快照空间 |
| **快照耗尽** | 如果快照卷满了，快照会被自动禁用（Invalidated），无法恢复 |
| **性能影响** | 有写惩罚（Write Penalty）：首次修改某块时，需先复制旧数据到快照卷 |
| **典型用途** | 数据库备份前做快照；软件升级前做快照，升级失败秒级回滚 |
| **限制** | 快照是"全卷快照"，不是文件级——恢复会覆盖整个 LV |

### 2.6 文件系统类型对比：ext4 vs XFS vs Btrfs vs ZFS

LVM 提供了灵活的卷管理，但文件系统的选择同样重要。不同的文件系统具有截然不同的特性，选错可能会在后期带来严重的运维问题。

#### 2.6.1 四种文件系统概述

```
+------------------------------------------------------------------+
|                    文件系统对比总览                                  |
|                                                                  |
|  时间线：                    ext4 → XFS → Btrfs → ZFS             |
|  1993                    2006   2001   2009   2005               |
|  ext2 诞生                 ext4   XFS    Btrfs  ZFS (Solaris)    |
|                           稳定    稳定   融入   移植到              |
|                                          Linux   Linux            |
+------------------------------------------------------------------+
```

#### 2.6.2 特性对比详表

| 特性 | ext4 | XFS | Btrfs | ZFS |
|------|------|-----|-------|-----|
| **开发年代** | 2006 | 1994 (IRIX), 2001 (Linux) | 2009 | 2005 (Solaris), 2010 (Linux) |
| **最大文件系统大小** | 1 EiB | 8 EiB | 16 EiB | 256 万亿 YiB |
| **最大单个文件大小** | 16 TiB | 8 EiB | 16 EiB | 16 EiB |
| **日志类型** | 有序日志（Ordered Journaling） | 元数据日志（Metadata Journaling） | Copy-on-Write B-tree | Copy-on-Write |
| **快照（Snapshot）** | 无原生支持 | 无原生支持 | 原生支持（读写快照） | 原生支持（读写快照） |
| **数据校验和（Checksum）** | 仅元数据（可选） | 仅元数据 | 元数据 + 数据 | 元数据 + 数据 |
| **压缩（Compression）** | 无 | 无 | 原生（zlib/lzo/zstd） | 原生（lz4/gzip/zstd） |
| **去重（Deduplication）** | 无 | 无 | 支持（离线去重） | 支持（在线去重） |
| **RAID 能力** | 无 | 无 | 原生 RAID 0/1/10/5/6 | 原生 RAID-Z/RAID-Z2/RAID-Z3 |
| **在线扩容** | 支持（需取消日志） | 支持 | 支持 | 支持 |
| **在线缩减** | 支持（需卸载） | 不支持 | 支持 | 不支持 |
| **fsck 速度** | 中等（取决于容量） | 极快（仅重放日志） | 在线检查（不需要 fsck） | 在线检查（不需要 fsck） |
| **碎片化** | 有碎片（e4defrag） | 较少碎片 | 有碎片（CoW 特性导致） | 有碎片（CoW 特性导致） |
| **Ubuntu 默认** | 是（桌面版） | 否 | 否 | 否（需安装 zfsutils-linux） |
| **RHEL/CentOS 默认** | 是（RHEL 6） | 是（RHEL 7+） | 技术预览 | 不支持 |
| **成熟度** | 非常成熟 | 非常成熟 | 较成熟（SUSE 默认） | 非常成熟（OpenZFS） |
| **内核态/用户态** | 内核态 | 内核态 | 内核态 | 用户态（CDDL 许可，非 GPL） |

#### 2.6.3 各文件系统深度剖析

**ext4（Fourth Extended Filesystem）**

ext4 是 Linux 历史上使用最广泛的文件系统。它是 ext3 的直接升级，继承了 ext 系列的所有特性，同时大幅提升了性能和容量上限。

```
ext4 内部结构：
┌──────────────────────────────────────────────────────────────┐
│                       Block Group 0                          │
│  ┌──────────┬──────────┬──────┬──────────┬────────────────┐  │
│  │Superblock│GDT       │Reserv│Data Block│Inode Table     │  │
│  │(备份)     │(组描述符表)│GDT   │Bitmap    │                │  │
│  └──────────┴──────────┴──────┴──────────┴────────────────┘  │
│                       Block Group 1                          │
│  ┌──────────┬──────────┬──────┬──────────┬────────────────┐  │
│  │Superblock│GDT       │Reserv│Data Block│Inode Table     │  │
│  │(备份)     │          │GDT   │Bitmap    │                │  │
│  └──────────┴──────────┴──────┴──────────┴────────────────┘  │
│                        ...                                    │
│                       Block Group N                          │
└──────────────────────────────────────────────────────────────┘
```

**优点**：
- 最广泛的兼容性和社区支持
- 支持从 ext2/ext3 原地升级
- 稳定的在线扩容
- 丰富的调优工具（`tune2fs`、`e2fsck`、`resize2fs`、`debugfs`）

**缺点**：
- 不支持数据校验和，无法检测静默数据损坏（Silent Data Corruption）
- 不支持快照、压缩、去重等现代特性
- fsck 在大容量卷上非常慢（可能需要数小时）
- 不支持在线缩减

**适用场景**：通用文件存储、系统分区、中小型数据库、需要广泛兼容的环境。

---

**XFS**

XFS 最初由 SGI（Silicon Graphics）为 IRIX 操作系统开发，2001 年移植到 Linux。它是为高性能和大容量设计的 64 位日志文件系统。

```
XFS 内部结构（分配组）：
┌──────────────────────────────────────────────────────────────┐
│                    Allocation Group 0 (AG 0)                  │
│  ┌──────────┬──────────┬──────────┬────────────────────────┐ │
│  │Superblock│AGF       │AGI       │Free Space (B+tree)     │ │
│  │          │(AG Free) │(AG Inode)│                        │ │
│  └──────────┴──────────┴──────────┴────────────────────────┘ │
│                    Allocation Group 1 (AG 1)                  │
│  ┌──────────┬──────────┬──────────┬────────────────────────┐ │
│  │Superblock│AGF       │AGI       │Free Space (B+tree)     │ │
│  │(备份)     │          │          │                        │ │
│  └──────────┴──────────┴──────────┴────────────────────────┘ │
│                        ...                                    │
└──────────────────────────────────────────────────────────────┘
```

XFS 使用 **分配组（Allocation Group, AG）** 将文件系统划分为多个独立区域。每个 AG 管理自己的 inode 和空闲空间，这种设计允许并发分配——多个 CPU 核心可以同时在不同 AG 中分配空间，极大提升并行写入性能。

**优点**：
- 极佳的大文件读写性能（特别是顺序 I/O）
- 支持在线扩容（但不支持缩减）
- 元数据日志（Metadata Journaling）——日志只记录元数据变更，写入快
- 在线碎片整理（`xfs_fsr`）
- 分配组设计提供优秀的并行 I/O 性能
- 适合大容量（PB 级）文件系统

**缺点**：
- 不支持缩减（一旦创建，只能扩大不能缩小）
- 不支持快照、压缩、去重（需配合 LVM 实现快照）
- 小文件频繁删写可能导致碎片
- 不支持数据校验和

**适用场景**：数据库服务器（MySQL/PostgreSQL/MongoDB）、大文件存储（视频/备份/镜像）、HPC 集群、高并发写入场景。

---

**Btrfs（B-tree Filesystem）**

Btrfs 是 Linux 社区开发的"下一代"文件系统，旨在提供现代存储管理所需的所有特性。它被设计为 ext4 的长期替代者。

```
Btrfs 内部结构（COW B-tree）：
┌──────────────────────────────────────────────────────────────┐
│                    Btrfs Data Structure                       │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐    │
│  │                  Root Tree                           │    │
│  │  ┌──────────┬──────────┬──────────┬──────────┐      │    │
│  │  │Extent Tree│FS Tree   │Chunk Tree│Checksum  │      │    │
│  │  │(空间分配)  │(目录结构)  │(块映射)   │Tree      │      │    │
│  │  └──────────┴──────────┴──────────┴──────────┘      │    │
│  └──────────────────────────────────────────────────────┘    │
│                                                              │
│  Copy-on-Write 机制：                                         │
│  写入数据时，新数据写入新位置，旧数据保持不变                     │
│  ┌────┐  写入  ┌────┐                                       │
│  │ A  │  →→→  │ A' │  ← 新数据写在新位置                      │
│  └────┘       └────┘                                         │
│  ┌────┐       ┌────┐  ← 旧数据保留（快照可见）                  │
│  │ A  │       │ A  │                                         │
│  └────┘       └────┘                                         │
└──────────────────────────────────────────────────────────────┘
```

**优点**：
- 原生快照（子卷 Subvolume）——创建瞬间完成，支持读写
- 数据校验和——检测并修复静默数据损坏
- 透明压缩——zlib / lzo / zstd，节省空间
- 内置 RAID 支持（RAID 0/1/10/5/6）
- 在线扩容和缩减
- 发送/接收（Send/Receive）——增量备份传输
- 写时复制——天然的事务安全性

**缺点**：
- RAID 5/6 模式仍不够稳定（write hole 问题）
- 碎片化比 ext4/XFS 严重
- 社区人力相对有限
- 某些场景性能不如 ext4/XFS（尤其是大量随机写入的 CoW 惩罚）
- fsck 工具仍在完善中

**适用场景**：需要快照/回滚的开发环境、容器存储（Docker、Podman）、NAS / 家庭文件服务器、需要数据完整性验证的归档存储。

---

**ZFS（Zettabyte File System）**

ZFS 最初由 Sun Microsystems 为 Solaris 开发，是"功能最完整"的文件系统。它同时是一个**文件系统**和一个**卷管理器**——集成了传统上由 LVM 和 RAID 提供的所有功能。

OpenZFS 项目将 ZFS 移植到了 Linux 和 FreeBSD。由于 CDDL 许可证与 GPL 不兼容，ZFS 不能嵌入 Linux 内核，而是作为内核模块（DKMS）加载。

```
ZFS 架构（池化存储）：
┌──────────────────────────────────────────────────────────────┐
│                    ZFS Storage Pool (zpool)                   │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │                    ZFS Datasets                        │  │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐             │  │
│  │  │zfs/root  │  │zfs/data  │  │zfs/logs  │  ← 文件系统   │  │
│  │  │/         │  │/data     │  │/var/log  │             │  │
│  │  └──────────┘  └──────────┘  └──────────┘             │  │
│  └────────────────────────────────────────────────────────┘  │
│                              │                               │
│  ┌───────────────────────────┴────────────────────────────┐  │
│  │                    ZFS Pool (zpool)                     │  │
│  │  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐                   │  │
│  │  │ vdev1│ │ vdev2│ │ vdev3│ │ vdev4│  ← 虚拟设备        │  │
│  │  │mirror│ │mirror│ │ RAIDZ│ │ CACHE│                   │  │
│  │  └──┬───┘ └──┬───┘ └──┬───┘ └──────┘                   │  │
│  │     │        │        │                                 │  │
│  │  ┌──┴──┐ ┌──┴──┐  ┌──┴──┐                              │  │
│  │  │sdb │ │sdc │ │sdd │ │sde │ │sdf │  ← 物理磁盘          │  │
│  │  └────┘ └────┘ └────┘ └────┘ └────┘                     │  │
│  └──────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

**优点**：
- **一切皆池**：存储池化管理，无需预先划分大小
- 数据完整性验证：端到端校验和（End-to-End Checksum），自动修复静默数据损坏
- 快照和克隆：零成本快照，可写克隆
- 透明压缩：lz4 / gzip / zstd，CPU 开销极小
- 在线去重（Deduplication）：节省存储空间（但内存开销大）
- RAID-Z / RAID-Z2 / RAID-Z3：比传统 RAID5/6 更安全（解决 write hole 问题）
- 发送/接收（zfs send/receive）：增量复制，灾难恢复利器
- 自适应替换缓存（ARC）：智能内存缓存，加速读写
- ZIL（ZFS Intent Log）+ SLOG：加速同步写入

**缺点**：
- CDDL 许可证与 GPL 不兼容——不能内置到 Linux 内核
- 需要安装 DKMS 模块（每次内核升级后可能需要重新编译）
- 内存消耗大（推荐 ECC 内存 + 至少 8 GB RAM）
- 不支持缩减（不能从池中移除 vdev）
- 学习曲线陡峭
- 不包含在标准 Ubuntu 安装中，需手动安装

**适用场景**：NAS / SAN 存储服务器（如 TrueNAS）、大数据归档、虚拟化存储（Proxmox VE）、对数据完整性要求极高的场景（金融、医疗）。

#### 2.6.4 场景选型建议

```
+------------------------------------------------------------------+
|                    文件系统选型决策树                               |
|                                                                  |
|  需要快照/压缩/数据校验？                                          |
|    ├── 是 → 需要极致性能 + 完整功能？                              |
|    │         ├── 是 → ZFS（内存充足 + ECC 推荐）                   |
|    │         └── 否 → Btrfs（内置 Linux 内核，更轻量）             |
|    └── 否 → 文件系统大小需要缩减？                                 |
|              ├── 是 → ext4                                       |
|              └── 否 → 主要存储大文件（> 1 GiB）？                  |
|                        ├── 是 → XFS                              |
|                        └── 否 → ext4                              |
+------------------------------------------------------------------+
```

| 场景 | 推荐文件系统 | 原因 |
|------|-------------|------|
| 操作系统根分区（/） | ext4 | 最广泛的兼容性，所有发行版支持 |
| 数据库存储（MySQL/PostgreSQL） | XFS | 大文件顺序写入性能优异 |
| Docker/容器存储 | Btrfs 或 XFS | Btrfs 支持快照回滚快速部署；XFS 性能可靠 |
| NAS / 家庭文件服务器 | ZFS 或 Btrfs | 数据完整性、快照、压缩 |
| 高并发 Web 应用 | XFS | 分配组并行 I/O，高吞吐 |
| 归档/备份存储 | ZFS | 数据校验和，压缩，去重 |
| 虚拟机磁盘镜像 | ZFS 或 XFS | ZFS 压缩+快照；XFS 大文件性能 |
| 嵌入式 / ARM 设备 | ext4 | 轻量且成熟 |

### 2.7 LVM 与文件系统的协同

LVM 和文件系统既可以独立使用，也可以组合使用：

```
+------------------------------------------------------------------+
|                    存储栈选项总览                                   |
|                                                                  |
|  选项 1：传统方式                                                  |
|  /dev/sda → 分区(/dev/sda1) → mkfs → mount                       |
|  适用：简单场景，不需要弹性管理                                     |
|                                                                  |
|  选项 2：LVM + ext4/XFS（本章重点）                                |
|  /dev/sda → PV → VG → LV → mkfs.ext4 → mount                     |
|  适用：需要在线扩容、快照的企业级环境                                |
|                                                                  |
|  选项 3：LVM + Btrfs（一般不推荐，Btrfs 自带卷管理）               |
|  /dev/sda → PV → VG → LV → mkfs.btrfs → mount                    |
|  适用：需要 LVM 快照 + Btrfs 特性的混合场景（较少见）               |
|                                                                  |
|  选项 4：ZFS（自包含，不需要 LVM）                                 |
|  /dev/sda ─┐                                                     |
|  /dev/sdb ─┤→ zpool create → zfs create → mount                  |
|  /dev/sdc ─┘                                                     |
|  适用：对数据完整性要求极高的场景（NAS/备份服务器）                  |
+------------------------------------------------------------------+
```

### 3.1 pvcreate：创建物理卷

#### 3.1.1 功能

将磁盘或分区初始化为 LVM 物理卷（Physical Volume, PV）。此操作会在设备上写入 LVM 元数据（Metadata），包括 PV 的 UUID、大小、以及标签信息。

> **注意**：`pvcreate` 会覆盖设备上已有的文件系统或分区表签名。确保目标设备上没有需要保留的数据。

#### 3.1.2 参数说明

| 参数 | 说明 | 必选/可选 | 默认值 |
|------|------|----------|--------|
| `DEVICE` | 目标磁盘或分区的设备路径 | 必选 | - |
| `-f, --force` | 强制创建，不提示确认 | 可选 | 交互式确认 |
| `-y, --yes` | 对所有提示回答 yes | 可选 | 交互式确认 |
| `-v, --verbose` | 显示详细信息 | 可选 | 简洁输出 |
| `--uuid UUID` | 指定 PV 的 UUID | 可选 | 自动生成 |
| `--dataalignment SIZE` | 数据对齐（影响性能，SSD 建议对齐到 1MiB） | 可选 | 自动检测 |
| `--setphysicalvolumesize SIZE` | 限制 PV 使用的空间大小（仅使用分区的一部分） | 可选 | 使用整个分区 |

#### 3.1.3 基本用法

```bash
# 将整块磁盘初始化为 PV（必须先确认磁盘上没有重要数据）
sudo pvcreate /dev/sdb

# 将分区初始化为 PV（推荐：先创建 GPT 分区）
sudo parted /dev/sdb mklabel gpt
sudo parted /dev/sdb mkpart primary 0% 100%
sudo pvcreate /dev/sdb1

# 强制创建（跳过确认提示）
sudo pvcreate -f /dev/sdc1

# 创建 PV 并指定数据对齐（SSD 建议对齐到 1 MiB）
sudo pvcreate --dataalignment 1M /dev/nvme0n2
```

#### 3.1.4 LVM 分区最佳实践

在使用 `pvcreate` 之前，建议先用 `parted` 或 `gdisk` 创建一个分区，然后对该分区执行 `pvcreate`——而不是对整块磁盘。原因：

1. 其他操作系统或工具看到整盘标记为 LVM 可能误认为磁盘未分区
2. 如果未来需要混合使用（某些分区给 LVM、某些不用），整盘初始化就做不到
3. 分区表提供了一层"这里有数据"的信息

```bash
# 推荐流程
sudo parted /dev/sdb mklabel gpt
sudo parted /dev/sdb mkpart lvm 0% 100%
sudo parted /dev/sdb set 1 lvm on        # 设置分区类型为 Linux LVM
sudo pvcreate /dev/sdb1
```

### 3.2 pvdisplay：显示物理卷详细信息

#### 3.2.1 功能

显示一个或多个物理卷的详细信息，包括 PV 名称、VG 所属、PV 大小、可用空间、PE 数量、UUID 等。

### 3.7 lvcreate：创建逻辑卷

#### 3.7.1 功能

从卷组中划分空间创建逻辑卷（Logical Volume, LV）。LV 可以像普通分区一样格式化和挂载。支持多种创建模式：指定大小、指定 PE 数量、使用百分比、创建快照、创建精简卷等。

#### 3.7.2 参数说明

| 参数 | 说明 | 必选/可选 | 默认值 |
|------|------|----------|--------|
| `-L, --size SIZE` | 指定 LV 的大小（如 10G、500M） | `-L` 或 `-l` 二选一 | - |
| `-l, --extents NUMBER` | 指定 PE 数量（也可以使用百分比，如 `100%FREE`） | `-L` 或 `-l` 二选一 | - |
| `-n, --name NAME` | 指定 LV 名称 | 必选 | - |
| `VG_NAME` | 卷组名称 | 必选 | - |
| `-s, --snapshot` | 创建快照卷（需配合 `-L` 和原始 LV 路径） | 可选 | 普通 LV |
| `-T, --thin` | 创建精简池（Thin Pool） | 可选 | 厚卷 |
| `-V, --virtualsize SIZE` | 用于精简卷的虚拟大小 | 可选 | - |
| `-m, --mirrors NUMBER` | 设置镜像数量 | 可选 | 0（无镜像） |
| `-i, --stripes NUMBER` | 设置条带数量 | 可选 | 1（无条带） |
| `-I, --stripesize SIZE` | 条带大小 | 可选 | 64 KiB |
| `--type TYPE` | LV 类型（linear/striped/mirror/raid1/raid5/raid6/thin-pool） | 可选 | linear |
| `-Z y/n, --zero y/n` | 是否清零 LV 第一个扇区（防止旧文件系统签名干扰） | 可选 | y |

#### 3.7.3 基本用法

```bash
# 1. 创建指定大小的线性 LV（最常用）
sudo lvcreate -L 10G -n lv_data vg_data

# 2. 创建时指定 PE 数量
sudo lvcreate -l 2560 -n lv_data vg_data
# 2560 PE × 4 MiB = 10240 MiB = 10 GiB

# 3. 使用百分比（使用 VG 中 50% 的空间）
sudo lvcreate -l 50%VG -n lv_half vg_data

# 4. 使用 VG 中所有剩余空间
sudo lvcreate -l 100%FREE -n lv_all vg_data

# 5. 创建条带化 LV（数据分散到多个 PV，提升并行读性能）
sudo lvcreate -L 10G -i 2 -I 64k -n lv_stripe vg_data
# -i 2：跨 2 个 PV 条带化
# -I 64k：条带大小 64 KiB

# 6. 创建 LV 时不触发 udev（在脚本或容器中有时需要）
sudo lvcreate -L 10G -n lv_data vg_data --noudevsync

# 7. 创建精简池和精简卷（Thin Provisioning，见进阶延伸 6.3）
# sudo lvcreate -L 20G -T vg_data/thinpool
# sudo lvcreate -V 50G -T vg_data/thinpool -n thin_vol
```

### 3.10 lvextend：扩展逻辑卷

#### 3.10.1 功能

增加逻辑卷的大小。这是 LVM 最常用的操作之一——在线扩容，无需卸载文件系统。

**关键操作分为两步**（缺一不可）：
1. `lvextend` — 扩大 LV 本身的容量
2. `resize2fs`（ext4）或 `xfs_growfs`（XFS）— 扩大文件系统以使用新增空间

#### 3.10.2 参数说明

| 参数 | 说明 | 必选/可选 | 默认值 |
|------|------|----------|--------|
| `-L, --size [+]SIZE` | 扩展到指定大小（如 `15G`）或增加指定大小（如 `+5G`） | 必选 | - |
| `-l, --extents [+]NUMBER` | 指定 PE 数量或百分比（如 `+100%FREE`） | `-L` 或 `-l` 二选一 | - |
| `LV` | 目标逻辑卷路径 | 必选 | - |
| `-r, --resizefs` | 同时调整底层文件系统大小（需文件系统支持） | 可选 | 不自动调整 |
| `-f, --force` | 强制执行 | 可选 | 不强制 |

#### 3.10.3 基本用法

```bash
# 完整的在线扩容流程（ext4）

# 步骤 1：确认当前状态
df -h /mnt/data
sudo lvs vg_data/lv_data

# 步骤 2：确认 VG 中有足够的空闲空间
sudo vgs vg_data
# 查看 VFree 列，确保有足够空间

# 步骤 3：扩展 LV（增加 5G）
sudo lvextend -L +5G /dev/vg_data/lv_data
# 输出：Size of logical volume vg_data/lv_data changed from 10.00 GiB to 15.00 GiB.

# 步骤 4：扩展 ext4 文件系统（在线操作，无需卸载！）
sudo resize2fs /dev/vg_data/lv_data
# 输出：Resizing the filesystem on /dev/vg_data/lv_data to 3932160 (4k) blocks.

# 步骤 5：验证
df -h /mnt/data
sudo lvs vg_data/lv_data

# 一键操作（lvextend 自动调文件系统）
sudo lvextend -r -L +5G /dev/vg_data/lv_data
# -r 等同于 --resizefs，自动调用合适的文件系统调整工具

# 扩展 LV 到特定大小（不是增量，而是绝对值）
sudo lvextend -L 20G /dev/vg_data/lv_data

# 使用 VG 中所有剩余空间
sudo lvextend -l +100%FREE /dev/vg_data/lv_data
```

**XFS 文件系统的扩容**：

XFS 不支持 `resize2fs`，需使用 `xfs_growfs`。注意：XFS 只能扩容，不能缩减。

```bash
# XFS 扩容流程
sudo lvextend -L +5G /dev/vg_data/lv_xfs
sudo xfs_growfs /mnt/xfs_data
# xfs_growfs 必须指定挂载点（不是设备路径！）
```

### 3.11 lvreduce：缩减逻辑卷

#### 3.11.1 功能

减少逻辑卷的大小。**这是 LVM 操作中最危险的操作之一**，操作顺序错误将导致数据永久丢失。

#### 3.11.2 缩减的正确顺序（铁律）

```
ext4 缩减顺序（必须先缩减文件系统，再缩减 LV！）：
┌──────────────────────────────────────────────────────────────┐
│  1. umount LV              ← 卸载（ext4 在线缩减不推荐）       │
│  2. e2fsck -f LV            ← 强制检查文件系统                │
│  3. resize2fs LV NEW_SIZE   ← 先缩减文件系统                  │
│  4. lvreduce -L NEW_SIZE LV ← 再缩减逻辑卷                    │
│  5. mount LV                ← 重新挂载                        │
└──────────────────────────────────────────────────────────────┘

顺序铁律：缩减时，先文件系统后 LV；扩容时，先 LV 后文件系统。
记忆口诀：缩减"内→外"（文件系统层→LV层），扩容"外→内"（LV层→文件系统层）
```

#### 3.11.3 参数说明

| 参数 | 说明 | 必选/可选 | 默认值 |
|------|------|----------|--------|
| `-L, --size [-]SIZE` | 缩减到指定大小或减少指定大小（如 `-5G`） | 必选 | - |
| `-l, --extents [-]NUMBER` | 指定 PE 数量或百分比 | `-L` 或 `-l` 二选一 | - |
| `LV` | 目标逻辑卷路径 | 必选 | - |
| `-f, --force` | 强制执行（跳过确认提示） | 可选 | 交互确认 |
| `-r, --resizefs` | 同时调整底层文件系统大小 | 可选 | 不自动调整 |

#### 3.11.4 基本用法

```bash
# ext4 安全缩减的完整流程

# 假设 lv_data 当前为 10G，要缩减到 5G

# 步骤 1：卸载 LV
sudo umount /mnt/data

# 步骤 2：强制检查文件系统（修复任何不一致）
sudo e2fsck -f /dev/vg_data/lv_data
# 确认 e2fsck 返回 0（无错误）或 1（已自动修复错误）

# 步骤 3：先缩减文件系统到 5G（必须先做这一步！）
sudo resize2fs /dev/vg_data/lv_data 5G
# 输出：Resizing the filesystem on /dev/vg_data/lv_data to 1310720 (4k) blocks.

# 步骤 4：再缩减 LV（与文件系统大小匹配）
sudo lvreduce -L 5G /dev/vg_data/lv_data
# 提示确认：WARNING: Reducing active logical volume to 5.00 GiB.
# 输入 y 确认

# 步骤 5：检查文件系统（可选但推荐）
sudo e2fsck -f /dev/vg_data/lv_data

# 步骤 6：重新挂载
sudo mount /dev/vg_data/lv_data /mnt/data
df -h /mnt/data

# 注意：XFS 不支持缩减！如果创建的是 XFS 文件系统，
# 不能使用 lvreduce 缩减它，否则文件系统将被破坏。
```

### 3.12 lvresize：统一调整逻辑卷

#### 3.12.1 功能

`lvresize` 是 `lvextend` 和 `lvreduce` 的综合命令，既可以扩展也可以缩减 LV。它的行为取决于 `-L` 参数是否带有 `+` 或 `-` 前缀。

#### 3.12.2 参数说明

| 参数 | 说明 | 必选/可选 | 默认值 |
|------|------|----------|--------|
| `-L, --size SIZE` | `+5G`=扩展，`-5G`=缩减，`5G`=设为绝对值 | 必选 | - |
| `-l, --extents NUMBER` | PE 数量或百分比 | `-L` 或 `-l` 二选一 | - |
| `-r, --resizefs` | 同时调整底层文件系统 | 可选 | 不自动调整 |
| `LV` | 目标逻辑卷路径 | 必选 | - |

#### 3.12.3 基本用法

```bash
# 扩展 LV（等同于 lvextend -L +2G）
sudo lvresize -L +2G /dev/vg_data/lv_data

# 缩减 LV（等同于 lvreduce -L -2G）
# 注意：仍在挂载状态的 LV 缩减需要先卸载
sudo lvresize -L -2G /dev/vg_data/lv_data

# 设置绝对值
sudo lvresize -L 15G /dev/vg_data/lv_data

# 一键调整（含文件系统）
sudo lvresize -r -L +3G /dev/vg_data/lv_data
# -r 会调用 resize2fs（ext4）或 xfs_growfs（XFS）

# 使用百分比
sudo lvresize -l +50%FREE /dev/vg_data/lv_data
```

### 3.13 lvremove：删除逻辑卷

#### 3.13.1 功能

删除逻辑卷。此操作不可逆，LV 上的所有数据将被永久销毁。

#### 3.13.2 参数说明

| 参数 | 说明 | 必选/可选 | 默认值 |
|------|------|----------|--------|
| `LV` | 要删除的逻辑卷路径 | 必选 | - |
| `-f, --force` | 强制执行，不提示确认 | 可选 | 交互确认 |

#### 3.13.3 基本用法

```bash
# 删除 LV 前务必确认：
# 1. 已卸载（umount）
# 2. 已备份重要数据
# 3. 已从 /etc/fstab 中移除相关条目

# 确认 LV 状态
sudo lvs vg_data/lv_test
df -h | grep lv_test

# 卸载（如果已挂载）
sudo umount /mnt/test_mount

# 删除 LV
sudo lvremove /dev/vg_data/lv_test
# 提示确认：Do you really want to remove active logical volume vg_data/lv_test? [y/n]:
# 输入 y

# 强制删除（跳过确认）
sudo lvremove -f /dev/vg_data/lv_test

# 验证删除
sudo lvs vg_data
```

### 3.14 pvremove、vgremove：删除 PV 和 VG

虽然任务简报未明确列出，但完整理解 LVM 生命周期需要掌握删除操作。

```bash
# ===== 删除 VG =====
# 前提：VG 内没有任何 LV
sudo vgremove vg_data
# 提示确认

# ===== 删除 PV =====
# 前提：PV 不属于任何 VG
sudo pvremove /dev/sdb1
# 清除 PV 上的 LVM 元数据

# ===== 完整的 LVM 拆卸流程（从 LV 到 PV）=====
# 1. 卸载所有 LV
sudo umount /mnt/data

# 2. 删除所有 LV
sudo lvremove -f /dev/vg_data/lv_data
sudo lvremove -f /dev/vg_data/lv_logs

# 3. 停用 VG（可选）
sudo vgchange -an vg_data

# 4. 删除 VG
sudo vgremove vg_data

# 5. 删除 PV 上的 LVM 信息
sudo pvremove /dev/sdb1 /dev/sdc1

# 6. 验证
sudo pvs
# 应该为空或 PV 已消失

# ===== 清理分区（如果需要彻底还原）=====
sudo wipefs -a /dev/sdb1     # 清除文件系统签名
sudo parted /dev/sdb rm 1    # 删除分区
```

**其他常用辅助命令**：

| 命令 | 用途 |
|------|------|
| `vgextend VG PV` | 向卷组添加新的物理卷（扩容 VG） |
| `vgreduce VG PV` | 从卷组中移除物理卷（需先迁移数据 `pvmove`） |
| `pvmove PV` | 将 PV 上的数据迁移到其他 PV |
| `pvresize PV` | 调整 PV 的大小（当底层分区大小改变后） |
| `vgchange -ay/-an VG` | 激活/停用卷组 |
| `lvchange -ay/-an LV` | 激活/停用逻辑卷 |

### 3.15 LVM 快照操作

LVM 快照是本章的高级重点。以下展示完整的快照创建、验证、回滚流程。

#### 3.15.1 创建快照

```bash
# 创建快照的基本命令
# lvcreate -s -L <快照大小> -n <快照名称> <原始LV路径>

# -s  = --snapshot，创建快照
# -L  = 快照卷的大小（用于存储 COW 数据）
# -n  = 快照的名称

# 示例：为 lv_data 创建一个 2G 的快照
sudo lvcreate -s -L 2G -n lv_data_snap_20260730 /dev/vg_data/lv_data

# 查看快照
sudo lvs -a
# 输出示例：
# LV                  VG      Attr       LSize  Pool Origin  Data%
# lv_data             vg_data owi-aos--- 10.00g
# lv_data_snap_20260730 vg_data swi-a-s---  2.00g      lv_data 0.00
#                                            ^^^              ^^^^
#                                      Attr 中 s=snapshot     Data%=COW使用率
```

#### 3.15.2 使用快照进行备份

```bash
# 场景：为数据库备份创建一致性快照

# 1. 暂停数据库写入（或使用 FLUSH TABLES WITH READ LOCK）
#    （不同数据库命令不同，这里以 MySQL 为例）
# mysql -e "FLUSH TABLES WITH READ LOCK; SYSTEM sleep 2; UNLOCK TABLES;"

# 2. 创建快照（秒级完成）
sudo lvcreate -s -L 5G -n lv_mysql_snap /dev/vg_data/lv_mysql

# 3. 挂载快照（只读）
sudo mkdir -p /mnt/mysql_snap
sudo mount -o ro /dev/vg_data/lv_mysql_snap /mnt/mysql_snap

# 4. 从快照备份数据
sudo rsync -av /mnt/mysql_snap/ /backup/mysql_$(date +%Y%m%d)/

# 5. 卸载并删除快照
sudo umount /mnt/mysql_snap
sudo lvremove -f /dev/vg_data/lv_mysql_snap
```

#### 3.15.3 快照回滚（恢复）

```bash
# 场景：软件升级失败，需要回滚系统 LV
# 方法：使用 lvconvert --merge

# 1. 升级前已创建快照 lv_root_snap

# 2. 合并快照（将原始 LV 回滚到快照创建时的状态）
sudo lvconvert --merge /dev/vg_system/lv_root_snap
# 注意：合并是即时完成的（标记操作），但实际数据恢复在后台进行
# 如果 LV 正在使用中（如根分区），合并将在下次重启时完成

# 3. 如果快照的原始卷是根分区或其他活跃卷
#    合并已被调度，需要重启
sudo reboot

# 4. 重启后验证
sudo lvs -a
# 快照应该已自动删除（合并后快照会被删除）
```

### 练习 27.7：LVM 信息收集与监控

**题目：**

编写一个脚本，实现以下功能：
（1）显示所有 PV 的名称、大小、所属 VG、空闲空间。
（2）显示所有 VG 的名称、PV 数量、总大小、空闲空间、空闲百分比。

## 5. 常见错误与排错

### 5.1 错误：缩减时先缩减 LV 再缩减文件系统

这是 LVM 操作中**数据丢失的首要原因**。

```bash
# 致命错误示例：
sudo lvreduce -L 5G /dev/vg_data/lv_data   # ← 先缩减了 LV
sudo e2fsck -f /dev/vg_data/lv_data         # ← 文件系统认为空间还是 10G！
# 结果：文件系统的数据块超出了 LV 的实际边界 → 数据损坏

# 正确顺序：
sudo umount /mnt/data
sudo e2fsck -f /dev/vg_data/lv_data         # ← 1. 检查
sudo resize2fs /dev/vg_data/lv_data 5G      # ← 2. 先缩文件系统
sudo lvreduce -L 5G /dev/vg_data/lv_data    # ← 3. 再缩 LV

# 记忆口诀：缩减时"内→外"，扩容时"外→内"
```

### 5.2 错误：尝试缩减 XFS 文件系统

XFS 文件系统**不支持缩减**，这是设计决定而不是 bug。如果强行缩减 LV 而文件系统是 XFS，数据立即损坏。

```bash
# 致命错误：
sudo mkfs.xfs /dev/vg_data/lv_xfs_data     # 创建了 XFS
# ...后来想缩减...
sudo lvreduce -L -5G /dev/vg_data/lv_xfs_data   # ← 数据损坏！

# 排错方法：
# 1. 检查文件系统类型
df -hT /mnt/xfs_data
# 或
sudo blkid /dev/vg_data/lv_xfs_data

# 2. 如果 Type 是 xfs，记住：不能缩减
# 3. 如果确实需要更小的 XFS 卷，只能：
#    - 备份数据 → 删除 LV → 创建更小的 LV → 创建 XFS → 恢复数据

# 预防：创建 LV 前想清楚——如果将来可能需要缩减，选 ext4 而不是 XFS
```

### 5.3 错误：VG 剩余空间不足

```bash
# 症状：
sudo lvextend -L +10G /dev/vg_data/lv_data
# 错误：Insufficient free space: 256 extents needed, but only 128 available

# 排查：
sudo vgs vg_data
# 查看 VFree 列 —— 这是 VG 中真正可以分配的空间

# VFree 可能小于预期的原因：
# 1. 被快照占用（快照也使用 VG 空间）
sudo lvs -a vg_data
# 查看是否有快照存在（Attr 中有 s 的）

# 2. PE 对齐浪费（部分 PE 因为对齐约束而不可用）

# 解决方法：
# 方法 1：添加新 PV 到 VG
sudo vgextend vg_data /dev/sdc1

# 方法 2：删除不需要的快照释放空间
sudo lvremove vg_data/old_snapshot

# 方法 3：缩减其他未使用的 LV
# （先缩减文件系统 → 再缩减 LV）
```

### 5.4 错误：快照空间耗尽

```bash
# 症状：快照相关的 LV 操作失败或 I/O 错误
# dmesg 中可能出现：device-mapper: snapshots: Invalidating snapshot

# 排查：
sudo lvs -a vg_data
# 查看快照的 Data% 列 —— 如果达到 100%，快照已失效

# 预防：
# 1. 创建快照时分配足够空间（推荐为原始卷的 10-20%）
# 2. 监控快照使用率
watch -n 10 'sudo lvs -a -o lv_name,data_percent,lv_size vg_data'

# 3. 如果快照用完了，唯一的办法是删除并重新创建
sudo lvremove -f vg_data/depleted_snapshot

# 4. 不能扩展已创建的快照卷
# 如果快照经常耗尽，创建新的快照时增大 -L 值
```

### 5.5 错误：系统启动时 LVM 卷未激活

```bash
# 症状：重启后 LV 设备文件不存在，无法挂载

# 排查步骤：
# 1. 检查 VG 和 LV 状态
sudo vgdisplay
sudo lvdisplay

# 2. 如果 LV Status 显示 "NOT available"
#    手动激活 VG 和 LV
sudo vgchange -ay vg_data
#    -a y = activate yes，激活 VG 内所有 LV

sudo lvchange -ay vg_data/lv_data
#    激活单个 LV

# 3. 如果每次启动都需要手动激活，检查 lvm2-lvmetad 服务
sudo systemctl status lvm2-lvmetad
sudo systemctl enable lvm2-lvmetad

# 4. 检查 initramfs 中是否包含 LVM 模块
sudo update-initramfs -u

# 5. 如果是根分区的 LV 问题（无法启动），进入 recovery mode 或使用 Live CD
#    - 用 Live CD 启动
#    - sudo vgchange -ay
#    - 挂载根 LV，chroot 修复
```

### 5.6 错误：`pvcreate` 时提示 "Device /dev/sdX excluded by a filter"

```bash
# 症状：
sudo pvcreate /dev/sdb1
# 错误：Device /dev/sdb1 excluded by a filter.

# 原因：LVM 的全局配置文件 /etc/lvm/lvm.conf 中的 filter 设置
# 可能排除了某些设备（例如所有 sd* 设备，或特定的磁盘）

# 排查：
grep filter /etc/lvm/lvm.conf
# 或
sudo lvm config --type full devices/filter

# 常见的 filter 设置：
# filter = [ "a|.*|" ]              ← 允许所有设备
# filter = [ "r|/dev/sda|" ]         ← 排除 /dev/sda
# filter = [ "a|/dev/sd|", "r|.*|" ] ← 只允许 sd* 设备

# 解决方法：
# 1. 检查 filter 设置
sudo lvmconfig devices/filter

# 2. 临时测试（不加 filter）
sudo pvcreate --config 'devices { filter = ["a|.*|"] }' /dev/sdb1

# 3. 永久修改（编辑 /etc/lvm/lvm.conf）
# sudo nano /etc/lvm/lvm.conf
# 找到 filter 行，调整为包含你的设备
# 典型配置：filter = [ "a|.*|" ]
```

### 5.7 错误：LVM 元数据不一致

```bash
# 症状：
sudo vgdisplay vg_data
# 错误：Volume group "vg_data" not found
# 但实际上 PV 上有 vg_data 的元数据

# 或
sudo pvs
# 某个 PV 的 VG 列显示 "unknown" 或 "[unknown]"

# 排查：
# 1. 扫描所有 PV
sudo pvscan --cache

# 2. 重新扫描 VG
sudo vgscan --mknodes

# 3. 检查 PV 的 LVM 头部信息
sudo pvck /dev/sdb1

# 4. 恢复 VG 元数据（极其危险的操作，仅在确认磁盘无问题时进行）
# 先查看备份
ls -la /etc/lvm/backup/
sudo cat /etc/lvm/backup/vg_data

# 从备份恢复
sudo vgcfgrestore -f /etc/lvm/backup/vg_data vg_data

# 预防：在修改 LVM 结构后自动备份（lvm.conf 中 backup = 1 默认开启）
```

## 6. 进阶延伸

### 6.1 数据迁移：`pvmove`——在线换盘

在不停机的情况下将某个 PV 上的所有数据迁移到其他 PV。这是更换旧磁盘或在存储阵列之间迁移数据的标准方法。

```bash
# 场景：/dev/sdb 的 S.M.A.R.T. 数据报错，需要在线更换

# 1. 确认 VG 中有其他可用的 PV 且空间足够
sudo pvs
sudo vgs vg_data

# 2. 添加新磁盘
sudo pvcreate /dev/sdd1
sudo vgextend vg_data /dev/sdd1

# 3. 在线迁移数据（从旧盘到新盘）
sudo pvmove /dev/sdb1 /dev/sdd1
# 这个过程可能很慢（取决于数据量），但完全在线——数据持续可读可写

# 4. 从 VG 中移除旧盘
sudo vgreduce vg_data /dev/sdb1

# 5. 清理旧盘上的 PV 元数据
sudo pvremove /dev/sdb1

# 6. 物理移除旧盘（如果硬件支持热插拔）
echo "数据已迁移，可以安全移除 /dev/sdb"

# 监控迁移进度
sudo pvmove -i 5  # 每 5 秒报告进度
```

### 6.2 LVM 条带化与镜像

LVM 不只是"合并空间"，还提供软件级别的条带化（Striping）和镜像（Mirroring）。

```bash
# ===== 条带化（提升读写性能）=====
# 将数据分散写入多个 PV，取得接近 RAID 0 的并行读写性能
sudo lvcreate -L 50G -i 3 -I 128k -n lv_striped vg_data
# -i 3：跨 3 个 PV 条带化（VG 中至少要有 3 个 PV）
# -I 128k：条带大小 128 KiB

# 查看条带化设置
sudo lvdisplay -m vg_data/lv_striped

# ===== 镜像（数据冗余）=====
# 创建 RAID 1 镜像 LV（需要 2 个 PV 或更多）
sudo lvcreate -L 20G -m 1 -n lv_mirror vg_data
# -m 1 = 1 个额外副本（总共 2 份数据）
# VG 中至少需要 2 个 PV（每个副本放在不同 PV 上）

# 查看镜像状态
sudo lvdisplay -m vg_data/lv_mirror

# ===== RAID 5 LV =====
# 需要至少 3 个 PV
sudo lvcreate --type raid5 -L 50G -i 2 -n lv_raid5 vg_data
# -i 2 = 数据块分布在 2 个 PV 上（+1 个校验 PV = 总共 3 个 PV）
```

### 6.3 精简配置（Thin Provisioning）

Thin Provisioning 允许创建"看起来很大"的 LV，但只在数据实际写入时才占用物理空间。这类似于虚拟机的"精简置备"磁盘。

```
传统（厚置备）LV：                  精简（Thin）LV：
┌─────────────────────┐           ┌─────────────────────┐
│ LV 100G             │           │ Virtual LV 100G     │
│ ├── 已写 20G 数据    │           │ ├── 已写 20G 数据    │
│ └── 80G 浪费         │           │ └── 80G 未分配       │
│                     │           │   （不占物理空间）    │
│ 占 VG 100G 空间      │           │ 占 Thin Pool 20G    │
└─────────────────────┘           └─────────────────────┘
```

```bash
# 1. 创建精简池（Thin Pool）
sudo lvcreate -L 20G -T vg_data/thinpool
# -T = --thin（创建精简池）
# 精简池是"实际的存储池"，20G 是池的物理大小

# 2. 在精简池中创建精简卷（可以"超分配"）
sudo lvcreate -V 100G -T vg_data/thinpool -n thin_vol1
sudo lvcreate -V 100G -T vg_data/thinpool -n thin_vol2
# -V 100G = 虚拟大小（看起来有 100G）
# 实际物理空间由 thinpool 提供（只有 20G！）

# 3. 格式化和挂载
sudo mkfs.ext4 /dev/vg_data/thin_vol1
sudo mount /dev/vg_data/thin_vol1 /mnt/thin1

# 4. 查看精简池使用率
sudo lvs -a vg_data
# 关注 Data% 列——精简池的物理空间使用率
# 如果达到 100%，所有精简卷的写入将失败

# 5. 扩展精简池
sudo lvextend -L +10G vg_data/thinpool
# 如果 VG 中有空间，会自动从 VG 中分配

# 警告：监控精简池使用率至关重要！
# 在 cron 中设置监控脚本，池使用超过 80% 时告警
watch -n 30 'sudo lvs -a -o lv_name,data_percent vg_data'
```

### 6.4 LVM 性能调优

```bash
# 1. 选择正确的 PE 大小
# 创建 VG 时选择合适的 PE 大小可以提升性能
sudo vgcreate -s 4M vg_performance /dev/nvme0n1p1
# SSD 建议 4M，HDD 大容量建议 8M 或 16M

# 2. 数据对齐（对 SSD 至关重要）
# 创建 PV 时指定对齐
sudo pvcreate --dataalignment 1M /dev/nvme0n1p1
# 或创建分区时确保起始扇区对齐到 1 MiB
sudo parted /dev/nvme0n1 mkpart primary 1MiB 100%

# 3. 条带化匹配物理磁盘数
# 如果 VG 中有 4 个 PV（4 块独立磁盘），条带化到 4 个 PV
sudo lvcreate -L 100G -i 4 -I 256k -n lv_fast vg_data

# 4. 调整 read-ahead 设置
sudo lvchange -r 2048 vg_data/lv_data
# -r 设置预读扇区数（Read Ahead），对顺序读取有显著影响

# 5. 查看 LV 的预读设置
sudo lvdisplay vg_data/lv_data | grep "Read ahead"

# 6. 定期检查碎片情况（对条带化 LV）
sudo lvs -o lv_name,segtype,stripes,stripe_size,devices vg_data
```

### 6.5 LVM 与加密：LUKS on LVM

结合 LUKS（Linux Unified Key Setup）加密，可以实现安全的企业存储方案。

```bash
# 方案 A：LUKS 在 LVM 之上（加密整个 VG 或 LV）
# 优点：可以为不同 LV 使用不同密钥，更灵活

# 方案 B：LVM 在 LUKS 之上（对整个磁盘加密后交给 LVM 管理）
# 优点：一个密钥管理整个磁盘，操作更简单

# 典型配置（方案 B，最常用）：
# 1. 加密分区
sudo cryptsetup luksFormat /dev/sdb1

# 2. 打开加密设备
sudo cryptsetup open /dev/sdb1 encrypted_disk

# 3. 将解密后的设备作为 PV 使用
sudo pvcreate /dev/mapper/encrypted_disk
sudo vgextend vg_data /dev/mapper/encrypted_disk

# 这样 VG 中的所有数据都是加密存储的
```

### 6.6 开机自动挂载 LVM 逻辑卷

修改 `/etc/fstab` 使 LVM 逻辑卷在开机时自动挂载。

```bash
# 1. 获取 LV 的 UUID
sudo blkid /dev/vg_data/lv_data
# 或使用设备路径
# /dev/vg_data/lv_data 或 /dev/mapper/vg_data-lv_data

# 2. 创建挂载点
sudo mkdir -p /data

# 3. 编辑 /etc/fstab
# 推荐使用设备路径（/dev/mapper/vg-lv 格式）：

# UUID=<uuid-from-blkid>  /data  ext4  defaults  0  2

sudo reboot
```

### 6.7 从传统分区迁移到 LVM

如果系统当前使用传统分区，可以将其迁移到 LVM 而不丢失数据。

```bash
# 注意：这是高级操作，务必先完整备份！

# 场景：/dev/sdb1（ext4，50G，传统分区，挂载到 /data）
# 目标：迁移到 LVM

# 1. 创建与现有分区大小相同的 LV（在另一块盘上）
sudo pvcreate /dev/sdc1
sudo vgcreate vg_data /dev/sdc1
sudo lvcreate -L 51G -n lv_data vg_data   # 略大于原分区
sudo mkfs.ext4 /dev/vg_data/lv_data

# 2. 复制数据
sudo mkdir -p /mnt/new_data
sudo mount /dev/vg_data/lv_data /mnt/new_data
sudo rsync -avxHAX /data/ /mnt/new_data/

# 3. 切换
sudo umount /data
sudo umount /mnt/new_data
sudo mount /dev/vg_data/lv_data /data

# 4. 更新 /etc/fstab
# 将 /dev/sdb1 的行替换为 /dev/mapper/vg_data-lv_data

# 5. 确认一切正常后，可以将旧分区加入 VG
sudo pvcreate /dev/sdb1
sudo vgextend vg_data /dev/sdb1
# 现在 VG 有了原分区的空间
```

### 6.8 ZFS 速览：LVM 的替代品

虽然本章以 LVM 为主角，但 ZFS 作为集成了卷管理和文件系统的一体化方案，值得简要了解。

```bash
# 安装 ZFS（Ubuntu 24.04）
sudo apt install -y zfsutils-linux

# ZFS 不需要 LVM——它自己管理存储池

# 创建存储池（相当于 LVM 的 VG）
sudo zpool create mypool mirror /dev/sdb /dev/sdc
# 创建一个镜像池（RAID 1 效果）

# 创建文件系统（相当于 LVM 的 LV + mkfs 一步完成）
sudo zfs create mypool/data
# 自动挂载到 /mypool/data

# 设置属性
sudo zfs set compression=lz4 mypool/data          # 透明压缩
sudo zfs set atime=off mypool/data                # 关闭访问时间更新（提升性能）

# 创建快照
sudo zfs snapshot mypool/data@before-upgrade      # 秒级完成

# 回滚快照
sudo zfs rollback mypool/data@before-upgrade      # 秒级完成

# 查看所有文件系统和快照
zfs list -t all
```

**LVM vs ZFS 选择建议：**

| 考量维度 | 推荐 |
|---------|------|
| 内置内核支持、无需额外安装 | LVM |
| 数据完整性校验、自动修复 | ZFS |
| 极致性能（无 CoW 开销） | LVM + XFS |
| 快照、压缩、去重一站解决 | ZFS |
| Ubuntu 标准安装、广泛社区 | LVM |
| NAS / 大容量归档 | ZFS |
| 与 virt-manager/KVM 集成 | LVM |
| 复杂存储拓扑、混合 RAID | ZFS |
