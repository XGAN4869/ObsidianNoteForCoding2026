## 1. 概述

### 1.1 从"定时执行"到"理解开机"

第 31 章你掌握了定时任务——cron 让系统按计划自动运行，systemd timer 提供了现代替代方案。六章系统篇走过来，你学会了管理磁盘、安装软件、启停服务、查看日志、编排任务。但有一个根本问题尚未回答：

- "按下电源键后，屏幕上那一串串滚动的文字是什么？"
- "GRUB 是什么？为什么开机时会显示一个选择菜单？"
- "BIOS 和 UEFI 有什么区别？我的电脑用的是哪一个？"
- "内核（Kernel）是怎么被加载进来的？initramfs 起什么作用？"
- "systemd 作为 PID 1 到底做了哪些事情？"
- "服务启动的顺序由谁决定？依赖关系在哪里定义？"
- "系统启动卡住了——怎么进入救援模式修复？"
- "`dmesg` 输出的那几千行信息从哪里来？怎么看懂关键部分？"

这些问题的核心只有一个：**启动流程（Boot Process）**——从按下电源键到出现登录提示符，Linux 系统经历的一段精密编排的旅程。如果说前面六章教会你"使用和维护运行中的系统"，那么本章将回答一个更底层的问题：**这系统本身是怎么跑起来的？**

### 1.3 历史背景：从 BIOS 到 UEFI，从 SysV Init 到 systemd

启动流程涉及两个维度的"新旧交替"——固件层的 BIOS→UEFI 和初始化层的 SysV→systemd：

```
固件层演化（~1981 - 至今）：                    初始化层演化（~1983 - 至今）：
────────────────────────                        ────────────────────────────
1981  IBM PC 引入 BIOS（Basic I/O System）      1983  AT&T Unix System V：SysV Init
      16 位实模式，1MB 地址空间                        串行启动，/etc/init.d/ 脚本
      主引导记录 MBR（Master Boot Record）             runlevel 0-6
      Legacy 引导，无安全引导机制                      依赖手动编号（S01, S02...）
                                                    │
2005  Intel 提出 EFI（Extensible Firmware）     2010  Lennart Poettering 发布 systemd
      后演变为 UEFI Forum 标准                    2015  Debian/Ubuntu 切换至 systemd
                                                    │
2012  Windows 8 要求 UEFI + Secure Boot         Ubuntu 24.04：systemd 255
      推动 UEFI 成为 PC 标配                          并行启动、声明式配置、cgroup 隔离
                                                     原生支持 socket 激活、timer、日志
2024  UEFI 2.10, 几乎所有新主板默认 UEFI
      GPT（GUID Partition Table）分区表
      Secure Boot, TPM 2.0 支持
```

> **为什么启动流程对系统管理员很重要？** 因为出问题总是在最糟糕的时候——凌晨三点服务器重启后卡在 GRUB 提示符、内核更新后驱动不兼容导致启动失败、磁盘 UUID 变更后找不到根分区。理解启动流程的每一步，你才能在故障发生时准确定位问题出在哪一环。

### 2.2 BIOS vs UEFI：两种固件标准深度对比

这是启动流程中最容易混淆的概念之一。BIOS 和 UEFI 不仅仅是"新旧的差别"，它们决定了分区表格式、引导方式、安全机制等一系列底层设计。

#### 2.2.1 核心差异对照表

| 特性 | BIOS（Legacy Boot） | UEFI（Unified Extensible Firmware Interface） |
|------|--------------------|----------------------------------------------|
| **诞生年份** | 1981（IBM PC） | 2005（Intel EFI），后成为 UEFI Forum 标准 |
| **运行模式** | 16 位实模式（Real Mode） | 32 位或 64 位保护模式（Protected Mode） |
| **寻址空间** | 最大 1 MB | 理论上无限制（取决于实现） |
| **分区表** | MBR（Master Boot Record） | GPT（GUID Partition Table） |
| **最大磁盘容量** | 2 TB（MBR 限制） | 9.4 ZB（GPT 限制） |
| **最大分区数** | 4 个主分区（或 3 主 + 1 扩展） | 128 个主分区（Windows 限制，GPT 标准支持更多） |
| **引导方式** | 读取磁盘第一个扇区（LBA 0），执行前 446 字节代码 | 读取 ESP（EFI System Partition）中的 .efi 可执行文件 |
| **引导文件位置** | MBR + 启动扇区，散布在磁盘上 | 集中在 ESP（FAT32 格式，通常是 /boot/efi） |
| **Secure Boot** | 不支持 | 支持（验证引导链签名，防止 bootkit） |
| **启动速度** | 较慢（串行初始化） | 较快（支持并行初始化） |
| **图形界面** | 文本菜单（蓝底白字） | 支持图形化设置界面（鼠标操作） |
| **网络功能** | 通常不支持 | 支持网络启动（PXE over IPv4/IPv6） |
| **分区标识** | 通过分区类型码（如 0x83 = Linux） | 通过 GUID（如 0FC63DAF-... = Linux 文件系统） |
| **多系统支持** | 各自写入 MBR，容易互相覆盖 | 各自在 ESP 中放一个 .efi 文件，互不冲突 |
| **兼容性** | 几乎所有 x86 系统都支持 | 2012 年之后的主板标配 |

#### 2.2.2 BIOS 引导流程详解

```
BIOS（Legacy Boot）引导的完整过程：
════════════════════════════════════════════════════════════════

  [开机] → CPU 从复位向量（Reset Vector）0xFFFFFFF0 开始执行
                │
                ▼
            BIOS 自检（POST）
            ├── 检测 CPU、内存、键盘、显示器
            ├── 初始化芯片组和基本 I/O
            └── 枚举 PCI 总线，发现存储控制器
                │
                ▼
            读取 BIOS 设置中的启动顺序（Boot Order）
            例如：USB → HDD → Network → CD-ROM
                │
                ▼
            找到第一个可引导的磁盘
            读取该磁盘的第一个扇区（LBA 0，512 字节）
                │
         ┌──────┴──────┐
         │  MBR 结构    │
         │  ┌─────────┐ │
         │  │ 446 字节 │ │ ← 引导代码（Bootstrap Code）
         │  │ 64 字节  │ │ ← 分区表（4 条记录，每条 16 字节）
         │  │ 2 字节   │ │ ← 引导签名 0x55AA
         │  └─────────┘ │
         └──────────────┘
                │
                ▼
            BIOS 验证 0x55AA → 将 446 字节引导代码加载到内存 0x7C00
            跳转执行
                │
                ▼
            引导代码查找活动分区（Active Partition，引导标志 = 0x80）
            读取活动分区的第一个扇区（VBR - Volume Boot Record）
                │
                ▼
            VBR 中的代码加载 GRUB2 的 core.img
            （core.img 位置在安装 GRUB 时写入 MBR 和第一个分区之间的
             "MBR Gap"，通常是扇区 1-63 或 1-2047）
                │
                ▼
            GRUB2 core.img 读取 /boot/grub/ 下的模块和 grub.cfg
                │
                ▼
            GRUB2 加载内核（vmlinuz）和 initramfs（initrd.img）
```

> **MBR Gap：** 在 MBR（LBA 0）和第一个分区起始位置之间，传统上预留了 63 个扇区（约 31KB）或 2047 个扇区（约 1MB，现代标准）。GRUB2 的 core.img 就藏在这个间隙中。这就是为什么 BIOS 模式下 GRUB 安装需要这个"间隙"——GPT 分区表没有这个间隙，所以 BIOS + GPT 的组合需要单独创建一个 BIOS Boot Partition。

#### 2.2.3 UEFI 引导流程详解

```
UEFI 引导的完整过程：
════════════════════════════════════════════════════════════════

  [开机] → UEFI 固件初始化（类似 BIOS POST，但更现代化）
                │
                ▼
            UEFI 读取 NVRAM 中的启动项（Boot#### 变量）
            启动项示例：
              Boot0001* ubuntu         HD(1,GPT,...)/EFI/ubuntu/grubx64.efi
              Boot0002* Windows Boot Manager  HD(1,GPT,...)/EFI/Microsoft/Boot/bootmgfw.efi
              Boot0003* UEFI: USB Drive       ...
                │
                ▼
            按 BootOrder 变量指定的顺序尝试启动项
                │
                ▼
            找到 ESP（EFI System Partition）
            ESP 必须格式化为 FAT32（或 FAT16/FAT12）
            包含标志：EFI System Partition GUID（C12A7328-F81F-11D2-BA4B-00A0C9693D93）
                │
                ▼
            从 ESP 中读取 .efi 文件并执行
            /EFI/ubuntu/grubx64.efi → GRUB2 的 EFI 可执行文件
            （Secure Boot 开启时，使用 shimx64.efi → grubx64.efi 链式验证）
                │
                ▼
            GRUB2 EFI 版本读取 /boot/grub/grub.cfg
            （注意：grub.cfg 在根文件系统的 /boot 下，不在 ESP 中）
                │
                ▼
            GRUB2 通过 UEFI 协议加载内核和 initramfs
            （UEFI 提供了标准化的文件读写、图形显示等服务）
```

#### 2.2.4 GPT 分区表结构

```
GPT（GUID Partition Table）磁盘布局：
════════════════════════════════════════════════════════════════

  LBA 0       ┌──────────────────────────┐
              │  保护性 MBR                │  ← 防止老旧工具认为磁盘是空的
              │  （Protective MBR）        │     只定义了一个 0xEE 类型的分区
              │  512 字节                  │
              └──────────────────────────┘
  LBA 1       ┌──────────────────────────┐
              │  GPT 头部                  │
              │  （GPT Header）            │  ← "EFI PART" 签名
              │  包含：分区表起始 LBA、     │     分区表 CRC32 校验
              │  分区数量、分区条目大小      │
              └──────────────────────────┘
  LBA 2-33    ┌──────────────────────────┐
              │  分区条目数组               │
              │  （Partition Entry Array） │  ← 每个条目 128 字节
              │  通常 128 个条目            │     包含：分区类型 GUID、
              │                            │     唯一分区 GUID、起始/结束 LBA、
              │                            │     属性标志、分区名称（UTF-16）
              └──────────────────────────┘
  LBA 34-...  ┌──────────────────────────┐
              │  实际分区数据               │
              │  ESP（通常第一个分区）       │  ← 大小通常 100MB-1GB
              │  根分区、/home、swap 等     │     FAT32 格式
              └──────────────────────────┘
  倒数 33-1   ┌──────────────────────────┐
              │  备份分区条目数组           │  ← GPT 的冗余机制
              └──────────────────────────┘
  最后一扇区  ┌──────────────────────────┐
              │  备份 GPT 头部             │
              └──────────────────────────┘
```

**Ubuntu 24.04 典型 GPT 分区布局：**

```bash
# 查看 GPT 分区表
sudo gdisk -l /dev/sda
```

典型输出：

```
Number  Start (sector)    End (sector)  Size       Code  Name
   1            2048         1050623   512.0 MiB   EF00  EFI System Partition
   2         1050624        ...        ...        8300  Linux filesystem
```

> **Code EF00** 是 GPT 中 EFI System Partition 的分区类型 GUID 简写（gdisk 内部使用的编码）。

#### 2.2.5 Secure Boot 工作流程

```
Secure Boot 验证链：
════════════════════════════════════════════════════════════════

  UEFI 固件
  ┌──────────────────────────────────────┐
  │  数据库：                              │
  │  ┌────────┐  ┌──────────┐            │
  │  │  db    │  │   dbx    │            │
  │  │(白名单) │  │ (黑名单)  │            │
  │  └────────┘  └──────────┘            │
  │  ┌────────┐  ┌──────────┐            │
  │  │  KEK   │  │   PK     │            │
  │  │(密钥交换│  │(平台密钥)│            │
  │  │  密钥)  │  │          │            │
  │  └────────┘  └──────────┘            │
  └──────────────────────────────────────┘
           │
           │ 验证签名
           ▼
  ┌──────────────────┐
  │  shimx64.efi     │  ← 由 Microsoft 签名的第一级引导程序
  │  （Shim）         │     在 db 白名单中（Microsoft 证书）
  │  Canonical 维护   │     验证下一级的签名
  └──────────────────┘
           │
           │ 验证 GRUB 签名（Canonical 密钥）
           ▼
  ┌──────────────────┐
  │  grubx64.efi     │  ← 由 Canonical 签名的 GRUB2
  │  （GRUB2 EFI）    │     放在 ESP 中
  └──────────────────┘
           │
           │ 加载（GRUB 本身不验证内核签名——如果启用 lockdown）
           ▼
  ┌──────────────────┐
  │  vmlinuz         │  ← Linux 内核
  │  （内核镜像）      │     在 Secure Boot 模式下，内核也应被签名
  └──────────────────┘
```

> **安全提示：** Secure Boot 不是万能的。它的主要防御对象是 bootkit（在操作系统启动前注入恶意代码的攻击方式）。如果你需要安装没有签名的第三方内核模块（如 NVIDIA 驱动、VirtualBox 内核模块），可能需要注册自己的 MOK（Machine Owner Key）或临时关闭 Secure Boot。

#### 2.2.6 如何判断你的系统用的哪种引导

```bash
# 方法 1：检查 /sys/firmware/efi 目录是否存在
# 这个目录只在 UEFI 引导时存在（由内核的 efivarfs 文件系统挂载）
ls /sys/firmware/efi/
# 如果目录存在且有内容 → UEFI 引导
# 如果 "No such file or directory" → BIOS（Legacy）引导

# 方法 2：使用 efibootmgr 查看 UEFI 启动项
efibootmgr
# UEFI 引导时输出：
# BootCurrent: 0001
# Timeout: 10 seconds
# BootOrder: 0001,0002,0003
# Boot0001* ubuntu
# Boot0002* Windows Boot Manager
#
# BIOS 引导时输出：
# EFI variables are not supported on this system.

# 方法 3：检查分区表类型
sudo fdisk -l /dev/sda | grep "Disklabel type"
# Disklabel type: gpt  ← 通常意味着 UEFI（但不绝对，BIOS+GPT 也合法）
# Disklabel type: dos  ← 通常意味着 BIOS

# 方法 4：检查是否有 ESP
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT,PARTTYPE | grep -i "C12A7328"
# 有输出 → 存在 ESP → UEFI 引导
# 无输出 → 可能没有 ESP → BIOS 引导
```

### 2.3 GRUB2 架构：引导加载器的多阶段设计

GRUB2（GRand Unified Bootloader version 2）是 Ubuntu 的默认引导加载器。它之所以叫"Grand Unified"，是因为它支持从几乎任何文件系统和任何操作系统引导——通过一套模块化的阶段式加载机制。

#### 2.3.1 GRUB2 的阶段结构

```
GRUB2 的四层加载模型：
════════════════════════════════════════════════════════════════

  ┌──────────────────────────────────────────────────────┐
  │  Stage 1：boot.img（引导扇区）                         │
  │  ─────────────────────────────                        │
  │  大小：446 字节（BIOS）或 .efi 文件（UEFI）             │
  │  位置：MBR 引导代码区（BIOS）或 ESP（UEFI）             │
  │  任务：加载 Stage 1.5 或直接加载 Stage 2                │
  │  能力：几乎为零——BIOS 下只有 446 字节                    │
  │        连文件系统都不认识，只懂 LBA 地址                  │
  └──────────────────────────┬───────────────────────────┘
                             │
                             ▼
  ┌──────────────────────────────────────────────────────┐
  │  Stage 1.5：core.img 中的文件系统驱动（BIOS 特有）      │
  │  ─────────────────────────────                        │
  │  位置：MBR Gap（LBA 1-2047）                           │
  │  任务：加载合适的文件系统驱动模块                       │
  │        因为 /boot/grub/ 可能在 ext4、XFS、Btrfs 上     │
  │        而 core.img 需要读取 /boot/grub/ 下的文件        │
  │  关键模块：ext2.mod, xfs.mod, btrfs.mod 等              │
  │  注意：UEFI 下不需要 Stage 1.5，因为 UEFI 固件本身      │
  │        提供 FAT 驱动来读取 ESP 中的 GRUB 模块            │
  └──────────────────────────┬───────────────────────────┘
                             │
                             ▼
  ┌──────────────────────────────────────────────────────┐
  │  Stage 2：/boot/grub/ 下的模块（*.mod 文件）           │
  │  ─────────────────────────────                        │
  │  位置：/boot/grub/x86_64-efi/（UEFI）                 │
  │        /boot/grub/i386-pc/（BIOS）                    │
  │  任务：加载配置文件 grub.cfg                           │
  │        提供 GRUB 命令行（grub> 提示符）                 │
  │        加载操作系统内核                                 │
  │  关键模块：normal.mod（正常模式）、linux.mod（加载 Linux）│
  └──────────────────────────┬───────────────────────────┘
                             │
                             ▼
  ┌──────────────────────────────────────────────────────┐
  │  GRUB 配置文件：/boot/grub/grub.cfg                    │
  │  ─────────────────────────────                        │
  │  由 update-grub（grub-mkconfig）自动生成                │
  │  定义启动菜单项、内核参数、超时时间等                     │
  │  不要手动编辑这个文件！修改 /etc/default/grub 后重新生成  │
  └──────────────────────────────────────────────────────┘
```

> **为什么 GRUB2 需要 1.5 阶段？** 在 BIOS 模式下，446 字节的 Stage 1 不足以包含完整的文件系统驱动。Stage 1 只知道 core.img 的物理位置（LBA 地址），而 core.img 需要文件系统驱动才能读取 /boot 分区上的 GRUB 模块和配置文件。这个"能读文件系统但还没显示菜单"的中间状态就是 Stage 1.5。

#### 2.3.2 GRUB2 关键文件清单

| 路径 | 用途 |
|------|------|
| `/etc/default/grub` | GRUB 主配置文件（用户编辑此文件） |
| `/boot/grub/grub.cfg` | 生成的最终配置（由 `update-grub` 自动生成，勿手动编辑） |
| `/etc/grub.d/` | 配置片段目录，`grub-mkconfig` 组合这些片段生成 grub.cfg |
| `/boot/grub/x86_64-efi/` | UEFI 模式下 GRUB 的模块文件（*.mod） |
| `/boot/grub/i386-pc/` | BIOS 模式下 GRUB 的模块文件 |
| `/boot/efi/EFI/ubuntu/grubx64.efi` | UEFI 模式下的 GRUB 可执行文件（ESP 中） |
| `/boot/vmlinuz-*` | Linux 内核镜像（压缩后的可执行文件） |
| `/boot/initrd.img-*` | initramfs 镜像 |

### 2.4 initramfs：为什么内核需要一个"临时根文件系统"

这是启动流程中常被误解的一个概念。让我们用一个生活类比来理解：

**类比：搬家**
- 你（内核）拿到了新房（硬件）的钥匙，但你还不知道：
  - 卧室（根文件系统）在哪块硬盘上？
  - 门锁（LUKS 加密）的密码是什么？
  - 卧室里面是榻榻米（ext4）还是地板（XFS）？需要什么工具（内核模块）才能打开？
- 于是你先住进临时帐篷（initramfs），帐篷里带了所有必要的工具——各种钥匙（内核模块）、地图（设备扫描脚本）、工具箱（fsck、mount 等命令）。
- 你勘探清楚环境，解锁真正的卧室，然后收起帐篷，搬进去。

#### 2.4.1 为什么需要 initramfs

```
没有 initramfs 的问题：
════════════════════════════════════════════════════════════════

  内核 → 需要挂载根文件系统 → 但根文件系统在磁盘上 → 需要磁盘驱动
  → 磁盘驱动在根文件系统的 /lib/modules/ 下

  死循环：要读根文件系统才能加载驱动，但没驱动就读不了根文件系统！

  解决方案：initramfs
  ───────────────────
  将必要的驱动、工具、脚本打包进一个小型内存文件系统（通常 50-150MB）
  内核先加载这个 initramfs，从中获取驱动，然后才挂载真正的根文件系统

initramfs 包含的内容：
══════════════════════
  ├── 内核模块（.ko 文件）
  │   ├── 磁盘控制器驱动（如 ahci, nvme, virtio）
  │   ├── 文件系统驱动（ext4, xfs, btrfs）
  │   ├── RAID/LVM 驱动（md, dm-mod）
  │   ├── 加密驱动（dm-crypt for LUKS）
  │   └── 网络驱动（用于 NFS root 等网络启动场景）
  │
  ├── 用户空间工具
  │   ├── busybox 或 klibc 工具集（sh, mount, ls, cat 等）
  │   ├── fsck（文件系统检查）
  │   ├── lvm, mdadm（LVM 和 RAID 管理）
  │   ├── cryptsetup（LUKS 加密）
  │   └── udev（设备管理）
  │
  └── 初始化脚本
      ├── /init（第一个执行的程序）
      ├── 扫描硬件、加载驱动
      ├── 检测根文件系统
      ├── 必要时解密/激活 LVM
      └── switch_root 到真实根文件系统
```

#### 2.4.2 initramfs 的两种格式

| 特性 | initramfs（initrd） | initramfs（cpio 归档） |
|------|--------------------|-----------------------|
| **格式** | 压缩的文件系统镜像（ext2/cramfs） | gzip/bzip2/lz4 压缩的 cpio 归档 |
| **挂载方式** | 通过 RAM 磁盘（/dev/ram0）挂载 | 通过 tmpfs 直接解压到内存 |
| **大小限制** | 受 RAM 磁盘大小限制 | 受可用内存限制 |
| **灵活性** | 需要内核支持对应的文件系统 | 纯内存操作，无需额外驱动 |
| **现代 Linux** | 已被淘汰 | 当前标准（2.6 内核起） |

> Ubuntu 24.04 使用 cpio 归档格式的 initramfs，文件位于 `/boot/initrd.img-*`（虽然后缀叫 "img"，但内部是 cpio 归档）。

#### 2.4.3 initramfs 内的 /init 脚本做了什么

```
initramfs 中 /init 脚本的典型执行流程：
════════════════════════════════════════════════════════════════

  [内核执行 /init]
        │
        ▼
  ┌──────────────────────────┐
  │ 1. 挂载虚拟文件系统        │  mount -t proc proc /proc
  │                            │  mount -t sysfs sysfs /sys
  │                            │  mount -t devtmpfs devtmpfs /dev
  └──────────┬───────────────┘
             ▼
  ┌──────────────────────────┐
  │ 2. 加载内核模块            │  从 /lib/modules/ 加载 .ko 文件
  │                            │  关键：磁盘控制器、文件系统、LVM/RAID
  └──────────┬───────────────┘
             ▼
  ┌──────────────────────────┐
  │ 3. 扫描硬件并等待设备就绪  │  udevadm trigger
  │                            │  udevadm settle
  └──────────┬───────────────┘
             ▼
  ┌──────────────────────────┐
  │ 4. 定位根文件系统设备      │  解析内核参数 root=UUID=...
  │                            │  blkid 查找对应设备
  └──────────┬───────────────┘
             ▼
  ┌──────────────────────────┐
  │ 5. 处理特殊存储层（可选）   │  LUKS 解密（cryptsetup）
  │                            │  LVM 激活（lvm vgchange -ay）
  │                            │  RAID 组装（mdadm --assemble）
  └──────────┬───────────────┘
             ▼
  ┌──────────────────────────┐
  │ 6. 检查根文件系统          │  fsck -y /dev/...
  └──────────┬───────────────┘
             ▼
  ┌──────────────────────────┐
  │ 7. 挂载根文件系统到 /root  │  mount /dev/... /root
  └──────────┬───────────────┘
             ▼
  ┌──────────────────────────┐
  │ 8. switch_root            │  cd /root
  │                            │  mount --move /sys /root/sys
  │                            │  mount --move /proc /root/proc
  │                            │  mount --move /dev /root/dev
  │                            │  exec switch_root /root /sbin/init
  └──────────┬───────────────┘
             ▼
  [真实根文件系统上的 /sbin/init（即 systemd）接管]
```

### 2.5 systemd 启动目标：从 basic 到 graphical

systemd 用 **target（目标）** 替代了 SysV Init 的 runlevel（运行级别）。target 是一个逻辑分组，将需要同时达到某种状态的 unit 组织在一起。

#### 2.5.1 systemd target 与 SysV runlevel 对照

| SysV Runlevel | 含义 | systemd Target | systemctl 别名 |
|---------------|------|----------------|----------------|
| 0 | 关机（Halt） | `poweroff.target` | `runlevel0.target` |
| 1 (S/single) | 单用户模式（救援） | `rescue.target` | `runlevel1.target` |
| 2 | 多用户模式（无网络） | `multi-user.target` | `runlevel2.target` |
| 3 | 多用户模式（文本） | `multi-user.target` | `runlevel3.target` |
| 4 | 保留（自定义） | `multi-user.target` | `runlevel4.target` |
| 5 | 多用户模式（图形） | `graphical.target` | `runlevel5.target` |
| 6 | 重启（Reboot） | `reboot.target` | `runlevel6.target` |

> **为什么 systemd 不再使用数字 runlevel？** 因为 runlevel 是一次只能处于一个的互斥状态，而 systemd target 可以同时激活多个，且支持依赖关系（Requires/Wants/After/Before），这比数字编号灵活得多。

#### 2.5.2 systemd target 依赖关系图

```
graphical.target 的完整启动依赖链：
════════════════════════════════════════════════════════════════

graphical.target                     ← 图形界面
    │
    └── Requires: multi-user.target
                │
                ├── Requires: basic.target
                │       │
                │       ├── Requires: sysinit.target
                │       │       │
                │       │       ├── 挂载文件系统（local-fs.target）
                │       │       │   └── /etc/fstab 中除了 noauto 的所有条目
                │       │       │
                │       │       ├── 激活 swap（swap.target）
                │       │       │
                │       │       ├── systemd-journald（日志）
                │       │       │
                │       │       ├── systemd-tmpfiles-setup（临时文件）
                │       │       │
                │       │       ├── systemd-sysusers（系统用户）
                │       │       │
                │       │       └── udev（设备管理）
                │       │
                │       ├── sockets.target
                │       │   └── D-Bus socket, syslog socket 等
                │       │
                │       ├── timers.target
                │       │   └── 所有启用的 timer unit
                │       │
                │       └── paths.target
                │           └── 路径监控 unit
                │
                ├── network.target（网络就绪）
                │
                ├── nss-user-lookup.target（用户查询服务）
                │
                └── 各种服务 unit
                    ├── ssh.service（SSH 服务）
                    ├── cron.service（定时任务）
                    ├── ufw.service（防火墙）
                    └── ...
                │
graphical.target 额外需要：
    └── display-manager.service
        └── gdm.service（GNOME Display Manager）
            └── gnome-session（桌面环境）
```

#### 2.5.3 四种关键 target 说明

| Target | 何时使用 | 启动了什么 | 不启动什么 |
|--------|---------|-----------|-----------|
| `graphical.target` | 正常桌面使用 | 所有服务 + 显示管理器 + 桌面环境 | — |
| `multi-user.target` | 服务器 / 远程管理 | 网络、SSH、cron、getty 等 | 显示管理器、桌面环境 |
| `rescue.target` | 修复系统配置错误 | 基本文件系统挂载、单用户 Shell（root） | 网络、多数服务 |
| `emergency.target` | 极度严重故障（根文件系统损坏） | 仅挂载根文件系统（只读）、最简 Shell | 网络、initramfs 之外的一切 |

```
救援级别对比：
════════════════════════════════════════════════════════════════

运行中的正常系统
    │
    │ systemctl isolate multi-user.target
    ▼
multi-user.target（文本模式）
    网络：✓  服务：✓  多用户：✓  图形：✗
    │
    │ systemctl isolate rescue.target
    │ 或 GRUB 中添加 systemd.unit=rescue.target
    ▼
rescue.target（救援模式 / 单用户模式）
    网络：✗  服务：✗  / 只读：✗（挂载为读写）
    仅挂载本地文件系统，启动基本 Shell（需要 root 密码）
    │
    │ systemctl isolate emergency.target

    ▼
emergency.target（紧急模式）
    网络：✗  服务：✗  / 只读：✓（ro）
    连 /etc/fstab 都不解析，直接在 initramfs 环境中给出最简 Shell
```

### 2.6 启动性能分析：systemd-analyze

`systemd-analyze` 是 systemd 自带的启动性能分析工具。它不只告诉你"启动花了多少秒"，还能分解到每个 unit 的时间消耗。

```bash

systemd-analyze critical-chain

# 用浏览器打开 boot.svg，可以看到彩色的启动时序图
```

### 2.7 内核环形缓冲区（Kernel Ring Buffer）与 dmesg

内核在启动过程中会产生大量消息——硬件检测、驱动加载、内存分配、错误警告。这些消息在被写入磁盘的日志文件之前，先存放在内存中的一个叫 **环形缓冲区**（ring buffer）的区域。`dmesg` 命令就是用来读取这个缓冲区的。

```
dmesg 输出的信息类别：
════════════════════════════════════════════════════════════════

  [    0.000000] ← 时间戳（从内核启动开始计，单位秒）
  │
  ├── BIOS/UEFI 信息
  │   ├── DMI（Desktop Management Interface，桌面管理接口）信息：制造商、型号
  │   └── ACPI（Advanced Configuration and Power Interface，高级配置与电源接口）表
  │
  ├── CPU 信息
  │   ├── 微码版本（microcode）
  │   └── 核心数、缓存大小
  │
  ├── 内存信息
  │   ├── 总量、可用量
  │   ├── 内存映射（e820）
  │   └── NUMA 节点信息
  │
  ├── PCI 设备枚举
  │   ├── 存储控制器（AHCI/NVMe）
  │   ├── 网卡（Ethernet/WiFi）
  │   ├── USB 控制器
  │   └── 显卡
  │
  ├── 驱动加载
  │   ├── 各驱动的初始化消息
  │   └── 固件加载（firmware loading）
  │
  ├── 文件系统挂载

  │
  └── 错误与警告
      ├── ACPI Error（通常可以忽略）
      ├── PCIe Bus Error（硬件问题或不兼容）
      └── driver probe failed（驱动加载失败）
```

## 3. 命令详解

### 3.1 GRUB2 配置管理

#### 3.1.1 /etc/default/grub —— 主配置文件

这是你唯一需要编辑的 GRUB 配置文件。`update-grub` 会读取这个文件，结合 `/etc/grub.d/` 下的脚本，生成最终的 `/boot/grub/grub.cfg`。

```bash
# 查看当前 GRUB 配置
cat /etc/default/grub
```

典型内容及每行的含义：

```ini
# 如果设置为 true，GRUB 菜单将保存上次选择的操作系统
# 下次启动时自动选择它
GRUB_DEFAULT=0

# 如果 GRUB_DEFAULT=saved，配合此设置工作
# GRUB_SAVEDEFAULT=true

# 菜单显示超时时间（秒）
# 0 = 不显示菜单直接启动；-1 = 一直等待用户选择
GRUB_TIMEOUT=10

# 子菜单的超时样式
# hidden = 显示倒计时但不显示菜单
# menu = 直接显示菜单
GRUB_TIMEOUT_STYLE=hidden

# 传递给 Linux 内核的命令行参数
# 这是最重要的配置项之一
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash"

# 内核参数说明：
# quiet     → 减少启动时的文字输出（不显示所有内核消息）
# splash    → 显示 Plymouth 启动画面（Ubuntu logo）
# nomodeset → 禁用内核模式设置（KMS，Kernel Mode Setting）
#              显卡驱动出问题时使用
# acpi=off  → 禁用 ACPI（高级配置与电源接口）
#             非常老的硬件可能需要
# single    → 进入单用户模式（= rescue.target）
# init=/bin/bash → 内核直接启动 bash 而不启动 systemd

# 传递给内核的额外参数（所有内核都接收，包括 recovery 模式）
GRUB_CMDLINE_LINUX=""

# 禁用哪些内核启动项（子菜单）
# GRUB_DISABLE_SUBMENU=y  → 所有内核直接在顶层菜单显示

# GRUB 的分辨率设置
# GRUB_GFXMODE=1920x1080
# GRUB_GFXPAYLOAD_LINUX=keep  → 保持 GRUB 的分辨率到内核

# 禁用 OS Prober（自动检测其他操作系统）
# GRUB_DISABLE_OS_PROBER=false
```

#### 3.1.2 修改内核启动参数（常见场景）

```bash
# 场景 1：禁用启动画面，查看详细启动信息（调试用）
# 编辑 /etc/default/grub：
GRUB_CMDLINE_LINUX_DEFAULT=""
# 去掉 quiet splash，然后：
sudo update-grub

# 场景 2：显卡驱动问题，需要禁用内核模式设置
# 编辑 /etc/default/grub：
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash nomodeset"
sudo update-grub

# 场景 3：设置默认启动项为第二个菜单项（编号从 0 开始）
# 编辑 /etc/default/grub：
GRUB_DEFAULT="1>2"   # 第一个菜单的子菜单中第 3 项（编号从 0 开始）
sudo update-grub

# 场景 4：减少 GRUB 等待时间（加快启动）
# 编辑 /etc/default/grub：
GRUB_TIMEOUT=3
sudo update-grub

# 场景 5：添加内核参数（永久生效，非临时）
# 编辑 /etc/default/grub：
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash mitigations=off"
# mitigations=off 关闭 CPU 安全漏洞缓解措施（提高性能，降低安全性）
sudo update-grub
```

#### 3.1.3 update-grub 的背后

```bash
# update-grub 是 grub-mkconfig 的便捷封装
# 等效于：
sudo grub-mkconfig -o /boot/grub/grub.cfg

# 执行 update-grub 时发生了什么：
# 1. 读取 /etc/default/grub
# 2. 执行 /etc/grub.d/ 下的脚本，按数字前缀排序：
#    00_header         → 生成 GRUB 头部配置（超时、分辨率等）
#    05_debian_theme   → 设置 GRUB 主题/配色
#    10_linux          → 检测已安装的内核（/boot/vmlinuz-*）
#                        为每个内核生成一个菜单项
#    20_linux_xen      → 检测 Xen 虚拟化内核
#    30_os-prober      → 检测其他操作系统（Windows 等）
#    30_uefi-firmware  → 添加"进入 UEFI 固件设置"菜单项
#    40_custom         → 用户自定义菜单项
#    41_custom         → 预留
# 3. 将结果写入 /boot/grub/grub.cfg

# 查看生成的 grub.cfg 结构（自动生成，不要手动编辑）
head -100 /boot/grub/grub.cfg
```

> **为什么不直接编辑 grub.cfg？** 因为每次内核更新、`update-grub` 或系统升级都会重新生成 grub.cfg，所有手动修改都会被覆盖。保持修改集中在 `/etc/default/grub` 和 `/etc/grub.d/` 中。

#### 3.1.4 临时修改内核参数（一次性，调试用）

```bash
# 在 GRUB 菜单中按 'e' 编辑当前启动项
# 找到以 "linux" 开头的那一行，在末尾添加参数
# 例如：
linux   /boot/vmlinuz-6.8.0-31-generic root=UUID=xxx ro  quiet splash
# 改为：
linux   /boot/vmlinuz-6.8.0-31-generic root=UUID=xxx ro  single
# 按 Ctrl+X 或 F10 启动

# 常用临时内核参数：
# single (或 1)       → 进入救援模式（rescue.target）
# systemd.unit=emergency.target  → 进入紧急模式
# systemd.unit=multi-user.target → 进入文本模式
# init=/bin/bash      → 内核直接启动 bash（绕过 systemd，极度紧急时使用）
# nomodeset           → 禁用 KMS（显卡问题）
# acpi=off            → 禁用 ACPI（电源管理问题）
# root=/dev/sdaX      → 指定根文件系统
# ro                  → 只读挂载根文件系统
# rw                  → 读写挂载根文件系统
```

### 3.2 initramfs 管理

#### 3.2.1 update-initramfs —— 管理 initramfs 镜像

```bash
# 基本语法
# update-initramfs [选项] [操作]

# 查看已安装内核的当前 initramfs
ls -lh /boot/initrd.img-*
# 输出示例：
# -rw-r--r-- 1 root root 85M Jul 15 10:23 /boot/initrd.img-6.8.0-31-generic

# 为当前运行的内核重新生成 initramfs
sudo update-initramfs -u
# -u: update，更新当前内核的 initramfs

# 为指定内核版本重新生成
sudo update-initramfs -u -k 6.8.0-31-generic
# -k: kernel version

# 为所有已安装的内核重新生成
sudo update-initramfs -u -k all

# 为当前内核强制重新生成（即使 initramfs 已存在）
sudo update-initramfs -c -k $(uname -r)
# -c: create

# 删除某个内核的 initramfs（卸载旧内核时使用）
sudo update-initramfs -d -k 6.8.0-30-generic
# -d: delete
```

#### 3.2.2 浏览 initramfs 内容

```bash
# 使用 lsinitramfs 查看 initramfs 包含的文件列表
lsinitramfs /boot/initrd.img-$(uname -r) | head -50
# 输出示例：
# .
# kernel
# kernel/x86
# kernel/x86/microcode
# kernel/x86/microcode/GenuineIntel.bin
# ...
# usr
# usr/bin
# usr/sbin
# usr/lib
# ...

# 统计 initramfs 中的文件数量
lsinitramfs /boot/initrd.img-$(uname -r) | wc -l

# 查看 initramfs 中是否包含某个驱动
lsinitramfs /boot/initrd.img-$(uname -r) | grep -i "ahci\|nvme\|virtio"

# 查看 initramfs 的大小和压缩信息
file /boot/initrd.img-$(uname -r)
# 输出示例：
# /boot/initrd.img-6.8.0-31-generic: Zstandard compressed data (zstd)

# 解压 initramfs 到临时目录（用于深入检查）
mkdir -p /tmp/initramfs-check
cd /tmp/initramfs-check
sudo unmkinitramfs /boot/initrd.img-$(uname -r) .
ls

# 查看 init 脚本
cat /tmp/initramfs-check/main/init
# 或（取决于 unmkinitramfs 的输出结构）
cat /tmp/initramfs-check/early/init
```

#### 3.2.3 mkinitcpio 说明

> **注意：** `mkinitcpio` 是 **Arch Linux** 的 initramfs 生成工具，**不适用于 Ubuntu**。Ubuntu 使用 `initramfs-tools`（命令为 `update-initramfs` 和 `mkinitramfs`）。如果你查阅 Arch Wiki 或其他发行版的资料，请注意这个差异。

```bash
# Ubuntu 的 initramfs 工具链
# 主要工具：
#   update-initramfs    → 用户友好的封装（最常用）
#   mkinitramfs         → 底层工具，update-initramfs 调用它
#   lsinitramfs         → 查看 initramfs 内容
#   unmkinitramfs       → 解压 initramfs

# 相关配置文件：
#   /etc/initramfs-tools/initramfs.conf   → 主配置
#   /etc/initramfs-tools/modules          → 指定额外包含的内核模块

# 查看当前 initramfs 配置
cat /etc/initramfs-tools/initramfs.conf
# 关键配置项：
#   MODULES=most    → 包含尽可能多的模块（默认，兼容性好）
#   MODULES=dep     → 只包含当前硬件需要的模块（更小，更快）
#   COMPRESS=zstd   → 压缩算法
#   BUSYBOX=y       → 是否包含 busybox
```

#### 3.3.2 isolate —— 运行时切换 target

```bash
# isolate 命令可以"跳到"指定的 target
# 系统会停止不属于新 target 的服务，启动新 target 需要的服务

# 切换到文本模式（停止图形界面）
sudo systemctl isolate multi-user.target
# 注意：X/Wayland 会话会终止！保存你的工作！
```

### 3.4 dmesg —— 内核环形缓冲区

#### 3.4.1 基本用法

```bash
# 查看完整的内核启动消息
dmesg
# 输出可能有几千行，通常配合 less 或 grep 使用

# 分页查看
dmesg | less

# 查看最新的 N 行（类似 tail）
dmesg | tail -50

# 查看前 N 行（启动最早的消息）
dmesg | head -50

# 以人类可读的时间戳显示
dmesg -H
# 输出示例：
# [Jul15 10:23] microcode: updated early: 0xb4 -> 0xf4, date = 2024-04-15
# [Jul15 10:23] Linux version 6.8.0-31-generic ...

# 显示原始时间戳（从启动开始的秒数）
dmesg -H | head -5
# 等价于不带 -H 的输出

# 持续监控新消息（类似 tail -f）
dmesg -w
# 热插拔 USB 设备时，你会即时看到内核的检测消息
# 按 Ctrl+C 退出
```

#### 3.4.2 过滤关键信息

```bash
# 过滤硬件检测信息
dmesg | grep -i "cpu\|processor"
dmesg | grep -i "memory\|mem"
dmesg | grep -i "sda\|nvme\|disk"
dmesg | grep -i "usb"
dmesg | grep -i "network\|eth\|wlan"

# 过滤错误和警告
dmesg | grep -i "error\|fail\|warn"

# 过滤 ACPI 消息（在桌面上很常见，通常可忽略）
dmesg | grep -i "acpi"

# 查看 PCI 设备枚举
dmesg | grep -i "pci"

# 查看文件系统相关信息
dmesg | grep -i "ext4\|xfs\|btrfs\|mount\|VFS"

# 查看 USB 设备插入/拔出（配合 dmesg -w 使用）
dmesg -w | grep -i "usb"

# 查看 iptables/netfilter 日志
dmesg | grep -i "nf_\|iptable"

# 彩色高亮关键词
dmesg --color=always | grep --color -E "error|fail|warn|BUG|Oops"
```

#### 3.4.3 dmesg 的机制与持久化

```bash
# dmesg 读取的是内核环形缓冲区（Ring Buffer）
# 大小有限（通常 4-16MB），旧消息会被新消息覆盖
# 可以通过内核参数调整：log_buf_len=4M

# 查看当前缓冲区大小（以字节为单位）
cat /sys/module/printk/parameters/log_buf_len

# 清除缓冲区（不推荐在生产环境操作）
sudo dmesg -c
# 这会清除缓冲区内容，并打印清除前的内容

# dmesg 的数据也进入了 systemd journal
# 可以通过 journalctl 查看（带索引、时间过滤等高级功能）
journalctl -k                    # 本次启动的内核消息
journalctl -k -b -1             # 上一次启动的内核消息
journalctl -k --since "10 minutes ago"

# 内核日志也会写入磁盘（如果 rsyslog 配置了 kern.*）
cat /var/log/kern.log | tail -30
```

#### 3.4.4 dmesg 级别（Loglevel）

```bash
# 内核消息分为 8 个级别（0 最高，7 最低）
# 级别定义（include/linux/kern_levels.h）：
#   KERN_EMERG    (0) 系统不可用
#   KERN_ALERT    (1) 必须立即采取行动
#   KERN_CRIT     (2) 临界条件
#   KERN_ERR      (3) 错误条件
#   KERN_WARNING  (4) 警告条件
#   KERN_NOTICE   (5) 正常但值得注意
#   KERN_INFO     (6) 信息性消息
#   KERN_DEBUG    (7) 调试级别

# 只显示错误级别及以上的消息（级别 0-3）
dmesg -l err

# 显示警告及以上的消息（级别 0-4）
```

## 5. 常见错误与排错

### 错误 1：update-grub 后找不到 Windows 启动项

**现象：** 双系统（Ubuntu + Windows），执行 `update-grub` 后 GRUB 菜单中 Windows 消失了。

**原因：** `os-prober`（OS Prober，操作系统探测工具）被禁用或未安装。Ubuntu 在某些版本中出于安全考虑默认禁用了它。

**解决：**

```bash
# 1. 确保 os-prober 已安装
sudo apt install os-prober

# 2. 确保 os-prober 已启用
grep "GRUB_DISABLE_OS_PROBER" /etc/default/grub
# 如果显示 GRUB_DISABLE_OS_PROBER=true，改为 false
# 或者删除这一行

# 3. 手动运行 os-prober 确认能检测到 Windows
sudo os-prober
# 输出示例：
# /dev/sda2:Windows 10:Windows:chain

# 4. 重新生成 GRUB 配置
sudo update-grub
# 输出中应包含 "Found Windows ..."

# 5. 重启验证
sudo reboot
```

### 错误 2：内核更新后系统无法启动

**现象：** 更新内核后，重启时看到 kernel panic 或黑屏，系统无法进入登录界面。

**原因：** 新内核与某些硬件不兼容，或 initramfs 生成时遗漏了关键驱动模块。

**解决：**

```
恢复步骤：
════════════════════════════════════════════════════════════════

1. 重启，在 GRUB 菜单中选择 "Advanced options for Ubuntu"
2. 选择一个旧版本的内核（不是 recovery mode）
3. 如果旧内核能正常启动，说明新内核有问题

4. 暂时使用旧内核，然后卸载有问题的内核：
   sudo apt remove linux-image-6.8.0-XX-generic
   sudo apt remove linux-headers-6.8.0-XX-generic

5. 或者尝试重新生成新内核的 initramfs：
   sudo update-initramfs -c -k 6.8.0-XX-generic
   sudo update-grub
```

```bash
# 列出所有已安装的内核
dpkg -l | grep linux-image

# 查看当前运行的内核
uname -r

# 卸载指定版本的内核
# sudo apt remove linux-image-[版本号]-generic
# sudo apt remove linux-headers-[版本号]-generic
```

### 错误 3：grub rescue 提示符

**现象：** 开机后直接进入 `grub rescue>` 提示符，无法进入 GRUB 菜单，显示类似：

```
error: no such partition.
Entering rescue mode...
grub rescue>
```

**原因：** GRUB 无法找到 `/boot/grub/` 所在的文件系统。通常是磁盘分区 UUID 变更了（比如你克隆了磁盘、或重新分区），而 GRUB 的 core.img 中硬编码的路径失效。

**解决：**

```bash
# 在 grub rescue> 提示符下：
# 1. 列出所有分区
ls
# 输出类似：(hd0) (hd0,gpt1) (hd0,gpt2)

# 2. 逐个尝试找出 /boot/grub 所在的分区
ls (hd0,gpt1)/
ls (hd0,gpt2)/
# 找到包含 /boot/grub/ 的分区

# 3. 设置 prefix 和 root
set prefix=(hd0,gpt2)/boot/grub
set root=(hd0,gpt2)

# 4. 加载 normal 模块
insmod normal
normal

# 5. 现在应该看到 GRUB 菜单了
# 启动后，重新安装 GRUB：
sudo grub-install /dev/sda          # BIOS
sudo grub-install --target=x86_64-efi  # UEFI
sudo update-grub
```

### 错误 4：/etc/fstab 错误导致启动失败

**现象：** 修改了 `/etc/fstab` 后重启，系统卡在启动流程中，或者进入 emergency mode。

**原因：** fstab 中的某个条目无法挂载（UUID 不存在、网络文件系统不可达、文件系统类型错误等），且该条目没有 `nofail` 选项。

**解决：**

```bash
# 在 emergency mode 下：
# 1. 重新挂载根文件系统为读写
mount -o remount,rw /

# 2. 编辑 /etc/fstab
vim /etc/fstab

# 3. 在可疑的挂载条目中添加 nofail 选项（让 systemd 在挂载失败时不阻塞启动）
# 例如：
# UUID=xxx  /data  ext4  defaults,nofail  0  2

# 4. 或者直接注释掉出错的条目（在行首加 #）

# 5. 测试 fstab 是否合法
mount -a

# 6. 重启
reboot
```

### 错误 5：dmesg 缓冲区被填满

**现象：** `dmesg` 的输出不完整，早期的启动消息丢失了。

**原因：** 内核环形缓冲区（Ring Buffer）大小有限（默认约 4MB），长时间运行后新消息覆盖了旧消息。

**解决：**

```bash
# 1. 使用 journalctl 代替（journal 持久化到磁盘，不受环形缓冲区限制）
journalctl -k                    # 本次启动的内核消息
journalctl -k -b -1             # 上一次启动的内核消息

# 2. 如果需要增大 dmesg 缓冲区（永久修改）
# 在 /etc/default/grub 中添加：
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash log_buf_len=16M"
sudo update-grub
sudo reboot

# 3. 或者查看 /var/log/kern.log（如果 rsyslog 在运行）
cat /var/log/kern.log | tail -100
```

### 错误 6：Secure Boot 阻止加载第三方内核模块

**现象：** 安装 NVIDIA 驱动或 VirtualBox 后，驱动无法加载，`dmesg` 显示类似：

```
Lockdown: modprobe: Loading of unsigned module is restricted
```

**原因：** Secure Boot 开启时，内核要求所有内核模块必须经过签名。第三方模块（如 NVIDIA、VirtualBox）默认没有签名。

**解决：**

```bash
# 方案 A：注册 MOK（Machine Owner Key，机器所有者密钥）
# 安装驱动后，通常会提示设置 MOK 密码
# 重启后进入 MOK Manager，选择 Enroll MOK

# 方案 B：检查 Secure Boot 状态
mokutil --sb-state
# 输出：SecureBoot enabled

# 方案 C：临时关闭 Secure Boot（不推荐，但有时是唯一选择）
# 进入 UEFI 固件设置 → Boot → Secure Boot → Disabled
# 注意：这会降低系统安全性

# 方案 D：使用 DKMS 自动签名
# Ubuntu 的 NVIDIA 驱动大部分情况下已经通过 DKMS 签好名了
sudo apt install --reinstall nvidia-dkms-XXX
```

### 错误 7：系统启动时长时间停在 "A start job is running for..."

**现象：** 启动时看到类似消息，持续 90 秒：

```
A start job is running for /dev/disk/by-uuid/XXXXX (1min 30s / no limit)
```

**原因：** systemd 在等待一个磁盘设备，但该设备不存在或不可达。通常是 `/etc/fstab` 中引用的分区 UUID 不存在，或者 swap 分区 UUID 变更了。

**解决：**

```bash
# 1. 查看当前所有分区的 UUID
sudo blkid

# 2. 检查 /etc/fstab 中的 UUID 是否与实际匹配
cat /etc/fstab

# 3. 检查 swap 的 UUID
cat /etc/fstab | grep swap
sudo blkid | grep swap

# 4. 不匹配时，更新 /etc/fstab 中的 UUID
# 或者使用 /dev/sdX 路径代替 UUID（不推荐，/dev/sdX 可能变化）

# 5. 如果某个磁盘确实不再需要，添加 nofail 选项
# UUID=old-uuid  /mnt/data  ext4  defaults,nofail  0  2
```

### 6.1 内核参数深入

除了常用的 `quiet`、`splash`、`single`，内核还支持大量调试和配置参数：

```bash
# 查看所有可用的内核参数（文档非常长）
# ls /usr/share/doc/linux-doc/admin-guide/kernel-parameters.txt
# 或在线文档：https://www.kernel.org/doc/html/latest/admin-guide/kernel-parameters.html

# === 调试类参数 ===
# debug               → 启用所有内核调试信息
# ignore_loglevel     → 打印所有级别的内核消息（包括 DEBUG）
# earlyprintk=vga     → 在 VGA 上尽早显示内核消息
# initcall_debug      → 打印每个内核初始化函数的耗时

# === 安全类参数 ===
# selinux=1           → 启用 SELinux（Ubuntu 默认使用 AppArmor）
# apparmor=1          → 启用 AppArmor
# mitigations=off     → 关闭所有 CPU 安全漏洞缓解（提高性能，降低安全性）
# spectre_v2=off      → 单独关闭 Spectre v2 缓解

# === 内存类参数 ===
# mem=4G              → 限制可用内存（测试用）
# memmap=...          → 指定内存映射
# cgroup_memory=1     → 启用 cgroup v1 memory controller

# === 存储类参数 ===
# root=/dev/sda2      → 指定根文件系统
# rootfstype=ext4     → 指定根文件系统类型
# rootflags=...       → 根文件系统的挂载选项
# ro                  → 只读挂载根
# rw                  → 读写挂载根

# === 显卡类参数 ===
# nomodeset           → 禁用内核模式设置
# nouveau.modeset=0   → 禁用 nouveau 驱动（NVIDIA）
# i915.modeset=0      → 禁用 i915 驱动（Intel）
# radeon.modeset=0    → 禁用 radeon 驱动（AMD）
```

### 6.2 自定义 GRUB 菜单项

```bash
# 在 /etc/grub.d/40_custom 中添加自定义菜单项
sudo vim /etc/grub.d/40_custom

# 示例 1：添加一个带特定内核参数的启动项
menuentry 'Ubuntu - Debug Mode' {
    set root='hd0,gpt2'
    linux   /boot/vmlinuz-$(uname -r) root=UUID=xxx ro debug ignore_loglevel
    initrd  /boot/initrd.img-$(uname -r)
}

# 示例 2：添加直接启动到 shell 的选项（紧急修复用）
menuentry 'Ubuntu - Emergency Shell (Bypass systemd)' {
    set root='hd0,gpt2'
    linux   /boot/vmlinuz-$(uname -r) root=UUID=xxx rw init=/bin/bash
    initrd  /boot/initrd.img-$(uname -r)
}

# 示例 3：添加 memtest 选项（如果安装了 memtest86+）
menuentry 'Memory Test (memtest86+)' {
    set root='hd0,gpt2'
    linux16 /boot/memtest86+x64.bin
}

# 修改后重新生成
sudo update-grub
```

### 6.3 Plymouth 启动画面定制

Plymouth 是 Ubuntu 启动时显示动画 Logo 的软件。它的行为可以通过内核参数和配置文件调整：

```bash
# 查看当前 Plymouth 主题
plymouth-set-default-theme
# 输出：bgrt（显示 OEM Logo）

# 列出可用主题
sudo plymouth-set-default-theme --list
# 通常有：bgrt, details, text

# 切换到纯文本模式（不显示 Logo，显示启动日志）
sudo plymouth-set-default-theme details
sudo update-initramfs -u
sudo reboot

# 恢复默认
sudo plymouth-set-default-theme bgrt
sudo update-initramfs -u

# 内核参数相关：
# splash             → 显示 Plymouth 启动画面
# nosplash           → 不显示启动画面
# quiet              → 隐藏启动消息
# 去掉 quiet         → 显示启动消息（Plymouth 下会叠加在画面上）
# quiet splash       → 默认（显示画面，隐藏消息）
# （无参数）          → 不显示画面，显示所有启动消息
```

### 6.4 systemd-boot（替代 GRUB）

systemd-boot（原名 gummiboot）是 systemd 项目提供的轻量级 UEFI 引导管理器。与 GRUB2 相比：

| 特性 | GRUB2 | systemd-boot |
|------|-------|-------------|
| **大小** | ~10MB+（含模块） | ~100KB |
| **配置复杂度** | 高（脚本生成 grub.cfg） | 低（纯文本配置文件） |
| **文件系统支持** | 几乎所有（通过模块） | 仅 FAT（ESP 本身） |
| **BIOS 支持** | 支持 | 不支持（仅 UEFI） |
| **主题/图形** | 支持 | 不支持 |
| **多系统探测** | os-prober 自动检测 | 需手动添加条目 |
| **内核更新自动配置** | update-grub 自动处理 | 需要钩子脚本 |

```bash
# 安装 systemd-boot（替代 GRUB，高级操作，慎用）
# sudo bootctl install
# sudo bootctl update

# 查看当前引导管理器
bootctl status
# 如果使用 GRUB，会显示 "Not booted with systemd-boot"

# 实际上，对于大多数 Ubuntu 用户：
# GRUB2 仍然是更成熟、兼容性更好的选择
# systemd-boot 适合追求极简的 UEFI-only 场景
```

> **建议：** 除非你明确需要 systemd-boot 的某个特性（如极快的启动速度、纯 UEFI 环境），否则继续使用 GRUB2 是更安全的选择。

### 6.5 kexec —— 不经过固件的内核重启

kexec 允许你"重启"内核而不经过固件（BIOS/UEFI）阶段，大幅减少系统重启时间：

```bash
# 安装 kexec 工具
sudo apt install kexec-tools

# 重启到新内核而不经过固件 POST
# 节省时间可达 30 秒到分钟级
# sudo kexec -l /boot/vmlinuz-$(uname -r) --initrd=/boot/initrd.img-$(uname -r) --reuse-cmdline
# sudo kexec -e

# 注意：kexec 跳过了固件初始化阶段
# 这意味着：
#   - 硬件不重新初始化（可能留下不稳定状态）
#   - 不适用于更换硬件后
#   - 调试时建议正常重启
```

### 6.6 启动流程的替代实现

Linux 生态中除了 GRUB2 + systemd 这条主流路线，还有其他选择：

```
引导加载器替代方案：
════════════════════════════════════════════════════════════════

  rEFInd
  ├── 特点：图形化的 UEFI 引导管理器，自动探测操作系统
  ├── 优势：美观的图标界面，自动检测内核更新
  └── 适用：多系统共存 + 追求美观

  syslinux / extlinux
  ├── 特点：轻量级 BIOS 引导加载器
  ├── 优势：极简，配置清晰
  └── 适用：嵌入式系统、LiveUSB

  EFISTUB（直接 UEFI 引导内核）
  ├── 特点：完全不要引导加载器，UEFI 直接加载内核
  ├── 优势：最快启动速度，零引导加载器开销
  └── 适用：单系统、极客、systemd-boot 的底层机制

初始化系统替代方案：
════════════════════════════════════════════════════════════════

  sysvinit
  ├── 特点：传统的 init 系统
  └── 适用：老式系统、极小化容器

  OpenRC
  ├── 特点：Gentoo 开发的 init 系统
  └── 适用：Gentoo/Alpine Linux

  runit
  ├── 特点：极简 init + 服务监督
  └── 适用：Void Linux、容器

  s6
  ├── 特点：基于进程监督的设计
  └── 适用：Artix Linux

  但以上都不是 Ubuntu 24.04 的选择——
  systemd 是现代 Ubuntu 唯一官方支持的初始化系统。
```
