第 29 章你掌握了 systemd——启动服务、查看状态、管理依赖。现在，一个新维度向你展开：

这些问题的中心只有一个：**日志（Log）**——Linux 系统的"黑匣子"。如果说进程是系统的"心跳"，文件系统是系统的"骨架"，那么日志就是系统的"日记本"和"行车记录仪"。

### 1.3 历史背景：从 syslog 到 journald

Linux 的日志体系经历了两个时代的演变：

```
传统 syslog 时代（~1980s - 2015）：            systemd journal 时代（2015 - 至今）：
────────────────────────────────────           ────────────────────────────────────
协议：RFC 3164 / RFC 5424 (syslog)             协议：journald 私有二进制格式
守护进程：syslogd / rsyslogd / syslog-ng       守护进程：systemd-journald
传输方式：UDP/TCP + Unix Socket（/dev/log）    传输方式：Unix Socket + stdout/stderr 捕获
存储格式：纯文本（Plain Text）                  存储格式：结构化二进制（Binary Journal）
查询方式：grep / less                          查询方式：journalctl（结构化查询）
轮替方式：logrotate（外部工具）                 轮替方式：内置（journald.conf）+ logrotate
集中收集：需额外配置 syslog relay              集中收集：journald 原生支持远程转发
字段支持：无（所有内容混在 MSG 字段中）         字段支持：每个事件含数十个结构化字段
```

**关键时间线：**

```
1985   syslog 成为 4.3BSD 的一部分，syslogd 守护进程首次引入
       │
1998   rsyslog（RainerScript syslog）项目启动，提供过滤、队列、
       多线程和数据库输出等高级特性
       │
2011   systemd v38：journald 首次引入，作为 systemd 日志子系统
       │
2015   Ubuntu 15.04 切换到 systemd，journald 成为默认日志收集器
       │
2024   Ubuntu 24.04 LTS：systemd 255 + rsyslog 8.x 并行运行，
       journald 收集，rsyslog 将日志写入传统文本文件
```

> **为什么叫"journal"？** systemd 的设计者 Lennart Poettering 选择这个词来强调其设计理念——日志不仅仅是单向的"消息记录"，而是类似文件系统中的"日志文件系统（Journaling Filesystem）"概念，具备结构化、可索引、可验证的特性。

## 2. 核心概念

### 2.1 Linux 日志体系全景：双层协作架构

在 Ubuntu 24.04 中，日志的"旅程"分为两层——**journald** 负责收集，**rsyslog** 负责分发：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       Linux 日志体系双层协作架构                              │
│                                                                             │
│   ┌─────────────────────────── 日志来源层 ─────────────────────────────────┐ │
│   │                                                                       │ │
│   │  systemd 服务     传统 daemon     内核 ───printk──→ /dev/kmsg         │ │
│   │  (stdout/stderr)  (syslog API)   (Kernel)              │              │ │
│   │       │                │            │                  │              │ │
│   │       │    syslog(3)   │            │                  │              │ │
│   │       │     ─────────► │            │                  │              │ │
│   │       │                ▼            │                  │              │ │
│   │       │         ┌──────────┐        │                  │              │ │
│   │       │         │ /dev/log │◄───────┘                  │              │ │
│   │       │         │(Unix 套  │                           │              │ │
│   │       │         │ 接字)    │                            │              │ │
│   │       │         └────┬─────┘                            │              │ │
│   │       │              │                                  │              │ │
│   └───────┼──────────────┼──────────────────────────────────┼──────────────┘ │
│           │              │                                  │                │
│           │              ▼                                  ▼                │
│   ┌───────┴──────────────┼────── 收集层：systemd-journald ──┼──────────────┐ │
│   │       │              │                                  │              │ │
│   │       │         ┌────┴──────────────────────────────────┴──────┐       │ │
│   │       │         │            systemd-journald                  │       │ │
│   │       │         │                                              │       │ │
│   │       ▼         │  · 接收 service stdout/stderr（PID 1 转发）   │       │ │
│   │   journald      │  · 接收 /dev/log 上的 syslog 消息            │       │ │
│   │   直接捕获      │  · 接收 /dev/kmsg 的内核消息                  │       │ │
│   │                 │  · 存储为结构化二进制日志到                   │       │ │
│   │                 │    /run/log/journal/（易失）或                │       │ │
│   │                 │    /var/log/journal/（持久）                  │       │ │
│   │                 └────────────────────┬─────────────────────────┘       │ │
│   │                                     │                                  │ │
│   └─────────────────────────────────────┼──────────────────────────────────┘ │
│                                         │                                    │
│                                         ▼                                    │
│   ┌──────────────── 分发层：rsyslog ───────────────────────────────────────┐ │
│   │                                                                       │ │
│   │   ┌──────────────────────────────────────────────────────────────┐    │ │
│   │   │                      rsyslogd                                │    │ │
│   │   │                                                              │    │ │
│   │   │  · 通过 imuxsock 模块读取 /dev/log                            │    │ │
│   │   │  · 通过 imjournal 模块读取 journal（可选，Ubuntu 默认开启）     │    │ │
│   │   │  · 根据 /etc/rsyslog.conf 规则分发到不同文件                   │    │ │
│   │   └──────────────────────┬───────────────────────────────────────┘    │ │
│   │                          │                                            │ │
│   │          ┌───────────────┼───────────────┬──────────────┐             │ │
│   │          ▼               ▼               ▼              ▼             │ │
│   │   /var/log/syslog  /var/log/auth.log  /var/log/   /var/log/           │ │

│   │                                     (内核消息)  (守护进程)             │ │

│                                                                             │

```

**数据流的关键节点：**

| 节点 | 类型 | 作用 |
|------|------|------|
| `/dev/log` | Unix Domain Socket | syslog(3) 的写入入口，由 journald 和 rsyslog 共同监听 |
| `/dev/kmsg` | 字符设备 | 内核环形缓冲区（Kernel Ring Buffer），journald 读取内核消息 |
| `/run/systemd/journal/stdout` | Unix Socket | systemd 将服务的 stdout/stderr 转发至此 |
| `/run/log/journal/` | 目录 | journal 文件存储（易失，重启丢失，默认位置） |
| `/var/log/journal/` | 目录 | journal 文件存储（持久化，需手动创建该目录） |
| `/var/log/` | 目录 | rsyslog 输出的传统文本日志文件 |

### 2.2 syslog 协议：Facility 与 Priority

**syslog 协议**（定义于 RFC 5424）是 Linux 日志体系的基础通信协议。每条 syslog 消息由一个 **Facility**（设施/来源类别）和一个 **Priority**（优先级/严重级别）共同标识。

#### 2.2.1 Facility（设施）

Facility 表示"日志消息来自哪个子系统"。它是一个 0-23 的整数，对应预定义的类别：

```
┌─────────────────────────────────────────────────────────────────────┐
│                     syslog Facility 编码表                           │
│                                                                     │
│   代码    名称        说明                         典型产生者       │
│   ─────  ──────────  ──────────────────────────  ────────────────  │
│   0      kern        内核消息                     Linux 内核        │
│   1      user        用户级消息                   普通用户程序      │
│   2      mail        邮件系统                     Postfix/Sendmail  │
│   3      daemon      系统守护进程                 没有专用 facility │
│                                                   的守护进程       │
│   4      auth        安全/认证相关                 login, su, pam   │
│   5      syslog      syslog 内部消息              syslogd/rsyslogd  │
│   6      lpr         打印系统                     CUPS             │
│   7      news        网络新闻系统                 NNTP daemon      │
│   8      uucp        UUCP 子系统（已废弃）         UUCP             │
│   9      cron        定时任务                     cron, atd        │
│   10     authpriv    私密安全认证                  sshd, sudo       │
│   11     ftp         FTP 守护进程                 vsftpd/proftpd   │
│   12-15  -           保留/未定义                    -               │
│   16-23  local0~7    本地自定义                   用户应用          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**为什么需要 Facility？** 它让你能按消息来源分流日志。例如：
- 所有认证失败的消息（authpriv）写入 `/var/log/auth.log`，方便安全审计
- 所有内核消息（kern）写入 `/var/log/kern.log`，方便硬件调试
- 所有邮件消息（mail）写入 `/var/log/mail.log`，方便邮件系统排错

```bash
# 在 rsyslog 配置中，facility 用名称表示（不区分大小写）
# 例如：
auth,authpriv.*                 /var/log/auth.log
kern.*                          -/var/log/kern.log
local0.*                        /var/log/myapp.log
```

#### 2.2.2 Priority / Severity（优先级/严重级别）

Priority 表示"消息有多重要"。它是一个 0-7 的整数，数字越小越严重：

```
┌─────────────────────────────────────────────────────────────────────┐
│                     syslog Priority / Severity 编码表                │
│                                                                     │
│   代码  名称      全称           含义                      典型场景  │
│   ──── ──────── ────────────── ──────────────────────── ──────────  │
│   0    emerg    Emergency       系统不可用                内核崩溃  │
│                                  (System is unusable)     (panic)   │
│                                                                     │
│   1    alert    Alert           必须立即采取行动           磁盘故障  │
│                                  (Action must be taken              │
│                                   immediately)                      │
│                                                                     │
│   2    crit     Critical        严重情况                  硬件错误  │
│                                  (Critical conditions)              │
│                                                                     │
│   3    err      Error           错误情况                  服务崩溃  │
│                                  (Error conditions)                 │
│                                                                     │
│   4    warning  Warning         警告情况                  磁盘快满  │
│                                  (Warning conditions)               │
│                                                                     │
│   5    notice   Notice          正常但重要的事件           启动完成  │
│                                  (Normal but significant            │
│                                   condition)                        │
│                                                                     │
│   6    info     Informational   信息性消息                服务启动  │
│                                  (Informational messages)           │
│                                                                     │
│   7    debug    Debug           调试级别的消息            开发调试  │
│                                  (Debug-level messages)             │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Priority 的匹配规则：** `*.err` 匹配 err 及更严重的级别（emerg, alert, crit, err），而不是只匹配 err。即 `*.err` = priority <= 3 的所有消息。这是一个"向上匹配"的语义。

```bash
# rsyslog 中的 priority 用法示例：
# *.emerg             匹配所有 facility 的 emerg 级别消息
# kern.crit           匹配内核的 crit 及以上级别消息
# authpriv.warning    匹配认证的 warning 及以上级别消息
# mail.*              匹配邮件系统的所有级别消息
# *.=err              只匹配 err 级别（使用 = 前缀精确匹配）
# *.!=info            排除 info 级别（使用 ! 前缀取反）
# *.none              不匹配任何消息（用于排除）

# journalctl 中的使用（支持缩写）：
journalctl -p err      # emerg, alert, crit, err
journalctl -p warning  # emerg, alert, crit, err, warning
journalctl -p info     # 一切（最宽松）
```

> **注意：** journalctl 也使用 0-7 的编码，但命名略有不同：`emerg`, `alert`, `crit`, `err`, `warning`, `notice`, `info`, `debug`。与 syslog 完全兼容。

### 2.3 journald：systemd 的日志子系统

**systemd-journald** 是 systemd 的日志守护进程，作为系统中所有日志消息的"第一站"和"总汇点"。

```
┌─────────────────────────────────────────────────────────────────────┐
│                     journald 内部架构                                 │
│                                                                     │
│   输入源                                                             │
│   ┌─────────────────────────────────────────────────────────────┐   │
│   │                                                             │   │
│   │  /dev/log          ← syslog(3) API 调用（兼容传统程序）       │   │
│   │  /dev/kmsg         ← 内核环形缓冲区                           │   │
│   │  /run/systemd/      ← systemd 管理的服务 stdout/stderr       │   │
│   │    journal/stdout                                             │   │
│   │  /run/systemd/      ← 本地程序通过 journal API 直接写入       │   │
│   │    journal/socket                                             │   │
│   │  audit socket      ← 内核审计子系统                           │   │
│   │                                                             │   │
│   │         │                                                   │   │
│   │         ▼                                                   │   │
│   │  ┌──────────────────────────────────────────────────────┐  │   │
│   │  │              journald 核心处理                         │  │   │
│   │  │                                                      │  │   │
│   │  │  1. 解析消息并提取结构化字段                           │  │   │
│   │  │  2. 添加隐式字段（_PID, _UID, _GID, _COMM,           │  │   │
│   │  │     _SYSTEMD_UNIT, _TRANSPORT, _BOOT_ID, ...）        │  │   │
│   │  │  3. 写入二进制 journal 文件                            │  │   │
│   │  │  4. 转发给 syslog socket（供 rsyslog 消费）            │  │   │
│   │  │  5. 转发给 /dev/console, wall 等（按配置）             │  │   │
│   │  └──────────────────────┬───────────────────────────────┘  │   │
│   └─────────────────────────┼──────────────────────────────────┘   │
│                             │                                       │
│   输出                                                              │
│   ┌─────────────────────────────────────────────────────────────┐   │
│   │                                                             │   │
│   │  /run/log/journal/   ← journal 文件（易失模式，默认）         │   │
│   │  /var/log/journal/   ← journal 文件（持久模式，需手动创建）    │   │
│   │  syslog socket       ← 转发给 rsyslog/syslog-ng             │   │
│   │  /dev/console        ← 紧急消息输出到控制台                   │   │
│   │  journalctl          ← 用户查询                              │   │
│   │                                                             │   │
│   └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**journald 的核心优势：**

1. **结构化字段**：每条日志自动附带数十个隐式字段，无需依赖正则解析：
   - `_PID`：产生日志的进程 PID
   - `_UID`：产生日志的用户 UID
   - `_GID`：用户组 GID
   - `_COMM`：可执行文件名称
   - `_EXE`：可执行文件的完整路径
   - `_CMDLINE`：进程的完整命令行
   - `_SYSTEMD_UNIT`：所属的 systemd unit
   - `_SYSTEMD_USER_UNIT`：所属的用户级 unit
   - `_TRANSPORT`：消息传输方式（stdout/syslog/kernel/audit/driver/journal）
   - `_BOOT_ID`：本次启动的唯一标识
   - `_MACHINE_ID`：本机的唯一标识
   - `_HOSTNAME`：主机名
   - `PRIORITY`：syslog 优先级（0-7）
   - `MESSAGE`：实际消息正文
   - `MESSAGE_ID`：消息类型标识

2. **启动追踪**：通过 `_BOOT_ID` 可以精确查询特定一次启动周期内的所有日志

3. **完整性保护**：journal 文件使用前向安全密封（Forward Secure Sealing，FSS），可以检测日志是否被篡改

4. **按需索引**：journal 文件本身不建索引，查询时实时遍历，空间效率高

**在 Ubuntu 24.04 上启用持久化 journal：**

```bash
# 默认情况下，journal 存储在 /run/log/journal/（易失，重启丢失）
# 要启用持久化存储，需要创建 /var/log/journal/ 目录：

sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix /var/log/journal
sudo systemctl restart systemd-journald

# 验证
ls /var/log/journal/
# 输出：一个以 machine-id 命名的目录，如：
# 3e6c4c9b8c4a4b6e8e1b5a4c7d9f0a1b/

# 查看 journal 磁盘使用情况
journalctl --disk-usage
# 输出示例：
# Archived and active journals take up 72.0M in the file system.
```

### 2.4 rsyslog：传统 syslog 的现代实现

**rsyslog（Rocket-fast System for Log processing）** 是 Ubuntu 24.04 默认的 syslog 守护进程。它在 journald 之后运行，负责将收集到的日志**分发**为传统文本文件。

```
┌─────────────────────────────────────────────────────────────────────┐
│                     rsyslog 架构                                      │
│                                                                     │
│   输入模块（Input Modules）                                           │
│   ┌───────────────────────────────────────────────────────────────┐ │
│   │  imuxsock    ← 读取 /dev/log（Unix socket）                   │ │
│   │  imjournal   ← 读取 journald 的 journal（Ubuntu 24.04 默认）  │ │
│   │  imklog      ← 读取内核日志（/proc/kmsg）                     │ │
│   │  imtcp       ← TCP 端口 514 接收远程 syslog                    │ │
│   │  imudp       ← UDP 端口 514 接收远程 syslog                    │ │
│   └───────────────────────────────────────────────────────────────┘ │
│                               │                                      │
│                               ▼                                      │
│   ┌───────────────────────────────────────────────────────────────┐ │
│   │                    rsyslog 核心引擎                            │ │
│   │                                                               │ │
│   │  消息解析 → 规则引擎（Ruleset）→ 过滤 → 模板 → 队列            │ │
│   └───────────────────────────────────────────────────────────────┘ │
│                               │                                      │
│                               ▼                                      │
│   输出模块（Output Modules）                                          │
│   ┌───────────────────────────────────────────────────────────────┐ │
│   │  omfile      → 写入文件（如 /var/log/syslog）                 │ │
│   │  omusrmsg    → 发送给用户终端                                  │ │
│   │  omfwd       → 转发到远程 syslog 服务器                        │ │
│   │  ommysql     → 写入 MySQL/PostgreSQL 数据库                   │ │
│   │  omelasticsearch → 写入 Elasticsearch                         │ │
│   └───────────────────────────────────────────────────────────────┘ │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**rsyslog 的核心能力：**
- 基于 facility + priority 的精确路由规则
- 支持消息过滤、模板化输出
- 内存队列和磁盘队列（保证消息不丢失）
- 支持 TCP/TLS 加密传输
- 多线程处理，高吞吐量

### 2.5 journald 与 rsyslog 的协作关系

在 Ubuntu 24.04 中，journald 和 rsyslog 并非互斥，而是**互补协作**：

```
│   实际使用建议：                                                      │
│   ┌─────────────────────────────────────────────────────────────┐   │
│   │  · 日常排查 → journalctl（快速查询、结构化过滤）              │   │

│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.7 日志轮替（Log Rotation）

日志文件会持续增长。如果没有轮替机制，`/var/log/syslog` 可能几个月后占满整个磁盘。

**logrotate** 是 Linux 标准的日志轮替工具。它定期将旧日志重命名、压缩、保留一定数量后删除：

```
┌─────────────────────────────────────────────────────────────────────┐
│                    logrotate 轮替机制                                 │
│                                                                     │
│   原始文件: /var/log/myapp.log                                      │
│                                                                     │
│   第 1 次轮替：                                                      │
│   ┌─────────────────────────────────────────────────────────────┐   │
│   │  myapp.log  →  myapp.log.1  →  清空 myapp.log               │   │
│   └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│   第 2 次轮替：                                                      │
│   ┌─────────────────────────────────────────────────────────────┐   │
│   │  myapp.log  →  myapp.log.1                                   │   │
│   │  myapp.log.1 → myapp.log.2  →  清空 myapp.log               │   │
│   └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│   如果配置了 compress：                                              │
│   ┌─────────────────────────────────────────────────────────────┐   │
│   │  myapp.log  ← 当前                                            │   │
│   │  myapp.log.1.gz  ← 上一次压缩后的                             │   │
│   │  myapp.log.2.gz  ← 再上一次                                  │   │
│   │  myapp.log.3.gz  ← 被 rotate 3 限制，再旧的被删除            │   │
│   └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**logrotate 的运行时机：**

```bash
# logrotate 由 systemd timer 每天触发：
systemctl list-timers | grep logrotate
# 输出示例：
# Thu 2024-07-31 00:00:00 CST 13h left  ...  logrotate.timer

# 或者查看 cron（传统方式）：
cat /etc/cron.daily/logrotate
# cron 方式也是每天执行一次
```

**logrotate 配置的位置：**

```bash

# 各服务的独立配置（推荐）
ls /etc/logrotate.d/
# 输出示例：
# apache2  apt  dpkg  nginx  rsyslog  samba  unattended-upgrades
# 每个文件对应一个服务的日志轮替规则
```

## 3. 命令详解

### 3.1 journalctl：结构化日志查询

`journalctl` 是查询 systemd journal 的唯一入口。与 `grep` 加正则表达式的传统方式不同，`journalctl` 提供了**字段级别**的精确过滤。

#### 3.1.1 基本查询

```bash
# ===== 无参数：显示所有日志（从最早的开始） =====
journalctl
# 按 PageUp/PageDown 翻页，按 q 退出，按 / 搜索
# 注意：无参数时输出可能非常长，通常配合过滤条件使用

# ===== 查看本次启动的日志 =====
journalctl -b
# 等价于 journalctl --boot=0
# -b -1 查看上一次启动的日志
# -b -2 查看上上次启动的日志

# ===== 列出所有可查询的启动记录 =====
journalctl --list-boots
# 输出示例：
#   -3 3e6c4c9b... Mon 2024-07-28 08:00:00 CST—Mon 2024-07-28 22:00:00 CST
#   -2 a1b2c3d4... Tue 2024-07-29 08:00:00 CST—Tue 2024-07-29 22:00:00 CST
#   -1 f9e8d7c6... Wed 2024-07-30 08:00:00 CST—Wed 2024-07-30 09:00:00 CST
#    0 1a2b3c4d... Wed 2024-07-30 09:01:00 CST—Wed 2024-07-30 10:30:00 CST
#    ↑ 当前启动

# ===== 限制最近的 N 条 =====
journalctl -n 20
# 显示最新的 20 条

# ===== 实时跟踪（类似 tail -f） =====
journalctl -f
# 按 Ctrl+C 停止

# ===== 跳到日志末尾 =====
journalctl -e
# 直接显示最近的日志页
```

#### 3.1.2 按时间过滤

```bash
# ===== --since 和 --until =====

# 查看今天的日志
journalctl --since today

# 查看昨天的日志
journalctl --since yesterday --until today

# 查看最近 1 小时
journalctl --since "1 hour ago"

# 查看最近 30 分钟
journalctl --since "30 min ago"

# 精确时间范围
journalctl --since "2024-07-30 09:00:00" --until "2024-07-30 10:00:00"

# 绝对时间（支持多种格式）
journalctl --since "2024-07-30"              # 当天 00:00 开始
journalctl --since "2024-07-30 09:00:00"     # 精确到秒
journalctl --since "2024-07-30 09:00"        # 精确到分
```

**--since / --until 支持的日期格式：**

| 格式 | 示例 | 说明 |
|------|------|------|
| `today` | `--since today` | 今天 00:00:00 |
| `yesterday` | `--since yesterday` | 昨天 00:00:00 |
| `tomorrow` | `--until tomorrow` | 明天 00:00:00 |
| `now` | `--since "5 min ago"` | 5 分钟前 |
| `N hour/min/sec ago` | `--since "2 hours ago"` | N 小时/分钟/秒前 |
| `YYYY-MM-DD HH:MM:SS` | `--since "2024-07-30 09:00:00"` | 精确时间戳（24小时制） |
| `YYYY-MM-DD` | `--since "2024-07-30"` | 当天 00:00:00 |

#### 3.1.3 按 Unit 过滤

```bash
# ===== 按 systemd unit 过滤 =====

# 查看特定服务的日志
journalctl -u ssh.service
# 或简写：
journalctl -u ssh

# 结合时间过滤
journalctl -u nginx --since "1 hour ago"

# 查看多个 unit 的日志
journalctl -u ssh -u nginx

# 查看本次启动中某个服务的日志
journalctl -b -u cron
```

#### 3.1.4 按优先级过滤

```bash
# ===== -p 参数：按优先级过滤 =====

# 查看错误及更严重的日志
journalctl -p err
# 等价于：emerg, alert, crit, err

# 查看警告及更严重的日志
journalctl -p warning
# 等价于：emerg, alert, crit, err, warning

# 只查看 emerg 级别
journalctl -p emerg

# 查看特定范围
journalctl -p warning..err
# 只显示 warning, notice, info(?), err(?)
# 注意：.. 表示数值范围，warning=4, err=3，所以 4..3 是无效范围
# 正确的范围示例：journalctl -p err..warning
# 即 priority 3-4 之间的消息（err 和 warning）

# 实际中更常用的是 "不低于某级别" 的用法：
journalctl -p info     # 所有消息（最宽松）
journalctl -p err      # 只看错误和更严重的
```

**journalctl -p 级别的数值对照：**

| 级别名 | 数值 | -p 参数效果 |
|--------|------|------------|
| `emerg` | 0 | 只显示 emerg |
| `alert` | 1 | emerg, alert |
| `crit` | 2 | emerg, alert, crit |
| `err` | 3 | emerg, alert, crit, err |
| `warning` | 4 | emerg .. warning |
| `notice` | 5 | emerg .. notice |
| `info` | 6 | emerg .. info（几乎所有消息） |
| `debug` | 7 | 所有消息（包括调试） |

#### 3.1.5 按字段精确过滤

这是 journalctl 最强大的特性：**字段级（Field-Level）过滤**。

```bash
# ===== 查看所有可用的 journal 字段 =====
journalctl -o verbose --no-pager | head -50
# 你会看到类似以下的结构化字段：
# _UID=1000
# _GID=1000
# _PID=2345
# _COMM=sshd
# _EXE=/usr/sbin/sshd
# _SYSTEMD_UNIT=ssh.service
# _TRANSPORT=syslog
# _BOOT_ID=1a2b3c4d5e6f...
# _MACHINE_ID=3e6c4c9b8c4a...
# _HOSTNAME=myserver
# PRIORITY=6
# SYSLOG_FACILITY=10
# SYSLOG_IDENTIFIER=sshd

# ===== 按用户过滤 =====
# 查看 root 用户(UID=0)产生的所有日志
journalctl _UID=0

# 查看当前用户产生的日志
journalctl _UID=$(id -u)

# ===== 按进程过滤 =====
# 查看 PID 为 1234 的进程产生的日志
journalctl _PID=1234

# 查看所有 sshd 进程产生的日志
journalctl _COMM=sshd

# 按可执行文件完整路径过滤
journalctl _EXE=/usr/sbin/sshd

# ===== 按 systemd unit 过滤（与 -u 等价） =====
journalctl _SYSTEMD_UNIT=ssh.service

# ===== 按传输方式过滤 =====
# 查看来自内核的消息
journalctl _TRANSPORT=kernel

# 查看来自 syslog 的消息
journalctl _TRANSPORT=syslog

# 查看服务 stdout/stderr 的消息
journalctl _TRANSPORT=stdout

# ===== 组合过滤 =====
# 查看 root 用户在过去 1 小时内产生的所有错误
journalctl _UID=0 -p err --since "1 hour ago"

# 查看 ssh.service 的警告及以上级别的日志

# 查看 nginx 和 php-fpm 两个单元的错误日志

```

**_TRANSPORT 的所有取值：**

| 值 | 含义 |
|----|------|
| `kernel` | 内核消息（来自 /dev/kmsg） |
| `syslog` | 通过 syslog(3) API 发送的消息 |
| `stdout` | systemd 服务捕获的标准输出 |
| `journal` | 通过 journal API 直接写入的消息 |
| `audit` | 内核审计子系统的消息 |
| `driver` | systemd 内部生成的消息 |

### 3.3 logger：手动写入日志

`logger` 命令让你从命令行或 Shell 脚本中向 syslog 写入自定义消息。

```bash
# ===== 基本用法 =====
# 写入一条简单的日志消息
logger "Hello from the shell"
# 验证：查看刚才写入的消息
journalctl -n 1
# 输出：
# Jul 30 11:00:00 myserver ubuntu[12345]: Hello from the shell

# ===== 指定 priority =====
logger -p user.err "Something went wrong!"
journalctl -n 1 -p err
# 参数说明：-p <facility>.<priority>
# 如：user.err, local0.info, auth.warning

# ===== 指定 tag（标识符） =====
logger -t MYBACKUP "Backup started"
journalctl -n 1
# 输出：
# Jul 30 11:00:00 myserver MYBACKUP: Backup started
# 默认 tag 是当前用户名

# ===== 包含 PID =====
logger -i "Message with PID"
# 输出示例：
# Jul 30 11:00:00 myserver ubuntu[12345]: Message with PID
# -i 参数将当前进程的 PID 附加到消息中

# ===== 从标准输入读取 =====
echo "This comes from stdin" | logger

# ===== 从文件读取内容并写入 =====
logger -f /etc/hostname
# 将文件内容作为日志消息发送

# ===== 写入到远程 syslog 服务器 =====
# logger -n 192.168.1.50 -P 514 "Remote log message"
# -n: 远程主机 IP
# -P: 端口（默认 514）

# ===== 综合示例：备份脚本中的日志 =====
cat > ~/log-lesson30/backup-with-logging.sh << 'SCRIPT'
#!/bin/bash
BACKUP_DIR="/tmp/backups"
LOG_TAG="MYBACKUP"

# 使用 logger 记录关键步骤
logger -t "$LOG_TAG" -p local0.info "Backup started at $(date)"

mkdir -p "$BACKUP_DIR"

if cp /etc/hosts "$BACKUP_DIR/hosts.bak" 2>/dev/null; then
    logger -t "$LOG_TAG" -p local0.info "Backup of /etc/hosts succeeded"
else
    logger -t "$LOG_TAG" -p local0.err "Backup of /etc/hosts FAILED"
    exit 1
fi

logger -t "$LOG_TAG" -p local0.info "Backup completed at $(date)"
exit 0
SCRIPT

chmod +x ~/log-lesson30/backup-with-logging.sh

# 运行脚本
~/log-lesson30/backup-with-logging.sh

# 查看自定义日志（按 tag 过滤）
journalctl -t MYBACKUP
# 或使用 SYSLOG_IDENTIFIER 字段：
journalctl SYSLOG_IDENTIFIER=MYBACKUP
```

**logger 常用参数表：**

| 参数 | 说明 | 示例 |
|------|------|------|
| `-p` | 指定 facility.priority | `logger -p local0.err "Error"` |
| `-t` | 指定 tag（标识符） | `logger -t MYAPP "Message"` |
| `-i` | 在消息中包含 PID | `logger -i "With PID"` |
| `-f` | 从文件读取消息内容 | `logger -f /path/to/file` |
| `-n` | 发送到远程 syslog 服务器 | `logger -n 192.168.1.50` |
| `-P` | 远程端口（配合 -n） | `logger -n 192.168.1.50 -P 514` |
| `-s` | 同时输出到 stderr | `logger -s "Also to stderr"` |
| `--` | 停止解析开关（防止 - 开头的消息被误解析） | `logger -- "-starting-service"` |

#### 3.4.2 logrotate 子配置文件详解

```bash
# 查看 rsyslog 的 logrotate 配置
cat /etc/logrotate.d/rsyslog
```

典型的 `/etc/logrotate.d/rsyslog` 配置及逐行解释：

```
/var/log/syslog                          # 要轮替的日志文件（支持通配符）
/var/log/mail.log
/var/log/kern.log
/var/log/auth.log
/var/log/user.log
/var/log/cron.log
{
        rotate 4                         # 保留 4 份旧日志（.1, .2, .3, .4）
        daily                           # 每天轮替一次
        missingok                       # 如果日志文件不存在，不报错
        notifempty                      # 如果日志文件为空，不轮替
        delaycompress                   # 延迟压缩：最新的那份 .1 不压缩
        compress                        # 压缩旧日志（gzip）
        sharedscripts                   # 所有文件轮替完后只执行一次 postrotate
        postrotate                      # 轮替后执行的脚本
                /usr/lib/rsyslog/rsyslog-rotate
                # 这个脚本向 rsyslogd 发送 HUP 信号，让它重新打开日志文件
        endscript
}
```

**logrotate 配置指令详解：**

| 指令 | 说明 | 典型值 |
|------|------|--------|
| `daily` | 每天轮替一次 | `daily`, `weekly`, `monthly`, `yearly` |
| `rotate N` | 保留 N 份旧日志 | `rotate 4`（保留 .1 到 .4） |
| `size N` | 日志达到指定大小时轮替 | `size 100M`, `size 500k` |
| `maxsize N` | 日志超过该大小时即使在预定时间之前也轮替 | `maxsize 100M` |
| `minsize N` | 日志小于该大小时不轮替（即使到了预定时间） | `minsize 1M` |
| `compress` | 用 gzip 压缩旧日志 | `compress` |
| `delaycompress` | 延迟一轮压缩（最新归档不压缩） | `delaycompress` |
| `nocompress` | 不压缩 | `nocompress` |
| `missingok` | 日志文件不存在时不报错 | `missingok` |
| `nomissingok` | 日志文件不存在时报错 | `nomissingok` |
| `notifempty` | 文件为空时不轮替 | `notifempty` |
| `ifempty` | 文件为空时也轮替（默认） | `ifempty` |
| `create MODE OWNER GROUP` | 轮替后创建指定权限的新文件 | `create 0640 syslog adm` |
| `nocreate` | 不创建新文件 | `nocreate` |
| `copytruncate` | 复制后截断原文件（不重命名） | `copytruncate` |
| `sharedscripts` | 所有匹配文件轮替后只运行一次脚本 | `sharedscripts` |
| `nosharedscripts` | 每个文件轮替后都运行脚本（默认） | `nosharedscripts` |
| `postrotate / endscript` | 轮替后执行的脚本 | `postrotate` ... `endscript` |
| `prerotate / endscript` | 轮替前执行的脚本 | `prerotate` ... `endscript` |
| `dateext` | 使用日期作为后缀（如 `.20240730`） | `dateext` |
| `dateformat` | 日期后缀的格式 | `dateformat -%Y%m%d` |
| `maxage N` | 删除超过 N 天的旧日志 | `maxage 30` |
| `olddir DIR` | 将旧日志移动到指定目录 | `olddir /var/log/old` |
| `su USER GROUP` | 以指定用户/组身份执行轮替（Ubuntu 24.04 默认需要） | `su root syslog` |

#### 3.4.3 编写自定义 logrotate 配置

```bash
# ===== 场景：为一个自定义应用配置日志轮替 =====

# 第 1 步：创建测试日志目录和文件
sudo mkdir -p /var/log/myapp
sudo touch /var/log/myapp/myapp.log
sudo chmod 644 /var/log/myapp/myapp.log

# 生成一些测试日志
for i in $(seq 1 100); do
    echo "[$(date)] - Entry $i - This is a log message for testing logrotate" | \
        sudo tee -a /var/log/myapp/myapp.log > /dev/null
done

# 检查文件大小
ls -lh /var/log/myapp/myapp.log

# 第 2 步：创建 logrotate 配置文件
sudo tee /etc/logrotate.d/myapp << 'EOF'
/var/log/myapp/myapp.log {
    daily                    # 每天轮替
    rotate 7                # 保留 7 天
    compress                # 压缩旧日志
    delaycompress          # 延迟压缩（最新的备份不压缩）
    missingok              # 文件不存在时不报错
    notifempty             # 文件为空不轮替
    create 644 root root   # 创建新文件
    maxsize 10M            # 超过 10MB 强制轮替
    dateext                # 使用日期后缀
    dateformat -%Y%m%d     # 日期格式

    postrotate
        # 通知应用重新打开日志文件（示例）
        # /bin/systemctl reload myapp.service > /dev/null 2>&1 || true
        echo "Log rotated at $(date)" >> /var/log/myapp/rotate.log
    endscript
}
EOF

# 第 3 步：测试配置是否正确
sudo logrotate -d /etc/logrotate.d/myapp
# -d: debug 模式（dry-run，不实际执行）
# 检查输出中的 WARNING 和 ERROR

# 第 4 步：强制执行一次轮替（即使不到轮替时间）
sudo logrotate -f /etc/logrotate.d/myapp
# -f: force 模式（强制执行，忽略时间条件）

# 第 5 步：验证结果
ls -lh /var/log/myapp/
# 你应该看到：
# myapp.log              ← 新的空日志文件
# myapp.log-20240730.gz  ← 被压缩的旧日志
# rotate.log             ← postrotate 脚本写入的记录
```

**logrotate 命令常用参数：**

| 参数 | 说明 |
|------|------|
| `-d` | Debug 模式，模拟执行但不实际修改文件 |
| `-f` | 强制轮替，忽略时间/大小条件 |
| `-v` | 详细输出（Verbose） |
| `-s FILE` | 指定状态文件路径（默认 `/var/lib/logrotate/status`） |
| `CONFIG` | 指定配置文件路径 |

典型的 `50-default.conf` 核心规则：

#### 3.5.2 规则语法详解

**基本格式：**

```
<facility>.<priority>    <action>
```

**facility 和 priority 的写法：**

| 写法 | 含义 |
|------|------|
| `*` | 所有 facility 或所有 priority |
| `facility1,facility2` | 匹配多个 facility |
| `*.priority` | 所有 facility 的指定 priority |
| `facility.*` | 指定 facility 的所有 priority |
| `facility.=priority` | 精确匹配（只用 = 号时） |
| `facility.!=priority` | 排除（不等于） |
| `*.none` | 排除所有（常用于排除某个 facility） |

```bash
# 配置示例详解

# 示例 1：将所有认证消息写入 auth.log
# auth,authpriv.*  /var/log/auth.log
# ↑ 匹配 auth 和 authpriv 两个 facility 的所有 priority 消息

# 示例 2：将所有消息写入 syslog，但排除认证消息
# *.*;auth,authpriv.none  /var/log/syslog
# ↑ 所有 facility.priority，但 auth 和 authpriv 排除

# 示例 3：将内核的所有 critical 消息写入单独文件
# kern.crit  /var/log/kern-crit.log

# 示例 4：文件路径前的 - 号表示异步写入（性能更好，但崩溃时可能丢失消息）
# kern.*  -/var/log/kern.log
# ↑ 前面有 - 号 = 不立即同步到磁盘
# ↑ 没有 - 号 = 每条消息都 fsync（慢但安全）

# 示例 5：emerg 级消息发送到所有登录用户的终端
# *.emerg  :omusrmsg:*
```

#### 3.5.3 编写自定义 rsyslog 规则

```bash
# ===== 场景 1：将某个应用的消息写入独立文件 =====

# 第 1 步：创建自定义规则文件
sudo tee /etc/rsyslog.d/30-myapp.conf << 'EOF'
# 将 facility 为 local0 的所有消息写入 /var/log/myapp.log
local0.*                        /var/log/myapp.log

# 将 local0 的错误级别单独写一份
local0.err                      /var/log/myapp-error.log

# 将 local1 的消息转发到远程服务器（取消注释以启用）
# local1.*                      @@192.168.1.100:514
# @@ 表示 TCP，@ 表示 UDP
EOF

# 第 2 步：创建目标日志文件
sudo touch /var/log/myapp.log /var/log/myapp-error.log
sudo chmod 644 /var/log/myapp.log /var/log/myapp-error.log

# 第 3 步：重启 rsyslog 以加载新配置
sudo systemctl restart rsyslog
# 或使用 reload（如果支持）：
# sudo systemctl reload rsyslog

# 第 4 步：测试
logger -p local0.info "Test message from myapp to local0.info"
logger -p local0.err "Test error from myapp to local0.err"

# 验证
sudo tail -n 5 /var/log/myapp.log
# 应该看到刚才写入的消息

sudo tail -n 5 /var/log/myapp-error.log
# 应该只看到错误级别的消息
```

```bash

sudo tee /etc/rsyslog.d/40-discard-noisy.conf << 'EOF'

:msg, contains, "DHCPACK"                    stop
:msg, contains, "dnsmasq-dhcp"               stop

# stop 表示"处理到此为止，不再继续往下匹配"

```

```bash
# ===== 场景 3：使用高级过滤（RainerScript 语法） =====

sudo tee /etc/rsyslog.d/35-advanced-filter.conf << 'EOF'
# RainerScript 风格的过滤（比传统的 facility.priority 更灵活）
# 将包含 "ERROR" 且来自特定程序的日志写入专用文件

if $programname == "myapp" and $syslogseverity <= 3 then {
    action(type="omfile" file="/var/log/myapp-critical.log")
    stop
}

# $syslogseverity 的值：
# 0=emerg, 1=alert, 2=crit, 3=err, 4=warning, 5=notice, 6=info, 7=debug
# $syslogseverity <= 3 即 err 及以上

# 将 nginx 的日志单独分流（如果 nginx 通过 syslog 写日志）
if $programname == "nginx" then {
    action(type="omfile" file="/var/log/nginx-syslog.log")
    stop
}
EOF

sudo systemctl restart rsyslog
```

（4）使用日期作为后缀，格式为 `-YYYYMMDD`。
（5）文件为空时不轮替，文件不存在时不报错。

```bash
# 第 1 步：创建目录和测试日志
sudo mkdir -p /var/log/exercise-app
for i in $(seq 1 500); do
    echo "[$(date)] Line $i - Exercise log for logrotate testing" | \
        sudo tee -a /var/log/exercise-app/app.log > /dev/null
done
ls -lh /var/log/exercise-app/app.log

sudo tee /etc/logrotate.d/exercise-app << 'EOF'
/var/log/exercise-app/app.log {

    rotate 10
    compress
    delaycompress
    dateext

    missingok

# 第 5 步：验证结果

# 应看到：
```

## 5. 常见错误与排错

### 5.1 错误：`journalctl` 提示普通用户看不到日志

```bash
# 症状：
journalctl
# 输出：
# No journal files were found.
# 或者只能看到当前用户的日志，看不到系统日志

# 原因：
# journald 默认只允许 root 和 adm/systemd-journal 组的用户查看所有日志

# 排查：
groups $(whoami)
# 查看当前用户所属的组

# 解决方法 1：将用户加入 adm 组
sudo usermod -a -G adm $(whoami)
# 然后重新登录（logout 再 login）使组生效

# 解决方法 2：将用户加入 systemd-journal 组
sudo usermod -a -G systemd-journal $(whoami)
# 重新登录后生效

# 验证：
groups
# 应该能看到 adm 或 systemd-journal
```

### 5.2 错误：journal 日志丢失（重启后之前的日志不见了）

```bash
# 症状：
# 重启系统后，journalctl -b -1 显示 "Data has no entries"
# 或者之前的 journal 日志都不见了

# 原因：
# 默认的 journal 存储路径是 /run/log/journal/（tmpfs，易失存储）
# 重启后内容自动消失

# 排查：
ls -la /var/log/journal/
# 如果目录不存在或为空，说明没有启用持久化

# 解决方法：启用持久化存储
sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix /var/log/journal
sudo systemctl restart systemd-journald

# 验证：
ls /var/log/journal/
# 应该出现一个以 machine-id 命名的目录

# 验证持久化是否生效：
sudo journalctl --flush
# 将 /run/log/journal/ 中的日志刷写到 /var/log/journal/
```

### 5.3 错误：`journalctl --disk-usage` 显示 journal 占用过多空间

```bash
# 症状：
journalctl --disk-usage
# 输出：
# Archived and active journals take up 4.2G in the file system.

# 原因：
# journal 没有配置空间上限，持续增长

# 解决方法 1：立即清理
# 按大小清理
sudo journalctl --vacuum-size=500M
# 按时间清理
sudo journalctl --vacuum-time=4weeks

# 解决方法 2：配置自动限制
sudo tee -a /etc/systemd/journald.conf << 'EOF'

# 限制持久 journal 总大小
SystemMaxUse=500M

# 限制运行时 journal 总大小
RuntimeMaxUse=100M

# 单个 journal 文件最大大小
SystemMaxFileSize=100M

# 最大保留时间
MaxRetentionSec=1month
EOF

sudo systemctl restart systemd-journald

# 验证配置生效
journalctl --disk-usage
```

### 5.4 错误：logrotate 没有按时轮替

```bash
# 症状：
# 日志文件持续增长，已经很久没有被轮替了

# 排查步骤：
# 第 1 步：检查 logrotate 的定时器/cron 是否正常
systemctl status logrotate.timer
# 或：
ls -la /etc/cron.daily/logrotate

# 第 2 步：手动测试配置
sudo logrotate -d /etc/logrotate.conf
# 查看是否有错误信息

# 第 3 步：查看 logrotate 的状态文件
sudo cat /var/lib/logrotate/status
# 该文件记录了每个日志文件上次轮替的时间
# 格式：log_path date
# 如："/var/log/syslog" 2024-7-30-10:0:0

# 第 4 步：手动强制执行
sudo logrotate -fv /etc/logrotate.conf
# 观察输出中的错误信息

# 常见原因与解决：
# 1. 时间条件未满足 → 使用 -f 强制轮替，或等待定时触发
# 2. 权限不足 → 检查 /var/log/ 下文件的权限
# 3. 配置语法错误 → 使用 logrotate -d 检查
# 4. notifempty + 文件为空 → 去掉 notifempty 或向文件写入内容
# 5. delaycompress 默认让旧归档不压缩，不是不轮替（注意区分）
```

### 5.5 错误：rsyslog 配置不生效

```bash
# 症状：
# 修改了 /etc/rsyslog.d/ 下的配置，但日志没有按预期路由

# 排查步骤：
# 第 1 步：检查配置语法
sudo rsyslogd -N1
# 如果有错误，它会明确报告哪个文件哪一行有问题

# 第 2 步：确认是否重启了 rsyslog
sudo systemctl restart rsyslog
# 或 reload（部分配置支持热加载）：
# sudo systemctl reload rsyslog

# 第 3 步：检查目标文件是否存在且可写
sudo touch /var/log/myapp.log
sudo chmod 644 /var/log/myapp.log
# 注意：rsyslog 以 syslog 用户身份运行，该用户需要对目标文件有写权限

# 第 4 步：确认规则没有被前面的规则"吞掉"
# rsyslog 从上到下匹配规则，如果某条消息被前面的规则匹配并
# 跳到了另一个 ruleset 或被 stop 终止，就不会到达后面的规则

# 第 5 步：查看 rsyslog 的运行日志
sudo journalctl -u rsyslog --since "5 min ago"
# 或：
sudo grep rsyslog /var/log/syslog | tail -20

# 第 6 步：使用 logger 逐条测试
logger -p local0.info "test 1"
sudo tail -1 /var/log/myapp.log
# 如果没有出现，说明规则没有生效

# 第 7 步：确认文件名中的数字前缀是否正确
ls /etc/rsyslog.d/
# 文件按字母顺序加载，数字前缀控制加载顺序
# 如果前面的文件中有 stop 指令，后面的规则可能不会执行
```

### 5.6 错误：/var/log/ 磁盘空间被日志占满

```bash
# 症状：
df -h /
# 输出显示根分区使用率 100%
# 或：
df -h /var/log
# 输出显示 /var/log 所在分区满了

# 排查步骤：
# 第 1 步：快速定位大文件
sudo du -sh /var/log/*
# 或找出最大的 10 个文件：
sudo find /var/log -type f -exec du -h {} + | sort -rh | head -10

# 第 2 步：识别异常增长的文件
ls -lhS /var/log/
# -S: 按大小排序

# 常见原因与解决方法：
# 原因 1：某个服务疯狂输出错误日志
# 解决：先用 journalctl -p err 定位问题服务，修复根本原因

# 原因 2：logrotate 没有正常工作
# 解决：强制运行 sudo logrotate -f /etc/logrotate.conf

# 原因 3：journal 占用了大量空间
# 解决：
sudo journalctl --vacuum-size=500M

# 原因 4：某个日志文件被删除但句柄未释放（lsof 可查看）
# 解决：重启对应的服务，让服务释放已删除文件的句柄
sudo lsof | grep deleted | grep /var/log

# 紧急处理：快速释放空间
sudo journalctl --vacuum-size=200M
sudo logrotate -f /etc/logrotate.conf
# 手动截断超大文件（谨慎使用，会丢失日志）：
# sudo truncate -s 0 /var/log/problematic.log
```

### 5.7 错误：`Failed to parse priority` 或类似错误

```bash
# 症状（journalctl）：
journalctl -p critical
# 错误：
# Failed to parse log level "critical"

# 原因：
# journalctl 使用 syslog 标准级别名，不支持 "critical"
# 正确的级别名是 "crit"

# 解决方法：使用正确的级别名
journalctl -p crit     # ✓ 正确（不是 critical）
journalctl -p err      # ✓ 正确（不是 error）
journalctl -p warning  # ✓ 正确（不是 warn）

# 级别名的正确写法：
# emerg, alert, crit, err, warning, notice, info, debug

# 级别名的错误写法：
# emergency, critical, error, warn  ← 这些都不被识别
```

### 6.2 journalctl 与 grep/awk 的管道组合

journalctl 的强大在于结构化查询，但当你需要更复杂的文本处理时，可以与 grep/awk 组合：

```bash
# ===== 管道到 grep =====
# 查找日志中包含特定关键词的行
journalctl --since today | grep -i "timeout"

# 统计某个错误出现的次数
journalctl -p err --since yesterday | grep -c "Connection refused"

# ===== 管道到 awk =====
# 提取特定字段做统计
journalctl -u nginx --since "1 hour ago" -o cat | \
    awk '{print $1}' | sort | uniq -c | sort -rn

# 统计每种 priority 的分布
journalctl -b -o json | \
    jq -r '.PRIORITY // "unknown"' | \
    sort | uniq -c | sort -rn
# 注意：需要安装 jq（sudo apt install jq）

# ===== 按进程名统计日志数量 =====
journalctl -b -o json --no-pager | \
    jq -r '._COMM // "unknown"' | \
    sort | uniq -c | sort -rn | head -10
# 输出示例：
#    2345 sshd
#    1234 systemd
#     890 cron
#     567 sudo
```

### 6.3 集中式日志：远程 syslog 转发

在生产环境中，通常需要将多台服务器的日志集中收集到一台日志服务器。

```bash
# ===== 客户端配置（发送端） =====
# 假设日志服务器 IP 为 192.168.1.100

sudo tee /etc/rsyslog.d/50-remote-forward.conf << 'EOF'
# 使用 UDP（不可靠但简单）
*.* @192.168.1.100:514

# 或使用 TCP（可靠传输）
# *.* @@192.168.1.100:514

# 只转发特定消息
# authpriv.* @@192.168.1.100:514
# local0.*  @@192.168.1.100:514
EOF

sudo systemctl restart rsyslog

# ===== 服务端配置（接收端） =====
# 在日志服务器上（192.168.1.100）

# 第 1 步：加载 TCP/UDP 接收模块
sudo tee /etc/rsyslog.d/50-remote-receive.conf << 'EOF'
# 加载 UDP 接收模块
module(load="imudp")
input(type="imudp" port="514")

# 加载 TCP 接收模块
module(load="imtcp")
input(type="imtcp" port="514")

# 将接收到的远程日志按主机名分目录存储
$template RemoteLogs,"/var/log/remote/%HOSTNAME%/%$YEAR%-%$MONTH%-%$DAY%.log"
*.* ?RemoteLogs
EOF

sudo systemctl restart rsyslog

# 第 2 步：检查端口是否监听
ss -tunlp | grep 514
# 输出示例：
# udp  UNCONN  0  0  0.0.0.0:514  0.0.0.0:*  users:(("rsyslogd",pid=890,fd=15))
# tcp  LISTEN  0  25 0.0.0.0:514  0.0.0.0:*  users:(("rsyslogd",pid=890,fd=16))

# 第 3 步：防火墙放行（如果启用了 ufw）
sudo ufw allow 514/tcp
sudo ufw allow 514/udp
```

### 6.4 journald 的完整性保护：FSS 密封

journald 支持**前向安全密封（Forward Secure Sealing，FSS）**，用于检测日志是否被篡改：

```bash
# 第 1 步：生成 FSS 密钥
sudo journalctl --setup-keys
# 输出：
# Machine ID: 3e6c4c9b8c4a4b6e8e1b5a4c7d9f0a1b
# Key Fingerprint: ABC1-2345-DEF6-7890-GHIJ-KLMN-OPQR-STUV
# The sealing key is: /var/log/journal/3e6c4.../fss
# FSS 密钥会自动保存

# 第 2 步：验证 journal 完整性
sudo journalctl --verify
# 输出示例：
# PASS: /var/log/journal/3e6c.../system.journal
# PASS: /var/log/journal/3e6c.../user-1000.journal
# 如果出现 FAIL，说明日志可能被篡改或损坏

# 第 3 步：验证特定文件
sudo journalctl --verify --file=/var/log/journal/3e6c.../system.journal

# 注意：
# · FSS 只验证启用密封之后写入的日志
# · 损坏的 journal 文件可能无法通过验证
# · FSS 不能防止日志被删除，只能检测篡改
```

### 6.5 分析 sudo 使用记录

```bash
# ===== 审计谁在什么时间执行了什么 sudo 命令 =====

# 方法 1：从 auth.log 提取
sudo grep "sudo:" /var/log/auth.log | tail -20
# 输出格式：
# Jul 30 09:10:01 myserver sudo: ubuntu : TTY=pts/0 ; PWD=/home/ubuntu ; USER=root ; COMMAND=/usr/bin/systemctl restart nginx

# 方法 2：从 journal 提取
journalctl _COMM=sudo -o cat --no-pager
# 更方便阅读，但没有完整的上下文

# 方法 3：详细分析（用 awk 格式化）
sudo grep "sudo:.*COMMAND=" /var/log/auth.log | \
    awk '{
        user=$5;
        cmd_start=index($0, "COMMAND=");
        cmd=substr($0, cmd_start+8);
        print $1, $2, $3, "USER:", user, "|", cmd
    }'
# 输出示例：
# Jul 30 09:10:01 USER: ubuntu: | /usr/bin/systemctl restart nginx
# Jul 30 10:15:22 USER: ubuntu: | /usr/bin/apt update
```

### 6.6 构建自定义日志监控脚本

```bash
# 使用 journalctl 的 JSON 输出来构建简单的日志监控

cat > ~/log-lesson30/log-monitor.sh << 'SCRIPT'
#!/bin/bash
# 简易日志监控脚本：检查最近 5 分钟内是否有错误

        echo "=== Error Report: $(date) ==="
        echo "Total errors: $ERROR_COUNT"
        echo ""
        echo "Error details:"

    } >> "$ALERT_FILE"

    echo ""
    echo "Errors by unit:"
    journalctl -p err --since "$MONITOR_PERIOD ago" -o json --no-pager 2>/dev/null | \
        jq -r '. | "\(._SYSTEMD_UNIT // "unknown")"' 2>/dev/null | \
        sort | uniq -c | sort -rn
else
    echo "[OK] No errors in the last $MONITOR_PERIOD"
fi
SCRIPT

chmod +x ~/log-lesson30/log-monitor.sh
~/log-lesson30/log-monitor.sh
```

### 6.7 通过 logger 实现应用级日志标准化

```bash
# 在生产环境中，建议应用直接通过 syslog(3) API 写入日志
# 但 Shell 脚本可以通过 logger 达到相同效果

cat > ~/log-lesson30/std-logging-lib.sh << 'LIBRARY'
#!/bin/bash
# ============================================================
# 标准化 Shell 脚本日志库
# 用法：source 本文件后，使用 log_info / log_warn / log_err
# ============================================================

# 配置区：按需修改
LOG_TAG="${LOG_TAG:-MYSCRIPT}"
LOG_FAC="${LOG_FAC:-local0}"

log_info() {
    logger -t "$LOG_TAG" -p "${LOG_FAC}.info" "$*"
}

log_warn() {
    logger -t "$LOG_TAG" -p "${LOG_FAC}.warning" "$*"
}

log_err() {
    logger -t "$LOG_TAG" -p "${LOG_FAC}.err" "$*"
}

log_debug() {
    # 通过环境变量控制是否输出调试日志
    if [ "${LOG_DEBUG:-0}" = "1" ]; then
        logger -t "$LOG_TAG" -p "${LOG_FAC}.debug" "$*"
    fi
}

# 使用示例：
# log_info "Starting data processing..."
# log_warn "Disk usage at 85%"
# log_err "Failed to connect to database"
# LOG_DEBUG=1 log_debug "Variable X=$X, Y=$Y"
LIBRARY

# 测试标准化日志库
source ~/log-lesson30/std-logging-lib.sh

log_info "System check started"
log_warn "Low disk space on /var"
log_err "Cannot reach backup server"
LOG_DEBUG=1 log_debug "Internal state: mode=full, threads=4"

# 查看所有 tag 为 MYSCRIPT 的日志
journalctl SYSLOG_IDENTIFIER=MYSCRIPT
```
