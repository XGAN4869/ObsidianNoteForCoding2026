## 1. 概述

### 1.1 从"重定向操作符"到"文件描述符"

第 20 章你掌握了 Shell 的重定向操作符---`>` 将输出写入文件，`|` 连接两个进程，`2>&1` 合并 stdout 和 stderr。你学会了用 `tee` 分叉数据流、用 Here Document 嵌入多行文本、用进程替换将命令输出"伪装"成文件。你能够像搭积木一样组合 Unix 小工具，构建数据处理流水线。

现在，你需要深入一层，理解这些操作符**底层的统一抽象**：

- "`2>&1` 为什么是把 stderr 复制到 stdout，而不是让两者绑定在一起？"
- "`exec 3>file` 打开的文件描述符 3，和 stdin/stdout/stderr 有什么区别？"
- "一个进程最多能同时打开多少个文件？如果遇到了 'Too many open files' 错误怎么办？"
- "如何查看一个正在运行的进程打开了哪些文件？`lsof` 的输出各列代表什么？"
- "`/proc/PID/fd/` 目录里的数字符号链接是什么？为什么它们能反映进程的文件描述符？"
- "什么是非阻塞 I/O（Non-blocking I/O）？为什么网络编程和高性能服务器需要它？"
- "`ulimit -n` 是什么？系统级和用户级的文件描述符限制各在哪里配置？"

这些问题的核心是**文件描述符（File Descriptor，fd）**---Unix "一切皆文件"哲学在进程层面的具体体现。第 20 章教你"怎么用"重定向；本章教你"为什么是这样"---理解文件描述符的本质，你才能真正驾驭 I/O 系统。

文件描述符是 Unix 设计中最优雅的抽象之一。无论你操作的是磁盘文件、终端、管道、网络 socket，还是设备驱动，进程内部都只用一个**非负整数**来代表它。当你调用 `write(1, "hello", 5)` 时，你不关心 fd 1 指向的是终端还是文件---这正是"一切皆文件"的力量。

## 2. 核心概念

### 2.1 文件描述符是什么：内核视角

第 20 章介绍了文件描述符是"进程打开文件的句柄"。本节从内核数据结构的角度深入解释。

```
+------------------------------------------------------------------+
|                    文件描述符的三级结构                                |
|                                                                  |
|  进程 A (task_struct)                                             |
|  ┌─────────────────────┐                                          |
|  │  files_struct *files │────→                                    |
|  └─────────────────────┘                                          |
|                               ┌──────────────────────────────────┐|
|  文件描述符表（fdtable）      │ 进程私有的 fd 数组                  │|
|  ┌─────────────────────┐     │  ┌─────┬────────────────────────┐ │|
|  │  fd[0] ──→ (struct file *)│  │  fd[0] → tty (终端输入)      │ │|
|  │  fd[1] ──→ (struct file *)│  │  fd[1] → tty (终端输出)      │ │|
|  │  fd[2] ──→ (struct file *)│  │  fd[2] → tty (终端错误)      │ │|
|  │  fd[3] ──→ (struct file *)│  │  fd[3] → /var/log/app.log    │ │|
|  │  fd[4] ──→ NULL            │  │  fd[4] → 未使用              │ │|
|  │  ...                       │  │  ...                        │ │|
|  └─────────────────────┘     │  └──────────────────────────────┘ │|
|                               └──────────────────────────────────┘|
|                                                                  |
|  内核打开文件表（open file table，全局）                             |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  struct file {                                                │ |
|  │    f_mode:   O_RDONLY | O_WRONLY | O_RDWR | O_NONBLOCK       │ |
|  │    f_pos:    当前读/写偏移量（字节）                             │ |
|  │    f_flags:  打开标志                                          │ |
|  │    f_count:  引用计数（有多少个 fd 指向这个 struct file）        │ |
|  │    f_op:    → 操作函数集（不同文件类型有不同的 read/write 实现）  │ |
|  │    f_inode: → 指向 inode（磁盘文件）或 socket 对象等             │ |
|  │  }                                                            │ |
|  └──────────────────────────────────────────────────────────────┘ |
+------------------------------------------------------------------+
```

**关键理解：**

1. **文件描述符表是进程私有的**：每个进程有自己的 fd 数组，fd 编号只在本进程内有意义。进程 A 的 fd 3 和进程 B 的 fd 3 通常指向完全不同的打开文件。
2. **struct file 是全局的**：内核为每个"打开实例"创建一个 struct file。如果两个进程打开了同一个文件，它们有各自的 struct file（和各自的 f_pos 偏移量）。
3. **f_count 引用计数**：同一个进程可以用多个 fd 指向同一个 struct file（通过 `dup2()`），此时 f_count > 1。这就是 `2>&1` 的内核实现。
4. **f_op 操作函数集**：不同文件类型（ext4 文件、socket、管道、设备文件）有完全不同的 read/write 实现，但进程通过统一接口调用，无需关心底层差异。

```bash
# 观察当前 shell 的 fd 表
echo "=== 当前 Shell 进程的文件描述符 ==="
echo "进程 PID: $$"
ls -la /proc/$$/fd/
# 输出示例：
# lrwx------ 1 user user 64 Jul 30 10:00 0 -> /dev/pts/0
# lrwx------ 1 user user 64 Jul 30 10:00 1 -> /dev/pts/0
# lrwx------ 1 user user 64 Jul 30 10:00 2 -> /dev/pts/0
# lrwx------ 1 user user 64 Jul 30 10:00 255 -> /dev/pts/0

# 注意：
# - 0/1/2 都指向同一个终端设备 /dev/pts/0
# - 255 是 Bash 内部使用的 fd（用于保存终端状态）
# - 每个 fd 都是一个符号链接，指向实际打开的文件路径
```

### 2.2 标准文件描述符：0、1、2

```
+------------------------------------------------------------------+
|                    三大标准文件描述符                                 |
|                                                                  |
|  fd 编号    名称      POSIX 常量      默认连接       方向            |
|  ─────────────────────────────────────────────────                |
|    0      stdin    STDIN_FILENO    键盘/终端     输入 → 进程       |
|    1      stdout   STDOUT_FILENO   终端显示屏    进程 → 输出       |
|    2      stderr   STDERR_FILENO   终端显示屏    进程 → 输出       |
|                                                                  |
|  关键事实：                                                       |
|  - 这三个 fd 在 fork() 时从父进程继承                              |
|  - Shell 在 fork()+exec() 之间设置重定向，修改这三个 fd 的指向      |
|  - 程序启动时假定 fd 0/1/2 已打开且可用                            |
|  - 编号 0/1/2 是 POSIX 标准的约定，所有 Unix 系统都遵守             |
+------------------------------------------------------------------+
```

```bash
# 验证：每个 Linux 进程启动时 0/1/2 都已打开
# 查看 init 进程 (PID 1) 的 fd
ls -la /proc/1/fd/ 2>/dev/null | head -10
# 输出示例：
# lrwx------ 1 root root 64 ... 0 -> /dev/null
# lrwx------ 1 root root 64 ... 1 -> /dev/null
# lrwx------ 1 root root 64 ... 2 -> /dev/null

# 即使最简单的进程也拥有这三个 fd
# 程序可以安全地使用 write(1, ...) 和 write(2, ...) 而不检查 fd 是否有效
```

### 2.3 用户文件描述符：3 及以上

fd 编号 0、1、2 是标准约定。当进程通过 `open()`、`socket()`、`pipe()` 等系统调用打开新文件时，内核分配**当前可用的最小未使用编号**。

```
+------------------------------------------------------------------+
|                    文件描述符的分配规则                               |
|                                                                  |
|  内核保证：open() / socket() / pipe() 返回当前最小的未使用 fd 编号    |
|                                                                  |
|  示例：                                                          |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  初始状态：fd 0, 1, 2 已占用 → 下一个 open() 返回 3             │ |
|  │  打开 /tmp/a.log → fd 3                                       │ |
|  │  打开 /tmp/b.log → fd 4                                       │ |
|  │  关闭 fd 3       → 3 变为可用                                  │ |
|  │  打开 /tmp/c.log → fd 3（返回最小的可用编号！）                  │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                                                  |
|  这个"最小可用"规则是实现重定向的基础：                              |
|  - close(1); open("file") → fd 变成 1（原来的 stdout）            |
|  - dup2(3, 1) → 让 fd 1 指向 fd 3 的 struct file                |
+------------------------------------------------------------------+
```

```bash
# 创建一个简单的 C 程序来演示 fd 分配（或用 Bash 模拟）
# 在 Bash 中，exec 可以手动打开文件描述符
exec 3>/tmp/fd-demo-a.txt
exec 4>/tmp/fd-demo-b.txt
echo "=== 打开两个自定义 fd 后 ==="
ls -la /proc/$$/fd/ | grep -E "/3$|/4$"
# 输出示例：
# lrwx------ 1 user user 64 ... 3 -> /tmp/fd-demo-a.txt
# lrwx------ 1 user user 64 ... 4 -> /tmp/fd-demo-b.txt

# 向自定义 fd 写入数据
echo "写入 fd 3 的数据" >&3
echo "写入 fd 4 的数据" >&4

# 验证文件内容
echo "=== 文件内容验证 ==="
cat /tmp/fd-demo-a.txt
cat /tmp/fd-demo-b.txt

# 关闭 fd 3 后再打开新文件 → 会得到 fd 3
exec 3>&-
exec 3>/tmp/fd-demo-c.txt
echo "=== 关闭并重新分配后 ==="
ls -la /proc/$$/fd/ | grep -E "/3$|/4$"
# fd 3 现在指向了新文件

# 清理
exec 3>&-
exec 4>&-
rm -f /tmp/fd-demo-a.txt /tmp/fd-demo-b.txt /tmp/fd-demo-c.txt
```

### 2.4 文件描述符的继承：fork() 与 exec()

理解 fd 在 fork/exec 期间的继承规则，是理解 Shell 重定向实现的关键。

```
+------------------------------------------------------------------+
|                    fork() 与 exec() 中的 fd 继承                      |
|                                                                  |
|  fork() 之后：                                                    |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  子进程的 fd 表是父进程 fd 表的完整拷贝                           │ |
|  │  父子进程的 fd 指向相同的 struct file（f_count 增加）             │ |
|  │  这意味着：如果父子进程同时写同一个 fd，写入是交错的               │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                                                  |
|  exec() 之后：                                                    |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  fd 表默认保留（除非文件设置了 FD_CLOEXEC 标志）                  │ |
|  │  FD_CLOEXEC（close-on-exec）：exec() 时自动关闭此 fd             │ |
|  │  这个标志用于防止子进程意外继承不相关的 fd                         │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                                                  |
|  Shell 重定向的执行流程（回顾第 20 章 2.5 节）：                     |
|  1. Shell 调用 pipe() 或 open()，获得新 fd                          |
|  2. Shell fork() 创建子进程                                       |
|  3. 子进程用 dup2() 将新 fd 复制到 0/1/2                            |
|  4. 子进程关闭原始 fd                                              |
|  5. 子进程 exec() 执行目标程序                                     |
|  6. 目标程序继承了设置好的 fd 0/1/2，正常读写                        |
+------------------------------------------------------------------+
```

```bash
# 验证：子 shell 可以看到父 shell 打开的 fd
cat > /tmp/fd-inherit-demo.sh << 'SCRIPT'
#!/bin/bash
echo "=== 父进程 PID: $BASHPID ==="

# 在父 shell 中打开一个自定义 fd
exec 8>/tmp/inherited-file.txt
echo "父进程打开了 fd 8"
ls -la /proc/$BASHPID/fd/8

# 创建子 shell —— fd 8 会被继承
(
    echo "=== 子进程 PID: $BASHPID ==="
    echo "子进程也能看到 fd 8:"
    ls -la /proc/$BASHPID/fd/8
    echo "子进程向 fd 8 写入数据" >&8
)

echo "=== 验证文件内容 ==="
cat /tmp/inherited-file.txt

exec 8>&-
rm -f /tmp/inherited-file.txt
SCRIPT
bash /tmp/fd-inherit-demo.sh
rm -f /tmp/fd-inherit-demo.sh
```

### 2.5 write() 的本质：阻塞 I/O 与内核缓冲区

理解了 fd 的结构后，我们需要理解"写数据"这个动作本身到底发生了什么。

```
+------------------------------------------------------------------+
|                    阻塞 write() 的内部流程                           |
|                                                                  |
|  用户进程                         内核                              |
|  ┌──────────┐                   ┌─────────────────────────────┐   |
|  │ write(1, │                   │                             │   |
|  │  "hello",│ ──→ 系统调用 ──→   │  VFS 层                     │   |
|  │  5)      │                   │    │                        │   |
|  │          │                   │    ↓                        │   |
|  │  [阻塞]  │                   │  文件系统层（ext4/xfs/...）   │   |
|  │  等待... │                   │    │                        │   |
|  │          │                   │    ↓                        │   |
|  │  [返回]  │ ←── 返回 5 ──←    │  Page Cache（页缓存）        │   |
|  └──────────┘                   │    │                        │   |
|                                 │    ↓（异步刷盘）              │   |
|                                 │  块设备驱动                  │   |
|                                 │    │                        │   |
|                                 │    ↓                        │   |
|                                 │  磁盘                        │   |
|                                 └─────────────────────────────┘   |
|                                                                  |
|  关键理解：                                                       |
|  1. write() 返回 5 表示数据已复制到内核缓冲区，不保证已写入磁盘       |
|  2. 如果内核缓冲区（Page Cache）已满，write() 会阻塞                |
|  3. 如果 fd 以 O_NONBLOCK 打开且缓冲区满，write() 返回 -1 + EAGAIN |
|  4. 对于管道：如果管道缓冲区满且读端未读取，write() 阻塞             |
+------------------------------------------------------------------+
```

### 2.6 阻塞 I/O vs 非阻塞 I/O：概念引入

这是理解文件描述符高级用法的核心概念。

```
+------------------------------------------------------------------+
|                    阻塞 I/O vs 非阻塞 I/O                            |
|                                                                  |
|  阻塞 I/O（Blocking I/O，默认模式）：                               |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  read(fd, buf, size):                                         │ |
|  │    如果 fd 没有数据可读 → 进程睡眠，直到数据到达                 │ |
|  │  write(fd, buf, size):                                        │ |
|  │    如果 fd 的缓冲区已满 → 进程睡眠，直到有空闲空间               │ |
|  │                                                              │ |
|  │  适用场景：简单的命令行工具、单任务脚本、大多数日常程序           │ |
|  │  优点：编程简单，逻辑清晰                                       │ |
|  │  缺点：一个进程只能处理一个 I/O 操作，无法同时处理多个连接        │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                                                  |
|  非阻塞 I/O（Non-blocking I/O，需设置 O_NONBLOCK）：                |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  read(fd, buf, size):                                         │ |
|  │    如果 fd 没有数据可读 → 立即返回 -1，errno = EAGAIN          │ |
|  │  write(fd, buf, size):                                        │ |
|  │    如果 fd 的缓冲区已满 → 立即返回 -1，errno = EAGAIN          │ |
|  │                                                              │ |
|  │  适用场景：网络服务器、GUI 事件循环、高性能 I/O                 │ |
|  │  优点：一个进程可以同时管理多个 fd，吞吐量高                     │ |
|  │  缺点：编程复杂，需要轮询或事件通知机制（select/poll/epoll）     │ |
|  └──────────────────────────────────────────────────────────────┘ |
+------------------------------------------------------------------+
```

```bash
# 在 Shell 层面，我们可以观察到阻塞 I/O 的行为
# 实验：管道缓冲区满导致的阻塞

echo "=== 观察管道阻塞行为 ==="
# 创建一个慢速消费者
# 生产者快速产生大量数据，消费者慢速读取
timeout 3 bash -c '
    # 生产者：产生大块数据
    for i in $(seq 1 1000); do
        printf "%-1000s" "x" | tr " " "x"
        echo ""
    done
' 2>/dev/null | (
    # 消费者：极慢速读取
    while read -r line; do
        echo "读取了 ${#line} 字节"
        sleep 0.5
    done
) 2>/dev/null || echo "(可能因 timeout 或 SIGPIPE 终止)"
# 观察：生产者会因为管道缓冲区满而阻塞
```

## 3. 命令详解

### 3.1 exec：在 Shell 中直接操控文件描述符

`exec` 命令在 Shell 中有两种截然不同的用法：

1. **`exec command`**：用 command 替换当前 Shell 进程（不创建子进程）。执行后，当前 Shell 不复存在。
2. **`exec [N]>file` / `exec [N]<file` / `exec [N]>&-`**：在当前 Shell 中直接修改文件描述符（不执行新命令）。这是本章的重点。

#### 3.1.1 exec 的基本 fd 操作

```
exec 的 fd 操作语法：

  exec N>file      打开（或创建）file 为 fd N，只写模式（覆盖）
  exec N>>file     打开（或创建）file 为 fd N，只写模式（追加）
  exec N<file      打开 file 为 fd N，只读模式
  exec N<>file     打开 file 为 fd N，读写模式
  exec N>&M        将 fd N 复制到 fd M 当前指向的位置（dup2）
  exec N<&M        同上（< 和 > 在此语义下没有区别）
  exec N>&-        关闭 fd N
  exec N<&-        同上，关闭 fd N
  
  注意：N 和 M 都是文件描述符编号。如果省略 N：
  exec >file       等价于 exec 1>file（重定向 stdout）
  exec <file       等价于 exec 0<file（重定向 stdin）
```

```bash
# === exec 基本操作演示 ===

# 1. 打开自定义文件描述符（写模式）
exec 3>/tmp/exec-demo-write.txt
echo "向 fd 3 写入" >&3
echo "再写一行" >&3
exec 3>&-  # 关闭 fd 3

echo "=== 写入结果 ==="
cat /tmp/exec-demo-write.txt

# 2. 打开自定义文件描述符（追加模式）
echo "第一轮" > /tmp/exec-demo-append.txt
exec 3>>/tmp/exec-demo-append.txt
echo "追加的行" >&3
exec 3>&-

echo "=== 追加结果 ==="
cat /tmp/exec-demo-append.txt

# 3. 打开自定义文件描述符（只读模式）
echo -e "line1\nline2\nline3" > /tmp/exec-demo-read.txt
exec 3</tmp/exec-demo-read.txt
# 使用 read -u 从 fd 3 读取
read -u 3 first_line
echo "第一行: $first_line"
read -u 3 second_line
echo "第二行: $second_line"
exec 3<&-

# 4. 打开文件描述符（读写模式）
exec 3<>/tmp/exec-demo-rw.txt
echo "写入数据" >&3
# 注意：读写模式共享同一个文件偏移量
# 写入后偏移在末尾，直接读取读不到数据
# 需要 seek 到开头（Bash 不支持 seek，所以实际很少用<>）
exec 3>&-

# 清理
rm -f /tmp/exec-demo-write.txt /tmp/exec-demo-append.txt \
      /tmp/exec-demo-read.txt /tmp/exec-demo-rw.txt
```

#### 3.1.2 exec 复制文件描述符（dup2 语义）

这是 `exec` 最强大也最常被误解的功能。`exec N>&M` 在内核中调用 `dup2(M, N)`：让 fd N 指向 fd M 当前指向的 struct file。

```
exec N>&M 的语义（精确描述）：

  1. 如果 fd N 已经打开，先关闭它（close(N)）
  2. 将 fd M 复制到 fd N（dup2(M, N)）
  
  结果：fd N 和 fd M 指向同一个 struct file，共享同一个 f_pos

  关键理解：这和第 20 章的 "2>&1" 本质相同！
  - 在重定向中：ls > file 2>&1（Shell 在子进程中执行 dup2）
  - 在 exec 中：exec 2>&1（在当前 Shell 中执行 dup2，效果持久）
```

```bash
# === exec 复制 fd 的详细演示 ===

# 准备：打开一个文件作为目标
echo "原始 stdout" > /tmp/dup-demo-original.txt

# 场景1：保存原始 stdout 到 fd 3，然后重定向 stdout
echo "=== 场景1：保存并恢复 stdout ==="
echo "这条消息在重定向前（终端显示）"

# 保存当前 stdout 到 fd 3
exec 3>&1

# 将 stdout 重定向到文件
exec > /tmp/dup-demo-output.txt

echo "这条消息被重定向到文件了"
echo "这条也是"

# 恢复 stdout（从 fd 3 复制回来）
exec >&3
# 关闭 fd 3（已不需要）
exec 3>&-

echo "这条消息恢复在终端显示"

echo ""
echo "=== 文件内容 ==="
cat /tmp/dup-demo-output.txt

# 场景2：将 stderr 和 stdout 都重定向到同一个文件
echo ""
echo "=== 场景2：统一输出 ==="
exec 3>&1                        # 保存原始 stdout
exec > /tmp/dup-demo-all.txt     # stdout → 文件
exec 2>&1                        # stderr → 跟 stdout 一样（文件）

echo "stdout 消息"
echo "stderr 消息" >&2

# 恢复
exec >&3
exec 2>&3
exec 3>&-

echo "--- 文件验证 ---"
cat /tmp/dup-demo-all.txt

# 场景3：交换 stdout 和 stderr
echo ""
echo "=== 场景3：交换 stdout 和 stderr ==="
exec 3>&1                        # fd 3 → 原始 stdout（终端）
exec 4>&2                        # fd 4 → 原始 stderr（终端）
exec 1>&4                        # stdout → 原始 stderr 的位置
exec 2>&3                        # stderr → 原始 stdout 的位置
# 现在 stdout 和 stderr 互换了！
# 但两者都指向终端，从视觉上无法区分

# 实际验证：将"交换后的 stdout"重定向到文件
# （注意：此时的 stdout 实际上是原来的 stderr）
echo "这是通过交换后的 stdout 输出的" > /tmp/swap-test.txt
echo "这是通过交换后的 stderr 输出的（其实走了原来的 stdout）" >&2

echo "--- swap-test.txt 内容 ---"
cat /tmp/swap-test.txt

# 恢复
exec 1>&3
exec 2>&4
exec 3>&-
exec 4>&-

# 清理
rm -f /tmp/dup-demo-original.txt /tmp/dup-demo-output.txt \
      /tmp/dup-demo-all.txt /tmp/swap-test.txt
```

#### 3.1.3 exec 关闭文件描述符

```bash
# 关闭自定义 fd
exec 3>/tmp/close-demo.txt
echo "fd 3 已打开"
ls /proc/$$/fd/3 2>/dev/null && echo "可以访问 fd 3" || echo "fd 3 不存在"

exec 3>&-
echo "fd 3 已关闭"
ls /proc/$$/fd/3 2>/dev/null && echo "可以访问 fd 3" || echo "fd 3 不存在（正确）"

rm -f /tmp/close-demo.txt

# 为什么需要显式关闭 fd？
# 1. 及时释放内核资源（每个 fd 占用内存）
# 2. 触发文件数据的 flush（关闭时内核为确保完整写入）
# 3. 避免子进程意外继承不必要的 fd
# 4. 对于管道/socket：关闭写端会让对端读到 EOF

# 演示：关闭写端触发 EOF
cat > /tmp/pipe-close-demo.sh << 'SCRIPT'
#!/bin/bash
# 创建一个管道
tmpfifo=$(mktemp -u /tmp/demo-pipe-XXXXX)
mkfifo "$tmpfifo"

# 后台进程：等待接收所有数据
( cat "$tmpfifo"; echo "读取到 EOF" ) &

# 向管道写入数据
echo "第一条数据" > "$tmpfifo"
echo "第二条数据" > "$tmpfifo"

# 关闭写端（通过关闭 fd）
exec 3>"$tmpfifo"
echo "第三条数据" >&3
exec 3>&-  # 关闭写端 → 读端收到 EOF

wait
rm -f "$tmpfifo"
SCRIPT
bash /tmp/pipe-close-demo.sh 2>/dev/null
rm -f /tmp/pipe-close-demo.sh
```

#### 3.1.4 exec 的高级组合模式

```bash
# === 模式1：多路输出（同时写入多个日志文件） ===
echo "=== 多路输出 ==="

exec 3>/tmp/log1.txt
exec 4>/tmp/log2.txt

# 定义一个函数，同时向多个 fd 输出
multi_echo() {
    local msg="$1"
    echo "$msg"      # stdout（当前终端）
    echo "$msg" >&3  # fd 3（log1.txt）
    echo "$msg" >&4  # fd 4（log2.txt）
}

multi_echo "这条消息出现在三个地方"
multi_echo "同步写入多个日志"

exec 3>&-
exec 4>&-

echo "--- log1.txt ---"
cat /tmp/log1.txt
echo "--- log2.txt ---"
cat /tmp/log2.txt
rm -f /tmp/log1.txt /tmp/log2.txt

# === 模式2：在脚本中临时重定向一段代码块 ===
echo ""
echo "=== 代码块临时重定向 ==="

cat > /tmp/block-redirect.sh << 'SCRIPT'
#!/bin/bash

# 保存原始 fd
exec 3>&1
exec 4>&2

# 重定向一个代码块
{
    exec > /tmp/block-output.txt
    exec 2>&1

    echo "块内的 stdout"
    echo "块内的 stderr" >&2
}
# 注意：在代码块内部 exec 会改变当前 shell 的 fd
# 所以需要手动恢复！

# 恢复
exec >&3
exec 2>&4
exec 3>&-
exec 4>&-

echo "=== 块外的输出（终端可见） ==="
cat /tmp/block-output.txt
rm -f /tmp/block-output.txt
SCRIPT
bash /tmp/block-redirect.sh
rm -f /tmp/block-redirect.sh

# === 模式3：去重写法——先保存，再重定向，最后恢复 ===
echo ""
echo "=== 保存-重定向-恢复 模式 ==="

# 一条命令完成：保存、重定向、执行、恢复
{
    echo "这部分输出正常显示在终端"
    # 临时重定向到文件
    exec 3>&1 > /tmp/save-restore.txt 2>&1
    echo "这部分输出进入文件"
    exec >&3 2>&3 3>&-
    echo "恢复后正常显示"
}

echo "--- 文件内容 ---"
cat /tmp/save-restore.txt
rm -f /tmp/save-restore.txt
```

### 3.2 lsof：查看进程打开的文件描述符

`lsof`（LiSt Open Files）是诊断文件描述符相关问题的核心工具。它列出系统中所有进程打开的所有文件。

#### 3.2.1 lsof 基本用法

```
lsof 的基本语法：

  lsof                   列出所有进程的所有打开文件（输出极多）
  lsof -p PID            只列出指定 PID 打开的文件
  lsof -c NAME           只列出以 NAME 开头的命令打开的文件
  lsof -u USERNAME       只列出指定用户进程打开的文件
  lsof /path/to/file     只列出打开了指定文件的进程
  lsof -i                只列出网络连接（socket）
  lsof -i :PORT          只列出使用指定端口的连接
  lsof -d N              只列出 fd 编号为 N 的文件
  lsof +D /dir           列出打开了 /dir 下任何文件的进程（递归）

常用组合：
  lsof -p PID -d 0-10    查看某个进程的 fd 0 到 10
  lsof -i TCP:80         查看使用 80 端口的 TCP 连接
  lsof -c ssh            查看 ssh 命令打开的所有文件
```

```bash
# === lsof 基本演示 ===

# 1. 查看当前 shell 打开的文件
echo "=== 当前 Shell 打开的文件（fd 0-5） ==="
lsof -p $$ -d 0-5 2>/dev/null || echo "(可能需要 sudo 权限查看部分条目)"

# 2. 打开一个文件后观察 lsof 的变化
echo ""
echo "=== 打开文件前后的对比 ==="
exec 8>/tmp/lsof-demo.txt
echo "打开 fd 8 后："
lsof -p $$ -d 8 2>/dev/null
echo "---"
exec 8>&-
echo "关闭 fd 8 后："
lsof -p $$ -d 8 2>/dev/null || echo "fd 8 已不存在" 
rm -f /tmp/lsof-demo.txt

# 3. 查看特定命令打开的文件
echo ""
echo "=== systemd (PID 1) 打开的文件（前 10 条） ==="
lsof -p 1 2>/dev/null | head -10
```

#### 3.2.2 lsof 输出列详解

```
lsof 输出示例：
COMMAND   PID   TID TASKCMD   USER   FD      TYPE   DEVICE SIZE/OFF   NODE NAME
bash    12345                   user  cwd       DIR    259,2     4096 131072 /home/user
bash    12345                   user  rtd       DIR    259,2     4096      2 /
bash    12345                   user  txt       REG    259,2  1446024 262145 /usr/bin/bash
bash    12345                   user  mem       REG    259,2  2029224 262148 /usr/lib/x86_64-linux-gnu/libc.so.6
bash    12345                   user    0u      CHR    136,0      0t0      3 /dev/pts/0
bash    12345                   user    1u      CHR    136,0      0t0      3 /dev/pts/0
bash    12345                   user    2u      CHR    136,0      0t0      3 /dev/pts/0
bash    12345                   user    3w      REG    259,2      100 135168 /tmp/somefile.txt

列解释：
  COMMAND  : 进程的命令名（前 9 个字符）
  PID      : 进程 ID
  USER     : 进程所有者
  FD       : 文件描述符编号 + 访问模式
             0u = fd 0, read+write (u = update)
             1w = fd 1, write only
             2u = fd 2, read+write
             3r = fd 3, read only
             4w = fd 4, write only
             cwd = current working directory（当前工作目录）
             rtd = root directory（根目录）
             txt = program text（程序的可执行文件/代码段）
             mem = memory-mapped file（内存映射文件）
             DEL = deleted file（已删除但仍被打开的文件）
  TYPE     : 文件类型
             REG = regular file（普通文件）
             DIR = directory（目录）
             CHR = character device（字符设备）
             FIFO = named pipe（命名管道）
             sock = socket（套接字）
             unix = unix domain socket
             IPv4/IPv6 = 网络 socket
  DEVICE   : 设备编号（主设备号,次设备号）
  SIZE/OFF : 文件大小（字节）或当前偏移量
  NODE     : 文件的 inode 编号
  NAME     : 文件名或挂载点
```

```bash
# 演示：解析 lsof 输出各字段

echo "PID: $$"

# 打开几种不同类型的文件来展示
exec 7>/tmp/lsof-types-demo.txt   # 普通文件（REG）
mkdir -p /tmp/lsof-types-dir       # 目录（DIR --- 工作目录）
cd /tmp/lsof-types-dir

echo ""
echo "=== 各类型 fd 的 lsof 输出 ==="
lsof -p $$ -d 0,1,2,7 2>/dev/null

echo ""
echo "FD 列解读："
echo "  0u = 可读可写"
echo "  1u = 可读可写"
echo "  2u = 可读可写"
echo "  7w = 只写"

# 查看 cwd（当前工作目录）
echo ""
echo "=== 工作目录条目 ==="
lsof -p $$ -a -d cwd 2>/dev/null

# 清理
exec 7>&-
cd - > /dev/null
rm -f /tmp/lsof-types-demo.txt
rm -rf /tmp/lsof-types-dir
```

### 3.3 /proc/PID/fd/：进程文件描述符的符号链接视图

`/proc` 伪文件系统为每个进程提供了其文件描述符的可视化入口。每个进程的 `/proc/PID/fd/` 目录包含一系列以 fd 编号命名的符号链接（Symbolic Link），指向该 fd 当前打开的文件。

#### 3.3.1 /proc/PID/fd/ 的结构

```
/proc/PID/fd/ 目录：

  lrwx------ 0 -> /dev/pts/0    → stdin 指向终端
  lrwx------ 1 -> /dev/pts/0    → stdout 指向终端
  lrwx------ 2 -> /dev/pts/0    → stderr 指向终端
  lrwx------ 3 -> /var/log/app.log   → 自定义打开的文件
  lrwx------ 4 -> socket:[56789]     → socket
  lrwx------ 5 -> pipe:[12345]       → 匿名管道
  lrwx------ 6 -> anon_inode:[eventpoll]  → epoll 实例

注意：
  - 每个链接名就是 fd 编号
  - 链接目标反映实际文件路径
  - 对于 socket/pipe，目标显示的是内核对象 ID 而非文件路径
  - 如果链接目标显示 "(deleted)"，说明文件已被删除但 fd 仍持有
```

```bash
# === /proc/PID/fd/ 详细探索 ===

echo "=== 当前 Shell 进程的 /proc/$$/fd/ ==="
ls -la /proc/$$/fd/

echo ""
echo "=== 每个 fd 的详细信息 ==="
for fd in /proc/$$/fd/*; do
    if [[ -e "$fd" ]]; then
        fd_num=$(basename "$fd")
        target=$(readlink "$fd")
        # 获取 fd 的打开标志（如果有的话）
        flags=$(cat "/proc/$$/fdinfo/$fd_num" 2>/dev/null | head -3)
        echo "fd $fd_num → $target"
        if [[ -n "$flags" ]]; then
            echo "  flags: $(echo "$flags" | head -1)"
        fi
    fi
done

# 演示：打开新 fd 后 /proc/PID/fd/ 的变化
echo ""
echo "=== 打开新 fd 后的变化 ==="
exec 7>/tmp/proc-fd-demo.txt
echo "fd 7 已打开："
ls -la /proc/$$/fd/7
echo "fd 7 的 fdinfo："
cat /proc/$$/fdinfo/7 2>/dev/null
exec 7>&-
rm -f /tmp/proc-fd-demo.txt
```

#### 3.3.2 /proc/PID/fdinfo/：更详细的 fd 信息

```bash

echo ""

echo "           010000  = O_DIRECTORY"

```

#### 3.3.3 /proc/PID/fd/ 的实际用途

```bash
# === 用途1：恢复被误删但仍被进程持有的文件 ===

echo "=== 恢复已删除但进程持有的文件 ==="
echo "这是重要数据" > /tmp/important-data.txt
# 在子 shell 中保持文件打开并删除
(
    exec 8</tmp/important-data.txt
    rm /tmp/important-data.txt
    echo "文件已删除，但 fd 8 仍持有："
    ls -la /proc/$BASHPID/fd/8
    # 通过 /proc/PID/fd/8 恢复数据
    cp /proc/$BASHPID/fd/8 /tmp/recovered-data.txt
    exec 8<&-
)
echo "恢复的文件内容："
cat /tmp/recovered-data.txt
rm -f /tmp/recovered-data.txt

# === 用途2：查看进程是否打开了某个特定文件 ===
echo ""
echo "=== 检查进程是否打开了特定文件 ==="
touch /tmp/check-open.txt
exec 9>/tmp/check-open.txt
# 方法：对比 /proc/PID/fd/ 中链接目标
if ls -la /proc/$$/fd/ 2>/dev/null | grep -q "/tmp/check-open.txt"; then
    echo "当前进程打开了 /tmp/check-open.txt"
fi
exec 9>&-
rm -f /tmp/check-open.txt

# === 用途3：在不支持 /dev/fd 的系统上，用 /proc/self/fd 代替 ===
echo ""
echo "=== /proc/self/fd 等同于 /proc/$$/fd ==="
echo "/proc/self 始终指向当前进程"
ls /proc/self/fd/0 2>/dev/null && echo "/proc/self/fd/0 可用"
# /proc/self/fd/N 等价于 /dev/fd/N（如果 /dev/fd 存在的话）
```

### 3.4 ulimit：文件描述符数量限制

每个进程可以打开的文件描述符数量是有限的。这个限制由内核和 Shell 共同控制。

#### 3.4.1 ulimit 的基本概念

```
+------------------------------------------------------------------+
|                    文件描述符限制的层次                                |
|                                                                  |
|  系统级硬上限（内核参数）                                            |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  fs.nr_open = 1048576 (默认值，/proc/sys/fs/nr_open)          │ |
|  │  fs.file-max = 9223372036854775807 (系统总 fd 数上限)           │ |
|  │  这两个是系统管理员可以通过 sysctl 调整的内核参数                  │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                              ▼                                    |
|  用户级限制（PAM limits.conf）                                     |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  /etc/security/limits.conf                                    │ |
|  │    username  hard  nofile  65536                              │ |
|  │    username  soft  nofile  1024                               │ |
|  │  hard limit: 用户不可超越的上限（需 root 提高）                   │ |
|  │  soft limit: 用户当前可使用的上限（用户可提高至 hard limit）       │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                              ▼                                    |
|  进程级限制（Shell ulimit）                                        |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  ulimit -n  → 查看当前进程的 soft limit                         │ |
|  │  ulimit -n 4096  → 调整当前 shell 的 soft limit（不可超过 hard） │ |
|  │  子进程继承父进程的 ulimit 设置                                  │ |
|  └──────────────────────────────────────────────────────────────┘ |
+------------------------------------------------------------------+
```

#### 3.4.2 ulimit -n：查看和调整 fd 限制

```bash

echo "soft limit (软限制，当前生效): $(ulimit -n)"
echo "hard limit (硬限制，不可超越): $(ulimit -Hn)"

# 查看所有 ulimit 设置
echo ""
echo "=== 所有 ulimit 设置 ==="
ulimit -a

# 临时调整 soft limit（在子 shell 中测试，不改变当前 shell）
echo ""
echo "=== 在子 shell 中调整 fd 限制 ==="
(
    echo "子 shell 调整前: $(ulimit -n)"
    ulimit -n 2048 2>/dev/null && echo "调整后: $(ulimit -n)" || echo "无法调整（可能超过了 hard limit）"
)

echo "父 shell 限制未变: $(ulimit -n)"
```

#### 3.4.3 触发 "Too many open files" 错误

```bash
done
exec 5<&-
echo "读取完毕（收到了 EOF）"

wait
rm -f "$PIPE_PATH"
```

## 5. 常见错误与排错

### 5.1 误区：exec 打开的 fd 不会被子进程继承

**错误案例：**

```bash
exec 3>output.txt
./some_script.sh  # 期望 fd 3 不被继承
```

**问题：**

默认情况下，`exec` 打开的文件描述符**会**被子进程继承（除非设置了 FD_CLOEXEC 标志）。这意味着 `some_script.sh` 内部可以访问 fd 3。

**正确做法：**

```bash
# 如果不需要子进程继承，使用完立即关闭
exec 3>output.txt
echo "data" >&3
exec 3>&-  # 在启动子进程前关闭

# 或者使用子 shell 隔离
(
    exec 3>output.txt
    echo "data" >&3
)
# 子 shell 结束后 fd 3 自动关闭
./some_script.sh  # 此时 fd 3 不存在
```

### 5.2 误区：exec N>&M 是"绑定"操作

**错误案例：**

```bash
exec 3>file.txt
exec 2>&3     # 期望 stderr "绑定" 到 fd 3
exec 3>file2.txt  # 期望 stderr 跟着 fd 3 变化
# 实际上 stderr 仍然指向 file.txt，不会自动切换到 file2.txt
```

**问题：**

`exec 2>&3` 并非创建一个"引用绑定"或"别名"。它在内核中执行 `dup2(3, 2)`：**将 fd 3 当前指向的 struct file 复制一份给 fd 2**。之后 fd 2 和 fd 3 指向同一个 struct file，但改变 fd 3 的指向不会影响 fd 2。

```bash
# 验证：复制后各自独立
exec 3>/tmp/ex51-a.txt
exec 4>&3                # fd 4 指向和 fd 3 相同的文件
echo "via fd 3" >&3
echo "via fd 4" >&4
# 两者写入同一个文件（共享偏移量！）
echo "=== 文件内容（可能交错） ==="
cat /tmp/ex51-a.txt

exec 3>&-                # 关闭 fd 3 — fd 4 不受影响！
echo "via fd 4 after closing fd 3" >&4
echo "=== 关闭 fd 3 后通过 fd 4 写入 ==="
cat /tmp/ex51-a.txt

exec 4>&-
rm -f /tmp/ex51-a.txt
```

**正确理解：**

`exec N>&M` 就是 `dup2(M, N)` 的 Shell 封装。需要"绑定"效果时，应在每次修改 fd M 后重新执行复制：

```bash
exec 3>file.txt
exec 2>&1            # stderr 始终跟着 stdout
exec > other.txt     # 改变 stdout — 需要重新复制 stderr
exec 2>&1            # stderr 现在才指向 other.txt
```

### 5.3 误区：关闭 fd 后立即重新打开会获得不同编号

**错误案例：**

```bash
exec 3>file.txt
exec 3>&-
exec 5>another.txt  # 期望新 fd 是 5
```

**问题：**

这不是错误，但容易误解。由于 Linux 的"分配最小可用编号"规则，关闭 fd 3 后下一个 `exec` 打开文件会获得 fd 3，而不是自动递增到更大的编号。

```bash
exec 3>/tmp/ex53-a.txt
exec 3>&-
exec 4>/tmp/ex53-b.txt  # 获得 fd 3，因为你指定的就是 4（不会自动分配）
# 实际上 exec 4> 明确指定了 fd 编号，所以获得 fd 4
# 但如果你写 exec >file（省略编号），等价于 exec 1>file

# 真正的最小可用编号演示：
(
    # 当前 fd 0,1,2 被占用，下一个最小可用是 3
    exec 3>/tmp/ex53-c.txt
    exec 4>/tmp/ex53-d.txt
    exec 3>&-  # 关闭 fd 3，最小可用变为 3
    # 如果只使用重定向而不指定编号，Bash 不提供"自动分配"的 exec 语法
    # 但 C 程序的 open() 调用会获得 fd 3
    exec 4>&-
)
rm -f /tmp/ex53-*.txt
```

### 5.4 误区：ulimit -n 显示的值是全局的

**错误案例：**

```bash
# 终端 A
ulimit -n 2048
# 终端 B
ulimit -n  # 期望看到 2048
```

**问题：**

`ulimit -n` 的设置是**进程级别**的，只影响当前 Shell 及其子进程，不会影响其他终端或已运行的进程。每个 Shell 会话有自己独立的 ulimit 设置。

**正确理解：**

```bash
# ulimit 是每个进程独立的资源限制
# 在不同终端中各自独立
echo "终端 A 的限制: $(ulimit -n)"
# 在另一个终端中：
# echo "终端 B 的限制: $(ulimit -n)"
# 两者的值互不影响

# 如果想永久修改，需要编辑 /etc/security/limits.conf
# 或在 ~/.bashrc 中添加 ulimit -n 4096
```

### 5.5 误区：lsof 不需要权限就能看到所有进程

**错误案例：**

```bash
lsof  # 期望看到所有进程的所有 fd
```

**问题：**

`lsof` 要查看其他用户的进程的 fd，通常需要 root 权限。普通用户只能查看自己进程的 fd。如果没有 sudo，`lsof` 的很多输出会是空的或报 "Permission denied"。

**正确做法：**

```bash
# 普通用户查看自己的进程
lsof -u "$USER"

# 查看特定进程（如果是自己的进程则不需要 root）
lsof -p $$

# 查看系统级 fd 统计（不需要 lsof，通过 /proc 即可）
ls /proc/*/fd/ 2>/dev/null | wc -l
```

### 5.6 误区：/proc/PID/fd/ 中的符号链接可以直接写入

**错误案例：**

```bash
cat /etc/passwd > /proc/12345/fd/1
# 期望通过 /proc/fd/ 向另一个进程的 stdout 写入
```

**问题：**

虽然 `/proc/PID/fd/N` 是符号链接，但直接写入它的行为与写入目标文件**不完全相同**。对于某些 fd 类型（如 socket、管道），不能简单地通过 `/proc/PID/fd/` 的路径进行读写。此外，向其他进程的 fd 写入通常需要该进程的权限或 root 权限，并且可能因权限检查而失败。

**正确理解：**

`/proc/PID/fd/` 主要用于**查看和诊断**，而非用于进程间通信。进程间通信应使用管道、socket、共享内存等标准 IPC 机制。

```bash
# /proc/PID/fd/ 最可靠的用途是读取/恢复文件内容
# 以及诊断 fd 的指向
# 例如：恢复已删除的文件
cp /proc/12345/fd/3 /tmp/recovered  # 可以（对于普通文件）

# 但以下操作不可靠：
# echo "msg" > /proc/12345/fd/1  # 行为未定义，可能失败
```

### 5.7 误区：exec 后的重定向只影响当前命令

**错误案例：**

```bash
exec > output.txt
echo "这是输出"
# 期望后续 echo 恢复正常在终端显示
echo "这也在文件中！"  # 困惑：为什么也在文件里？
```

**问题：**

`exec > file`（不带命令名）的语义是：**永久重定向当前 Shell 的 stdout**，直到你再次用 `exec` 恢复。这与 `command > file` 完全不同（后者只影响 command 本身）。

**正确理解：**

```bash
# exec 不带命令名 = 永久改变当前 Shell 的 fd
exec > /tmp/permanent-output.txt
echo "第一行"   # 进入文件
echo "第二行"   # 进入文件

# 要恢复，需要之前保存了原始 fd
# 或者打开新的终端

# 对比：带命令名的 exec = 替换当前 Shell 进程
# exec ls  # 当前 Shell 被 ls 替换，执行完 ls 后终端会关闭！
```

## 6. 进阶延伸

### 6.1 非阻塞 I/O 的深入理解

#### 6.1.1 为什么需要非阻塞 I/O

阻塞 I/O 模型下，一个进程一次只能处理一个 I/O 操作。对于需要同时处理多个连接的网络服务器，这会导致严重的性能问题。

```
+------------------------------------------------------------------+
|                    阻塞 I/O 的困境                                    |
|                                                                  |
|  场景：一个网络服务器需要同时处理 1000 个客户端连接                    |
|                                                                  |
|  如果使用阻塞 I/O（每个连接一个线程/进程）：                          |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  线程1: read(client1_fd) → 阻塞（等待 client1 发数据）          │ |
|  │  线程2: read(client2_fd) → 阻塞（等待 client2 发数据）          │ |
|  │  ...                                                         │ |
|  │  线程1000: read(client1000_fd) → 阻塞                          │ |
|  │                                                              │ |
|  │  问题：                                                       │ |
|  │  - 1000 个线程 = 大量的上下文切换开销                           │ |
|  │  - 每个线程有自己的栈（默认 8MB）= 8GB 内存开销                  │ |
|  │  - 大多数线程在大多数时间都在空等                                │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                                                  |
|  如果使用非阻塞 I/O + 事件循环（如 nginx, Node.js）：               |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  单线程事件循环：                                              │ |
|  │    while (1) {                                                │ |
|  │        ready_fds = epoll_wait(fds);  // 获取就绪的 fd          │ |
|  │        for each fd in ready_fds:                              │ |
|  │            data = read(fd);  // 非阻塞，立即返回                │ |
|  │            process(data);                                     │ |
|  │    }                                                          │ |
|  │                                                              │ |
|  │  优势：                                                       │ |
|  │  - 单线程管理所有连接，无上下文切换开销                          │ |
|  │  - 内存占用极小                                                │ |
|  │  - 只有就绪的连接才消耗 CPU                                     │ |
|  └──────────────────────────────────────────────────────────────┘ |
+------------------------------------------------------------------+
```

#### 6.1.2 在 Shell 中观察阻塞与非阻塞的区别

```bash
# Shell 层面的概念演示：阻塞读取 vs 带超时的读取

echo "=== 演示阻塞读取 ==="
echo "read 命令默认阻塞：等待用户输入"

# 创建一个命名管道来演示
PIPE=/tmp/ex61-blocking-pipe

echo "在后台 3 秒后向管道写入数据..."
(sleep 3; echo "数据到达" > "$PIPE") &

echo "$(date '+%H:%M:%S') 开始阻塞读取..."
read -r result < "$PIPE"
echo "$(date '+%H:%M:%S') 读取到: $result"

wait
rm -f "$PIPE"

# 使用 timeout 模拟非阻塞效果
echo ""
echo "=== 使用 timeout 实现带超时的读取（模拟非阻塞） ==="

mkfifo "$PIPE2"

echo "尝试读取（0.5 秒超时）..."
if timeout 0.5 cat "$PIPE2" 2>/dev/null; then
    echo "读取到数据"
else
    echo "超时：管道中没有数据（相当于非阻塞 I/O 的 EAGAIN）"
fi

rm -f "$PIPE2"

# read -t 实现带超时的读取

echo "=== read -t 的带超时读取 ==="
echo "等待 2 秒输入（不输入则超时）..."

else
    echo "超时！(类似于非阻塞 I/O 的效果)"
fi
```

#### 6.1.3 非阻塞 I/O 与 select/poll/epoll

```
非阻塞 I/O 本身只解决了"不阻塞"的问题，但没有解决"何时有数据"的问题。
为此，Linux 提供了三种 I/O 多路复用（I/O Multiplexing）机制：

  select()  : 最早的多路复用，有 fd 数量限制（通常 1024）
             每次调用需要重新传入整个 fd 集合，O(n) 复杂度
  
  poll()    : select 的改进版，无 fd 数量限制
             但每次仍需要遍历整个 fd 数组，O(n) 复杂度
  
  epoll()   : Linux 2.6+ 的高性能多路复用
             基于事件驱动，只返回就绪的 fd，O(1) 复杂度
             是 nginx、Node.js、Go runtime 的底层依赖

  epoll 的核心思想：
  1. epoll_create() — 创建一个 epoll 实例（返回一个 fd！）
  2. epoll_ctl() — 向 epoll 实例注册感兴趣的 fd 和事件
  3. epoll_wait() — 阻塞等待，但只返回有事件发生的 fd
  
  这种设计意味着内核主动通知，而不是用户态轮询。
```

```bash
# 查看系统中 epoll 实例的使用情况
echo "=== 系统 epoll 使用情况 ==="
# epoll 实例作为 fd 出现在 /proc/PID/fd/ 中
# 类型为 anon_inode:[eventpoll]
echo "查找当前用户进程中的 epoll 实例："
for pid_dir in /proc/*/fd/; do
    pid=$(echo "$pid_dir" | cut -d/ -f3)
    # 只检查数字 PID
    [[ "$pid" =~ ^[0-9]+$ ]] || continue
    # 检查是否有 epoll fd
    ls -la "$pid_dir" 2>/dev/null | grep -q "eventpoll" && {
        echo "  PID $pid 使用了 epoll"
        ls -la "$pid_dir" 2>/dev/null | grep "eventpoll" | while read -r line; do
            fd=$(echo "$line" | awk '{print $9}')
            echo "    fd: $fd"
        done
    }
done 2>/dev/null | head -10
```

### 6.2 FD_CLOEXEC：防止文件描述符泄漏

`FD_CLOEXEC`（Close-on-EXEC）是一个文件描述符标志。当进程调用 `exec()` 执行新程序时，所有设置了此标志的 fd 会被自动关闭。

```
+------------------------------------------------------------------+
|                    FD_CLOEXEC 标志的用途                              |
|                                                                  |
|  问题场景：                                                       |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  1. 程序 A 打开了一个日志文件（fd 3）                          │ |
|  │  2. 程序 A fork() + exec() 启动程序 B                         │ |
|  │  3. 程序 B 继承了 fd 3                                        │ |
|  │  4. 即使程序 B 不写日志，fd 3 仍被占用                         │ |
|  │  5. 如果程序 B 长期运行 → 日志文件无法被轮转/删除               │ |
|  │  6. 更糟的是：如果程序 B 是 setuid 程序 → 安全漏洞！            │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                                                  |
|  解决方案：                                                       |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  在打开文件后立即设置 FD_CLOEXEC：                              │ |
|  │    fd = open("file", O_RDWR | O_CLOEXEC);                     │ |
|  │  或：                                                        │ |
|  │    fcntl(fd, F_SETFD, FD_CLOEXEC);                            │ |
|  │                                                              │ |
|  │  这样在 exec() 时 fd 自动关闭，不会泄漏到子程序                  │ |
|  └──────────────────────────────────────────────────────────────┘ |
+------------------------------------------------------------------+
```

```bash
# 观察 Shell 中 fd 的 close-on-exec 标志
echo "=== 查看 fd 的 close-on-exec 标志 ==="
# 通过 /proc/PID/fdinfo/ 查看
echo "fd 0 的 flags："
cat /proc/$$/fdinfo/0 2>/dev/null
echo ""
echo "flags 的八进制值含义："
echo "  若第 20 位（O_CLOEXEC = 02000000 八进制）为 1："
echo "  则该 fd 在 exec() 时会被自动关闭"

# 在较新的 Bash 中，可以使用 exec 的特定语法
# Bash 没有直接的 exec N>file cloexec 语法
# 但我们可以检查子进程是否继承了父进程的 fd
exec 7>/tmp/ex62-cloexec-demo.txt
echo "父进程 fd 7 的内容" >&7

# 子进程继承测试
echo ""
echo "=== 子进程是否继承 fd 7？ ==="
(
    if ls /proc/$BASHPID/fd/7 &>/dev/null; then
        echo "子进程继承了 fd 7:"
        ls -la /proc/$BASHPID/fd/7
    else
        echo "子进程没有继承 fd 7（close-on-exec 已设置）"
    fi
)

exec 7>&-
rm -f /tmp/ex62-cloexec-demo.txt
```

### 6.3 文件描述符与系统性能

#### 6.3.1 fd 数量对系统的影响

```
每个打开的文件描述符消耗的内核资源：

  - struct file 对象：约 200-300 字节
  - struct file_operations：每个文件类型约 200 字节（但多个同类型 fd 共享）
  - 文件系统缓存条目：取决于文件大小和访问模式
  - 对于 socket：额外的网络缓冲区（读缓冲 + 写缓冲）

示例计算（10000 个打开文件）：
  10000 × 300 字节（struct file）  = ~3 MB
  10000 × 64KB（管道缓冲区）       = ~640 MB（如果是管道）
  
因此大量 fd 的内存开销主要来自缓冲区，而非 fd 结构本身。
```

#### 6.3.2 fd 泄漏的诊断方法

```bash
# === fd 泄漏诊断 ===

cat > /tmp/ex63-fd-leak-check.sh << 'SCRIPT'
#!/bin/bash

# 监控进程的 fd 数量变化，检测是否存在泄漏

MONITOR_PID=${1:-$$}     # 要监控的 PID，默认当前 shell
INTERVAL=${2:-2}         # 采样间隔（秒）
DURATION=${3:-30}        # 监控时长（秒）

echo "监控 PID $MONITOR_PID 的 fd 数量（每 ${INTERVAL}s 采样一次，共 ${DURATION}s）"
echo ""

prev_count=0
elapsed=0
while [[ $elapsed -lt $DURATION ]]; do
    if [[ ! -d /proc/$MONITOR_PID/fd ]]; then
        echo "进程 $MONITOR_PID 已结束"
        break
    fi

    current_count=$(ls /proc/$MONITOR_PID/fd/ 2>/dev/null | wc -l)
    timestamp=$(date '+%H:%M:%S')

    if [[ $current_count -gt $prev_count ]]; then
        change="↑ +$((current_count - prev_count))（可能泄漏）"
    elif [[ $current_count -lt $prev_count ]]; then
        change="↓ -$((prev_count - current_count))"
    else
        change="→ 不变"
    fi

    printf "[%s] fd 数量: %-4d  %s\n" "$timestamp" "$current_count" "$change"
    prev_count=$current_count
    sleep "$INTERVAL"
    elapsed=$((elapsed + INTERVAL))
done

echo ""
echo "监控完成。如果 fd 数量持续增长，可能存在文件描述符泄漏。"
echo "使用 lsof -p $MONITOR_PID 查看具体哪些 fd 被打开。"
SCRIPT

# 创建一个用于演示的测试（模拟 fd 泄漏）
cat > /tmp/ex63-fd-leaker.sh << 'LEAK'
#!/bin/bash
echo "模拟器 PID: $$"
echo "每 3 秒打开 2 个 fd 但不关闭..."

    eval "exec $((i+10))>/tmp/leaked-\$i.txt"
    echo "  打开了 fd $((i+10))"
    sleep 3
done
echo "模拟器完成（fd 已泄漏）"
sleep 5
LEAK

# 启动模拟器并在后台监控
# bash /tmp/ex63-fd-leaker.sh &
# LEAKER_PID=$!
# bash /tmp/ex63-fd-leak-check.sh $LEAKER_PID 3 20
# kill $LEAKER_PID 2>/dev/null
# wait $LEAKER_PID 2>/dev/null
# 以上为注释，实际执行时间太长

echo "fd 泄漏检查脚本已生成: /tmp/ex63-fd-leak-check.sh"
echo "fd 泄漏模拟器已生成: /tmp/ex63-fd-leaker.sh"
echo "手动执行以观察效果："
echo "  bash /tmp/ex63-fd-leaker.sh &"
echo "  bash /tmp/ex63-fd-leak-check.sh \$! 3 20"

rm -f /tmp/ex63-fd-leak-check.sh /tmp/ex63-fd-leaker.sh
rm -f /tmp/leaked-*.txt
```

### 6.5 文件描述符与 Socket 编程

在 Linux 中，socket 也是文件描述符的一种。`socket()` 系统调用返回的同样是一个整数 fd，你可以像操作文件一样对它进行 `read()`、`write()`、`close()` 操作。

```
+------------------------------------------------------------------+
|                    Socket 作为文件描述符                              |
|                                                                  |
|  socket() 返回一个 fd                                               |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │                                                              │ |
|  │  int sockfd = socket(AF_INET, SOCK_STREAM, 0);               │ |
|  │  // sockfd 现在是一个普通的文件描述符                           │ |
|  │                                                              │ |
|  │  write(sockfd, "GET / HTTP/1.0\r\n\r\n", 18);               │ |
|  │  // 和写文件完全相同的系统调用                                  │ |
|  │                                                              │ |
|  │  read(sockfd, buffer, sizeof(buffer));                       │ |
|  │  // 和读文件完全相同的系统调用                                  │ |

|  │  // 和关闭文件完全相同的系统调用                                │ |
|  │                                                              │ |
|  │  这就是"一切皆文件"的力量：                                    │ |

```

```bash
# 在 Bash 中通过 /dev/tcp 观察 socket 作为 fd 的行为
# （回顾第 20 章 6.5 节）

echo "=== /dev/tcp 伪设备（socket fd 在 Bash 中的体现） ==="

# 打开一个 TCP 连接（在子 shell 中）
(
    # Bash 会自动创建一个 socket fd
    if exec 3<>/dev/tcp/example.com/80 2>/dev/null; then
        echo "TCP 连接已建立（fd 3 是一个 socket）"
        echo "fd 3 在 /proc 中的信息："
        ls -la /proc/$BASHPID/fd/3 2>/dev/null
        echo ""
        echo "发送 HTTP 请求："
        echo -e "HEAD / HTTP/1.0\r\nHost: example.com\r\n\r\n" >&3
        echo "响应头："
        head -5 <&3
        exec 3>&-
    else
        echo "无法连接（可能无网络或权限问题）"
    fi
) 2>/dev/null || echo "连接测试失败"
```

### 6.7 实战建议：构建健壮的 fd 管理习惯

```
每天都会用到的 fd 管理最佳实践：

1. 脚本开头保存原始 fd
   exec 3>&1 4>&2       # 保存 stdout 和 stderr
   在脚本结束时或出错时恢复

2. 用完的 fd 立即关闭
   exec N>&-  或  exec N<&-
   不要等到脚本结束才关闭 —— 资源越早释放越好

3. 使用子 shell 隔离 fd 作用域
   (
       exec 3>temp.log
       do_something
   )
   # fd 3 在子 shell 结束后自动清理，无需手动 close

4. 在长时间运行的服务脚本中定期检查 fd 数量
   通过 /proc/$$/fd/ 或 lsof 监控

5. 设置合理的 ulimit
   ulimit -n 4096  # 或更高，取决于应用需求

6. 当遇到 "Too many open files" 时：
   - 先用 lsof -p PID 查看哪些 fd 被打开
   - 检查是否有 fd 泄漏（同样的文件被反复打开未关闭）
   - 评估是否需要提高 ulimit -n
   - 检查系统级 fs.file-max 是否足够
```

**本章小结：**

本章深入了 Linux I/O 系统的底层核心：文件描述符。回顾本章学到的关键知识：

1. **文件描述符的本质**：一个整数索引，指向内核的 struct file 对象。它实现了"一切皆文件"的抽象，让进程通过统一的接口操作所有 I/O 资源。

2. **exec 操控 fd**：`exec N>file` 打开/重定向 fd，`exec N>&M` 复制 fd（dup2），`exec N>&-` 关闭 fd。这些操作直接作用于当前 Shell 进程，不做 fork。

3. **lsof**：最强大的 fd 诊断工具，可以回答"谁打开了这个文件"、"这个进程打开了哪些文件"、"哪个 socket 连接对应哪个进程"等问题。

4. **`/proc/PID/fd/`**：通过符号链接直接观察任何进程的 fd 状态，是系统诊断和文件恢复的重要工具。

5. **ulimit**：进程级的 fd 数量限制。从 `ulimit -n`（Shell 层面）到 `limits.conf`（PAM 层面）到 `fs.nr_open`（内核层面），形成三级限制体系。

6. **非阻塞 I/O**：从"阻塞 vs 非阻塞"的概念引入，到 select/poll/epoll I/O 多路复用的全景图，理解高性能服务器为什么需要这些机制。

文件描述符是 Unix/Linux 编程中最基础也最重要的抽象。理解它，你就真正理解了"一切皆文件"这句话的含义。在第 20 章，你学会了如何用 Shell 操作符连接数据流；在本章，你理解了这些操作符底层的内核机制。这两章共同构成了 Linux I/O 的完整知识体系。
