## 1. 概述

### 1.1 从"用好系统"到"理解系统的核心"

前面的章节带你掌握了从文件管理到 Shell 编程、从服务管理到网络配置的完整技能链。你学会了用 `systemctl` 管理服务，用 `iptables` 配置防火墙，用 `ssh` 远程登录，用 `cron` 调度任务——所有这些能力都建立在一个共同的基础之上：**Linux 内核（Linux Kernel）**。

内核是操作系统的心脏。它运行在 CPU 的最高特权级别（Ring 0），直接管理硬件资源——CPU 调度、内存分配、磁盘 I/O、网络协议栈——并向用户空间程序提供统一的系统调用（System Call）接口。你执行的每一个命令，从 `ls` 到 `sshd`，最终都要通过系统调用进入内核才能完成实际操作。

**为什么需要管理内核模块和参数？**

Linux 内核虽然是一个整体式内核（Monolithic Kernel），但它通过**可加载内核模块（Loadable Kernel Module, LKM）**实现了高度的灵活性和可扩展性。这意味着：

- **不需要重新编译内核就能添加功能：** 插入一个新硬件的驱动程序？加载对应的内核模块即可。
- **不需要的功能不占用内存：** 未加载的模块只是磁盘上的 `.ko` 文件，不消耗运行时资源。
- **运行时调整内核行为：** 通过 `sysctl` 修改内核参数，无需重启——从网络协议栈的缓冲区大小到虚拟内存的交换倾向，都可以动态调整。

**本章的核心使命：建立对 Linux 内核运行时的管理能力。** 你将学会查看内核信息、管理内核模块的加载与卸载、通过 `sysctl` 和 `/proc/sys` 动态调整内核参数，以及探索 `/proc` 和 `/sys` 两个关键伪文件系统。这些技能在你需要排查硬件驱动问题、优化系统性能、或深入了解系统行为时至关重要。

### 1.3 本章覆盖的命令与概念

| 类别 | 命令/概念 | 用途 |
|------|----------|------|
| **内核信息** | `uname` | 打印内核名称、版本、架构等系统信息——了解"我在跑什么内核" |
| **模块列表** | `lsmod` | 列出当前已加载的所有内核模块——内核的"已安装插件清单" |

| **依赖生成** | `depmod` | 扫描所有模块并生成依赖关系数据库——`modprobe` 依赖它 |

| **内核对象** | `/sys/` | sysfs 文件系统——内核对象（设备、驱动、总线、模块参数）的结构化视图 |
| **进程信息** | `/proc/` | procfs 文件系统——进程信息和内核运行时状态的窗口 |

**关键认知：Linux 是"整体式内核 + 模块"的混合架构。** 它不是一个纯粹的微内核（Microkernel），核心子系统（进程调度、内存管理、文件系统、网络协议栈）都运行在内核空间中，共享同一个地址空间。但它通过可加载内核模块（LKM）机制，将设备驱动、文件系统类型、网络协议等可选功能编译为独立的 `.ko` 文件，可以在运行时动态加载和卸载。这种设计兼顾了整体式内核的高性能和微内核的灵活性。

### 2.2 内核版本编号规则

Linux 内核的版本号承载着重要的信息。理解版本号的构成，是你判断内核功能、安全补丁状态和兼容性的基础。

#### 2.2.1 当前版本格式（3.0 之后，2011 年起）

从 Linux 3.0 开始，内核版本号的格式简化为：

```
w.xx.y-zzz-flavor

例如：6.8.0-31-generic
      │ │ │  │    └─── flavor: 内核风味/变体
      │ │ │  │
      │ │ │  └──────── ABI 号: Ubuntu 特定的应用二进制接口修订号
      │ │ │
      │ │ └─────────── 补丁级别 (patchlevel): 上游稳定版补丁号
      │ │
      │ └───────────── 主版本号 (major): 上游主要版本号
      │
      └─────────────── 主版本 (version): 上游主版本号
```

每个部分的含义：

| 字段 | 含义 | 示例值 `6.8.0-31-generic` |
|------|------|--------------------------|
| `w` (version) | 上游主版本号。每约 2-3 个月发布一个新的大版本 | `6` |
| `xx` (major) | 该主版本内的修订号。用于新功能和较大变更 | `8` |
| `y` (patchlevel) | 上游稳定版补丁号。只包含 bug 修复和安全补丁 | `0` |
| `zzz` (ABI) | Ubuntu 特有的 ABI（Application Binary Interface，应用二进制接口）号。在内核配置变化导致内核模块不兼容时递增 | `31` |
| `flavor` | 内核构建变体。不同变体针对不同使用场景优化 | `generic` |

**Ubuntu 24.04 LTS 常见的内核风味（flavor）：**

| 风味 | 全称 | 适用场景 |
|------|------|---------|
| `generic` | 通用内核 | 桌面和服务器通用——默认选择。包含广泛的硬件驱动支持 |
| `lowlatency` | 低延迟内核 | 音频制作、实时数据处理——降低调度延迟，牺牲部分吞吐量 |
| `oracle` | Oracle 优化内核 | 针对 Oracle 数据库负载优化 |
| `aws` | AWS 优化内核 | Amazon Web Services 云环境的优化内核 |
| `azure` | Azure 优化内核 | Microsoft Azure 云环境的优化内核 |
| `gcp` | GCP 优化内核 | Google Cloud Platform 云环境的优化内核 |
| `kvm` | KVM 虚拟化内核 | 作为 KVM 虚拟机 Guest 运行时的精简内核 |
| `oem` | OEM 内核 | 厂商定制的内核——通常包含特定硬件的额外驱动 |

```bash
# 查看当前内核的完整版本信息
uname -r
# 输出：6.8.0-31-generic

# 查看内核版本号中各部分的详细含义
cat /proc/version
# 输出示例：
# Linux version 6.8.0-31-generic (buildd@lcy02-amd64-091) (x86_64-linux-gnu-gcc-13
# (Ubuntu 13.2.0-4ubuntu3) 13.2.0, GNU ld (GNU Binutils for Ubuntu) 2.42) #31-Ubuntu
# SMP PREEMPT_DYNAMIC Sat Apr 20 02:32:42 UTC 2024
```

#### 2.2.2 内核版本编号的历史演变

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Linux 内核版本编号演变史                             │
│                                                                      │
│  1991 - 1994    0.01 → 1.0                                          │
│                 早期开发阶段，版本号无固定规则                          │
│                                                                      │
│  1994 - 2011    1.0 → 2.6.39                                        │
│                 格式: major.minor.patch                              │
│                 • 奇数 minor = 开发版 (如 2.5.x)                      │
│                 • 偶数 minor = 稳定版 (如 2.6.x)                      │
│                 这一规则在 2.6.x 之后被废弃                            │
│                                                                      │
│  2011 年至今    3.0 → 6.x                                            │
│                 格式: w.xx.y (简化)                                   │
│                 • Linus Torvalds 决定简化版本号                        │
│                 • 不再区分开发版/稳定版                                │
│                 • 所有版本都相对稳定，开发工作在发布候选版 (RC) 中完成  │
│                 • 大约每 9-10 周发布一个新的大版本                      │
│                                                                      │
│  版本号跳转典故：                                                      │
│  • 2.6.39 → 3.0 (2011): 20 周年，Torvalds 嫌版本号太长                │
│  • 3.19 → 4.0 (2015): 遵循"大版本号数到太大就进位"的习惯               │
│  • 4.20 → 5.0 (2019): 同上                                          │
│  • 5.19 → 6.0 (2022): 同上                                          │
└─────────────────────────────────────────────────────────────────────┘
```

**安全提醒：** 内核版本号直接关系到系统的安全状态。许多安全漏洞（CVE, Common Vulnerabilities and Exposures）都针对特定的内核版本。一旦发现你运行的内核版本存在已知漏洞，应立即通过 `apt upgrade` 更新内核包（Ubuntu 上内核更新不需要重启整个系统——详见 6.3 节的 Livepatch 话题）。

```bash
# 列出已安装的所有内核版本
dpkg -l | grep linux-image
# 输出示例：
# ii  linux-image-6.8.0-31-generic  6.8.0-31.31  amd64  Linux kernel image for version 6.8.0 on 64 bit x86
# ii  linux-image-6.8.0-35-generic  6.8.0-35.35  amd64  Linux kernel image for version 6.8.0 on 64 bit x86

# 查看当前启动的内核版本
uname -r
# 6.8.0-35-generic

# 查看已安装但未使用的旧内核
dpkg -l | grep '^ii.*linux-image' | grep -v "$(uname -r)"
```

### 2.3 可加载内核模块（LKM）

#### 2.3.1 什么是内核模块

内核模块是一段可以在运行时动态加载到内核中的代码，它扩展了内核的功能而不需要重新编译整个内核。每个编译好的模块是一个 `.ko`（Kernel Object）文件，存放在 `/lib/modules/$(uname -r)/` 目录下。

```
┌─────────────────────────────────────────────────────────────────────┐
│                 模块的物理位置与逻辑关系                                │
│                                                                      │
│  磁盘上 (文件系统):                                                   │
│  /lib/modules/6.8.0-31-generic/                                     │
│  ├── kernel/                                                         │
│  │   ├── drivers/           ← 设备驱动（最大的模块类别）               │
│  │   │   ├── net/           ←     网卡驱动                           │
│  │   │   ├── gpu/           ←     显卡驱动                           │
│  │   │   ├── block/         ←     块设备驱动                         │
│  │   │   └── ...            ←     各类外设驱动                        │
│  │   ├── fs/                ← 文件系统驱动                            │
│  │   │   ├── ext4/                                                      │
│  │   │   ├── xfs/                                                       │
│  │   │   └── nfs/                                                       │
│  │   ├── net/               ← 网络协议模块                            │
│  │   │   ├── ipv6/                                                      │
│  │   │   └── netfilter/                                                │
│  │   └── ...                                                            │
│  ├── modules.alias          ← 模块别名数据库                          │
│  ├── modules.dep            ← 模块依赖关系（modprobe 使用）            │
│  ├── modules.symbols        ← 模块导出的符号表                        │
│  └── modules.builtin        ← 编译进内核（非模块）的组件列表           │
│                                                                      │
│  内存中 (内核空间):                                                   │
│  已加载的模块成为内核的一部分，运行在内核地址空间                       │
│  → lsmod 查看 /sys/module/*/ 互访                                     │
└─────────────────────────────────────────────────────────────────────┘
```

```bash
# 查看当前内核的模块目录
ls /lib/modules/$(uname -r)/
# 输出示例：
# build   modules.alias   modules.dep    modules.symbols
# kernel  modules.alias.bin  modules.dep.bin  modules.softdep
# misc    modules.builtin    modules.devname  modules.srp
# ...

# 统计模块总数
find /lib/modules/$(uname -r)/kernel -name '*.ko' | wc -l
# Ubuntu 24.04 上通常有 4000-5000+ 个模块文件

# 查看所有模块占用的磁盘空间
du -sh /lib/modules/$(uname -r)/
# 通常在 200-500MB 范围内
```

#### 2.3.2 模块加载的完整流程

这是本章最核心的概念之一。理解模块加载的完整链路，你就真正理解了 `modprobe` 和 `insmod` 的区别。

```
┌─────────────────────────────────────────────────────────────────────┐
│                模块加载（Load）的完整流程                               │
│                                                                      │
│   用户或系统                       kmod 工具链                内核     │
```

#### 2.3.3 内置组件 vs 可加载模块

并非所有内核功能都是模块。很多核心功能在编译内核时就已决定是**内置（built-in）**还是**模块化（modular）**。

```bash
# 查看当前内核中编译进内核（非模块）的组件列表
wc -l /lib/modules/$(uname -r)/modules.builtin
# Ubuntu 24.04 上通常有 2000+ 个内置组件

# 查看某个组件是内置还是模块
# 方式1：检查 /proc/modules 或 lsmod
lsmod | grep ext4
# 如果有输出 → 该功能以模块形式存在
# 如果无输出 → 可能是内置的

# 方式2：检查 modules.builtin
grep ext4 /lib/modules/$(uname -r)/modules.builtin
# 如果有输出 → 编译进内核
# 如果无输出 + lsmod 有 → 以模块形式存在

# 方式3：检查内核配置（如果存在）
if [ -f /boot/config-$(uname -r) ]; then
    grep CONFIG_EXT4_FS /boot/config-$(uname -r)
fi
# 输出为 CONFIG_EXT4_FS=y → 内置
# 输出为 CONFIG_EXT4_FS=m → 模块化
# 输出为 CONFIG_EXT4_FS is not set → 未编译
```

### 2.4 /proc 伪文件系统（procfs）

`/proc` 是一个虚拟文件系统（Virtual File System），它并不存储在实际的磁盘上。它的内容由内核在访问时动态生成，是用户空间窥探内核内部状态的"窗口"。`/proc` 有两个主要用途：

1. **进程信息：** 每个运行中的进程在 `/proc/<PID>/` 下有一个目录，包含该进程的内存映射、文件描述符、命令行参数、环境变量等
2. **内核信息：** `/proc` 下的非数字目录和文件提供系统的全局信息——CPU 信息、内存统计、内核版本、挂载信息、网络统计等

```bash
# 查看 /proc 的一级结构
ls /proc/
# 典型的输出包含：
# 数字目录（进程 PID）、数字命名的目录都是进程信息
# 非数字文件/目录：cpuinfo, meminfo, uptime, version, partitions,
#                  mounts, filesystems, sys/, net/, ...

# 查看 /proc 的类型
mount | grep proc
# 输出示例：
# proc on /proc type proc (rw,nosuid,nodev,noexec,relatime)
```

**本章重点关注的路径：**

| 路径 | 内容 | 示例用途 |
|------|------|---------|
| `/proc/cpuinfo` | CPU 详细信息——型号、核心数、频率、缓存大小、支持的指令集 | `grep "model name" /proc/cpuinfo` |
| `/proc/meminfo` | 内存使用统计——总量、空闲、缓冲区、缓存、交换区 | `grep MemAvailable /proc/meminfo` |
| `/proc/version` | 内核版本字符串——包含编译信息 | `cat /proc/version` |
| `/proc/cmdline` | 内核启动参数——Bootloader 传递给内核的参数 | `cat /proc/cmdline` |
| `/proc/uptime` | 系统运行时间和空闲时间（秒） | `cat /proc/uptime` |
| `/proc/loadavg` | 系统负载平均值——1分钟、5分钟、15分钟 | `cat /proc/loadavg` |
| `/proc/modules` | 已加载模块列表（与 `lsmod` 输出同源） | `cat /proc/modules` |
| `/proc/mounts` | 当前挂载点信息（与 `mount` 命令同源） | `cat /proc/mounts` |
| `/proc/partitions` | 磁盘分区信息 | `cat /proc/partitions` |
| `/proc/devices` | 已注册的字符设备和块设备 | `cat /proc/devices` |
| `/proc/filesystems` | 内核支持的文件系统类型 | `cat /proc/filesystems` |
| `/proc/sys/` | **sysctl 可调参数**——内核运行时参数的读写接口 | 详见 2.6 节和 3.9 节 |
| `/proc/net/` | 网络协议栈统计——ARP 表、路由表、TCP 连接、网络设备 | `cat /proc/net/tcp` |

**`/proc` 的核心特性——动态性：**

```bash
# /proc 中的文件大小通常显示为 0，因为它们的内容在读取时动态生成
ls -lh /proc/cpuinfo
# 输出：-r--r--r-- 1 root root 0 Jul 30 12:00 /proc/cpuinfo
#      注意文件大小为 0！

cat /proc/cpuinfo | wc -l
# 但实际能读取出数百行内容——内容在读取的瞬间由内核生成

# 连续两次读取同一个文件，内容可能不同
cat /proc/uptime; sleep 1; cat /proc/uptime
# 第一次：1234567.89 987654.32
# 第二次：1234568.89 987655.32
# 两次读取的值不同——因为它是实时状态的真实反映
```

### 2.5 /sys 伪文件系统（sysfs）

`/sys` 是另一个虚拟文件系统（sysfs），于 Linux 2.6 引入。与 `/proc` 混在一起存放各种信息不同，`/sys` 提供了**结构化的、层次化的内核对象视图**——它将内核中的设备、驱动、总线、类、模块等以目录树的形式组织起来。

```
┌─────────────────────────────────────────────────────────────────────┐
│                      /sys 的顶层结构                                    │
│                                                                      │
│  /sys/                                                               │
│  ├── block/          ← 块设备（磁盘、分区、loop 设备）                   │
│  │   ├── sda/                     ← sda 磁盘                         │
│  │   │   ├── size                 ←     磁盘大小（扇区数）             │
│  │   │   ├── stat                 ←     I/O 统计                     │
│  │   │   └── sda1/               ←     第一个分区                    │
│  │   └── loop0/                   ← loop 设备                       │
│  │                                                                   │
│  ├── bus/            ← 总线类型（PCI、USB、SCSI、I2C、SPI...）          │
│  │   ├── pci/                     ← PCI 总线                         │
│  │   │   ├── devices/            ←     每个 PCI 设备                 │
│  │   │   └── drivers/            ←     PCI 驱动                     │
│  │   └── usb/                     ← USB 总线                         │
│  │                                                                   │
│  ├── class/          ← 按功能分类的设备（不看连接方式，只看功能）        │
│  │   ├── net/                     ← 所有网络接口                      │

│  │   ├── tty/                     ← 所有终端设备                      │
│  │   ├── backlight/               ← 背光控制                         │
│  │   ├── thermal/                 ← 温度传感器                        │
│  │   └── power_supply/            ← 电源信息（电池、AC 适配器）        │
│  │                                                                   │
│  ├── devices/        ← 所有设备按物理拓扑排列                          │
│  │   ├── pci0000:00/              ← PCI 总线 0 上的设备               │
│  │   │   ├── 0000:00:02.0/       ←     显卡                        │
│  │   │   └── 0000:00:1f.6/       ←     以太网控制器                  │
│  │   └── virtual/                 ← 虚拟设备                         │
│  │                                                                   │
│  ├── firmware/       ← 固件接口（ACPI、EFI、设备树）                    │
│  │                                                                   │
│  ├── fs/             ← 文件系统相关信息                               │
│  │                                                                   │
│  ├── kernel/         ← 内核全局参数（调度、内存、调试）                   │
│  │   ├── mm/                      ← 内存管理参数                      │
│  │   └── debug/                   ← 动态调试接口                      │
│  │                                                                   │

│  │   ├── e1000e/                  ← e1000e 模块                      │
│  │   │   ├── parameters/         ←     模块参数                     │
│  │   │   ├── sections/           ←     ELF 段信息                   │
│  │   │   └── refcnt              ←     引用计数                     │
│  │   └── ...                                                           │
│  │                                                                   │
│  └── power/           ← 电源管理接口                                 │
└─────────────────────────────────────────────────────────────────────┘
```

**`/sys` 的核心设计原则：**

1. **一个文件一个值：** `/sys` 中的每个文件通常只包含一个值——这与 `/proc` 的表格形式不同
2. **属性可读写：** 有些文件可以写入，从而在运行时改变内核行为（例如背光亮度、CPU 频率策略）
3. **结构化层次：** 设备按物理拓扑（`/sys/devices/`）和功能分类（`/sys/class/`）两种视角组织
4. **符号链接连接视角：** `/sys/class/net/eth0` 实际上是一个符号链接，指向 `/sys/devices/pci0000:00/.../net/eth0`

```bash
# 查看 /sys 的类型
mount | grep sysfs
# 输出示例：
# sysfs on /sys type sysfs (rw,nosuid,nodev,noexec,relatime)

# 查看网卡的 /sys 信息
ls /sys/class/net/
# 列出所有网络接口

# 查看 eth0（或 enp0s3 等）的详细信息
# 注意：实际接口名因系统而异，使用 $(ip -o link show | awk -F': ' '{print $2}' | head -1) 获取第一个非 lo 接口
FIRST_IFACE=$(ip -o link show | awk -F': ' '{print $2}' | grep -v lo | head -1)
echo "第一个网络接口: $FIRST_IFACE"
cat /sys/class/net/$FIRST_IFACE/address   # MAC 地址
cat /sys/class/net/$FIRST_IFACE/mtu       # MTU
cat /sys/class/net/$FIRST_IFACE/speed     # 链路速度（Mbps）
cat /sys/class/net/$FIRST_IFACE/operstate # 运行状态 (up/down)
```

### 2.6 sysctl 机制与内核参数调优

`sysctl` 是运行时调整内核参数的标准接口。它通过 `/proc/sys/` 文件系统与内核通信——读取某个参数就是读取 `/proc/sys/` 下对应的文件，写入就是向对应文件写入值。

```
┌─────────────────────────────────────────────────────────────────────┐
│                     sysctl 机制架构                                     │
│                                                                      │
│  用户接口                                                             │
│  ┌───────────────┐    ┌───────────────┐    ┌───────────────────────┐│
│  │ sysctl 命令    │    │ echo/cat      │    │ 配置文件               ││
│  │ sysctl -w     │    │ > /proc/sys/  │    │ /etc/sysctl.conf     ││
│  │ 参数=值       │    │               │    │ /etc/sysctl.d/*.conf  ││
│  └───────┬───────┘    └───────┬───────┘    └───────────┬───────────┘│
│          │                    │                        │             │
│          └────────────────────┼────────────────────────┘             │
│                               │                                      │
│                      /proc/sys/ 文件系统                              │
│                               │                                      │
│  ┌────────────────────────────┼───────────────────────────────────┐ │
│  │                            ▼                    内核空间        │ │
│  │  ┌─────────────────────────────────────────────────────────┐   │ │
│  │  │  内核参数表（Kernel Parameter Table）                      │   │ │
│  │  │                                                           │   │ │
│  │  │  /proc/sys/ 目录树直接映射到内核内部的数据结构：            │   │ │
│  │  │                                                           │   │ │
│  │  │  /proc/sys/net/    →  网络协议栈参数                        │   │ │
│  │  │  /proc/sys/kernel/ →  内核核心参数（hostname, panic等）     │   │ │
│  │  │  /proc/sys/vm/     →  虚拟内存管理参数                      │   │ │
│  │  │  /proc/sys/fs/     →  文件系统参数（打开文件数限制等）       │   │ │
│  │  │  /proc/sys/dev/    →  设备相关参数                          │   │ │
│  │  │  /proc/sys/user/   →  用户命名空间参数                      │   │ │
│  │  └─────────────────────────────────────────────────────────┘   │ │
│  └────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  配置持久化流程：                                                      │
│  ┌─────────────────────────────────────────────────────────────────┐ │
│  │  systemd-sysctl.service                                        │  │
│  │  ┌──────────┐    ┌──────────────┐    ┌────────────────────┐   │  │
│  │  │ 系统启动 →│───►│ systemd-     │───►│ /etc/sysctl.conf  │   │  │
│  │  │           │    │ sysctl       │    │ .d/*.conf         │   │  │
│  │  │           │    │ --system     │    │ .d/*.conf         │   │  │
│  │  │           │    │              │    │ /run/sysctl.d/     │   │  │
│  │  │           │    │              │    │ /usr/lib/sysctl.d/ │   │  │
│  │  └──────────┘    └──────────────┘    └────────────────────┘   │  │
│  └─────────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────┘
```

**sysctl 参数命名规则：** `/proc/sys/` 下的路径分隔符 `/` 在 sysctl 中替换为 `.`。

```bash
# 路径和 sysctl 键的对应关系：
# /proc/sys/net/ipv4/ip_forward  ←→  net.ipv4.ip_forward
# /proc/sys/kernel/hostname      ←→  kernel.hostname
# /proc/sys/vm/swappiness        ←→  vm.swappiness
```

**配置文件的优先级（从低到高）：**

| 优先级 | 路径 | 说明 |
|--------|------|------|
| 最低 | `/usr/lib/sysctl.d/*.conf` | 发行版默认配置——不要直接修改 |
| 中等 | `/etc/sysctl.d/*.conf` | **系统管理员自定义配置——推荐使用** |
| 较高 | `/run/sysctl.d/*.conf` | 运行时配置（重启后丢失） |
| 最高 | `/etc/sysctl.conf` | 传统默认文件——仍然有效，但推荐使用 `/etc/sysctl.d/` |

**同一参数出现在多个文件时，按字母顺序读取，后读取的覆盖先读取的。**

## 3. 命令详解

### 3.1 uname —— 打印系统信息

`uname`（Unix Name）是最简单也最常用的内核信息查询命令。它从内核数据结构中直接读取系统信息。

**基本语法：**

```
uname [选项...]
```

#### 3.1.1 uname 参数表

| 参数 | 全称 | 说明 | 示例输出 |
|------|------|------|---------|
| `-s` | Kernel Name | 内核名称 | `Linux` |
| `-n` | Nodename | 网络主机名 | `ubuntu-server` |
| `-r` | Kernel Release | 内核发布版本号 | `6.8.0-31-generic` |
| `-v` | Kernel Version | 内核编译版本字符串 | `#31-Ubuntu SMP PREEMPT_DYNAMIC Sat Apr 20 ...` |
| `-m` | Machine | 硬件架构名称 | `x86_64` |
| `-p` | Processor | 处理器类型（在某些系统上同 `-m`） | `x86_64` |
| `-i` | Hardware Platform | 硬件平台（在某些系统上同 `-m`） | `x86_64` |
| `-o` | Operating System | 操作系统名称 | `GNU/Linux` |
| `-a` | All | 打印所有以上信息（按上述顺序） | 组合输出 |

#### 3.1.2 参数实战示例

```bash
# ========== 基本使用 ==========

# 1. 只打印内核名称
uname -s
# 输出：Linux

# 2. 打印内核版本（最常用）
uname -r
# 输出：6.8.0-31-generic

# 3. 打印所有信息（最常用组合）
uname -a
# 输出示例：
# Linux ubuntu-server 6.8.0-31-generic #31-Ubuntu SMP PREEMPT_DYNAMIC
# Sat Apr 20 02:32:42 UTC 2024 x86_64 x86_64 x86_64 GNU/Linux

# ========== 实用组合 ==========

# 4. 只获取内核版本号（用于脚本）
KERNEL_VER=$(uname -r)
echo "当前内核版本: $KERNEL_VER"

# 5. 获取硬件架构
uname -m
# 输出：x86_64 (表示 64 位 x86)
# 或：aarch64 (表示 64 位 ARM)

# 6. 判断是否为 64 位系统
if [ "$(uname -m)" = "x86_64" ]; then
    echo "64 位 x86 架构"
elif [ "$(uname -m)" = "aarch64" ]; then
    echo "64 位 ARM 架构"
fi

# 7. 获取完整的内核版本和编译信息
cat /proc/version
# 比 uname -v 更详细——包含编译器版本
# 输出：Linux version 6.8.0-31-generic (buildd@lcy02-amd64-091)
# (x86_64-linux-gnu-gcc-13 (Ubuntu 13.2.0-4ubuntu3) 13.2.0,
# GNU ld (GNU Binutils for Ubuntu) 2.42) #31-Ubuntu SMP PREEMPT_DYNAMIC
# Sat Apr 20 02:32:42 UTC 2024
```

### 3.2 lsmod —— 列出已加载模块

`lsmod` 显示当前已加载到内核中的所有模块及其依赖关系。其数据来源于 `/proc/modules`。

**基本语法：**

```
lsmod
```

> `lsmod` 没有选项参数——直接运行即可。它的输出格式化自 `/proc/modules`。

```bash
# 1. 列出所有已加载模块
lsmod
# 输出示例（截取前几行）：
# Module                  Size  Used by
# xt_conntrack           16384  1
# nft_chain_nat          16384  2
# xt_REDIRECT            12288  1
# ...
# e1000e                315392  0
# ...
# 列说明：
#   Module    = 模块名称
#   Size      = 模块占用的内存大小（字节）——不是 .ko 文件大小
#   Used by   = 依赖此模块的其他模块数量和名称

# 2. 统计已加载模块数量
lsmod | wc -l
# 减去表头行：实际模块数 = 行数 - 1

# 3. 查找特定模块
lsmod | grep e1000e
# 如果输出为空 → 该模块未加载
# 如果 Used by 为 0 → 无其他模块依赖它

# 4. 查看哪些模块被使用最多（按 Used by 排序）
lsmod | awk 'NR>1 {print $3, $1, $4}' | sort -rn | head -10

# 5. 比较 lsmod 和 /proc/modules（两者数据同源）
diff <(lsmod | tail -n +2 | awk '{print $1, $2, $3}' | sort) \
     <(cat /proc/modules | awk '{print $1, $2, $3}' | sort)
# 应该没有差异——lsmod 就是对 /proc/modules 的美化输出
```

**理解 `Used by` 列：**

```
Module                  Size  Used by
ufs                    73728  0
msdos                  20480  0
fat                    86016  2 vfat,msdos
```

- `fat` 模块的 `Used by` 为 `2 vfat,msdos`——表示 `vfat` 和 `msdos` 两个模块依赖 `fat`
- `ufs` 和 `msdos` 的 `Used by` 为 `0`——没有其他模块依赖它们，可以安全卸载
- **模块卸载规则：** 只有 `Used by` 为 `0` 的模块才能被卸载；依赖链中的底层模块不能被直接卸载

### 3.3 modinfo —— 查看模块信息

`modinfo` 显示内核模块文件的元数据（Metadata）——描述、作者、许可证、依赖关系、参数列表、固件文件、签名信息等。

**基本语法：**

```
modinfo [选项...] <模块名|模块文件路径>
```

#### 3.3.1 modinfo 参数表

| 参数 | 全称 | 说明 | 示例 |
|------|------|------|------|
| `-F <field>` | Field | 只打印指定字段的值——用于脚本 | `modinfo -F description e1000e` |
| `-b <path>` | Basedir | 指定模块搜索的基础目录 | `modinfo -b /path/to/root e1000e` |
| `-k <kernel>` | Kernel | 指定内核版本（而非当前运行的内核） | `modinfo -k 6.8.0-31-generic e1000e` |
| `-0` | Null | 使用 NULL 字符作为字段分隔符——对机器友好 | `modinfo -0 e1000e` |
| `--field <field>` | — | `-F` 的长格式 | `modinfo --field author e1000e` |

#### 3.3.2 参数实战示例

```bash
# ========== 查看模块信息 ==========

# 1. 查看模块的完整信息
modinfo e1000e
# 输出示例（部分）：
# filename:       /lib/modules/6.8.0-31-generic/kernel/drivers/net/ethernet/intel/e1000e/e1000e.ko
# version:        3.2.6-k
# license:        GPL v2
# description:    Intel(R) PRO/1000 Network Driver
# author:         Intel Corporation, <linux.nics@intel.com>
# srcversion:     B5A8C3D2E1F...
# alias:          pci:v00008086d00001502sv*sd*bc*sc*i*
# alias:          pci:v00008086d0000105Esv*sd*bc*sc*i*
# ...
# depends:        ptp, i2c-algo-bit
# retpoline:      Y
# name:           e1000e
# vermagic:       6.8.0-31-generic SMP preempt mod_unload modversions
# sig_id:         PKCS#7
# signer:         Canonical Ltd. Secure Boot Module Signing Key
# sig_key:        51:3D:17:FA:...
# sig_hashalgo:   sha512
# signature:      46:10:A1:3A:...

# 2. 提取单个字段（脚本友好）
modinfo -F description e1000e
# 输出：Intel(R) PRO/1000 Network Driver

modinfo -F depends e1000e
# 输出：ptp,i2c-algo-bit

modinfo -F author e1000e
# 输出：Intel Corporation, <linux.nics@intel.com>

# 3. 查看模块的可用参数（重要！）
modinfo -F parm e1000e
# 输出示例：
# debug:Debug level (0=none,...,16=all) (int)
# ...
# 每个参数可用于 modprobe 加载时配置

# 4. 查看整个模块目录中所有模块的 description
for mod in /lib/modules/$(uname -r)/kernel/drivers/net/ethernet/intel/e1000e/*.ko; do
    echo "=== $(basename $mod) ==="
    modinfo -F description "$mod" 2>/dev/null
done

# 5. 检查模块的签名信息（安全启动相关）
modinfo -F sig_id e1000e
# 输出：PKCS#7 （表示模块有有效签名）
# 如果 Secure Boot 开启，未签名的模块将无法加载

# 6. 查看模块的文件路径
modinfo -F filename e1000e
# 输出：/lib/modules/6.8.0-31-generic/kernel/drivers/net/ethernet/intel/e1000e/e1000e.ko

# 7. 使用文件路径而非模块名
modinfo /lib/modules/$(uname -r)/kernel/drivers/net/ethernet/intel/e1000e/e1000e.ko
# 效果与 modinfo e1000e 相同——但必须给出完整路径
```

**`modinfo` 输出字段详解：**

| 字段 | 含义 |
|------|------|
| `filename` | 模块文件的绝对路径 |
| `version` | 模块驱动版本（由模块作者定义的版本号） |
| `license` | 模块的许可证类型——GPL/BSD/Proprietary。内核不接受专有模块 |
| `description` | 模块的简短描述 |
| `author` | 模块作者信息 |
| `srcversion` | 源代码版本的哈希值——用于判断两个 `.ko` 是否编译自同一源码 |
| `alias` | 硬件 ID 别名——用于 `modprobe` 根据硬件 ID 自动匹配模块 |
| `depends` | 该模块的硬依赖——加载此模块前必须先加载这些 |
| `softdep` | 软依赖——建议在加载前/后加载，但非强制 |
| `parm` | 模块接受的参数及其描述——可在加载时通过 `modprobe` 传递 |
| `retpoline` | 是否使用了 Retpoline（Spectre 漏洞缓解技术） |
| `name` | 模块的逻辑名称 |
| `vermagic` | 内核版本魔数——模块必须与运行内核匹配，否则拒绝加载 |
| `sig_id` / `signer` / `sig_key` | 数字签名信息——UEFI Secure Boot 需要有效签名 |

### 3.4 modprobe —— 智能加载与卸载模块

`modprobe` 是内核模块管理的高级命令。与 `insmod`/`rmmod` 不同，`modprobe` 能够**自动解析依赖关系**——它会根据 `modules.dep` 数据库决定模块的加载顺序，确保先加载被依赖的模块。

**基本语法：**

```
modprobe [选项...] <模块名> [模块参数=值...]
modprobe -r [选项...] <模块名...>
```

#### 3.4.1 modprobe 参数表

| 参数 | 全称 | 说明 | 示例 |
|------|------|------|------|
| `-r` | Remove | 卸载模块（及未被使用的依赖模块） | `modprobe -r e1000e` |
| `-f` | Force | 强制加载或卸载——绕过版本检查或使用计数 | `modprobe -f mymodule` |
| `-v` | Verbose | 显示详细操作过程——打印每一步在做什么 | `modprobe -v e1000e` |
| `-n` | Dry-run | 干运行——不实际执行，仅显示将执行的操作 | `modprobe -n -v e1000e` |
| `-s` | Syslog | 将错误信息发送到 syslog 而非 stderr | `modprobe -s e1000e` |
| `-q` | Quiet | 安静模式——不显示错误信息 | `modprobe -q nonexist` |
| `-C <file>` | Config | 指定配置文件（默认 `/etc/modprobe.d/`） | `modprobe -C /path/to/config e1000e` |
| `-d <dir>` | Dirname | 指定模块搜索的基础目录 | `modprobe -d /lib/modules/6.8.0-31-generic` |
| `--show-depends` | — | 仅显示模块的依赖链，不实际加载 | `modprobe --show-depends e1000e` |
| `--first-time` | — | 如果模块已经加载则报错（而非静默成功） | `modprobe --first-time e1000e` |
| `--ignore-install` | — | 忽略模块的 install 命令（不执行安装脚本） | `modprobe --ignore-install e1000e` |

#### 3.4.2 参数实战示例

```bash
# ========== 加载模块 ==========

# 1. 基本加载
sudo modprobe e1000e
# 如果模块已加载，静默成功（无输出）
# 如果模块未加载，加载它及其所有依赖

# 2. 查看加载过程中的依赖解析（干运行 + 详细输出）
sudo modprobe -n -v e1000e
# 输出示例：
# insmod /lib/modules/6.8.0-31-generic/kernel/drivers/ptp/ptp.ko
# insmod /lib/modules/6.8.0-31-generic/kernel/drivers/i2c/algos/i2c-algo-bit.ko
# insmod /lib/modules/6.8.0-31-generic/kernel/drivers/net/ethernet/intel/e1000e/e1000e.ko
# 解释：按依赖顺序依次执行 insmod——先加载依赖，再加载目标

# 3. 查看模块的完整依赖链（不加载）
modprobe --show-depends e1000e
# 输出与 -n -v 类似，但格式更适合脚本解析

# 4. 加载模块并传递参数
sudo modprobe e1000e debug=1
# 传递 debug=1 参数给 e1000e 模块
# 可用参数通过 modinfo -F parm e1000e 查看

# ========== 卸载模块 ==========

# 5. 基本卸载
sudo modprobe -r e1000e
# 卸载 e1000e——同时卸载不再被其他模块使用的依赖模块
# 如果模块正在被使用（Used by > 0），卸载失败

# 6. 模拟卸载——查看将卸载哪些模块
sudo modprobe -r -n -v e1000e
# 输出示例（假设无其他依赖）：
# rmmod e1000e
# rmmod ptp
# rmmod i2c-algo-bit
# 解释：按依赖逆序卸载——先卸载使用者，再卸载被依赖者

# 7. 强制卸载（危险！）
sudo modprobe -r -f e1000e
# -f 强制卸载，即使模块正在使用
# ⚠ 这可能导致系统不稳定或数据丢失——仅用于调试

# ========== 配置模块加载行为 ==========

# 8. 查看模块加载时的自动配置
ls /etc/modprobe.d/
# 系统级和用户级模块加载配置文件

# 9. 创建模块黑名单（阻止模块自动加载）
echo "blacklist pcspkr" | sudo tee /etc/modprobe.d/blacklist-pcspkr.conf
# 阻止 PC 扬声器模块自动加载
# 需要重启或运行 sudo update-initramfs -u 生效

# 10. 查看模块加载配置文件
cat /etc/modprobe.d/blacklist.conf 2>/dev/null || echo "文件不存在"
```

### 3.5 insmod —— 直接插入模块

`insmod` 是低级命令——它直接将 `.ko` 文件插入内核，**不执行任何依赖检查**。如果模块依赖其他模块而它们尚未加载，`insmod` 会失败。

**基本语法：**

```
insmod <模块文件完整路径> [模块参数=值...]
```

```bash
# ========== insmod 基本使用 ==========

# 1. 使用完整路径插入模块
# ⚠ 先确认依赖已加载（用 modprobe --show-depends 查看）
sudo insmod /lib/modules/$(uname -r)/kernel/drivers/net/ethernet/intel/e1000e/e1000e.ko

# 2. 如果依赖未加载，insmod 会失败
sudo insmod /lib/modules/$(uname -r)/kernel/drivers/net/ethernet/intel/e1000e/e1000e.ko
# 可能的错误：
# insmod: ERROR: could not insert module e1000e.ko: Unknown symbol in module
# 这个错误说明模块需要的符号（由依赖模块提供）不存在——依赖未加载

# 3. 传递参数
sudo insmod /lib/modules/$(uname -r)/kernel/drivers/net/ethernet/intel/e1000e/e1000e.ko debug=2

# ========== insmod vs modprobe 对比 ==========
# insmod:  只做一件事——将指定的 .ko 文件插入内核
#          需要：完整的文件路径
#          不管：依赖关系
#          使用场景：调试、测试、临时插入手动编译的模块
#
# modprobe: 智能加载——解析依赖、处理别名、读取配置
#           需要：模块名（不需要路径）
#           管理：依赖关系、黑名单、模块参数配置
#           使用场景：日常工作——99% 的情况下应该用 modprobe
```

### 3.6 rmmod —— 直接移除模块

`rmmod` 是 `insmod` 的反操作——直接从内核中移除模块，不处理依赖关系。

**基本语法：**

```
rmmod [选项...] <模块名>
```

#### 3.6.1 rmmod 参数表

| 参数 | 全称 | 说明 |
|------|------|------|
| `-f` | Force | 强制移除——即使模块正在使用（危险！） |
| `-v` | Verbose | 显示详细操作信息 |
| `-w` | Wait | 等待直到模块不再被使用——而非立即报错 |
| `-s` | Syslog | 输出发送到 syslog |

```bash
# ========== rmmod 基本使用 ==========

# 1. 移除模块（使用模块名，不是文件路径）
sudo rmmod e1000e
# 如果模块正在使用中：
# rmmod: ERROR: Module e1000e is in use

# 2. 查看模块的使用者
lsmod | grep e1000e
# Used by 列显示使用者

# 3. 强制移除（危险）
sudo rmmod -f e1000e
# 即使模块在使用中也强制移除——可能导致内核崩溃或数据丢失
# 仅用于紧急调试

# 4. 等待移除（模块被释放后自动移除）
sudo rmmod -w e1000e
# 如果模块正在使用，命令会阻塞等待，直到使用计数降为 0

# ========== rmmod vs modprobe -r ==========
# rmmod <模块名>:        只移除指定的单个模块——如果该模块被其他模块依赖，失败
# modprobe -r <模块名>:  智能移除——递归处理依赖，先移除使用者，再移除被依赖者
# 推荐：始终使用 modprobe -r，除非你明确知道自己在做什么
```

### 3.7 depmod —— 生成模块依赖数据库

`depmod` 扫描 `/lib/modules/$(uname -r)/` 下的所有内核模块，分析它们的符号依赖关系，生成 `modules.dep` 和其他辅助数据库文件。`modprobe` 依赖这些文件来解析依赖关系。

**基本语法：**

```
depmod [选项...] [内核版本]
```

#### 3.7.1 depmod 参数表

| 参数 | 全称 | 说明 |
|------|------|------|
| `-a` | All | 处理所有模块（默认行为） |
| `-A` | Quick | 快速模式——只处理比 `modules.dep` 更新的模块 |
| `-n` | Dry-run | 干运行——输出依赖关系到 stdout，不写入文件 |
| `-v` | Verbose | 显示每个模块的处理过程 |
| `-e` | Errors | 报告所有无法解析的符号引用 |
| `-b <dir>` | Basedir | 指定基础目录（用于交叉编译场景） |

```bash
# ========== depmod 基本使用 ==========

# 1. 生成当前内核的模块依赖（需要 root 权限）
sudo depmod -a
# 扫描 /lib/modules/$(uname -r)/ 下所有 .ko 文件
# 生成 modules.dep, modules.alias, modules.symbols 等文件

# 2. 快速模式——只处理有变化的模块
sudo depmod -A
# 比较文件时间戳，跳过未修改的模块，速度更快

# 3. 查看依赖数据库的更新效果
ls -la /lib/modules/$(uname -r)/modules.dep
# 检查文件的修改时间

# 4. 干运行——查看将生成的依赖关系
depmod -n | head -20
# 输出示例：
# kernel/arch/x86/kvm/kvm-intel.ko: kernel/arch/x86/kvm/kvm.ko
# kernel/drivers/net/ethernet/intel/e1000e/e1000e.ko: kernel/drivers/ptp/ptp.ko ...

# 5. 安装新内核或手动编译内核模块后
sudo depmod -a $(uname -r)
# 显式指定内核版本（通常不需要——默认为当前运行内核）

# 6. 检查依赖完整性——报告所有未解析的符号
sudo depmod -ae
# -a: 处理所有模块
# -e: 报告无法解析的符号引用
# 这可以帮助发现损坏的模块或缺失的依赖

# ========== 何时需要运行 depmod ==========
# 1. 手动编译并安装了一个新的内核模块
# 2. 更新了 linux-modules 软件包
# 3. 安装了新的内核版本
# 4. 从源代码编译并 make modules_install 之后
```

**`depmod` 生成的关键文件：**

| 文件 | 内容 | 用途 |
|------|------|------|
| `modules.dep` | 模块依赖列表 | `modprobe` 解析加载依赖链 |
| `modules.dep.bin` | 上面的二进制索引版本 | 加速依赖查询 |
| `modules.alias` | 硬件 ID 到模块名的映射 | 插入新硬件时自动匹配驱动 |
| `modules.alias.bin` | 上面的二进制索引版本 | 加速别名查询 |
| `modules.symbols` | 模块导出符号与对应模块的映射 | 快速查找哪个模块导出了某个符号 |
| `modules.builtin` | 编译进内核（非模块）的组件列表 | 区分内置功能与模块化功能 |
| `modules.softdep` | 软依赖定义 | `modprobe` 处理 pre/post 软依赖 |
| `modules.devname` | 设备名称到模块的映射 | 创建设备节点时使用 |

### 3.8 sysctl —— 运行时内核参数管理

`sysctl` 是管理和调优内核运行时参数的标准工具。它能临时修改参数（重启后失效），也能配合配置文件实现持久化。

**基本语法：**

```
sysctl [选项...] [参数键...]
sysctl -w 参数键=值
sysctl -p [配置文件]
```

#### 3.8.1 sysctl 参数表

| 参数 | 全称 | 说明 | 示例 |
|------|------|------|------|
| `-a` | All | 显示所有可用的内核参数 | `sysctl -a` |
| `-A` | — | `-a` 的别名（某些系统上） | `sysctl -A` |
| `-w` | Write | 写入（修改）一个参数的值 | `sysctl -w net.ipv4.ip_forward=1` |
| `-p [file]` | Load | 从配置文件加载参数（默认 `/etc/sysctl.conf`） | `sysctl -p` |
| `-n` | Name-only | 只显示值，不显示键名 | `sysctl -n kernel.hostname` |
| `-e` | Ignore-errors | 忽略未知键的错误 | `sysctl -e -p /tmp/custom.conf` |
| `-q` | Quiet | 安静模式——不输出到 stdout | `sysctl -q -w net.ipv4.ip_forward=1` |
| `--system` | — | 加载所有系统配置文件（按优先级） | `sysctl --system` |
| `--load` | — | `-p` 的别名 | `sysctl --load /etc/sysctl.conf` |
| `--write` | — | `-w` 的长格式 | `sysctl --write net.ipv4.ip_forward=1` |

#### 3.8.2 参数实战示例

```bash
# ========== 查看内核参数 ==========

# 1. 查看所有参数（非常多——通常配合 grep）
sysctl -a | wc -l
# Ubuntu 24.04 上通常有 1500-2000+ 个参数

# 2. 查看特定类别的参数
sysctl -a | grep ^net.ipv4
# 或更精确
```

### 3.9 /proc/sys 探索

`/proc/sys/` 是 sysctl 参数的底层文件系统接口。`sysctl` 命令本质上就是对 `/proc/sys/` 下文件的读取和写入操作。

```bash
# ========== /proc/sys 目录结构 ==========

# 1. 查看顶层分类
ls /proc/sys/
# 输出：abi/  debug/  dev/  fs/  kernel/  net/  user/  vm/

# 2. 查看网络相关的分类
ls /proc/sys/net/
# 输出：core/  ipv4/  ipv6/  unix/  ...

# ========== 读取参数（与 sysctl 等效） ==========

# 3. 读取 IP 转发状态（两种方式等效）
cat /proc/sys/net/ipv4/ip_forward
# 输出：0 或 1
sysctl -n net.ipv4.ip_forward
# 输出：0 或 1

# 4. 读取主机名
cat /proc/sys/kernel/hostname
sysctl -n kernel.hostname

# 5. 读取 swappiness
cat /proc/sys/vm/swappiness
sysctl -n vm.swappiness

# ========== 写入参数（需要 root 权限） ==========

# 6. 临时修改 swappiness
sudo sh -c 'echo 20 > /proc/sys/vm/swappiness'
# 验证
cat /proc/sys/vm/swappiness
# 输出：20

# 7. 使用 tee 写入（管道 + sudo 的标准方式）
echo 60 | sudo tee /proc/sys/vm/swappiness

# ========== 遍历 /proc/sys 树 ==========

# 8. 查看所有可读的参数（非递归——仅一级）
ls /proc/sys/net/ipv4/
# 输出：ip_forward, tcp_syncookies, tcp_keepalive_time, ...
# 每个文件都是一个可调内核参数

# 9. 批量读取某类参数的值
for param in /proc/sys/net/ipv4/tcp_*; do
    echo "$(basename $param) = $(cat $param 2>/dev/null)"
done 2>/dev/null | head -10

# 10. 找出可写的参数（权限检查）
ls -la /proc/sys/net/ipv4/ip_forward | head -1
# 输出示例：
# -rw-r--r-- 1 root root 0 Jul 30 12:00 /proc/sys/net/ipv4/ip_forward
# 注意：如果有 w 权限（对 root），说明可写
```

### 3.10 /sys 探索

`/sys` 提供了结构化、层次化的内核对象视图。以下探索你最常用到的几条路径。

```bash
# ========== /sys/class —— 按功能分类 ==========

# 1. 查看网络接口类
ls /sys/class/net/
# 输出：eth0/  lo/  wlan0/ ...

# 2. 获取第一个非 lo 接口的信息
FIRST_IFACE=$(ls /sys/class/net/ | grep -v lo | head -1)
echo "接口: $FIRST_IFACE"
cat /sys/class/net/$FIRST_IFACE/address    # MAC 地址
cat /sys/class/net/$FIRST_IFACE/mtu        # MTU 值
cat /sys/class/net/$FIRST_IFACE/carrier    # 物理链路状态（1=有链路，0=无）
cat /sys/class/net/$FIRST_IFACE/operstate  # 操作状态（up/down）
cat /sys/class/net/$FIRST_IFACE/speed      # 协商速率（Mbps），如果不可用则返回错误

# 3. 查看温度传感器
ls /sys/class/thermal/
for zone in /sys/class/thermal/thermal_zone*; do
    echo "$(basename $zone): $(cat $zone/type 2>/dev/null) = $(cat $zone/temp 2>/dev/null) 毫摄氏度"
done

# 4. 查看电源信息（笔记本电脑）
if [ -d /sys/class/power_supply/BAT0 ]; then
    echo "电池容量: $(cat /sys/class/power_supply/BAT0/capacity)%"
    echo "电池状态: $(cat /sys/class/power_supply/BAT0/status)"
fi

# ========== /sys/block —— 块设备 ==========

# 5. 查看第一个磁盘的信息
FIRST_DISK=$(ls /sys/block/ | grep -E '^sd[a-z]$|^vd[a-z]$' | head -1)
echo "磁盘: $FIRST_DISK"
cat /sys/block/$FIRST_DISK/size    # 扇区数（扇区 = 512 字节）
echo "大小: $(( $(cat /sys/block/$FIRST_DISK/size) * 512 / 1024 / 1024 / 1024 )) GB"
cat /sys/block/$FIRST_DISK/stat    # I/O 统计
cat /sys/block/$FIRST_DISK/queue/scheduler  # I/O 调度器

# ========== /sys/module —— 已加载模块的参数 ==========

# 6. 查看 e1000e 模块的参数
ls /sys/module/e1000e/parameters/ 2>/dev/null
# 输出：debug, ...

# 7. 查看模块的引用计数
cat /sys/module/e1000e/refcnt 2>/dev/null
# 0 表示无其他模块依赖它——可以安全卸载

# 8. 查看模块的持有者（依赖它的模块列表）
ls /sys/module/e1000e/holders/ 2>/dev/null

# ========== /sys/kernel —— 内核全局信息 ==========

# 9. 查看内核启动参数
cat /sys/kernel/uevent_seqnum

# 10. 查看内核安全信息
ls /sys/kernel/security/

# 11. 查看已加载的内核模块列表（与 lsmod 等效）
ls /sys/module/

# ========== 实用技巧：通过 /sys 动态调整硬件行为 ==========

# 12. 修改 I/O 调度器（需要 root）
sudo sh -c 'echo mq-deadline > /sys/block/sda/queue/scheduler'
cat /sys/block/sda/queue/scheduler
# 方括号标识当前活跃的调度器：[mq-deadline] kyber bfq none

# 13. 控制磁盘 Write Cache
cat /sys/block/sda/queue/write_cache 2>/dev/null
# write back 或 write through
```

### 练习 4：分析 insmod 与 modprobe 的行为差异

**任务：**
1. 选择一个有依赖的模块（依赖数 >= 1）
2. 先用 `rmmod` 或 `modprobe -r` 确保它和它的依赖都被卸载
3. 尝试用 `insmod` 只插入目标模块（不加载依赖）——观察错误
4. 再用 `modprobe` 正确加载——观察自动解析依赖的过程
5. 总结 `insmod` 和 `modprobe` 的核心区别

**参考答案：**

```bash

DEP_MODULE=$(lsmod | awk 'NR>1 && $4 != "" {print $1; exit}')
echo "有依赖的模块: $DEP_MODULE"

# 记录其依赖
DEP_LIST=$(modinfo -F depends $DEP_MODULE 2>/dev/null)
echo "其依赖: ${DEP_LIST:-无}"

# 2. 卸载模块（递归卸载依赖）
sudo modprobe -r $DEP_MODULE 2>/dev/null
echo "已卸载 $DEP_MODULE 及其不再被使用的依赖"

# 3. 找到 .ko 文件路径
KO_PATH=$(modinfo -F filename $DEP_MODULE 2>/dev/null)
echo "模块文件: $KO_PATH"

# 尝试用 insmod 只加载目标模块
echo "=== 尝试 insmod（预期失败——缺少依赖） ==="
sudo insmod $KO_PATH 2>&1
# 错误示例：
# insmod: ERROR: could not insert module e1000e.ko: Unknown symbol in module
# 含义：模块引用的符号（函数/变量）在内核中找不到——因为依赖模块未加载

# 4. 用 modprobe 正确加载
echo "=== 使用 modprobe（预期成功——自动加载依赖） ==="
sudo modprobe -v $DEP_MODULE
# 输出显示按依赖顺序依次执行 insmod

# 5. 总结差异：
# insmod:  只加载指定的 .ko 文件——不管依赖、不管配置、不管别名
# modprobe: 完整的模块管理——解析依赖（modules.dep）、解析别名（modules.alias）、
#           读取配置（/etc/modprobe.d/）、处理软依赖（modules.softdep）

# 清理：卸载练习用模块
sudo modprobe -r $DEP_MODULE 2>/dev/null
```

```bash
echo ""  # 换行
# 解析出关键参数
echo "root 分区: $(cat /proc/cmdline | tr ' ' '\n' | grep '^root=' | cut -d= -f2)"
echo "quiet 模式: $(grep -q 'quiet' /proc/cmdline && echo '是' || echo '否')"

# 6. 进程数统计
echo "=== 进程统计 ==="
PROC_COUNT=$(ls -d /proc/[0-9]* 2>/dev/null | wc -l)
echo "当前进程数: $PROC_COUNT"
echo "（包括线程：$(ls -d /proc/[0-9]*/task/[0-9]* 2>/dev/null | wc -l)）"

# 7. 对比 /proc/modules 和 lsmod
echo "=== 模块列表一致性检查 ==="
LSMOD_COUNT=$(lsmod | tail -n +2 | wc -l)
PROC_MOD_COUNT=$(cat /proc/modules | wc -l)
echo "lsmod 模块数: $LSMOD_COUNT"
echo "/proc/modules 模块数: $PROC_MOD_COUNT"
if [ "$LSMOD_COUNT" -eq "$PROC_MOD_COUNT" ]; then
    echo "一致——lsmod 来源即 /proc/modules"
else
    echo "不一致——可能某些模块正在被加载或卸载中"
fi
```

## 5. 常见错误与排错

### 错误 1：modprobe: FATAL: Module not found

**现象：**

```
modprobe: FATAL: Module module_name not found in directory /lib/modules/6.8.0-31-generic
```

**原因和排查步骤：**

```bash
# === 系统化排查"模块未找到" ===

# 步骤 1：确认模块名拼写正确
# 模块名是区分大小写的！
modprobe e1000E   # ✗ 错误——大写 E
modprobe e1000e   # ✓ 正确

# 步骤 2：用 modinfo 确认模块是否存在
modinfo nonexistent_module
# 如果输出 "modinfo: ERROR: Module nonexistent_module not found."
# 说明该模块确实不存在——可能是：
#   a) 模块名拼写错误
#   b) 该功能编译进内核而非模块（检查 modules.builtin）
#   c) 该模块不在当前内核版本的模块目录中

# 步骤 3：搜索可能的模块名
find /lib/modules/$(uname -r)/kernel -name '*key_word*' 2>/dev/null

# 步骤 4：检查该功能是否编译进内核
grep module_name /lib/modules/$(uname -r)/modules.builtin
# 如果有输出 → 该功能已内置，不需要（也不能）用 modprobe 加载

# 步骤 5：检查内核版本是否与模块匹配
uname -r
modinfo -F vermagic /path/to/module.ko
# vermagic 必须与 uname -r 一致
# 不一致的典型原因：安装了新内核但未重启

# 步骤 6：如果模块是手动编译的
# 运行 depmod 更新数据库
sudo depmod -a

# 步骤 7：检查 Secure Boot 是否阻止了模块加载
sudo mokutil --sb-state
# 如果输出 "SecureBoot enabled"，未签名的自编译模块无法加载
# 解决方案：签注模块或临时禁用 Secure Boot（不推荐）
```

### 错误 2：insmod: Unknown symbol in module

**现象：**

```
insmod: ERROR: could not insert module mydriver.ko: Unknown symbol in module
```

**含义：** 模块引用了某个函数或变量（符号），但在当前运行内核中找不到该符号——通常是因为依赖模块未加载。

**原因和排查步骤：**

```bash
# === 排查 Unknown symbol ===

# 步骤 1：用 dmesg 查看具体缺失的符号
sudo dmesg | tail -20
# 会显示类似：
# mydriver: Unknown symbol some_function (err -2)
# 告诉你具体缺少什么符号

# 步骤 2：找出哪个模块提供该符号
sudo grep some_function /lib/modules/$(uname -r)/modules.symbols
# 输出示例：
# alias symbol:some_function dependency_module
# 告诉你要加载 dependency_module 才能提供该符号

# 步骤 3：正确的方式——使用 modprobe 而非 insmod
# ❌ 错误方式：
sudo insmod /path/to/mydriver.ko
# insmod: ERROR: could not insert module ...

# ✓ 正确方式：
sudo modprobe mydriver
# modprobe 自动解析依赖——先加载 dependency_module，再加载 mydriver

# 步骤 4：如果模块是手动编译的——检查 vermagic
modinfo /path/to/mydriver.ko | grep vermagic
uname -r
# 两者不一致 → 模块是为不同内核版本编译的 → 重新编译
# 这是自编译模块最常见的错误来源
```

### 错误 3：rmmod: Module is in use

**现象：**

```
rmmod: ERROR: Module module_name is in use
```

**原因和排查步骤：**

```bash
# === 排查"模块正在使用" ===

# 步骤 1：查看谁在使用该模块
lsmod | grep module_name
# Used by 列显示依赖者

# 步骤 2：查看模块的 holders（sysfs 视角）
ls /sys/module/module_name/holders/
# 列出所有持有该模块引用的模块

# 步骤 3：查看哪些进程在使用该模块提供的设备
# 对于设备驱动——查找 /dev 下对应的设备节点
ls -la /dev/ | grep -i device_name

# 步骤 4：找出打开该设备文件的进程
# 假设设备节点为 /dev/mydevice
sudo lsof /dev/mydevice
# 或
sudo fuser -v /dev/mydevice

# 步骤 5：安全卸载的方法
# a) 停止相关服务/进程再卸载
# b) 使用 modprobe -r 自动处理依赖
sudo modprobe -r module_name

# c) 等待模块被释放（rmmod -w）
sudo rmmod -w module_name
# 命令会阻塞，直到使用计数降为 0

# ⚠ 不推荐：强制卸载
# sudo rmmod -f module_name
# 强制卸载使用中的模块可能导致内核不稳定——仅用于紧急调试
```

### 错误 4：sysctl: permission denied

**现象：**

```
sysctl: permission denied on key 'net.ipv4.ip_forward'
```

**原因：** 修改 `/proc/sys/` 下的参数需要 root 权限。

```bash
# === 正确的权限操作 ===

# ❌ 错误——没有 sudo
sysctl -w net.ipv4.ip_forward=1
# sysctl: permission denied on key 'net.ipv4.ip_forward'

# ✓ 正确——使用 sudo
sudo sysctl -w net.ipv4.ip_forward=1

# ❌ 错误——管道 + echo 而不是 sh -c
echo 1 > /proc/sys/net/ipv4/ip_forward
# -bash: /proc/sys/net/ipv4/ip_forward: Permission denied
# 因为重定向 > 是由当前 shell 执行的，而非 root

# ✓ 方法 1——使用 sudo sh -c
sudo sh -c 'echo 1 > /proc/sys/net/ipv4/ip_forward'

# ✓ 方法 2——使用 tee
echo 1 | sudo tee /proc/sys/net/ipv4/ip_forward

# ✓ 方法 3——使用 sysctl（最佳实践）
sudo sysctl -w net.ipv4.ip_forward=1
```

### 错误 5：sysctl: setting key "..." Invalid argument

**现象：**

```
sysctl: setting key "net.ipv4.ip_forward": Invalid argument
```

**原因：** 设置的值超出了参数允许的范围（如类型错误、值太大/太小、格式不正确）。

```bash
# === 常见值类型错误 ===

# ❌ 设置非整数值给整型参数
sudo sysctl -w vm.swappiness=abc
# sysctl: setting key "vm.swappiness": Invalid argument
# vm.swappiness 期望 0-200 之间的整数

# ❌ 布尔参数使用了非 0/1 的值
sudo sysctl -w net.ipv4.ip_forward=true
# 错误。应使用：
sudo sysctl -w net.ipv4.ip_forward=1

# ❌ 值超出允许范围
sudo sysctl -w vm.swappiness=999
# sysctl: setting key "vm.swappiness": Invalid argument
# swappiness 范围是 0-200

# ✓ 正确：先检查参数说明
# 使用 sysctl -a 查看当前值作为参考
sysctl -a | grep vm.swappiness
# 从当前值推断合理范围
```

### 6.2 编写一个简单的内核模块

亲自编写并编译一个内核模块，是理解 LKM 机制最直接的方式。以下是一个最小化 "Hello World" 模块的完整代码：

```c
// hello_kernel.c —— 最小化的 Linux 内核模块
// 保存为 ~/kernel-lesson37/hello_kernel/hello_kernel.c

#include <linux/module.h>    // 所有内核模块都需要
#include <linux/kernel.h>    // KERN_INFO 日志级别宏
#include <linux/init.h>      // __init 和 __exit 宏

// 模块加载时调用的函数
static int __init hello_init(void)
{
    printk(KERN_INFO "Hello, kernel! Module loaded.\n");
    return 0;  // 返回 0 表示成功
}

// 模块卸载时调用的函数
static void __exit hello_exit(void)
{
    printk(KERN_INFO "Goodbye, kernel! Module unloaded.\n");
}

// 注册加载和卸载函数
module_init(hello_init);
module_exit(hello_exit);

// 模块元数据
MODULE_LICENSE("GPL");
MODULE_AUTHOR("Ubuntu Learner");
MODULE_DESCRIPTION("A minimal Hello World kernel module");
MODULE_VERSION("0.1");
```

配套的 Makefile：

```makefile
# Makefile —— 保存为 ~/kernel-lesson37/hello_kernel/Makefile
# 注意：Makefile 中的缩进必须是 Tab，不能是空格！

obj-m += hello_kernel.o

# 使用当前运行内核的头文件编译
KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean
```

编译和测试：

```bash
# 安装编译工具
sudo apt update && sudo apt install -y build-essential linux-headers-$(uname -r)

# 编译模块
cd ~/kernel-lesson37/hello_kernel
make

# 应该生成 hello_kernel.ko 文件
ls -la hello_kernel.ko
modinfo hello_kernel.ko

# 加载模块
sudo insmod hello_kernel.ko

# 查看内核日志（模块的 printk 输出）
sudo dmesg | tail -5
# 应该看到：Hello, kernel! Module loaded.

# 确认模块已加载
lsmod | grep hello_kernel

# 检查 sysfs
ls /sys/module/hello_kernel/

# 卸载模块
sudo rmmod hello_kernel

# 再次查看日志
sudo dmesg | tail -5
# 应该看到：Goodbye, kernel! Module unloaded.

# 清理
make clean
```

**关键认知：** 内核模块与用户空间程序有着根本性的不同：

| 特性 | 用户空间程序 | 内核模块 |
|------|-------------|---------|
| 运行空间 | 用户空间（Ring 3） | 内核空间（Ring 0） |
| 错误后果 | 程序崩溃（不影响系统） | 内核崩溃（Kernel Panic）——整个系统宕机 |
| 内存访问 | 隔离的虚拟地址空间 | 共享内核地址空间——越界写直接破坏内核 |
| 库支持 | 可使用 glibc 等所有库 | 只能使用内核导出函数 |
| 入口/出口 | `main()` / `return` | `module_init()` / `module_exit()` |
| 调试 | gdb、printf | `printk()`、`dmesg`、kgdb |
| 编译 | gcc（普通编译） | 需要内核构建系统（kbuild） |

### 6.3 内核实时补丁（Kernel Livepatch）

Ubuntu 24.04 LTS 支持 **Kernel Livepatch（内核实时补丁）**——在不重启系统的情况下修复内核安全漏洞。这对生产环境中要求高可用性的服务器（如数据库服务器、Web 集群）至关重要。

```
┌─────────────────────────────────────────────────────────────────────┐
│                    内核更新方式对比                                     │
│                                                                      │
│  传统方式（安全更新）：                                                │
│  sudo apt upgrade → 安装新内核包 → 提示重启 → 业务中断                 │
│  （虽然可以 kexec 加速重启，但仍需中断服务）                            │
```

### 6.4 内核参数与性能调优的深度方向

**（1）网络协议栈深度调优**

```bash
# TCP 缓冲区大小（影响网络吞吐量）
sysctl net.ipv4.tcp_rmem      # 读缓冲：[min, default, max]
sysctl net.ipv4.tcp_wmem      # 写缓冲：[min, default, max]
sysctl net.core.rmem_max      # 最大接收缓冲
sysctl net.core.wmem_max      # 最大发送缓冲

# TCP 拥塞控制算法
sysctl net.ipv4.tcp_congestion_control
# Ubuntu 24.04 默认：cubic
# 高带宽高延迟（长肥管道）可选：bbr
# sudo modprobe tcp_bbr
# sudo sysctl -w net.ipv4.tcp_congestion_control=bbr
```

**（2）文件系统性能**

```bash
# 脏页（Dirty Page）管理——控制磁盘写入行为
sysctl vm.dirty_ratio            # 脏页比例上限
sysctl vm.dirty_background_ratio # 后台写回启动阈值
sysctl vm.dirty_expire_centisecs # 脏页过期时间（百分之一秒）
sysctl vm.dirty_writeback_centisecs # 写回间隔

# VFS 缓存压力——控制 inode/dentry 缓存回收倾向
sysctl vm.vfs_cache_pressure
# 默认 100。降低值（如 50）使缓存更持久——适合文件服务器
```

**（3）OOM Killer 行为**

```bash
# OOM（Out of Memory）Killer 是内核在内存耗尽时的最后手段
# 它选择并杀死一个进程来释放内存

# 启用/禁用 OOM Killer
sysctl vm.oom_kill_allocating_task
# 0（默认）：选择最"划算"的进程杀死
# 1：直接杀死触发 OOM 的进程

# 完全禁用内存过量分配（不推荐）
sysctl vm.overcommit_memory
# 0（默认）：启发式检查
# 1：总是允许过量分配
# 2：严格限制——总分配不超过 swap + RAM * overcommit_ratio
```

### 6.5 dkms —— 动态内核模块支持

DKMS（Dynamic Kernel Module Support，动态内核模块支持）是一个框架，用于在系统更新内核时自动重新编译那些不在主线内核树中的第三方模块（如 NVIDIA 驱动、VirtualBox 内核模块）。

```
┌─────────────────────────────────────────────────────────────────────┐
│                     DKMS 工作流程                                      │
│                                                                      │
│  正常流程（无 DKMS）：                                                │
│  apt upgrade 安装新内核 → 手动重新编译第三方模块 → 加载模块           │
│  （容易忘记——新内核中功能缺失）                                        │
│                                                                      │
│  DKMS 流程（自动）：                                                   │
│  安装新内核 → kernel post-install hook 触发 DKMS                      │
│  → DKMS 对每个注册模块执行：检查 → 编译 → 安装 → depmod               │
│  → 新内核直接可用所有第三方模块                                        │
└─────────────────────────────────────────────────────────────────────┘
```

```bash
# 查看已注册的 DKMS 模块
dkms status
# 输出示例：
# nvidia/550.107.02, 6.8.0-31-generic, x86_64: installed
# virtualbox/7.0.16, 6.8.0-31-generic, x86_64: installed
# 格式：模块名/版本, 内核版本, 架构: 状态

# 查看 DKMS 的模块源码树
ls /var/lib/dkms/
ls /usr/src/
```

### 6.6 内核启动参数调优

内核在启动时通过 Bootloader（GRUB）接收启动参数（Kernel Command Line）。这些参数控制着内核的初始化行为——从根文件系统位置到硬件虚拟化支持、从电源管理到调试日志。

```bash
# 查看当前启动时使用的内核参数
cat /proc/cmdline
# 输出示例：
# BOOT_IMAGE=/boot/vmlinuz-6.8.0-31-generic root=UUID=abc123... ro quiet splash

# 常见内核启动参数含义：
# ro             → 以只读模式挂载根文件系统（启动后 initramfs 会重新挂载为 rw）
# quiet          → 减少启动时的内核日志输出
# splash         → 显示 Plymouth 启动画面
# nomodeset      → 禁用内核模式设置（KMS）——显卡驱动问题时的调试手段
# acpi=off       → 禁用 ACPI——电源管理问题的调试手段
# memtest        → 启动内存测试
# init=/bin/bash → 指定 init 进程（应急模式——直接进入 root shell）

# 临时修改启动参数（GRUB 菜单）
# 1. 启动时在 GRUB 菜单按 'e' 编辑启动项
# 2. 找到 linux 开头的那一行
# 3. 添加/修改参数
# 4. 按 F10（或 Ctrl+X）启动

# 永久修改 GRUB 启动参数
# sudo nano /etc/default/grub
# 修改 GRUB_CMDLINE_LINUX_DEFAULT 行：
# GRUB_CMDLINE_LINUX_DEFAULT="quiet splash"
# 添加参数后：
# GRUB_CMDLINE_LINUX_DEFAULT="quiet splash nomodeset"
# 更新 GRUB 配置：
# sudo update-grub
# 重启生效
```

## 本章总结

完成本章后，你应该掌握以下核心能力：

1. **内核信息获取：** 使用 `uname` 和 `/proc/version` 了解运行内核的版本、架构和编译信息
2. **版本号解读：** 理解 `6.8.0-31-generic` 中每个数字的含义——上游版本、ABI 号、内核风味
3. **模块管理：** 使用 `lsmod` 查看已加载模块，`modinfo` 查看模块元数据，`modprobe` 智能加载/卸载模块
4. **模块加载流程：** 理解完整的加载链路——请求 → 别名解析 → 依赖解析 → insmod → 内核注册
5. **低级操作：** 理解 `insmod`/`rmmod` 与 `modprobe` 的区别——前者直接操作，后者智能管理
6. **参数调优：** 使用 `sysctl` 查看和修改内核运行时参数，理解临时修改和持久化配置的区别
7. **配置持久化：** 通过 `/etc/sysctl.d/` 创建持久化参数配置，理解加载优先级
8. **系统探查：** 在 `/proc` 中读取实时系统信息（CPU、内存、进程、负载），在 `/sys` 中探索设备树和内核对象

**这些能力是 Phase 6 的基石。** 接下来的章节将深入进程、内存和性能调优——每一项都建立在你对内核机制的理解之上。内核不再是黑盒——你已经有能力观察它、管理它、甚至调校它。
