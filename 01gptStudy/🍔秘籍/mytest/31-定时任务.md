## 1. 概述

### 1.1 从"看懂日志"到"运行自动化"

第 30 章你掌握了日志系统——journald 的结构化查询、rsyslog 的日志分发、logrotate 的自动轮替。现在，一个新问题浮现：

- "系统每天凌晨 3 点自动轮替日志——这个'每天凌晨 3 点'是由谁决定的？"
- "想在每天凌晨 2 点自动备份数据库——怎么写这个定时规则？"
- "笔记本合上盖子后，凌晨 3 点的定时任务错过了怎么办？"
- "有一台服务器凌晨 5 点要做好几个维护操作——怎么编排它们的先后顺序？"
- "crontab 的 5 个星号代表什么？`0 3 * * *` 和 `0 */3 * * *` 有什么区别？"
- "我有一个脚本只需要在今天下午 3 点运行一次——cron 能做吗？"
- "systemd 的 timer 和传统的 cron 有什么区别？用哪个更好？"

这些问题的核心只有一个：**定时任务（Scheduled Task）**——Linux 系统的自动化心跳。如果说进程是系统的"肌肉"，日志是系统的"记忆"，那么定时任务就是系统的"生物钟"——它让 Linux 在没有人工干预的情况下，按照预定计划自动执行任务。

**定时任务的核心使命：在正确的时间、以正确的用户身份、在正确的环境中，自动执行预定义的命令或脚本，使系统维护和应用运维摆脱"守着时钟按回车"的手工时代。**

### 1.3 历史背景：从 cron 到 systemd timer

Linux 定时任务的演化并非"新酒装旧瓶"，而是一段有趣的进化史：

```
cron 时代（1975 - 至今）：                       systemd timer 时代（2013 - 至今）：
────────────────────────                        ────────────────────────────────
创建者：Ken Thompson（Unix）                     创建者：Lennart Poettering, Kay Sievers
设计年份：1975（Version 6 Unix）                  设计年份：2013（systemd 209 引入 timer）
守护进程：crond / cronie / dcron                 守护进程：systemd（PID 1 自身）
时间精度：1 分钟（最小粒度）                      时间精度：1 秒（OnCalendar=）
配置格式：5 字段时间表达式                        配置格式：声明式 unit 文件
错过处理：不处理（跳过了就跳过了）                 错过处理：Persistent= 选项自动补跑
环境问题：PATH 陷阱（/usr/bin:/bin）              环境问题：继承 systemd 环境
依赖管理：无（想保证顺序只能 sleep）               依赖管理：Before=/After=/Requires= 原生支持
资源限制：无                                     资源限制：CPUQuota=/MemoryMax= 原生支持
日志集成：重定向到文件或 mail                     日志集成：stdout/stderr 自动进入 journal
```

**关键时间线：**

```
1975   Version 6 Unix：Ken Thompson 编写了首个 cron 守护进程
       │
1987   Paul Vixie 重写 cron（Vixie cron），成为 Linux 标准实现
       引入 5 字段时间表达式、crontab 命令、/etc/cron.d/ 等特性
       │
2000   anacron 诞生：解决"笔记本关机错过 cron 任务"的问题
       │
2007   Red Hat 的 Marcela Maslanova 开发 cronie
       （Vixie cron 的现代化 fork，加入 anacron 集成和 PAM 支持）
       │
2013   systemd 209：引入 timer unit，提供秒级精度、错过补跑、
       依赖管理和资源控制
       │
2024   Ubuntu 24.04 LTS：cronie 1.6.1 + systemd 255 并行运行，
       cron 处理传统任务，timer 覆盖系统级任务
```

> **为什么叫"cron"？** 源自希腊语 "chronos"（时间）。Ken Thompson 选择这个名字来强调它与时间的紧密关联——cron 就是一个时间驱动的任务调度器。

## 2. 核心概念

### 2.1 Linux 定时任务体系全景

在 Ubuntu 24.04 中，定时任务由四套机制共同构成。它们并非"四选一"，而是**各司其职、相互补充**：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       Linux 定时任务体系全景                                  │
│                                                                             │
│   ┌─────────────────────── cron（定期任务）────────────────────────────────┐ │
│   │                                                                       │ │
│   │   用户级                              系统级                           │ │
│   │   ┌──────────────────────┐    ┌──────────────────────────────────┐    │ │
│   │   │  crontab -e          │    │  /etc/crontab                    │    │ │
│   │   │  每用户独立文件        │    │  系统级 crontab（支持 user 字段）  │    │ │
│   │   │  存储在               │    │                                  │    │ │
│   │   │  /var/spool/cron/    │    │  /etc/cron.d/                    │    │ │
│   │   │  crontabs/USERNAME   │    │  独立文件，支持 user 字段          │    │ │
│   │   └──────────────────────┘    │                                  │    │ │
│   │                               │  /etc/cron.hourly/               │    │ │
│   │                               │  /etc/cron.daily/                │    │ │
│   │                               │  /etc/cron.weekly/               │    │ │
│   │                               │  /etc/cron.monthly/              │    │ │
│   │                               │  直接放脚本，由 run-parts 执行     │    │ │
│   │                               └──────────────────────────────────┘    │ │
│   │                                                                       │ │
│   │   守护进程：crond（每分钟醒来检查一次是否有任务需要执行）                  │ │
│   │   时间精度：1 分钟                                                      │ │
│   │   错过策略：不补跑（错过了就等下次）                                      │ │
│   └───────────────────────────────────────────────────────────────────────┘ │
│                                                                             │
│   ┌─────────────────────── anacron（错过补偿）─────────────────────────────┐ │
│   │                                                                       │ │
│   │   配置：/etc/anacrontab                                               │ │
│   │   调度：每天由 cron.daily 触发一次                                      │ │
│   │   用途：对 cron.daily/weekly/monthly 中因关机而错过的任务进行补偿        │ │
│   │   时间精度：1 天                                                        │ │
│   │   错过策略：启动时检测 + 补偿执行                                        │ │
│   └───────────────────────────────────────────────────────────────────────┘ │
│                                                                             │
│   ┌─────────────────────── at（一次性任务）─────────────────────────────────┐ │
│   │                                                                       │ │
│   │   守护进程：atd（持续运行，到点执行）                                     │ │
│   │   管理命令：at（创建）、atq（查看）、atrm（删除）                         │ │
│   │   时间精度：1 分钟                                                      │ │
│   │   用途："今天下午 3 点执行一次这个脚本"                                    │ │
│   └───────────────────────────────────────────────────────────────────────┘ │
│                                                                             │
│   ┌─────────────────────── systemd timer（现代替代）────────────────────────┐ │
│   │                                                                       │ │
│   │   配置：.timer unit 文件 + .service unit 文件                           │ │
│   │   管理：systemctl list-timers / start / stop / enable                   │ │
│   │   时间精度：1 秒（OnCalendar=）                                          │ │
│   │   错过策略：Persistent=yes 自动补跑                                      │ │
│   │   额外能力：依赖管理、资源限制、日志集成                                   │ │
│   └───────────────────────────────────────────────────────────────────────┘ │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**选择建议：**

| 场景 | 推荐工具 | 理由 |
|------|---------|------|
| 个人用户的简单定时任务 | `crontab -e` | 最直观，无需 root |
| 系统级周期性维护（日志轮替等） | `/etc/cron.daily/` + anacron | 标准化目录，错过自动补跑 |
| 需要秒级精度 | systemd timer | cron 只支持分钟级 |
| 需要错过补跑 + 依赖管理 | systemd timer | `Persistent=` + `After=` |
| "今天下午 3 点跑一次" | `at` | 一次性任务的最佳选择 |
| 需要资源限制（CPU/内存） | systemd timer | cron 无此能力 |
| 需要任务日志自动进入 journal | systemd timer | stdout/stderr 自动捕获 |

### 2.2 cron 5 字段时间表达式

cron 的核心语法是**5 字段时间表达式**，它定义了"任务在什么时间触发"。这是整个 Unix/Linux 定时任务体系的基石。

#### 2.2.1 5 个字段的含义

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        cron 5 字段时间表达式                                  │
│                                                                             │
│      分钟        小时        日          月         星期                       │
│   ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐              │
│   │  minute │ │  hour   │ │   day   │ │  month  │ │ weekday │              │
│   │  0-59   │ │  0-23   │ │  1-31   │ │  1-12   │ │  0-7    │              │
│   └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘              │
│        │           │           │           │           │                    │
│        │           │           │           │           │                    │
│   ┌────┴───────────┴───────────┴───────────┴───────────┴─────────────┐     │
│   │                                                                  │     │
│   │  示例：30  2  *  *  *                                           │     │
│   │        │   │  │  │  │                                            │     │
│   │        │   │  │  │  └─── 星期：* = 每天（0和7都表示周日）          │     │
│   │        │   │  │  └────── 月份：* = 每月                           │     │
│   │        │   │  └───────── 日期：* = 每天                           │     │
│   │        │   └──────────── 小时：2 = 凌晨 2 点（24小时制）           │     │
│   │        └──────────────── 分钟：30 = 第 30 分                      │     │
│   │                                                                  │     │
│   │   含义：每月的每一天，凌晨 2:30，执行任务。                         │     │
│   └──────────────────────────────────────────────────────────────────┘     │
│                                                                             │
│   字段顺序（记忆口诀）：                                                     │
│   "分 时 日 月 周" —— 从小到大，分钟开始，星期收尾。                         │
│                                                                             │
│   weekday 注意事项：                                                         │
│   · 0 和 7 都表示周日（Sunday）                                              │
│   · 1 = 周一，2 = 周二，...，6 = 周六                                       │
│   · 可用英文前三个字母缩写：mon, tue, wed, thu, fri, sat, sun               │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 2.2.2 有效值列表

| 字段 | 取值范围 | 说明 |
|------|---------|------|
| minute（分钟） | 0-59 | 任务在每小时的第几分钟执行 |
| hour（小时） | 0-23 | 24 小时制，0 = 凌晨 0 点 |
| day of month（日期） | 1-31 | 注意：不是所有月份都有 31 天 |
| month（月份） | 1-12 或 jan-dec | 1 = 一月，英文前三个字母可用 |
| day of week（星期） | 0-7 或 sun-sat | 0 和 7 = 周日；mon, tue... 均可 |

#### 2.2.3 特殊字符与运算符

cron 的 5 字段支持丰富的运算符，这是理解 cron 表达式"高级玩法"的关键：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        cron 时间表达式运算符                                  │
│                                                                             │
│   符号      含义                 示例                  说明                  │
│   ───────  ───────────────────  ────────────────────  ────────────────────  │
│   *        匹配所有值            * * * * *            每分钟执行一次         │
│                                 0 * * * *            每小时的第 0 分执行    │
│                                                                             │

│                                                                             │

│   @hourly   每小时 0 分          @hourly /sbin/check   等价于 0 * * * *    │

│   特别注意：                                                                │
│   · */5 表示"从 0 开始每隔 5"——即 0, 5, 10, 15, ... 55                  │
│   · 1-10/2 表示"从 1 到 10 每隔 2"——即 1, 3, 5, 7, 9                      │
│   · "日"和"星期"同时指定时是"或"关系（不是"且"）：                           │
│     0 0 1,15 * 1 → 每月 1 号和 15 号，或者每周一——三者满足任一就触发        │
│     0 0 * * 1-5  → 周一到周五（因为日字段是 *）                             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

| 表达式 | 含义 | 常见用途 |

| `0 3 * * *` | 每天凌晨 3:00 | 日常备份 |

| `0 3 1 * *` | 每月 1 号凌晨 3:00 | 月度报表 |
| `0 3 1 1 *` | 每年 1 月 1 日凌晨 3:00 | 年度归档 |
| `*/5 * * * *` | 每 5 分钟 | 高频监控 |
| `0 */3 * * *` | 每 3 小时的第 0 分 | 定期快照 |
| `0 9-17 * * 1-5` | 工作日 9:00-17:00 每小时 | 办公时间巡检 |
| `0 0,12 * * *` | 每天 0:00 和 12:00 | 每日两次同步 |

| `@reboot` | 系统启动时 | 启动后初始化 |

### 2.3 cron 运行时的环境变量陷阱

这是 cron 用户最容易踩的坑：**cron 执行任务时的环境变量和你交互式 Shell 的环境变量完全不同**。

```bash
# === 交互式 Shell 的 PATH ===
echo $PATH
# 输出示例：
# /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:...

# === cron 执行时的默认 PATH ===
# cron 默认只设置：
# PATH=/usr/bin:/bin
# 这比交互式 Shell 少了很多路径！
```

**cron 运行时环境的关键差异：**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    交互式 Shell vs cron 运行环境对比                         │
│                                                                             │
│   变量           交互式 Shell 的值          cron 环境的值         影响       │
│   ────────────  ────────────────────────  ────────────────────  ──────────  │
│   PATH          /usr/local/sbin:          /usr/bin:/bin          命令找不到 │
│                 /usr/local/bin:                                   错误      │
│                 /usr/sbin:/usr/bin:                                        │
│                 /sbin:/bin:...                                            │
│                                                                             │
│   HOME          /home/username            /home/username          相同     │
│                                                                             │
│   SHELL         /bin/bash                 /bin/sh                 不同 Shell│
│                                                                             │
│   LOGNAME       username                  username                相同     │
│                                                                             │
│   USER          username                  (未设置)                可能为空  │
│                                                                             │
│   LANG          en_US.UTF-8               (未设置)                locale 问题│
│                                                                             │

│                                                                             │
│   别名          alias ll='ls -la'         无                      别名失效  │

│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**常见的环境变量陷阱场景：**

```bash
# 陷阱 1：命令找不到
# 你的 crontab 中写了：
# 0 3 * * * /usr/local/bin/mybackup.sh
# → 这个没问题，因为用了绝对路径

# 但如果你写的是：
# 0 3 * * * mybackup.sh
# → 失败！因为 cron 的 PATH 中没有 /usr/local/bin/

# 陷阱 2：脚本内部用了相对命令
# 你的脚本 mybackup.sh 中有：
#   rsync -a /data /backup
# → 失败！因为 cron 环境中找不到 rsync（/usr/bin/rsync 在 PATH 中可能没问题，
#    但如果你装了更新版本的 rsync 在 /usr/local/bin/ 里，就会用错版本）

# 陷阱 3：脚本依赖 .bashrc 中的环境变量
# 你的 crontab 中：
# 0 3 * * * $HOME/scripts/db-backup.sh
# → 脚本中使用了 DB_PASSWORD 这种在 ~/.bashrc 中设置的变量
# → cron 不加载 .bashrc！变量为空！

# 陷阱 4：% 符号是特殊字符
# 0 3 * * * echo "Backup at $(date +%Y%m%d)" >> /tmp/backup.log
# → 错误！cron 中 % 是换行符的转义字符
# → 需要转义：\%Y\%m\%d
```

**解决方案（三种策略）：**

```bash
# 策略 1：所有路径用绝对路径（最安全、最推荐）
0 3 * * * /usr/local/bin/mybackup.sh

# 策略 2：在 crontab 文件顶部设置环境变量
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=admin@example.com
HOME=/home/ubuntu

0 3 * * * mybackup.sh

# 策略 3：在脚本内部显式设置 PATH
#!/bin/bash
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
# 后续代码...

# 策略 4（调试用）：让 cron 加载完整的 profile
0 3 * * * . $HOME/.profile; /path/to/script.sh
```

### 2.4 用户级 cron vs 系统级 cron

cron 任务分为两个层次，它们在权限、格式和管理方式上各有不同：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                     用户级 cron vs 系统级 cron                                │
│                                                                             │
│                     用户级 cron                 系统级 cron                  │
│                     ──────────────              ──────────────               │
│   管理命令           crontab -e                 直接编辑文件                 │
│                     crontab -l                  (/etc/crontab,              │
│                     crontab -r                  /etc/cron.d/*)              │
│                                                                             │
│   文件位置           /var/spool/cron/           /etc/crontab                │
│                     crontabs/USERNAME           /etc/cron.d/*.conf          │
│                                                                             │
│   格式              5 字段 + 命令               5 字段 + user + 命令         │
│                     例：                        例：                         │
│                     0 3 * * * backup.sh        0 3 * * * root backup.sh    │
│                                                 ↑ 多了用户名               │
│                                                                             │
│   执行身份          以对应用户身份执行           以指定 user 字段的身份执行   │
│                                                                             │
│   是否需要 root     不需要（自己的 crontab）    需要 root 权限               │
│                                                                             │
│   适用场景          个人开发者的定时任务         系统管理员的全局维护任务     │
│                    如：用户级备份              如：日志轮替、更新检查        │
│                                                                             │
│   用户权限控制       /etc/cron.allow            /etc/cron.allow            │
│                     /etc/cron.deny             /etc/cron.deny              │
│                     （控制哪些用户能使用 cron）  （同上）                    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

```bash
# 查看某个用户是否有 cron 权限
cat /etc/cron.allow 2>/dev/null || echo "cron.allow 不存在"
cat /etc/cron.deny 2>/dev/null || echo "cron.deny 不存在"

# cron 访问控制的优先级：
# 1. 如果 /etc/cron.allow 存在 → 只有文件中的用户可以使用 cron
# 2. 如果只有 /etc/cron.deny 存在 → 除了文件中的用户外，其他人都可以用
# 3. 如果两个文件都不存在 → 只有 root 可以使用 cron（Ubuntu 默认是空的 deny）
```

### 2.5 /etc/cron.* 目录结构详解

Ubuntu 24.04 的 `/etc/` 下有一套设计精巧的 cron 目录体系：

```
/etc/
│
├── crontab                          ← 系统级 crontab（主配置）
│   格式：分 时 日 月 周 user command
│   示例：17 * * * * root cd / && run-parts --report /etc/cron.hourly
│
├── cron.d/                          ← 软件包可独立存放定时规则
│   ├── anacron                       # anacron 的 cron 触发规则
│   ├── e2scrub_all                   # ext4 文件系统定期检查
│   └── popularity-contest            # 软件包流行度统计（如果安装了）
│
├── cron.hourly/                     ← 每小时执行（由 /etc/crontab 调用）
│   └── (放可执行脚本即可)
│
├── cron.daily/                      ← 每天执行（由 /etc/crontab 调用）
│   ├── apache2
│   ├── apport
│   ├── apt-compat
│   ├── dpkg
│   ├── logrotate                    # ← 第 30 章提到的 logrotate 就是在这里触发
│   ├── man-db
│   └── ...
│
├── cron.weekly/                     ← 每周执行
│   ├── man-db
│   └── ...
│
└── cron.monthly/                    ← 每月执行
    └── ...
```

```bash
# 探索 /etc/crontab 的内容
cat /etc/crontab
```

典型的 `/etc/crontab` 内容：

```
SHELL=/bin/sh
PATH=/usr/local/sbin:/usr/local/bin:/sbin:/bin:/usr/sbin:/usr/bin

# 分 时 日 月 周 用户    命令
17 *    * * *   root    cd / && run-parts --report /etc/cron.hourly
25 6    * * *   root    test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.daily; }
47 6    * * 7   root    test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.weekly; }
52 6    1 * *   root    test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.monthly; }
```

**解读这段配置的关键设计：**

```
17 *    * * *   hourly  → 每小时的 17 分执行 cron.hourly/
25 6    * * *   daily   → 每天 6:25 执行 cron.daily/
47 6    * * 7   weekly  → 每周日 6:47 执行 cron.weekly/
52 6    1 * *   monthly → 每月 1 日 6:52 执行 cron.monthly/

注意：这些时间故意错开（17分、25分、47分、52分），避免同一时刻
大量任务同时启动造成系统负载尖峰（thundering herd）。
```

**关键发现：** Ubuntu 24.04 的 `/etc/crontab` 中，daily/weekly/monthly 命令前面都有一个 `test -x /usr/sbin/anacron ||` 条件。这意味着：

- 如果 anacron **可用**（test -x 为真）→ cron 跳过这些目录，交给 anacron 处理
- 如果 anacron **不可用**（test -x 为假）→ cron 自己执行这些目录中的脚本

这是 cron 与 anacron 协作的精妙设计。详见 2.6 节。

### 2.6 anacron：为什么笔记本电脑需要它

cron 有一个致命假设：**计算机会 24/7 持续运行**。当每天凌晨 3 点的 `cron.daily` 任务执行时，cron 假设你的电脑在那一刻是开着的。

现实呢？笔记本电脑白天工作，晚上合盖休眠或关机。凌晨 3 点的备份任务会**被悄悄跳过**。

**anacron（Anachronistic Cron，意为"不合时宜的 cron"）** 就是为解决这个问题而生的：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                     cron 的问题与 anacron 的解决                              │
│                                                                             │
│   场景：一台笔记本电脑                                                       │
│                                                                             │
│   Day 1 (周一)              Day 2 (周二)              Day 3 (周三)           │
│   ────────────             ────────────             ────────────            │
│   08:00 开机                08:00 开机                08:00 开机             │
│   09:00-18:00 工作中         09:00-18:00 工作中         09:00-18:00 工作中    │
│   18:05 休眠/关机            18:05 休眠/关机            18:05 休眠/关机      │
│                                                                             │
│   仅 cron：                 │ 仅 cron：               │ 仅 cron：            │
│   cron.daily @ 6:25         │ cron.daily @ 6:25       │ cron.daily @ 6:25   │
│   → 电脑已关机，跳过！       │ → 电脑已关机，跳过！      │ → 电脑已关机，跳过！  │
│                                                                             │
│                            │                         │                      │
│   有 anacron：              │ 有 anacron：            │ 有 anacron：         │
│   cron.daily 未执行         │ anacron 检测到           │ anacron 检测到       │
│   anacron 记录：            │ day1 的 daily 还没跑     │ 上次 daily 是 3 天前 │
│   logrotate last run:       │ → 开机后补跑！           │ → 开机后补跑！       │
│   2024-07-27               │ → logrotate 执行了       │ → logrotate 执行了   │
│                                                                             │
│   anacron 的核心机制：                                                       │
│   1. 在 /var/spool/anacron/ 下为每个周期各存一个时间戳文件                     │
│   2. 每次运行 anacron 时检查"距离上次执行是否超过了周期"                       │
│   3. 如果超过了 → 立即补跑                                                    │
│   4. 执行完后更新该周期的时间戳                                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**anacron 的配置文件：**

```bash
# 查看 anacron 主配置
cat /etc/anacrontab
```

典型的 `/etc/anacrontab` 内容：

```
# /etc/anacrontab: configuration file for anacron

SHELL=/bin/sh
PATH=/usr/local/sbin:/usr/local/bin:/sbin:/bin:/usr/sbin:/usr/bin
HOME=/root
LOGNAME=root

# 周期(天)  延迟(分钟)  任务标识符      命令
1           5           cron.daily      nice run-parts /etc/cron.daily
7           10          cron.weekly     nice run-parts /etc/cron.weekly
@monthly    15          cron.monthly    nice run-parts /etc/cron.monthly
```

**anacrontab 字段详解：**

| 字段 | 含义 | 示例说明 |
|------|------|---------|
| 周期（period） | 多少天为一个周期 | `1` = 每天一次；`7` = 每周一次；`@monthly` = 每月一次 |
| 延迟（delay） | 补跑前等待多少分钟 | `5` = 启动后等 5 分钟再跑（让系统先稳定下来） |
| 标识符（job-identifier） | 任务的唯一名称 | 用于命名 `/var/spool/anacron/` 下的时间戳文件 |
| 命令（command） | 实际执行的命令 | `nice run-parts /etc/cron.daily` |

**anacron 的触发方式：**

```bash
# anacron 不是守护进程！它本身不常驻内存。
# 它由 cron 每天触发一次（通过 /etc/cron.d/anacron）：
cat /etc/cron.d/anacron
# 输出示例：
# 30 7    * * *   root    [ -e /var/run/systemd/system ] && \
#                          [ ! -d /run/systemd/system ] || \
#                          /usr/sbin/anacron -s
# 含义：每天早上 7:30，如果系统正在运行，就执行 anacron

# 你也可以手动触发 anacron：
sudo anacron -f
# -f: 强制执行所有任务（忽略时间戳）
# -u: 只更新时间戳不执行任务
# -d: 在前台运行（不 fork 到后台）
# -s: 串行执行任务（一个接一个，避免资源争抢）
# -n: 立即执行，忽略延迟字段
```

**anacron vs cron 对比决策表：**

| 特性 | cron | anacron |
|------|------|---------|
| 最小时间精度 | 1 分钟 | 1 天 |
| 执行时机 | 精确到分钟 | 启动后某个时间 |
| 错过补跑 | 不支持 | 核心功能 |
| 适用机器 | 服务器（24/7 运行） | 笔记本/台式机（非 24/7） |
| 配置位置 | crontab | /etc/anacrontab |
| 依赖 crond | 是（crond 守护进程） | 需要 cron 或 systemd 来触发 |

### 2.7 at：一次性定时任务

cron 和 anacron 解决的是**重复性**任务。但如果你的需求是"今天下午 3 点把这份报告生成一下，就这一次"，用 cron 就太笨重了：先 `crontab -e` 加上一条，到时间后还要记得 `crontab -e` 删掉。

**at** 就是为此设计的——专门处理**一次性**定时任务。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        at 的工作模型                                          │
│                                                                             │
│   用户                     atd 守护进程                     任务执行          │
│   ──────                  ────────────                   ──────────         │
│                                                                             │
│   at 15:00                ┌──────────────┐               ┌──────────────┐   │
│   ─────────►               │              │               │              │   │
│           创建任务          │   任务队列    │  15:00 到了  │  执行脚本     │   │
│           存入队列          │              │  ────────►   │  stdout/stderr│  │
│           获得 job ID      │  job 1: 15:00│               │  邮件给用户   │   │
│                           │  job 2: 17:30│               │              │   │
│   atq                     │  job 3: 09:00│               └──────────────┘   │
│   ─────────►               │              │                                 │
│           查看队列          └──────┬───────┘                                 │
│                                   │                                         │
│   atrm 1                   ◄──────┘                                         │
│   ─────────►                                                                 │
│           删除job 1                                                          │
│                                                                             │
│   关键特性：                                                                │
│   · atd 守护进程持续运行，逐个检查任务到期时间                                │
│   · 任务以提交任务时的当前工作目录和环境变量快照来执行                        │
│   · 任务的 stdout/stderr 会通过邮件发送给用户                                │
│   · 时间精度：1 分钟                                                         │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**at 的时间表达式（极其灵活）：**

```bash
# ===== 绝对时间 =====
at 15:00                    # 今天下午 3:00（如果已过，则是明天下午 3:00）
at 15:00 July 31            # 7月31日下午3:00
at 3:00 PM                  # 使用 AM/PM
at 15:00 2024-12-31         # 指定完整日期
at midnight                 # 午夜 0:00
at noon                     # 中午 12:00
at teatime                  # 下午 4:00（传统英式下午茶时间）

# ===== 相对时间 =====
at now + 5 minutes          # 5 分钟后
at now + 1 hour             # 1 小时后
at now + 2 days             # 2 天后
at now + 3 weeks            # 3 周后
at now + 1 month            # 1 月后
at 2:00 PM + 3 days         # 3 天后的下午 2:00

# ===== 特殊时刻 =====
at 10:00 tomorrow           # 明天上午 10:00
at 10:00 next week          # 下周上午 10:00
```

**at 的访问控制：**

```bash
# 与 cron 类似，at 也有 allow/deny 机制：
cat /etc/at.allow 2>/dev/null || echo "at.allow 不存在"
cat /etc/at.deny 2>/dev/null || echo "at.deny 不存在"
# 优先级规则与 cron 完全相同
```

### 2.8 systemd timer：现代 cron 替代方案

在第 29 章中你学过 systemd 的 service unit。现在引入一对新搭档：**timer unit（定时器单元）**。

timer unit 替代了 cron 的"定时触发"部分，而**具体的任务仍然由 service unit 来执行**。这是 systemd 设计的精妙之处——将"什么时候执行"和"执行什么"分离。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                     cron 模型 vs systemd timer 模型                          │
│                                                                             │
│   cron 模型（耦合）：                                                        │
│   ┌──────────────────────────────────────┐                                  │
│   │  0 3 * * * /usr/local/bin/backup.sh  │  ← 时间 + 命令混在一起            │
│   └──────────────────────────────────────┘                                  │
│                                                                             │
│   systemd timer 模型（解耦）：                                                │
│   ┌─────────────────────┐    ┌─────────────────────────┐                    │
│   │  backup.timer       │    │  backup.service          │                    │
│   │                     │    │                         │                    │
│   │  [Timer]            │    │  [Service]              │                    │
│   │  OnCalendar=daily   │───►│  ExecStart=/usr/local/  │                    │
│   │  Persistent=true    │    │    bin/backup.sh        │                    │
│   └─────────────────────┘    └─────────────────────────┘                    │
│        ↑ "什么时候"               ↑ "做什么"                                 │
│                                                                             │
│   优势：                                                                    │
│   1. 同样的 service 可以被手动启动（systemctl start），也可以被 timer 触发    │
│   2. 可以为一个 service 配置多个 timer                                       │
│   3. 一个 timer 的触发失败不会影响 service unit 本身的定义                    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**systemd timer 的核心配置选项：**

```ini
[Timer]
# === 基于日历的触发（类似 cron） ===
OnCalendar=daily                    # 每天 0:00
OnCalendar=hourly                   # 每小时 0 分
OnCalendar=*-*-* 03:00:00           # 每天 3:00:00（秒级精度）
OnCalendar=Mon..Fri *-*-* 09:00:00  # 工作日 9:00
OnCalendar=*-*-1,15 03:00:00        # 每月 1 号和 15 号 3:00
OnCalendar=*:0/5                    # 每 5 分钟

# === 基于间隔的触发（类似单调定时器） ===
OnUnitActiveSec=1h                  # 上次激活后 1 小时
OnBootSec=5min                      # 启动后 5 分钟
OnStartupSec=30s                    # systemd 启动后 30 秒

# === 错过补偿 ===
Persistent=true                     # 如果错过触发时间，下次启动时补跑

# === 随机延迟（避免惊群效应） ===
RandomizedDelaySec=300              # 随机延迟最多 300 秒

# === 时区 ===
# (默认使用系统时区，可通过 timedatectl 设置)

# === 唤醒系统 ===
WakeSystem=false                    # 是否从休眠中唤醒系统来执行任务
```

**systemd timer 相对于 cron 的六大优势：**

1. **秒级精度**：cron 最小粒度是 1 分钟；`OnCalendar=*-*-* 03:00:30` 可以在 3 点 0 分 30 秒执行
2. **错过补跑**：`Persistent=true` 让关机期间错过的任务在下次开机时自动补跑，无需 anacron
3. **依赖管理**：`.timer` 可以指定 `Before=/After=/Requires=` 来编排任务间的顺序
4. **资源限制**：`.service` 中可以设置 `CPUQuota=`, `MemoryMax=` 等——cron 做不到
5. **日志集成**：timer 触发的任务，其 stdout/stderr 自动进入 journal，无需手动重定向
6. **统一管理**：`systemctl list-timers` 查看所有定时器，`systemctl status` 查看执行结果，无需分散到 crontab 和 mail

```bash
# 查看当前系统中所有活动的 timer
systemctl list-timers
# 输出示例：
# NEXT                         LEFT          LAST                         PASSED       UNIT                           ACTIVATES
# Thu 2024-07-31 00:00:00 CST  13h left      Wed 2024-07-30 00:00:00 CST  10h ago      logrotate.timer                logrotate.service
# Thu 2024-07-31 06:15:00 CST  19h left      Wed 2024-07-30 06:15:00 CST  4h 15min ago apt-daily.timer               apt-daily.service
# Thu 2024-07-31 07:15:00 CST  20h left      Wed 2024-07-30 07:15:00 CST  3h 15min ago apt-daily-upgrade.timer       apt-daily-upgrade.service
# ... (更多 timer)

# 这个输出告诉你：下一次何时触发、还剩多久、上次何时触发、由哪个 service 执行
```

## 3. 命令详解

### 3.1 crontab：管理用户级定时任务

`crontab` 命令管理当前用户的 cron 任务。它不是直接编辑 `/var/spool/cron/crontabs/` 下的文件，而是通过 `crontab` 命令来实现安全的读写。

```bash
# ===== 列出当前用户的 cron 任务 =====
crontab -l
# 如果是第一次使用，输出：
# no crontab for ubuntu

# ===== 编辑当前用户的 cron 任务 =====
crontab -e
# 首次运行会让你选择编辑器（nano/vim），选择你熟悉的
# 如果想换编辑器：
# export EDITOR=vim
# 或持久化：echo "export EDITOR=vim" >> ~/.bashrc

# ===== 删除当前用户的所有 cron 任务 =====
crontab -r
# 危险操作！会删除所有任务！
# 用 -i 参数确认：
crontab -ri
# 会提示：crontab: really delete ubuntu's crontab?

# ===== 从文件导入 cron 任务 =====
# 方法：先把任务写在文本文件中，然后导入
cat > ~/schedule-lesson31/mycron.txt << 'EOF'
# 每分钟写一条时间戳到日志文件
* * * * * echo "Cron ran at $(date)" >> /tmp/cron-test.log
EOF

crontab ~/schedule-lesson31/mycron.txt
# 导入后，mycron.txt 中的内容替换了当前用户的 crontab

# 验证
crontab -l
# 输出你刚才写入的内容

# ===== 查看其他用户的 cron 任务（需要 root 权限） =====
sudo crontab -l -u root     # 查看 root 用户的 crontab
sudo crontab -l -u www-data # 查看 www-data 用户的 crontab

# ===== 编辑其他用户的 cron 任务 =====
sudo crontab -e -u root
```

**crontab -l 输出格式：**

```bash
# 每一行是一条任务
# 格式：分 时 日 月 周 命令
# 示例：
0 3 * * * /usr/local/bin/backup.sh
*/5 * * * * /usr/local/bin/healthcheck.sh
```

**crontab 常用参数表：**

| 参数 | 含义 | 示例 |
|------|------|------|
| `-l` | 列出（list）当前用户的 crontab | `crontab -l` |
| `-e` | 编辑（edit）当前用户的 crontab | `crontab -e` |
| `-r` | 删除（remove）当前用户的 crontab | `crontab -r` |
| `-i` | 交互式确认（配合 -r） | `crontab -ri` |
| `-u USER` | 指定用户（需要 root 权限） | `sudo crontab -l -u root` |
| `FILE` | 从文件导入（替换当前 crontab） | `crontab myfile.txt` |

### 3.2 编写 crontab 任务的最佳实践

#### 3.2.1 完整的 crontab 文件结构

一个编写良好的 crontab 文件应该像一份"定时任务文档"，而不是一堆神秘的数字和命令：

```bash
cat > ~/schedule-lesson31/professional-crontab.txt << 'EOF'
# ============================================================
# Crontab for user: ubuntu
# Last updated: 2024-07-30
# Description: 系统日报、数据库备份、健康检查
# ============================================================

# === 环境变量（务必设置） ===
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=admin@example.com
HOME=/home/ubuntu

# === 定时任务 ===

# 每天凌晨 3:00：数据库全量备份
0 3 * * * /usr/local/bin/db-backup.sh >> /var/log/backup.log 2>&1

# 每小时：系统健康检查
0 * * * * /usr/local/bin/healthcheck.sh

# 周一至周五 9:00-17:00，每 30 分钟：办公室巡检
*/30 9-17 * * 1-5 /usr/local/bin/office-check.sh

# 每月 1 日凌晨 4:00：月度报表生成
0 4 1 * * /usr/local/bin/monthly-report.sh

# 每周日凌晨 2:30：系统更新检查（不自动安装）
30 2 * * 0 /usr/local/bin/check-updates.sh

# === 注释掉的旧任务（保留以供参考） ===
# 0 2 * * * /usr/local/bin/old-backup.sh  # 2024-06 废弃，已迁移到 systemd timer
EOF

# 查看文件内容作为参考，但不要让真正导入系统 crontab
cat ~/schedule-lesson31/professional-crontab.txt
```

#### 3.2.2 输出重定向策略

cron 任务的输出处理有三种常见策略：

```bash
# 策略 A：追加到日志文件（最常用）
0 3 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1
# >> ：追加模式（日志不会被覆盖）
# 2>&1：标准错误也输出到同一个文件

# 策略 B：丢弃所有输出（静默模式）
0 * * * * /usr/local/bin/quiet-task.sh > /dev/null 2>&1
# > /dev/null：丢弃标准输出
# 2>&1：标准错误也丢弃

# 策略 C：不重定向——cron 会发邮件
0 3 * * * /usr/local/bin/backup.sh
# 如果有输出，cron 会通过邮件发送给 MAILTO 指定的人
# 前提：系统安装了 MTA（Mail Transfer Agent，如 postfix）
# Ubuntu 24.04 默认没有安装 MTA，所以不重定向时输出会丢失

# 策略 D：同时写日志和发邮件（高级）
0 3 * * * /usr/local/bin/backup.sh 2>&1 | tee -a /var/log/backup.log | \
    mail -s "Backup Report $(date)" admin@example.com
```

#### 3.2.3 在 crontab 中使用 % 符号

```bash
# 问题：cron 中 % 是换行符的转义字符
# 这条会出错：
# 0 3 * * * echo "Today is $(date +%Y%m%d)" >> /tmp/date.log

# 解决方法：用反斜杠转义 %
0 3 * * * echo "Today is $(date +\%Y\%m\%d)" >> /tmp/date.log

# 或者把命令放到脚本中，在 crontab 里调用脚本（推荐）
# crontab: 0 3 * * * /usr/local/bin/log-date.sh
# 脚本内部可以正常使用 %，无需转义
```

### 3.3 /etc/cron.* 系统级配置

#### 3.3.1 /etc/crontab：系统级 crontab

```bash
# 查看系统级 crontab
cat /etc/crontab
```

与用户级 `crontab -e` 的关键区别：

| 特性 | 用户级 crontab | /etc/crontab |
|------|---------------|-------------|
| 编辑方式 | `crontab -e` | 直接编辑文件 |
| 格式 | `分 时 日 月 周 命令` | `分 时 日 月 周 用户 命令` |
| 用户字段 | 不需要（隐含为当前用户） | 必须指定（第 6 个字段） |
| 环境变量 | 可以在文件中设置 | 在文件开头设置 |

#### 3.3.2 /etc/cron.d/：软件包独立定时规则

```bash
# 查看 /etc/cron.d/ 的内容
ls /etc/cron.d/
# 输出示例：
# anacron  e2scrub_all  popularity-contest

# 查看一个例子
cat /etc/cron.d/anacron
```

**`/etc/cron.d/` 的设计意图：** 让第三方软件包在安装时把定时规则放到 `/etc/cron.d/` 下，而不是修改 `/etc/crontab` 主文件。这样每个包的定时任务是独立的、可分别管理的。

```bash
# /etc/cron.d/ 下的文件格式与 /etc/crontab 相同：
# 分 时 日 月 周 用户 命令
# 示例（创建自定义系统定时任务）：
sudo tee /etc/cron.d/lesson31-demo << 'EOF'
# 每天凌晨 2:15，以 root 身份执行
15 2 * * * root echo "System cron.d test at $(date)" >> /tmp/crond-demo.log
EOF

# 过一分钟后验证 cron 加载了该配置
sleep 65 && sudo tail -5 /var/log/syslog | grep CRON
# 应该看到 cron 重新加载了配置

# 验证日志
sudo cat /tmp/crond-demo.log 2>/dev/null || echo "还没到凌晨 2:15，稍后查看"

# 清理
sudo rm /etc/cron.d/lesson31-demo
```

> **注意：** `/etc/cron.d/` 下的文件名不能包含 `.`（点号）以外的特殊字符。cron 会忽略包含 `.` 的文件名，但某些 cron 实现会忽略包含非字母数字字符的文件名。建议只用字母、数字、下划线和连字符，并以 `.conf` 结尾不会有问题。

#### 3.3.3 cron.hourly/daily/weekly/monthly：直接放脚本

```bash
# 这四个目录的机制非常简单：把可执行脚本放进去就行

# 查看 cron.daily 中有哪些脚本
ls -la /etc/cron.daily/
# 输出示例：
# -rwxr-xr-x 1 root root  311 May  2  2024 0anacron
# -rwxr-xr-x 1 root root  102 Mar 22  2024 apache2
# -rwxr-xr-x 1 root root  376 Feb 14  2024 apport
# -rwxr-xr-x 1 root root 1244 Feb 14  2024 apt-compat
# -rwxr-xr-x 1 root root  123 Dec 11  2023 dpkg
# -rwxr-xr-x 1 root root  397 Feb 14  2024 logrotate
# -rwxr-xr-x 1 root root  231 Jan 16  2024 man-db

# 关键点：
# 1. 脚本必须有可执行权限（chmod +x）
# 2. 脚本由 run-parts 按字母顺序逐个执行
# 3. 脚本名不能包含 . 以外的特殊字符（run-parts 会跳过它们）

# === 实验：创建一个 cron.hourly 测试脚本 ===
sudo tee /etc/cron.hourly/lesson31-hourly-test << 'SCRIPT'
#!/bin/bash
echo "[$(date)] cron.hourly test script executed" >> /tmp/hourly-test.log
SCRIPT

sudo chmod +x /etc/cron.hourly/lesson31-hourly-test

# 等待下一个整点过后的第 17 分钟（在 /etc/crontab 中配置）
# 或者手动运行 run-parts 来测试：
sudo run-parts --report /etc/cron.hourly

# 验证
cat /tmp/hourly-test.log
# 输出：
# [Tue Jul 30 11:17:01 CST 2024] cron.hourly test script executed

# 清理测试脚本
sudo rm /etc/cron.hourly/lesson31-hourly-test
sudo rm /tmp/hourly-test.log
```

**run-parts 命令：** 这四个目录的核心执行器。

```bash
# run-parts 按字母顺序运行目录中的所有可执行文件
# 基本用法：
run-parts /etc/cron.daily

# 常用参数：
# --report    显示每个脚本的执行结果
# --test      只列出要执行的脚本，不实际执行
# --regex RE  用正则表达式筛选执行哪些文件

# 示例：
sudo run-parts --test /etc/cron.daily
# 输出（列出但不执行）：
# /etc/cron.daily/0anacron
# /etc/cron.daily/apache2
# /etc/cron.daily/apport
# ...
```

### 3.5 at / atq / atrm：一次性任务完整操作

#### 3.5.1 at：创建一次性任务

```bash
# ===== 方法 1：交互式输入（在 at 提示符下输入命令，按 Ctrl+D 结束） =====
at now + 2 minutes
# 进入 at 交互模式：
# at> echo "Hello from at command!" > /tmp/at-test.txt
# at> date >> /tmp/at-test.txt
# at> <EOT>  ← 按 Ctrl+D 结束输入
# 输出：job 1 at Tue Jul 30 11:05:00 2024

# 等 2 分钟后验证：
sleep 130
cat /tmp/at-test.txt
# 输出：
# Hello from at command!
# Tue Jul 30 11:05:00 CST 2024

# ===== 方法 2：管道输入（脚本化） =====
echo "echo 'Pipeline at test' > /tmp/at-pipe.txt" | at now + 1 minutes

# ===== 方法 3：从文件读取命令 =====
cat > ~/schedule-lesson31/at-commands.txt << 'EOF'
echo "=== At Job Report ===" > /tmp/at-report.txt
echo "Time: $(date)" >> /tmp/at-report.txt
echo "User: $(whoami)" >> /tmp/at-report.txt
echo "Uptime: $(uptime)" >> /tmp/at-report.txt
EOF

at -f ~/schedule-lesson31/at-commands.txt now + 2 minutes
# -f: 从文件读取命令

# ===== 方法 4：指定不同的 Shell =====
at -c /bin/bash now + 5 minutes
# -c: 指定要用哪个 Shell 来执行命令

# ===== at 的常用参数 =====
at -q b now + 2 minutes    # -q: 指定队列（a-z，a=默认，b=批处理）
at -M now + 1 minutes      # -M: 即使没有输出也不发邮件
at -m now + 1 minutes      # -m: 任务完成后一定发邮件（即使没有输出）
```

**at 常用参数表：**

| 参数 | 含义 | 示例 |
|------|------|------|
| `-f FILE` | 从文件读取命令 | `at -f script.sh now + 1 hour` |
| `-m` | 任务完成后发邮件（即使没输出） | `at -m now + 5 minutes` |
| `-M` | 不发邮件（即使有输出） | `at -M now + 5 minutes` |
| `-q QUEUE` | 指定队列（a-z，默认 a） | `at -q b now + 1 hour` |
| `-c JOB` | 查看任务的完整环境（打印到 stdout） | `at -c 3` |
| `-t TIME` | 用 `[[CC]YY]MMDDhhmm[.ss]` 格式指定时间 | `at -t 202407311500` |
| `-v` | 显示任务执行时间 | `at -v now + 1 hour` |

#### 3.5.2 atq：查看任务队列

```bash

# 任务ID  执行时间                     队列  提交用户

# 查看特定队列的任务
atq -q b
# 无输出表示队列 b 中无任务
```

#### 3.5.3 atrm：删除任务

```bash
# 假设 atq 显示：
# 8   Tue Jul 30 12:00:00 2024 a ubuntu

# 删除指定 ID 的任务
atrm 8
# 或等效的：at -d 8

# 验证已删除
atq
# 任务 8 不再出现

# 批量删除一定时间范围内的所有任务（atrm 没有这个功能，需用脚本）：

```

```bash
# Ctrl+D
# 假设 job ID 是 9
```

### 3.6 systemd timer：创建现代定时任务

#### 3.6.1 创建你的第一个 timer

timer 需要两个文件：`.service`（做什么）和 `.timer`（什么时候做）。

```bash
# 第 1 步：创建 service unit（定义任务内容）
sudo tee /etc/systemd/system/lesson31-hello.service << 'EOF'
[Unit]
Description=Lesson 31 - Hello Timer Demo
Documentation=man:systemd.timer(5)

[Service]
Type=oneshot
ExecStart=/bin/bash -c 'echo "[$(date)] Timer fired! Hello from systemd timer." >> /tmp/timer-hello.log'
User=nobody
EOF

# Type=oneshot：一次性执行完就退出（适合定时任务）
# Type=simple：持续运行（适合服务）

# 第 2 步：创建 timer unit（定义触发时间）
sudo tee /etc/systemd/system/lesson31-hello.timer << 'EOF'
[Unit]
Description=Lesson 31 - Timer that fires every 1 minute
Documentation=man:systemd.timer(5)

[Timer]
# 每分钟触发一次
OnCalendar=*:0/1
# 如果错过了（如关机期间），下次启动时补跑
Persistent=true
# 随机延迟最多 10 秒（避免多任务同时启动）
RandomizedDelaySec=10

[Install]
WantedBy=timers.target
EOF

# 第 3 步：重新加载 systemd 配置
sudo systemctl daemon-reload

# 第 4 步：启用并启动 timer
sudo systemctl enable --now lesson31-hello.timer
# enable：开机自动启动
# --now：立即启动

# 第 5 步：查看 timer 状态
systemctl status lesson31-hello.timer
# 输出示例：
# ● lesson31-hello.timer - Lesson 31 - Timer that fires every 1 minute
#    Loaded: loaded (/etc/systemd/system/lesson31-hello.timer; enabled)
#    Active: active (waiting) since Tue 2024-07-30 11:00:00 CST
#    Trigger: Tue 2024-07-30 11:01:00 CST

# 第 6 步：查看所有 timer
systemctl list-timers | grep lesson31
# 输出：
# NEXT                         LEFT     LAST PASSED  UNIT                ACTIVATES
# Tue 2024-07-30 11:01:00 CST  30s left n/a  n/a     lesson31-hello.timer lesson31-hello.service

# 第 7 步：等待触发，验证结果
sleep 70
cat /tmp/timer-hello.log
# 输出：
# [Tue Jul 30 11:01:03 CST 2024] Timer fired! Hello from systemd timer.

# 第 8 步：查看 service 的执行记录
systemctl status lesson31-hello.service
# 注意：oneshot 服务执行完就退出了，状态会显示 "inactive (dead)"

# 第 9 步：清理
sudo systemctl stop lesson31-hello.timer
sudo systemctl disable lesson31-hello.timer
sudo rm /etc/systemd/system/lesson31-hello.service
sudo rm /etc/systemd/system/lesson31-hello.timer
sudo systemctl daemon-reload
rm /tmp/timer-hello.log
```

#### 3.6.2 OnCalendar= 表达式详解

`OnCalendar=` 是 systemd timer 中最强大的时间表达方式，比 cron 的 5 字段更灵活：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                     OnCalendar= 表达式语法                                    │
│                                                                             │
│   格式：星期 年-月-日 时:分:秒                                               │
│                                                                             │
│   星期可选：                                                                 │
│   Mon,Tue,Wed,Thu,Fri,Sat,Sun 2024-07-30 15:00:00                          │
│   ↑ 可选前缀                       ↑ 日期部分               ↑ 时间部分       │
│                                                                             │
│   同时支持：                                                                 │
│   · 简写宏：hourly, daily, weekly, monthly, yearly, quarterly, semiannually  │
│   · 秒级精度：OnCalendar=*-*-* 03:00:30                                    │
│   · 省略规则：                                                               │
│     OnCalendar=*-*-* 03:00     → 每天 3:00（省略秒 = 00）                   │
│     OnCalendar=*-*-* 03:00:00 → 每天 3:00:00（完整写法）                    │
│     OnCalendar=03:00          → 每天 3:00（省略日期部分 = *-*-*)            │
│     OnCalendar=Mon *-*-* 09:00→ 每周一 9:00                                 │
│     OnCalendar=*-*-1 03:00    → 每月 1 日 3:00（省略年份 = 每年）           │
│                                                                             │
│   范围与列表：                                                               │
│     OnCalendar=Mon..Fri *-*-* 09:00        → 工作日 9:00                   │
│     OnCalendar=Mon,Wed,Fri *-*-* 15:30     → 周一/三/五 15:30               │
│     OnCalendar=*-*-1,15 03:00:00           → 每月 1 号和 15 号 3:00         │
│                                                                             │
│   重复间隔：                                                                 │
│     OnCalendar=*:0/5                       → 每 5 分钟                     │
│     OnCalendar=*:0/15                      → 每 15 分钟                    │
│     OnCalendar=hourly                      → 每小时                        │
│     OnCalendar=*-*-* *:0/30                → 每 30 分钟                    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**OnCalendar= 与 cron 表达式对照：**

| cron 表达式 | OnCalendar= 表达式 | 含义 |
|-------------|-------------------|------|
| `0 3 * * *` | `*-*-* 03:00:00` 或 `daily`（0:00 而非 3:00） | 每天凌晨 3:00 |
| `0 3 1 * *` | `*-*-1 03:00:00` | 每月 1 日凌晨 3:00 |
| `*/5 * * * *` | `*:0/5` | 每 5 分钟 |
| `0 9-17 * * 1-5` | `Mon..Fri *-*-* 09,10,11,12,13,14,15,16,17:00` | 工作日 9-17 点 |
| `30 2 * * 0` | `Sun *-*-* 02:30:00` | 每周日凌晨 2:30 |

```bash
OnCalendar=*-*-* 03:00:00
Persistent=true

[Install]
WantedBy=timers.target
```

```bash
sudo tee /etc/systemd/system/orch-task-c.timer << 'EOF'
[Unit]
Description=Orchestration Timer C - 04:00

[Timer]
OnCalendar=*-*-* 04:00:00
Persistent=true

[Install]
WantedBy=timers.target

# 第 4 步：加载并启用

sudo systemctl enable orch-task-a.timer orch-task-b.timer orch-task-c.timer
```

## 5. 常见错误与排错

### 5.1 错误：cron 任务不执行（最常见的 5 个原因）

```bash
# 症状：
# crontab -l 显示任务已添加，但到时间了没有任何反应

# ===== 排查清单（按频率排序） =====

# 原因 1：PATH 问题——命令使用了相对路径或不在 cron 的 PATH 中
# 检查方法：在 crontab 开头显式设置 PATH
# crontab -e 添加：
# PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
# 或者在任务中使用绝对路径

# 原因 2：cron 守护进程没有运行
systemctl status cron
# 如果显示 inactive：
sudo systemctl start cron
sudo systemctl enable cron

# 原因 3：用户没有 cron 权限
cat /etc/cron.allow 2>/dev/null && echo "cron.allow exists — only listed users can use cron"
cat /etc/cron.deny
# 检查当前用户是否在 deny 列表中
grep "^$(whoami)$" /etc/cron.deny && echo "YOU ARE DENIED!"
# 解决方法：从 /etc/cron.deny 中移除你的用户名

# 原因 4：crontab 语法错误
# cron 对语法很挑剔——多了空格、少了换行都可能导致任务被忽略
# 检查方法：
crontab -l | cat -A
# $ 表示行尾，^I 表示 Tab
# 确保每行以换行符结尾（最后一行必须有换行符！）

# 原因 5：% 符号未转义
# 0 * * * * echo $(date +%Y%m%d)  →  错误！
# 0 * * * * echo $(date +\%Y\%m\%d)  →  正确

# ===== 通用调试技巧 =====
# 创建一个"每分钟"测试任务来验证 cron 本身是否正常
crontab -l > /tmp/cron-backup.txt
echo "* * * * * echo 'Cron is alive at \$(date)' >> /tmp/cron-alive-test.log" | crontab -
# 等 1 分钟后：
sleep 65 && cat /tmp/cron-alive-test.log
# 如果有输出 → cron 本身正常，问题在你的特定任务上
# 如果无输出 → cron 服务有问题，检查 systemctl status cron

# 恢复原来的 crontab
crontab /tmp/cron-backup.txt
rm /tmp/cron-alive-test.log /tmp/cron-backup.txt
```

### 5.2 错误：cron 任务的脚本行为与手动执行不同

```bash
# 症状：
# 手动运行脚本 /usr/local/bin/backup.sh 一切正常
# 但在 crontab 中定时执行时失败或行为异常

# ===== 根本原因：环境差异 =====

# 排查步骤：
# 第 1 步：让 cron 告诉你具体出了什么错
# 在 crontab 中把 stdout 和 stderr 都重定向到文件：
# 0 3 * * * /usr/local/bin/backup.sh >> /tmp/backup.log 2>&1
# 1 分钟后检查 /tmp/backup.log

# 第 2 步：在脚本开头添加环境诊断
cat > ~/schedule-lesson31/test-cron-env.sh << 'SCRIPT'
#!/bin/bash
# 把这行放到你的原脚本最开头（调试用）
env > /tmp/cron-debug-env.txt
echo "PWD: $PWD" >> /tmp/cron-debug-env.txt
echo "PATH: $PATH" >> /tmp/cron-debug-env.txt
SCRIPT

# 第 3 步：检查 Shell 差异
# cron 默认使用 /bin/sh（在 Ubuntu 上是 dash，不是 bash）
# 如果你的脚本用了 bash 特有的语法（如 [[ ]]，数组，source 别名等），会失败
# 解决方法：
# A. 在 crontab 顶部设置：SHELL=/bin/bash
# B. 或在脚本中使用 #!/bin/bash 作为 shebang
# C. 或在 crontab 中用显式的 shebang 调用：
#    0 3 * * * /bin/bash /usr/local/bin/backup.sh

# 第 4 步：用 at 模拟 cron 环境
# at 和 cron 的执行环境几乎相同
echo "/usr/local/bin/backup.sh" | at now + 1 minutes
# 可以快速验证脚本在 "非交互式" 环境中是否正常
```

### 5.3 错误：/etc/cron.d/ 或 cron.hourly 中的脚本不执行

```bash
# 症状：
# 在 /etc/cron.hourly/ 下放了脚本，但到时间了没有执行

# ===== 排查清单 =====

# 原因 1：脚本没有可执行权限
ls -la /etc/cron.hourly/
# 检查权限列：应为 -rwxr-xr-x（至少要有 x）
# 解决方法：
sudo chmod +x /etc/cron.hourly/your-script

# 原因 2：脚本名包含非法字符
# run-parts 会跳过以下文件名：
# · 包含 . 的文件（如 script.sh）  ← Ubuntu 的 run-parts 默认跳过含 . 的文件
# · 包含 ~ 的备份文件（如 script.sh~）
# · 以 # 开头的文件
# 合法文件名：只含 字母、数字、下划线、连字符
# 测试哪些文件会被执行：
sudo run-parts --test /etc/cron.hourly/
# --test 只列出会执行的脚本，不实际执行

# 原因 3：anacron 接管了这些目录
# 如果系统有 anacron，cron 可能把 daily/weekly/monthly 的执行权交给了 anacron
# 检查 /etc/crontab：
grep anacron /etc/crontab
# 如果看到 test -x /usr/sbin/anacron || ... — 说明 anacron 优先
# cron.hourly 不受 anacron 影响，始终由 cron 执行

# 原因 4：文件扩展名问题
# 在 Ubuntu 24.04 中，/etc/cron.d/ 下的文件名如果包含 .，
# cron 可能会忽略它们（取决于 cron 实现）
# 解决方法：不要给 /etc/cron.d/ 下的文件加扩展名
# 例如：用 /etc/cron.d/myjob 而不是 /etc/cron.d/myjob.conf

# 全面测试：
# 1. 手动运行 run-parts 检查
sudo run-parts --report /etc/cron.hourly/ 2>&1
# 查看能否看到你的脚本和可能的错误

# 2. 检查 cron 的系统日志
sudo grep CRON /var/log/syslog | tail -20
# 或
journalctl -u cron --since "10 min ago"
```

### 5.4 错误：at 任务到了时间没执行

```bash
# 症状：
# atq 显示有任务，但到了指定时间任务没有触发

# ===== 排查步骤 =====

# 第 1 步：确认 atd 服务正在运行

at -c JOB_ID | head -40

# 如果文件不存在 → atd 服务有问题
```

### 6.1 cron 表达式测试工具与在线验证

```bash
# ===== 方法 1：使用 systemd-analyze calendar（推荐） =====
# 验证一个时间表达式，并显示下次触发时间
systemd-analyze calendar "*-*-* 03:00:00"
```

### 6.2 cron 与 systemd timer 的相互迁移

当你决定从 cron 迁移到 systemd timer（或反之），以下是实用的对照指南：

```bash
# ===== cron → systemd timer 迁移模板 =====

# 原始 cron 任务：
# 0 3 * * * /usr/local/bin/backup.sh

# 迁移步骤：
# 1. 创建 service unit
sudo tee /etc/systemd/system/backup.service << 'EOF'
[Unit]
Description=Database Backup
[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
EOF

# 2. 创建 timer unit
sudo tee /etc/systemd/system/backup.timer << 'EOF'
[Unit]
Description=Daily Database Backup Timer
[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true
[Install]
WantedBy=timers.target
EOF

# 3. 启用 timer，停用 cron 任务
sudo systemctl daemon-reload
sudo systemctl enable --now backup.timer
# crontab -e 删除或注释掉对应行
```

**迁移对照表：**

| cron 特性 | systemd timer 等效 |
|-----------|-------------------|
| `MAILTO=admin` | 无需——输出自动进入 journal，可以用 `journalctl -u` 查看 |
| `PATH=...` | 继承 systemd 环境，或在 `.service` 中用 `Environment=` |
| `SHELL=/bin/bash` | `.service` 中用 `/bin/bash -c '...'` |
| `>> /var/log/xxx.log 2>&1` | 无需——stdout/stderr 自动进入 journal |
| `@reboot` | `OnBootSec=` 或手动触发 `WantedBy=multi-user.target` |
| `@daily` / `@hourly` | `OnCalendar=daily` / `OnCalendar=hourly` |
| 关闭错过补偿 | 不加 `Persistent=` 即可（默认 false） |

### 6.3 使用 systemd timer 实现秒级精度任务

cron 的最小粒度是 1 分钟。systemd timer 可以做到秒级：

```bash
# 场景：每 30 秒检查一次 Web 服务是否在线

sudo tee /etc/systemd/system/web-healthcheck.service << 'EOF'
[Unit]
Description=Web Server Health Check (every 30 sec)

[Service]
Type=oneshot
ExecStart=/bin/bash -c 'curl -s -o /dev/null -w "%%{http_code}" http://localhost 2>&1 | \
    xargs -I {} echo "[$(date -Iseconds)] HTTP Status: {}" >> /tmp/web-health.log'
EOF

sudo tee /etc/systemd/system/web-healthcheck.timer << 'EOF'
[Unit]
Description=Web Health Check Timer (30 sec interval)

[Timer]
# 每 30 秒触发一次
OnUnitActiveSec=30s
# 首次启动后 10 秒开始
OnBootSec=10s
# 精确模式（不累积延迟）
AccuracySec=1s

[Install]
WantedBy=timers.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now web-healthcheck.timer

# 观察 1 分钟
sleep 65
cat /tmp/web-health.log
# 能看到约每 30 秒一条记录

# 清理
sudo systemctl stop web-healthcheck.timer
sudo systemctl disable web-healthcheck.timer
sudo rm /etc/systemd/system/web-healthcheck.{service,timer}
sudo systemctl daemon-reload
rm /tmp/web-health.log
```

### 6.4 邮件通知：cron 任务失败的报警

Ubuntu 24.04 默认没有安装 MTA（Mail Transfer Agent），所以 cron 的邮件通知功能默认不可用。如果需要邮件通知，有以下方案：

```bash
# ===== 方案 1：安装并配置 postfix（传统方案） =====
# sudo apt install postfix -y
# 选择 "Local only" 配置
# 然后 cron 任务中不重定向输出，cron 会自动发邮件给 MAILTO 指定的地址
# 缺点：需要额外维护 MTA，且容易被垃圾邮件过滤器拦截

# ===== 方案 2：使用 curl 调用 Webhook（推荐） =====
# 通过 Slack/Discord/钉钉/企业微信的 Webhook 发送报警

cat > ~/schedule-lesson31/send-alert.sh << 'SCRIPT'
#!/bin/bash
# 通过 Webhook 发送 cron 失败告警
WEBHOOK_URL="https://hooks.slack.com/services/YOUR/WEBHOOK/URL"

send_alert() {
    local subject="$1"
    local message="$2"
    curl -s -X POST -H 'Content-type: application/json' \
        --data "{\"text\":\"[CRON ALERT] ${subject}\n\`\`\`${message}\`\`\`\"}" \
        "$WEBHOOK_URL" > /dev/null 2>&1
}

# 使用方式：在 crontab 中：
# 0 3 * * * /usr/local/bin/backup.sh || /home/ubuntu/send-alert.sh "Backup Failed" "Check /var/log/backup.log"
SCRIPT

# ===== 方案 3：systemd timer + OnFailure= =====
# 使用 systemd timer 的 OnFailure= 机制（原生支持，无需外部工具）

sudo tee /etc/systemd/system/backup-with-alert.service << 'EOF'
[Unit]
Description=Database Backup with Alert on Failure
OnFailure=backup-failure-alert@%i.service

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
EOF

sudo tee /etc/systemd/system/backup-failure-alert@.service << 'EOF'
[Unit]
Description=Alert for failed backup of %i

[Service]
Type=oneshot
ExecStart=/bin/bash -c 'echo "[$(date)] BACKUP FAILED for %i" >> /var/log/backup-alerts.log'
# 替换为实际的告警脚本（如 curl webhook）
EOF

# 原理：如果 backup.service 失败（退出码非 0），systemd 自动触发 OnFailure= 指定的单元
```

### 6.5 批量管理系统定时任务

在管理多台服务器时，手动维护 crontab 几乎不可能。以下是实用策略：

```bash
# ===== 策略 1：使用配置管理工具 =====
# Ansible、Puppet、Chef、Salt 等都可以管理 crontab 和 systemd timer
# Ansible 示例（概念，非可执行命令）：
# - name: Ensure daily backup is scheduled
#   ansible.builtin.cron:
#     name: "daily backup"
#     minute: "0"
#     hour: "3"
#     job: "/usr/local/bin/backup.sh"

# ===== 策略 2：托管到 /etc/cron.d/ =====
# 使用 /etc/cron.d/ 代替 crontab -e，方便用版本控制管理：
# 将 /etc/cron.d/ 下的文件加入 git 仓库

# ===== 策略 3：使用 systemd timer + 版本控制 =====
# .timer 和 .service 文件天然适合放入版本控制（Git）
# /etc/systemd/system/ 或 /usr/lib/systemd/system/

# ===== 策略 4：集中式调度 =====
# 对于大规模集群，使用专门的作业调度系统：
# - Jenkins（CI/CD 但常用于定时任务）
# - Airflow（数据处理流水线）
# - Rundeck（运维自动化）
# - Nomad / Kubernetes CronJob（容器原生）

cat > ~/schedule-lesson31/bulk-cron-manager.sh << 'SCRIPT'
#!/bin/bash
# 简易批量 cron 管理脚本
# 用于在多台服务器上统一部署定时任务

# 定义所有定时任务
declare -A CRON_JOBS

CRON_JOBS["daily-backup"]="0 3 * * * root /usr/local/bin/backup.sh"
CRON_JOBS["healthcheck"]="*/5 * * * * root /usr/local/bin/healthcheck.sh"
CRON_JOBS["log-cleanup"]="0 2 * * 0 root /usr/local/bin/cleanup-logs.sh"

# 部署所有任务
echo "=== Deploying CRON Jobs ==="
for name in "${!CRON_JOBS[@]}"; do
    job="${CRON_JOBS[$name]}"
    if [ -f "/etc/cron.d/${name}" ]; then
        echo "SKIP: /etc/cron.d/${name} already exists"
    else
        echo "${job}" | sudo tee "/etc/cron.d/${name}" > /dev/null
        echo "CREATED: /etc/cron.d/${name}"
    fi
done

echo ""
echo "=== Current CRON.d Contents ==="
ls -la /etc/cron.d/
SCRIPT

chmod +x ~/schedule-lesson31/bulk-cron-manager.sh
```

### 6.6 timer unit 的高级选项

```bash
# ===== 查看 systemd.timer 的完整文档 =====
man systemd.timer

# ===== 常用高级选项速查 =====

# FixedRandomDelay=：固定随机延迟（替代 RandomizedDelaySec=）
# RandomizedDelaySec=：随机延迟范围（加减法，而非固定偏移）

# WakeSystem=：是否唤醒休眠的系统来执行任务
# WakeSystem=true  # 需要硬件支持 RTC（Real-Time Clock）唤醒

# RemainAfterElapse=：elapse 后是否保持 active 状态
# RemainAfterElapse=no  # 默认：触发后回到 waiting 状态

# Unit=：指定要激活的 service（默认与 timer 同名）
# 如果名为 myapp.timer，默认激活 myapp.service
# 可以用 Unit=other-service.service 显式指定别的 service

# ===== 单调定时器（Monotonic Timer） =====
# 除了 OnCalendar= 的"日历式"触发，timer 还支持"单调式"触发：
# OnActiveSec=：从 timer 自身被激活起算
# OnBootSec=：从系统启动起算
# OnStartupSec=：从 systemd 启动起算
# OnUnitActiveSec=：从上一次 service 激活起算
# OnUnitInactiveSec=：从上一次 service 停止起算

# 一个 timer 可以同时组合多种触发方式

# ===== 示例：复杂触发组合 =====
sudo tee /etc/systemd/system/complex-timer-demo.timer << 'EOF'
[Unit]
Description=Complex timer demo
[Timer]
# 每天早上 8:00 触发一次
OnCalendar=*-*-* 08:00:00
# 此外，每次系统启动后 5 分钟也触发
OnBootSec=5min
# 如果错过了（关机期间），补跑
Persistent=true
# 随机延迟 0-120 秒
RandomizedDelaySec=120
# 触发精度（秒）
AccuracySec=1s
[Install]
WantedBy=timers.target
EOF

# 查看这个 timer 的下次触发时间
systemd-analyze calendar "*-*-* 08:00:00"
```
