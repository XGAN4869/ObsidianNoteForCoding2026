## 1. 概述

### 1.1 从"搜文字"到"描述模式"

第 11 章你学会了用 `grep` 搜索文本--在日志中找 `ERROR`，在代码中搜 `TODO`，用 `-E` 匹配 `error|warning|fatal`。这些搜索背后，都有一个共同的核心：**正则表达式（Regular Expression，简称 Regex 或 RE）**。

正则表达式不是 Linux 特有的发明，也不属于任何一个命令。它是一种**描述文本模式的语言**--你用一套简洁的符号告诉计算机："我要找的东西，长这个样子。" 然后计算机在文本中寻找符合这个"样子"的所有内容。

```
你脑海中的想法：                     正则表达式：
─────────────────────────────────   ─────────────────
"找一个手机号码"                    →  1[3-9]\d{9}
"找以 # 开头的行"                  →  ^#
"找引号中间的内容"                  →  "[^"]*"
"找重复出现的单词"                  →  \b(\w+)\s+\1\b
```

如果说第 10 章解决的是"文件里有什么"，第 11 章解决的是"如何找到你关心的行"，那么本章解决的是最底层的问题：**如何精确描述你要找的东西**。

### 1.2 为什么这一章如此重要

本章是 Linux 文本处理体系中的**核心枢纽章节**。它不教你任何一个新命令，但它教授的知识是后续三个章节的基础：

```

          │                   │                   │
          ├── 搜索匹配行       ├── 替换文本          ├── 按列分析
          ├── 过滤输出         ├── 删除行            ├── 数值计算
          └── 统计匹配         └── 插入内容          └── 格式化报告
```

**本章的特殊性：**

- 本章**不教命令**，教的是命令背后的"语言"。第 3 节不是"命令详解"而是"语法详解"。
- 正则表达式在 `grep`、`sed`、`awk`、`vim`、`less`、`python`、`javascript` 等几十个工具和语言中都有应用。**学好正则是一次投资，终身受益。**
- 正则表达式有两种学习方式："遇到什么学什么"（碎片化）和"系统掌握语法体系"（本章方式）。前者导致学了就忘，后者形成永久技能。

### 1.3 正则表达式的本质

正则表达式的本质是一个**模式匹配引擎（Pattern Matching Engine）**的输入语言。你在脑海中构建一个"模式"，写成正则表达式，交给引擎，引擎在文本中扫描，找到所有符合该模式的子串。

```
输入文本 ──→  [正则引擎]  ──→ 匹配结果
                │
                ├── 逐字符扫描输入文本
                ├── 在每个位置尝试与模式匹配
                ├── 匹配成功 → 记录匹配位置和内容
                └── 匹配失败 → 继续扫描下一个位置
```

**关键认知：**

- **正则表达式描述的是"模式"而非"值"：** `\d{3}` 不匹配字面量 `\d{3}`，它匹配"任意三个连续数字"。这是一种间接描述。
- **正则匹配是"贪婪（Greedy）"的--默认尽可能多匹配：** `a.*b` 在 `a1b2b` 中匹配的是 `a1b2b`（整段），而非 `a1b`。这是初学者最容易踩入的陷阱。
- **正则表达式有自己的"方言"：** Linux 世界中存在三种方言--BRE（Basic Regular Expression）、ERE（Extended Regular Expression）、PCRE（Perl Compatible Regular Expression）。同一段文本，同样的模式写法，在不同方言中可能产生完全不同的结果。

### 1.4 历史背景

正则表达式诞生于 1951 年，数学家 Stephen Cole Kleene 首次用"正则集合（Regular Sets）"的概念描述了形式语言。1968 年，Ken Thompson（Unix 创始人之一）将这一理论实现于早期的文本编辑器中，成为 `ed` 编辑器中的搜索功能。1974 年，`grep` 命令从 `ed` 中独立出来（名字来自 `ed` 的 `g/re/p` 命令）。

此后几十年，正则表达式经历了三个重要的演进阶段：

| 年代 | 发展 | 代表工具 |
|------|------|---------|
| 1970s | BRE（Basic Regular Expression）--最原始的 Unix 正则 | `grep`（默认）、`sed`（默认）、`ed`、`vi` |
| 1980s | ERE（Extended Regular Expression）--消除转义歧义 | `egrep`（`grep -E`）、`awk` |
| 1990s | PCRE（Perl Compatible Regular Expression）--引入前瞻、后顾、非贪婪 | `grep -P`、Perl、Python、Ruby、JavaScript |

**BRE 是历史遗留的方言，ERE 是当前 Linux 工具链中的主流，PCRE 是功能最丰富但非 POSIX 标准的方言。** 本章将以 ERE 为主线讲解核心语法，同时在每个语法点上标注三种方言的差异。

### 1.5 本章学习目标

完成本章后，你将能够：

- 理解正则表达式的**匹配机制**：逐字符扫描、贪婪默认、回溯（Backtracking）
- 熟练编写**字符类（Character Class）**：自定义 `[abc]`、排除 `[^abc]`、范围 `[a-z]`、预定义 `\d` `\w` `\s`、POSIX 类 `[[:digit:]]`
- 精确控制**量词（Quantifier）**：`*` `+` `?` `{n}` `{n,m}`，理解贪婪与非贪婪（Lazy）的差异
- 使用**锚点（Anchor）**定位匹配位置：`^`（行首）、`$`（行尾）、`\b`（单词边界）
- 运用**分组（Grouping）**与**捕获（Capture）**：`()` 分组、`\1` 反向引用（Backreference）、`(?:)` 非捕获分组
- 理解**交替（Alternation）**和**环视断言（Lookaround）**：`|` 或、`(?=)` 前瞻、`(?<=)` 后顾
- 区分 **BRE、ERE、PCRE** 的语法差异，能根据需要选择正确的方言
- 在 90% 的日常 Linux 场景中，不再需要查阅正则手册

## 2. 核心概念

### 2.1 字面量与元字符：正则世界的两种角色

在正则表达式中，每个字符扮演两种角色之一：

| 角色 | 含义 | 示例 |
|------|------|------|
| **字面量（Literal）** | 匹配它自己。字符 `a` 匹配文本中的 `a` | `hello` 匹配文本中的 `hello` |
| **元字符（Metacharacter）** | 有特殊含义，不匹配它自己。`.` 匹配"任意字符"，而非字面量的点 | `.` 匹配 `a`、`3`、`!`、空格... |

**ERE 中的元字符（14 个）：**

```
.  *  +  ?  |  (  )  [  ]  {  }  ^  $  \
```

这 14 个字符在正则表达式中有特殊含义。如果你想匹配它们的字面量（比如真的想匹配文本中的一个点号），就必须**转义（Escape）**--在前面加上反斜杠 `\`：

```
元字符  转义为字面量
──────  ──────────
.       \.
*       \*
+       \+
?       \?
|       \|
(       \(
)       \)
[       \[
]       \]
{       \{
}       \}
^       \^
$       \$
\       \
```

**BRE 的特殊之处：** 在 BRE 中，`+`、`?`、`|`、`(`、`)`、`{`、`}` 这 7 个字符**默认不是元字符**--它们被视为字面量。要使它们成为元字符，反而需要加 `\` 转义。这是 BRE 最令人困惑的设计：

```
字符    BRE 中的含义            ERE 中的含义
──────  ──────────────────────  ────────────
+       字面量加号               元字符（一个或多个）
\+      元字符（一个或多个）       转义为字面量加号
(       字面量左括号              元字符（分组开始）
\(      元字符（分组开始）         转义为字面量左括号
```

**本章的约定：** 为保持语法讲解的清晰性，本章默认使用 **ERE** 语法（`grep -E` 方言）进行讲解。BRE 和 PCRE 的差异会在 3.9 节的三栏对照表中完整呈现。

### 2.2 正则引擎的工作方式

理解正则引擎的工作方式，能帮助你避免大量直觉性的错误。

#### 2.2.1 两个核心规则

**规则 1：最左匹配（Leftmost Match）**

引擎从左到右扫描文本，在**第一个可能的位置**开始匹配。一旦在某个位置匹配成功，引擎报告该匹配并从该位置之后继续扫描。

```
在文本 "abc123def" 中搜索 \d+：

扫描过程：
位置 0: a → 不是数字，继续
位置 1: b → 不是数字，继续
位置 2: c → 不是数字，继续
位置 3: 1 → 是数字！从位置 3 开始匹配 \d+
        → 123 全部是数字 → 匹配 "123"，记录结果
位置 6: d → 不是数字，继续
位置 7: e → 不是数字，继续
位置 8: f → 不是数字，继续

结果：匹配 "123"（位置 3-5）
```

**规则 2：默认贪婪（Greedy）**

当使用量词（`*`、`+`、`?`、`{n,m}`）时，引擎默认采用**贪婪匹配**--尽可能多地消费字符，只在不满足后续模式时才会"吐"回一些字符（称为**回溯，Backtracking**）。

```
在文本 "a1b2b" 中搜索 a.*b：

贪婪过程：
a   → 匹配字面量 'a'
.*  → 尽可能多地匹配 → 消费 "1b2b"（到了字符串末尾）
b   → 需要匹配 'b'，但已经到末尾了 → 回溯！
.*  → 吐回最后一个字符 'b'（现在 .* 匹配 "1b2"）
b   → 匹配 'b'！
结果：匹配 "a1b2b"

非贪婪过程（PCRE 的 .*?）：
a   → 匹配字面量 'a'
.*? → 尽可能少地匹配 → 初始匹配空串 ""
b   → 需要匹配 'b'，但当前位置是 '1' → 扩展 .*?
.*? → 扩展到 "1"
b   → 需要 'b'，当前位置是 'b' → 匹配！
结果：匹配 "a1b"
```

**如果只用 ERE（不支持非贪婪），要想匹配"最短"结果，需要换个思路：用排除字符类 `[^b]*` 代替 `.*`：**

```
在文本 "a1b2b" 中搜索 a[^b]*b：

a     → 匹配字面量 'a'
[^b]* → 匹配所有非 'b' 的字符 → "1"
b     → 匹配字面量 'b'
结果：匹配 "a1b"（精准匹配到第一个 b）
```

这个"用排除来替代非贪婪"的技巧在 ERE 编程中极为常用。

#### 2.2.2 回溯的代价

回溯让正则引擎变得强大，但也带来了性能风险。一个写得不好的正则表达式可能导致**灾难性回溯（Catastrophic Backtracking）**--匹配时间从毫秒爆炸到数分钟甚至数小时。

```bash
# 一个典型的灾难性回溯案例（不要在实际文本上运行！）
echo "aaaaaaaaaaaaaaaaaaaaaaaaaaaa" | grep -E "(a+)+b"
# 这个看似简单的正则会因为指数级回溯而极慢
# 原因：每个 + 都尝试不同的分割方式，组合爆炸
```

**理解回溯，是写出高效正则表达式的关键。** 在 5.8 节会详细讨论如何避免灾难性回溯。

### 2.3 正则表达式的三种方言

Linux 世界中存在三种正则方言。它们的关系是"层层叠加"：

```
BRE（Basic Regular Expression）
 │
 └── ERE（Extended Regular Expression）= BRE + 更自然的元字符 + 部分增强
      │
      └── PCRE（Perl Compatible Regular Expression）= ERE + 简写字符类 + 非贪婪 + 环视 + 更多高级特性
```

**快速区分三者的标志性语法：**

| 特性 | BRE | ERE | PCRE |
|------|-----|-----|------|
| `+`（一个或多个） | `\+` | `+` | `+` |
| `()`（分组） | `\(...\)` | `(...)` | `(...)` |
| `|`（或） | `\|` | `|` | `|` |
| `\d`（数字） | 不支持 | 不支持 | 支持 |
| `\s`（空白符） | 不支持 | 不支持 | 支持 |
| `.*?`（非贪婪） | 不支持 | 不支持 | 支持 |
| `(?=...)`（前瞻） | 不支持 | 不支持 | 支持 |
| `(?:...)`（非捕获） | 不支持 | 不支持 | 支持 |

**选择建议（你在实践中应该用什么）：**

- 编写 Shell 脚本，追求 POSIX 兼容：**ERE**（`grep -E`、`awk`）
- 日常交互式搜索：**ERE**（`grep -E`）或直接使用 **PCRE**（`grep -P`）
- 需要非贪婪、环视、简写字符类：**PCRE**（`grep -P`）
- 维护老旧的 sed/vi 脚本：**BRE**（不推荐在新代码中使用）

## 3. 语法详解

以下语法讲解以 **ERE**（`grep -E`）为主线。BRE 和 PCRE 的差异在 3.9 节完整呈现。

### 3.1 字面量匹配（Literal Match）

最基本的正则表达式就是字面量字符串本身。字母、数字、空格等非元字符，直接匹配它们自己。

```bash
# 准备测试文本
cat > /tmp/regex_literal.txt << 'EOF'
hello world
Hello World
hello123
123hello
say hello to the world
HellO
EOF

# 字面量匹配：搜索 "hello"（区分大小写）
grep -E "hello" /tmp/regex_literal.txt
# 输出：
# hello world
# hello123
# 123hello
# say hello to the world
# 注意："Hello World" 和 "HellO" 不匹配（h 和 H 不同）

# 字面量匹配：搜索 "123"
grep -E "123" /tmp/regex_literal.txt
# 输出：
# hello123
```

**字面量匹配只能做精确的字符串查找。** 当你的需求是"找包含 `hello` 的行"时，字面量足够。但当需求变成"找以 `hello` 开头的行"或"找包含 3 个数字的行"时，你需要元字符的能力。

### 3.2 字符类（Character Class）

字符类是正则表达式中最重要的抽象：**不指定具体的字符，而是指定"一类字符中的任意一个"**。

#### 3.2.1 点号 `.` -- 匹配任意单个字符

`.`（点号）是字符类的特例--它匹配**任意单个字符**（除了换行符 `\n`）。

```bash
# 准备测试数据
cat > /tmp/regex_dot.txt << 'EOF'
cat
cbt
c t
c.t
c9t
c@t
ct
cart
EOF

# . 匹配任意单个字符
grep -E "c.t" /tmp/regex_dot.txt
# 输出：
# cat       ← . 匹配了 'a'
# cbt       ← . 匹配了 'b'
# c t       ← . 匹配了 ' '（空格）
# c.t       ← . 匹配了 '.'（字面量的点）
# c9t       ← . 匹配了 '9'
# c@t       ← . 匹配了 '@'
# 不匹配 ct（没有中间字符），不匹配 cart（中间有 2 个字符）
```

`.` 的强大在于"不管中间是什么"。但这也带来了危险：它能匹配任何内容，可能导致过度匹配。

**匹配字面量的点号：** 用 `\.` 转义。

```bash
# 匹配字面量的点（如 IP 地址中的点）
grep -E "192\.168" /tmp/regex_dot.txt
# \. 只匹配字面量的点号，不匹配其他字符
```

#### 3.2.2 自定义字符类 `[ ]` -- 指定字符集合

`[abc]` 匹配**方括号内任意一个字符**：`a`、`b` 或 `c`。

```bash
# 准备测试数据
cat > /tmp/regex_charclass.txt << 'EOF'
gray
grey
griy
gruy
gry
Gray
EOF

# [abc]：匹配 a、b 或 c 中的任意一个
grep -E "gr[ae]y" /tmp/regex_charclass.txt
# 输出：
# gray     ← [ae] 匹配了 'a'
# grey     ← [ae] 匹配了 'e'
# 不匹配：griy（'i' 不在 [ae] 中）、gruy、gry、Gray

# 可以放更多字符
grep -E "gr[aeiou]y" /tmp/regex_charclass.txt
# 输出：gray、grey、griy、gruy（元音字母都匹配）
```

#### 3.2.3 排除字符类 `[^ ]` -- 不包含

`[^abc]` 匹配**不是 `a`、`b`、`c` 的任意一个字符**。`^` 在方括号内的**第一个位置**时，表示"排除"（取反）。

```bash
# [^ae]：匹配不是 'a' 或 'e' 的任意字符
grep -E "gr[^ae]y" /tmp/regex_charclass.txt
# 输出：
# griy     ← [^ae] 匹配了 'i'（不是 a 也不是 e）
# gruy     ← [^ae] 匹配了 'u'
# 不匹配：gray（a 被排除）、grey（e 被排除）
# 不匹配：gry（中间没有字符）、Gray（G 不是 r）
```

**注意：`^` 只有在方括号内的第一个位置时才是"排除"操作符：**

```bash
# [a^b]：匹配 'a'、'^' 或 'b'（^ 不在第一个位置，是字面量）
grep -E "gr[a^e]y" /tmp/regex_charclass.txt
# 输出：gray、grey（^ 被当作普通字符，未出现所以没额外匹配）
```

#### 3.2.4 范围表示 `[a-z]` -- 连续的字符区域

`[a-z]` 匹配从 `a` 到 `z` 的任意一个小写字母。范围基于 ASCII / Unicode 编码顺序。

```bash
# [a-z]：任意小写字母
grep -E "[a-z]" /tmp/regex_charclass.txt

# [0-9]：任意数字
grep -E "[0-9]" /tmp/regex_charclass.txt

# [a-zA-Z]：任意字母（大小写都行）
grep -E "[a-zA-Z]" /tmp/regex_charclass.txt

# [a-zA-Z0-9]：任意字母或数字（等价于 PCRE 的 \w 但不含下划线）
grep -E "[a-zA-Z0-9]" /tmp/regex_charclass.txt
```

**可以组合多个范围和单个字符：**

```bash
# [a-zA-Z0-9_.]：字母、数字、下划线、点号
grep -E "[a-zA-Z0-9_.]" /tmp/regex_charclass.txt

# [0-9aeiou]：数字或元音字母
grep -E "[0-9aeiou]" /tmp/regex_charclass.txt
```

**常见陷阱：`[a-z]` 的范围边界需要正确：**

```bash
# 正确
[a-z]    # 小写字母 a 到 z
[0-9]    # 数字 0 到 9

# 错误
[z-a]    # 范围倒置，无意义（不同引擎行为不同，应避免）
[a-Z]    # 跨越大写/小写区域的 ASCII 间隙，包含 [ \ ] ^ _ ` 等意外字符！
```

正确的写法应该是 `[a-zA-Z]` 而非 `[a-Z]`，因为 ASCII 表中 `a`(97) 到 `Z`(90) 的区间与直觉不符。

#### 3.2.5 预定义简写字符类 -- PCRE 专用

PCRE（`grep -P`）提供了一组**简写字符类（Shorthand Character Classes）**，用 `\字母` 表示常见字符集合：

| 简写 | 含义 | 等价于 | 反简写 | 反含义 | 等价于 |
|------|------|--------|--------|--------|--------|
| `\d` | 数字（Digit） | `[0-9]` | `\D` | 非数字 | `[^0-9]` |
| `\w` | 单词字符（Word） | `[a-zA-Z0-9_]` | `\W` | 非单词字符 | `[^a-zA-Z0-9_]` |
| `\s` | 空白符（Space） | `[ \t\n\r\f\v]` | `\S` | 非空白符 | `[^ \t\n\r\f\v]` |

```bash
# 准备测试数据
cat > /tmp/regex_shorthand.txt << 'EOF'
hello world
abc123_def
   indent with tabs and spaces
line4
!@#$% special chars
EOF

# PCRE 简写字符类
grep -P "\d+" /tmp/regex_shorthand.txt
# 输出：abc123_def

grep -P "\w+" /tmp/regex_shorthand.txt
# 输出所有包含单词字符的行

grep -P "\s" /tmp/regex_shorthand.txt
# 输出包含空白符的行（空格、制表符等）
```

**ERE/BRE 的等效替代方案：**

| PCRE 简写 | ERE/BRE 等效 |
|-----------|-------------|
| `\d` | `[0-9]` |
| `\D` | `[^0-9]` |
| `\w` | `[a-zA-Z0-9_]` |
| `\W` | `[^a-zA-Z0-9_]` |
| `\s` | `[[:space:]]` 或 `[ \t\n\r\f\v]` |
| `\S` | `[^[:space:]]` |

#### 3.2.6 POSIX 字符类 -- BRE/ERE 通用

POSIX 标准定义了一套**命名字符类（Named Character Classes）**，所有 POSIX 兼容的正则引擎（包括 BRE、ERE）都支持：

| POSIX 类 | 含义 | 等价于（ASCII） |
|----------|------|----------------|
| `[[:alnum:]]` | 字母和数字（Alphanumeric） | `[a-zA-Z0-9]` |
| `[[:alpha:]]` | 字母（Alphabetic） | `[a-zA-Z]` |
| `[[:digit:]]` | 数字（Digit） | `[0-9]` |
| `[[:lower:]]` | 小写字母 | `[a-z]` |
| `[[:upper:]]` | 大写字母 | `[A-Z]` |
| `[[:space:]]` | 空白字符 | `[ \t\n\r\f\v]` |
| `[[:blank:]]` | 空格和制表符 | `[ \t]` |
| `[[:punct:]]` | 标点符号 | `` !"#$%&'()*+,-./:;<=>?@[\]^_`{|}~ `` |
| `[[:print:]]` | 可打印字符 | `[[:graph:] ]` |
| `[[:graph:]]` | 可见字符（非空白、非控制字符） | `[[:alnum:][:punct:]]` |
| `[[:cntrl:]]` | 控制字符 | ASCII 0-31 和 127（DEL） |
| `[[:xdigit:]]` | 十六进制数字字符 | `[0-9a-fA-F]` |

```bash
# 使用 POSIX 字符类
cat > /tmp/regex_posix.txt << 'EOF'
Hello World 2026
line2 has	tabs
!@#$% punctuation!
12345
EOF

# [[:digit:]] 匹配数字
grep -E "[[:digit:]]" /tmp/regex_posix.txt
# 输出：Hello World 2026、12345

# [[:alpha:]] 匹配字母
grep -E "[[:alpha:]]" /tmp/regex_posix.txt
# 输出包含字母的行

# [[:punct:]] 匹配标点符号
grep -E "[[:punct:]]" /tmp/regex_posix.txt
# 输出：!@#$% punctuation!

# POSIX 类可以放在自定义字符类中
grep -E "[[:digit:][:punct:]]" /tmp/regex_posix.txt
# 匹配数字或标点符号
```

**POSIX 类不可用简写替代（在 BRE/ERE 中）：** `[:digit:]` 不是独立的语法，必须放在方括号内：`[[:digit:]]`（双层方括号）。外层 `[]` 是字符类，内层 `[:digit:]` 是 POSIX 命名类。

```bash
# 错误写法
grep -E "[:digit:]" /tmp/regex_posix.txt
# [:digit:] 被解释为匹配字符 ':', 'd', 'i', 'g', 't' 中任意一个！

# 正确写法
grep -E "[[:digit:]]" /tmp/regex_posix.txt
# [[:digit:]] 正确匹配数字
```

### 3.3 量词（Quantifier）

量词控制**前一个元素**出现的次数。这里的"元素"可以是一个字面量字符、一个字符类、或一个分组。

```
元素        量词          含义
────        ────          ────
a           *            字符 'a' 重复 0 次或多次
[0-9]       +            数字重复 1 次或多次
(ab)        ?            分组 'ab' 出现 0 次或 1 次
\d          {3}          数字恰好出现 3 次
```

#### 3.3.1 `*` -- 零次或多次

`a*` 匹配**零个或多个 `a`**。这是最常用的量词之一。

```bash
cat > /tmp/regex_quant.txt << 'EOF'
ac
abc
abbc
abbbc
accc
bc
ab
EOF

# a* 匹配零个或多个 'a'
grep -E "ab*c" /tmp/regex_quant.txt
# 输出：
# ac       ← a 后面跟 0 个 b，然后是 c
# abc      ← a 后面跟 1 个 b，然后是 c
# abbc     ← a 后面跟 2 个 b，然后是 c
# abbbc    ← a 后面跟 3 个 b，然后是 c
# 不匹配：accc（c 后面还有 c）、bc（没有 a）、ab（没有 c）
```

`*` 的最常见用法之一是配合 `.` 使用：`.*` 匹配**任意内容**（包括空串）。这在提取特定模式之间的内容时非常有用。

#### 3.3.2 `+` -- 一次或多次

`a+` 匹配**一个或多个 `a`**。与 `*` 的区别是：`+` 要求至少出现一次。

```bash
# + 要求至少出现一次
grep -E "ab+c" /tmp/regex_quant.txt
# 输出：
# abc      ← 1 个 'b'
# abbc     ← 2 个 'b'
# abbbc    ← 3 个 'b'
# 不匹配：ac（0 个 b 不满足 +）

# 对比 *：ac 会被匹配
grep -E "ab*c" /tmp/regex_quant.txt
# 输出：ac、abc、abbc、abbbc
```

**`*` 和 `+` 的选择：**

- 用 `*`：元素可以不存在（可选元素）
- 用 `+`：元素必须至少存在一次

#### 3.3.3 `?` -- 零次或一次（可选）

`a?` 匹配**零个或一个 `a`**。`?` 表示元素是"可有可无"的。

```bash
# ? 表示前面的字符最多出现一次
# 实际例子：匹配英式/美式拼写
echo -e "color\ncolour\ncolouur\ncolors" | grep -E "colou?r"
# 输出：
# color      ← 美式拼写（0 个 u）
# colour     ← 英式拼写（1 个 u）
# colors     ← 美式拼写 + s（不需要在乎后面的 s）
# 不匹配：colouur（2 个 u，超过了 ? 的 0-1 限制）
```

**`?` 的常用场景：**

```bash
# 匹配可选的协议前缀
grep -E "https?://" urls.txt
# 's?' 表示 's' 可有可无，同时匹配 http:// 和 https://

# 匹配可选的扩展名
grep -E "index\.html?" file.txt
# 同时匹配 index.htm 和 index.html
```

#### 3.3.4 `{n}` `{n,}` `{n,m}` -- 精确重复次数

花括号量词提供了最精确的重复次数控制：

| 语法 | 含义 | 示例 |
|------|------|------|
| `{n}` | 恰好 n 次 | `\d{3}` = 恰好 3 个数字 |
| `{n,}` | 至少 n 次 | `\d{3,}` = 至少 3 个数字 |
| `{n,m}` | n 到 m 次（含两端） | `\d{3,5}` = 3 到 5 个数字 |

```bash
cat > /tmp/regex_braces.txt << 'EOF'
a
ab
abb
abbb
abbbb
abbbbb
EOF

# {3}：恰好 3 次
grep -E "ab{3}" /tmp/regex_braces.txt
# 输出：abbb（恰好 3 个 b）

# {2,}：至少 2 次
grep -E "ab{2,}" /tmp/regex_braces.txt
# 输出：abb、abbb、abbbb、abbbbb（2 个或更多 b）

# {2,4}：2 到 4 次
grep -E "ab{2,4}" /tmp/regex_braces.txt
# 输出：abb、abbb、abbbb（2、3 或 4 个 b，不含 abbbbb）
```

**BRE 中需要转义：** 在 BRE 中，`{` 和 `}` 默认是字面量，必须写成 `\{n\}` 才能作为量词：

```
ERE：ab{3}      ← 3 个 b
BRE：ab\{3\}    ← 3 个 b（需要转义）
```

**量词的常用组合：**

```bash
# 匹配 IPv4 地址（简化版）
grep -E "[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}"

# 匹配 8 位十六进制颜色代码
grep -E "#[0-9a-fA-F]{6}"

# 匹配 11 位手机号（中国大陆）
grep -E "1[3-9][0-9]{9}"
```

### 3.4 贪婪匹配 vs 非贪婪匹配（Lazy Matching）

这是正则表达式中**最重要的高级概念之一**，也是初学者最容易出错的地方。

#### 3.4.1 贪婪匹配（Greedy）-- 默认行为

**所有量词（`*`、`+`、`?`、`{n,m}`）默认都是贪婪的。** 贪婪量词会尽可能多地匹配字符，只有在后续模式无法满足时才会"回溯"。

```bash
# 演示贪婪匹配
cat > /tmp/regex_greedy.txt << 'EOF'
<div>hello</div><div>world</div>
EOF

# 贪婪匹配：.* 尽可能多地消费
grep -E "<div>.*</div>" /tmp/regex_greedy.txt
# 匹配：<div>hello</div><div>world</div>
#        ^                            ^
#        |                            |
#        └───── 整段被一次性匹配 ───────┘
#
# 解析过程：
# <div>  → 匹配第一个 <div>
# .*     → 贪婪地消费了 "hello</div><div>world"（一直到末尾）
# </div> → 需要匹配 </div>，但已经到末尾了 → 回溯
# .*     → 逐步吐回字符，直到找到 </div>
# </div> → 匹配最后一个 </div>
# 结果：匹配了整个字符串！
```

**为什么这不是我们想要的？** 如果你想要提取 HTML 标签的内容，你可能期望匹配结果是两个 `<div>...</div>` 块，而不是一整个。

#### 3.4.2 非贪婪匹配（Lazy）-- PCRE 的 `*?` `+?` `??` `{n,m}?`

在量词后面加 `?`，将贪婪量词变成**非贪婪（Lazy / Non-Greedy）**量词。非贪婪量词会尽可能**少**地匹配字符。

| 贪婪量词 | 非贪婪版本 | 含义 |
|---------|-----------|------|
| `*` | `*?` | 零次或多次（尽可能少） |
| `+` | `+?` | 一次或多次（尽可能少） |
| `?` | `??` | 零次或一次（尽可能少--即优先选择零次） |
| `{n,m}` | `{n,m}?` | n 到 m 次（尽可能少--优先匹配 n 次） |

**非贪婪匹配仅在 PCRE（`grep -P`）中可用。BRE/ERE 不支持。**

```bash
# 非贪婪匹配：.*? 尽可能少地消费
grep -Po "<div>.*?</div>" /tmp/regex_greedy.txt
# 匹配：
# <div>hello</div>
# <div>world</div>
#
# 解析过程（第一个匹配）：
# <div>  → 匹配第一个 <div>
# .*?   → 非贪婪，初始匹配空串 ""
# </div> → 需要 </div>，当前位置是 'h' → 不匹配 → 扩展 .*?
# .*?   → 扩展到 "h"
# </div> → 还是不匹配 → 继续扩展 .*?
# ...逐步扩展...
# .*?   → 扩展到 "hello"
# </div> → 匹配！
# 结果：<div>hello</div>（最短匹配）
```

#### 3.4.3 贪婪 vs 非贪婪可视化对比

```
文本: <tag>content1</tag><tag>content2</tag>

贪婪 <tag>.*</tag>:
    <tag>content1</tag><tag>content2</tag>
    ^                                  ^
    └──────── 一次匹配全部 ────────────┘

非贪婪 <tag>.*?</tag>:
    <tag>content1</tag><tag>content2</tag>
    ^               ^ ^               ^
    └── 匹配 1 ────┘ └── 匹配 2 ────┘
```

#### 3.4.4 ERE 中替代非贪婪的方法：排除字符类

在 ERE 中，你不能使用 `*?`，但可以用**排除字符类**达到类似效果：

```bash
# ERE 替代方案：用排除字符类 [^<]* 代替 .*?
grep -Eo "<div>[^<]*</div>" /tmp/regex_greedy.txt
# [^<]* 匹配所有非 '<' 字符
# 输出：
# <div>hello</div>
# <div>world</div>
```

**排除字符类替代方案对照表：**

| 非贪婪目标 | PCRE 写法 | ERE 等价写法 |
|-----------|----------|-------------|
| 匹配到第一个 `"` | `".*?"` | `"[^"]*"` |
| 匹配到第一个 `>` | `<.*?>` | `<[^>]*>` |
| 匹配到第一个空格 | `\S.*?\s` | `[^ ]* ` |
| 匹配到第一个 `)` | `\(.*?\)` | `\([^)]*\)` |

**排除字符类的方法非常高效：** 因为 `[^x]*` 不会产生回溯（一旦遇到 `x` 就停止），而 `.*?` 会在每次不匹配时尝试扩展，发生回溯。

### 3.5 锚点（Anchor）

锚点不匹配任何字符，它们匹配的是**位置（Position）**--字符串中的特定位置。锚点有零宽度（Zero-Width），它们约束匹配必须发生在特定的前后文环境中。

#### 3.5.1 `^` -- 行首

`^` 匹配**行的开头**。只有当模式出现在行首时，整个表达式才匹配。

```bash
cat > /tmp/regex_anchor.txt << 'EOF'
hello world
world hello
  hello with spaces
say hello
hello
EOF

# ^ 匹配行首
grep -E "^hello" /tmp/regex_anchor.txt
# 输出：
# hello world       ← hello 在行首
# hello             ← hello 在行首
# 不匹配：
#   world hello     ← hello 在行尾
#     hello with spaces  ← hello 前面有空格
#   say hello       ← hello 在前面有 "say "

# 匹配空行
grep -E "^$" /tmp/regex_anchor.txt
# $ 紧跟 ^ 表示行首和行尾之间没有内容
```

**`^` 的两种含义（取决于上下文）：**

| 位置 | 含义 | 示例 |
|------|------|------|
| 字符类外、模式开头 | 行首锚点 | `^hello`（以 hello 开头） |
| 字符类内、第一个位置 | 排除 | `[^ae]`（不是 a 或 e） |
| 字符类内、非第一个位置 | 字面量 `^` | `[a^b]`（a、^ 或 b） |

#### 3.5.2 `$` -- 行尾

`$` 匹配**行的结尾**。

```bash
# $ 匹配行尾
grep -E "hello$" /tmp/regex_anchor.txt
# 输出：
# world hello       ← hello 在行尾
# hello             ← hello 同时在行首和行尾
# 不匹配：hello world、say hello（行尾不是 hello）
```

**将 `^` 和 `$` 结合使用：**

```bash
# 匹配整行只有 "hello" 的行（精确匹配 -- 等价于 grep -x）
grep -E "^hello$" /tmp/regex_anchor.txt
# 输出：hello（只有这行从头到尾恰好是 "hello"）

# 匹配以数字开头的行
grep -E "^[0-9]" /tmp/regex_anchor.txt

# 匹配以句号结尾的行
grep -E "\.$" /some/file.txt
```

#### 3.5.3 `\b` -- 单词边界（PCRE 专用）

`\b` 匹配**单词边界（Word Boundary）**--即单词字符（`\w`：字母、数字、下划线）与非单词字符之间的位置。`\b` 也是一个零宽度断言。

```bash
cat > /tmp/regex_boundary.txt << 'EOF'
cat
category
the cat sat
concatenate
cat!
_cat_
EOF

# \b 单词边界（PCRE）
grep -P "\bcat\b" /tmp/regex_boundary.txt
# 输出：
# cat               ← cat 是整行
# the cat sat       ← cat 前后都是空格
# cat!              ← cat 后是标点符号（非单词字符）
# 不匹配：
#   category        ← cat 后面是 'e'（单词字符），没有边界
#   concatenate     ← cat 前面是 'n'，后面是 'e'
#   _cat_           ← cat 前后都是 '_'（下划线是单词字符！）
```

**`\b` 的工作原理：** `\b` 匹配这样的位置--一侧是 `\w` 字符，另一侧是 `\W` 字符（或行首/行尾）。

```
文本:     the cat sat
位置:     ↑  ↑  ↑  ↑
         \b \b \b \b
```

#### 3.5.4 `\B` -- 非单词边界（PCRE 专用）

`\B` 是 `\b` 的反面--匹配**不在单词边界**的位置。

```bash
# \B：匹配非单词边界的位置
grep -P "\Bcat\B" /tmp/regex_boundary.txt
# 输出：concatenate（cat 在单词内部，前后都是单词字符）

grep -P "cat\B" /tmp/regex_boundary.txt
# 输出：category（cat 后面跟的是单词字符）
```

#### 3.5.5 `\<` 和 `\>` -- 单词边界（BRE/ERE 专用）

BRE 和 ERE 中，`\b` 不可用（字符类简写是 PCRE 特性）。替代方案是 `\<`（单词开始）和 `\>`（单词结束）：

```bash
# ERE 中的单词边界
grep -E "\<cat\>" /tmp/regex_boundary.txt
# 等价于 PCRE 的 \bcat\b
# 输出：cat、the cat sat、cat!

# \< 单词开头
grep -E "\<cat" /tmp/regex_boundary.txt
# 输出：cat、category、the cat sat、cat!

# \> 单词结尾
grep -E "cat\>" /tmp/regex_boundary.txt
# 输出：cat、the cat sat、cat!
```

**注意：** `\<` 和 `\>` 是 GNU 扩展，不是 POSIX 标准的一部分。在极简嵌入式系统中可能不支持。

### 3.6 交替（Alternation）-- `|`

`|` 表示**或（OR）**关系。`A|B` 匹配模式 A **或**模式 B。

```bash
cat > /tmp/regex_alter.txt << 'EOF'
cat
dog
bird
cats
dogs
cat and dog
EOF

# | 或：匹配 cat 或 dog
grep -E "cat|dog" /tmp/regex_alter.txt
# 输出：
# cat
# dog
# cats          ← 包含 "cat"
# dogs          ← 包含 "dog"
# cat and dog   ← 包含两者

# | 可以串联多个选项
grep -E "ERROR|WARN|FATAL" /var/log/syslog
# 匹配三种日志级别的任意一种

# | 配合分组
grep -E "^(cat|dog|bird)$" /tmp/regex_alter.txt
# 输出：cat、dog、bird（整行精确匹配三个词之一）
```

**`|` 的优先级：** `|` 的优先级很低。`^cat|dog$` 的含义是 `(^cat)|(dog$)`，而非 `^(cat|dog)$`。如果意图是后者，需要用括号分组。

```bash
# 这两个表达式的含义不同
grep -E "^cat|dog$" /tmp/regex_alter.txt
# 含义：(^cat) | (dog$) → 以 cat 开头 或 以 dog 结尾

grep -E "^(cat|dog)$" /tmp/regex_alter.txt
# 含义：整行恰好是 cat 或 dog
```

**BRE 中需要转义：** `\|` 而非 `|`。

```bash
# BRE 中的或
grep "cat\|dog" /tmp/regex_alter.txt
```

### 3.7 分组与捕获（Grouping and Capture）

#### 3.7.1 捕获分组 `()` -- 分组并记住匹配内容

`(pattern)` 有两大功能：

1. **分组（Grouping）：** 将一部分模式组合为一个整体，以便对其整体应用量词或交替
2. **捕获（Capture）：** 引擎"记住"该分组匹配到的具体文本，供后续使用

```bash
cat > /tmp/regex_group.txt << 'EOF'
abab
ababab
abcabc
abababab
ab
abc
EOF

# 分组 + 量词：匹配重复的 "ab"
grep -E "^(ab)+$" /tmp/regex_group.txt
# (ab) 是一个整体，+ 表示这个整体重复 1 次或多次
# 输出：
# abab          ← (ab) 重复 2 次
# ababab        ← (ab) 重复 3 次
# abababab      ← (ab) 重复 4 次

# 分组 + 交替
grep -E "^(ab|abc)+$" /tmp/regex_group.txt
# 匹配 "ab" 或 "abc" 重复一次或多次

# 实用的分组示例
grep -E "([0-9]{1,3}\.){3}[0-9]{1,3}" file.txt
# 匹配 IPv4 地址：三组"数字." + 最后一组数字
```

#### 3.7.2 反向引用（Backreference）-- `\1` `\2` ... `\9`

**这是 ERE 与 BRE 最具标志性的高级特性之一。** 捕获分组中的内容可以被**反向引用（Backreference）**--用在同一个正则表达式中，引用之前某个分组捕获到的具体文本。

`\1` 引用第 1 个捕获分组的内容，`\2` 引用第 2 个，依次类推，最多到 `\9`。

```bash
cat > /tmp/regex_backref.txt << 'EOF'
hello hello
the the word
this is is repeated
abc abc def
abc def abc
EOF

# 反向引用：匹配重复的单词
grep -E "\b(\w+)\s+\1\b" /tmp/regex_backref.txt
# 解析：
# \b       → 单词边界
# (\w+)    → 第 1 个捕获分组：一个或多个单词字符
# \s+      → 一个或多个空白符
# \1       → 反向引用：引用第 1 组捕获到的内容（即前面的单词）
# \b       → 单词边界
# 输出：
# hello hello       ← \1 = "hello"
# the the           ← \1 = "the"
# is is             ← \1 = "is"
```

```bash
# 用 PCRE -o 提取重复的单词
grep -Po "\b(\w+)\s+\1\b" /tmp/regex_backref.txt

# 匹配 HTML 标签对
echo "<h1>Title</h1><div>Content</div>" | grep -Po "<(\w+)>.*?</\1>"
# (\w+) 捕获标签名，\1 引用确保闭合标签匹配
# 输出：<h1>Title</h1>、<div>Content</div>
```

```bash
# 多个反向引用
cat > /tmp/regex_multiback.txt << 'EOF'
abc-def-abc
xyz-123-xyz
abc-def-ghi
EOF

grep -E "^([a-z]+)-([0-9a-z]+)-\1$" /tmp/regex_multiback.txt
# \1 引用第一个分组（前面的字母部分），确保首尾相同
# 输出：
# abc-def-abc      ← 首尾都是 abc
# xyz-123-xyz      ← 首尾都是 xyz
# 不匹配：abc-def-ghi（首尾不同）
```

#### 3.7.3 非捕获分组 `(?:)` -- PCRE 专用

有时候你只需要**分组**功能（对子模式整体应用量词），但不需要**捕获**（不打算使用 `\1` 引用）。此时可以使用**非捕获分组（Non-Capturing Group）** `(?:pattern)`。

```bash
# 捕获分组（默认）：捕获并分配编号
grep -E "([0-9]+)-([a-z]+)" file.txt
# 两个捕获组：\1 = 数字，\2 = 字母

# 非捕获分组（PCRE）：只分组不捕获
grep -P "(?:[0-9]+)-(?:[a-z]+)" file.txt
# 不产生捕获组，减少内存开销，提高性能
```

**为什么使用非捕获分组？**

1. **性能：** 捕获需要保存匹配的子串，有额外开销。大量分组时差异明显。
2. **编号清晰：** 当只有部分分组需要被引用时，非捕获分组不占用编号，使 `\1`、`\2` 的对应关系更清晰。

```bash
# 对比：捕获 vs 非捕获
# 捕获版本：每个括号都产生一个组
grep -P "(?:https?|ftp)://([^/]+)/(.*)" urls.txt
# (?:https?|ftp)  → 非捕获：只分组，不占用 \1
# ([^/]+)         → 捕获组 1：主机名
# (.*)           → 捕获组 2：路径

# 如果全部用捕获分组，编号会乱：
grep -P "(https?|ftp)://([^/]+)/(.*)" urls.txt
# \1 = 协议，\2 = 主机名，\3 = 路径
# 如果后续只用 \2 和 \3，\1 被浪费
```

#### 3.7.4 命名捕获组 `(?P<name>)` -- PCRE 专用

PCRE 还支持**命名捕获组（Named Capture Group）**，给捕获内容一个名字，解决 `\1` `\2` 编号不直观的问题：

```bash
# 命名捕获组
grep -P "(?P<protocol>https?)://(?P<host>[^/]+)/(?P<path>.*)" urls.txt
# (?P<protocol>...)  → 命名为 "protocol"
# (?P<host>...)      → 命名为 "host"
# (?P<path>...)      → 命名为 "path"
```

**注意：** `grep` 本身不直接支持按名称引用捕获组。但在 Python、Perl、PHP 等编程语言中，命名捕获组是非常实用的特性。

### 3.8 环视断言（Lookaround Assertions）-- PCRE 专用

环视断言是 PCRE 最强大的特性之一。它们让你能够基于**前后文条件**（而非内容本身）进行匹配。环视是**零宽度（Zero-Width）**的--它们检查条件是否满足但不消费任何字符。

| 断言 | 名称 | 含义 | 方向 |
|------|------|------|------|
| `(?=...)` | 正向先行断言（Positive Lookahead） | 后面必须跟着 `...` | 向右看 |
| `(?!...)` | 负向先行断言（Negative Lookahead） | 后面不能跟着 `...` | 向右看 |
| `(?<=...)` | 正向后行断言（Positive Lookbehind） | 前面必须是 `...` | 向左看 |
| `(?<!...)` | 负向后行断言（Negative Lookbehind） | 前面不能是 `...` | 向左看 |

#### 3.8.1 `(?=...)` -- 正向先行断言

匹配某个位置，该位置**之后必须跟随**指定的模式。但断言本身不消费字符。

```bash
cat > /tmp/regex_lookahead.txt << 'EOF'
abc123
abc456
xyz789
abc000
def123
EOF

# 正向先行断言：匹配后面跟数字的 "abc"
grep -P "abc(?=\d+)" /tmp/regex_lookahead.txt
# 输出：
# abc123        ← abc 后面跟了数字 123
# abc456        ← abc 后面跟了数字 456
# abc000        ← abc 后面跟了数字 000
# 不匹配：
#   xyz789      ← 不是 abc
#   def123      ← 不是 abc

# 注意：断言不消费字符
echo "abc123" | grep -Po "abc(?=\d+)"
# 输出：abc（断言的条件 123 只是被检查，没有被消费到匹配结果中）
```

#### 3.8.2 `(?!...)` -- 负向先行断言

匹配某个位置，该位置**之后不能跟随**指定的模式。

```bash
# 负向先行断言：匹配后面不是数字的 "abc"
grep -P "abc(?!\d)" /tmp/regex_lookahead.txt
# 在测试数据中，"abc" 总是后面跟数字，所以无输出

# 更实际的例子：找出不是 "localhost" 的主机名
cat > /tmp/regex_negahead.txt << 'EOF'
localhost
localhost:8080
example.com
192.168.1.1
localhosts
EOF

grep -P "^(?!localhost$)" /tmp/regex_negahead.txt
# 匹配整行不是 "localhost" 的行
# 输出：除 "localhost" 之外的所有行
```

#### 3.8.3 `(?<=...)` -- 正向后行断言

匹配某个位置，该位置**之前必须是**指定的模式。

```bash
cat > /tmp/regex_lookbehind.txt << 'EOF'
price=100
cost=200
total=100
amount=50
price=xxx
EOF

# 正向后行断言：匹配前面是 "price=" 的数字
grep -Po "(?<=price=)\d+" /tmp/regex_lookbehind.txt
# 输出：
# 100          ← 前面是 "price="
# （第二个 "price=xxx" 后面不是数字，不匹配）
```

**后行断言的一个重要限制：** 后行断言中的模式必须匹配**固定长度**（不能使用 `+`、`*` 等不确定长度的量词）。`(?<=\d+)` 在大多数 PCRE 实现中是不支持的，因为 `\d+` 的长度不固定。

```bash
# 正确：固定长度的后行断言
grep -P "(?<=#)[0-9a-fA-F]{6}" colors.txt
# (?<=#) 检查前面是否有一个 '#' 字符（长度固定为 1）

# 正确：使用 {n} 固定长度量词
grep -P "(?<=\d{4}-)\d{2}-\d{2}" dates.txt
# 检查前面是否有 "2024-"（4 位数字 + 连字符，长度固定）

# 错误（大多数引擎不支持）：使用 + 等可变长度量词
# grep -P "(?<=\d+\.)\d+" file.txt  # 很多引擎会报错
```

#### 3.8.4 `(?<!...)` -- 负向后行断言

匹配某个位置，该位置**之前不能是**指定的模式。

```bash
# 负向后行断言：匹配前面不是 "$" 的数字
cat > /tmp/regex_negbehind.txt << 'EOF'
$100
100
price: 200
$300
400 dollars
EOF

grep -Po "(?<!\$)\b\d+\b" /tmp/regex_negbehind.txt
# 输出：
# 100          ← 前面不是 $
# 200          ← 前面不是 $
# 400          ← 前面不是 $
# 不匹配：
#   $100       ← 前面是 $
#   $300       ← 前面是 $

# 注意：$ 需要转义（\$）以免被误认为是行尾锚点
```

#### 3.8.5 环视断言的实用场景汇总

```bash
# 1. 密码验证：必须包含至少一个数字、一个小写字母、一个大写字母
# （需要多个先行断言，它们各自检查不同的条件）
grep -P "^(?=.*\d)(?=.*[a-z])(?=.*[A-Z]).{8,}$" passwords.txt
# (?=.*\d)        → 先行断言：整行中某处有数字
# (?=.*[a-z])     → 先行断言：整行中某处有小写字母
# (?=.*[A-Z])     → 先行断言：整行中某处有大写字母
# .{8,}          → 实际匹配：至少 8 个字符

# 2. 提取不包含特定后缀的单词
grep -Po "\b\w+\b(?!ing\b)" text.txt
# 匹配不以 "ing" 结尾的单词

# 3. 查找注释中的代码
grep -P "(?<=//)\s*TODO.*" source.c
# 匹配 // 后面的 TODO 注释

# 4. 提取价格数值（不包含货币符号）
grep -Po "(?<=\$)\d+(?:\.\d{2})?" prices.txt
# 前面是 $ 的数字，可选的小数部分
```

### 练习 12.2：量词 -- 贪婪匹配的陷阱

**题目：**

（1）在 `data.txt` 中，用正则表达式 `<.*>` 搜索 HTML 标签。观察 `.*` 的贪婪行为。是否匹配了每一个独立的标签？

（2）使用 `<[^>]*>` 重新搜索。比较两个正则表达式的结果。哪个更准确地匹配了每个 HTML 标签？

（3）使用 PCRE 的非贪婪量词 `<.*?>` 搜索。结果与（1）还是（2）相同？

## 5. 常见错误与排错

### 5.1 把字符类 `[ERROR]` 误当成单词搜索

**现象：**

```bash
grep "[ERROR]" syslog.txt
```

预期只匹配包含单词 `ERROR` 的行，但实际上 `INFO`、`WARN` 等行也被匹配了。

**原因：** `[ERROR]` 是**字符类**，匹配 E、R、O 中任意一个字符。`INFO` 中有 O，`WARN` 中有 R，所以都被匹配了。

**解决：**

```bash
# 正确：直接搜索单词（字面量）
grep "ERROR" syslog.txt

# 或使用单词边界确保整词匹配
grep -w "ERROR" syslog.txt

# 或使用多选（交替）
grep -E "ERROR|FATAL" syslog.txt
```

**记忆技巧：** `[ ]` 是字符类--匹配**一个**字符，这个字符可以是括号中的任何一个。永远不要用 `[word]` 来搜索单词 `word`。

### 5.2 忘记 `.` 匹配任意字符（IP 地址搜索）

**现象：**

```bash
grep "192.168.1.1" access.log
```

不仅匹配了 `192.168.1.1`，还匹配了 `192.168.1.100`、`192.168.1.10` 等。因为 `.` 是正则元字符，匹配**任意单个字符**，而不仅仅是字面量的点。

**解决：**

```bash
# 方法 1：转义点号（常规方式）
grep "192\.168\.1\.1" access.log

# 方法 2：使用 -F 固定字符串（推荐：最简单最安全）
grep -F "192.168.1.1" access.log

# 方法 3：使用 -w 整词匹配（对 IP 有效，因为点号是词分隔符）
grep -w "192.168.1.1" access.log

# 方法 4：精确匹配 IP 边界
grep -E "\b192\.168\.1\.1\b" access.log
```

### 5.3 贪婪匹配陷阱 -- `.*` 吞掉太多内容

**现象：**

```bash
grep -Eo "<.*>" data.txt
```

期望输出每个 HTML 标签单独一行，但实际输出了一整段内容（从第一个 `<` 到最后一个 `>`）。

**原因：** `.*` 是**贪婪（Greedy）**匹配，尽可能多地消费字符。`<` 匹配第一个 `<`，`.*` 一直消费到文本末尾，然后回溯到最后一个 `>`。

**解决：**

```bash
# 方法 1：PCRE 非贪婪（推荐：最清晰）
grep -Po "<.*?>" data.txt

# 方法 2：ERE 排除字符类（推荐：无需 PCRE，且无回溯）
grep -Eo "<[^>]*>" data.txt

# 方法 3：在更复杂的场景中使用排除字符类
grep -Eo '"[^"]*"' data.txt
# [^"]* 匹配所有非引号字符，自动在第一个 " 处停止
```

**记忆技巧：** 当你需要"从 A 匹配到第一个 B"，用 `A[^B]*B`（排除法），而不是 `A.*B`（贪婪法）。

### 5.4 BRE 转义混乱 -- `+` `?` `|` `(` `)` `{` `}` 需要反直觉的转义

**现象：**

```bash
# 想用 BRE 搜索 "ab" 重复一次或多次
grep "(ab)+" data.txt
# 错误：BRE 中 () 和 + 都是字面量
# 实际搜索的是字面量字符串 "(ab)+"
```

**原因：** BRE 中，`+`、`?`、`|`、`(`、`)`、`{`、`}` 默认是**字面量字符**，需要转义才能作为元字符使用。这与大多数现代工具（ERE、PCRE、Python、JavaScript）的行为相反。

**解决：**

```bash
# 选择 1：老老实实写 BRE 转义
grep "\(ab\)\+" data.txt

# 选择 2：使用 -E 切换到 ERE（强烈推荐）
grep -E "(ab)+" data.txt

# 选择 3：使用 -P 切换到 PCRE
grep -P "(ab)+" data.txt
```

**建议：** 对于新脚本和新学习者，默认使用 ERE（`grep -E`）。BRE 仅用于维护老旧脚本或需要最大兼容性的场景。

### 5.5 `^` 和 `$` 位置错误 -- 锚点与交替的优先级

**现象：**

```bash
# 想匹配以 "ERROR" 或 "WARN" 开头的行
grep -E "^ERROR|WARN" syslog.txt
# 实际匹配：以 ERROR 开头的行 或 包含 WARN 的行（任何位置）
# 而不是：以 ERROR 或 WARN 开头的行
```

**原因：** `|` 的优先级非常低。`^ERROR|WARN` 被解释为 `(^ERROR)|(WARN)`，而非 `^(ERROR|WARN)`。

**解决：**

```bash
# 正确：用括号明确优先级
grep -E "^(ERROR|WARN)" syslog.txt

# 或分两种写法
grep -E "^ERROR|^WARN" syslog.txt
```

### 5.6 `[a-Z]` 范围跨越大小写 -- 包含意外字符

**现象：**

```bash
grep -E "[a-Z]+" file.txt
```

期望匹配大小写字母，但结果匹配了 `[`、`\`、`]`、`^`、`_` 等额外字符。

**原因：** 在 ASCII 编码表中，小写 `a` 的码点是 97，大写 `Z` 的码点是 90。`[a-Z]` 的范围从 97 到 90--这是一个包含中间 6 个符号的区间。

```
ASCII 表片段（码点）：
... Z  [  \  ]  ^  _  `  a ...
   90  91 92 93 94 95 96 97
   └── 顺序写反了的 [a-Z] 范围 ──┘
```

**解决：**

```bash
# 正确：分开写或明确范围
grep -E "[a-zA-Z]+" file.txt      # 小写 + 大写
grep -E "[[:alpha:]]+" file.txt   # POSIX 字母类（推荐）
```

### 5.7 把零宽度断言当成了消费匹配

**现象：**

```bash
# 想用 -o 提取 "后面跟了数字的 abc"
echo "abc123" | grep -Po "abc(?=\d+)"
# 输出：abc（没有数字）
# 初学者可能期望输出 abc123
```

**原因：** `(?=...)` 是零宽度断言--它检查条件但不消费任何字符。匹配结果只包含断言**之前**的内容。

**解决：**

```bash
# 如果需要包含数字，不要把条件放在断言中
echo "abc123" | grep -Po "abc\d+"
# 输出：abc123

# 如果需要断言在中间（匹配某部分但依赖上下文）
echo "abc123" | grep -Po "abc(?=\d+)\d+"
# 输出：abc123（(?=\d+) 检查后续是数字，然后 \d+ 消费这些数字）
```

### 5.8 灾难性回溯（Catastrophic Backtracking）

**现象：**

```bash
# 这个看似无害的正则需要极长时间执行
echo "aaaaaaaaaaaaaaaaaaaaaaab" | grep -E "(a+)+b"
# 可能需要数秒到数分钟（取决于 a 的数量）
```

**原因：** 当正则引擎使用回溯（Backtracking）时，嵌套的量词可能导致指数级的组合爆炸。`(a+)+` 中，每个 `+` 都尝试不同的分割方式，失败后回溯并尝试另一种分割，可能的组合数以指数增长。

**灾难性回溯的三个条件：**

1. 嵌套的量词：`(a+)+`、`(a*)*`、`(.+)+`
2. 重叠的匹配范围：两个量词可以匹配相同的字符
3. 模式以无法匹配的后缀结尾：`b` 在 `a` 组成的字符串中找不到

**解决：**

```bash
# 方法 1：减少嵌套（推荐--最根本的解决方案）
grep -E "a+b" file.txt
# (a+)+b → a+b：消除不必要的嵌套量词

# 方法 2：使用原子组（PCRE，防止回溯）
grep -P "(?>a+)+b" file.txt
# (?>...) 原子组：匹配后不回溯，如果后续失败直接放弃

# 方法 3：改写模式避免重叠
grep -E "a{2,}b" file.txt
# 用固定量词 {2,} 替代嵌套的 +
```

**最常见的灾难性回溯陷阱：**

| 危险模式 | 安全替代 | 场景 |
|---------|---------|------|
| `(.+)+` | `.+` | 匹配任意内容 |
| `([a-z]+)*` | `[a-z]*` | 匹配字母序列 |
| `(.*,)+` | `[^,]+(,[^,]+)*` | 逗号分隔的值 |
| `(\w+)+@` | `\w+@` | email 地址前缀 |

### 6.5 正则表达式与 awk 的预览

### 6.6 正则表达式性能优化

对于大规模文本处理，正则的性能至关重要：

**优化原则 1：使用锚点减少扫描范围**

```bash
# 慢：在每行的每个位置都尝试匹配
grep "pattern" huge_file.txt

# 快：只在行首尝试匹配（跳过 99% 的位置）
grep "^pattern" huge_file.txt
```

**优化原则 2：避免无意义的 `.*`**

```bash
# 慢：.* 先捕获所有内容再回溯
grep -E ".*ERROR$" huge_file.txt

# 快：直接匹配（等价）
grep -E "ERROR$" huge_file.txt
# grep 默认就是包含匹配，.* 在大多数场景是完全多余的
```

**优化原则 3：使用 `-F` 代替正则（当不需要正则时）**

```bash
# 慢：正则引擎编译和回溯
grep "exact_string" huge_file.txt

# 快：Boyer-Moore 算法直接字符串搜索
grep -F "exact_string" huge_file.txt
# 大文件上差异可达 2-5 倍
```

**优化原则 4：使用排除字符类代替 `.*?`**

```bash
# PCRE 非贪婪（慢）：每一步都尝试后续匹配
grep -Po '".*?"' huge_file.txt

# ERE 排除字符类（快）：遇到分隔符就停止，无回溯
grep -Eo '"[^"]*"' huge_file.txt
```

**优化原则 5：避免嵌套量词**

```bash
# 危险：嵌套量词可能导致灾难性回溯
grep -E "([a-z]+)+" huge_file.txt

# 安全：单层量词
grep -E "[a-z]+" huge_file.txt
```

### 6.7 从正则到形式语言理论

如果你对正则表达式背后的理论感兴趣：

- **正则语言（Regular Language）** 是乔姆斯基体系（Chomsky Hierarchy）中最基础的一层：3 型文法
- **有限自动机（Finite Automaton, FA）** 是正则引擎的理论模型：确定性（DFA）和非确定性（NFA）
- BRE 和 ERE 理论上是**正则**的（Regular），可以被转换为有限自动机，以线性时间 O(n) 匹配
- PCRE 的后向引用（`\1`）和环视断言使 PCRE 超越了严格的正则语言范畴，进入了上下文相关语言（Context-Sensitive Language）领域

**实用结论：** BRE/ERE 可以用线性时间（O(n)）匹配，而 PCRE 的某些特性（尤其是嵌套的 `+` 和 `*` 配合回溯）在最差情况下需要指数时间。这也是为什么 GNU grep 的 BRE/ERE 永远比 PCRE 更稳定可预测。

### 6.8 正则表达式速记口诀

作为本章的收尾，记住这 8 条口诀，覆盖 90% 的正则使用场景：

```
1. . 是任意，[abc] 是其中之一
2. [^abc] 是排除，[a-z] 是范围
3. * 零或多，+ 一或多，? 可无可一
4. {0,3} 零到三，{3} 恰好三，{3,} 至少三
5. ^ 是行首，$ 是行尾，\b 是词界
6. () 捕获，\1 引用，(?:) 只分不捕
7. | 是或者，(?=) 后必须是，(?!) 后不准是
8. 贪婪是默认，? 变法变懒（*?, +?, ??, {n,m}?）
```

## 本章小结

恭喜你完成了第十二章--正则表达式完全指南！这是整个 Linux 文本处理序列中最硬核、也最重要的一章。

回顾本章，你现在应该能够：

- 理解正则表达式的**本质**：一种描述文本模式的语言，核心是"模式匹配"而非"值查找"
- 掌握**元字符**的角色：14 个特殊字符（`. * + ? | ( ) [ ] { } ^ $ \`）及其转义方法
- 熟练使用**字符类**：`[abc]`（自定义）、`[^abc]`（排除）、`[a-z]`（范围）、`\d \w \s`（PCRE 简写）、`[[:digit:]]`（POSIX 类）
- 精确控制**量词**：`*`（零或多）、`+`（一或多）、`?`（零或一）、`{n}` `{n,}` `{n,m}`（精确重复）
- 区分**贪婪（Greedy）vs 非贪婪（Lazy）**：默认贪婪（尽可能多），PCRE 的 `*?` `+?` 切换为非贪婪（尽可能少），ERE 中用排除字符类 `[^x]*` 实现类似效果
- 使用**锚点**定位：`^`（行首）、`$`（行尾）、`\b` `\<` `\>`（单词边界）
- 运用**分组与捕获**：`()` 捕获分组、`\1` 反向引用、`(?:)` 非捕获分组
- 掌握**交替** `|` 和**环视断言**：`(?=)`（正向先行）、`(?!`（负向先行）、`(?<=)`（正向后行）、`(?<!`（负向后行）
- 区分三种**正则方言**：BRE（最老，反直觉转义）、ERE（现代 Linux 标准）、PCRE（最丰富，非 POSIX）

**记住最重要的原则：**

1. **默认用 ERE，需要高级特性用 PCRE：** 日常 Linux 任务中，`grep -E` 覆盖 90% 场景。需要 `\d`、非贪婪、环视时升级到 `grep -P`。
2. **贪婪是默认，陷阱常在此：** `.*` 总是尽可能多匹配。当结果不符预期时，第一个检查项：是否是贪婪匹配导致？
3. **排除字符类优于非贪婪（在 ERE 中）：** `[^x]*` 不仅能在 ERE 中使用，而且比 PCRE 的 `.*?` 更快（无回溯）。
4. **正则不是用来"读"的，是用来"写"和"测"的：** 一个好的正则表达式来自反复测试。使用 `grep -Eo` 检查匹配内容，使用 `grep -c` 检查匹配数量，使用 regex101.com 进行交互式调试。

**在下一章（第 13 章）中，我们将学习 sed -- 流编辑器。** 你马上就会看到，本章学到的正则表达式知识在 sed 中被完整地复用。sed 的核心命令 `s/模式/替换/` 直接使用正则表达式，反向引用 `\1` 在替换操作中扮演着关键角色。准备好将你的"搜索"能力升级为"编辑"能力吧！
