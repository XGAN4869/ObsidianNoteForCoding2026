## 1. 概述

### 1.1 从"会用命令"到"会解决问题"

你学完了前面 35 章——文件操作、权限管理、进程调度、磁盘管理、网络配置、SSH 远程连接、系统服务、日志分析、定时任务、启动流程。你已经掌握了几十个命令和上百个参数。但现在，真正考验你的是另一个层次的问题：

- 凌晨 3 点，监控报警："生产服务器磁盘使用率 98%"。你 SSH 上去，面对一个陌生的系统——从哪里开始查？
- 用户反馈："网站打不开"。你登录服务器，nginx 进程在运行、端口在监听、但页面返回 502——问题出在哪一层？
- `apt install` 报错 "Unable to locate package"——是 sources.list 的问题、网络的问题、还是拼写错误？
- 服务器重启后卡在 GRUB rescue 提示符——你没有安装盘，也没有物理访问权限——怎么办？
- SSH 连接被拒绝，但 ping 能通——是 sshd 没启动、防火墙拦截了端口、还是 SSH 配置把你挡在了门外？
- `sudo` 命令突然返回 "user is not in the sudoers file"——你没有 root 密码，即将被锁在自己的系统外面。

这些问题的共同特征是：**你不知道原因，但你知道症状。** 你面对的不是 "执行这条命令查看结果"，而是 "发生了这个现象，我需要找到根本原因"。

这就是本章的核心使命：**建立系统化的故障排查思维框架**——一种独立于具体命令、适用于各类场景的元技能（Meta-Skill）。如果说前 35 章是教会你使用各种工具，那么本章就是教会你：面对一个未知的故障，如何选择正确的工具、按照正确的顺序、提出正确的问题。

### 1.3 本章覆盖的命令与概念

| 类别 | 命令/概念 | 用途 |
|------|----------|------|
| **诊断框架** | O-H-V-R 循环 | Observe（观察）→ Hypothesize（假设）→ Verify（验证）→ Resolve（解决） |
| **系统启动** | `journalctl -b`, `systemctl list-units --failed`, `grub>` 命令行 | 启动失败诊断——从 GRUB 到 emergency mode 的逐层排查 |
| **磁盘空间** | `df -h`, `du -sh`, `lsof \| grep deleted`, `ncdu`, `journalctl --disk-usage` | 磁盘满的根因定位——大文件、已删除但未释放、日志膨胀 |
| **性能问题** | `top`, `htop`, `ps aux --sort=-%cpu`, `strace -p`, `perf top`, `pidstat` | CPU/内存飙高——找到消耗资源的进程和系统调用 |
| **网络故障** | `ping`, `traceroute`, `ip route`, `ss -tlnp`, `dig`, `ufw status`, `tcpdump` | 网络不通——从物理层到应用层的逐层诊断 |
| **服务故障** | `systemctl status`, `journalctl -u`, `ss -tlnp`, `strace -f` | 服务无法启动——状态、日志、配置、端口、依赖的五步诊断 |
| **权限问题** | `id`, `ls -la`, `namei -l`, `getfacl`, `aa-status`, `sudo -l` | Permission denied——用户身份、文件权限、ACL、AppArmor、sudo 的全链路排查 |
| **综合排查** | `dmesg`, `tail -f /var/log/syslog`, `sar`, `vmstat`, `iostat` | 未知问题的多维度信息收集 |

### 1.4 本章目标

完成本章后，你将能够：

- 掌握 O-H-V-R 诊断框架，面对任何故障都有条不紊地展开排查
- 理解"分诊"（Triage）的概念——先判断问题的严重程度和大致范围，再深入细节
- 对六大类常见症状（启动失败、磁盘满、性能高、网络不通、服务不启动、权限拒绝）建立条件反射式的诊断路线
- 熟练使用 `df` → `du` → `lsof` 链路快速定位磁盘空间消耗源
- 熟练使用 `top` → `ps` → `strace` 链路快速定位 CPU/内存消耗者
- 熟练使用 `ping` → `ip route` → `ss` → `dig` → `tcpdump` 链路快速定位网络故障点
- 熟练使用 `systemctl status` → `journalctl -u` → `ss` 链路快速诊断服务故障
- 理解"检查清单"（Checklist）思维——用系统化的步骤替代直觉式的猜测
- 培养"第一性原理"思维——不被表面症状迷惑，追查到最根本的原因
- 在无法复现故障时，知道如何收集证据、保存现场、事后分析

## 2. 核心概念

### 2.1 O-H-V-R 诊断框架

所有有效的故障排查，无论领域如何，都遵循同一个基本循环：

```
┌─────────────────────────────────────────────────────────────────┐
│                    O-H-V-R 诊断循环                               │
│                                                                  │
│         ┌──────────────────────────────────────┐                │
│         │  O - Observe（观察）                   │                │
│         │  ─────────────────────               │                │
│         │  收集症状、错误信息、日志、            │                │
│         │  时间线、环境变化                      │                │
│         │  "发生了什么？什么时候开始的？          │                │
│         │   影响范围多大？有错误信息吗？"          │                │
│         └──────────────┬───────────────────────┘                │
│                        ▼                                         │
│         ┌──────────────────────────────────────┐                │
│         │  H - Hypothesize（假设）               │                │
│         │  ────────────────────────             │                │
│         │  基于观察形成最可能的原因假设           │                │
│         │  "如果问题是 X，那么应该看到 Y"        │                │
│         │  列出 2-3 个候选假设，按可能性排序     │                │
│         └──────────────┬───────────────────────┘                │
│                        ▼                                         │
│         ┌──────────────────────────────────────┐                │
│         │  V - Verify（验证）                    │                │
│         │  ────────────────────                 │                │
│         │  设计实验验证或排除每个假设             │                │
│         │  "执行命令 A，如果输出 B 则假设成立"   │                │
│         │  每次只改变一个变量                     │                │
│         └──────────────┬───────────────────────┘                │
│                        ▼                                         │
│              ┌──── 假设验证通过？ ────┐                           │
│              │ 是                    │ 否                        │
│              ▼                       ▼                           │
│         ┌──────────────┐    ┌──────────────────────┐            │
│         │ R - Resolve  │    │ 返回 H 或 O           │            │
│         │  执行修复     │    │ 修正假设 / 收集更多   │            │
│         │  验证修复效果  │    │ 信息                  │            │
│         │  记录根因      │    └──────────────────────┘            │
│         └──────────────┘                                         │
└─────────────────────────────────────────────────────────────────┘
```

**O-H-V-R 不是一次性的线性流程，而是一个循环。** 当验证推翻假设时，你回到观察阶段重新收集信息或回到假设阶段修正方向。这个循环可能重复多次，每次循环都让你离根因更近一步。

#### 2.1.1 Observe（观察）—— 收集症状而非猜测

"观察"不是"看一眼"。有效的观察需要系统和条理：

**观察的五个维度：**

```
1. WHAT（什么症状）：
   - 确切的错误信息是什么？（复制完整输出，不要凭记忆）
   - 什么行为不正常？（慢？不可用？报错？无响应？）
   - 什么行为仍然正常？（缩小范围）

2. WHEN（何时开始）：
   - 故障最早什么时候出现？
   - 是突然发生的还是逐渐恶化的？
   - 有没有时间规律（如每天凌晨 3 点）？

3. WHERE（影响范围）：
   - 影响一台服务器还是多台？
   - 影响所有用户还是特定用户？
   - 影响所有操作还是特定操作？

4. WHAT CHANGED（什么变了）：
   - 最近有没有部署新代码、安装新软件、修改配置？
   - 最近有没有系统更新、内核升级、安全补丁？
   - 最近有没有流量变化、用户量变化？

5. CONTEXT（上下文）：
   - 系统负载如何？（`uptime`、`top`）
   - 磁盘空间够吗？（`df -h`）
   - 日志里有什么？（`journalctl -p err --since "1 hour ago"`）
```

**观察的黄金法则：永远先收集完整信息，再下判断。** 最常见的排查错误就是：看到第一个可疑线索就跳到结论，忽略了更关键的证据。

#### 2.1.2 Hypothesize（假设）—— 从现象推导到原因

基于观察到的症状，形成可验证的因果假设。

**假设的质量标准：**

| 好的假设 | 差的假设 |
|----------|----------|
| "CPU 使用率 100% 是因为某个进程死循环，我可以查 top 确认" | "CPU 高就是因为程序有问题" |
| "nginx 502 可能是因为后端 PHP-FPM 没启动，我可以查 systemctl status php8.3-fpm" | "502 多半是 nginx 配置的问题" |
| "磁盘满可能是 /var/log 下的日志没轮替，我可以查 du -sh /var/log" | "磁盘满了，得加硬盘" |

**假设的优先级排序：**

```
可能性高 + 验证成本低  →  最先验证
可能性高 + 验证成本高  →  次优先
可能性低 + 验证成本低  →  再次
可能性低 + 验证成本高  →  最后考虑
```

**如何形成好的假设：**

1. **对照正常状态** —— 如果系统的正常运行状态你心中有数，异常就不难捕捉
2. **分层思考** —— 从底层到顶层逐层排查（硬件 → 内核 → 系统服务 → 应用）
3. **排除法** —— 先排除最常见的原因，缩小可能性空间
4. **时间线关联** —— 把症状的发生时间和系统的变更时间对齐

#### 2.1.3 Verify（验证）—— 用证据说话

假设必须被验证——不能靠直觉跳过这一步。"我觉得是这个问题"和"我确认是这个问题"之间，隔着一条命令的输出。

**验证的原则：**

```
1. 每次只改变一个变量
   - 如果一次修改了三个配置再重启，你不知道是哪个修改起的作用
   - 修改 → 测试 → 确认，然后再进行下一个修改

2. 区分"相关"和"因果"
   - "CPU 高的时候磁盘 I/O 也高"不代表 CPU 高是磁盘 I/O 引起的
   - 可能是同一个根因导致了两者同时升高（如大量请求涌入）

3. 可重复性
   - 如果故障是可复现的——设计最小复现步骤
   - 如果故障是间歇性的——增加监控粒度，捕捉发生时刻的快照

4. 反向验证
   - 当你认为找到了原因，问自己："如果这个原因不存在，故障还会发生吗？"
   - 如果可以——撤销你的改动，看故障是否复现
```

#### 2.1.4 Resolve（解决）—— 修复根因而非症状

解决了症状不等于解决了问题。

```
症状（Symptom）  vs  根因（Root Cause）
────────────────     ────────────────────
"磁盘空间满了"         "日志轮替配置错误，/var/log 没有自动清理"
"服务 502 错误"        "PHP-FPM 进程池耗尽，因为慢查询占满了所有 worker"
"SSH 连接超时"         "ufw 默认策略改为 deny 但没有放行 22 端口"
"CPU 长期 100%"        "cron 任务每分钟重启一个死循环脚本"
```

**修复后必须做的三件事：**

1. **验证修复效果** —— 故障现象确实消失了
2. **了解为什么这个修复起作用** —— 如果你不理解为什么修好了，它可能随时再坏
3. **防止复发** —— 是配置问题就修正配置，是流程问题就改进流程，是监控盲区就添加告警

### 2.2 "分诊"思维 —— 先判断类别再深入细节

当面对一个未知故障时，最忌讳的就是一头扎进细节。你应该先做"分诊"（Triage）——快速判断问题属于哪个大类，就像急诊室分诊台根据症状把病人分到不同科室。

**快速分诊的五个关键问题：**

```
问题 1：系统在运行吗？
  ├─ 是 → 问题 2
  └─ 否 → 启动故障路线（2.3 启停链路）
           检查：能否 ping 通？能否进入 GRUB？能否进入 emergency mode？

问题 2：系统资源够吗？
  ├─ 是 → 问题 3
  └─ 否 → 资源不足路线（2.3 资源链路）
           df -h（磁盘）、free -h（内存）、uptime（负载）

问题 3：网络通吗？
  ├─ 是 → 问题 4
  └─ 否 → 网络故障路线（2.3 网络链路）

问题 4：服务在运行吗？
  ├─ 是 → 问题 5
  └─ 否 → 服务故障路线（2.3 服务链路）

问题 5：权限对吗？
  ├─ 是 → 深层排查（应用逻辑、数据一致性、竞态条件等）
  └─ 否 → 权限故障路线（2.3 权限链路）
```

这五个问题覆盖了 90% 的日常故障场景。当你在凌晨被报警叫醒时，按这个顺序逐一排查——不要跳过任何一步，也不要打乱顺序（从底层到上层）。

### 2.3 六大诊断路线总览

下表是六种最典型故障场景的诊断路线图。每种路线在第三章命令详解中展开。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      六大诊断路线速查                                     │
├──────────────┬──────────────────────────────────────────────────────────┤
│ 启停链路      │ GRUB> → journalctl -b -1 → systemctl list-units --failed│
│ （启动失败）   │ → /etc/fstab → emergency mode → dmesg                  │
├──────────────┼──────────────────────────────────────────────────────────┤
│ 资源链路      │ df -h → du -sh /* → lsof | grep deleted                 │
│ （磁盘/CPU/内存）│ → free -h → top → ps aux --sort=-%cpu → strace -p     │
├──────────────┼──────────────────────────────────────────────────────────┤
│ 网络链路      │ ping → traceroute → ip route → ss -tlnp                 │
│ （网络不通）   │ → dig/nslookup → ufw/iptables → tcpdump                │
├──────────────┼──────────────────────────────────────────────────────────┤
│ 服务链路      │ systemctl status → journalctl -u → ss -tlnp             │
│ （服务不启动） │ → /etc/配置语法检查 → strace -f → 依赖检查              │
├──────────────┼──────────────────────────────────────────────────────────┤
│ 权限链路      │ id → ls -la → namei -l → getfacl → aa-status → sudo -l  │
│ （权限拒绝）   │ → /etc/sudoers → /etc/passwd & /etc/group              │
├──────────────┼──────────────────────────────────────────────────────────┤
│ 综合链路      │ dmesg → tail /var/log/syslog → sar → vmstat → iostat    │
│ （原因不明）   │ → journalctl -p err --since "..." → 以上链路逐一排查    │
└──────────────┴──────────────────────────────────────────────────────────┘
```

### 2.4 排查中最致命的五个认知偏差

在学会正确的排查方法之前，先了解最容易犯的错误——这些不是技术问题，而是思维问题。

```
认知偏差 1：锚定效应（Anchoring）
  "我看到第一个错误信息就认定是它导致的，忽略了其他线索。"
  → 解决：在形成假设之前，先收集至少三个独立的观察。

认知偏差 2：确认偏误（Confirmation Bias）
  "我只在找支持自己假设的证据，对反证视而不见。"
  → 解决：主动寻找能推翻你假设的证据。如果找不到反证，假设更可靠。

认知偏差 3：近期性偏差（Recency Bias）
  "上次遇到类似问题是因为 X，所以这次肯定也是 X。"
  → 解决：每个问题都从零开始观察——相似的症状可能有完全不同的根因。

认知偏差 4：鸵鸟效应（Ostrich Effect）
  "不敢看日志，因为日志太长太复杂，希望重启能解决问题。"
  → 解决：日志是你最好的朋友——`journalctl -p err --since "1 hour ago"` 只需要一秒钟。

认知偏差 5：过早优化（Premature Optimization）
  "还没有确定根因就开始改配置、调参数、加资源。"
  → 解决：在验证假设成立之前，不要执行任何修复操作。
```

## 3. 命令详解

### 3.1 启停链路：系统无法启动

系统启动失败是最让人紧张的故障——因为你的所有排查工具都在那个启动不了的系统中。本节从你看到的现象出发，逐步拆解每一层可能的问题。

#### 3.1.1 启动流程回顾与故障分段

在排查启动问题之前，你需要清楚地知道：正常启动经过了哪些阶段，你在哪个阶段卡住了。

```
电源接通
  │
  ▼
┌────────────────────────────────────────────────────────────┐
│ 阶段 0：BIOS/UEFI 固件                                      │
│ ─────────────────────────                                  │
│ 执行 POST（Power-On Self-Test，开机自检）                    │
│ 故障表现：黑屏、无任何输出、蜂鸣报警                          │
│ 关键词：硬件故障、内存松动、主板问题                          │
│ 你能做的：检查物理连接、进入 BIOS/UEFI 设置                   │
└──────────────┬─────────────────────────────────────────────┘
               ▼
┌────────────────────────────────────────────────────────────┐
│ 阶段 1：GRUB 引导加载程序（Boot Loader）                      │
│ ────────────────────────────────────────                    │
│ 加载内核（vmlinuz）和 initramfs 到内存                       │
│ 故障表现：grub> 提示符、grub rescue> 提示符、"No such device" │
│ 关键词：MBR/GPT 损坏、/boot 分区找不到、grub.cfg 丢失        │
│ 你能做的：grub> 命令行手动引导、grub rescue> 下 set/insmod    │
└──────────────┬─────────────────────────────────────────────┘
               ▼
┌────────────────────────────────────────────────────────────┐
│ 阶段 2：内核加载（Kernel Loading）                           │
│ ────────────────────────────────                            │
│ 内核解压、初始化硬件、挂载根文件系统                          │
│ 故障表现：Kernel panic、黑屏光标闪烁、启动卡住不继续          │
│ 关键词：initramfs 损坏、根分区 UUID 错误、缺少驱动模块        │
│ 你能做的：grub> 编辑内核参数、添加 init=/bin/bash 进入 Shell │
└──────────────┬─────────────────────────────────────────────┘
               ▼
┌────────────────────────────────────────────────────────────┐
│ 阶段 3：init / systemd 初始化                                │
│ ────────────────────────────────                            │
│ systemd 作为 PID 1 启动，激活所有 target 和 service           │
│ 故障表现：emergency mode、卡在某个服务启动、启动极慢          │
│ 关键词：/etc/fstab 错误、服务依赖死锁、文件系统损坏           │
│ 你能做的：emergency mode 下输入 root 密码进入 Shell、       │
│           journalctl -b 查看日志                            │
└──────────────┬─────────────────────────────────────────────┘
               ▼
┌────────────────────────────────────────────────────────────┐
│ 阶段 4：用户空间就绪                                         │
│ ────────────────                                           │
│ 登录提示符出现、显示管理器（GDM）启动                         │
│ 故障表现：登录后黑屏、网络不通、服务异常                       │
│ 关键词：用户配置错误、.bashrc/.profile 语法错误、驱动问题     │
└────────────────────────────────────────────────────────────┘
```

#### 3.1.2 场景 1：GRUB rescue 提示符

**现象：** 启动后显示：

```
error: no such device: <UUID>.
Entering rescue mode...
grub rescue>
```

**诊断思路：** GRUB 找到了自己的引导代码，但找不到 `/boot/grub` 目录（里面有 `grub.cfg` 和模块），或者找不到 `/boot` 分区所在的磁盘。

**排查步骤：**

```bash
# 步骤 1：查看 GRUB 知道的设备和分区
grub rescue> ls
# 输出示例：
# (hd0) (hd0,msdos1) (hd0,msdos2) (hd1) (hd1,msdos1)

# 步骤 2：逐个检查分区，找到 /boot 所在的分区
grub rescue> ls (hd0,msdos1)/
# 如果看到 vmlinuz-*, initrd.img-*, grub/ 等 → 这就是 /boot
# 如果看到 bin/, etc/, usr/ 等 → 这是根分区 /

# 步骤 3：找到后，设置 prefix 和 root
grub rescue> set prefix=(hd0,msdos1)/grub
grub rescue> set root=(hd0,msdos1)
grub rescue> insmod normal
grub rescue> normal
# 此时应该能看到正常的 GRUB 菜单了

# 步骤 4：如果 insmod normal 失败——模块路径不对
grub rescue> ls (hd0,msdos1)/grub/
# 确认 grub/ 目录下是否有 *.mod 文件（GRUB 模块）
# 如果没有——GRUB 安装不完整，需要从 Live CD 重新安装 GRUB
```

**进入系统后的修复：**

```bash
# 如果能进入系统（通过 grub> 手动引导进入），修复 GRUB：
sudo grub-install /dev/sda          # 重新安装到 MBR（BIOS 模式）
sudo update-grub                     # 重新生成 /boot/grub/grub.cfg

# 如果是 UEFI 系统：
sudo grub-install --target=x86_64-efi --efi-directory=/boot/efi
sudo update-grub
```

**常见原因总结：**

| 原因 | 症状 | 修复 |
|------|------|------|
| 磁盘顺序变化 | GRUB 找不到原分区 | `grub rescue>` 下手动引导，进入系统后 `update-grub` |
| 删除了/boot 分区 | `ls (hd0,X)/` 找不到 vmlinuz | 需要用 Live CD 恢复内核 |
| MBR/GPT 被覆盖 | GRUB 完全不出现 | 用 Live CD 启动，`grub-install` |
| /boot/grub/grub.cfg 丢失 | `grub>` 提示符（非 rescue） | `grub>` 下 `configfile (hd0,X)/grub/grub.cfg` |

#### 3.1.3 场景 2：Kernel Panic

**现象：** 启动过程中出现类似以下的输出后系统挂死：

```
Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(0,0)
```

**诊断思路：** 内核加载成功，但在尝试挂载根文件系统时失败了。最常见的原因：根分区 UUID 不匹配、initramfs 缺少必需的驱动模块（如磁盘控制器驱动）、或根文件系统损坏。

```bash
# 在 GRUB 菜单界面：
# 1. 按 'e' 编辑当前菜单项
# 2. 找到 linux 开头的行，大概长这样：
#    linux /vmlinuz-... root=UUID=xxxx-xxxx ro quiet splash
#
# 3. 移除 quiet splash（这样能看到更详细的内核输出）
# 4. 临时尝试不同的 root 参数：
#    - root=/dev/sda1 （用设备名替代 UUID）
#    - root=/dev/nvme0n1p2 （NVMe 磁盘）
#    - 如果是 LVM：root=/dev/mapper/ubuntu--vg-ubuntu--lv
#
# 5. 按 Ctrl+X 或 F10 启动

# 如果上述方法进入系统，永久修复 UUID：
sudo blkid | grep <你的根分区>
# 对比 /etc/fstab 和 /boot/grub/grub.cfg 中的 UUID 是否一致

# 如果 UUID 变了（比如因为克隆磁盘/分区），更新：
sudo update-grub
# update-grub 会自动探测当前分区的 UUID 并写入 grub.cfg

# 如果 initramfs 损坏或缺少驱动：
sudo update-initramfs -u -k all
```

**Kernel Panic 常见原因速查：**

```
"Unable to mount root fs"        →  根分区 UUID 错误或 initramfs 缺少驱动
"Attempted to kill init"         →  systemd/init 进程崩溃（极其罕见，通常是内存损坏）
"Out of memory"                  →  内核启动参数缺少 mem= 但实际内存不足
"Not syncing: ..." 后跟硬件信息  →  硬件故障（内存、主板）
```

#### 3.1.4 场景 3：Emergency Mode（紧急模式）

**现象：** 启动后进入紧急模式，显示：

```
You are in emergency mode. After logging in, type "journalctl -xb"
to view system logs, "systemctl reboot" to reboot,
or "exit" to continue bootup.
Give root password for maintenance
(or press Control-D to continue):
```

**诊断思路：** systemd 启动过程遇到了一个关键问题——最常见的是 `/etc/fstab` 中配置的分区无法挂载。systemd 让你进入紧急模式手动修复。

```bash
# 步骤 1：输入 root 密码进入 Shell

# 步骤 2：查看启动日志——这是最关键的一步
journalctl -xb | grep -E "error|fail|timed out" -i
# 或
journalctl -xb -p err
# 重点看红色的错误行——通常在启动日志的最后部分

# 步骤 3：检查 /etc/fstab 中的挂载点
cat /etc/fstab
# 逐一验证每个非注释行中配置的分区是否存在：
sudo blkid | grep <UUID>
# 或
lsblk -f

# 步骤 4：尝试手动挂载所有 fstab 条目——定位哪个分区有问题
sudo mount -a
# mount -a 会尝试挂载 fstab 中所有未挂载的分区
# 如果某个分区挂载失败——错误信息会告诉你具体是哪个

# 步骤 5：检查文件系统是否损坏
sudo fsck -n /dev/sdaX    # -n 只检查，不修复（安全）
# 如果发现错误：
sudo fsck -y /dev/sdaX    # -y 自动修复（会修改磁盘，谨慎使用）

# 步骤 6：如果是不需要的分区（如已移除的备份盘），注释掉对应行
sudo nano /etc/fstab
# 在问题行的行首添加 # 注释

# 步骤 7：如果是 swap 分区 UUID 变化
sudo blkid | grep swap
# 用新的 UUID 更新 /etc/fstab

# 步骤 8：修复后重启
systemctl reboot
# 或
reboot
```

**Emergency Mode 常见原因：**

| 原因 | journalctl 中的关键信息 | 修复 |
|------|----------------------|------|
| fstab 分区 UUID 变了 | `Timed out waiting for device /dev/disk/by-uuid/xxxx` | 更新 fstab 或 `update-grub` |
| 文件系统损坏 | `FS-Cache: Duplicate cookie detected` 或 fsck 报错 | `fsck -y /dev/sdXN` |
| 网络挂载（NFS）超时 | `mount.nfs: Connection timed out` | 在 fstab 中添加 `nofail` 选项 |
| 磁盘硬件故障 | `I/O error, dev sda` | 更换磁盘，从备份恢复 |
| 加密分区（LUKS）未解锁 | 等待密码输入的提示 | 输入 LUKS 密码 |

**emergency mode 下的常用操作速查：**

```bash
# 查看失败的服务
systemctl list-units --failed

# 查看详细的启动时间分析
systemd-analyze blame

# 查看启动的依赖链
systemd-analyze critical-chain

# 重新加载 systemd（修改 fstab 或 unit 文件后）
systemctl daemon-reload

# 查看所有挂载点状态
systemctl list-units --type=mount

# 如果有网络（emergency mode 通常不启动网络）
# 可以手动启动网络以便查找资料
systemctl start systemd-networkd
```

### 3.2 资源链路：磁盘空间满 / CPU 内存飙高

资源问题是最常见的运行时故障——系统在运行，但"不够用了"。

#### 3.2.1 磁盘空间满 —— 全链路排查

**快速判断：**

```bash
# 一秒钟确认是不是磁盘问题
df -h
# 如果任一挂载点的 Use% 接近 100%——问题确认
# 特别关注 /（根分区）和 /var（日志分区）
```

**完整排查链路：从大到小，逐层定位**

```
df -h                              ← 第 1 步：看哪个挂载点满了
    │
    ▼
du -sh <挂载点>/* 2>/dev/null      ← 第 2 步：看是哪个一级目录占用大
    │   | sort -rh | head -20
    ▼
du -sh <大目录>/* 2>/dev/null      ← 第 3 步：逐层深入
    │   | sort -rh | head -20        重复此步骤直到找到具体的大文件
    ▼
lsof | grep deleted                ← 第 4 步：检查"幽灵文件"
    │                                已删除但被进程占用的文件
    ▼
journalctl --disk-usage            ← 第 5 步：检查 journal 日志
journalctl --vacuum-size=500M        如果太大，清理
    │
    ▼
apt 缓存？内核包？docker 镜像？     ← 第 6 步：检查特定应用
du -sh /var/cache/apt/archives
dpkg -l | grep linux-image
docker system df
```

**详细操作步骤：**

```bash
# ===== 第 1 步：全局概览 =====
df -h
# 输出示例：
# Filesystem      Size  Used Avail Use% Mounted on
# /dev/sda2        98G   93G  0.0G 100% /          ← 根分区满了！
# /dev/sda1       511M  6.1M  505M   2% /boot/efi

# ===== 第 2 步：定位一级目录 =====
sudo du -sh /* 2>/dev/null | sort -rh | head -20
# 输出示例：
# 45G    /var         ← /var 最大！
# 12G    /usr
# 8.5G   /home
# 5.2G   /snap
# ...

# ===== 第 3 步：深入 /var =====
sudo du -sh /var/* 2>/dev/null | sort -rh | head -10
# 输出示例：
# 38G    /var/log     ← 日志占用了 38G！

# ===== 第 3 步（继续）：深入 /var/log =====
sudo du -sh /var/log/* 2>/dev/null | sort -rh | head -10
# 输出示例：
# 20G    /var/log/syslog
# 12G    /var/log/kern.log
# 5.2G   /var/log/journal
# ...

# ===== 找到罪魁祸首——大文件定位 =====
# 查找大于 100MB 的文件
sudo find /var/log -type f -size +100M -exec ls -lh {} \; | sort -k5 -rh

# 或者使用 ncdu（交互式磁盘使用分析器——TUI 界面，更方便）
sudo ncdu /var/log
# ncdu 的优势：
# - 用方向键在目录间导航
# - 按大小排序
# - 直接按 d 键删除选中文件
# - 按 ? 查看所有快捷键
```

**四种常见的"磁盘已满但找不到文件"的情况：**

```bash
# 情况 1：已删除但进程仍占用的文件（最常见的"隐形"占用）
# ─────────────────────────────────────────────────
# 场景：你删除了一个大日志文件，但 df 显示空间没有释放
# 原因：进程仍然持有该文件的文件描述符——数据在进程关闭前不会释放

# 检测：
sudo lsof 2>/dev/null | grep -i deleted | awk '{print $1, $2, $7}' | sort -u
# 或者更直观：
sudo lsof 2>/dev/null | grep deleted | awk '{sum+=$7} END {print sum/1024/1024 " MB 被幽灵文件占用"}'

# 典型案例输出：
# java      12345  root   10w   REG   8,2  8589934592  123456 /var/log/app.log (deleted)
# ↑ 这个文件已被删除，但 java (PID 12345) 仍然持有它——8GB 未释放！

# 修复：
# 方法 1：重启进程（推荐——但服务会短暂中断）
sudo systemctl restart <服务名>
# 方法 2：截断文件描述符（不中断进程——高级操作）
# : > /proc/12345/fd/10   # 清空该 fd 指向的内容
# 方法 3：发送信号让进程重新打开日志文件
# sudo kill -HUP 12345    # 并非所有进程都响应 HUP

# ─────────────────────────────────────────────────

# 情况 2：journal 日志过大
# ─────────────────────────
journalctl --disk-usage
# 输出示例：
# Archived and active journals take up 4.5G on disk.

# 限制 journal 大小：
sudo nano /etc/systemd/journald.conf
# 修改以下行：
# SystemMaxUse=500M
# SystemKeepFree=10G
# MaxFileSec=1week
sudo systemctl restart systemd-journald

# 立即清理：
journalctl --vacuum-size=500M     # 保留最近的 500MB
journalctl --vacuum-time=7d       # 保留最近 7 天

# ─────────────────────────────────────────────────

# 情况 3：/var/cache/apt/archives 中积累了大量 .deb 包
# ───────────────────────────────────────────────────────
du -sh /var/cache/apt/archives
# 清理：
sudo apt clean         # 删除所有已下载的包文件
sudo apt autoclean     # 只删除过时的包文件

# ─────────────────────────────────────────────────

# 情况 4：旧内核占用 /boot 分区
# ────────────────────────────────
df -h /boot
dpkg -l | grep -E 'linux-image|linux-headers' | awk '{print $2, $3}'

# 查看当前运行的内核：
uname -r

# 删除旧内核（保留当前和上一版本）：
sudo apt autoremove --purge
# 或者手动删除：
# sudo apt purge linux-image-5.15.0-XX-generic
```

**使用 ncdu 进行交互式排查（强烈推荐）：**

```bash
# ncdu 是终端下的交互式磁盘使用分析器——远比 du + sort 高效
sudo ncdu /

# 操作方式：
# ↑↓    ：在目录间移动
# Enter ：进入目录
# ←     ：返回上级目录
# d     ：删除选中的文件/目录（谨慎！）
# n     ：按名称排序
# s     ：按大小排序（默认）
# g     ：切换显示百分比/图形/两者
# ?     ：帮助
# q     ：退出

# 如果 ncdu 扫描 / 太慢（因为文件太多），先扫描一级目录：
sudo ncdu /var
sudo ncdu /home
```

#### 3.2.2 CPU/内存飙高 —— 全链路排查

**快速判断：**

```bash
# 一秒钟看清系统整体状态
top -bn1 | head -20
# 或
htop    # 交互式，按 F6 选择排序字段

# 关键指标：
# load average: 查看 1/5/15 分钟平均负载——高于 CPU 核心数就是过载
# %Cpu(s): us(用户态)、sy(内核态)、wa(I/O等待)、id(空闲)
# MiB Mem: total/free/used——关注 available 而非 free
```

**CPU 高排查链路：**

```
top / htop                         ← 第 1 步：找到消耗 CPU 的进程
    │
    ▼
ps aux --sort=-%cpu | head -20     ← 第 2 步：确认进程和启动参数
    │
    ▼
strace -c -p <PID>                 ← 第 3 步：统计时间花在哪些系统调用
    │  或
strace -p <PID> -e trace=all       ← 实时观察进程在做什么
    │
    ▼
perf top -p <PID>                  ← 第 4 步：找到热点函数（需要 perf 工具）
    │  （如果进程是 C/Go/Rust 等编译语言）
    │
    ▼
lsof -p <PID>                      ← 第 5 步：查看进程打开了哪些文件/连接
cat /proc/<PID>/status             ← 查看进程详细信息
```

**详细操作：**

```bash
# ===== 第 1 步：top 的常用交互 =====
top
# 运行时按键：
# 1      ：展开/折叠每个 CPU 核心的使用率
# P      ：按 CPU 使用率排序（shift+p）
# M      ：按内存使用率排序（shift+m）
# c      ：切换显示完整命令行
# k      ：终止进程（输入 PID 和信号）
# f      ：选择要显示的列
# W      ：保存当前配置到 ~/.toprc

# ===== 第 1 步（替代）：htop =====
htop
# htop 的优势：
# - 彩色显示，更直观
# - 鼠标支持
# - 可以水平/垂直滚动
# - F6 选择排序字段（PERCENT_CPU, PERCENT_MEM 等）
# - F9 发送信号给进程
# - F5 树状视图——看清父子进程关系
# - F3 搜索进程
# - F4 过滤进程

# ===== 第 2 步：ps 查看 CPU 消耗 TOP 10 =====
ps aux --sort=-%cpu | head -20
# 输出列：USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND

# 查看特定用户的进程：
ps -u www-data --sort=-%cpu

# ===== 第 3 步：strace 系统调用追踪 =====

# 选项 A：统计模式——看时间花在哪些系统调用上（推荐先做这个）
sudo strace -c -p 12345
# 等 10-30 秒后按 Ctrl+C，输出类似：
# % time     seconds  usecs/call     calls    errors syscall
# ------ ----------- ----------- --------- --------- ----------------
#  89.23    5.234567        5234      1000           futex
#   5.12    0.300123         300      1000           read
#   3.45    0.202345         202      1000       500 openat
# → 89% 的时间花在 futex 上——进程在频繁等待锁！

# 选项 B：实时追踪——看进程现在正在做什么
sudo strace -p 12345 -e trace=network
# 只看网络相关的系统调用

sudo strace -p 12345 -e trace=file
# 只看文件相关的系统调用

sudo strace -p 12345 -f -e trace=process
# -f：追踪子进程  -e trace=process：只看进程创建相关的调用

# 选项 C：追踪并限制输出速率
sudo strace -p 12345 -e trace=write -o /tmp/strace.out &
# -o：输出到文件  &：后台运行

# ===== 第 4 步：perf 热点分析 =====
# 注意：perf 需要 linux-tools 包
sudo perf top -p 12345
# 实时显示该进程最耗 CPU 的函数——适合长时间运行的编译型程序

# 采样 30 秒后生成报告：
sudo perf record -p 12345 -g -- sleep 30
sudo perf report
# -g：记录调用栈（Call Graph）——可以看到函数是谁调用的

# ===== 第 5 步：进程详细信息 =====
cat /proc/12345/status | grep -E "^(Name|State|VmRSS|VmSize|Threads|voluntary_ctxt_switches|nonvoluntary_ctxt_switches)"
# State: R(running), S(sleeping), D(uninterruptible sleep → I/O等待), Z(zombie)
# nonvoluntary_ctxt_switches 高 → 进程频繁被抢占，可能 CPU 确实不够

# 查看进程的环境变量：
cat /proc/12345/environ | tr '\0' '\n'

# 查看进程的当前工作目录：
ls -la /proc/12345/cwd

# 查看进程的打开文件描述符：
ls -la /proc/12345/fd/
```

**内存高排查链路：**

```bash
# ===== 第 1 步：整体内存概览 =====
free -h
# 关键理解：
# - "available" 才是真正可用的内存（而非 "free"）
# - Linux 会使用空闲内存做文件缓存（buffers/cache）——这是正常的
# - 只有当 "available" 很低时，才需要关注

# ===== 第 2 步：按内存使用排序的进程 =====
ps aux --sort=-%mem | head -20
# 或
top -o %MEM    # top 中按 O 然后选 mem

# ===== 第 3 步：查看特定进程的内存映射 =====
sudo cat /proc/<PID>/smaps | grep -E "^(Rss|Pss|Swap):" | awk '{sum+=$2} END {print sum " kB"}'
# Rss (Resident Set Size): 进程实际占用的物理内存
# Pss (Proportional Set Size): 分摊共享库后的比例内存（更准确）
# Swap: 被交换出去的内存

# 汇总所有进程的 PSS：
sudo cat /proc/*/smaps 2>/dev/null | grep ^Pss: | awk '{sum+=$2} END {print sum/1024 " MB"}'

# ===== 第 4 步：查看内存使用排名（使用 smem 工具） =====
# smem 可以更准确地报告内存使用（考虑共享库）
sudo apt install -y smem
smem -rs pss       # 按 PSS 排序
smem -rs uss       # 按 USS（Unique Set Size）排序——进程独占的内存

# ===== 第 5 步：查看 slab 缓存（内核数据结构占用） =====
cat /proc/meminfo | grep -E "^(Slab|SReclaimable|SUnreclaim):"
# Slab 过高可能意味着内核数据结构泄漏（如 dentry cache）

# 查看 slab 详情：
sudo slabtop
```

**I/O 等待高（`%wa` 高）排查：**

```bash
# I/O 等待（wa）高意味着 CPU 在等磁盘——不是 CPU 的问题，是磁盘慢

# 查看整体 I/O 情况：
iostat -x 1 5
# 关键列：
# %util   → 磁盘利用率（接近 100% 表示磁盘繁忙）
# await   → 平均 I/O 等待时间（毫秒）
# r/s, w/s → 每秒读写次数

# 找出哪些进程在大量 I/O：
sudo iotop -o
# -o：只显示正在做 I/O 的进程

# 用 pidstat 看进程级别的 I/O：
pidstat -d 1 5
# 输出列：kB_rd/s（每秒读取 KB）, kB_wr/s（每秒写入 KB）
```

### 3.3 网络链路：网络不通

网络故障的诊断原则是从底层到上层、从近到远，逐层排除。

**OSI 模型简化版排查层级：**

```
┌────────────────────────────────────────────────────────────┐
│ 第 7 层：应用层                                              │
│ ────────────────                                            │
│ 问题：服务监听了吗？配置对吗？                                 │
│ 命令：ss -tlnp, curl -v, systemctl status, 查看服务日志       │
├────────────────────────────────────────────────────────────┤
│ 第 4 层：传输层                                              │
│ ────────────────                                            │
│ 问题：端口可达吗？防火墙放行了吗？                             │
│ 命令：nc -zv, telnet, ss -tlnp, iptables -L, ufw status     │
├────────────────────────────────────────────────────────────┤
│ 第 3 层：网络层                                              │
│ ────────────────                                            │
│ 问题：路由正确吗？IP 包能到达目标吗？                          │
│ 命令：ping, traceroute, ip route, ip addr                   │
├────────────────────────────────────────────────────────────┤
│ 第 2 层：数据链路层                                          │
│ ────────────────────                                        │
│ 问题：网卡链路状态正常吗？ARP 解析正常吗？                     │
│ 命令：ip link, ethtool, arp -n                              │
├────────────────────────────────────────────────────────────┤
│ 第 1 层：物理层                                              │
│ ──────────────                                              │
│ 问题：网线插着吗？网卡灯亮吗？                                 │
│ 检查：物理连接、网卡指示灯                                     │
└────────────────────────────────────────────────────────────┘
```

**完整排查链路：**

```bash
# ===== 第 1 步：确认网卡链路状态 =====
ip link show
# 关注 UP 和 LOWER_UP 标志：
# <BROADCAST,MULTICAST,UP,LOWER_UP>  → 正常（链路建立）
# <BROADCAST,MULTICAST>              → 链路未建立（网线未插/交换机端口关闭）
# <NO-CARRIER,BROADCAST,MULTICAST,UP> → 无载波信号

# 更详细的链路信息：
sudo ethtool <网卡名>
# 关键字段：
# Link detected: yes  → 物理链路正常
# Speed: 1000Mb/s     → 协商速率

# ===== 第 2 步：确认 IP 地址配置 =====
ip addr show
# 确认：
# 1. 网卡有 IP 地址吗？（inet ...）
# 2. IP 地址在正确的子网段吗？
# 3. 如果是 DHCP——获取到地址了吗？

# 如果是 DHCP 没有获取到地址：
sudo dhclient -v <网卡名>     # 手动触发 DHCP 请求
# 或
sudo networkctl renew <网卡名>  # systemd-networkd 管理时

# ===== 第 3 步：确认路由表 =====
ip route show
# 确认 default route（默认网关）存在：
# default via 192.168.1.1 dev eth0 proto dhcp src 192.168.1.100 metric 100

# 如果没有默认路由：
sudo ip route add default via <网关IP> dev <网卡名>

# ===== 第 4 步：测试本地网络连通性 =====
# 测试网关
ping -c 4 <网关IP>
# 通了 → 本地网络没问题，继续向上排查
# 不通 → 局域网有问题（交换机/VLAN/防火墙/网线）
#   检查 ARP：
ip neigh show   # 确认网关的 MAC 地址是否解析成功

# ===== 第 5 步：测试互联网连通性 =====
ping -c 4 8.8.8.8
# 通了 → IP 层可达
# 不通 → 路由或上游防火墙问题
#   排查路由：
traceroute -n 8.8.8.8
#   看数据包在哪一跳消失了

# ===== 第 6 步：测试 DNS 解析 =====
dig google.com +short
# 或
nslookup google.com
# 解析失败：
#   - 先确认 /etc/resolv.conf 中的 DNS 服务器：
cat /etc/resolv.conf
#   - 测试能否连通 DNS 服务器：
ping -c 2 <DNS服务器IP>
#   - 手动用特定 DNS 测试：
dig @8.8.8.8 google.com +short
#   - 如果 systemd-resolved 在管理 DNS：
resolvectl status

# ===== 第 7 步：检查防火墙 =====
# ufw：
sudo ufw status verbose
# 如果没有放行需要的端口：
sudo ufw allow 80/tcp

# iptables/nftables：
sudo iptables -L -n -v          # 查看所有规则及其命中次数
sudo iptables -L INPUT -n -v    # 只看 INPUT 链
# 注意：默认策略是 DROP 还是 ACCEPT？
sudo iptables -S                # 以"规则生成命令"格式输出

# ===== 第 8 步：确认服务是否在监听 =====
ss -tlnp
# 确认：
# 1. 服务是否监听在正确的端口？
# 2. 监听地址是 0.0.0.0（所有接口）还是 127.0.0.1（仅本地）？
# 3. 如果绑定在 127.0.0.1——外部肯定连不上

# ===== 第 9 步：抓包分析 =====
# 如果以上步骤都正常但就是不通——抓包：
sudo tcpdump -i eth0 -nn port 80 -w /tmp/capture.pcap
# -i eth0：监听的网卡
# -nn：不解析主机名和端口名（更快）
# port 80：只捕获 80 端口的数据包
# -w：写入文件（可用 Wireshark 分析）

# 简单实时查看：
sudo tcpdump -i eth0 -nn port 80 -A
# -A：以 ASCII 显示包内容（方便查看 HTTP 请求/响应）

# 查看 TCP 握手过程：
sudo tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin) != 0'
# 只显示 SYN 和 FIN 包——看清连接的建立和关闭
```

**网络排查的黄金组合 —— 一条命令快速分诊：**

```bash
# 这个组合能在 10 秒内定位网络问题的层级：
echo "=== IP 配置 ===" && \
ip -br addr && \
echo "" && \
echo "=== 默认路由 ===" && \
ip route | grep default && \
echo "" && \
echo "=== 网关连通 ===" && \
ping -c 2 -W 1 $(ip route | grep default | awk '{print $3}') 2>&1 && \
echo "" && \
echo "=== DNS 测试 ===" && \
dig +short google.com 2>&1 && \
echo "" && \
echo "=== 监听端口 ===" && \
ss -tlnp | head -20
```

### 3.4 服务链路：服务无法启动

**五步诊断法：**

```
步骤 1：systemctl status <服务>     ← 看状态、PID、最近的日志
步骤 2：journalctl -u <服务> -xe    ← 看详细错误日志
步骤 3：<服务> configtest           ← 检查配置文件语法
步骤 4：ss -tlnp \| grep <端口>      ← 检查端口是否被占用
步骤 5：strace -f <启动命令>        ← 追踪启动过程
```

**详细操作：**

```bash
# ===== 步骤 1：查看服务状态 =====
systemctl status nginx
# 关注以下信息：
# - Loaded: 服务 unit 文件路径，是否 enabled
# - Active: active (running) / inactive (dead) / failed / activating
# - Main PID: 主进程 PID
# - 最后几行日志（通常包含失败原因的直接线索）

# 查看所有失败的服务：
systemctl list-units --failed
# 输出示例：
# UNIT          LOAD   ACTIVE SUB    DESCRIPTION
# nginx.service loaded failed failed nginx - high performance web server

# ===== 步骤 2：查看详细日志 =====
journalctl -u nginx --since "5 minutes ago" -xe
# -x：显示编录（catalog）信息（帮助文本）
# -e：跳到末尾
# 如果服务启动很快失败：
journalctl -u nginx --since "$(systemctl show -p ActiveEnterTimestamp nginx | cut -d= -f2)"

# 查看所有错误级别的日志：
journalctl -u nginx -p err

# 实时跟踪（复现问题时使用）：
journalctl -u nginx -f

# ===== 步骤 3：检查配置文件语法 =====
# 大多数主流服务支持配置语法检查：
sudo nginx -t                          # nginx
sudo apache2ctl configtest             # Apache
sudo sshd -t                           # SSH Server
sudo postfix check                     # Postfix
sudo named-checkconf                   # BIND DNS
sudo mysqld --validate-config          # MySQL 8.0+

# 如果是 systemd unit 文件的问题：
systemd-analyze verify /etc/systemd/system/<服务>.service

# ===== 步骤 4：检查端口占用 =====
ss -tlnp | grep <端口号>
# 如果端口已被占用——冲突是启动失败的原因
# 解决方法：
# - 修改服务的监听端口
# - 停止占用端口的进程

# 查看谁在监听这个端口：
sudo ss -tlnp | grep :80
# LISTEN  0  128  0.0.0.0:80  0.0.0.0:*  users:(("nginx",pid=1234,fd=6))

# ===== 步骤 5：追踪启动过程（高级） =====
# 当以上步骤都找不到原因时：
sudo strace -f -o /tmp/nginx.strace nginx -g 'daemon off;'
# -f：追踪子进程（fork/vfork/clone 创建的子进程也会被追踪）
# -o：输出到文件（避免和程序的输出混淆）
# 然后搜索错误：
grep -E "ENOENT|EACCES|EPERM" /tmp/nginx.strace
# ENOENT  → 文件或目录不存在
# EACCES  → 权限不足
# EPERM   → 操作不被允许

# 一键查看 strace 中的所有错误：
grep -oE '[A-Z]+\(.*\)\s+= -1 [A-Z]+' /tmp/nginx.strace | sort | uniq -c | sort -rn
# 输出每个失败系统调用的计数
```

**常见服务启动失败的根因速查：**

| 服务 | 最常见失败原因 | 快速检查命令 |
|------|--------------|-------------|
| nginx | 端口 80 被占用 / 配置语法错误 | `sudo ss -tlnp \| grep :80` / `sudo nginx -t` |
| Apache | 同上 + 模块未启用 | `sudo apache2ctl configtest` |
| MySQL/MariaDB | 数据目录权限 / 磁盘满 | `sudo ls -la /var/lib/mysql` / `df -h` |
| SSH | 配置语法错误 / 端口冲突 | `sudo sshd -t` / `sudo ss -tlnp \| grep :22` |
| PHP-FPM | 配置中 sock 文件路径不存在 | `sudo ls -la /run/php/` |
| Docker | 依赖 containerd 未启动 | `sudo systemctl status containerd` |
| cron | crontab 语法错误 | `crontab -l \| grep -v '^#'` |
| systemd unit | unit 文件语法错误 / 依赖缺失 | `systemd-analyze verify <unit>` |

**服务启动了但功能不正常（如 502/503 错误）：**

```bash
# 这种情况最棘手——进程在运行，端口在监听，但返回错误

# 步骤 1：检查服务的错误日志（不是系统日志）
sudo tail -100 /var/log/nginx/error.log

# 步骤 2：查看服务的资源使用
top -p $(pgrep -d',' nginx)

# 步骤 3：测试服务的具体功能
# 对于 Web 服务——直接 curl 看响应
curl -v http://localhost 2>&1 | head -50

# 步骤 4：检查反向代理/后端连接
# nginx → PHP-FPM：确认 sock 文件路径和权限
ls -la /run/php/php8.3-fpm.sock
# nginx → 后端应用：确认 upstream 服务器可达
nc -zv <后端IP> <后端端口>

# 步骤 5：检查文件描述符限制
cat /proc/$(pgrep nginx | head -1)/limits | grep "open files"
# 如果达到了 limit——服务无法接受新连接
```

### 3.5 权限链路：Permission Denied

权限问题可能是排查频率最高的故障——几乎每天都会遇到。"Permission denied" 这个错误信息虽然简单，但根因可能藏在用户、文件权限、ACL、AppArmor、sudo 配置等各个层面。

**完整排查链路：**

```
步骤 1：id                                ← 确认"我是谁"
步骤 2：ls -la <文件>                      ← 确认文件的基本权限
步骤 3：namei -l <绝对路径>                ← 检查路径上所有目录的执行权限
步骤 4：getfacl <文件>                     ← 检查 ACL（Access Control List）
步骤 5：ls -laZ <文件> (SELinux)           ← 检查安全上下文（Ubuntu 默认不启用 SELinux）
   或  aa-status + /var/log/syslog         ← 检查 AppArmor（Ubuntu 强制访问控制）
步骤 6：sudo -l                            ← 检查 sudo 权限
步骤 7：cat /etc/passwd \| grep <用户>     ← 检查用户账号状态
   或  passwd -S <用户>                    ← 检查账户是否锁定/过期
```

**详细操作：**

```bash
# ===== 步骤 1：确认身份 =====
id
# 输出示例：
# uid=1000(user) gid=1000(user) groups=1000(user),4(adm),27(sudo),999(docker)
# 关注：
# - 你的 uid 是什么？（root 是 0）
# - 你在哪些组里？
# - 你是否在 sudo 组？

# 查看其他用户的信息：
id www-data

# 临时切换到 root（如果你在 sudo 组）：
sudo -i

# ===== 步骤 2：文件基本权限 =====
ls -la /path/to/file
# -rw-r--r--  1 root  www-data  4096 Jul 30 10:00 config.ini
# 解读：
# - 类型（第一位）：- 普通文件, d 目录, l 符号链接
# - 权限（后九位）：rw- r-- r-- = 所有者可读写, 组只读, 其他人只读
# - 所有者：root
# - 所属组：www-data

# 记住：
# 读文件 → 需要文件自身的 r 权限
# 写文件 → 需要文件自身的 w 权限
# 执行文件（脚本/二进制） → 需要文件自身的 x 权限
# 进入目录（cd） → 需要目录的 x 权限
# 列出目录内容（ls） → 需要目录的 r 权限
# 在目录中创建/删除文件 → 需要目录的 w 权限

# ===== 步骤 3：整个路径的权限检查 =====
# 最关键也最容易忽略的排查！
namei -l /var/www/html/index.html
# 输出示例：
# f: /var/www/html/index.html
# drwxr-xr-x root     root     /
# drwxr-xr-x root     root     var
# drwxr-x--- root     www-data www     ← /var/www 没有其他人的 x 权限！
# drwxr-xr-x www-data www-data html
# -rw-r--r-- www-data www-data index.html
# ↑ 即使 index.html 的权限正确（644），因为你不在 www-data 组，
#   你根本无法进入 /var/www 目录——namei 一目了然

# 修复路径权限：
# 给目录添加其他用户的执行权限（只加 x，不加 r——安全）
sudo chmod o+x /var/www

# ===== 步骤 4：ACL 权限 =====
# 标准 rwx 权限模型之外，文件可能还有 ACL 条目
getfacl /path/to/file
# 输出示例：
# # file: /path/to/file
# # owner: root
# # group: root
# user::rw-
# user:alice:r--       ← ACL：用户 alice 有读权限
# group::r--
# mask::r--
# other::---

# 设置 ACL：
setfacl -m u:alice:rw /path/to/file     # 给 alice 读写权限
setfacl -m g:developers:r /path/to/file # 给 developers 组读权限
setfacl -x u:alice /path/to/file        # 移除 alice 的 ACL

# 目录的默认 ACL（新创建的文件/子目录自动继承）：
setfacl -m d:g:developers:rwx /shared/

# ls 输出中有 "+" 号表示有 ACL：
# -rw-r--r--+ 1 root root ...  ← 注意那个 "+" 号

# ===== 步骤 5：AppArmor 强制访问控制 =====
# Ubuntu 使用 AppArmor（而非 SELinux）作为强制访问控制
sudo aa-status
# 关注：
# - 哪些 profile 处于 enforce mode（强制模式——会真正拦截）
# - 哪些 profile 处于 complain mode（抱怨模式——只记录不拦截）

# 如果怀疑 AppArmor 在拦截：
sudo tail -50 /var/log/syslog | grep -i apparmor
# 或
sudo journalctl -k | grep -i apparmor
# 看到 "apparmor="DENIED"" 就是 AppArmor 在拦截

# 临时禁用某个 profile（排查用——确认是不是 AppArmor 的问题）：
sudo aa-complain /etc/apparmor.d/<profile>
# 或
sudo aa-disable /etc/apparmor.d/<profile>

# 重新启用：
sudo aa-enforce /etc/apparmor.d/<profile>

# 查看某个进程的 AppArmor 状态：
cat /proc/<PID>/attr/current
# 输出如：nginx (enforce) 或 unconfined

# ===== 步骤 6：sudo 权限 =====
sudo -l
# 列出当前用户能通过 sudo 执行的命令
# 输出示例：
# User user may run the following commands on myserver:
#     (ALL : ALL) ALL        ← 可以执行所有命令
#     (root) NOPASSWD: /usr/bin/systemctl restart nginx  ← 只能重启 nginx

# 如果输出 "user is not in the sudoers file"：
# 1. 确认你在 sudo 组吗？
groups | grep -o sudo
# 2. 检查 /etc/sudoers（需要 root 权限——如果你已经不在 sudo 组，需要物理访问或 Live CD）
#    pkexec visudo  （如果 pkexec 可用）
#    或重启进入 recovery mode 后用 root shell 修复
# 3. 把自己加回 sudo 组：
#    usermod -aG sudo <用户名>

# ===== 步骤 7：用户账号状态 =====
passwd -S <用户名>
# 输出示例：
# user P 07/30/2024 0 99999 7 -1
# 解读：P(password set), L(locked), NP(no password)

# 账号被锁定：
sudo passwd -u <用户名>    # 解锁
# 密码过期：
sudo chage -l <用户名>     # 查看密码过期信息

# 用户的 shell 是不是 /bin/false 或 /usr/sbin/nologin？
cat /etc/passwd | grep <用户名>
# 如果 shell 是 /usr/sbin/nologin——该用户不能登录
```

**权限问题常见根因速查：**

| 错误信息 | 最可能的原因 | 排查命令 |
|---------|-------------|---------|
| `Permission denied` 操作文件 | 文件权限/所有者不对 | `ls -la <文件>` |
| `Permission denied` cd 进目录 | 目录缺少 x 权限 | `namei -l <绝对路径>` |
| `Permission denied` 执行脚本 | 脚本没有 x 权限或 shebang 不对 | `ls -la <脚本>` + `file <脚本>` |
| `sudo: ... not in sudoers` | 用户不在 sudo 组 | `groups` |
| `su: Authentication failure` | 密码错误 / root 账户锁定 | `sudo passwd -S root` |
| `cannot create file` | 目录没有 w 权限 | `ls -la <目录>` |
| 服务能启动但功能受限 | AppArmor profile 限制 | `sudo aa-status` + `dmesg` |
| SSH 密钥登录失败 | `~/.ssh` 或 `authorized_keys` 权限过于宽松 | `ls -la ~/.ssh/` |
| `Unable to write to ...` | 磁盘只读挂载 / 磁盘满 | `mount \| grep <挂载点>` + `df -h` |

### 练习 1：磁盘满 —— 定位并清理

**场景：** 你接到报警，服务器的根分区（`/`）磁盘使用率达到 98%。你 SSH 登录到服务器。

**任务：**
1. 使用 `df -h` 确认根分区确实接近满
2. 使用 `du` 逐层定位到占用空间最多的目录和文件
3. 检查是否有"已删除但未释放"的文件（幽灵文件）
4. 检查 journal 日志占用
5. 写出清理方案

**参考答案：**

```bash
# 1. 确认磁盘状态
df -h /
# 假设输出：/dev/sda2  98G  93G  1.0G  99% /

# 2. 逐层定位
# 第一层：看哪个一级目录最占空间
sudo du -sh /* 2>/dev/null | sort -rh | head -10
# 假设输出：
# 45G    /var        ← 嫌疑最大
# 12G    /usr
# 8.5G   /home
# ...

# 第二层：深入 /var
sudo du -sh /var/* 2>/dev/null | sort -rh | head -10
# 假设输出：
# 38G    /var/log    ← 日志
# 3.2G   /var/cache
# 2.1G   /var/lib
# ...

# 第三层：深入 /var/log
sudo du -sh /var/log/* 2>/dev/null | sort -rh | head -10
# 假设输出：
# 20G    /var/log/syslog
# 12G    /var/log/nginx
# 5.2G   /var/log/journal
# ...

# 第四层：找出具体的大文件
sudo find /var/log -type f -size +500M -exec ls -lh {} \;
# 假设输出：
# -rw-r----- 1 syslog adm 20G Jul 30 03:00 /var/log/syslog
# -rw-r----- 1 syslog adm 12G Jul 15 00:00 /var/log/syslog.1
# -rw-r----- 1 root   adm 8.5G Jul 20 00:00 /var/log/nginx/access.log

# 3. 检查幽灵文件
sudo lsof 2>/dev/null | grep deleted | awk '{printf "PID=%-8s CMD=%-15s SIZE=%s\n", $2, $1, $7}' | sort -u
# 如果有输出——那些就是被进程占用但已删除的文件

# 4. 检查 journal
journalctl --disk-usage
# 假设输出：Archived and active journals take up 5.2G on disk.

# 5. 清理方案
# 方案 A：清理旧日志（保留最近的）
sudo journalctl --vacuum-size=500M
# 方案 B：清理旧的 syslog 归档
sudo rm /var/log/syslog.1
# 方案 C：截断当前 syslog（保留进程的写入）
sudo truncate -s 0 /var/log/syslog
# 方案 D：配置日志轮替防止复发
# 检查 /etc/logrotate.d/ 中的配置
# 方案 E：清理 apt 缓存
sudo apt clean
# 方案 F：清理旧内核
sudo apt autoremove --purge

# 验证清理效果
df -h /
```

### 练习 2：CPU 飙高 —— 抓到元凶

**场景：** `top` 显示 CPU 使用率持续 95% 以上，`load average` 达到 8.0（服务器是 4 核）。你需要找到消耗 CPU 的进程并判断它是正常业务还是异常行为。

**任务：**
1. 使用 `top` / `htop` 找到 CPU 使用率最高的进程
2. 获取该进程的详细信息（完整命令行、工作目录、环境变量）
3. 使用 `strace` 分析该进程在做什么
4. 判断是正常业务负载还是异常（死循环、攻击、配置错误）
5. 如果是异常——写出应急处理方案

**参考答案：**

```bash
# 1. 找到 CPU 最高的进程
# 方法一：top 中按 P（大写）按 CPU 排序
top
# 假设看到：PID 20456, 进程名 php, CPU 使用 96%

# 方法二：ps 一次性输出
ps aux --sort=-%cpu | head -5
# USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
# www-data 20456 96.2  2.1 450000 88000 ?        R    02:30  45:30 php-fpm: pool www

# 2. 获取进程详细信息
# 完整命令行：
cat /proc/20456/cmdline | tr '\0' ' '
# 或
ps -fp 20456

# 工作目录：
sudo ls -la /proc/20456/cwd
# 如果指向某个网站目录——可能是某个 PHP 脚本在死循环

# 环境变量：
cat /proc/20456/environ | tr '\0' '\n' | grep -E "SCRIPT_FILENAME|REQUEST_URI|HTTP_HOST"
# 如果能找到 SCRIPT_FILENAME——你就知道是哪个脚本在运行

# 3. strace 分析
sudo strace -c -p 20456
# 等 10 秒后 Ctrl+C，看统计：
# 假设输出显示 read() 和 write() 调用极多：
# % time     seconds  usecs/call     calls    errors syscall
# ------ ----------- ----------- --------- --------- ----------------
#  45.23    4.523456        4523      1000           read
#  42.17    4.217890        4217      1000           write

# 进一步查看 read/write 的详情：
sudo strace -p 20456 -e trace=read,write 2>&1 | head -20
# 如果看到大量小数据块读写——可能是密集的文件操作或网络 I/O

# 或用 strace 看文件操作：
sudo strace -p 20456 -e trace=open,openat,stat 2>&1 | head -30

# 4. 判断根因
# 查看是否是最近才出现的：
journalctl -u php8.3-fpm --since "1 hour ago" -p warning | tail -20

# 检查是否被大量请求打满：
# 查看 PHP-FPM 的慢日志（slow log）：
sudo grep -c "script_filename" /var/log/php8.3-fpm.log 2>/dev/null
# 或者查看 nginx 的访问日志频率：
sudo tail -1000 /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head -10
# 如果某个 IP 请求量极高——可能是攻击或爬虫

# 5. 应急处理
# 如果是某个 PHP 脚本死循环：
# 方案 A：重启 PHP-FPM 进程池
sudo systemctl restart php8.3-fpm
# 方案 B：只终止问题进程
sudo kill 20456
# 方案 C：如果是恶意请求——封禁 IP
sudo ufw deny from <攻击IP>
# 方案 D：降低 PHP 脚本执行时间上限
# 编辑 /etc/php/8.3/fpm/pool.d/www.conf
# php_admin_value[max_execution_time] = 30
sudo systemctl reload php8.3-fpm
```

### 练习 3：网络不通 —— 逐层诊断

**场景：** 你的服务器突然无法访问外部 API (`api.example.com:443`)，但本地服务都正常运行。应用日志显示 `Connection timed out`。

**任务：**
1. 按从底层到上层的顺序，逐步排查
2. 判断问题出在本地、局域网、ISP 还是目标服务器
3. 使用 `tcpdump` 确认是否有数据包发出
4. 写出根因判断和解决方案

**参考答案：**

```bash
# 1. 确认网卡链路和 IP 配置
ip link show <网卡名>
ip addr show <网卡名>
# 预期：UP + LOWER_UP, 有 IP 地址

# 2. 确认默认路由
ip route | grep default
# 确认网关正常

# 3. 测试网关连通性
ping -c 4 $(ip route | grep default | awk '{print $3}')
# 通了 → 局域网 OK

# 4. 测试互联网连通性
ping -c 4 8.8.8.8
# 通了 → 互联网可达，问题可能在 DNS 或目标服务器

# 5. 测试 DNS
dig api.example.com +short
# 或者直接查 DNS 服务器
dig @8.8.8.8 api.example.com +short
# 如果解析成功 → DNS 不是问题

# 6. 测试目标端口可达性
nc -zv api.example.com 443
# Connection timed out → 端口不可达

# 7. 路由追踪
traceroute -n api.example.com
# 看数据包在哪一跳消失
# 如果在本机之后的第一跳就消失了 → 问题在网关/防火墙
# 如果到了某个公网节点后消失 → 问题在上游 ISP 或目标服务器

# 8. 抓包确认
sudo tcpdump -i <网卡名> -nn host api.example.com and port 443
# 在另一个终端执行：
curl -v --connect-timeout 5 https://api.example.com 2>&1
# 如果 tcpdump 能看到 SYN 包发出但没有 SYN-ACK 回来 → 上行通畅，对端或中间防火墙丢弃
# 如果 tcpdump 什么都看不到 → 本地防火墙拦截了出口流量

# 9. 检查本地防火墙出站规则
sudo ufw status verbose
sudo iptables -L OUTPUT -n -v
# 是否有拒绝出站到 443 的规则？

# 10. 根因判断
# - 如果 ping 8.8.8.8 通但 api.example.com 不通 → 目标服务器可能宕机或封锁了你的 IP
# - 如果 traceroute 在某个节点后全部超时 → 该节点或之后的路由器有问题
# - 如果 tcpdump 看不到发出的包 → 本地防火墙拦截
# - 如果看到发出的包但没回包 → 中间防火墙或目标防火墙

# 解决方案：
# 本地防火墙问题 → 添加出站规则
# 目标服务器问题 → 联系对方管理员，或切换到备用 API
# 路由问题 → 如果是云环境，检查 VPC/安全组/路由表配置
```

### 练习 5：Permission Denied —— 全链路排查

**场景：** 作为用户 `deploy`，你试图读取 `/var/www/app/.env` 文件，但收到 `Permission denied`。你需要排查整个权限链路。

**任务：**
1. 确认 `deploy` 用户的身份和组
2. 检查文件的权限和所有者
3. 使用 `namei -l` 检查路径上每一级目录的权限
4. 检查是否有 ACL
5. 检查 AppArmor 是否在拦截
6. 修复权限问题（确保最小权限原则）

**参考答案：**

```bash
# 1. 确认身份
id deploy
# uid=1001(deploy) gid=1001(deploy) groups=1001(deploy),1002(developers)

# 2. 检查文件权限
ls -la /var/www/app/.env
# -rw-r----- 1 www-data www-data 256 Jul 30 10:00 /var/www/app/.env
# 文件所有者：www-data，所属组：www-data，权限：640
# deploy 既不是 www-data，也不在 www-data 组 → 没有读权限

# 3. 全路径排查（即使改了文件权限可能还不够！）
namei -l /var/www/app/.env
# 输出：
# drwxr-xr-x root     root     /
# drwxr-xr-x root     root     var
# drwxr-x--- root     www-data www      ← 目录 /var/www 只有 www-data 组能进入！
# drwxr-xr-x www-data www-data app       ← 目录 /var/www/app 也是 www-data 组能进入
# -rw-r----- www-data www-data .env
# 问题在于：deploy 不在 www-data 组，连 /var/www 都进不去！

# 4. 检查 ACL
getfacl /var/www
getfacl /var/www/app
getfacl /var/www/app/.env
# 如果没有 "+" 号，说明没有额外的 ACL

# 5. 检查 AppArmor
sudo aa-status | grep -i "var/www"
# 如果输出相关 profile → 查看具体限制
sudo journalctl -k | grep -i apparmor | grep -i denied

# 6. 修复方案（最小权限原则）
# 方案 A：如果 deploy 需要常规访问——加入 www-data 组
sudo usermod -aG www-data deploy
# deploy 需要重新登录才能生效

# 方案 B：如果只需要读取 .env 文件——使用 ACL 只给这一个文件加权限
# 首先需要让 deploy 能进入路径上的目录：
sudo setfacl -m u:deploy:x /var/www
sudo setfacl -m u:deploy:x /var/www/app
# 然后给文件加读权限：
sudo setfacl -m u:deploy:r /var/www/app/.env

# 验证：
sudo -u deploy cat /var/www/app/.env
# 应该能成功读取

# 方案 C：使用 sudo（如果 deploy 有 sudo 权限）
# 在 /etc/sudoers 中添加：
# deploy ALL=(www-data) NOPASSWD: /bin/cat /var/www/app/.env
# 然后：
# sudo -u www-data cat /var/www/app/.env
```

### 练习 6：综合场景 —— 凌晨告警

**场景：** 凌晨 3 点，你收到三条告警：
1. "服务器 web-01 CPU 使用率超过 95%，持续 15 分钟"
2. "nginx 返回 502 错误率超过 10%"
3. "磁盘 I/O 延迟超过 200ms"

你 SSH 登录服务器，`uptime` 显示 `load average: 24.5, 18.2, 10.1`（8 核 CPU）。

**任务：**
1. 列出你的排查顺序（先查什么，后查什么，为什么）
2. 针对每个线索给出具体的排查命令
3. 判断可能的根因（给出 2-3 个假设并验证）
4. 写出应急处理步骤
5. 写出事后排查方向（防止复发）

**参考答案：**

```bash
# ===== 第 1 步：快速分诊（1 分钟内） =====
# 先获取系统整体状态——不要急于跳到细节

uptime                      # 确认负载趋势
free -h                     # 内存压力
df -h /                     # 磁盘空间（I/O 告警可能与磁盘满有关）
df -i /                     # inode 使用率

# 假设输出：
# load average: 24.5, 18.2, 10.1  ← 极高，8核的正常值应 < 8
# free: available 还有 4GB        ← 内存不是主要问题
# df -h /: 使用 95%               ← 磁盘接近满了！
# df -i /: 使用 12%               ← inode 不是问题

# ===== 第 2 步：分析 CPU 消耗（2 分钟） =====
# 找到消耗 CPU 的进程
ps aux --sort=-%cpu | head -15
# 假设输出显示：
# www-data  4567 45.2  ... php-fpm
# www-data  4568 42.1  ... php-fpm
# www-data  4569 38.7  ... php-fpm
# → 多个 PHP-FPM 进程占用极高 CPU

# 查看 PHP-FPM 进程数
pgrep -c php-fpm
# 假设输出：48（8核服务器，48个 PHP worker —— 过多！）

# 检查 PHP-FPM 进程状态：
sudo strace -c -p 4567
# 等 10 秒输出：
# 89% 时间在 read()/write() → 大量 I/O 操作

# ===== 第 3 步：分析 I/O（2 分钟） =====
# 查看磁盘 I/O 状况
iostat -x 1 3
# %util 接近 100% → 磁盘确实繁忙

# 找到产生 I/O 的进程
sudo iotop -bon1 | head -15
# 假设输出显示 php-fpm 进程在大量写入 /var/log/php/slow.log

# 也看看 mysql：
sudo iotop -bon1 | grep mysql
# 如果 mysql 也在大量读写 → 数据库可能是根因

# ===== 第 4 步：分析 502 原因（2 分钟） =====
# 检查 PHP-FPM 状态
systemctl status php8.3-fpm

# 查看 PHP-FPM 错误日志
sudo tail -50 /var/log/php8.3-fpm.log | grep -E "error|warning|max_children"

# 假设看到：
# WARNING: [pool www] server reached pm.max_children setting (50),
#          consider raising it
# WARNING: [pool www] child 4567 exited on signal 9 (SIGKILL)
#          after 60.123456 seconds

# → PHP-FPM 子进程数达到上限，新请求被拒绝 → nginx 返回 502

# ===== 第 5 步：关联时间线和根因假设 =====
# 查看 PHP 慢日志——哪类请求最慢？
sudo tail -100 /var/log/php/slow.log 2>/dev/null
# 给定时看有没有规律：
# 假设大量请求集中在 /api/search?q=<某个复杂查询>
# → 某个搜索请求引发了慢查询，消耗了大量 PHP worker

# 查看数据库慢查询
# MySQL 慢查询日志：
sudo tail -50 /var/log/mysql/slow.log 2>/dev/null
# 或当前正在执行的查询：
sudo mysql -e "SHOW FULL PROCESSLIST;"
# 如果有长时间运行的 SELECT——根因确认：
# 某条 SQL 查询没有索引，全表扫描 → PHP 进程等待数据库 →
# worker 被占满 → 新请求 502 → CPU 和 I/O 飙升

# ===== 第 6 步：根因判断 =====
# 最可能的根因：数据库慢查询导致 PHP worker 阻塞
# 证据链：
# 1. CPU 高 → 大量 PHP worker 在运行（不是死循环）
# 2. I/O 高 → 数据库全表扫描产生大量磁盘读取
# 3. 502 高 → PHP-FPM worker 全被占满，新请求被拒绝
# 4. 磁盘渐满 → MySQL binlog 或 PHP 日志疯长
# 时间线关联：凌晨 2:45 左右开始 → 可能是定时任务触发

# 验证：检查 cron 任务
sudo crontab -l -u root
sudo crontab -l -u www-data
# 是否有凌晨定时任务？

# ===== 第 7 步：应急处理 =====
# 优先级：恢复服务 > 保留现场 > 查找根因

# 应急措施 1：终止问题查询
sudo mysql -e "KILL <慢查询的ID>;"

# 应急措施 2：临时增加 PHP-FPM 子进程数
sudo sed -i 's/pm.max_children = 50/pm.max_children = 80/' \
    /etc/php/8.3/fpm/pool.d/www.conf
sudo systemctl reload php8.3-fpm

# 应急措施 3：如果磁盘快满了——紧急清理
sudo journalctl --vacuum-size=500M
sudo systemctl reload php8.3-fpm

# 应急措施 4：临时禁用慢查询日志（减少 I/O）
# 编辑 /etc/php/8.3/fpm/pool.d/www.conf
# ;slowlog = /var/log/php/slow.log
# request_slowlog_timeout = 0
# sudo systemctl reload php8.3-fpm

# 应急措施 5（最后手段）：重启服务栈
sudo systemctl restart mysql
sudo systemctl restart php8.3-fpm
sudo systemctl restart nginx

# ===== 验证恢复 =====
uptime && systemctl status php8.3-fpm nginx mysql
curl -o /dev/null -s -w '%{http_code}\n' http://localhost/health
# 返回 200 → 服务恢复

# ===== 第 8 步：事后排查 =====
# 1. 保留证据：
#    保存今晚的所有日志到安全位置
sudo journalctl -u mysql --since "02:00" --until "04:00" > /tmp/incident-mysql.log
sudo journalctl -u php8.3-fpm --since "02:00" --until "04:00" > /tmp/incident-php.log

# 2. 找到那条问题查询：
grep "SELECT\|UPDATE\|DELETE" /tmp/incident-mysql.log | sort | uniq -c | sort -rn | head -10

# 3. 用 EXPLAIN 分析那条查询：
sudo mysql -e "EXPLAIN <问题查询>;"
# 如果 type=ALL（全表扫描）→ 需要添加索引

# 4. 防止复发：
# - 给相关表添加索引
# - 设置 PHP-FPM 的 request_terminate_timeout（请求超时自动终止）
# - 调整 pm.max_children 为合理值（根据内存计算）
# - 添加监控告警：CPU > 80% 持续 5 分钟就应该通知
# - 监控 PHP-FPM worker 使用率
# - MySQL 慢查询日志永久开启（long_query_time = 2）
```

### 练习 7：GRUB rescue 恢复

**场景：** 服务器重启后显示 `grub rescue>` 提示符。你需要在不使用 Live CD 的情况下（远程管理卡/IPMI 可用，能看屏幕和键盘输入）恢复系统。

**任务：**
1. 在 `grub rescue>` 提示符下定位 `/boot` 分区
2. 手动加载 GRUB 模块并启动系统
3. 进入系统后永久修复 GRUB

**参考答案：**

```bash
# === 在 grub rescue> 中操作 ===

# 1. 列出所有磁盘和分区
grub rescue> ls
# 输出：(hd0) (hd0,msdos1) (hd0,msdos2) (hd1) (hd1,msdos1)

# 2. 逐个检查分区内容，找到 /boot
grub rescue> ls (hd0,msdos1)/
# 如果看到 vmlinuz-..., initrd.img-..., grub/ 等 → 这就是 /boot 分区
# 如果看到 bin/ etc/ usr/ var/ → 这是根分区 /, /boot 在子目录下

# 3a. 如果是独立 /boot 分区（最常见情况）：
grub rescue> set prefix=(hd0,msdos1)/grub
grub rescue> set root=(hd0,msdos1)
grub rescue> insmod normal
grub rescue> normal
# 此时应该看到正常的 GRUB 菜单了——选择 Ubuntu 启动

# 3b. 如果 /boot 在根分区内：
grub rescue> set prefix=(hd0,msdos2)/boot/grub
grub rescue> set root=(hd0,msdos2)
grub rescue> insmod normal
grub rescue> normal

# 3c. 如果 insmod normal 失败：
# 模块可能在其他路径——尝试：
grub rescue> ls (hd0,msdos1)/grub/i386-pc/
# 如果能看到 normal.mod → 路径正确，但可能缺少其他依赖
grub rescue> insmod linux
grub rescue> linux (hd0,msdos1)/vmlinuz-<按Tab自动补全> root=/dev/sda2
grub rescue> initrd (hd0,msdos1)/initrd.img-<按Tab自动补全>
grub rescue> boot
# 直接手动指定内核和 initramfs 来启动

# === 进入系统后永久修复 ===

# 1. 确认当前分区布局
lsblk -f

# 2. BIOS 模式：
sudo grub-install /dev/sda        # 重装 GRUB 到 MBR
sudo update-grub                  # 重新生成 grub.cfg

# 3. UEFI 模式：
sudo grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=Ubuntu
sudo update-grub

# 4. 验证
sudo grub-install --recheck /dev/sda
echo $?  # 应该输出 0

# 5. 如果 grub.cfg 中 UUID 不对——手动检查
cat /boot/grub/grub.cfg | grep "root=UUID"
blkid | grep <你的根分区>
# 确认 UUID 匹配
```

### 练习 8：Emergency Mode 恢复

**场景：** 服务器启动后进入 emergency mode。你输入 root 密码进入 Shell。

**任务：**
1. 使用 `journalctl -xb` 找到导致进入 emergency mode 的原因
2. 检查 `/etc/fstab`
3. 修复问题
4. 验证并重启

**参考答案：**

```bash
# 1. 查看启动日志中的错误
journalctl -xb -p err --no-pager | tail -30
# 假设输出关键信息：
# systemd[1]: Timed out waiting for device /dev/disk/by-uuid/abc123-def456-...
# systemd[1]: Dependency failed for /mnt/backup.
# systemd[1]: Dependency failed for Local File Systems.
# → /mnt/backup 分区找不到——可能是一块外接备份盘被拔掉了

# 2. 查看 /etc/fstab
cat /etc/fstab
# 找到问题行：
# UUID=abc123-def456 /mnt/backup ext4 defaults 0 2
# 这个 UUID 对应的磁盘不在了

# 3. 确认该设备确实不存在
ls -la /dev/disk/by-uuid/ | grep abc123
# 无输出——确认设备不存在

# 4. 修复
# 如果该分区确实不再需要——注释掉 fstab 中的对应行：
sudo nano /etc/fstab
# 在对应行的行首添加 #
# UUID=abc123-def456 /mnt/backup ext4 defaults 0 2

# 或者添加 nofail 选项（systemd 不会因为挂载失败而进入 emergency mode）：
# UUID=abc123-def456 /mnt/backup ext4 defaults,nofail 0 2

# 如果该分区是临时的（需要重新插上）——添加 nofail 然后重启：
# UUID=abc123-def456 /mnt/backup ext4 defaults,nofail 0 2

# 5. 测试挂载
sudo mount -a
# 如果没有错误——fstab 修复成功

# 6. 重启
systemctl reboot
# 系统应该正常启动了
```

### 练习 9：权限导致的 SSH 密钥登录失败

**场景：** 用户配置了 SSH 密钥，但每次登录仍然被要求输入密码。`ssh -v` 显示密钥被尝试了但被服务器拒绝。

**任务：**
1. 检查本地私钥权限
2. 使用 `ssh -vvv` 查看详细认证过程
3. 登录服务器检查 `authorized_keys` 和相关目录权限
4. 检查 sshd 配置
5. 修复并验证

**参考答案：**

```bash
# === 客户端排查 ===

# 1. 本地私钥权限
ls -la ~/.ssh/id_ed25519
# 权限必须是 600 (-rw-------)
# 如果是 644 或其他——sshd 会拒绝使用
chmod 600 ~/.ssh/id_ed25519

# 2. 详细连接日志
ssh -vvv user@server 2>&1 | grep -E "Offering|auth|Accepted|denied|Permission"
# 关键行：
# debug1: Offering public key: /home/user/.ssh/id_ed25519 ED25519 SHA256:xxxx
# debug1: Authentications that can continue: publickey,password
# debug1: Next authentication method: publickey
# → 客户端发送了公钥，但服务器没有接受——问题在服务器端

# === 服务器端排查 ===

# 3. 检查 authorized_keys
ls -la ~/.ssh/authorized_keys
# 权限必须是 600 (-rw-------)

# 4. 检查 .ssh 目录
ls -lad ~/.ssh
# 权限必须是 700 (drwx------)

# 5. 检查 HOME 目录
ls -lad ~
# 所有者必须是用户自己
# 组和其他人不能有写权限（sshd 会拒绝）——通常是 755 或 750

# 6. 检查 sshd 日志
sudo tail -50 /var/log/auth.log | grep sshd
# 或
sudo journalctl -u ssh --since "5 minutes ago"
# 关键信息：
# Authentication refused: bad ownership or modes for directory /home/user
# → HOME 目录权限过于宽松（组或其他人有写权限）
# 修复：
chmod 755 ~

# Authentication refused: bad ownership or modes for file /home/user/.ssh/authorized_keys
# → authorized_keys 权限不对
# 修复：
chmod 600 ~/.ssh/authorized_keys

# 7. 检查 sshd_config
sudo sshd -T | grep -E "pubkeyauthentication|passwordauthentication|authorizedkeysfile"
# pubkeyauthentication yes      ← 必须 yes
# authorizedkeysfile .ssh/authorized_keys

# 8. 如果以上都正确——可能是公钥内容不匹配
# 客户端：导出本地私钥对应的公钥
ssh-keygen -y -f ~/.ssh/id_ed25519
# 服务器：查看 authorized_keys 中的公钥
cat ~/.ssh/authorized_keys
# 两者应该完全一致（最后一部分——公钥的主体）

# 9. 服务器端一键修复脚本
mkdir -p ~/.ssh
chmod 700 ~/.ssh
touch ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
chmod 755 ~
```

## 5. 常见错误与排错

### 错误 1：跳过观察阶段直接下判断

**现象：** 看到一个错误信息就认定是它导致的，然后花半小时解决了一个非根因的问题，发现故障还在。

**案例：**

```
用户报告："网站打不开，浏览器一直转圈"
管理员看到 nginx error.log 中有 "connect() failed (111: Connection refused)
while connecting to upstream" → 认定 PHP-FPM 没启动 → 重启 PHP-FPM →
问题依旧 → 1 小时后才发现是磁盘满了，PHP-FPM 无法写日志，导致进程卡死
```

**正确做法：**
- 先跑 `df -h`、`free -h`、`uptime`——30 秒就能排除最常见的基础设施问题
- 多收集 2-3 条独立证据再形成假设
- 问自己："如果我的假设是对的，我应该还能看到什么其他症状？"

---

### 错误 2：同时修改多个变量

**现象：** 在排查过程中同时做了多个修改（改了配置文件、重启了服务、调整了防火墙规则），然后不确定是哪个修改解决了问题。

**案例：**

```
管理员怀疑 SSH 登录慢是 DNS 反向解析的问题：
1. 修改了 sshd_config 中的 UseDNS=no
2. 同时修改了 GSSAPIAuthentication=no
3. 同时重启了 sshd 和 systemd-resolved
4. 发现登录快了 → 但不知道是哪个修改起作用的
5. 下次在其他服务器遇到同样问题——又得重新猜
```

**正确做法：**
- 每次只做一个修改
- 修改后立即测试效果
- 如果没效果——撤销（或记录），进行下一个修改
- 知道"哪个修改有效"比"问题解决了"更重要

---

### 错误 3：只修症状不修根因

**现象：** 把症状消除了就认为问题解决了，但没有追查根本原因，导致问题反复出现。

**案例：**

```
凌晨 2 点磁盘满 → 管理员手动清理了日志 → 第二天凌晨 2 点又满了。
根因：logrotate 配置有误，日志从未被轮替。
正确做法：清理磁盘后，检查 /etc/logrotate.d/ 配置，确保日志有定期轮替策略。
```

**修改验证清单：**
1. 症状消失了吗？
2. 我知道根因是什么吗？
3. 我做了什么来防止复发？（配置修改 / 监控告警 / 文档记录）

---

### 错误 4："重启试试"——无脑重启

**现象：** 遇到任何问题先重启服务或重启系统——重启确实经常能解决问题，但同时销毁了排查根因所需的现场证据。

**重启的代价：**
- 内存中的状态信息全部丢失（进程列表、连接状态、缓存内容）
- 日志时间被重置——难以关联故障前后的时间线
- 如果重启后故障依旧——你既没有解决问题，又丢失了排查线索

**何时可以重启：**
- 你已经收集了足够的诊断信息
- 你确信问题是由内存泄漏/僵尸进程等重启可恢复的状态引起的
- 服务恢复的优先级远高于保留现场（如生产环境大面积故障）

**何时不能重启：**
- 你还没有收集任何日志
- 这是这个故障第一次出现——保留现场对排查至关重要
- 你想"试试看"——试之前先想清楚你在测试什么假设

---

### 错误 5：忽略日志中的时间线

**现象：** 看到错误日志但忽略了时间戳，导致误判因果。

**案例：**

```
应用日志：
10:00:00 - ERROR: Database connection timeout
10:00:05 - WARNING: Retry attempt 1 failed
10:00:10 - CRITICAL: Service unavailable

管理员看到 "CRITICAL: Service unavailable" 就去查服务配置——
但实际上 10:00:00 的数据库连接超时才是根因，后面的都是连锁反应。

数据库日志：
09:59:55 - Disk I/O error on /var/lib/mysql/data.ibd
09:59:58 - InnoDB: Unable to write to data file
→ 磁盘 I/O 错误才是真正的根因！
```

**正确做法：**
- 看到错误后，向前追溯 1-5 分钟——找第一个异常事件
- 关注"第一个错误"而非"最严重的错误"
- 把多条日志按时间线排列，构建事件链

---

### 错误 6：忽视"没有变化"也是线索

**现象：** 排查时只关注"什么出错了"，忽略了"什么还是正常的"。正常的部分对缩小范围至关重要。

**案例：**

```
数据库连接失败
- 应用 A 连不上数据库
- 应用 B 也连不上数据库
- 但是直接在服务器上 mysql 命令行可以连接

"没有变化"的线索：
- mysql 命令行能连 → 数据库进程本身是正常的
- 两台应用都连不上 → 不是应用代码的问题
→ 问题很可能在网络层（防火墙规则只允许 localhost 连接）
→ 检查：sudo iptables -L -n | grep 3306
→ 确认：防火墙只允许 127.0.0.1 访问 3306 端口
```

**记住：** 每次排查时都问自己——"哪些部分还在正常工作？"这个信息与"哪些部分出了问题"同等重要。

## 6. 进阶延伸

### 6.1 从"会排查"到"防患于未然"

本章教给你的排查方法论解决了"发生了故障怎么办"的问题。但更高层次的能力是**让故障不发生，或者即使发生了也能快速自愈**。以下是你在掌握基础排查后应该深入的方向。

#### 6.1.1 可观测性（Observability）三大支柱

传统的监控告诉你"出了问题"（告警），但可观测性让你能回答"为什么出了问题"（诊断）。

```
┌─────────────────────────────────────────────────────────────────┐
│                    可观测性三大支柱                                │
│                                                                  │
│  1. Metrics（指标）                                               │
│  ─────────────────                                               │
│  聚合的数字数据——反映系统的宏观状态                                 │
│  工具：Prometheus + Grafana, Netdata, Zabbix                     │
│  示例：                                                          │
│  - CPU 使用率趋势图                                               │
│  - nginx 请求速率（requests/sec）                                │
│  - MySQL 慢查询计数                                              │
│  - 磁盘使用率预测（X 天后将满）                                    │
│                                                                  │
│  2. Logs（日志）                                                  │
│  ────────────────                                                │
│  离散的事件记录——反映特定时刻发生了什么                             │
│  工具：Loki + Grafana, ELK Stack (Elasticsearch + Logstash       │
│        + Kibana), journald + rsyslog 集中化                      │
│  示例：                                                          │
│  - nginx 访问日志 → 请求来源、响应时间、状态码                      │
│  - 应用错误日志 → 堆栈跟踪、错误消息                               │
│  - 审计日志 → 谁在什么时间做了什么                                  │
│                                                                  │
│  3. Traces（链路追踪）                                            │
│  ────────────────────                                            │
│  请求在分布式系统中的完整路径——反映"一个请求经历了什么"              │
│  工具：Jaeger, Zipkin, OpenTelemetry                             │
│  示例：                                                          │
│  用户请求 → nginx (2ms) → PHP-FPM (200ms)                        │
│                         → MySQL 查询 (190ms)  ← 瓶颈在这里！      │
│                         → Redis 缓存 (3ms) → 返回 HTML (5ms)     │
└─────────────────────────────────────────────────────────────────┘
```

**Metrics + Logs + Traces 的关系：**

```
Metrics 告诉你："错误率突然升高了"（告警触发）
  ↓
Traces 告诉你："错误集中在 /api/search 接口，瓶颈在 MySQL"（定位范围）
  ↓
Logs 告诉你："MySQL 慢查询日志显示全表扫描 users 表"（定位根因）
  ↓
然后你用本章学的排查方法论去修复和验证
```

#### 6.1.2 主动式排查 —— 还没坏就开始查

与其等故障发生再排查，不如主动寻找隐患：

```bash
# 每日/每周主动检查清单

# 1. 检查失败的服务
systemctl list-units --failed

# 2. 检查磁盘趋势（今天的 90% 可能就是明天的 100%）
df -h | awk '$5+0 > 80 {print "WARNING: "$6" is "$5" full"}'

# 3. 检查最近的系统错误
journalctl -p err --since "24 hours ago" --no-pager | wc -l

# 4. 检查是否有僵尸进程
ps aux | grep -w Z | wc -l

# 5. 检查日志大小趋势
du -sh /var/log/
journalctl --disk-usage

# 6. 检查关键服务端口是否在监听
ss -tlnp | grep -E ':22 |:80 |:443 |:3306 '

# 7. 检查是否有计划外的重启
last reboot | head -5

# 8. 检查安全更新
apt list --upgradable 2>/dev/null | grep -i security
```

#### 6.1.3 故障复盘（Postmortem）—— 让每次故障都有长期价值

每次故障解决后，花 15 分钟写一份简短的复盘记录：

```
故障复盘模板（5 个问题）：

1. 发生了什么？（一句话描述）
   示例：凌晨 3 点 web-01 磁盘满导致 nginx 返回 502，持续 30 分钟

2. 根因是什么？
   示例：MySQL 慢查询日志未设置轮替，积累了 45GB 的历史日志

3. 怎么发现的？（告警 / 用户投诉 / 自己发现的）
   示例：磁盘使用率 > 90% 的告警触发，但收到告警时已经 99%

4. 怎么解决的？
   示例：清理了 MySQL 慢查询日志，配置了 logrotate 轮替策略（7 天后删除）

5. 如何防止复发？
   示例：
   - 配置了 MySQL 慢查询日志的 logrotate（已执行）
   - 添加了磁盘使用率 > 80% 的预警级别告警（提前通知）
   - 在 crontab 中添加了每日磁盘趋势检查
```

### 6.2 排查工具进阶

#### 6.2.1 bpftrace / eBPF —— 动态内核追踪

`strace` 和 `perf` 已经能解决大部分问题，但当问题深入到内核层面时，eBPF（Extended Berkeley Packet Filter）是终极武器：

```bash
# bpftrace —— 动态内核追踪的瑞士军刀
sudo apt install -y bpftrace

# 示例 1：谁在删除文件？（定位幽灵文件的产生者）
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_unlink { printf("%s (PID %d) deleted %s\n", comm, pid, str(args->pathname)); }'

# 示例 2：哪个进程在执行最多磁盘 I/O？
sudo bpftrace -e 'kprobe:blk_account_io_done { @[comm] = count(); }'
# 按 Ctrl+C 后会输出统计

# 示例 3：追踪 TCP 重传（网络丢包检测）
sudo bpftrace -e 'kprobe:tcp_retransmit_skb { printf("TCP retransmit from %s (PID %d)\n", comm, pid); }'

# 示例 4：列出所有新创建的进程（fork/exec）
sudo bpftrace -e 'tracepoint:sched:sched_process_exec { printf("%s (PID %d) exec by %s\n", comm, pid, curtask->parent->comm); }'
```

#### 6.2.2 自动化诊断脚本

将本章的排查命令组合成自动化脚本——在凌晨被叫醒时，一行命令就能收集所有关键信息：

```bash
#!/bin/bash
# 文件：~/bin/quick-diag.sh
# 用途：一键收集系统诊断信息
# 使用：quick-diag.sh > /tmp/diag-$(date +%Y%m%d-%H%M%S).txt

echo "========== 诊断时间：$(date) =========="
echo ""

echo "========== 1. 系统运行时间与负载 =========="
uptime
echo ""

echo "========== 2. 磁盘使用 =========="
df -h | grep -vE '^(tmpfs|devtmpfs|snapfuse|none)'
echo ""

echo "========== 3. 内存使用 =========="
free -h
echo ""

echo "========== 4. CPU/内存 TOP 5 进程 =========="
ps aux --sort=-%cpu | head -6
echo "---"
ps aux --sort=-%mem | head -6
echo ""

echo "========== 5. 失败的服务 =========="
systemctl list-units --failed --no-legend 2>/dev/null || echo "无失败服务"
echo ""

echo "========== 6. 最近 1 小时的错误日志 =========="
journalctl -p err --since "1 hour ago" --no-pager 2>/dev/null | tail -20
echo ""

echo "========== 7. 网络监听端口 =========="
ss -tlnp 2>/dev/null | grep LISTEN
echo ""

echo "========== 8. 幽灵文件（已删除未释放） =========="
sudo lsof 2>/dev/null | grep deleted | awk '{printf "PID=%-8s CMD=%-15s SIZE=%s\n", $2, $1, $7}' | sort -u | head -10
echo ""

echo "========== 9. journal 磁盘占用 =========="
journalctl --disk-usage 2>/dev/null
echo ""

echo "========== 10. 最近的重启记录 =========="
last reboot | head -5
echo ""

echo "========== 诊断完成 =========="
```

### 6.3 排查思维的最高境界：冷静

最后一点——与具体技术无关，但比任何命令都重要：

```
故障排查最重要的工具不是 strace，不是 tcpdump，更不是 Google，
而是你面对故障时的冷静。

冷静来源于：
1. 你有一套方法论（O-H-V-R）——即使面对未知，也知道从哪开始
2. 你有一组检查清单——不会遗漏常见问题
3. 你见过足够多的故障——经验告诉你什么可能、什么不可能
4. 你知道最坏的结果是什么——即使彻底搞不定，也有备份可以恢复

当你凌晨 3 点被叫醒，
当生产环境警报大作，
当领导在背后焦急等待——

深呼吸。打开终端。先跑 df -h && free -h && uptime。
然后，按本章教你的方法，一步一步来。

你不需要记住每个命令的参数，
你只需要知道：面对这个症状，我应该从哪里开始。
这就是本章的全部意义。
```
