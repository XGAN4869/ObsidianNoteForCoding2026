## 2. 核心概念

### 2.1 什么是进程？

**进程（Process）** 是程序的执行实例。一个程序（如 `/usr/bin/nginx`）存放在磁盘上，是静态的代码和数据；当它被加载到内存中运行起来，就成为一个或多个进程。

```
+------------------------------------------------------------------+
|                    程序 vs 进程                                    |
|                                                                  |
|  程序（Program）                    进程（Process）                 |
|  ┌─────────────────────┐          ┌─────────────────────┐        |
|  │ /usr/bin/nginx      │          │ PID 1234            │        |
|  │ (磁盘上的二进制文件)   │  执行 →  │ 状态: Running       │        |
|  │ 静态、永久            │          │ 内存: 50MB          │        |
|  │ 一个文件              │          │ CPU时间: 2.3秒      │        |  │                     │          │ 打开的文件: 12个     │        |
|  │                     │          │ 网络连接: 80端口     │        |
|  └─────────────────────┘          └─────────────────────┘        |
|                                                                  |
|  关键区别：一个程序可以同时有多个进程实例                              |
|                                                                  |
|  /usr/bin/nginx  ─── 启动 4 个 worker 进程:                       |
|  ├── PID 1234: nginx master process                              |
|  ├── PID 1235: nginx worker process                              |
|  ├── PID 1236: nginx worker process                              |
|  └── PID 1237: nginx worker process                              |
+------------------------------------------------------------------+
```

### 2.2 PID 与 PPID：进程的身份证

每个进程有两个核心标识符：

| 标识符 | 全称 | 含义 | 特殊值 |
|--------|------|------|--------|
| **PID** | Process IDentifier（进程标识符） | 进程的唯一编号 | PID 1 = systemd（init 进程） |
| **PPID** | Parent Process IDentifier（父进程标识符） | 创建该进程的父进程的 PID | PPID 0 = 内核直接创建的进程 |

**进程的父子关系形成一棵树：**

```
PID 1: systemd (init 进程 — 所有进程的祖先)
├── PID 500: sshd (SSH 服务守护进程)
├── PID 600: cron (定时任务调度器)
├── PID 700: bash (用户登录 shell)
│   ├── PID 701: vim (从 shell 启动的编辑器)
│   ├── PID 702: sleep 1000 (从 shell 启动的睡眠命令)
│   └── PID 703: ps aux (从 shell 启动的 ps 命令)
├── PID 800: nginx (Web 服务器)
│   ├── PID 801: nginx worker
│   ├── PID 802: nginx worker
│   └── PID 803: nginx worker
└── PID 900: python3 /app/server.py
    └── PID 901: python3 /app/worker.py
```

```bash
# 查看当前 shell 的 PID
echo $$
# 输出示例：700

# 查看当前 shell 的父进程 PID
echo $PPID
# 输出示例：500

# 用 pstree 查看进程树（需要安装：sudo apt install -y psmisc）
pstree -p $$ 2>/dev/null || echo "pstree 未安装，可以 sudo apt install -y psmisc"
```

**关键规则：**

- 每个进程（除了 PID 1）都有一个父进程
- 当父进程先于子进程退出时，子进程成为**孤儿进程（Orphan Process）**，被 PID 1（systemd）收养
- 当子进程退出但父进程未调用 `wait()` 回收时，子进程成为**僵尸进程（Zombie Process）**

### 2.3 进程状态：进程的"生命体征"

在 Linux 中，进程处于以下几种状态之一：

```
+------------------------------------------------------------------+
|                    进程状态转换图                                   |
|                                                                  |
|                    ┌─────────────┐                                |
|                    │  创建 (New)  │  fork() 系统调用创建新进程      |
|                    └──────┬──────┘                                |
|                           │                                       |
|                           v                                       |
|              ┌─────────────────────────┐                         |
|              │   就绪 (Runnable / R)    │  等待 CPU 调度            |
|              └──────────┬──────────────┘                         |
|                         │                                         |
|            调度器分配CPU  │                                         |
|                         v                                         |
|              ┌─────────────────────────┐  等待 I/O、信号等        |
|       ┌──────│   运行 (Running / R)     │──────┐                   |
|       │      └─────────────────────────┘      │                   |
|       │                                        │                   |
|       │ 时间片用完                              │ 等待资源            |
|       v                                        v                   |
|  ┌─────────┐                          ┌──────────────┐            |
|  │ 就绪 (R) │                          │ 睡眠 (Sleep)  │            |
|  └─────────┘                          │  S / D        │            |
|                                        └──────┬───────┘            |
|       │                                        │                   |
|       │                                        │ 信号/事件          |
|       │                                        v                   |
|       │                               ┌──────────────┐            |
|       └───────────────────────────────│  就绪 (R)     │            |
|                                        └──────────────┘            |
|                                                                  |
|                    ┌─────────────┐                                |
|                    │ 停止 (T)     │  SIGSTOP / Ctrl+Z 暂停进程     |
|                    │  Stopped     │                                |
|                    └─────────────┘                                |
|                                                                  |
|                    ┌─────────────┐                                |
|                    │ 僵尸 (Z)     │  进程已退出，但父进程尚未        |
|                    │  Zombie      │  调用 wait() 回收退出状态      |
|                    └─────────────┘                                |
+------------------------------------------------------------------+
```

**进程状态代码完整表（ps 输出中的 STAT 列）：**

| 代码 | 状态 | 含义 | 示例场景 |
|------|------|------|---------|
| **R** | Running（运行中） | 正在 CPU 上运行，或在运行队列中等待 | 计算密集型任务 |
| **S** | Sleeping（可中断睡眠） | 等待事件完成（I/O、信号等），可被信号唤醒 | 等待用户输入、等待网络数据 |
| **D** | Disk sleep（不可中断睡眠） | 等待 I/O 完成，不可被信号中断 | 等待磁盘读写完成 |
| **T** | Stopped（已停止） | 被作业控制信号（SIGSTOP/Ctrl+Z）暂停 | `vim` 被 Ctrl+Z 挂起 |
| **Z** | Zombie（僵尸） | 进程已退出，但父进程未回收退出状态 | 父进程未调用 `wait()` |
| **X** | Dead（已死亡） | 进程正在被清理 | 极少见到 |

**附加标志（附加在状态代码后面的小写字母）：**

| 附加标志 | 含义 |
|----------|------|
| `<` | 高优先级（nice 值为负） |
| `N` | 低优先级（nice 值为正） |
| `l` | 多线程进程 |
| `s` | 会话领导者（session leader） |
| `+` | 前台进程组中的进程 |

```bash
# 观察不同状态的进程
# R: 运行中
ps -eo pid,stat,comm | grep ' R'

# S: 睡眠中（最常见）
ps -eo pid,stat,comm | grep ' S' | head -5

# D: 不可中断睡眠（需要访问磁盘的进程）
ps -eo pid,stat,comm | grep ' D' || echo "(通常看不到 D 状态——除非在 I/O 压力大的时候)"

# T: 已停止
sleep 1000 &
SLPID=$!
kill -STOP $SLPID
ps -p $SLPID -o pid,stat,comm
kill -CONT $SLPID
kill $SLPID 2>/dev/null
```

### 2.4 进程优先级与 nice 值

#### 2.4.1 优先级 vs nice 值

Linux 的进程调度有两个关联的概念：

| 概念 | 英文 | 范围 | 含义 | 查看方式 |
|------|------|------|------|---------|
| **优先级** | Priority | 0--139 | 内核调度器使用的实际优先级，数值越小优先级越高 | `ps -l` 的 PRI 列 |
| **nice 值** | Nice value | -20 到 +19 | 用户可设置的"善意"程度，数值越小越"自私"（获取更多 CPU） | `ps -l` 的 NI 列 |

**nice 值的直观理解：**

```
nice 值  ──────────────────────────────────────────
          -20  -10   0   +10  +20
          │     │    │     │     │
          自私         默认         友善（nice）
          抢占更多 CPU              让出 CPU 给其他进程

实际优先级 = 实时优先级（0-99）或 nice 值映射（100-139）

对于普通进程（非实时）：
  priority = 20 + nice      （大致映射，实际由调度器决定）
  
  nice = -20  → priority ≈ 0   （几乎最高优先）
  nice =   0  → priority ≈ 20  （默认）
  nice = +19  → priority ≈ 39  （最低优先）
```

```bash
# 查看当前 shell 的 nice 值
ps -o pid,nice,comm -p $$
# 输出示例：
# PID  NI COMMAND
# 700   0 bash

# 以较低的优先级启动一个命令
nice -n 10 sleep 100 &
# 查看其 nice 值
ps -o pid,nice,comm -p $!
```

#### 2.4.2 nice 值的权限规则

只有 root 用户或具有 `CAP_SYS_NICE` 能力的进程可以将 nice 值设为负数（提高优先级）。普通用户只能将 nice 值设为 0 或正数（降低优先级），且只能增大 nice 值（`renice` 时）。

### 2.5 信号（Signal）：进程间的通信方式

**信号（Signal）** 是 Linux 中进程间异步通信的一种机制。一个进程可以向另一个进程发送一个信号，接收进程按照预设的处理器（handler）响应。

```
+------------------------------------------------------------------+
|    发送方            信号                接收方                      |
|  ┌──────────┐       ──────>        ┌──────────────┐             |
|  │ 用户/SHELL│     SIGINT          │ 目标进程     │             |
|  │ (Ctrl+C)  │                     │              │             |
|  └──────────┘                     └──────────────┘             |
|                                        │                         |
|                             根据信号类型和进程设置：                 |
|                               ├── 执行默认动作（终止/忽略/转储）      |
|                               ├── 调用用户注册的信号处理器           |
|                               └── 忽略信号                        |
+------------------------------------------------------------------+
```

#### 2.5.1 核心信号速查表

| 信号编号 | 信号名 | 默认动作 | 含义 | 可捕获？ | 典型触发方式 |
|----------|--------|---------|------|---------|------------|
| **1** | `SIGHUP` | 终止 | 挂断（Hangup）——终端关闭时发送 | 是 | 关闭终端、`kill -1` |
| **2** | `SIGINT` | 终止 | 中断（Interrupt） | 是 | **Ctrl+C** |
| **3** | `SIGQUIT` | 转储+终止 | 退出——比 SIGINT 更"强烈" | 是 | **Ctrl+\\** |
| **9** | `SIGKILL` | 终止 | 强制杀死——**不可捕获、不可忽略** | **否** | `kill -9 PID` |
| **15** | `SIGTERM` | 终止 | 终止——礼貌地请求进程退出 | 是 | `kill PID`（默认） |
| **17** | `SIGCHLD` | 忽略 | 子进程状态改变（退出/停止） | 是 | 子进程退出时自动发送给父进程 |
| **18** | `SIGCONT` | 继续 | 继续执行已停止的进程 | 是 | `kill -CONT PID` 或 `fg`/`bg` |
| **19** | `SIGSTOP` | 停止 | 暂停进程——**不可捕获、不可忽略** | **否** | `kill -STOP PID` |
| **20** | `SIGTSTP` | 停止 | 终端停止（Terminal Stop） | 是 | **Ctrl+Z** |

**不可捕获的信号（SIGKILL=9 和 SIGSTOP=19）：**

这两个信号是"最终手段"：
- **SIGKILL（9）**：内核直接终止进程，不给进程任何清理的机会。进程无法注册处理器，也无法忽略。
- **SIGSTOP（19）**：内核直接暂停进程，同样无法被捕获或忽略。

#### 2.5.2 SIGTERM vs SIGKILL：优雅终止 vs 暴力终止

```
+------------------------------------------------------------------+
|                    SIGTERM (15) vs SIGKILL (9)                     |
|                                                                  |
|  kill PID (SIGTERM)                    kill -9 PID (SIGKILL)      |
|  ┌──────────────────┐                  ┌──────────────────┐      |
|  │ 1. 发送 SIGTERM  │                  │ 1. 发送 SIGKILL  │      |
|  │ 2. 进程收到信号   │                  │ 2. 内核直接杀死   │      |
|  │ 3. 进程执行清理：  │                  │    进程——没有     │      |
|  │    - 保存数据     │                  │    任何清理机会   │      |
|  │    - 关闭文件     │                  │ 3. 进程立即消失   │      |
|  │    - 释放资源     │                  │                  │      |
|  │    - 通知子进程   │                  │  风险：           │      |
|  │ 4. 进程退出       │                  │  - 数据丢失       │      |
|  │                  │                  │  - 文件损坏       │      |
|  │  结果：安全、干净   │                  │  - 锁未释放       │      |
|  └──────────────────┘                  └──────────────────┘      |
|                                                                  |
|  规则：总是先尝试 SIGTERM。如果进程无响应，再用 SIGKILL。           |
|  从 init 脚本到 systemd，这个规则始终不变。                         |
+------------------------------------------------------------------+
```

```bash
# 演示 SIGTERM vs SIGKILL
sleep 1000 &
SLEEP_PID=$!
echo "sleep 进程 PID: $SLEEP_PID"

# 用 SIGTERM（默认）终止
kill $SLEEP_PID
sleep 0.1
ps -p $SLEEP_PID > /dev/null 2>&1 && echo "进程仍在运行" || echo "进程已终止（SIGTERM）"

# 重新启动并测试 SIGKILL
sleep 1000 &
SLEEP_PID=$!
kill -9 $SLEEP_PID
sleep 0.1
ps -p $SLEEP_PID > /dev/null 2>&1 && echo "进程仍在运行" || echo "进程已终止（SIGKILL）"
```

#### 2.5.3 信号的可移植性

信号编号在不同 Unix 系统上可能不同。**在脚本中，始终使用信号名而非编号：**

```bash
# 推荐：使用信号名（可移植）
kill -TERM 1234
kill -KILL 1234
kill -HUP  1234

# 不推荐：使用数字（可能在不同系统上含义不同）
kill -15 1234   # 在 Linux 上是 SIGTERM，但不保证其他系统也一样
kill -9  1234   # 同上
```

### 2.6 /proc 伪文件系统：进程的"信息窗口"

**`/proc`** 是一个伪文件系统（Pseudo-filesystem），它不占用磁盘空间，完全存在于内存中。`/proc` 下的文件不是在磁盘上存储的实际数据，而是内核在读取时**实时生成**的。

```
+------------------------------------------------------------------+
|                    /proc 伪文件系统的结构                           |
|                                                                  |
|  /proc/                                                          |
|  ├── cpuinfo          → CPU 信息（型号、频率、缓存）               |
|  ├── meminfo          → 内存使用概况                               |
|  ├── loadavg          → 系统负载（1/5/15 分钟平均值）              |
|  ├── uptime           → 系统运行时间                               |
|  ├── version          → 内核版本                                   |
|  ├── filesystems      → 支持的文件系统列表                          |
|  ├── mounts           → 当前挂载点                                 |
|  ├── sys/             → /proc/sys/ — 内核参数（可写）               |
|  │                                                               |
|  ├── 1/               → PID 1 (systemd) 的进程目录                 |
|  │   ├── cmdline      → 启动该进程的完整命令行                      |
|  │   ├── status       → 进程状态摘要（名称、状态、PID、内存等）     |
|  │   ├── stat         → 进程状态（机器可读格式）                    |
|  │   ├── statm        → 进程内存使用（以页为单位）                  |
|  │   ├── environ      → 进程的环境变量                             |
|  │   ├── fd/          → 打开的文件描述符目录                       |
|  │   │   ├── 0        → 标准输入                                   |
|  │   │   ├── 1        → 标准输出                                   |
|  │   │   ├── 2        → 标准错误                                   |
|  │   │   └── ...      → 其他打开的文件/套接字                       |
|  │   ├── cwd          → 指向当前工作目录的符号链接                  |
|  │   ├── exe          → 指向可执行文件的符号链接                    |
|  │   ├── root         → 指向进程根目录的符号链接                    |
|  │   ├── maps         → 内存映射区域                               |
|  │   ├── limits       → 资源限制                                   |
|  │   ├── cgroup       → 控制组信息                                 |
|  │   ├── mountinfo    → 挂载命名空间信息                           |
|  │   ├── io           → I/O 统计信息                               |
|  │   ├── net/         → 网络相关信息                               |
|  │   └── task/        → 线程子目录                                |
|  │                                                               |
|  ├── 500/             → PID 500 的进程目录                         |
|  ├── 600/             → PID 600 的进程目录                         |
|  └── ...                                                          |
+------------------------------------------------------------------+
```

**关键特性：**

1. **实时性**：每次 `cat /proc/1234/status` 时，内核都会实时生成当前信息
2. **文件大小为零**：`ls -l /proc/meminfo` 显示大小为 0，因为这些文件是虚拟的
3. **可读可写**：部分 `/proc/sys/` 下的文件可写，用于调整内核参数
4. **无磁盘占用**：`/proc` 不占用任何磁盘空间（`df -h /proc` 会显示 0 块）

```bash
# 探索 /proc 文件系统
echo "=== 系统信息 ==="
cat /proc/uptime
# 输出示例：1234567.89 9876543.21
# 第一个数字：系统运行总秒数；第二个数字：所有 CPU 空闲总秒数

echo ""
echo "=== 当前 shell 的进程信息 ==="
echo "PID: $$"
echo "命令行:"
cat /proc/$$/cmdline | tr '\0' ' '
# 输出示例：bash
# 注意：/proc/PID/cmdline 使用空字符 \0 作为分隔符，需要 tr 转换

echo ""
echo "当前工作目录:"
ls -l /proc/$$/cwd
# 输出示例：lrwxrwxrwx 1 user user 0 ... /proc/700/cwd -> /home/user

echo ""
echo "可执行文件:"
ls -l /proc/$$/exe
# 输出示例：lrwxrwxrwx 1 root root 0 ... /proc/700/exe -> /usr/bin/bash

echo ""
echo "打开的文件描述符（前 5 个）:"
ls -l /proc/$$/fd/ | head -5
```

#### 2.6.2 /proc/PID/cmdline 详解

```bash
# cmdline 使用空字符 \0 分隔参数
cat /proc/$$/cmdline | xxd | head -3

# 00000000: 6261 7368 00                            bash.

# 正确读取方式：将 \0 转换为可读分隔符

echo ""

# 对于有空格参数的程序，每个参数独立显示
```

## 3. 命令详解

### 3.1 ps —— 查看进程快照

**ps**（**P**rocess **S**tatus）是最基础、最常用的进程查看命令。它显示执行命令那一刻的进程快照（snapshot），而非实时更新。

#### 3.1.1 ps 的三种参数风格

ps 命令有着 Unix 命令中最复杂的参数体系之一，因为它同时支持三种不同的参数风格：

| 风格 | 前缀 | 示例 | 历史来源 | 特点 |
|------|------|------|---------|------|
| **BSD 风格** | 无前缀 | `ps aux` | BSD Unix | 选项字母不加 `-` |
| **GNU 风格** | `--`（双横线） | `ps --pid 1234` | GNU 项目 | 长选项，语义明确 |
| **UNIX 风格** | `-`（单横线） | `ps -ef` | POSIX/Unix 标准 | 短选项，可组合 |

**重要：同名字母在不同风格下含义完全不同！**

```bash
# 三个最常用的组合——先建立肌肉记忆
ps aux      # BSD 风格：显示所有用户的所有进程（最常用）
ps -ef      # UNIX 风格：显示所有进程的完整信息
ps -ely     # UNIX 风格：显示所有进程（含线程），含 nice/priority

# 容易混淆的例子：
ps u        # BSD 风格：以"用户导向"格式显示当前用户的进程
ps -u       # UNIX 风格：等价于 ps -u $USER，按用户过滤
# 注意：ps u 和 ps -u 是完全不同的含义！
```

#### 3.1.2 ps aux —— BSD 风格详解（最常用）

```bash
# 显示所有用户的所有进程
ps aux | head -10
```

**ps aux 各列含义：**

| 列名 | 全称 | 含义 |
|------|------|------|
| `USER` | User | 进程所属用户 |
| `PID` | Process ID | 进程 ID |
| `%CPU` | CPU usage | CPU 使用率（占单核的百分比，多核可 > 100%） |
| `%MEM` | Memory usage | 物理内存使用率（占总量的百分比） |
| `VSZ` | Virtual SiZe | 虚拟内存大小（kB） |
| `RSS` | Resident Set Size | 常驻物理内存大小（kB） |
| `TTY` | TeleTYpe terminal | 控制终端（`?` 表示无终端，守护进程） |
| `STAT` | State | 进程状态代码（见 2.3 节） |
| `START` | Start time | 进程启动时间 |
| `TIME` | CPU time | 累计 CPU 使用时间 |
| `COMMAND` | Command | 命令名（含参数，宽度受限） |

#### 3.1.3 ps -ef —— UNIX 风格详解

```bash
# 显示所有进程的完整信息
ps -ef | head -10
```

**ps -ef 各列含义：**

| 列名 | 全称 | 含义 |
|------|------|------|
| `UID` | User ID | 进程所属用户名 |
| `PID` | Process ID | 进程 ID |
| `PPID` | Parent PID | 父进程 ID |
| `C` | CPU utilization | CPU 利用率（整数，已废弃的调度因子） |
| `STIME` | Start time | 进程启动时间 |
| `TTY` | Terminal | 控制终端 |
| `TIME` | CPU time | 累计 CPU 时间 |
| `CMD` | Command | 完整命令（含参数，宽度比 BSD 宽） |

#### 3.1.4 ps 关键参数表

**BSD 风格参数（无 `-` 前缀）：**

| 参数 | 说明 | 必选/可选 |
|------|------|----------|
| `a` | 显示所有用户的进程（与终端关联） | 可选 |
| `u` | 以用户导向格式输出 | 可选 |
| `x` | 显示无终端的进程（守护进程等） | 可选 |
| `aux` | 组合：显示所有进程 + 用户格式 | 可选 |

**UNIX 风格参数（`-` 前缀）：**

| 参数 | 说明 | 必选/可选 | 默认值 |
|------|------|----------|--------|
| `-e` | 显示所有进程 | 可选 | — |
| `-f` | 完整格式（full format） | 可选 | — |
| `-l` | 长格式（含 nice/priority） | 可选 | — |
| `-u USER` | 按用户过滤 | 可选 | 当前用户 |
| `-p PID` | 按 PID 过滤 | 可选 | 全部 |
| `-C CMD` | 按命令名过滤 | 可选 | 全部 |
| `-o FORMAT` | 自定义输出格式 | 可选 | 默认列 |
| `--sort SPEC` | 按指定列排序 | 可选 | PID |
| `-H` | 显示进程树（层级缩进） | 可选 | — |
| `--forest` | ASCII 艺术树格式显示 | 可选 | — |

#### 3.1.5 ps 自定义输出格式（-o）

```bash
# 自定义输出格式：只显示你关心的列
ps -eo pid,ppid,user,nice,stat,comm --sort=-%mem | head -10
# -e: 所有进程
# -o: 指定输出列（逗号分隔）
# --sort=-%mem: 按内存使用率降序排列（- 表示降序）

# 可用列名速查：
# pid, ppid, user, group, nice, pri, stat, pcpu, pmem,
# vsz, rss, sz, comm, cmd, args, etime, start, time,
# euser, egroup, fname, f

# 显示进程启动时间（经过时间）
ps -eo pid,comm,etime,start --sort=-etime | head -10
# etime: 从启动到现在经过的时间（格式：[[DD-]hh:]mm:ss）
```

#### 3.1.6 ps 常用场景速查

```bash
# 1. 按 CPU 使用率排序（找出最耗 CPU 的进程）
ps aux --sort=-%cpu | head -10

# 2. 按内存使用率排序
ps aux --sort=-%mem | head -10

# 3. 查看特定用户的进程
ps -u username

# 4. 查看特定命令的所有进程
ps -C nginx
ps -C python3 -o pid,ppid,user,%cpu,%mem,etime,args

# 5. 查看进程树（父子关系）
ps -ejH
ps auxf    # BSD 风格，用 ASCII 树显示

# 6. 显示线程（lightweight processes）
ps -eLf    # L 参数显示线程

# 7. 查看进程的安全上下文（SELinux）
ps -eZ     # 需要 SELinux 启用

# 8. 找出占用内存最多的 5 个进程
ps aux --sort=-%mem | head -6

# 9. 实时监控——每 1 秒刷新一次 ps
watch -n 1 'ps aux --sort=-%cpu | head -10'
# watch 不属于 ps，但组合使用非常实用
```

### 3.2 top —— 交互式进程监控

**top** 是 Linux 下最经典的系统监控工具。与 `ps` 的一次性快照不同，`top` 提供**实时、交互式**的进程视图。

```bash
# 启动 top（默认每 3 秒刷新一次）
top

# 常见启动参数
top -d 1           # 每 1 秒刷新（默认 3 秒）
top -u username    # 只显示指定用户的进程
top -p 1234,5678   # 只监控指定的 PID
top -b -n 1        # 批处理模式：输出一次后退出（适合脚本）
```

#### 3.2.1 top 输出解读


**第一行：系统概览**

| 字段 | 含义 |
|------|------|

| 字段 | 含义 |
|------|------|

| `sleeping` | 睡眠中的任务数 |

| `st` | steal | 被虚拟机管理程序（hypervisor）"窃取"的时间 |

**第四行 & 第五行：内存状态**

| 字段 | 含义 |
|------|------|
| `total` | 总内存量 |
| `free` | 空闲内存（完全未使用） |
| `used` | 已使用内存 |
| `buff/cache` | 用于缓冲区/缓存在内存（可被回收） |

### 3.3 htop —— top 的增强版

**htop** 是由 Hisham Muhammad 开发的交互式进程查看器，是 `top` 的现代替代品。它拥有彩色界面、鼠标支持、垂直和水平滚动、进程树视图等增强功能。

```bash
# 安装 htop
sudo apt install -y htop

# 启动 htop
htop

# 以树形视图启动
htop -t

# 只显示指定用户的进程
htop -u $USER

# 只显示指定 PID 的进程
htop -p 1234,5678
```

#### 3.3.1 htop vs top 对比

| 特性 | top | htop |
|------|-----|------|

### 3.4 atop —— 高级系统性能监控

**atop** 是一个高级的系统与进程监控工具，由 Gerlof Langeveld 开发。与 top/htop 不同，atop 的独特之处在于：

- **持久化日志**：atop 可以将性能数据写入日志，事后回放分析
- **资源全貌**：不仅监控 CPU 和内存，还监控磁盘 I/O、网络、进程调度
- **自动归档**：通过 `atop` 服务，可以 7x24 小时记录系统性能（日志每天自动轮转）

```bash
# 启动 atop（默认每 10 秒刷新）

# 回放历史日志
```

### 3.5 pidof —— 根据程序名查找 PID

**pidof** 查找指定程序的 PID。它是 `/sbin/pidof`，由 `killall5` 包提供。

```bash
# 查找 sshd 的 PID
pidof sshd
# 输出示例：1234 1235 1236
#（多个 PID 用空格分隔，因为有多个 sshd 进程）

# 只返回一个 PID（第一个匹配的）
pidof -s sshd
# -s: single shot，只返回一个

# 返回脚本程序 PID（需要 -x 参数）
pidof -x /path/to/script.sh
# -x: 也匹配 shell 脚本（默认只匹配原生可执行文件）

# 排除特定 PID
pidof sshd -o 1234
# -o: omit，排除 PID 1234。常用于在脚本中排除自身
pidof myscript.sh -o %PPID
# %PPID 表示排除父进程
```

### 3.6 pgrep —— 基于模式查找进程

**pgrep** 比 `pidof` 更强大，支持正则表达式模式匹配和丰富的过滤条件。

```bash
# 基本用法：按名称查找
pgrep bash
# 输出：所有名为 bash 的进程的 PID

# 使用完整命令行匹配（默认只匹配进程名）
pgrep -f "python3 /app/server.py"
# -f: 匹配完整命令行（而非仅进程名）

# 只匹配完全相同的进程名
pgrep -x bash
# -x: exact match，精确匹配进程名（而非子串）

# 使用正则表达式
pgrep '^ssh'
# 匹配以 "ssh" 开头的进程名

# 显示更多信息
pgrep -l bash       # 显示 PID 和进程名
pgrep -a bash       # 显示 PID 和完整命令行

# 按用户过滤
pgrep -u root sshd

# 按进程组过滤
pgrep -g 1000

# 按父进程 PID 过滤（查找某个进程的所有子进程）
pgrep -P 1234
# -P: Parent，查找 PPID 为 1234 的所有进程

# 显示进程的最老/最新实例
pgrep -o bash     # oldest，最早启动的 bash
pgrep -n bash     # newest，最近启动的 bash

# 反转匹配
pgrep -v -u root  # 不是 root 用户的所有进程

# 按终端过滤
pgrep -t tty1     # 在 tty1 终端上的进程
```

#### 3.6.1 pgrep 参数表

| 参数 | 说明 | 必选/可选 | 默认值 |
|------|------|----------|--------|
| `-f` | 匹配完整命令行（而非仅进程名） | 可选 | 关闭 |
| `-l` | 同时显示 PID 和进程名 | 可选 | 关闭 |
| `-a` | 同时显示 PID 和完整命令行 | 可选 | 关闭 |
| `-x` | 精确匹配进程名（不匹配子串） | 可选 | 关闭 |
| `-u USER` | 按有效用户过滤 | 可选 | 全部用户 |
| `-U USER` | 按实际用户过滤 | 可选 | 全部用户 |
| `-g GID` | 按进程组过滤 | 可选 | 全部 |
| `-P PPID` | 按父进程 PID 过滤 | 可选 | 全部 |
| `-t TTY` | 按控制终端过滤 | 可选 | 全部 |
| `-o` | 只返回最老的进程（按启动时间） | 可选 | 关闭 |
| `-n` | 只返回最新的进程（按启动时间） | 可选 | 关闭 |
| `-v` | 反转匹配（显示不匹配的进程） | 可选 | 关闭 |

```bash
# 实战示例：pgrep 的多种用法
# 1. 检查 nginx 是否在运行
if pgrep -x nginx > /dev/null; then
    echo "nginx 正在运行"
else
    echo "nginx 未运行"
fi

# 2. 查找所有 Python 进程并显示详情

# 3. 统计指定用户的进程数

pgrep -P 1234 -l
```

### 3.7 pkill —— 按名称（或其他条件）发送信号

**pkill** 是 `pgrep` 的"发送信号"版本——它使用与 `pgrep` 相同的匹配逻辑，但向匹配的进程发送信号。

```bash
# 基本用法：向所有匹配的进程发送 SIGTERM
pkill nginx
# 等效于：kill $(pgrep nginx)

# 发送特定信号
pkill -HUP nginx       # 重新加载 nginx 配置
pkill -TERM java        # 优雅终止 Java 进程
pkill -9 myapp          # 强制杀死 myapp（不推荐，除非必要时）

# 使用完整命令行匹配
pkill -f "python3 /app/server.py"

# 精确匹配
pkill -x nginx

# 只杀最老/最新的进程
pkill -o myapp    # 只杀最早的实例
pkill -n myapp    # 只杀最新的实例

# 按用户过滤
pkill -u nobody myworker

# 按终端过滤
pkill -t pts/1
# 杀掉 pts/1 终端上的所有进程（强制注销该用户）
```

| 参数 | 说明 | 必选/可选 | 默认值 |

| `-SIGNAL` | 指定发送的信号（可省略 SIG 前缀） | 可选 | `-TERM` (15) |
| `-f` | 匹配完整命令行 | 可选 | 关闭 |
| `-x` | 精确匹配进程名 | 可选 | 关闭 |
| `-u USER` | 按有效用户过滤 | 可选 | 全部用户 |

| `-t TTY` | 按控制终端过滤 | 可选 | 全部 |
| `-o` | 只匹配最老的进程 | 可选 | 关闭 |

| `-i` | 忽略大小写 | 可选 | 关闭 |

### 3.8 kill —— 向指定 PID 发送信号

**kill** 是最基本的信号发送工具。尽管名字叫 "kill"，它的真正功能是**向进程发送信号**，而不仅仅是"杀死"进程。

```bash
# 基本语法
kill [ -SIGNAL | -s SIGNAL ] PID ...

# 发送 SIGTERM（默认）
kill 1234
kill -TERM 1234
kill -s TERM 1234
kill -15 1234

# 发送 SIGKILL（强制终止）
kill -9 1234
kill -KILL 1234

# 发送 SIGHUP（重新加载配置）
kill -HUP 1234

# 发送 SIGSTOP（暂停进程）
kill -STOP 1234

# 发送 SIGCONT（恢复进程）
kill -CONT 1234

# 向多个 PID 发送信号
kill -TERM 1234 5678 9012
```

#### 3.8.1 kill 参数表

| 参数 | 说明 | 必选/可选 | 默认值 |
|------|------|----------|--------|
| `-l` | 列出所有信号名 | 可选 | — |
| `-l SIGNAL` | 显示指定信号的编号 | 可选 | — |
| `-s SIGNAL` | 指定信号名 | 可选 | `TERM` |
| `-SIGNAL` | 指定信号（简写） | 可选 | `TERM` |
| `PID` | 目标进程 ID | **必选** | — |

```bash
# 列出所有信号
kill -l
# 输出示例（共 64 个信号）：
#  1) SIGHUP       2) SIGINT       3) SIGQUIT      4) SIGILL
#  5) SIGTRAP      6) SIGABRT      7) SIGBUS       8) SIGFPE
#  9) SIGKILL     10) SIGUSR1     11) SIGSEGV     12) SIGUSR2
# 13) SIGPIPE     14) SIGALRM     15) SIGTERM     16) SIGSTKFLT
# 17) SIGCHLD     18) SIGCONT     19) SIGSTOP     20) SIGTSTP
# ...

# 查询特定信号的编号
kill -l KILL
# 输出：9

kill -l TERM
# 输出：15
```

#### 3.8.2 kill 的特殊 PID 值

向 PID 传 0 不会杀死任何进程，但会检查是否可以向目标发送信号：

```bash
# 检查 PID 是否存在且有权限向其发送信号
kill -0 1234 && echo "进程存在" || echo "进程不存在或无权限"
# -0: 不发送任何信号，只做权限检查
```

### 3.9 killall —— 按进程名杀死所有匹配进程

**killall** 根据进程名（而非 PID）发送信号给所有匹配的进程。

```bash
# 基本用法
killall nginx
# 杀死所有名为 nginx 的进程（发送 SIGTERM）

# 发送特定信号
killall -HUP nginx

# 交互模式（逐个确认）
killall -i myapp
# 输出：Kill myapp(12345) ? (y/N)
# 输入 y 确认，n 跳过

# 忽略大小写
killall -I MyApp

# 只杀死指定时间之前启动的进程
killall -o 3600 myapp
# -o: older than，杀死运行超过 3600 秒（1 小时）的进程
# 时间格式：数字=秒，可以带后缀 m（分钟）、h（小时）、d（天）

# 只杀死指定时间以内启动的进程
killall -y 300 myapp
# -y: younger than，杀死运行不到 300 秒（5 分钟）的进程

# 按用户过滤
killall -u nobody myworker
```

### 3.10 nice / renice —— 调整进程优先级

#### 3.10.1 nice —— 以指定优先级启动进程

```bash
# 基本语法
nice [OPTION] COMMAND [ARG...]

# 以较低优先级启动（nice = 10）
nice -n 10 gzip hugefile.log

# 以较高优先级启动（nice = -5）——需要 root
sudo nice -n -5 /usr/local/bin/critical-task

# 不带 -n 时，默认 nice = 10
nice mysqldump mydb > backup.sql

# 查看启动后的实际 nice 值
nice -n 15 sleep 100 &
ps -o pid,nice,comm -p $!
kill $! 2>/dev/null
```

#### 3.10.2 renice —— 修改运行中进程的优先级

```bash
# 基本语法
renice [-n] PRIORITY [ -g | -p | -u ] TARGET ...

# 按 PID 修改
renice -n 10 -p 1234
# 将 PID 1234 的 nice 值设为 10

# 按进程组修改（GID）
renice -n 5 -g 1000

# 按用户修改（所有该用户的进程）
renice -n 10 -u nobody

# 简写形式（省略 -p）
renice 10 1234

# 提高优先级（负数）——需要 root
sudo renice -n -5 -p 1234
```

#### 3.10.3 nice/renice 参数表

| 参数 | 说明 | 必选/可选 | 默认值 |
|------|------|----------|--------|
| `-n N` 或 `-N` | nice 值偏移量 | **必选** | 10（nice 命令） |
| `-p PID` | 按 PID 指定目标 | 可选（默认） | — |
| `-g GID` | 按进程组 ID 指定目标 | 可选 | — |
| `-u USER` | 按用户名指定目标 | 可选 | — |

```bash
# 权限规则测试
# 普通用户可以增大 nice 值（降低优先级）
renice -n 10 -p $$
# 会成功

# 普通用户不可以减小 nice 值（提高优先级）
renice -n -5 -p $$ 2>&1 || echo "权限不足——需要 root"
# 报错：renice: failed to set priority: Permission denied

# 普通用户再次增大 nice 值（14 > 10）
renice -n 14 -p $$
# 会成功——一旦提高了 nice 值，可以继续提高
```

### 3.11 nohup —— 忽略 HUP 信号

**nohup**（**no** **h**ang**up**）让进程在终端关闭（挂断）后继续运行。通常用于在终端中启动一个长时间运行的任务，然后安全地关闭终端。

#### 3.11.1 问题场景

```
+------------------------------------------------------------------+
|                    终端关闭时的信号流                               |
|                                                                  |
|  终端 (terminal)                                                  |
|     │                                                            |
|     │  你关闭终端窗口 / SSH 断开连接                                |
|     │                                                            |
|     v                                                            |
|  bash (PID 700)  ← 收到 SIGHUP                                   |
|     │                                                            |
|     │  bash 向它的所有子进程转发 SIGHUP                           |
|     │                                                            |
|     v                                                            |
|  ├── vim (PID 701)      ← 收到 SIGHUP → 退出                     |
|  ├── sleep (PID 702)    ← 收到 SIGHUP → 退出                     |
|  └── tar (PID 703)      ← 收到 SIGHUP → 退出（备份中断！）        |
|                                                                  |
|  问题：你启动了一个需要运行 2 小时的备份脚本，                    |
|        关闭 SSH 会话后备份被中断。                                 |
|                                                                  |
|  解决：nohup                                                     |
|  nohup ./backup.sh &                                             |
|  → 进程忽略 SIGHUP，终端关闭后继续运行                             |
+------------------------------------------------------------------+
```

#### 3.11.2 nohup 基本用法

```bash
# 基本用法
nohup COMMAND [ARG...] &

# 示例：在后台运行备份脚本，关闭终端后继续运行
nohup ./long-backup.sh &

# 输出默认重定向到 nohup.out
# 正常输出（stdout + stderr）→ nohup.out
# 如果当前目录不可写 → ~/nohup.out

# 指定输出文件
nohup ./backup.sh > backup.log 2>&1 &

# 查看 nohup 进程
jobs          # 如果在当前 shell 中启动
ps aux | grep backup.sh
```

#### 3.11.3 nohup 的执行过程

```bash
# 演示 nohup 的行为
echo '#!/bin/bash
echo "脚本启动，PID: $$"
for i in 1 2 3 4 5; do
    echo "工作... $i"
    sleep 1
done
echo "完成"' > /tmp/test-nohup.sh
chmod +x /tmp/test-nohup.sh

# 用 nohup 启动
nohup /tmp/test-nohup.sh > /tmp/nohup-test.log 2>&1 &

# 查看日志
sleep 6
cat /tmp/nohup-test.log
# 输出：
# 脚本启动，PID: xxxx
# 工作... 1
# 工作... 2
# 工作... 3
# 工作... 4
# 工作... 5
# 完成

# 清理
rm -f /tmp/test-nohup.sh /tmp/nohup-test.log
```

#### 3.11.4 nohup 参数表

| 参数 | 说明 | 必选/可选 | 默认值 |
|------|------|----------|--------|
| `--help` | 显示帮助信息 | 可选 | — |
| `--version` | 显示版本信息 | 可选 | — |
| `COMMAND` | 要执行的命令 | **必选** | — |

### 3.12 disown —— 从作业列表中移除

**disown** 是 bash 内置命令，用于将一个后台作业从 shell 的作业表中移除。这样即使 shell 退出，该作业也不会收到 SIGHUP。

```
+------------------------------------------------------------------+
|                    nohup vs disown                                |
|                                                                  |
|  nohup（事前防御）：                     disown（事后补救）：       |
|                                                                  |
|  $ nohup ./script.sh &                 $ ./script.sh &           |
|  启动时就忽略 HUP                        (已经在前台/后台运行)      |
|                                         $ Ctrl+Z                 |
|                                         $ bg                     |
|                                         $ disown %1              |
|                                         从作业表移除               |
|                                                                  |
|  使用场景：                          使用场景：                    |
|  - 你知道这个任务要跑很久               - 你忘记用 nohup 了          |
|  - 启动时就规划好了                     - 任务已经在运行中           |
|                                         - 你突然需要登出           |
+------------------------------------------------------------------+
```

#### 3.12.1 disown 用法

```bash
# 基本用法
# 1. 先启动任务（或已有任务在运行）
sleep 3600 &
# 2. 查看作业列表
jobs
# 输出：[1]+  Running   sleep 3600 &

# 3. 从作业表中移除（shell 退出时不会发 SIGHUP）
disown %1

# disown 的三种形式
disown %1          # 从作业表移除，但进程继续运行
disown -h %1       # 不移除，但标记为"shell 退出时不发 SIGHUP"
disown -r          # 从作业表移除所有正在运行的作业
disown -a          # 从作业表移除所有作业

# 验证：作业表不再有条目
jobs
# 输出：（空）

# 但进程仍在运行
kill %1 2>/dev/null || ps -p $(pgrep sleep) > /dev/null 2>&1 && echo "进程仍存活"
```

### 3.13 jobs / fg / bg / wait —— Shell 作业控制

#### 3.13.1 作业控制概念

Shell 的**作业控制（Job Control）**允许你在一个终端中管理多个进程——暂停、恢复、前后台切换。

```
+------------------------------------------------------------------+
|                    作业控制示意图                                   |
|                                                                  |
|  终端                                                             |
|  ┌─────────────────────────────────────────────────────────────┐ |
|  │  $ vim file.txt            ← 前台作业（占用终端）              │ |
|  │  [Ctrl+Z]                                                   │ |
|  │  [1]+  Stopped   vim       ← 暂停，返回 shell                │ |
|  │                                                             │ |
|  │  $ sleep 100 &             ← 后台作业                        │ |
|  │  [2] 12345                                                   │ |
|  │                                                             │ |
|  │  $ jobs                                                     │ |
|  │  [1]+  Stopped    vim file.txt                               │ |
|  │  [2]-  Running    sleep 100 &                                │ |
|  │                                                             │ |
|  │  $ fg %1                  ← 将 vim 恢复到前台                │ |
|  │  [vim 界面]                                                  │ |
|  └─────────────────────────────────────────────────────────────┘ |
+------------------------------------------------------------------+
```

#### 3.13.2 jobs —— 查看作业列表

```bash
# 创建一些作业用于演示
sleep 100 &
sleep 200 &
sleep 300 &

# 查看所有作业
jobs
# 输出：
# [1]   Running                 sleep 100 &
# [2]-  Running                 sleep 200 &
# [3]+  Running                 sleep 300 &
#  + 表示当前作业（fg/bg 默认操作的对象）
#  - 表示上一个作业

# 只显示正在运行的作业
jobs -r

# 只显示已停止的作业
jobs -s

# 显示作业的 PID
jobs -l
# 输出包含 PID：
# [1]   12345 Running          sleep 100 &

# 只显示指定作业
jobs %2

# 清理
kill %1 %2 %3 2>/dev/null
```

**jobs 参数表：**

| 参数 | 说明 | 必选/可选 |
|------|------|----------|
| `-l` | 同时显示 PID | 可选 |
| `-p` | 只显示 PID | 可选 |
| `-r` | 只显示运行中的作业 | 可选 |
| `-s` | 只显示已停止的作业 | 可选 |
| `%N` | 指定作业编号 | 可选 |

#### 3.13.3 fg —— 将后台作业切换到前台

```bash
# 将最近一个作业切换到前台
fg

# 将指定编号的作业切换到前台
fg %1

# 将指定名称的作业切换到前台
fg %sleep
# % 后跟命令名的前缀，匹配最近的以该前缀开头的作业

# 将指定字符串匹配的作业切换到前台
fg %?vim
# %? 后跟字符串，匹配命令行包含该字符串的作业

# 演示
sleep 100 &
jobs
fg %1
# sleep 100 现在在前台运行
# 用 Ctrl+C 终止
```

#### 3.13.4 bg —— 在后台恢复已停止的作业

```bash
# 典型场景：在 vim 中按了 Ctrl+Z，vim 被暂停
# vim         ← 现在在后台 Stopped 状态
# 用 bg 让它在后台继续运行
bg %1
# 但 vim 是需要终端的交互程序，在后台可能无法正常工作
# 更适合的场景：一个普通命令被 Ctrl+Z 暂停后恢复

# 演示
sleep 300 &
# [1] 12345
sleep 300
# 这是一个前台命令
# 按 Ctrl+Z
# [2]+  Stopped   sleep 300
bg %2
# [2]+ sleep 300 &
# 在后台继续运行
jobs
# [1]   Running   sleep 300 &
# [2]-  Running   sleep 300 &

kill %1 %2 2>/dev/null
```

#### 3.13.5 wait —— 等待后台作业完成

```bash
# wait 等待指定的后台进程完成，然后返回其退出码

# 等待所有后台作业完成
wait
echo "所有后台作业完成"

# 等待指定作业
sleep 5 &
SLEEP_JOB=$!
wait $SLEEP_JOB
echo "sleep 5 已完成，退出码：$?"

# 等待指定作业编号
sleep 3 &
wait %1
echo "作业 %1 已完成"

# 实战示例：并行处理，然后等待全部完成
echo "开始并行处理..."
for i in 1 2 3 4 5; do
    ( sleep $((RANDOM % 5 + 1)); echo "任务 $i 完成" ) &
done
echo "等待所有任务完成..."
wait
echo "全部任务完成！"

# wait 也可用于等待进程退出（发送信号后的等待）
sleep 100 &
W_PID=$!
kill -TERM $W_PID
wait $W_PID 2>/dev/null
echo "进程 $W_PID 已退出"
```

### 3.14 /proc/PID/status 与 /proc/PID/cmdline

这两个 `/proc` 目录下的文件已在 2.6 节介绍过。以下是一些实战用例：

```bash
# === /proc/PID/status 实战用例 ===

# 查看特定进程的详细状态
PID_TO_CHECK=$$
echo "=== PID: $PID_TO_CHECK ==="

# 提取进程名称
awk '/^Name:/ {print $2}' /proc/$PID_TO_CHECK/status

# 提取进程状态
awk '/^State:/ {print $2, $3}' /proc/$PID_TO_CHECK/status

# 提取内存使用（物理内存 RSS）
awk '/^VmRSS:/ {print $2, $3}' /proc/$PID_TO_CHECK/status
awk '/^VmSize:/ {print $2, $3}' /proc/$PID_TO_CHECK/status

# 提取线程数
awk '/^Threads:/ {print $2}' /proc/$PID_TO_CHECK/status

# 提取父进程 PID
awk '/^PPid:/ {print $2}' /proc/$PID_TO_CHECK/status

# 提取 UID
awk '/^Uid:/ {print $2, $3, $4, $5}' /proc/$PID_TO_CHECK/status

# 提取上下文切换次数
awk '/^voluntary_ctxt_switches:/ {print $2}' /proc/$PID_TO_CHECK/status
awk '/^nonvoluntary_ctxt_switches:/ {print $2}' /proc/$PID_TO_CHECK/status

# === /proc/PID/cmdline 实战用例 ===

# 查看进程的完整命令行（将 \0 替换为空格）
cat /proc/$PID_TO_CHECK/cmdline | tr '\0' ' '
echo ""

# 只看进程名（第一个字段）
cut -d '' -f1 /proc/$PID_TO_CHECK/cmdline | tr '\0' '\n'
# 注意：更可靠的方式：
cat /proc/$PID_TO_CHECK/comm
# /proc/PID/comm 只包含进程名（不含路径和参数）

# 在一行内显示所有运行中进程的命令行
for pid in /proc/[0-9]*/; do
    pid=${pid%/}; pid=${pid#/proc/}
    if [ -f /proc/$pid/cmdline ]; then
        printf "PID %-6s: " "$pid"
        tr '\0' ' ' < /proc/$pid/cmdline 2>/dev/null
        echo ""
    fi
done 2>/dev/null | head -10
```

```bash
for pid in /proc/[0-9]*/; do
    pid=${pid%/}; pid=${pid#/proc/}

        name=$(cat /proc/$pid/comm 2>/dev/null)

```

```bash
echo "=== 僵尸进程 ==="
```

```bash
echo "=== 按物理内存使用排名（前5） ==="
```

## 5. 常见错误与排错

### 5.1 kill 命令"不起作用"——用错了信号

**现象：**

```bash
kill 12345
# 进程没有退出

ps -p 12345
# 进程仍然在运行
```

**原因：** `kill` 默认发送的是 SIGTERM (15)，进程可以选择**捕获并忽略**这个信号。某些程序（如 `dd`、数据库服务）会推迟或拒绝 SIGTERM。

**解决：**

```bash
# 先确认进程确实收到了信号
kill -0 12345 && echo "进程存在"

# 尝试更强的信号
kill -QUIT 12345   # SIGQUIT — 比 SIGTERM 更强，通常会产生 core dump
kill -INT 12345    # SIGINT — 等同于 Ctrl+C

# 如果以上都不行，最后的手段
kill -9 12345      # SIGKILL — 内核直接终止，不可被忽略
```

**调试技巧——检查进程正在等待什么：**

```bash
# 查看 D 状态（不可中断睡眠）的进程——通常只能等 I/O 完成
ps -eo pid,stat,wchan,comm | grep '^.* D'
# wchan (wait channel): 显示进程正在等待什么内核资源
```

### 5.2 僵尸进程 (Zombie) 无法清理

**现象：**

```bash
ps aux | grep Z
# 显示状态为 Z 的进程

kill -9 12345
# 僵尸进程依然存在
```

**原因：** 僵尸进程**已经死了**——它已经结束了执行，只是父进程还没有读取它的退出状态。你不能杀死一个已经死了的东西。解决僵尸进程的唯一方法是让**父进程**调用 `wait()` 或终止父进程。

**解决：**

```bash
# 1. 查找僵尸进程的父进程
ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/ {print "僵尸 PID:", $1, "父进程 PID:", $2}'

# 2. 查看父进程是否还在运行
ps -p PPID

# 3. 方案 A：向父进程发送 SIGCHLD（提示子进程已退出）
kill -CHLD PPID

# 4. 方案 B：终止父进程（让 systemd 收养僵尸进程并清理）
kill PPID
# 如果父进程是重要的服务，此方法可能影响服务

# 注意：少量僵尸进程是正常的，大多数僵尸进程很快会被父进程清理。
# 仅在僵尸进程持续累积时才需要干预。
```

### 5.3 nice 值修改权限问题

**现象：**

```bash
renice -n -5 -p 12345
# 输出：renice: failed to set priority for 12345 (process ID): Permission denied
```

**原因：** 普通用户只能增大 nice 值（降低优先级），不能减小 nice 值（提高优先级）。只有 root 或具有 `CAP_SYS_NICE` 能力的进程可以设置负 nice 值。

**另外：** 一旦你在某次 `renice` 中提高了 nice 值，之后就不能再降低它（即使降低后的值仍大于 0）：

```bash
# 假设当前 nice = 0
renice -n 10 -p 12345    # 成功：0 → 10
renice -n 5 -p 12345     # 失败：10 → 5 是降低 nice 值
renice -n 15 -p 12345    # 成功：10 → 15 是继续提高
```

**解决：**

```bash
# 使用 sudo 提高优先级
sudo renice -n -5 -p 12345

# 或在启动时就以较高优先级运行
sudo nice -n -5 ./critical-task
```

### 5.4 pgrep 匹配不到进程

**现象：**

```bash
pgrep my-python-app
# 没有输出——但进程确实在运行

ps aux | grep python
# 显示 python3 /opt/myapp/server.py
```

**原因：** `pgrep` 默认只匹配**进程名**（即 `/proc/PID/comm` 的内容，通常限制为 15 个字符），不匹配完整命令行。`python3` 的进程名是 `python3`（15 字符限制），不是 `my-python-app`。完整的命令行参数需要 `-f` 参数才能匹配。

**解决：**

```bash
# 方案 1：使用 -f 匹配完整命令行
pgrep -f "my-python-app"

# 方案 2：使用 -f 匹配参数中的某个唯一字符串
pgrep -f "/opt/myapp/server.py"

# 方案 3：使用 -a 查看实际匹配到了什么
pgrep -a python3
# 帮助理解进程名和完整命令行的区别

# 查看进程名（/proc/PID/comm 的内容，受 15 字符限制）
cat /proc/$(pgrep -f server.py | head -1)/comm 2>/dev/null
```

### 5.5 killall 杀掉了不该杀的进程

**现象：**

```bash
killall python
# 所有 Python 进程都被终止——包括正在运行的 Jupyter Notebook 和另一个开发服务器
```

**原因：** `killall` 匹配**进程名**，而所有 Python 程序的进程名都是 `python3`（或 `python`）。`killall java` 会杀死所有 Java 进程；`killall nginx` 会杀死所有 nginx 进程（包括 master 和所有 worker）。

**解决：**

```bash
# 方案 1：先查看会匹配哪些进程
pgrep -a python3

# 方案 2：使用 pkill 的 -f 匹配更具体的命令行
pkill -f "/opt/myapp/server.py"

# 方案 3：使用 killall 的交互模式（逐个确认）
killall -i python3
# 输出：Kill python3(12345) ? (y/N)  ← 逐个确认

# 方案 4：使用 killall -y（按启动时间过滤）
killall -y 60 python3
# 只杀死运行不到 60 秒的进程（排除长时间运行的服务）

# 方案 5：先 pgrep 确认再 kill
pgrep -a python3 | grep -i "myapp" | awk '{print $1}' | xargs kill
```

### 5.6 nohup 的输出丢失

**现象：**

```bash
nohup ./long-task.sh &
# 关闭终端后，回来发现 nohup.out 是空的或不完整
```

**原因：**

1. **输出缓冲（Buffering）**：程序使用标准 C 库的缓冲 I/O，数据在缓冲区中尚未写入文件。当进程正常结束时缓冲区会被刷新，但如果进程被过早终止，缓冲区中的数据就会丢失。
2. **写入错误**：`nohup.out` 所在目录不可写或磁盘空间不足。
3. **重定向覆盖**：如果你已经重定向了输出（`> output.log 2>&1`），nohup 不会再创建 `nohup.out`。

**解决：**

```bash
# 方案 1：使用 stdbuf 禁用输出缓冲
stdbuf -oL nohup ./long-task.sh > output.log 2>&1 &
# -oL: 对标准输出使用行缓冲（line buffering）

# 方案 2：使用 unbuffer（需要 expect 包）
sudo apt install -y expect
unbuffer nohup ./long-task.sh > output.log 2>&1 &

# 方案 3：在脚本中显式刷新输出
# 在你的脚本中添加：
# export PYTHONUNBUFFERED=1    # Python 脚本
# stdbuf -oL ...               # 通用方案
# 或使用 flush() 调用
```

### 5.7 fg 操作了错误的作业

**现象：**

```bash
fg
# 本想把 vim 切回前台，结果把一个 sleep 99999 拉到了前台
```

**原因：** `fg` 默认操作的是**当前作业**（`jobs` 中用 `+` 标记的那个），不一定是你要的那个。

**解决：**

```bash
# 总是先用 jobs 查看作业列表
jobs
# 输出：
# [1]   Stopped    vim file.txt
# [2]-  Stopped    sleep 99999
# [3]+  Stopped    top

# 明确指定要操作哪个作业
fg %1          # 按作业编号
fg %vim        # 按命令名前缀
fg %?txt       # 按命令行包含的字符串

# 记住：
# %1  = 作业编号 1
# %str = 命令以 str 开头
# %?str = 命令行包含 str
# %%   = 当前作业
# %+   = 当前作业（同 %%）
# %-   = 上一个作业
```

### 5.8 SIGTSTP（Ctrl+Z）无法停止进程

**现象：**

```bash
./run-server.sh
# 按 Ctrl+Z 没有反应，进程继续运行
```

**原因：** 进程阻塞了 SIGTSTP 信号，或进程处于**不可中断睡眠（D 状态）**等待 I/O。

**解决：**

```bash
# 确认进程状态
ps -p PID -o pid,stat,wchan,comm
# 如果 STAT 是 D：进程在等待 I/O 完成，无法被信号中断
#  只能等待 I/O 完成，或重启系统

# 如果可以使用 htop
# 在 htop 中选中进程 → F9 → 选择 SIGSTOP（如果进程可停止）
```

### 5.9 误用 kill -9 导致数据丢失

**现象：**

使用 `kill -9` 杀死了一个数据库进程或文件写入进程，导致数据文件损坏。

**原因：** `SIGKILL` 不允许进程执行清理操作——缓冲区未刷新、锁未释放、临时文件未删除。

**解决与预防：**

```bash
# 预防：遵循"先礼后兵"原则
# 第一步：SIGTERM（礼貌地请求退出）
kill -TERM $PID
sleep 3

# 第二步：检查是否退出
if kill -0 $PID 2>/dev/null; then
    echo "SIGTERM 未生效，再等待 5 秒..."
    sleep 5
fi

# 第三步：仍存活，尝试 SIGINT
if kill -0 $PID 2>/dev/null; then
    echo "发送 SIGINT..."
    kill -INT $PID
    sleep 2
fi

# 第四步：最后手段——SIGKILL
if kill -0 $PID 2>/dev/null; then
    echo "警告：使用 SIGKILL 强制终止！数据可能丢失！"
    kill -KILL $PID
fi
```

## 6. 进阶延伸

### 6.1 进程的完整生命周期

了解进程从创建到消亡的完整流程，有助于理解各种进程管理工具背后的原理：

```
+------------------------------------------------------------------+
|                    进程生命周期                                     |
|                                                                  |
|  fork()         父进程调用 fork()，创建一个自身的副本                |
|     │                                                             |
|     v                                                             |
|  exec()         子进程调用 exec()，用新程序替换自身的内存映像       |
|     │                                                             |
|     v                                                             |
|  运行            进程执行新程序的代码                                |
|     │                                                             |
|     ├── SIGSTOP/SIGTSTP → 停止 (T) → SIGCONT → 继续运行          |
|     │                                                             |
|     ├── 等待 I/O → 不可中断睡眠 (D) → I/O 完成 → 继续运行          |
|     │                                                             |
|     └── 等待事件 → 可中断睡眠 (S) → 事件到达 → 继续运行            |
|     │                                                             |
|     v                                                             |
|  exit()          进程调用 exit() 或接收到终止信号                    |
|     │                                                             |
|     v                                                             |
|  僵尸 (Z)        进程已退出，等待父进程调用 wait() 回收              |
|     │                                                             |
|     └── 父进程 wait() → 进程被回收，完全消失                       |
+------------------------------------------------------------------+
```

### 6.2 使用 /proc/sys 动态调整内核参数

`/proc/sys/` 下的许多文件是可写的，允许在不重启系统的情况下调整内核参数：

```bash
# 查看所有可调参数
sudo sysctl -a | head -20

# 常见调优参数
# 1. 调整进程可打开的最大文件数
cat /proc/sys/fs/file-max
# 输出：9223372036854775807

# 2. 调整单个进程的最大文件描述符数
ulimit -n            # 查看当前限制
ulimit -n 65536      # 临时提高限制

# 3. 内核 PID 的最大值
cat /proc/sys/kernel/pid_max
# 输出：4194304（默认约 400 万）

# 4. 调整 swap 的使用倾向（0=尽量不用 swap，100=积极使用 swap）
cat /proc/sys/vm/swappiness
# 输出：60（默认值）
# sudo sysctl vm.swappiness=10  # 降低 swap 使用倾向

# 5. 使用 sysctl 持久化配置
# 编辑 /etc/sysctl.d/99-custom.conf：
# vm.swappiness=10
# fs.file-max=2097152
# 应用：sudo sysctl -p /etc/sysctl.d/99-custom.conf
```

### 6.3 cgroups —— 现代进程资源控制

**cgroups**（**C**ontrol **Groups**，控制组）是 Linux 内核提供的进程资源限制、优先级控制、统计和隔离机制。它是 Docker、systemd、Kubernetes 等工具的基础。

```bash
# 查看当前进程所属的 cgroup
cat /proc/$$/cgroup
# 输出示例：
# 0::/user.slice/user-1000.slice/session-3.scope

# 使用 systemd-cgls 查看 cgroup 树
systemd-cgls 2>/dev/null || echo "需要 systemd"

# 使用 systemd-cgtop 监控 cgroup 资源使用
systemd-cgtop 2>/dev/null || echo "需要 systemd"

# 使用 systemd-run 在临时 cgroup 中运行命令（带资源限制）
sudo systemd-run --scope -p CPUQuota=50% -p MemoryMax=512M \
  --user stress-ng --cpu 2 --timeout 60s

# cgroups v2 的关键文件：
# /sys/fs/cgroup/  — cgroups v2 的统一层级
ls /sys/fs/cgroup/
```

### 6.4 作业控制的高级用法

#### 6.4.1 配合 bash 的 `trap` 捕获信号

```bash
# 编写一个脚本，优雅地处理 SIGINT 和 SIGTERM
cat > /tmp/trap-demo.sh << 'SCRIPT'
#!/bin/bash

cleanup() {
    echo ""
    echo "收到终止信号，正在清理..."
    # 在这里执行清理操作
    rm -f /tmp/trap-demo-temp-*.txt
    echo "清理完成，退出。"
    exit 0
}

# 设置信号处理器
trap cleanup SIGINT SIGTERM

echo "脚本运行中（PID: $$）"
echo "按 Ctrl+C 或发送 SIGTERM 来测试..."
echo ""

# 模拟长时间运行的任务
counter=0
while true; do
    echo "[$(date +%H:%M:%S)] 工作中... 第 $((++counter)) 次"
    sleep 1
done
SCRIPT
chmod +x /tmp/trap-demo.sh

echo "运行 /tmp/trap-demo.sh 然后按 Ctrl+C 测试"
echo "（不在此自动运行，需手动执行）"
```

### 6.5 使用 strace 追踪进程行为

**strace** 可以追踪一个进程进行的系统调用（system call），是排查进程行为的最强大工具之一：


### 6.7 负载平均值（Load Average）深入理解

```
+------------------------------------------------------------------+
|                    负载平均值的含义                                  |
|                                                                  |
|  load average 不是 CPU 使用率！                                    |
|                                                                  |
|  CPU 使用率 = CPU 忙碌的时间比例（可以一直 100%）                   |
|  负载平均值 = 等待 CPU + 等待 I/O 的进程平均数                     |
|                                                                  |
|  0.15 0.22 0.18（负载）→ 系统非常空闲              |
|  1.00 1.00 1.00（负载）→ 单核系统满载               |
|  4.00 3.50 3.20（负载）→ 4 核系统接近满载            |
|                                                                  |
|  判断标准：                                                       |
|  - 负载 < CPU 核心数：系统有余力                                   |
|  - 负载 = CPU 核心数：系统正好满载                                 |
|  - 负载 > CPU 核心数：系统过载，有进程在排队等待                   |
|                                                                  |
|  注意：高负载 + 低 CPU 使用率 → 大量进程在等待 I/O                 |
|        低负载 + 高 CPU 使用率 → 少数进程在密集计算                 |
|                                                                  |
|  查看 CPU 核心数：                                                |
|  nproc                                                           |
|  grep -c ^processor /proc/cpuinfo                                |
+------------------------------------------------------------------+
```

```bash
# 查看 CPU 核心数和负载
echo "CPU 核心数: $(nproc)"
echo "当前负载: $(cat /proc/loadavg | awk '{print $1, $2, $3}')"

# 判断系统是否过载
cores=$(nproc)
load1=$(cat /proc/loadavg | awk '{print $1}')
if (( $(echo "$load1 > $cores" | bc -l 2>/dev/null || echo 0) )); then
    echo "警告：系统过载（负载 $load1 > 核心数 $cores）"
else
    echo "系统负载正常（负载 $load1 <= 核心数 $cores）"
fi
```

### 6.8 进程管理最佳实践总结

```
+------------------------------------------------------------------+
|               进程管理最佳实践速查                                  |
|                                                                  |
|  1. 终止进程：先 SIGTERM，等待，再 SIGKILL                          |
|     kill PID        → 等待 3-5 秒                                |
|     kill -0 PID     → 检查是否还活着                              |
|     kill -KILL PID  → 最后手段                                    |
|                                                                  |
|  2. 查找进程：pgrep 优先于 ps | grep                               |
|     pgrep -a nginx        （直接获得 PID 和命令行）               |
|     ps aux | grep nginx   （需要额外过滤 grep 自身）              |
|                                                                  |
|  3. 后台任务：提前规划                                             |
|     - 用 nohup + & 启动长时间任务                                  |
|     - 用 disown 补救忘记用 nohup 的情况                            |
|     - 用 tmux/screen 获得更完善的会话管理                          |
|                                                                  |
|  4. 监控策略：分场景选择合适的工具                                  |
|     - 日常检查：htop（直观、快捷）                                  |
|     - 脚本采样：top -b -n 1 或 ps                                  |
|     - 事后分析：atop（历史回放）                                    |
|     - 特定进程：/proc/PID/* 直接读取                               |
|                                                                  |
|  5. 优先级调整：非必要不调整                                        |
|     - 默认 nice=0 对绝大多数场景足够                               |
|     - 仅在确认需要时才调整优先级                                    |
|     - 使用 renice 比 nice 更常见（运行时调整）                      |
|                                                                  |
|  6. 僵尸进程：通常不需要手动处理                                    |
|     - 少量短暂僵尸是正常的（父进程很快回收）                        |
|     - 持续累积 → 检查父进程是否阻塞                                |
|     - 父进程是服务 → 可能需要修复/重启服务                          |
|                                                                  |
|  7. 信号使用：脚本中始终用信号名                                    |
|     trap cleanup SIGINT SIGTERM   （推荐）                       |
|     trap cleanup 2 15              （不推荐，不可移植）            |
+------------------------------------------------------------------+
```

> **本章小结：**
>
> 1. **进程是程序在内存中的运行实例**，每个进程有唯一的 PID 和父进程 PPID，形成一棵从 systemd（PID 1）起的进程树
> 2. **五种进程状态**：R（运行/就绪）、S（可中断睡眠）、D（不可中断睡眠）、T（已停止）、Z（僵尸）。僵尸进程无法被 kill，只能通过父进程回收
> 3. **nice 值**控制 CPU 分配的"善意"程度：-20（最不 nice，抢占 CPU）到 +19（最 nice，让出 CPU）。普通用户只能增大 nice 值（降低优先级）
> 4. **信号（Signal）**是进程间的异步通信机制。SIGTERM (15) 是礼貌终止（可被捕获），SIGKILL (9) 是强制终止（不可捕获），SIGSTOP (19) 是强制暂停（不可捕获）。**在脚本中始终使用信号名而非数字编号**
> 5. **`/proc` 伪文件系统**是内核的"信息窗口"——文件在读取时实时生成，不占磁盘空间。`/proc/PID/status` 和 `/proc/PID/cmdline` 是查看进程内部状态的核心入口
> 6. **ps 有三种参数风格**：BSD（无前缀，`ps aux`）、UNIX（单横线，`ps -ef`）、GNU（双横线，`ps --pid 1234`）。同名字母在不同风格下含义完全不同
> 7. **top/htop/atop** 各有定位：top 经典轻量，htop 直观友好，atop 专注历史回放和性能分析
> 8. **进程查找**：`pgrep` 优先于 `pidof`（支持正则和完整命令行匹配）。`pkill` 是 `pgrep` + `kill` 的组合
> 9. **作业控制**：`jobs` 查看、`fg` 前台化、`bg` 后台化、`Ctrl+Z` 暂停、`disown` 从作业表移除。`nohup` 让进程忽略 HUP 信号，终端关闭后继续运行
> 10. **进程管理的黄金法则**：终止进程时先 SIGTERM、等待、再 SIGKILL；监控进程时先 htop（直观）、再 atop（深度）、最后 /proc（精确）
