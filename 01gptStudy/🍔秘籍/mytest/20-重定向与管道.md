## 1. 概述

### 1.1 从"控制进程"到"连接进程"

第 18 章你学会了查看和管理系统中的进程---用 `ps aux` 浏览快照，用 `kill` 发送信号。第 19 章你深入理解了信号与作业控制---`trap` 捕获信号、`Ctrl+Z` 暂停进程、`nohup` 让进程在后台持续运行。你掌握了"一个进程"的生命周期管理。

现在，你需要将视角从"单个进程"提升到"进程间的协作"：

- "如何将 `ls -la` 的输出直接传给 `grep` 过滤，而不是先存到文件里再读？"
- "为什么 `command > file 2>&1` 和 `command 2>&1 > file` 的结果不同？"
- "`find / -name '*.log' 2>/dev/null` 里的 `2>/dev/null` 到底做了什么？"

- "`cat << EOF > config.txt` 和直接 `echo` 多行文本有什么区别？"

这些问题的核心是**重定向（Redirection）和管道（Pipe）**---Unix 哲学中"一切皆文件"（Everything is a file）和"组合小工具"（Composition of small tools）的支柱机制。

重定向和管道是 Unix 设计哲学的核心体现。Douglas McIlroy（管道概念的发明者）在 1964 年提出了这一范式：**"我们需要一种方式，把程序像花园软管（garden hose）一样拧在一起---当一个程序需要另一种方式处理数据时，它们的数据流可以互相连接。"** 这个看似简单的想法，催生了一个完整的生态系统：小而专注的工具，通过管道组合成强大的数据处理流水线。

## 2. 核心概念

### 2.1 一切皆文件：Unix 的 I/O 模型

在 Unix 中，**一切皆文件（Everything is a file）**。这不仅仅是一句口号---它是操作系统 I/O 模型的核心设计原则。无论你操作的是磁盘上的真实文件、键盘、屏幕、网络 socket、管道还是设备驱动，操作系统都通过一个统一的抽象来对待它们：**文件描述符（File Descriptor）**。

```
+------------------------------------------------------------------+
|                 Unix "一切皆文件" 模型                               |
|                                                                  |
|   进程（Process）                                                  |
|   ┌──────────────────────────────┐                                |
|   │                              │                                |
|   │  你的程序（如 cat、grep、bash）│                                |
|   │                              │                                |
|   │  系统调用：                   │                                |
|   │  open() read() write() close()│                               |
|   │                              │                                |
|   └──────────┬───────────────────┘                                |
|              │                                                     |
|    文件描述符表（每个进程私有）                                       |
|   ┌──────────┴───────────────────────────────────────────┐        |
|   │  0 → stdin     1 → stdout     2 → stderr    3+ → ...│        |
|   └──────────┬───────────────────────────────────────────┘        |
|              │                                                     |
|   VFS（虚拟文件系统层）                                              |
|   ┌──────────┴───────────────────────────────────────────┐        |
|   │                                                       │        |
|   │  ext4     tmpfs     proc     /dev     pipe    socket  │        |
|   │  (磁盘)  (内存)    (进程)   (设备)   (管道)  (网络)   │        |
|   │                                                       │        |
|   │  同一套 read/write/close 系统调用作用于所有类型！       │        |
|   └──────────────────────────────────────────────────────┘        |
+------------------------------------------------------------------+
```

**这意味着什么？** 当一个程序调用 `write(1, "hello", 5)` 时，它不知道也不关心文件描述符 1 到底指向什么---它可能是磁盘文件、终端、管道、网络 socket 或 `/dev/null`。**重定向的本质，就是改变这些文件描述符"指向"的目标。**

### 2.2 标准输入、标准输出、标准错误

每个进程在启动时，Shell 会为它打开三个默认的文件描述符：

```
+------------------------------------------------------------------+
|                    三大标准数据流                                    |
|                                                                  |
|  文件描述符编号    名称         默认连接        方向                  |
|  ─────────────────────────────────────────────                     |
|      0         stdin (标准输入)   键盘         输入 → 进程          |
|      1         stdout (标准输出)  终端显示屏    进程 → 输出          |
|      2         stderr (标准错误)  终端显示屏    进程 → 输出          |
|                                                                  |
|  关键理解：                                                       |
|  - stdout 和 stderr 默认都输出到终端，但它们是两个独立的通道        |
|  - stdout 是"正常结果"，stderr 是"错误/诊断信息"                    |
|  - 它们可以被独立重定向到不同的目标                                 |
|  - 这是 Unix 设计的精妙之处：数据和日志从诞生之日起就分流了          |
+------------------------------------------------------------------+
```

```bash
# 观察三大数据流的默认行为
# stdout 和 stderr 都输出到终端，看起来没有区别

echo "这是 stdout 输出"
# 输出：这是 stdout 输出

echo "这是 stderr 输出" >&2
# 输出：这是 stderr 输出

# 但当你重定向时，差异就显现了：
# 重定向 stdout，stderr 仍然显示在终端
echo "stdout" 2>/dev/null
# 输出：stdout

echo "stderr" >&2 2>/dev/null
# （无输出，因为 stderr 被重定向到了 /dev/null）
```

### 2.3 文件描述符的底层原理

文件描述符（File Descriptor，简称 fd）是一个非负整数，是进程内部用来标识一个打开文件的"句柄"。当进程打开一个文件（通过 `open()` 系统调用），内核返回一个文件描述符；之后进程对该文件的所有操作（`read()`、`write()`、`close()`）都通过这个数字来引用。

```
+------------------------------------------------------------------+
|                    文件描述符的内部结构                                |
|                                                                  |
|  进程控制块（task_struct）                                         |
|  ┌──────────────────────────┐                                     |
|  │  files_struct *files     │──→ 文件描述符表                       |
|  └──────────────────────────┘    ┌─────┬──────────────────────┐   |
|                                  │  0  │ → tty (stdin)        │   |
|  文件描述符表（fdtable）          │  1  │ → tty (stdout)       │   |
|  ┌──────────────────────────┐    │  2  │ → tty (stderr)       │   |
|  │  fd[0] → struct file *   │    │  3  │ → /var/log/app.log   │   |
|  │  fd[1] → struct file *   │    │  4  │ → pipe:[56789]       │   |
|  │  fd[2] → struct file *   │    └─────┴──────────────────────┘   |
|  │  fd[3] → struct file *   │                                     |
|  │  fd[4] → struct file *   │    struct file（内核文件对象）        |
|  │  ...                     │    ┌──────────────────────────┐     |
|  └──────────────────────────┘    │  f_mode: 可读/可写/追加   │     |
|                                  │  f_pos: 当前读写位置      │     |
|                                  │  f_op:  操作函数指针      │     |
|                                  └──────────────────────────┘     |
+------------------------------------------------------------------+
```

**重定向的本质操作：**

当 Shell 执行重定向（如 `command > file.txt`）时，它在 `fork()` 之后、`exec()` 之前执行以下步骤：

1. 打开目标文件（`open("file.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644)`），获得一个新的文件描述符（比如 fd 3）
2. 关闭原来的 fd 1（stdout）
3. 将 fd 3 复制到 fd 1（`dup2(3, 1)`）
4. 关闭 fd 3

结果：文件描述符 1 现在指向 `file.txt`。程序执行时，所有向 fd 1 的 `write()` 调用都会被写入文件。

```bash
# 在 /proc 中直接观察当前 shell 的文件描述符
echo "=== 当前 shell 打开的文件描述符 ==="
ls -la /proc/$$/fd/
# 输出示例：
# lrwx------ 1 user user 64 ... 0 -> /dev/pts/0
# lrwx------ 1 user user 64 ... 1 -> /dev/pts/0
# lrwx------ 1 user user 64 ... 2 -> /dev/pts/0
# lrwx------ 1 user user 64 ... 255 -> /dev/pts/0

# 注意：0、1、2 都指向同一个终端设备 /dev/pts/0
# 这解释了为什么 stdout 和 stderr 默认都输出到同一终端

# 创建一个子 shell 并重定向，观察 fd 的变化
bash -c 'ls -la /proc/$$/fd/' > /tmp/fd-list.txt
cat /tmp/fd-list.txt
# 在子 shell 中，fd 1 指向了 /tmp/fd-list.txt（管道或普通文件）

rm -f /tmp/fd-list.txt
```

### 2.4 为什么区分 stdout 和 stderr？

这个设计决策是 Unix 成功的关键因素之一。将"正常输出"和"错误信息"从诞生之日就分开，意味着：

```
+------------------------------------------------------------------+
|              stdout 与 stderr 分流的设计意图                         |
|                                                                  |
|  stdout（数据通道）：                                              |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  - 程序的"产品"——可以安全地传给下一个程序处理                   │ |
|  │  - 格式规范、可预测                                           │ |
|  │  - 示例：grep 的匹配行、find 的文件列表、cat 的文件内容        │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                                                  |
|  stderr（诊断通道）：                                              |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  - 程序的"日志"——给用户看的诊断信息，不是数据产物               │ |
|  │  - 格式自由、可包含时间戳、文件名、错误码                       │ |
|  │  - 示例：文件的权限错误、命令的进度条、grep "not found" 警告   │ |
|  └──────────────────────────────────────────────────────────────┘ |
|                                                                  |
|  实践价值：                                                       |
|  ┌──────────────────────────────────────────────────────────────┐ |
|  │  find / -name "*.log" 2>/dev/null                            │ |
|  │  ↑          ↑           ↑                                    │ |
|  │  数据       数据        错误（权限拒绝）→ 丢弃，不污染数据       │ |
|  │                                                              │ |
|  │  find / -name "*.log" > logfiles.txt 2>errors.txt            │ |
|  │  数据 → 保存到文件        错误 → 保存到另一个文件               │ |
|  └──────────────────────────────────────────────────────────────┘ |
+------------------------------------------------------------------+
```

```bash
# 演示 stdout 和 stderr 的分流价值
# 创建一些测试目录
mkdir -p /tmp/redirect-test/subdir
echo "test content" > /tmp/redirect-test/subdir/file.txt
chmod 000 /tmp/redirect-test/subdir  # 移除读权限

# 只捕获 stdout（数据），忽略 stderr（权限错误）
echo "=== 场景1：忽略错误信息 ==="
find /tmp/redirect-test -type f 2>/dev/null
# 输出：/tmp/redirect-test/subdir/file.txt
# （权限错误被静默丢弃）

# 将 stdout 和 stderr 分别保存
echo "=== 场景2：数据和错误分别保存 ==="
find /tmp/redirect-test -type f > /tmp/output.txt 2>/tmp/errors.txt
echo "--- 数据文件 ---"
cat /tmp/output.txt
echo "--- 错误文件 ---"
cat /tmp/errors.txt

# 清理
chmod 755 /tmp/redirect-test/subdir
rm -rf /tmp/redirect-test /tmp/output.txt /tmp/errors.txt
```

### 2.5 管道的本质：内核缓冲区连接

管道（Pipe）是连接两个进程的数据通道。与重定向不同（重定向连接进程和文件），管道连接的是**两个进程**。

```
+------------------------------------------------------------------+
|                    管道的数据流模型                                   |
|                                                                  |
|  command1  |  (管道)  |  command2                                  |
|  ┌───────┐ | ┌──────┐ | ┌───────┐                                 |
|  │ 进程A  │ | │ 内核  │ | │ 进程B  │                                 |
|  │       │─|→│ 环形  │─|→│       │                                 |
|  │ stdout│ | │ 缓冲区 │ | │ stdin │                                 |
|  └───────┘ | │(64KB) │ | └───────┘                                 |
|            | └──────┘ |                                            |
|            |           |                                            |
|  write()  →│  memcpy  │→ read()                                    |
|  (用户态)   │  (内核态) │  (用户态)                                  |
|                                                                  |
|  关键特性：                                                       |
|  1. 管道缓冲区在 Linux 上是 64KB（16 个 4KB 页）                   |
|  2. 如果写端写满了缓冲区，write() 会阻塞，直到读端读取数据          |
|  3. 如果读端读取空缓冲区，read() 会阻塞，直到写端写入数据           |
|  4. 如果写端关闭了 fd，读端 read() 返回 0（EOF）                   |
|  5. 如果读端关闭了 fd，写端 write() 触发 SIGPIPE 信号              |
+------------------------------------------------------------------+
```

**Shell 管道的执行流程：**

```
1. Shell 调用 pipe() 系统调用，创建一个管道
   → 获得两个 fd：pipe_fd[0]（读端）和 pipe_fd[1]（写端）

2. Shell fork() 创建子进程 A
   → 子进程 A 关闭 pipe_fd[0]（读端）
   → 子进程 A 将 pipe_fd[1] dup2 到 fd 1（stdout）
   → 子进程 A exec() 执行 command1

3. Shell fork() 创建子进程 B
   → 子进程 B 关闭 pipe_fd[1]（写端）
   → 子进程 B 将 pipe_fd[0] dup2 到 fd 0（stdin）
   → 子进程 B exec() 执行 command2

4. Shell 关闭管道两端的 fd，等待两个子进程退出
```

```bash
# 验证管道缓冲区大小
# 方法1：使用 ulimit（管道容量可能受限于此）
ulimit -p
# 输出：8（表示 8 × 512 字节 = 4096 字节，但实际 Linux 管道缓冲区是 64KB）

# 方法2：通过 /proc 查看实际管道容量（Linux 2.6.35+）
cat /proc/sys/fs/pipe-max-size
# 输出：1048576（1MB，这是可设置的最大值，默认仍是 64KB）

# 方法3：实验观察阻塞行为
# 以下命令创建一个写满管道缓冲区的场景
dd if=/dev/zero bs=64K count=1 2>/dev/null | (sleep 2; wc -c)
# dd 写入 64KB，刚好填满一个管道缓冲区
# 如果写入更多数据，dd 会阻塞直到 wc 开始读取
```

### 2.6 管道中的缓冲区阻塞实验

```bash
# 实验：感受管道阻塞
# 这个实验演示：当管道写端填充速度 > 读端消费速度时，写端会阻塞

echo "=== 管道阻塞演示 ==="
# 快速生产者 + 慢速消费者
# 生产者每秒产生大量数据，消费者每秒只读一点点
(
  for i in $(seq 1 100); do
    echo "数据块 $i: $(head -c 1000 /dev/zero | tr '\0' 'x')"
  done
) | (
  while read -r line; do
    echo "读取: ${line:0:40}..."
    sleep 0.1  # 消费者故意变慢
  done
)
echo "管道实验完成"
```

## 3. 命令详解

### 3.1 输出重定向：`>` 和 `>>`

#### 3.1.1 `>` --- 覆盖写入

```
语法：
  command > file

语义：
  1. 如果 file 不存在，创建它
  2. 如果 file 已存在，先清空（truncate）再写入
  3. command 的 stdout 被重定向到 file
  4. command 的 stderr 不受影响，仍然输出到终端
```

```bash
# 基本用法：将命令输出写入文件
echo "第一行内容" > /tmp/demo.txt
cat /tmp/demo.txt
# 输出：第一行内容

# 再次写入 --- 文件被清空后重新写入
echo "第二行内容" > /tmp/demo.txt
cat /tmp/demo.txt
# 输出：第二行内容
# （注意：原来的"第一行内容"被覆盖了！）

# > 会先清空文件！
# 如果想保留原有内容，使用 >>
```

**`>` 的操作顺序：先打开/创建文件，再执行命令**

```bash
# 关键理解：Shell 在命令执行前就完成了重定向设置
# 这意味着 > 会在命令运行前就清空文件！

# 错误示例：想用 sort 排序一个文件并写回原文件
echo "c" > /tmp/sort-test.txt
echo "a" >> /tmp/sort-test.txt
echo "b" >> /tmp/sort-test.txt
cat /tmp/sort-test.txt
# 输出：
# c
# a
# b

sort /tmp/sort-test.txt > /tmp/sort-test.txt
cat /tmp/sort-test.txt
# 输出：（空文件！）
# 为什么？因为 > /tmp/sort-test.txt 在 sort 读取文件之前就清空了它！

# 正确的做法：先输出到临时文件，再替换
sort /tmp/sort-test.txt > /tmp/sort-test.tmp && mv /tmp/sort-test.tmp /tmp/sort-test.txt

rm -f /tmp/demo.txt /tmp/sort-test.txt /tmp/sort-test.tmp
```

#### 3.1.2 `>|` --- 强制覆盖

```bash
# 当 shell 的 noclobber 选项开启时，> 不能覆盖已存在的文件
set -o noclobber
echo "test" > /tmp/exists.txt
echo "overwrite" > /tmp/exists.txt
# 输出：bash: /tmp/exists.txt: cannot overwrite existing file

# 使用 >| 强制覆盖（绕过 noclobber）
echo "overwrite" >| /tmp/exists.txt
cat /tmp/exists.txt
# 输出：overwrite

# 恢复默认设置
set +o noclobber
rm -f /tmp/exists.txt
```

#### 3.1.3 `>>` --- 追加写入

```
语法：
  command >> file

语义：
  1. 如果 file 不存在，创建它
  2. 如果 file 已存在，在文件末尾追加内容（不覆盖）
  3. command 的 stdout 被重定向到 file
```

```bash
# 追加写入
echo "第一行" > /tmp/append-demo.txt
echo "第二行" >> /tmp/append-demo.txt
echo "第三行" >> /tmp/append-demo.txt
cat /tmp/append-demo.txt
# 输出：
# 第一行
# 第二行
# 第三行

# 典型用法：构建日志文件
for i in 1 2 3; do
  echo "[$(date '+%H:%M:%S')] 处理第 $i 项" >> /tmp/process.log
done
cat /tmp/process.log
# 输出示例：
# [14:30:01] 处理第 1 项
# [14:30:01] 处理第 2 项
# [14:30:01] 处理第 3 项

rm -f /tmp/append-demo.txt /tmp/process.log
```

### 3.2 输入重定向：`<`

```
语法：
  command < file

语义：
  1. command 的 stdin 来自 file（而不是键盘）
  2. command 的 stdout 和 stderr 不受影响
```

```bash
# 基本用法：让命令从文件读取输入
echo -e "apple\nbanana\ncherry" > /tmp/fruits.txt

# 方法1：用管道
cat /tmp/fruits.txt | sort

# 方法2：用输入重定向（更高效 --- 避免额外的 cat 进程）
sort < /tmp/fruits.txt
# 输出：
# apple
# banana
# cherry

# < 并非对所有命令都有意义
# 有些命令（如 grep）可以直接接受文件名参数
grep "apple" /tmp/fruits.txt  # 推荐：直接传文件名
grep "apple" < /tmp/fruits.txt  # 也可以，但不如上一种清晰

rm -f /tmp/fruits.txt
```

**`<` 的本质：**

```
sort < file.txt

在内部相当于：
  1. open("file.txt", O_RDONLY) → fd 3
  2. dup2(3, 0)                 → fd 0 指向 file.txt
  3. close(3)
  4. exec("sort")               → sort 从 fd 0 读取，即从 file.txt 读取
```

### 3.3 错误重定向：`2>`、`2>>`

#### 3.3.1 `2>` --- 重定向 stderr

```bash
# 只有 stderr 被重定向，stdout 仍然输出到终端
echo "=== 没有错误 ==="
find /root -name "*.conf" 2>/tmp/find-errors.txt
# stdout（找到的文件）显示在终端
# stderr（权限拒绝的错误）写入 /tmp/find-errors.txt

cat /tmp/find-errors.txt
# 输出示例：
# find: '/root': Permission denied

# 如果想同时丢弃 stdout，只保留 stderr
find / -name "*.conf" > /dev/null 2>/tmp/all-errors.txt
# stdout 被丢弃，stderr 被保存

rm -f /tmp/find-errors.txt /tmp/all-errors.txt
```

#### 3.3.2 `2>>` --- 追加写入 stderr

```bash
# 追加方式写入 stderr 日志
for dir in /root /var/log /etc; do
  find "$dir" -name "*.conf" 2>>/tmp/err-accum.txt
done
cat /tmp/err-accum.txt
# 多次 find 的错误信息都被追加在一起

rm -f /tmp/err-accum.txt
```

### 3.4 合并流：`2>&1`、`1>&2`、`&>`、`&>>`、`|&`

#### 3.4.1 `2>&1` --- 将 stderr 合并到 stdout

这是最常用但也最容易引起困惑的重定向操作符。

```
语法：
  command > file 2>&1

语义（从右向左读）：
  2>&1 = 将文件描述符 2 指向文件描述符 1 当前所指向的位置

关键理解：
  > file 2>&1  ≠  2>&1 > file
  这两者完全不同！
```

```bash
# 详细演示：操作顺序的重要性

# 准备：创建一个会产生 stdout 和 stderr 的命令
# ls 同时列出一个存在的文件和一个不存在的文件
echo "test" > /tmp/exists.txt

# === 正确做法：>file 2>&1 ===
# 解释：1. > file  → stdout 指向 file
#       2. 2>&1    → stderr 指向 stdout 当前所指向的（file）
# 结果：stdout 和 stderr 都进入 file
ls -l /tmp/exists.txt /tmp/nonexistent.txt > /tmp/both-output.txt 2>&1
echo "=== 正确: >file 2>&1 ==="
cat /tmp/both-output.txt
# 输出包含：
# -rw-r--r-- 1 user user 5 ... /tmp/exists.txt  （来自 stdout）
# ls: cannot access '/tmp/nonexistent.txt': ...  （来自 stderr）

# === 错误做法：2>&1 >file ===
# 解释：1. 2>&1    → stderr 指向 stdout 当前所指向的（终端）
#       2. > file  → stdout 指向 file（但 stderr 仍然指向旧的终端！）
# 结果：stdout 进入 file，stderr 仍然显示在终端
ls -l /tmp/exists.txt /tmp/nonexistent.txt 2>&1 > /tmp/wrong-output.txt
echo "=== 错误: 2>&1 >file ==="
echo "--- 文件内容（只有 stdout）---"
cat /tmp/wrong-output.txt
echo "--- stderr 在终端上，不在文件中（上面应该已经显示了错误信息）---"

# 清理
rm -f /tmp/exists.txt /tmp/both-output.txt /tmp/wrong-output.txt
```

**操作顺序的详细图解：**

```
正确：> file 2>&1
─────────────────────────────────────────────
初始状态：  fd1 → terminal, fd2 → terminal

步骤1: > file
        fd1 → file         (stdout 指向文件)
        fd2 → terminal     (stderr 不变)

步骤2: 2>&1
        fd1 → file
        fd2 → file         (stderr 复制 fd1 的指向)
        
结果：两者都到 file ✓


错误：2>&1 > file
─────────────────────────────────────────────
初始状态：  fd1 → terminal, fd2 → terminal

步骤1: 2>&1
        fd1 → terminal
        fd2 → terminal     (stderr 复制 fd1 的指向，都是 terminal)

步骤2: > file
        fd1 → file         (stdout 改变指向)
        fd2 → terminal     (stderr 的指向不受影响！)
        
结果：stdout 到 file，stderr 到 terminal ✗
```

#### 3.4.2 `1>&2` --- 将 stdout 合并到 stderr

```bash
# 将正常输出也发送到 stderr 的方向
# 在某些脚本中用于统一输出通道
echo "这是重要信息，应该输出到 stderr" 1>&2
# 输出：这是重要信息，应该输出到 stderr
# （看起来和普通 echo 一样，但实际上走的是 stderr 通道）

# 验证：尝试捕获 stdout
echo "stdout info" 1>&2 > /tmp/capture.txt
cat /tmp/capture.txt
# 输出：（空文件 --- 因为输出走了 stderr，不在 stdout）

# 原理：
# 1>&2 表示 "将 fd 1 指向 fd 2 当前所指向的位置"
# > /tmp/capture.txt 表示 "将 fd 1 指向 /tmp/capture.txt"
# 操作顺序：先执行 1>&2，将 fd1 指向 stderr（终端）
#           再执行 > /tmp/capture.txt，将 fd1 指向文件
# 结果：先走的输出（1>&2 之后的 echo 还没执行，但重定向已生效）
# 实际上这里的命令有歧义，因为在同一行中多个重定向会被同时处理

# 更清晰的演示：
echo "to stdout" > /tmp/out.txt
echo "to stderr" 1>&2 2>/tmp/err.txt
cat /tmp/out.txt
# 输出：to stdout
cat /tmp/err.txt
# 输出：to stderr

rm -f /tmp/capture.txt /tmp/out.txt /tmp/err.txt
```

#### 3.4.3 `&>` 和 `&>>` --- 合并重定向（Bash 简写）

```bash
# &> = 同时重定向 stdout 和 stderr 到同一个文件（覆盖模式）
# 等价于 > file 2>&1

ls /tmp/exists 2>/dev/null || echo "exists 不存在" > /tmp/exists
ls -l /tmp/exists /tmp/nonexists &> /tmp/all-output.txt
echo "=== &> 效果 ==="
cat /tmp/all-output.txt
# 输出包含成功和错误两行信息

# &>> = 同时重定向 stdout 和 stderr 到同一个文件（追加模式）
# 等价于 >> file 2>&1

echo "第一轮" &> /tmp/append-all.txt
echo "第二轮" &>> /tmp/append-all.txt
echo "=== &>> 效果 ==="
cat /tmp/append-all.txt
# 输出：
# 第一轮
# 第二轮

rm -f /tmp/exists /tmp/all-output.txt /tmp/append-all.txt
```

#### 3.4.4 `|&` --- stderr 也通过管道

```bash
# |& 将 stdout 和 stderr 都传给管道
# 等价于 2>&1 |

# 普通管道：stderr 不进入管道
ls /tmp /nonexistent 2>/dev/null | wc -l
# 输出：只有 /tmp 下的条目数，错误信息被丢弃了

# |&：stderr 也进入管道
ls /tmp /nonexistent |& wc -l
# 输出：/tmp 下的条目数 + 1（错误信息那一行）
```

### 3.5 管道：`|`

#### 3.5.1 基本管道

```bash
# 管道的最基本用法：将一个命令的 stdout 传给另一个命令的 stdin
ls -la /usr/bin | head -5
# 输出：/usr/bin 下前 5 个文件

# 多级管道：任意多个命令串联
cat /etc/passwd | grep -v 'nologin' | grep -v 'false' | cut -d: -f1 | sort
# 解释：
#   cat /etc/passwd              → 输出所有用户记录
#   grep -v 'nologin'            → 排除 /usr/sbin/nologin 的用户
#   grep -v 'false'              → 排除 /bin/false 的用户
#   cut -d: -f1                  → 提取用户名（第一列）
#   sort                         → 排序
# 输出：所有可以登录的用户名（排序后）
```

#### 3.5.2 管道不是"接续执行"

```bash
# 误区：管道中的命令是并发执行的，不是先后执行的

# 所有管道命令在 fork 后几乎同时启动
# 它们通过读/写操作在管道缓冲区上同步

# 一个简单的观察：
( echo "A"; sleep 2; echo "B" ) | ( echo "开始"; cat; echo "结束" )
# 输出顺序：
# 开始
# A
# （等待 2 秒）
# B
# 结束
# 
# 注意："开始"先出现，说明第二个子进程立即启动了
# 然后 cat 阻塞在 read() 上，等待管道数据
```

#### 3.5.3 管道缓冲区与程序行为

管道的缓冲机制会影响程序的行为，特别是在处理实时数据时：

```bash
# 实验：管道缓冲对实时输出的影响

# C 标准库的 stdio 缓冲策略：
# - stdout 连接到终端：行缓冲（Line Buffered），每行刷新
# - stdout 连接到管道：全缓冲（Fully Buffered），缓冲区满才刷新

# 以下是演示脚本
cat > /tmp/pipe-buff-demo.sh << 'EOF'
#!/bin/bash
# 模拟实时输出程序
for i in $(seq 1 5); do
    echo "第 $i 行输出"
    sleep 0.3
done
EOF
chmod +x /tmp/pipe-buff-demo.sh

# 直接运行 → 实时看到输出（行缓冲）
echo "=== 直接运行（实时输出）==="
bash /tmp/pipe-buff-demo.sh

# 通过管道 → 可能看到积攒的输出（全缓冲）
echo "=== 通过管道（可能延迟）==="
bash /tmp/pipe-buff-demo.sh | cat

# 使用 stdbuf 或 unbuffer 强制行缓冲
echo "=== 强制行缓冲 ==="
stdbuf -oL bash /tmp/pipe-buff-demo.sh | cat
# 或
# unbuffer bash /tmp/pipe-buff-demo.sh | cat  （需要 expect 包）

rm -f /tmp/pipe-buff-demo.sh
```

#### 3.5.4 命名管道（Named Pipe / FIFO）

除了 Shell 的匿名管道（`|`），Linux 还支持命名管道：

```bash
# 创建命名管道
mkfifo /tmp/myfifo

# 在另一个终端中读取（没有另一个终端时，用后台进程模拟）
# 终端2: cat /tmp/myfifo

# 在当前终端写入
echo "Hello via FIFO" > /tmp/myfifo &
cat /tmp/myfifo
# 输出：Hello via FIFO

# 清理
rm -f /tmp/myfifo
```

### 3.6 tee：分叉数据流

`tee` 命令从 stdin 读取数据，同时写入 stdout 和指定的文件。它是管道中"分叉"数据流的工具。

```
+------------------------------------------------------------------+
|                    tee 的数据流模型                                  |
|                                                                  |
|  command1 ──→ stdout ──→ tee ──→ stdout ──→ command2             |
|                           │                                       |
|                           ↓                                       |
|                         file                                      |
|                                                                  |
|  tee 像一个"三通管接头"：                                          |
|  数据从左侧流入，同时流向右侧和下方                                  |
+------------------------------------------------------------------+
```

```bash
# tee 基本用法：同时显示和保存
echo "=== tee 基本演示 ==="
echo -e "apple\nbanana\ncherry" | tee /tmp/fruits-backup.txt
# 输出同时显示在终端和写入文件

echo ""
echo "=== 验证文件内容 ==="
cat /tmp/fruits-backup.txt

# tee -a：追加模式
echo -e "date\ndragonfruit" | tee -a /tmp/fruits-backup.txt
echo ""
echo "=== 追加后的文件 ==="
cat /tmp/fruits-backup.txt

# tee 在管道中间分叉（调试管道的利器）
echo ""
echo "=== 使用 tee 调试管道 ==="
cat /etc/passwd | tee /tmp/step1.txt | head -3 | tee /tmp/step2.txt
echo "--- step1.txt（cat 的原始输出，全部内容）---"
wc -l /tmp/step1.txt
echo "--- step2.txt（head -3 的输出）---"
cat /tmp/step2.txt
rm -f /tmp/step2.txt  # step1.txt 先保留

# tee /dev/null：丢弃 stdout（罕见但合法）
echo ""
echo "=== tee 到 /dev/null ==="
echo "这个数据被丢弃了" | tee /tmp/saved.txt > /dev/null
cat /tmp/saved.txt
# 输出：这个数据被丢弃了
# （数据被保存到文件，但不在终端显示）

rm -f /tmp/fruits-backup.txt /tmp/step1.txt /tmp/saved.txt
```

**tee 的典型场景：**

```bash
# 场景1：在管道中记录中间结果，方便调试
grep "ERROR" /var/log/syslog 2>/dev/null | tee /tmp/errors.log | wc -l
# 既能看到行数，又保存了错误日志

# 场景2：写入需要 sudo 权限的文件
echo "server=8.8.8.8" | sudo tee /etc/some-config.conf
# 因为 > 的重定向由当前 shell 执行（权限不够）
# 而 tee 在 sudo 下运行（有权限写入）

# 场景3：同时写入多个文件
echo "backup done" | tee /tmp/status1.txt /tmp/status2.txt /tmp/status3.txt > /dev/null
cat /tmp/status1.txt /tmp/status2.txt /tmp/status3.txt

rm -f /tmp/status1.txt /tmp/status2.txt /tmp/status3.txt
```

### 3.7 特殊设备文件：`/dev/null`、`/dev/zero`、`/dev/urandom`、`/dev/fd/`

`/dev` 目录下的文件不是普通文件---它们是**设备文件（Device Files）**，代表内核中的设备驱动。当你读写这些文件时，实际上是在与内核驱动交互。

#### 3.7.1 `/dev/null` --- 数据黑洞

```
/dev/null 是"空设备"（null device）：
- 写入的数据被立即丢弃
- 读取时立即返回 EOF（文件结束）

它是丢弃不需要的输出的标准方式。
```

```bash
# 丢弃 stdout
cat /etc/passwd > /dev/null
# （没有输出）

# 丢弃 stderr
find /root -name "*.conf" 2>/dev/null
# 只看到找到的文件，权限错误被丢弃

# 丢弃 stdout 和 stderr
grep -r "something" /etc/ > /dev/null 2>&1

# 测试命令的退出码而不看输出
if ls /nonexistent > /dev/null 2>&1; then
    echo "目录存在"
else
    echo "目录不存在（退出码非 0）"
fi
# 输出：目录不存在（退出码非 0）

# /dev/null 读取 → 总是返回 EOF
cat /dev/null
# （没有任何输出）
```

#### 3.7.2 `/dev/zero` --- 无限零字节流

```
/dev/zero 是"零设备"（zero device）：
- 无限供应 '\0'（NULL 字节）
- 读取时返回连续的零字节流

典型用途：
- 创建指定大小的空文件
- 覆盖磁盘/分区（安全擦除）
- 为程序提供零值输入
```

```bash
# 创建一个 1MB 的全零文件
dd if=/dev/zero of=/tmp/zero-file.bin bs=1024 count=1024 2>/dev/null
ls -lh /tmp/zero-file.bin
# 输出示例：-rw-r--r-- 1 user user 1.0M ... /tmp/zero-file.bin

# 验证内容全为零
hexdump -C /tmp/zero-file.bin | head -3
# 输出：00 00 00 00 00 00 00 00 ...

# 用零覆盖来创建空白文件（比 > file 更精确控制大小）
dd if=/dev/zero of=/tmp/exactly-4k.bin bs=4096 count=1 2>/dev/null
ls -l /tmp/exactly-4k.bin
# 输出：-rw-r--r-- ... 4096 ... /tmp/exactly-4k.bin

# 测试程序的零输入处理
head -c 100 /dev/zero | xxd | head -5
# 输出：100 个 0x00 字节的 hexdump

rm -f /tmp/zero-file.bin /tmp/exactly-4k.bin
```

#### 3.7.3 `/dev/urandom` --- 伪随机数生成器

```
/dev/urandom 是"非阻塞随机数设备"（unlimited random）：
- 提供内核收集的熵（entropy）生成的伪随机字节流
- 非阻塞：即使熵池耗尽，也继续输出（用 CSPRNG 算法）
- 对比 /dev/random：熵池耗尽时会阻塞

典型用途：
- 生成随机密码
- 创建随机测试数据
- 加密密钥生成（非关键场景）
```

```bash
# 生成 16 字节的随机数据
head -c 16 /dev/urandom | xxd
# 输出示例：00000000: a3f1 2c8b 7e4d 9102 6538 cbaf 0d71 48fe  ..,.~M..e8...qH.

# 生成随机密码（32 字符）
head -c 32 /dev/urandom | base64 | head -c 32
# 输出示例：K7mXp2QvW9nR4sY6aB8tU3hD5fG1jL0o

# 生成随机数字
head -c 4 /dev/urandom | od -An -tu4
# 输出示例：2147483647

# 用随机数据填充文件（用于测试压缩、加密等）
dd if=/dev/urandom of=/tmp/random-test.bin bs=1024 count=10 2>/dev/null
ls -lh /tmp/random-test.bin
# 输出示例：-rw-r--r-- ... 10K ... /tmp/random-test.bin

rm -f /tmp/random-test.bin
```

#### 3.7.4 `/dev/fd/` --- 文件描述符目录

```
/dev/fd/ 是一个符号链接目录，包含指向当前进程打开的文件描述符的条目：
- /dev/fd/0 → stdin
- /dev/fd/1 → stdout
- /dev/fd/2 → stderr
- /dev/fd/N → 第 N 个文件描述符

典型用途：
- 在需要文件路径的场景中引用文件描述符
- 解决某些命令不接受 stdin 但接受文件名的问题
```

```bash
# /dev/fd/ 允许在需要文件名的位置使用管道
echo "=== /dev/fd/ 演示 ==="

# 某些命令不支持从 stdin 读取，但支持文件名
# 借助 /dev/fd/0 可以将管道数据"伪装"成文件

# 示例：diff 需要两个文件名，但我们可以用进程替换或 /dev/fd/
echo -e "a\nb\nc" > /tmp/file1.txt
echo -e "a\nx\nc" > /tmp/file2.txt

# 传统方式：需要临时文件
# 使用 /dev/fd/ 方式：直接用管道
diff /tmp/file1.txt /tmp/file2.txt
# 输出：
# 2c2
# < b
# ---
# > x

# /dev/fd/ 在进程替换不可用时有用（如某些旧 shell）
echo "current shell: $BASH_VERSION"

rm -f /tmp/file1.txt /tmp/file2.txt
```

### 3.8 进程替换：`<()` 和 `>()`

进程替换（Process Substitution）是 Bash 提供的一个强大特性。它允许将命令的输出（或输入）当作文件来使用。这在需要文件名参数但实际数据来自命令的场景中非常有用。

```
语法：
  <(command)   → 生成一个伪文件，内容是 command 的 stdout
  >(command)   → 生成一个伪文件，向它写入的数据会成为 command 的 stdin

底层实现：
  使用命名管道（named pipe）或 /dev/fd/ 来创建伪文件路径
  如：/dev/fd/63 或 /proc/self/fd/63
```

#### 3.8.1 `<()` --- 将命令输出当作文件

```bash
# 准备测试数据
echo -e "apple\nbanana\ncherry\ndate" > /tmp/list1.txt
echo -e "apple\nblueberry\ncherry\ndragonfruit" > /tmp/list2.txt

# 场景1：比较两个命令的输出，无需临时文件
echo "=== diff 两个命令的输出 ==="
diff <(sort /tmp/list1.txt) <(sort /tmp/list2.txt)
# 输出：
# 2,3c2,3
# < banana
# < date
# ---
# > blueberry
# > dragonfruit

# 场景2：逐行合并两个命令的输出
echo "=== paste 两个命令的输出 ==="
paste <(cat /tmp/list1.txt) <(cat /tmp/list2.txt)
# 输出：
# apple    apple
# banana   blueberry
# cherry   cherry
# date     dragonfruit

# 场景3：将 grep 的结果传给 diff
echo "=== 比较两个 grep 的结果 ==="
echo -e "apple 10\nbanana 20\ncherry 30" > /tmp/data1.txt
echo -e "apple 15\nbanana 20\ncherry 35" > /tmp/data2.txt
diff <(grep -v '#' /tmp/data1.txt) <(grep -v '#' /tmp/data2.txt)
# 输出差异行...

# 场景4：join 两个排序后的流
join <(sort /tmp/list1.txt) <(sort /tmp/list2.txt)
# 输出：apple（共同的条目）

# 查看 <() 生成的路径
echo <(echo hello)
# 输出示例：/dev/fd/63
# 这个路径指向一个命名管道，读取它会得到 "hello\n"

rm -f /tmp/list1.txt /tmp/list2.txt /tmp/data1.txt /tmp/data2.txt
```

#### 3.8.2 `>()` --- 将文件写入变为命令输入

```bash
# >() 不太常用，但在某些场景中很有用

# 场景：同时将输出写入多个处理流程
echo "=== >() 同时送给多个命令处理 ==="
echo "test data" | tee >(gzip > /tmp/output.gz) >(wc -c > /tmp/count.txt) > /dev/null
echo "--- 压缩结果 ---"
zcat /tmp/output.gz
echo ""
echo "--- 字符数 ---"
cat /tmp/count.txt

# 场景：将输出同时写入文件和传入管道
echo "=== 分叉输出 ==="
seq 1 5 | tee >(md5sum > /tmp/checksum.txt) | wc -l
# stdout 显示行数 5
echo "--- MD5 校验和 ---"
cat /tmp/checksum.txt

rm -f /tmp/output.gz /tmp/count.txt /tmp/checksum.txt
```

### 3.9 Here Document：`<<` 和 `<<-`

Here Document 允许在命令行或脚本中嵌入多行文本块，将其作为命令的 stdin。

#### 3.9.1 `<<` --- 基本 Here Document

```
语法：
  command << DELIMITER
  多行文本
  ...
  DELIMITER

语义：
  将 << 和 DELIMITER 之间的所有文本作为 command 的 stdin
  DELIMITER 必须是独占一行的字面标识符
```

```bash
# 基本用法：向 cat 传递多行文本
cat << EOF
这是第一行
这是第二行
这是第三行
EOF
# 输出：
# 这是第一行
# 这是第二行
# 这是第三行

# 传递给其他命令
wc -l << EOF
line one
line two
line three
line four
EOF
# 输出：4

# 写入文件（最常见的用法之一）
cat << EOF > /tmp/config.ini
[server]
host = localhost
port = 8080
timeout = 30

[database]
host = db.example.com
port = 5432
name = myapp
EOF
cat /tmp/config.ini

rm -f /tmp/config.ini
```

**Here Document 中的变量展开：**

```bash
# 默认情况下，Here Document 中的变量会被展开（和双引号字符串一样）
NAME="张三"
DATE=$(date '+%Y-%m-%d')

cat << EOF
用户: $NAME
日期: $DATE
当前目录: $PWD
EOF
# 输出：
# 用户: 张三
# 日期: 2026-07-30
# 当前目录: /home/user

# 如果要阻止变量展开，给 DELIMITER 加引号
cat << 'EOF'
用户: $NAME
日期: $DATE
当前目录: $PWD
EOF
# 输出：
# 用户: $NAME
# 日期: $DATE
# 当前目录: $PWD
```

#### 3.9.2 `<<-` --- 去除前导 Tab 的 Here Document

```bash
# <<- 会去除每行开头的 Tab 字符（不是空格！）
# 这对于在缩进的脚本中嵌入多行文本非常有用

cat > /tmp/indented-script.sh << 'SCRIPT'
#!/bin/bash
if true; then
    # 使用 <<- 让文本块可以缩进
    cat <<- EOF
	这一行前面有 Tab
	这一行前面也有 Tab
	但在输出中 Tab 被去除了
	EOF
fi
SCRIPT

bash /tmp/indented-script.sh
# 输出：
# 这一行前面有 Tab
# 这一行前面也有 Tab
# 但在输出中 Tab 被去除了

# 注意：<<- 只去除 Tab，不去除空格！
cat <<- EOF
    前面是四个空格（不会被去除）
	前面是一个 Tab（会被去除）
EOF
# 输出：
#     前面是四个空格（不会被去除）
# 前面是一个 Tab（会被去除）

rm -f /tmp/indented-script.sh
```

### 3.10 Here String：`<<<`

Here String 将单个字符串（而不是多行文本块）作为命令的 stdin。

```
语法：
  command <<< "string"

语义：
  将 "string"（加上一个换行符）作为 command 的 stdin
  
底层等价于：
  echo "string" | command
  但更高效，因为不需要创建管道的子进程
```

```bash
# 基本用法
cat <<< "Hello, World!"
# 输出：Hello, World!

# 将变量内容传给命令
PATH_LIST="/usr/bin:/usr/local/bin:/opt/bin"
tr ':' '\n' <<< "$PATH_LIST"
# 输出：
# /usr/bin
# /usr/local/bin
# /opt/bin

# 与 echo + 管道对比
echo "=== Here String vs 管道 ==="
# 方法1：管道（创建了子进程）
echo "$PATH_LIST" | tr ':' '\n'

# 方法2：Here String（在 bash 内部完成，无子进程）
tr ':' '\n' <<< "$PATH_LIST"
# 结果相同，但 Here String 更高效

# Here String 用于 read 命令
read -r FIRST SECOND REST <<< "one two three four five"
echo "FIRST=$FIRST, SECOND=$SECOND, REST=$REST"
# 输出：FIRST=one, SECOND=two, REST=three four five

# 将数组转换为字符串后处理
read -r -a ARR <<< "10 20 30 40 50"
echo "数组元素: ${ARR[@]}"
echo "元素个数: ${#ARR[@]}"
# 输出：
# 数组元素: 10 20 30 40 50
# 元素个数: 5
```

### 3.11 管道退出码：`PIPESTATUS` 和 `pipefail`

#### 3.11.1 问题：`$?` 只返回管道最后一个命令的退出码

```bash
# 默认情况下，管道的退出码是最后一个命令的退出码
echo "=== 默认管道退出码 ==="
# 第一个命令失败，但最后一个命令成功
false | true
echo "\$? = $?"
# 输出：$? = 0
# （true 成功，掩盖了 false 的失败！）

# 这是一个常见的 bug 来源
cat /nonexistent | sort | head -3
echo "\$? = $?"
# 如果 sort 和 head 成功，$? 可能是 0
# 但 cat 的失败被忽略了！
```

#### 3.11.2 `PIPESTATUS` --- 获取管道中所有命令的退出码

```bash
# PIPESTATUS 是一个数组，记录了管道中每个命令的退出码
echo "=== PIPESTATUS 演示 ==="

false | true | false
echo "整个管道的退出码: $?"
echo "PIPESTATUS[0] (false): ${PIPESTATUS[0]}"
echo "PIPESTATUS[1] (true):  ${PIPESTATUS[1]}"
echo "PIPESTATUS[2] (false): ${PIPESTATUS[2]}"
# 输出：
# 整个管道的退出码: 1
# PIPESTATUS[0] (false): 1
# PIPESTATUS[1] (true):  0
# PIPESTATUS[2] (false): 1

# 检查管道中是否有任何命令失败
cat /etc/passwd | grep -q "nonexistent_user" | wc -l
if [[ ${PIPESTATUS[1]} -ne 0 ]]; then
    echo "grep 没有找到匹配（退出码非零）"
fi

# PIPESTATUS 只能获取最近一个管道的退出状态
# 如果你需要保存它，必须在管道之后立即复制
false | true
STATUS=("${PIPESTATUS[@]}")
echo "保存的 PIPESTATUS: ${STATUS[@]}"
# 后续的管道不会影响 STATUS 数组
```

#### 3.11.3 `set -o pipefail` --- 任何一个命令失败则整体失败

```bash
# 启用 pipefail 后，管道中任何一个命令失败，整个管道就失败
echo "=== pipefail 效果 ==="

# 默认行为：只看最后一个命令
false | true
echo "默认模式 \$?: $?"

# 启用 pipefail
set -o pipefail
false | true
echo "pipefail 模式 \$?: $?"
# 输出：pipefail 模式 $?: 1

# pipefail 的精确语义：
# 管道的退出码 = 最后一个非零退出码
# 如果所有命令都成功，退出码 = 0

# 示例：中间的 grep 失败
cat /etc/passwd | grep "nonexistent" | wc -l
echo "pipefail 下 grep 失败的退出码: $?"
# 输出：pipefail 下 grep 失败的退出码: 1

# 恢复默认设置
set +o pipefail

# 建议：在所有脚本中使用 pipefail
# 并在需要精确判断时配合 PIPESTATUS
```

**pipefail 与 PIPESTATUS 的配合使用：**

```bash
# 脚本中的最佳实践
cat > /tmp/pipefail-demo.sh << 'SCRIPT'
#!/bin/bash
set -o pipefail

process_data() {
    # 使用 pipefail 确保错误不被忽略
    # 同时使用 PIPESTATUS 做精细诊断
    
    if ! output=$(cat /etc/passwd | grep "root" | wc -l 2>/dev/null); then
        echo "错误：管道处理失败"
        for i in "${!PIPESTATUS[@]}"; do
            echo "  命令 $i 退出码: ${PIPESTATUS[$i]}"
        done
        return 1
    fi
    echo "成功：找到 $output 行"
    return 0
}

process_data
echo "函数退出码: $?"
SCRIPT
bash /tmp/pipefail-demo.sh
rm -f /tmp/pipefail-demo.sh
```

### 3.13 复杂重定向的组合示例

```bash
# 场景1：脚本日志 --- stdout 到文件，stderr 到另一个文件，同时终端显示
cat > /tmp/complex-demo.sh << 'EOF'
#!/bin/bash
echo "正常信息 1"
echo "警告信息 1" >&2
echo "正常信息 2"
echo "错误信息 1" >&2
EOF
chmod +x /tmp/complex-demo.sh

# 执行并分开收集
bash /tmp/complex-demo.sh > /tmp/stdout.log 2> /tmp/stderr.log
echo "=== stdout.log ==="
cat /tmp/stdout.log
echo "=== stderr.log ==="
cat /tmp/stderr.log

# 场景2：stderr 也通过管道处理
echo "=== stderr 通过管道 ==="
bash /tmp/complex-demo.sh 2>&1 | grep "警告"

# 场景3：将 stdout 和 stderr 互换
echo "=== 交换 stdout 和 stderr ==="
bash /tmp/complex-demo.sh 3>&1 1>&2 2>&3 | grep "警告" 2>/dev/null
# 解释：
#   3>&1  → 用 fd 3 保存 stdout 当前指向的位置（终端）
#   1>&2  → stdout 指向 stderr 指向的位置（终端，但此时两个都已指向终端）
#   2>&3  → stderr 指向 fd 3 指向的位置（即原来的 stdout）

# 场景4：记录所有输出同时显示进度
echo "=== 记录所有输出 ==="
bash /tmp/complex-demo.sh 2>&1 | tee /tmp/full-output.log
echo "--- 完整日志 ---"
cat /tmp/full-output.log

rm -f /tmp/complex-demo.sh /tmp/stdout.log /tmp/stderr.log /tmp/full-output.log
```

### 练习 20.2：理解 2>&1 的顺序

**题目：**

解释以下两个命令的差异，并用实例验证你的解释：

```bash
ls /tmp /nonexistent > /tmp/out1.txt 2>&1
ls /tmp /nonexistent 2>&1 > /tmp/out2.txt
```

**答案：**

第一条命令（正确）：`> /tmp/out1.txt` 先将 stdout 指向文件，然后 `2>&1` 将 stderr 指向 stdout 当前指向的位置（即文件）。结果：stdout 和 stderr 都写入文件。

第二条命令（错误）：`2>&1` 先将 stderr 指向 stdout 当前指向的位置（即终端），然后 `> /tmp/out2.txt` 将 stdout 指向文件。结果：stdout 进入文件，stderr 仍然输出到终端。

```bash
echo "=== 验证 ==="

# 正确：两者都在文件
ls /tmp /nonexistent > /tmp/out1.txt 2>&1
echo "--- out1.txt（正确）---"
cat /tmp/out1.txt

# 错误：只有 stdout 在文件，stderr 出现在终端
echo "--- 终端输出（来自 stderr，以下可能显示错误信息）---"
ls /tmp /nonexistent 2>&1 > /tmp/out2.txt
echo "--- out2.txt（只有 stdout）---"
cat /tmp/out2.txt

rm -f /tmp/out1.txt /tmp/out2.txt
```

## 5. 常见错误与排错

### 5.1 误区：`2>&1 > file` 和 `> file 2>&1` 一样

**错误案例：**

```bash
# 以为这两个命令等价
ls /tmp /nonexistent 2>&1 > output.txt
ls /tmp /nonexistent > output.txt 2>&1
```

**问题：**

`2>&1 > output.txt` 先复制 stderr 到 stdout 当前的位置（终端），然后改变 stdout 的指向到文件。stderr 的指向不会因为后面 stdout 的改变而改变！文件描述符的复制是"值复制"，不是"引用绑定"。

**正确做法：**

```bash
# 始终将 > file 放在 2>&1 之前
ls /tmp /nonexistent > output.txt 2>&1
# 或使用简写 &>
ls /tmp /nonexistent &> output.txt
```

### 5.2 误区：管道中的 stderr 自动进入下一个命令

**错误案例：**

```bash
# 期望 stderr 也被传给 grep
find /root -name "*.conf" | grep "error"
# 实际上 grep 只收到了 stdout（找到的文件名），没有收到 stderr
```

**问题：**

普通管道 `|` 只连接前一个命令的 stdout 到后一个命令的 stdin。stderr 仍然输出到终端。

**正确做法：**

```bash
# 方法1：使用 2>&1 将 stderr 合并到 stdout
find /root -name "*.conf" 2>&1 | grep "error"

# 方法2：使用 |& (Bash 简写)
find /root -name "*.conf" |& grep "error"

# 方法3：只重定向 stderr 到管道，丢弃 stdout
find /root -name "*.conf" 2>&1 1>/dev/null | grep "error"
```

### 5.3 误区：`sudo command > file` 能写入无权限的文件

**错误案例：**

```bash
# 期望在 sudo 下写入 /etc/hosts
sudo echo "127.0.0.1 myapp" > /etc/hosts
# 报错：Permission denied
```

**问题：**

重定向由**当前 Shell** 执行，而不是由 `sudo` 启动的进程执行。Shell 在启动 `sudo` 之前就尝试打开 `/etc/hosts` 进行写入，但 Shell 本身没有 root 权限。

**正确做法：**

```bash
# 方法1：使用 tee
echo "127.0.0.1 myapp" | sudo tee /etc/hosts

# 方法2：使用 sudo bash -c 整体执行
sudo bash -c 'echo "127.0.0.1 myapp" > /etc/hosts'

# 方法3：先切换到 root shell
sudo -i  # 然后在 root shell 中执行重定向
```

### 5.4 误区：用 `>` 覆盖后再从同一文件读取

**错误案例：**

```bash
# 想排序一个文件并写回原文件
sort data.txt > data.txt
# data.txt 变成空文件！
```

**问题：**

Shell 在 `sort` 命令执行**之前**就执行了重定向。这意味着 `> data.txt` 会在 `sort` 读取 `data.txt` 之前就清空它。`sort` 读取的是一个已经空了的文件。

**正确做法：**

```bash
# 方法1：使用临时文件
sort data.txt > data.tmp && mv data.tmp data.txt

# 方法2：使用 sponge（来自 moreutils 包）
sort data.txt | sponge data.txt

# 方法3：使用 sort -o（sort 命令自己支持输出到文件）
sort data.txt -o data.txt
```

### 5.5 误区：`cat file | command` 总是比输入重定向好

**错误案例：**

```bash
# 无意义的 cat 使用
cat /etc/passwd | grep "root"
cat /var/log/syslog | head -10
cat data.txt | wc -l
```

**问题：**

`cat file | command` 创建了一个不必要的 `cat` 进程，并且多了一次数据拷贝。这被称为"无用的 cat 用法"（Useless Use of Cat，UUOC）。

**正确做法：**

```bash
# 直接用输入重定向或文件名参数
grep "root" /etc/passwd
head -10 /var/log/syslog
wc -l < data.txt
# 或
wc -l data.txt

# 什么时候 cat 是有意义的？
# 1. 多文件合并：cat a.txt b.txt | sort
# 2. 管道逻辑起点：当后续有多个管道操作时，cat 作为视觉上的"起点"
# 3. 交互式命令行中快速修改链头
```

### 5.6 误区：`/dev/null` 是一个普通文件

**错误案例：**

```bash
# 错误地删除了 /dev/null 并重新创建
rm /dev/null
touch /dev/null  # 危险！这会创建一个普通文件
```

**问题：**

`/dev/null` 是一个字符设备文件（Character Device），不是普通文件。如果误删并用 `touch` 重新创建，它变成一个普通文件，不再有"黑洞"行为---写入的数据会积累到磁盘上！此外，许多系统程序和脚本依赖 `/dev/null` 的行为，一个普通文件 `/dev/null` 会导致各种奇怪的问题。

**正确做法：**

```bash
# 如果不小心删除了 /dev/null（需要 root 权限），用 mknod 恢复：
# sudo mknod -m 666 /dev/null c 1 3

# 确认 /dev/null 的类型
ls -l /dev/null
# 输出：crw-rw-rw- 1 root root 1, 3 ... /dev/null
# 第一个字符 'c' 表示字符设备（character device）

# 确认其行为
echo "test" > /dev/null
ls -l /dev/null
# 即使写了数据，大小始终为 0（因为它是字符设备，不是普通文件）
```

### 5.7 误区：管道的两个命令先后执行

**错误案例：**

```bash
# 假设这个命令是先执行完 find 再执行 wc
find / -name "*.log" 2>/dev/null | wc -l
# 期望 find 完全执行完后 wc 才开始
```

**问题：**

管道中的两个命令是**同时启动**的，它们通过管道缓冲区同步。如果第一个命令产生数据的速度远超第二个命令的消费速度，第一个命令的 `write()` 会阻塞。反之，如果第二个命令消费速度超过第一个命令的生产速度，第二个命令的 `read()` 会阻塞。

这个误解在以下场景可能出问题：

- 想用管道实现"生产者完成后消费者开始"的串行逻辑
- 期望管道中的环境变量在两侧共享（它们在不同的进程中！）

**正确理解：**

```bash
# 管道是并发的，不是串行的
# 验证：
(echo "A"; sleep 2; echo "B") | (echo "Start"; cat; echo "End")
# 你会看到 "Start" 立即出现，然后是 "A"，2 秒后是 "B"，最后是 "End"
# 如果两个命令先后执行，"Start" 不会在 "A" 之前出现
```

### 5.8 误区：Here Document 的标记可以缩进

**错误案例：**

```bash
if true; then
    cat << EOF
    some text
    EOF     # 缩进不合法！EOF 必须从行首开始
fi
```

**问题：**

Here Document 的结束标记（DELIMITER）必须从行首开始（前面不能有任何空白字符，包括空格和 Tab）。如果结束标记前面有缩进，Shell 不会识别它，会把后续内容也当作 Here Document 的一部分。

**正确做法：**

```bash
# 方法1：使用 <<- 并保证内容以 Tab（不是空格）缩进
if true; then
    cat <<- EOF
	this line has tab indent
	EOF
fi

# 方法2：结束标记不缩进（牺牲代码美观）
if true; then
    cat << EOF
    some text
EOF
fi

# 方法3：使用 printf 或 echo 替代（对于简单文本）
if true; then
    printf '%s\n' "some text"
fi
```

### 5.9 误区：`PIPESTATUS` 可以在任何位置读取

**错误案例：**

```bash
false | true
echo "sth else" > /dev/null
echo "${PIPESTATUS[0]}"  # 可能已经被覆盖了！
```

**问题：**

`PIPESTATUS` 是一个活动变量，每次执行任何命令（包括简单的 `echo`）都会重置它。必须在管道之后**立即**读取。

**正确做法：**

```bash
false | true
PIPE_RESULT=("${PIPESTATUS[@]}")  # 立即保存
echo "sth else" > /dev/null
echo "PIPESTATUS[0] = ${PIPE_RESULT[0]}"  # 使用保存的值
```

## 6. 进阶延伸

### 6.1 匿名管道与命名管道的实现细节

在 Linux 内核中，管道由 `pipefs` 虚拟文件系统实现。

```
+------------------------------------------------------------------+
|                    Linux 管道内核实现                                 |
|                                                                  |
|  用户态                                                           |
|  ┌──────────┐  write(fd[1])    read(fd[0])  ┌──────────┐        |
|  │ 进程 A    │──────→ ──────────── ←───────│ 进程 B    │        |
|  └──────────┘         │ pipefs            └──────────┘        |
|                       │                                        |
|  内核态                │                                        |
|  ┌────────────────────┴─────────────────────────────────┐     |
|  │                  pipe_inode_info                       │     |
|  │  ┌──────────────────────────────────────────────────┐ │     |
|  │  │              环形缓冲区（16 × 4096 = 64KB）       │ │     |
|  │  │  head (写指针)          tail (读指针)              │ │     |
|  │  │     ↓                      ↓                      │ │     |
|  │  │  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐      │ │     |
|  │  │  │   │   │   │   │   │   │   │   │   │   │ ...  │ │     |
|  │  │  └───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘      │ │     |
|  │  │   page 0  page 1  ...             page 15        │ │     |
|  │  └──────────────────────────────────────────────────┘ │     |
|  │                                                       │     |
|  │  readers: 进程等待队列（等待数据）                      │     |
|  │  writers: 进程等待队列（等待空闲空间）                  │     |
|  └───────────────────────────────────────────────────────┘     |
+------------------------------------------------------------------+
```

**关键内核数据结构：**

- 管道由 16 个内存页（page）组成环形缓冲区（ring buffer），每个页 4KB，总计 64KB
- `head` 指针指向下一个写入位置
- `tail` 指针指向下一个读取位置
- 当 head == tail 时缓冲区为空
- 当 head + 1 == tail（模运算）时缓冲区已满
- 从 Linux 2.6.35 可以调整管道容量（通过 `fcntl(F_SETPIPE_SZ)`）

```bash
# 查看当前管道容量的系统限制
cat /proc/sys/fs/pipe-max-size
# 输出：1048576（1MB —— 这是最大可设置值）

# 查看管道使用情况（如果有活跃的管道）
lsof 2>/dev/null | grep "FIFO" | head -5
```

### 6.2 重定向的性能考量

不同重定向方式的性能差异在大量数据或高频调用时显著：

| 方式 | 子进程 | 内核拷贝 | 适用场景 |
|------|--------|---------|---------|
| `sort < file` | 1 | 1 次（内核→进程） | 单文件处理 |
| `cat file \| sort` | 2 | 2 次（内核→cat→内核→sort） | 多文件合并或管道链 |
| `tr ',' '\n' <<< "$VAR"` | 1 | 0（Bash 内部） | 小量字符串处理 |
| `echo "$VAR" \| tr ',' '\n'` | 2 | 1 次（通过管道） | 一般情况 |

```bash
# 性能对比实验（概念性）
echo "=== 大文件读取性能对比 ==="
# 创建一个 100MB 的测试文件
dd if=/dev/zero of=/tmp/bigfile.txt bs=1M count=100 2>/dev/null

echo "方法1：输入重定向（无额外进程）"
time wc -l < /tmp/bigfile.txt

echo "方法2：cat + 管道（多一个进程）"
time cat /tmp/bigfile.txt | wc -l

rm -f /tmp/bigfile.txt
```

### 6.3 高级管道：协同进程（Coprocess）

Bash 支持**协同进程（Coprocess）**，允许在后台运行一个命令，并通过文件描述符与之双向通信。

```bash
# 协同进程：bc 计算器作为后台协程
echo "=== 协同进程演示 ==="

# 启动 bc 作为协同进程
coproc BC { bc -l; }

# 向协同进程发送命令
echo "3.14159 * 2" >&${BC[1]}

# 读取结果
read -u ${BC[0]} RESULT
echo "结果: $RESULT"
# 输出：结果: 6.28318

# 发送更多计算
echo "sqrt(144)" >&${BC[1]}
read -u ${BC[0]} RESULT2
echo "结果: $RESULT2"
# 输出：结果: 12

# 关闭协同进程
exec {BC[0]}<&- {BC[1]}>&-
```

**协同进程的文件描述符：**

```
coproc NAME { command; }
# 之后：
#   ${NAME[0]} → 读取 command 的 stdout
#   ${NAME[1]} → 写入 command 的 stdin
```

### 6.4 更高级的进程替换：与命名管道的对比

进程替换 `<()` 内部使用命名管道（named pipe, FIFO）或 `/dev/fd/` 来实现。了解其底层机制有助于理解其限制：

```
<(command) 内部执行流程：

1. Bash 创建一个命名管道 (FIFO)
   → /dev/fd/63 （具体编号取决于进程）
   
2. Bash fork + exec 在后台执行 command
   → command 的 stdout 被重定向到 FIFO 的写端
   
3. Bash 将 /dev/fd/63 传递给外部命令
   → 外部命令打开 /dev/fd/63 读取
   → 实际从 FIFO 的读端读取 command 的输出

注意：<(command) 中的 command 必须产生输出
      >(command) 中的 command 必须消费输入
```

**进程替换 vs 管道 vs 临时文件：**

| 特性 | 管道 `\|` | 进程替换 `<()` | 临时文件 |
|------|----------|---------------|---------|
| 需要文件名参数？ | 否 | 是（提供的是伪文件名） | 是 |
| 并行执行？ | 是 | 是 | 否（先完整写入） |
| 需要磁盘空间？ | 否 | 否 | 是 |
| 可随机访问？ | 否（顺序流） | 否（顺序流） | 是 |
| 支持双向？ | 否 | 是（`<()` + `>()`） | 是 |

```bash
# 进程替换的并行执行演示
echo "=== 进程替换并行执行 ==="
time {
    diff <(sleep 2; echo "A"; echo "B") \
         <(sleep 2; echo "A"; echo "C")
}
# 两个 sleep 同时进行，总耗时约 2 秒（不是 4 秒）
```

### 6.5 `/dev/tcp` 和 `/dev/udp`：Bash 内置的网络重定向

Bash 提供了一个独特的特性：通过虚拟路径 `/dev/tcp/HOST/PORT` 和 `/dev/udp/HOST/PORT` 进行网络通信。这不是真实的文件系统路径，而是 Bash 内部识别并处理的特殊重定向目标。

```bash
# Bash TCP 客户端（测试端口是否开放）
echo "=== 测试 HTTP 连接 ==="
timeout 5 bash -c 'echo -e "GET / HTTP/1.0\r\n\r" > /dev/tcp/example.com/80 && head -1 < /dev/tcp/example.com/80' 2>/dev/null
# 输出示例：HTTP/1.0 200 OK

# 简单的端口检测
timeout 3 bash -c 'echo > /dev/tcp/8.8.8.8/53' 2>/dev/null && echo "端口 53 开放" || echo "端口 53 不可达"
# 输出示例：端口 53 开放

# 注意：/dev/tcp 只在 Bash 中有效！
# ls /dev/tcp  → "No such file or directory"（它不是真实的目录）
# 但在 Bash 的重定向中使用它，Bash 会在内部打开 TCP 连接
```

### 6.6 使用 `exec` 永久重定向当前 Shell

`exec` 命令可以在不创建子进程的情况下重定向当前 Shell 的文件描述符：

```bash
cat > /tmp/exec-redirect-demo.sh << 'SCRIPT'
#!/bin/bash

echo "=== exec 永久重定向 ==="
echo "这条消息在设置 exec 之前"

# 将当前脚本的 stdout 重定向到文件
exec > /tmp/exec-output.txt

echo "这条消息被写入文件，不会显示在终端"
echo "这条也是"

# 将 stderr 也重定向
exec 2>&1

echo "包括所有错误输出"

# 恢复终端输出（需要先保存原始 fd）
exec 3>&1
exec >&3
echo "这条消息恢复显示在终端"
SCRIPT
bash /tmp/exec-redirect-demo.sh
echo ""
echo "=== exec 重定向后的文件 ==="
cat /tmp/exec-output.txt

rm -f /tmp/exec-redirect-demo.sh /tmp/exec-output.txt
```

### 6.7 管道与信号：SIGPIPE 在实践中的影响

第 19 章详细讨论了 SIGPIPE 信号。这里从管道使用的角度补充关键知识：

```bash
# SIGPIPE 在实践中的表现
echo "=== SIGPIPE 演示 ==="

# head -1 读取一行后关闭 stdin
# yes 的 write() 在管道读端关闭后触发 SIGPIPE
yes | head -1
echo "退出码: $?"
# 输出：
# y
# 退出码: 141
# 141 = 128 + 13 (SIGPIPE)

# 这在脚本中可能会导致误报的"失败"
# 但这是正常的管道终止行为

# 处理 SIGPIPE 的最佳实践
cat > /tmp/sigpipe-handle.sh << 'SCRIPT'
#!/bin/bash
set -o pipefail

# 场景：用 head 截断无限循环输出
# 正确处理 SIGPIPE
{
    for i in $(seq 1 100); do
        echo "Line $i"
    done
} | head -5
echo "管道退出码: $?"
echo "PIPESTATUS: ${PIPESTATUS[@]}"
# PIPESTATUS[0] 为 141（收到 SIGPIPE）
# PIPESTATUS[1] 为 0  （head 正常退出）
SCRIPT
bash /tmp/sigpipe-handle.sh

rm -f /tmp/sigpipe-handle.sh
```

### 6.8 构建可复用的数据流水线模式

掌握重定向和管道后，你可以构建可复用的数据处理流水线。以下是一些常见模式：

**模式 1：过滤器链（Filter Chain）**

```bash
# 每一级管道是一个独立的过滤步骤
cat /etc/passwd \
  | grep -v '/nologin$' \
  | grep -v '/false$' \
  | cut -d: -f1,3 \
  | sort -t: -k2 -n \
  | column -s: -t
```

**模式 2：分叉合并（Fork-Join）**

```bash
# tee 分叉，分别处理，结果合并
echo "test data line" \
  | tee >(wc -c > /tmp/chars.txt) \
        >(wc -w > /tmp/words.txt) \
        >(md5sum > /tmp/md5.txt) \
  > /dev/null

echo "字符数: $(cat /tmp/chars.txt)"
echo "词数: $(cat /tmp/words.txt)"
echo "MD5: $(cat /tmp/md5.txt)"

rm -f /tmp/chars.txt /tmp/words.txt /tmp/md5.txt
```

**模式 3：条件分支（Conditional Branch）**

```bash
# 根据管道结果决定下一步处理
if grep -q "ERROR" < <(cat /var/log/syslog 2>/dev/null); then
    echo "发现错误！开始分析..."
    grep "ERROR" /var/log/syslog 2>/dev/null | head -5
else
    echo "未发现错误"
fi
```

**模式 4：循环管道（Loop Pipeline）**

```bash
# 在循环中使用管道处理数据
echo "=== 逐行处理 ==="
cat /etc/shells 2>/dev/null | while read -r shell; do
    [[ "$shell" =~ ^# ]] && continue
    echo "Shell: $shell ($(wc -c < "$shell" 2>/dev/null || echo '?'))"
done
```

**本章小结：**

重定向和管道是 Unix/Linux 中最基础也最强大的机制。它们共同构成了"Unix 哲学"的技术支柱：

1. **标准数据流（stdin/stdout/stderr）** 定义了进程间数据交换的统一接口
2. **重定向操作符** 允许你精确控制数据的目标和来源
3. **管道（`|`）** 让进程可以串联成数据处理流水线
4. **tee** 在管道中添加"分叉"能力
5. **进程替换（`<()` `>()`）** 解决了"需要文件名但只有命令输出"的矛盾
6. **Here Document/Here String** 让文本嵌入变得优雅
7. **PIPESTATUS/pipefail** 确保管道中的错误不会被悄然忽略

掌握这些机制，你就能像搭积木一样组合 Unix 小工具，构建出强大而简洁的命令行解决方案。这正是 Unix 区别于其他操作系统生态的核心竞争力。

在下一章中，我们将进入 Shell 脚本编程的世界，学习如何使用变量、条件判断、循环和函数来构建更复杂的自动化脚本。届时，重定向和管道将成为你脚本中数据流转的基本工具。
