# 第 11 课：生产构建与本地预览

## 本课目标

能生成生产构建，读懂 `dist` 的基本内容，用预览服务器检查结果，并建立“开发成功不等于构建成功”的习惯。

## 三条命令再次分开

```powershell
npm run dev
npm run build
npm run preview
```

`dev` 为开发服务，读取源码并提供快速更新。`build` 执行一次生产构建，默认从根目录 `index.html` 追踪模块并把结果写入 `dist`。`preview` 启动本地服务器，提供已经构建好的 `dist`，用于检查生产构建。执行 preview 前应先成功 build；修改源码后需要重新 build，旧的 preview 不会自动代表最新源码。

## 正确的构建流程

先停止不需要的重复服务，确保终端位于有 `package.json` 的项目根目录，然后执行：

```powershell
npm run build
```

成功时终端会列出生成的 HTML、JavaScript、CSS 或资源以及大小信息。构建成功只说明构建器完成任务，不保证每个业务功能都正确。接着执行：

```powershell
npm run preview
```

打开终端显示的地址。默认预览端口通常是 4173，但端口可能被占用或被项目配置改变，永远以终端实际地址为准。至少检查：首页能打开、刷新正常、图片和字体正常、控制台无关键错误、主要按钮和接口可用、动态导入页面可打开。

## dist 是结果，不是源码

`dist` 中的文件可能被压缩、分块和改名。例如 `index-某段哈希.js` 中的哈希有利于浏览器缓存。不要手工修改 `dist` 修 bug，因为下一次构建会覆盖修改，也无法把修复可靠地带回源码。修复应发生在 `src`、`index.html` 或配置文件中，然后重新构建。

通常 `dist` 可以从源码重新生成，不应把它与 `node_modules` 混为一谈：`node_modules` 是安装的依赖，`dist` 是构建输出。是否把 `dist` 提交到 Git 取决于部署方式和团队约定。现代 CI 平台常从源码安装和构建，此时通常不提交；某些特殊发布流程可能要求提交。不要替团队猜规则。

## 构建选项要克制

`build.outDir` 可以改变输出目录，`build.target` 可以调整目标浏览器语法范围，资源内联、CSS 拆分、source map 等也有配置。默认值适合多数现代浏览器项目。降低浏览器目标不代表所有 Web API 自动获得兼容，需要区分语法转换与 API polyfill。支持旧浏览器时应查官方 `@vitejs/plugin-legacy` 文档，并明确目标浏览器范围。

构建报告中的大 chunk 警告不等于构建失败。先确认真实性能问题，再考虑动态导入、路由懒加载或分包。盲目调高警告阈值只是隐藏提醒，盲目手写分包又可能破坏缓存和加载顺序。

## 常见“开发正常、构建失败”原因

文件名大小写不一致；TypeScript 或 lint 脚本在构建链中发现错误；代码依赖只存在于开发环境的全局对象；环境变量模式不同；资源路径或 `base` 不正确；某个插件只在开发路径经过测试。最有价值的信息通常是构建输出靠近末尾的第一条根因，而不是最后一行“build failed”。

## 检查点

执行 build，确认 `dist/index.html` 存在；不要双击它，使用 preview；修改源码中的标题，但不重新构建，观察 preview 仍是旧结果；重新 build 后再预览，确认更新。最后解释为什么不能直接修改 `dist`：它是可重新生成的构建结果。
