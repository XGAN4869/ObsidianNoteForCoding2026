# 09 常见错误与排查（先收集证据，再修改）

## 通用四步法

1. 记下完整错误类型、消息、文件名和行号。
2. 复现：什么输入一定能触发？
3. 缩小范围：在关键步骤打印安全的类型、长度、状态和耗时。
4. 只改一个原因，重新运行原来的复现步骤。

不要一看到报错就删除 `node_modules`、重装电脑或复制网上的“万能修复”。

## `node` 或 `npm` 不是命令

重新打开终端，执行 `where.exe node` 和 `node --version`。检查 PATH 是否包含 Node 安装目录；有多个版本时确认终端使用的路径。

## `Cannot find module`

确认当前目录、文件是否存在、相对路径是否以 `./` 或 `../` 开头。包名导入则检查 `package.json` 和 `npm install`。ESM 还要检查相对导入的扩展名和 `type` 设置。

## `EADDRINUSE`

端口已被占用。Windows 可执行 `Get-NetTCPConnection -LocalPort 3000` 查看占用情况；确认进程后再安全停止，或换一个端口。不要随意结束陌生系统进程。

## Promise 未等待或未捕获

出现顺序异常、`UnhandledPromiseRejection` 时，检查调用处是否缺少 `await`/`return`，以及顶层是否有 `try/catch` 或 `.catch()`。不要写空的 `catch(() => {})`。

## JSON 解析失败、400 与 413

确认请求头是 `application/json`、正文是合法 JSON。服务端捕获 `JSON.parse` 异常返回 400；超过 body 限制返回 413。不要为了“让它通过”取消请求体上限。

## 文件路径在不同系统失效

使用 `path.join`、`path.resolve` 或 ESM 的 `import.meta.url`。相对路径以 `process.cwd()` 为基准，记录启动目录和最终解析路径（不要记录敏感路径）。

## 数据库连接失败

逐项确认服务是否启动、主机和端口、账号权限、数据库名、字符集、连接超时和连接池上限。日志不要打印密码。若连接用完未释放，后续请求会排队或超时。

## Redis 异常

缓存不是唯一数据源。读取失败时回源数据库；写入失败记录指标并允许核心请求继续。为 key 设计统一前缀和 TTL，避免随机 key 无法清理。

## 服务内存持续上涨

检查未移除的监听器、无限增长数组、未关闭的流、定时器和缓存。用 `process.memoryUsage()` 观察趋势，再使用 Node Inspector/Heap Snapshot 定位，不要只增加机器内存。

## 发布后请求变慢

先看访问日志中的路径、状态码、耗时和 request id，再区分数据库、外部 API、CPU 计算或网络。检查慢查询、连接池、缓存命中率和事件循环延迟。

## 安全底线

用户输入必须有类型、长度、权限校验；SQL 参数化；文件限制大小并防路径穿越；密钥放环境变量；依赖定期审计；生产不暴露堆栈；进程不要用 root 运行。
