# 包、模块与依赖管理

## 1. 学习目标

理解包的可见性、模块文件、依赖版本和 internal 规则，能为项目划分清晰目录。

## 2. 包与文件

同一目录中的非测试 Go 文件通常属于同一个包。包名应简短、明确，避免 util、common 这类无边界名称。

~~~text
calculator/
├── add.go
├── subtract.go
└── calculator_test.go
~~~

## 3. 可见性

标识符首字母大写表示可从其他包访问；小写只在当前包可见。

~~~go
type UserService struct{}
func (s *UserService) Register() {}
func (s *UserService) validate() {}
~~~

导出的类型和函数应有文档注释，说明契约而不是重复名称。

## 4. import 与别名

~~~go
import (
	"context"
	"encoding/json"

	blogmodel "example.com/go-blog/internal/model"
)
~~~

只有冲突或增强可读性时使用别名。禁止点导入；空白导入只用于确实需要副作用注册的驱动。

## 5. init

init 无参数、无返回值，由运行时自动调用。它适合轻量注册，不适合数据库连接、网络请求等可能失败的操作。需要返回错误的初始化必须显式放进构造函数或 main。

## 6. go.mod 与 go.sum

~~~text
module example.com/go-blog

go 1.22
~~~

常用命令：

~~~powershell
go mod tidy
go get github.com/gin-gonic/gin
go list -m all
go mod graph
go mod why -m 模块路径
~~~

go.sum 保存依赖内容校验信息，应提交版本控制。不要随意手工修改。

## 7. 版本与升级

升级前先查看变更，再运行完整测试：

~~~powershell
go get example.com/dependency@v1.2.3
go mod tidy
go test ./...
~~~

主版本 v2+ 通常进入模块导入路径，例如 example.com/lib/v2。

## 8. internal 与 pkg

internal 下的包只能被指定父目录树内的代码导入，适合项目私有业务实现。

pkg 不是 Go 强制约定；只有确实希望其他项目复用时才放入 pkg。博客中的响应、JWT 等即使位于 pkg，也要保持稳定边界。

## 9. 拆包原则

按业务职责和变化原因拆分，而不是按“所有 struct 一个包、所有 interface 一个包”机械分层。

推荐依赖方向：

~~~text
handler → service → repository interface
                 ↑
          repository implementation
~~~

上层通过接口依赖能力，main 负责组装实现。避免 service 与 handler 互相导入。

## 10. 循环依赖处理

出现循环依赖通常说明职责放错位置。解决方式：

- 把共享的小类型移到更底层的明确包。
- 在使用方定义接口。
- 合并本来就属于同一职责的包。
- 通过事件或回调解除双向调用。

不要建立一个巨大的 common 包掩盖问题。

## 11. 博客模块示例

~~~text
go-blog/
├── cmd/server
├── internal/handler
├── internal/service
├── internal/repository
├── internal/model
└── pkg/response
~~~

cmd/server 只负责启动和组装；业务逻辑不能堆在 main.go 中。

## 12. 练习

1. 创建含两个包的小模块，并测试导出规则。
2. 使用 go mod why 查一个间接依赖来源。
3. 为博客的用户、文章、认证模块画依赖箭头。
4. 找一个可能叫 util 的函数，为它选择更具体的包。
