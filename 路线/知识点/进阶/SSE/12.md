# `my.md` 模型流式对话改进指南

> 分析对象：`src/pages/modelDialogue/my.md`
>
> 目标：把当前半成品按照容易理解、容易测试的顺序，逐步补成完整的 SSE 流式聊天页面。

## 一、先弄清楚：`my.md` 会不会运行

不会。

`my.md` 是 Markdown 笔记文件。文件里面虽然写了：

````md
```vue
<template>...</template>
```
````

但是这些内容只会作为代码示例展示，不会被 Vue 或 Vite 编译。

项目真正运行的文件是：

```text
src/pages/modelDialogue/modelDialogue.vue
```

所以：

- `my.md` 适合记录学习步骤。
- `modelDialogue.vue` 才是页面业务代码。
- 修改 `my.md` 不会改变浏览器里的页面。

## 二、当前 `my.md` 已经写对的部分

### 1. 输入框状态使用字符串

```js
const chatMessage = ref('')
```

这是正确的。textarea 输入的是文字，所以初始值应该是空字符串，而不是数组。

### 2. 使用数组保存会话

```js
const messageList = ref([])
```

这是正确方向。一轮聊天中会有多条 user 和 assistant 消息，因此应该用数组保存。

### 3. 使用 `reactive` 保存请求参数

```js
const chatData = reactive({})
```

两个选择组件会分别传来 `apiKeyId` 和 `model`，使用 `Object.assign` 合并是可以的。

### 4. 使用原生 `fetch`

SSE 需要读取 `response.body`，当前使用原生 `fetch` 的方向正确。

### 5. 使用 `shallowRef` 保存 AbortController

```js
const controller = shallowRef(null)
```

AbortController 是浏览器原生实例，不需要深层响应式，因此 `shallowRef` 合适。

## 三、当前 `my.md` 哪里不对

## 【必须改】

### 问题 1：模板没有循环显示消息

当前只有：

```vue
<MdPreview />
```

但没有：

```vue
v-for="item in messageList"
```

结果是：即使 `messageList` 成功添加了用户消息，页面也不会显示出来。

### 问题 2：`MdPreview` 没有绑定正文

当前：

```vue
<MdPreview />
```

至少需要传入：

```vue
<MdPreview :model-value="item.content" />
```

否则 Markdown 预览组件不知道应该显示什么。

### 问题 3：骨架屏一直显示

当前：

```vue
<t-skeleton theme="paragraph" />
```

它没有 `v-if`，所以不管是否正在请求都会显示。

应该根据 assistant 消息状态决定是否显示，例如：

```vue
<t-skeleton
  v-if="item.status === 'streaming' && !item.content"
  theme="paragraph"
/>
```

### 问题 4：发送前没有校验输入内容

当前直接把输入框内容 push 进去。如果用户只输入空格，也会发请求。

应该先写：

```js
const question = chatMessage.value.trim()

if (!question) return
```

### 问题 5：没有校验 API Key 和模型

如果用户没有选择 API Key 或模型，当前也会请求后端。

发送前至少需要检查：

```js
if (!chatData.apiKeyId) return
if (!chatData.model) return
```

当前 `selectModel.vue` 在清空选择时，还可能传出 `qwen/undefined`，所以发送函数里也应该防守：

```js
if (!chatData.model || chatData.model === 'qwen/undefined') return
```

### 问题 6：用户消息缺少状态

当前消息：

```js
{
  role: 'user',
  content: chatMessage.value,
}
```

后面为了排除失败或中断的 assistant 消息，建议统一增加：

```js
status: 'done'
```

### 问题 7：没有创建 assistant 消息

当前只添加 user 消息，没有创建 assistant 消息。

流式响应不能每收到一个 delta 就新增一条消息，而是应该先创建一个空对象：

```js
messageList.value.push({
  role: 'assistant',
  content: '',
  reasoning: '',
  status: 'streaming',
  finishReason: null,
  usage: null,
  error: '',
})
```

之后所有 delta 都追加到这个对象上。

### 问题 8：`assistantMessage` 声明了但没有使用

当前：

```js
const assistantMessage = ref(null)
```

但后面没有给它赋值，也没有用它更新页面。

更容易理解的方式是：创建 assistant 消息后，从响应式数组中取出最后一项。

```js
const assistantMessage =
  messageList.value[messageList.value.length - 1]
```

这个变量只服务当前一次请求，不必再声明成全局 Ref。

### 问题 9：输入框发送后没有清空

应该在保存 `question` 后写：

```js
chatMessage.value = ''
```

注意要先保存 `question`，再清空输入框。

### 问题 10：请求历史直接使用整个 `messageList`

当前：

```js
Object.assign(chatData, {
  stream: true,
  messages: messageList.value,
})
```

以后 assistant 消息会包含 `reasoning`、`usage`、`status` 和 `error`，这些字段没有必要发给模型。

应该整理成后端需要的最小结构：

```js
const requestMessages = messageList.value
  .filter((item) => item.status === 'done')
  .map((item) => ({
    role: item.role,
    content: item.content,
  }))
```

### 问题 11：原生 `fetch` 没有携带登录 Token

项目的 Axios 拦截器会自动添加：

```js
Authorization: token
```

但是原生 `fetch` 不会经过 Axios 拦截器，所以需要手动读取 Token：

```js
const token = getToken()

if (token) {
  headers.Authorization = token
}
```

否则登录接口受保护时可能返回 401。

### 问题 12：AbortController 没有真正创建和使用

当前只声明了：

```js
const controller = shallowRef(null)
```

发送前还要创建：

```js
controller.value = new AbortController()
```

并在 fetch 中传入：

```js
signal: controller.value.signal
```

否则 `controller.value?.abort()` 无法停止请求。

### 问题 13：没有检查 HTTP 状态和响应体

不能直接假设 `res.body` 一定存在。

应该检查：

```js
if (!response.ok) {
  throw new Error(`请求失败：HTTP ${response.status}`)
}

if (!response.body) {
  throw new Error('响应体不支持流式读取')
}
```

### 问题 14：`reader` 和 `decoder` 创建后没有使用

当前代码停在：

```js
const reader = body.getReader()
const decoder = new TextDecoder()
```

这只是拿到了工具，还没有读取任何数据。

必须通过循环执行：

```js
const { value, done } = await reader.read()
```

### 问题 15：关于 `response.body` 的注释不准确

当前注释说：

```js
// response.body 是同步的
```

更准确的理解是：

- `fetch()` 是异步的。
- fetch 成功后可以取得 `response.body`。
- `response.body` 是 ReadableStream。
- 调用 `reader.read()` 读取每一批数据仍然是异步的，必须 `await`。

### 问题 16：没有处理网络分片

一次 `reader.read()` 不等于一条完整 SSE。

可能出现：

- 一批数据中有多条 SSE。
- 一条 SSE 被拆成两批。
- 一个汉字的 UTF-8 字节被拆开。

所以需要：

```js
decoder.decode(value, { stream: true })
```

并用 `buffer` 保存不完整内容。

### 问题 17：没有兼容后端的双层 `data:`

当前后端实际格式：

```text
data:data: {JSON}
```

结束格式：

```text
data:data: [DONE]
```

前端必须先剥离 SSE 外层 `data:`，再剥离后端多加的一层 `data:`。

### 问题 18：没有解析 `reasoning_content` 和 `content`

后端先返回：

```js
delta.reasoning_content
```

再返回：

```js
delta.content
```

应该分别追加：

```js
assistantMessage.reasoning += delta.reasoning_content
assistantMessage.content += delta.content
```

不能把思考内容和最终正文混在同一个字段中。

### 问题 19：不能在 `finish_reason: 'stop'` 时结束读取

你的后端数据顺序是：

```text
finish_reason: stop
        ↓
usage 数据包
        ↓
[DONE]
```

如果看到 `stop` 就结束循环，会丢失 usage。

真正的结束标志应该是：

```text
[DONE]
```

### 问题 20：没有异常和收尾处理

需要使用：

```js
try {
  // 请求和读取
} catch (error) {
  // 标记 error 或 aborted
} finally {
  // 恢复按钮和清理 controller
}
```

否则请求失败后，`isTyping` 可能一直处于错误状态。

### 问题 21：组件卸载时没有停止请求

用户在回答生成中离开页面时，应该执行：

```js
onBeforeUnmount(() => {
  controller.value?.abort()
})
```

### 问题 22：刷新和清空按钮没有点击事件

两个按钮目前只有外观，没有 `@click`，所以点击不会执行任何逻辑。

### 问题 23：`RefreshIcon` 没有导入

模板使用了：

```vue
<refresh-icon />
```

脚本只导入了 `DeleteIcon`。应该同时导入：

```js
import {
  DeleteIcon,
  RefreshIcon,
} from 'tdesign-icons-vue-next'
```

## 第 8 步：先学会解析一条 SSE

### 这个 function 是干嘛的

`getSseData` 只负责剥离 SSE 外壳，不负责处理业务字段。

### 它接收什么数据

一条完整 SSE 文本，例如：

```text
data:data: {"choices":[]}
```

### 它返回什么结果

返回 JSON 字符串或 `[DONE]`。

```js
const getSseData = (frame) => {
  const dataText = frame
    .split('\n')
    .filter((line) => line.startsWith('data:'))
    .map((line) => line.slice(5).trimStart())
    .join('\n')

  let result = dataText

  if (result.startsWith('data:')) {
    result = result.slice(5).trimStart()
  }

  return result
}
```

### 小白应该怎么模仿

一个函数只负责一件事：这个函数只拆包装，不修改页面消息。

## 第 9 步：处理一条 SSE 业务数据

### 这个 function 是干嘛的

`handleSseFrame` 负责把一条 SSE 中的数据追加到 assistant 消息。

### 它接收什么数据

- `frame`：一条完整 SSE。
- `assistantMessage`：当前正在生成的 AI 消息。

### 它返回什么结果

- 收到 `[DONE]` 返回 `true`。
- 其他情况返回 `false`。

### 核心顺序

```text
剥离 data:
  ↓
判断 [DONE]
  ↓
JSON.parse
  ↓
保存 usage
  ↓
读取 choice.delta
  ↓
追加 reasoning_content/content
```

### 核心代码

```js
if (delta.reasoning_content) {
  assistantMessage.reasoning += delta.reasoning_content
}

if (delta.content) {
  assistantMessage.content += delta.content
}
```

## 第 10 步：循环读取网络流

### 这个 function 是干嘛的

`readSseStream` 负责把不规则的网络 chunk 拼成完整 SSE frame。

### 为什么需要 buffer

假设一条完整数据是：

```text
data:data: {"content":"你好"}\n\n
```

网络可能拆成：

```text
第一批：data:data: {"content":"你
第二批：好"}\n\n
```

所以第一批不能立刻 JSON.parse，必须先放进 buffer，等第二批到达后再拼起来。

### 固定骨架

```js
const reader = response.body.getReader()
const decoder = new TextDecoder('utf-8')

let buffer = ''
let receivedDone = false

while (!receivedDone) {
  const { value, done } = await reader.read()

  if (value) {
    buffer += decoder.decode(value, { stream: true })
  }

  if (done) {
    buffer += decoder.decode()
  }

  buffer = buffer.replace(/\r\n?/g, '\n')

  let frameEnd

  while ((frameEnd = buffer.indexOf('\n\n')) !== -1) {
    const frame = buffer.slice(0, frameEnd)
    buffer = buffer.slice(frameEnd + 2)

    if (!frame.trim()) continue

    receivedDone = handleSseFrame(frame, assistantMessage)

    if (receivedDone) break
  }

  if (done) break
}
```

## 第 11 步：使用 try/catch/finally 收尾

```js
try {
  const response = await fetch(/* 请求配置 */)

  await readSseStream(response, assistantMessage)
} catch (error) {
  if (error.name === 'AbortError') {
    assistantMessage.status = 'aborted'
  } else {
    assistantMessage.status = 'error'
    assistantMessage.error = error.message
  }
} finally {
  isTyping.value = false
  controller.value = null
  scrollAuto()
}
```

最后再处理这些显示细节：

- 正在生成时显示骨架屏。
- 生成中发送按钮变成停止按钮。

## 五、`handle_message` 的完整理解

### 这个 function 是干嘛的

它是整个聊天流程的总入口，负责校验、整理历史、创建消息、发送请求、读取流以及异常收尾。

### 它接收什么数据

不需要参数。它从页面状态中读取：

- `chatMessage.value`
- `chatData.apiKeyId`
- `chatData.model`
- `messageList.value`

### 它返回什么结果

不需要向调用者返回业务数据。它通过修改响应式状态更新页面。

### 它中间做了哪几步

1. 获取用户输入。
2. 校验输入、API Key 和模型。
3. 添加 user 消息。
4. 整理后端需要的历史消息。
5. 创建空 assistant 消息。
6. 清空输入框并锁定发送状态。
7. 创建 AbortController。
8. 整理 URL、请求头和请求体。
9. 发起 fetch。
10. 检查 HTTP 状态。
11. 调用 `readSseStream`。
12. 在 catch 中区分主动停止和真正错误。
13. 在 finally 中恢复页面状态。

### 小白应该怎么模仿

所有“提交类函数”都可以按这个顺序写：

```text
获取数据
  ↓
校验数据
  ↓
整理请求参数
  ↓
提前更新页面状态
  ↓
调用接口
  ↓
处理成功结果
  ↓
处理错误
  ↓
统一收尾
```

## 六、推荐的函数拆分

不要把所有代码都塞进 `handle_message`。推荐保持下面的职责：

| 函数 | 只负责什么 |
| --- | --- |
| `getParams` | 接收子组件参数 |
| `scrollAuto` | 滚动到底部 |
| `getSseData` | 去掉 SSE 的 data 外壳 |
| `handleSseFrame` | 处理一条完整 SSE |
| `readSseStream` | 把网络 chunk 拼成完整 SSE |
| `handle_message` | 组织整个发送流程 |
| `stopGenerate` | 停止当前请求 |
| `clearMessages` | 清空消息 |
| `refreshOptions` | 重新获取选择项 |

这种拆分值得模仿，因为每个函数只有一个明确任务，出错时更容易定位。

## 七、最终测试顺序

不要只测试一次“你好”。按照下面顺序逐个验证。

### 基础消息

- 输入“你好”后能显示 user 消息。
- 发送后输入框能清空。
- 空内容不能发送。
- 连续发送时历史消息顺序正确。

### 参数校验

- 未选 API Key 时不请求。
- 未选模型时不请求。
- 清空模型后不会发送 `qwen/undefined`。

### SSE

- `reasoning_content` 能逐段追加。
- `content` 能逐段追加。
- 中文和 emoji 没有乱码。
- 一次网络 chunk 包含多条 SSE 时不会漏数据。
- 一条 SSE 被拆成多批时不会 JSON.parse 报错。
- 双层 `data:data:` 能正常剥离。

### 完成状态

- `finish_reason: stop` 后继续读取 usage。
- 收到 `[DONE]` 后状态变成 done。
- token 用量能显示。

### 异常状态

- HTTP 401 能重新登录。
- HTTP 500 能显示错误。
- 后端提前断流能显示错误。
- 点击停止后状态变成 aborted。
- 离开页面后请求会取消。

### 页面操作

- 清空按钮能清空消息。
- 生成过程中不能直接清空。
- 刷新按钮能重新请求 API Key 和模型列表。
- 消息增加后能自动滚动到底部。

## 八、举一反三

### 同类 function 一般先做什么

先从 `ref` 或 `reactive` 中读取页面状态，并做必填校验。

### 再做什么

把页面状态整理成后端真正需要的参数，避免直接发送整个页面对象。

### 最后做什么

调用接口，在 `catch` 中处理异常，在 `finally` 中恢复 loading、按钮和控制器。

### 哪些内容应该抽出去

- 纯文本转换逻辑，例如 `getSseData`。
- 单条数据处理逻辑，例如 `handleSseFrame`。
- 网络循环逻辑，例如 `readSseStream`。
- 页面通用操作，例如 `scrollAuto`。

### 哪些情况适合 computed

如果以后希望根据输入框、API Key、模型和生成状态统一控制发送按钮，可以写：

```js
const canSend = computed(() => {
  return Boolean(
    chatMessage.value.trim() &&
      chatData.apiKeyId &&
      chatData.model &&
      !isTyping.value,
  )
})
```

当前阶段不是必须，先把基础流程写熟更重要。

### 哪些情况适合 watch

当前页面不需要 watch。API Key 和模型变化后，由子组件主动 emit 即可。不要为了使用 watch 而使用 watch。

## 九、一句话总结

这个页面的核心不是“写一个很大的 fetch”，而是先建立一条 assistant 消息，再把不规则网络分片拼成完整 SSE，最后把每个 delta 追加到这同一条消息中。
