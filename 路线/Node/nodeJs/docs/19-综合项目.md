# 19 综合项目：任务管理 API

这是把前面知识连起来的毕业练习。先做最小版，再逐步增加可靠性，不要求一次完成全部功能。

## 1. 需求

用户可以创建任务、查看自己的任务、标记完成、删除任务。每个任务有 `id`、`ownerId`、`title`、`status`、`createdAt`。只有任务所有者能查看和修改。

## 2. 第一期：内存版

实现：

- `GET /health`
- `GET /tasks?status=pending`
- `POST /tasks`
- `PATCH /tasks/:id`
- `DELETE /tasks/:id`

先固定一个练习用户 `ownerId=1`。为每个输入设置类型、长度和允许值，统一返回错误码。

## 3. 第二期：MySQL 版

建立 `tasks` 表和索引（`owner_id`、`status`、`created_at`）。把数据库读写放到 repository，把业务规则放到 service。创建任务和写审计记录需要事务。使用参数化 SQL 或可靠 ORM，迁移文件进入版本控制。

## 4. 第三期：认证与缓存

加入登录或测试 Token，服务端解析后得到 `ownerId`；每次查询都带 `owner_id` 条件。列表可使用 Redis 短缓存，创建/修改/删除后清理对应 key。Redis 失败时回源数据库。

## 5. 第四期：异步提醒

创建任务时发送“提醒任务”消息，worker 在指定时间发送通知。消息有版本、幂等键和最大重试次数；失败进入死信队列。HTTP 接口返回 `202` 表示已接受异步处理，不谎称通知已经完成。

## 6. 第五期：质量和部署

补齐单元、集成和 API 测试；加入 request id、JSON 日志、健康检查和优雅退出；使用 `npm ci` 发布；检查 body 上限、CORS、速率限制、依赖审计和备份恢复。

## 8. 评分标准（自评）

每项 0～2 分：能运行、能解释、能测试。项目不是越复杂分越高；能诚实写出限制，比“假装全部完成”更重要。
