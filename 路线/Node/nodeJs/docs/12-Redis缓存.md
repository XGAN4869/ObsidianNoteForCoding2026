# 12 Redis：缓存、计数和可靠性

## 1. Redis 适合做什么

Redis 是内存数据存储，常见数据结构有 string、hash、list、set、sorted set。它适合缓存、短期会话、计数、排行榜和 Streams 队列辅助数据；它不应自动替代唯一的持久化数据库。

## 2. Key 设计与 TTL

统一前缀和版本有助于排查：

```text
app:v1:user:42
app:v1:notes:list:user:42
```

缓存写入几乎都要设置过期时间（TTL），避免旧数据永久存在。读取失败时可以回源数据库；缓存失效不应让核心业务完全不可用。

## 3. Cache-aside（旁路缓存）

1. 先查 Redis。
2. 命中就返回。
3. 未命中则查数据库。
4. 把结果写回 Redis，并设置 TTL。
5. 数据更新成功后删除或更新对应缓存。

更新数据库和缓存不是天然原子操作，要接受短暂不一致，并按业务选择删除、延迟双删或消息通知等策略。

## 4. Pub/Sub 与 Streams

Pub/Sub 订阅者离线时通常收不到过去的消息，不能当作可靠任务队列。需要确认、重试和消费进度时使用 Redis Streams、RabbitMQ 或 Kafka 等可靠方案，并给消息设计幂等键。

## 5. 计数、Lua 与锁

`INCR` 可原子增加计数；限流计数通常配合 TTL。Lua 脚本可把“检查并修改”放在 Redis 内原子执行，但脚本要短小，不能在脚本中做慢操作。分布式锁必须设置过期时间、唯一 token，并在释放时确认 token 属于自己；复杂场景不要手写半可靠锁。

## 6. 持久化和高可用

RDB 是快照，AOF 是追加命令日志，二者各有恢复和性能取舍。副本可能有延迟；Sentinel 负责故障转移，但不能解决业务幂等。连接客户端应设置合理重连上限和超时。

## 动手题与检查

用 Redis 为 `GET /notes` 增加 30 秒缓存；修改笔记后清理缓存。模拟 Redis 不可用，确认 API 能否回源或返回明确降级结果。

- [ ] Key 有前缀和 TTL。
- [ ] 没把 Pub/Sub 当可靠队列。
- [ ] 了解缓存与数据库短暂不一致的可能。
