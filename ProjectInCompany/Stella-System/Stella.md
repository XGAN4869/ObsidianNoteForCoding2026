## 整体判断与推荐技术栈

这个项目不能只看成一组后台管理表格，它同时包含四类系统：

- Vue 页面与表单系统。
- WebSocket 实时状态系统。
- 拓扑图、资源趋势图等可视化系统。
- 文件传输与浏览器运维工具。

普通列表、分页和弹窗不是主要难点。真正困难的是：大量状态的增量更新、推送与轮询的数据一致性、浏览器能力边界、异常恢复，以及前后端协议是否清晰。

本文默认采用以下技术组合来讲解解决思路：

- Vue 3 + TypeScript。
- Vue Router + Pinia。
- Element Plus。
- AntV G6 绘制拓扑图，ECharts 绘制资源趋势图。
- Axios 处理普通 HTTP 请求。
- WebSocket 处理实时事件和终端数据。
- IndexedDB 保存大文件传输会话。
- xterm.js 实现浏览器终端界面。

## 难点一：卫星拓扑可视化

### 需求背景

需求要求在概览页展示星座、卫星及其链路关系，并支持至少 100 颗卫星、280 个节点的指标数据。用户还需要进行星座切换、画布缩放、拖拽、搜索定位、节点点击、悬停、右键菜单和详情跳转。在线状态由 WebSocket 推送，结构数据还会定时刷新。

### 困难原因

- 力导向布局、连线动画和节点状态更新都会占用主线程。
- 如果把每个节点做成 Vue DOM 组件，响应式代理和 DOM 更新成本较高。
- 如果每收到一条状态消息就销毁并重建 G6，画布会闪烁、位置会抖动。
- 全星座视图同时开启动画、标签和 Tooltip，容易掉帧。
- 切换星座或离开页面后，如果事件监听没有清理，会发生重复响应和内存泄漏。

### 推荐架构

把拓扑数据拆成低频结构数据和高频状态数据。

```text
拓扑结构接口（低频）
  ├─ 卫星节点
  ├─ 星座归属
  ├─ 卫星连线
  └─ 布局坐标

WebSocket（高频）
  ├─ 三类在线状态
  ├─ 资源摘要
  ├─ 告警状态
  └─ 链路状态
```

- 结构数据首次进入页面时加载，之后按需求每 20 秒校正一次。
- 状态消息只更新发生变化的节点或连线。
- G6 实例只创建一次，切换数据时执行增量更新，不反复销毁重建。

### 核心数据结构

```ts
interface SatelliteTopologyNode {
  id: string
  constellationId: string
  name: string
  type: string
  nodeCount: number
  resourceScore: number
  computeOnline: boolean
  imageServiceOnline: boolean
  dataOnline: boolean
  alarmLevel?: 'none' | 'warning' | 'critical'
  version: number
  updatedAt: number
}

interface SatelliteTopologyEdge {
  id: string
  source: string
  target: string
  online: boolean
  trafficStatus?: 'idle' | 'normal' | 'busy'
  version: number
  updatedAt: number
}
```

节点必须使用后端 ID 作为唯一标识，不能依赖名称，因为名称可能重复或被修改。

### Vue 与 G6 的职责

Vue 负责：

- 星座选择器和卫星搜索框。
- 当前选中卫星 ID。
- 信息卡片、右键菜单、加载状态和错误状态。
- 路由跳转和跨模块筛选。

G6 负责：

- 节点和连线绘制。
- 布局、缩放、拖拽和画布事件。
- 节点高亮、聚焦与状态样式更新。

推荐将 G6 实例放入 `markRaw()`，图数据使用 `shallowRef()`，避免 Vue 深度代理整个图数据。Pinia 中保存可序列化的业务数据，不保存 G6 实例。

### 页面运行流程

```text
进入概览路由
→ 读取星座筛选参数
→ 请求拓扑结构快照
→ 初始化或更新 G6
→ 建立节点 ID 索引
→ 订阅 WebSocket 状态事件
→ 增量更新对应节点
→ 用户点击节点
→ 按 ID 请求最新摘要
→ 打开信息卡片或跳转详情
```

### 实现步骤

1. 先用静态数据完成节点、边、缩放和拖拽。
2. 再加入节点点击、悬停、右键菜单和搜索定位。
3. 建立 `Map<satelliteId, nodeData>`，搜索确认后直接按 ID 聚焦，不扫描 DOM。
4. 接入结构接口，只在节点或边真正发生变化时更新图结构。
5. 接入 WebSocket，只修改节点状态样式。
6. 将一帧内的多条状态消息放入队列，通过 `requestAnimationFrame` 批量刷新。
7. 为全星座视图设置降级策略：隐藏低优先级标签，减少普通链路动画。
8. 在组件卸载时取消订阅、移除 ResizeObserver 和 G6 事件。

### 性能策略

- 拓扑结构不变时保留已有坐标，不重新运行布局。
- 缩放比例较小时隐藏名称和次要图标。
- 全星座视图只为告警链路或选中链路显示动画。
- 大型数据转换可以放入 Web Worker，避免阻塞 UI。
- 搜索建议做防抖，并建立名称到卫星 ID 的索引。
- 窗口 resize 使用 ResizeObserver 和防抖，不连续重绘。
- 接口请求支持 AbortController，快速切换星座时取消旧请求。

### 前后端职责

前端负责画布渲染、交互、状态合并和性能降级；后端负责返回稳定的节点 ID、边关系、版本号、更新时间和可计算的状态字段。布局可以由前端完成，但资源统计、卫星关系和链路真实性必须以后端数据为准。

### 异常场景

- 拓扑接口失败：保留旧数据并显示“数据可能已过期”，提供重试。
- WebSocket 断开：画布保留最后快照，顶部显示断线提示。
- 搜索目标已被删除：清除选中状态并提示目标不存在。
- 全星座数据过大：关闭普通动画，优先保证缩放和点击可用。

### 常见错误

- 每次状态变化都重新创建 G6。
- 使用卫星名称作为唯一键。
- 在深层 `watch` 中转换整张图。
- 每条推送都触发一次同步重绘。
- 页面卸载后没有移除图事件和定时器。

### 验收清单

- [ ] 100 颗卫星和合理数量连线下，缩放拖拽无明显卡顿。
- [ ] 单个卫星状态更新不会导致全图闪烁或重新布局。
- [ ] 搜索确认后 1 秒内定位并打开信息卡片。
- [ ] 连续状态消息不会导致内存持续上涨。
- [ ] 切换星座不会出现旧请求覆盖新页面。
- [ ] 离线卫星连线切换为虚线并停止动画。
- [ ] 页面反复进入退出后，事件监听数量不增加。

## 难点二：WebSocket 实时状态同步

### 需求背景

项目要求卫星状态、任务结果、告警和在线离线事件实时推送，延迟不超过 3 秒；连接断开后按 1、2、4 秒递增重连，最大间隔 30 秒；全系统复用同一个 WebSocket。同时，拓扑还有 20 秒轮询，数据任务有 3 秒轮询。

### 困难原因

- 多页面可能重复建立连接或重复订阅。
- 旧轮询响应可能覆盖较新的 WebSocket 状态。
- 重连后可能丢失断线期间的事件。
- Token 失效与普通网络断开需要不同处理。
- 事件重复、乱序或消息突发会导致状态错误和通知刷屏。

### 推荐架构

```text
全局 WebSocket 连接服务
        ↓
事件解析、校验、去重、分发中心
        ↓
卫星 Store / 任务 Store / 文件 Store / 通知 Store
        ↓
页面组件
```

连接服务在登录成功后由应用层启动，不写在具体业务页面中。普通页面只订阅业务 Store，不直接管理连接。

### 建议事件结构

```ts
interface RealtimeEvent<T> {
  eventId: string
  type: string
  resourceId: string
  version: number
  serverTime: number
  payload: T
}
```

- `eventId`：去重。
- `type`：区分卫星状态、任务状态、告警等。
- `resourceId`：定位业务对象。
- `version`：解决乱序和旧数据覆盖。
- `serverTime`：定位延迟和时间顺序问题。
- `payload`：业务字段。

### 运行流程

```text
登录成功
→ 获取可用访问凭证
→ 创建全局 WebSocket
→ 鉴权和订阅
→ 收到事件并校验结构
→ 按 eventId 去重
→ 按 version 判断新旧
→ 分发到对应 Store
→ 页面通过响应式状态更新
```

### 推送与轮询合并规则

典型竞争场景：

```text
10:00:00 发起轮询
10:00:01 WebSocket 通知卫星离线
10:00:02 轮询返回旧数据：卫星在线
```

如果直接覆盖，页面会错误恢复为在线。解决方式是让接口快照与事件都携带 `version` 或可靠的 `updatedAt`，Store 只接受更新版本更大的数据。

```ts
if (incoming.version > current.version) {
  updateState(incoming)
}
```

版本号应由后端产生，不能依赖前端接收时间。

### 断线重连与数据补偿

- 用户主动退出：永久关闭，不重连。
- Token 失效：刷新凭证或回到登录页，不无限重连。
- 浏览器离线：等待 `online` 事件后重连。
- 服务异常：指数退避，并增加约 ±20% 随机抖动，防止客户端同时重连。
- 重连成功：使用事件游标补发缺失事件；若后端不支持游标，则重新拉取状态快照、任务状态和未读通知。

推荐保存 `lastSequence`：

```text
重连成功
→ 发送 lastSequence
→ 后端补发缺失事件
→ 前端去重并合并
```

### 通知聚合

页面 Toast 和消息中心要分开处理。1 秒内的同类 Toast 可以聚合为“3 个任务执行成功”，但消息中心仍保留三条完整记录。聚合键可以由事件类型和资源类型组成。

### 前后端职责

前端负责连接状态、重连调度、事件去重、版本合并、通知聚合和 UI 反馈；后端负责事件唯一 ID、单调版本、事件游标、补发能力、鉴权与事件持久化。没有可靠版本号时，前端无法彻底解决乱序。

### 异常场景

- JSON 解析失败：记录可诊断信息，丢弃该消息，不让页面崩溃。
- 未识别事件类型：忽略并上报，不随意写入 Store。
- 重连成功但补偿失败：显示数据可能过期，并触发完整快照刷新。
- 消息突发：批量提交状态更新，限制 Toast 数量。
- 页面隐藏：保留关键连接，降低非关键图表刷新频率。

### 常见错误

- 每个页面创建一个 WebSocket。
- 只重连连接，不补齐断线期间的数据。
- 使用前端时间判断状态新旧。
- 退出登录后连接仍在重试。
- 页面订阅函数没有取消。
- Axios 轮询结果无条件覆盖推送状态。

### 验收清单

- [ ] 全系统只有一个业务 WebSocket 连接。
- [ ] 网络断开时出现全局提示，恢复后自动隐藏。
- [ ] 重连不会产生重复通知和重复订阅。
- [ ] 旧轮询响应不会覆盖新状态。
- [ ] 退出登录后连接停止且不会自动重连。
- [ ] 断线期间的事件能通过游标或快照补齐。
- [ ] 页面反复进入退出后定时器和订阅数量稳定。
- [ ] 事件触发到页面显示的延迟满足需求。

## 难点三：动态任务表单与预调度

### 需求背景

一个在轨任务可以包含多个动态子任务。每个子任务涉及类型、星座、卫星、节点、优先级、CPU、内存、共享内存、GPU、CAN、镜像、版本、启动命令、时间窗口、挂载目录和主机网络，并要求名称唯一性、资源校验、克隆回显与预调度推荐。

### 困难原因

- 字段多、联动多，容易形成大量互相触发的 `watch`。
- 动态数组使用索引作为 key 时，删除中间项会导致校验错位。
- 克隆回显可能触发不必要的联动请求。
- 用户选择的节点资源会实时变化，前端校验不能代表最终结果。
- 预调度是后端算法，前端既要展示推荐，也要允许用户覆盖。

### 推荐架构

即使页面表现为弹窗，也建议内部使用分步表单：

1. 任务基础信息。
2. 子任务列表与运行类型。
3. 部署位置和资源需求。
4. 调度推荐、校验结果与最终确认。

页面组件只负责步骤和交互；表单模型、校验规则、DTO 转换和异步选项加载分别放入清晰的函数或 composable 中。避免把全部逻辑塞入一个超长 Vue 文件。

### 核心数据结构

```ts
interface TaskForm {
  taskName: string
  subtasks: SubtaskForm[]
}

interface SubtaskForm {
  clientKey: string
  name: string
  type: 'once' | 'continuous' | 'scheduled'
  constellationId?: string
  satelliteId?: string
  nodeId?: string
  priority: number
  cpu?: number
  memoryMi?: number
  sharedMemoryMi?: number
  gpu?: number
  canDeviceIds: string[]
  imageId?: string
  imageVersion?: string
  serviceName?: string
  command?: string
  startTime?: string
  endTime?: string
  mountDirectories: MountDirectory[]
  useHostNetwork: boolean
}
```

每个子任务使用稳定的 `clientKey`，不能用数组下标作为 Vue key 或校验身份。

### 联动流程

```text
选择星座
→ 清空旧卫星和旧节点
→ 请求该星座下的卫星

选择卫星
→ 清空旧节点
→ 请求该卫星下的节点

选择节点
→ 请求当前可调度资源和 CAN 设备
→ 执行资源提示与校验
```

必须先清除下游值，否则用户更换星座后可能提交旧星座的节点 ID。

### 三层校验

第一层是前端同步校验：必填、名称格式、CPU 最小值、内存最小值、GPU 整数、优先级范围、时间范围、至少一个子任务。

第二层是前端异步校验：名称唯一性、镜像版本存在性、节点资源余量、CAN 可用性。异步请求需要防抖和取消旧请求。

第三层是后端提交校验：重新校验权限、资源、节点在线状态、名称唯一性、镜像、时间窗口。前端校验只能改善体验，不能替代后端校验。

### 资源校验

不能只比较申请量和总量，应比较当前可调度量：

```text
可调度资源 = 总资源 - 已分配资源 - 系统预留资源
```

提示应具体，例如：“节点 A 剩余 CPU 为 2 核，本子任务申请 4 核，还差 2 核”，而不是只显示“资源不足”。

### 预调度方案

前端收集任务需求并请求后端调度服务，后端返回候选结果和解释：

```ts
interface ScheduleRecommendation {
  satelliteId: string
  nodeId: string
  score: number
  reasons: string[]
  warnings: string[]
}
```

页面展示推荐位置、资源余量、推荐原因和风险。“采用推荐”必须由用户确认，不能静默覆盖用户选择。推荐失败时仍应允许用户手动配置。

### 创建与克隆流程

```text
打开创建弹窗
→ 初始化稳定表单模型
→ 加载基础选项
→ 用户添加子任务
→ 完成联动和校验
→ 请求预调度建议
→ 用户确认
→ DTO 转换
→ 携带幂等 requestId 提交
→ 显示结果并刷新列表
```

克隆任务要通过 `cloneTaskToForm()` 转换，清除原任务 ID、状态、创建时间、Pod、日志和结果文件。不要直接把详情接口对象塞进表单。

### 前后端职责

前端负责表单交互、基础校验、联动、推荐结果展示和 DTO 转换；后端负责最终资源校验、名称唯一性、调度算法、权限和幂等性。任务提交接口应支持幂等键，避免用户连续点击创建重复任务。

### 异常场景

- 选项请求失败：保留已填字段，提供局部重试。
- 资源在填写期间变化：提交时以服务端结果为准，并定位具体失败子任务。
- 预调度失败：允许手动选择，不阻塞整个表单。
- 克隆引用的镜像已删除：标记失效字段，要求重新选择。
- 表单有修改时离开：通过路由守卫和 `beforeunload` 提示。

### 常见错误

- 使用数组下标作为子任务 key。
- 依赖大量深层 `watch` 相互修改字段。
- 星座改变后没有清空卫星和节点。
- 直接提交页面模型，缺少 DTO 转换层。
- 只做前端资源校验。
- 提交按钮没有防重复和后端幂等支持。

### 验收清单

- [ ] 动态增删子任务后，字段和校验不会错位。
- [ ] 修改星座后旧卫星、节点和资源信息自动清空。
- [ ] 只有定时任务显示并校验时间窗口。
- [ ] 克隆不会携带原任务运行状态和结果信息。
- [ ] 资源变化后提交能得到准确的后端错误定位。
- [ ] 连续点击只创建一个任务。
- [ ] 表单有修改时离开会提示，未修改时不提示。
- [ ] 预调度失败后仍可手动完成配置。

## 难点四：10GB 大文件与断点续传

### 需求背景

系统要求上传、下载和删除卫星数据，支持 10GB 文件、传输进度、暂停恢复，以及浏览器关闭后重新进入仍能续传，验收成功率不低于 95%。

### 困难原因

- 单请求上传 10GB 文件失败后只能重传。
- 全量读取文件会造成巨大内存占用和页面卡顿。
- localStorage 不适合保存传输会话。
- 浏览器重启后，普通网页通常不能自动重新读取用户本地文件。
- 分片全部上传完成不等于服务端已经合并成功。

### 推荐架构

采用 tus、S3 Multipart 类似机制或明确的自定义分片协议：

```text
选择文件
→ 创建上传会话
→ 按后端下发大小切片
→ Web Worker 计算分片校验
→ 限制并发上传
→ IndexedDB 保存会话进度
→ 服务端合并
→ 完整文件校验
→ 标记完成
```

如果条件允许，优先使用成熟的 tus 协议，减少自定义协议的边界问题。

### 接口与状态

创建上传会话时发送文件名、大小、最后修改时间、目标卫星、节点和目录；后端返回 `uploadId`、`chunkSize`、已上传分片列表和过期时间。

```ts
interface UploadSessionRecord {
  uploadId: string
  fingerprint: string
  fileName: string
  fileSize: number
  lastModified: number
  chunkSize: number
  completedChunks: number[]
  targetPath: string
  status: UploadStatus
  expiresAt: number
  updatedAt: number
}

type UploadStatus =
  | 'waiting'
  | 'hashing'
  | 'uploading'
  | 'paused'
  | 'merging'
  | 'completed'
  | 'failed'
  | 'cancelled'
  | 'expired'
```

初始参数可使用 16MiB 分片、3 个并发、单片最多重试 3～5 次，但最终数值应由真实网络和服务端能力压测决定，最好由后端动态下发。

### 浏览器端实现

- 使用 `Blob.slice()` 按需读取分片，不把整个文件读入内存。
- 在 Web Worker 中计算分片 Hash，避免阻塞主线程。
- 使用 IndexedDB 保存会话和已完成分片，不保存完整 10GB 文件内容。
- 文件指纹至少包含名称、大小、最后修改时间，可补充文件头尾抽样 Hash。
- 每次恢复前先查询服务端已保存分片，以服务端结果为准。
- 暂停只停止新分片调度；取消需要调用后端接口清理临时数据。

### “关闭浏览器后恢复”的能力边界

普通网页重新打开后不能无条件读取用户本地文件。因此更现实的验收定义是：

> 用户重新选择同一个文件后，系统通过文件指纹匹配原上传会话，并从尚未完成的分片继续上传。

Chrome 和 Edge 可以使用 File System Access API 保存文件句柄，但可能再次要求用户授权，且跨浏览器兼容性有限。如果业务要求完全无人操作自动恢复，需要考虑 Electron 或专用桌面客户端。

### 下载断点续传

服务端需要支持 HTTP Range：

```http
Range: bytes=1048576-
```

并返回 `206 Partial Content`、`Accept-Ranges` 和 `Content-Range`。普通浏览器下载可交给浏览器下载器；如果前端必须控制暂停和续写，需要 File System Access API 或桌面客户端支持，不能只靠普通 Axios 下载。

### 前后端职责

前端负责分片调度、进度显示、暂停恢复、会话持久化和失败重试；后端负责上传会话、分片幂等、校验、合并、过期清理、空间检查和 HTTP Range。分片重复上传不得破坏最终文件。

### 异常场景

- 网络中断：暂停新分片，恢复后查询服务端状态再继续。
- 上传会话过期：提示重新创建会话，不能无限重试。
- 文件同名但内容不同：指纹不匹配时禁止错误续传。
- 服务端空间不足：停止调度并显示明确原因。
- 所有分片完成但合并失败：状态停留在失败，不误报完成。
- 浏览器关闭：IndexedDB 保留会话元数据，重新选择文件后恢复。

### 常见错误

- 使用一个请求上传整个 10GB 文件。
- 把大文件转为 Base64。
- 把完整传输状态塞进 localStorage。
- 只看前端已传分片，不向服务端核对。
- 把“分片上传完”当成“文件可用”。
- 承诺普通浏览器可以无授权自动读取本地文件。

### 验收清单

- [ ] 10GB 文件不会整体进入内存，页面仍可正常操作。
- [ ] 单个分片失败可重试，重复分片不会损坏文件。
- [ ] 网络中断、刷新页面后可以继续传输。
- [ ] 重新选择同一文件后能恢复原会话。
- [ ] 同名不同内容的文件不会错误续传。
- [ ] 服务端合并和完整校验通过后才显示完成。
- [ ] 取消和过期会话能清理临时分片。
- [ ] 下载服务支持标准 Range 请求或明确采用浏览器原生恢复。

## 难点五：浏览器 SSH 终端

### 需求背景

系统需要通过浏览器登录后端服务器，支持 ANSI/VT100、真彩色、GPU 加速、多会话标签、快捷键、复制粘贴、窗口适配和文件传输。

### 困难原因

- 浏览器不能直接建立原生 SSH 连接。
- 终端不是普通文本框，需要 PTY、光标和转义序列支持。
- 大量输出可能阻塞主线程。
- 多标签需要独立连接和终端实例。
- SSH 密码、私钥、目标主机权限和审计都有安全风险。

### 推荐架构

```text
xterm.js
   ↓ WebSocket
业务系统 SSH 网关
   ↓ SSH + PTY
目标服务器
```

浏览器只连接受控的业务网关。后端负责 SSH 认证、PTY、主机白名单、权限校验、输入输出转发、会话超时和资源释放。

### 消息协议

控制消息和数据消息可以分开：

```text
INPUT      键盘输入
OUTPUT     终端输出
RESIZE     行列变化
HEARTBEAT  心跳
EXIT       会话结束
ERROR      会话错误
```

大量输出优先使用二进制 WebSocket 帧，避免反复 JSON 序列化；控制类消息可使用 JSON。

### xterm.js 组成

- `Terminal`：终端主体。
- `FitAddon`：适配容器尺寸。
- `SearchAddon`：搜索终端内容。
- `WebLinksAddon`：识别链接。
- `WebglAddon`：可选 GPU 加速，失败时回退普通渲染。

### 多会话管理

```ts
interface TerminalSessionMeta {
  sessionId: string
  connectionId: string
  title: string
  status: 'connecting' | 'connected' | 'disconnected' | 'closed'
}
```

Pinia 只保存会话元数据、激活标签和标签顺序。真实的 Terminal、WebSocket 和插件实例保存在独立会话管理服务的 `Map<sessionId, TerminalRuntime>` 中，不做持久化。

### 运行流程

```text
用户选择服务器
→ 前端请求短期会话票据
→ 后端校验用户与主机权限
→ 前端使用票据连接 SSH 网关
→ 后端创建 SSH 和 PTY
→ xterm.js 双向收发
→ ResizeObserver 触发终端适配
→ 关闭标签或超时
→ 前后端共同释放会话
```

### 尺寸与输出性能

容器变化时调用 FitAddon，并将新的 `cols`、`rows` 发送给后端调整 PTY，resize 消息需要防抖。大量输出先进入缓冲区，再按批次调用 `terminal.write()`；后端也要限制单会话流量和历史输出量。

### 安全方案

- SSH 密码不能出现在 URL 或 localStorage。
- 浏览器不直接保存服务器私钥。
- 用户不能任意输入未授权的目标主机。
- 建立连接前向业务后端申请一次性或短期 ticket。
- 后端维护主机白名单、RBAC、会话数限制和空闲超时。
- 退出登录时关闭所有终端会话。
- 审计记录会话和高层操作，但不能简单记录所有键盘输入，以免保存密码和 Token。

### 会话恢复

SSH 终端不能像普通消息连接一样随意重连。如果后端断线后立即销毁 PTY，前端只能创建新会话。可由后端提供 30～60 秒宽限期和短期恢复令牌，让短暂网络中断后恢复原 PTY；超过宽限期则明确提示会话已结束。

### 前后端职责

前端负责 xterm.js、标签页、输入输出、尺寸同步和交互反馈；后端负责 SSH、PTY、权限、凭证、安全审计、会话恢复与资源释放。前端不能独立完成安全的浏览器 SSH。

### 异常场景

- WebGL 加载失败：回退普通渲染。
- 网关断开：显示断开状态，尝试恢复或创建新会话。
- 输出过快：启用缓冲和背压，避免页面冻结。
- 页面关闭：通知后端并由服务端超时兜底释放。
- 权限变化：后端拒绝继续建立连接，不能只靠前端隐藏按钮。

### 常见错误

- 浏览器直接连接目标服务器 SSH 端口。
- 把终端实例放入可持久化 Pinia。
- resize 时只调整画面，不同步 PTY 行列。
- 每段输出都立即写入终端，没有缓冲。
- 把 SSH 密码长期保存在浏览器。
- 前端重连成功就假定原 SSH 会话仍存在。

### 验收清单

- [ ] `top`、`vim` 等交互程序和 ANSI 颜色显示正常。
- [ ] Ctrl+C、方向键、复制粘贴等行为符合预期。
- [ ] 窗口变化后前端尺寸和后端 PTY 同步。
- [ ] 多个标签页互不影响，单个会话断开不影响其他会话。
- [ ] 大量输出时页面仍可操作。
- [ ] 页面关闭后服务端会话最终释放。
- [ ] 未授权用户无法连接目标服务器。
- [ ] SSH 密码和私钥不会进入浏览器持久化存储。

## 难点六：路由与跨页面状态恢复

### 需求背景

需求要求支持浏览器前进后退、刷新、直接访问 URL、详情弹窗恢复、筛选状态恢复和未保存离开确认。拓扑、卫星、任务、文件之间还有大量跨模块跳转与自动筛选。

### 困难原因

- 状态只放在组件 `ref` 中，刷新后会丢失。
- 所有状态都放 Pinia 或 localStorage，会污染账号和页面，URL 也不能分享。
- 详情弹窗依赖基础列表和权限，不能在刷新时无条件立即打开。
- 搜索框每次输入都 `router.push()`，会产生大量无意义历史记录。

### 状态分类

| 状态 | 推荐位置 |
|---|---|
| 当前星座、卫星、任务 ID | 路由参数或 URL Query |
| 页码、排序、筛选、详情弹窗 ID | URL Query |
| 用户主题、侧栏折叠 | localStorage |
| 当前登录信息和全局业务状态 | Pinia |
| 未完成表单草稿 | sessionStorage 或带版本的持久化 Store |
| 大文件上传会话 | IndexedDB |
| G6、xterm、WebSocket 实例 | 内存服务，不持久化 |
| 大型接口数据 | 内存缓存并设置 TTL |

### 推荐 URL

```text
/constellation/satellites
  ?constellationId=c001
  &status=online
  &keyword=sat
  &page=2
  &pageSize=20
  &sort=cpuUsage
  &order=desc
  &detailId=s001
```

这能支持刷新恢复、分享 URL、前进后退、跨模块自动筛选和详情恢复。

### Push 与 Replace

- 明确进入新页面、打开重要详情时使用 `router.push()`。
- 搜索、分页、排序和普通筛选使用防抖后的 `router.replace()`。

否则用户按一次后退，可能需要经过十几次搜索输入历史。

### 恢复流程

```text
解析并校验路由参数
→ 恢复登录状态
→ 加载用户权限
→ 加载页面基础数据
→ 应用筛选、分页和排序
→ 校验详情 ID 是否存在
→ 打开详情弹窗
```

目标不存在时清除无效 Query 并提示；无权限时不渲染敏感详情，并引导至可访问页面。

### 未保存内容保护

- Vue Router 内部跳转使用 `onBeforeRouteLeave` 或统一路由守卫。
- 刷新、关闭标签页使用 `beforeunload`。
- 仅在表单真正变脏时注册拦截，页面卸载时移除监听。

草稿应携带用户 ID、创建时间、过期时间和结构版本。恢复时重新校验关联卫星、节点和镜像是否仍然存在。不要持久化组件实例、文件对象和请求对象。

### 跨模块导航

统一封装行为级导航函数：

```ts
openSatelliteDetail(satelliteId)
openSatelliteTasks(satelliteId)
openSatelliteData(satelliteId)
openConstellationSatellites(constellationId)
```

业务组件不自行拼接 URL，避免路由变化后大量修改。

### 前后端职责

前端负责 URL 状态、恢复顺序、权限前置判断、草稿和导航契约；后端负责稳定 ID、资源存在性、权限真实性和可恢复的详情接口。权限最终判断必须在后端完成。

### 异常场景

- Query 类型错误：使用默认值并替换为合法 URL。
- 详情对象已删除：关闭弹窗并保留当前列表。
- 草稿版本过旧：提示无法直接恢复，可提供查看或清除。
- 用户切换账号：清除上一个账号的页面缓存和草稿。
- 快速切换筛选：取消旧请求，避免旧数据回写。

### 常见错误

- 页面筛选全部只存在组件内存。
- 所有数据无过期时间地放入 localStorage。
- 搜索每输入一个字符都 `router.push()`。
- 基础数据未加载就打开详情弹窗。
- 只在路由跳转时提示，刷新页面时没有提示。
- 前端隐藏菜单后就认为权限安全。

### 验收清单

- [ ] 刷新后筛选、排序、分页和详情状态能恢复。
- [ ] 复制 URL 到新标签页能打开相同业务位置。
- [ ] 浏览器前进后退符合用户预期。
- [ ] 无效参数不会导致页面报错。
- [ ] 目标被删除或无权限时有安全、友好的处理。
- [ ] 表单修改后离开会提示，未修改时不提示。
- [ ] 切换账号后不会读取前一个账号的草稿。
- [ ] 快速筛选不会出现旧请求覆盖新结果。

## 六个难点共同需要的基础设施

### TypeScript 与 OpenAPI

优先从 OpenAPI/Swagger 生成接口类型，统一分页、错误、状态枚举、时间、WebSocket 事件和文件任务状态。生成类型外再增加业务适配层，把接口 DTO 转成页面模型，避免页面直接依赖不稳定的后端字段。

### 统一状态字典

```ts
const taskStatusMap = {
  waiting: { label: '等待中', color: 'warning' },
  running: { label: '运行中', color: 'primary' },
  completed: { label: '已完成', color: 'success' },
  failed: { label: '已失败', color: 'danger' },
} as const
```

列表、详情、拓扑、通知和图表复用同一份映射，避免同一个状态在不同页面颜色不同。

### 统一错误处理

- Axios 层处理 401、403、404、500、超时和请求取消。
- Store 处理业务错误码和状态回滚。
- 页面处理局部加载、空数据、失败占位和重试。
- 全局错误边界防止单个组件异常导致整页白屏。

Axios 拦截器不要对所有失败都无条件弹 Toast，否则多个并行请求失败时会刷屏。

### 请求与生命周期管理

- 搜索、星座切换和标签页切换使用 AbortController 取消旧请求。
- 所有轮询在组件卸载时清除。
- 全局 WebSocket 与页面订阅分开管理。
- ResizeObserver、G6 事件和浏览器事件都要有对应清理逻辑。

### 权限控制

- 路由 meta 控制页面入口。
- 业务权限控制按钮和操作。
- 后端对每个敏感接口再次鉴权。
- SSH 主机访问、任务创建、文件删除等不能只靠前端隐藏。

### 测试分层

单元测试：版本比较、消息去重、资源校验、DTO 转换、路由解析、文件切片。

组件测试：动态子任务、筛选同步 URL、详情恢复、离线提示、上传暂停恢复。

集成测试：WebSocket 断线重连、任务创建、大文件续传、多 SSH 会话、跨模块跳转。

性能测试：100 颗卫星、280 个节点、500 个图表点、1000 条消息、高频事件、终端大量输出和 10GB 文件分片。

### 推荐顺序

```text
Vue Router 状态恢复
→ Pinia 与 WebSocket
```

## 面试怎么讲

可以这样概括：

> 这个项目的难点不是常规表格，而是卫星拓扑的高频增量更新、推送与轮询的一致性、复杂任务表单、大文件断点续传、浏览器 SSH 和页面状态恢复。我会先把结构数据和实时状态分离，用单例 WebSocket 与版本号解决乱序；拓扑图只做节点级更新；任务表单采用稳定 clientKey、分层校验和 DTO 转换；文件传输采用分片协议和 IndexedDB 会话；SSH 通过后端网关连接 xterm.js；可分享状态进入 URL，运行实例留在内存。这样既能保证性能，也能让异常恢复和测试有明确边界。

如果被追问“你个人主要负责什么”，不要把后端算法说成自己的实现，应明确区分：前端负责交互、状态管理、协议消费和异常反馈；后端负责调度、文件合并、SSH 和最终权限校验。

## 今日复刻任务

用 Vue 3 + TypeScript 完成一个缩小版练习，不需要真实后端：

1. 创建一个包含 20 个模拟卫星节点的 G6 拓扑图。
2. 使用一个模拟 WebSocket，每秒随机修改一颗卫星的三类在线状态。
3. Store 按 `version` 忽略旧消息，拓扑只更新目标节点。
4. 搜索卫星后聚焦并打开信息卡片，将 `satelliteId` 写入 URL Query。
5. 刷新页面后根据 Query 恢复选中卫星和卡片。
6. 增加断线提示和指数退避重连模拟。
7. 编写至少三个测试：旧版本消息被忽略、搜索恢复成功、组件卸载后订阅被清理。

完成后再扩展一个简化任务表单：支持动态添加子任务、星座/卫星/节点三级联动，以及 CPU 资源不足提示。
