# Vue Components Communication

把组件通信当成“职责设计 + 状态流向”问题，而不是先写 API 的问题。

先完成四个判断：

1. 判断组件属于页面组件/容器组件、业务区块组件，还是展示组件。
2. 画清一条链路：状态被谁持有 -> 方法被谁触发 -> 数据传给谁 -> 改完怎么回流。
3. 判断当前传递的是“值”、“动作”、“控制权”，还是“共享状态”。
4. 如果用户给的是完整项目链路，不只看组件，还要继续追到 `App`、`store`、`services`、`Storage` 和外部 API。

如果用户要分析现有代码，先查看：

- 组件树
- `props`、`emit`、`v-model`、`slot`、`defineExpose`
- `provide/inject`
- `store`
- 页面生命周期
- `App` 级恢复逻辑
- `services` 中的运行时桥接和副作用
- `uni.setStorageSync`、`uni.getStorageSync`、`uni.removeStorageSync` 的读写点
- `schema`、`jsonSchema`、`formSchema`、`columns`、`fields`、`rules` 等 JSON Schema / 配置式 UI 定义

如果用户要设计新组件，不要先发明接口；先分层、再定归属、最后才落通信 API。

如果用户明确要提示词示例，再读取 [references/prompt-examples.md](references/prompt-examples.md)。

如果用户明确要生成适合 canvas 的 Markdown 结构，再读取 [references/canvas-output-template.md](references/canvas-output-template.md)。

## 使用顺序

1. 标出每个组件的类型。
2. 为每一份状态找出唯一的真实持有者。
3. 为每一个交互找出触发者、执行者、影响范围和回流点。
4. 补查这条链路有没有继续流入 `store`、`services`、`Storage` 或 `App`。
5. 如果页面由 JSON Schema 或配置数组驱动，先解释 Schema 约束了哪些数据结构和 UI 行为。
6. 根据传递内容选择通信方式。
7. 用“更好的封装性、更简洁的代码、更明确的语义”解释方案。
8. 只有在边界清楚后，才给出 `props`、`emit`、`v-model`、`slot`、`provide/inject` 或 store 设计。

## 三类组件职责

### 页面组件 / 容器组件

- 持有页面级、提交级、跨区块协同级的真实业务状态。
- 负责接口请求、数据整合、提交、副作用、路由参数、权限、缓存恢复、跨区块协调。
- 把稳定的数据和配置向下传，把语义明确的事件向上接。
- 优先承接会影响提交结果、页面布局、兄弟组件联动、权限判断、路由状态、Storage 恢复的逻辑。
- 不要把页面级 source of truth 偷偷下放给子组件长期持有。

### 业务区块组件

- 负责某个业务区块的展示、局部交互流程和临时状态。
- 可以持有“仅对当前区块有意义”的短生命周期状态。
- 接收父组件传入的数据，完成区块内组织、展示、局部交互，再通过多个语义化 `emit` 把意图抛出。
- 适合承接“局部复杂，但不该升级为页面全局状态”的逻辑。
- 不要把页面级 source of truth 放在业务区块组件里长期维护。

### 展示组件

- 保持纯 UI 优先，只持有极轻的本地状态。
- 本地状态只应服务于展示体验，例如 hover、focus、临时展开、输入草稿、动画开关。
- 主要职责是接收值、渲染值、抛出交互。
- 优先保持无业务知识、弱耦合、可复用。
- 不要负责请求数据、拼装提交参数、修改共享业务状态。

## 通信方式决策

先问一句：我现在传的是“值”、还是“动作”、还是“控制权”、还是“共享状态”。

### 传“值”

- 优先使用 `props`。
- 如果父组件持有值、子组件负责编辑值，优先使用 `v-model` 或 `modelValue + update:modelValue`。
- 如果子组件只需要展示，不要把它设计成可写。

### 传“动作”

- 优先使用 `emit`。
- 事件名用业务语义命名，例如 `submit-vehicle`、`close-vehicle`、`open-detail`。
- 让“谁触发”和“谁决策”分离：子组件负责表达意图，父组件负责做业务决策。

### 传“控制权”

- 父组件要控制子组件结构或渲染片段时，优先使用 `slot`。
- 父组件要命令式调用子组件能力时，谨慎使用 `ref + defineExpose`。
- `defineExpose` 只保留窄而明确的控制面，不承载核心业务状态同步。

### 传“共享状态”

- 同一棵局部子树稳定共享配置、上下文、服务对象时，优先考虑 `provide/inject`。
- 跨页面、跨远距离兄弟组件、跨模块共用一份真实状态时，再考虑 `store`。
- 不要因为两三层 `props` 就立刻上 store。
- 不要把 `provide/inject` 当作隐藏式全局状态通道。

## 项目级链路补查

当用户给的不是单个组件，而是一整个页面目录、模块目录或完整链路时，不要停在父子组件。

继续补查这 4 类节点：

### `App`

- 是否存在启动恢复、前台恢复、登录后恢复、全局副作用恢复。

### `store`

- 是否存在共享状态、登录态同步、后端状态回填、本地缓存同步。

### `services`

- 是否存在 runtime 桥接层、底层引擎层、权限层、轮询层、上报层。
- 要分清“业务状态”和“运行时状态”是不是被拆成了两层甚至三层。

### `Storage`

- 必查 `setStorageSync`、`getStorageSync`、`removeStorageSync`。
- 记录每个 key：
  - 谁写
  - 谁读
  - 什么时候更新
  - 什么时候删除
  - 它代表业务状态、运行时状态，还是失败补偿状态
- 如果一个模块有多个 Storage key，不要把它们混成同一层 source of truth。

### `JSON Schema / 配置式 UI`

当前端页面、表单、表格、筛选器、动态弹窗、低代码区域或 Agent 工具参数由配置驱动时，要把 JSON Schema 当成“数据结构规则 + UI 渲染契约”来解释。

先区分两件事：

- JSON 是实际数据本身，例如表单值、接口入参、后端返回值、缓存内容。
- JSON Schema 是描述这份数据是否合法、字段是否完整、类型是否正确、结构是否稳定的规则说明。

分析 Schema 时按这个顺序看：

1. 看整体 `type`：它约束的是对象、数组、字符串、数字、布尔值，还是可以为空。
2. 看 `properties` / 字段配置：每个字段叫什么、类型是什么、在 UI 上渲染成什么控件。
3. 看 `required`：哪些字段是业务必填，哪些只是展示或可选配置。
4. 看基础约束：`minimum`、`maximum`、`minLength`、`maxLength`、`pattern`、`enum`。
5. 看数组结构：`items` 说明数组里每一项的结构，常见于列表、表格列、动态表单项。
6. 看嵌套对象：继续追内部 `properties` 和 `required`，不要只停在第一层字段。
7. 看业务扩展字段：例如 `label`、`component`、`placeholder`、`visible`、`disabled`、`rules`、`options`、`api`、`props`、`events`，它们通常不是标准 JSON Schema，而是项目自己的 UI 协议。

解释配置式代码时，要说明这份 Schema 在链路中的位置：

- 如果它决定页面结构或控件类型，它更像“渲染配置”，通常由页面组件/容器组件持有或从接口加载。
- 如果它决定校验规则，它连接的是“输入值 -> 校验 -> 错误提示 -> 提交拦截”的链路。
- 如果它决定选项、联动、显隐、禁用，它连接的是“状态变化 -> 配置条件判断 -> UI 重新渲染”的链路。
- 如果它决定接口参数或工具参数，它连接的是“用户输入 -> 结构化参数 -> Schema 校验 -> API / tool call”的链路。

前端讲解时优先使用这套句式：

- “这份 JSON 是数据；这份 Schema 是规则。”
- “`type` 决定值的基本形状，`properties` 决定字段清单，`required` 决定哪些字段必须出现。”
- “`enum` 限制只能选固定值，`pattern` 限制字符串格式，`items` 说明数组每一项长什么样。”
- “项目里的 `component`、`label`、`rules`、`options` 是在标准 Schema 外面扩展出来的 UI 配置。”

不要把 Schema 解释成普通常量数组。它通常承担三类职责：

- 数据约束：字段、类型、必填、范围、格式、枚举、嵌套结构。
- UI 生成：根据字段配置渲染输入框、选择器、表格列、筛选项、弹窗内容。
- 流程守门：在提交、保存、导入、接口调用或 Agent tool call 前统一校验结构。

## 状态归属判断

- 会影响提交参数、接口调用、兄弟联动、页面摘要、权限、路由、缓存恢复的状态，优先由页面组件/容器组件持有。
- 只影响某个业务区块内部交互、卸载后可丢失、父组件不必实时感知的状态，优先由业务区块组件持有。
- 只服务于 UI 细节、交互反馈、纯展示体验的状态，优先由展示组件持有。
- 如果多个组件都要改一份值，先找真实拥有者，再决定是 `v-model`、`emit` 回流，还是升级为共享状态。
- 如果状态还会跨页面恢复、跨登录恢复、跨服务恢复，继续往 `store`、`services`、`Storage` 追，不要只停留在组件层。

## 回流设计

- 先定义真实状态在哪一层结束。
- 再定义变更从哪一层发起。
- 让改动沿着显式链路回到真实持有者。
- 对外说明每一条关键链路：谁发起、谁处理、谁更新、谁重渲染。
- 如果链路经过 `Storage`，明确写出“写入 -> 读取 -> 恢复”的顺序。
- 如果回流链路说不清，通常说明组件边界或状态归属还没分好。

## 推荐输出格式

先给职责判断，再给通信方案，最后再给代码建议。

输出时尽量包含这些内容：

1. 组件分层表：组件名、组件类型、持有状态、接收数据、发出动作。
2. 项目级节点表：`App`、`store`、`services`、`Storage`、API 各自负责什么。
3. 关键链路表：状态被谁持有、方法被谁触发、数据传给谁、改完怎么回流。
4. Storage 总表：key、写入者、读取者、触发时机、业务语义。
5. Schema / 配置表：配置名、约束对象、字段定义、必填项、校验规则、UI 扩展字段、触发链路。
6. 通信方式选择：为什么是 `props` / `emit` / `v-model` / `slot` / `defineExpose` / `provide/inject` / `store`。
7. 优势说明：分别从封装性、代码简洁度、语义明确性解释。
8. 如果用户要生成 canvas，再补：
   - 节点清单
   - 连线清单
   - 推荐分组方式

## 约束与反模式

- 不要一上来先设计 API。
- 不要只看父子组件就结束，忽略 `App/store/services/Storage`。
- 不要无脑把所有状态都上提。
- 不要为了少传两层 `props` 就引入 store。
- 不要让展示组件知道接口、权限、缓存、提交编排。
- 不要让业务区块组件静默改写父组件拥有的数据。
- 不要把 `provide/inject` 用成难追踪的业务状态黑盒。
- 不要把多个 Storage key 混成一份状态。
- 不要把“业务状态”“runtime 状态”“失败补偿状态”混为一谈。
- 不要把 JSON Schema 只说成“一个配置对象”，要讲清它约束了什么数据、驱动了什么 UI、在哪个流程点被校验。
- 不要把项目自定义的 `component`、`label`、`rules`、`options` 误认为都是标准 JSON Schema 字段。

## 代码建议边界

- 用户只要分析时，只输出职责、链路、通信判断和必要的重构建议。
- 用户要代码时，优先给最小骨架和关键接口，不要提前铺满实现细节。
- 用户要重构时，优先保留现有业务语义，只调整职责边界和通信方式。
