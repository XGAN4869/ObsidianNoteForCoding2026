# Obsidian Note Analyse

整理 Obsidian Markdown 笔记的结构，重点是“保留原文、补充层级、拆分解释”。将用户已有内容视为需要保护的源材料；新增标题和说明必须帮助阅读，但不能替换、润色或删除原文。

## 工作流程

### 1. 读取并建立原文基线

- 读取用户指定的全部 `.md` 文件，并使用正确的 UTF-8 编码。
- 先识别现有标题、段落、代码围栏、Obsidian 图片/内部链接、表格、列表和 callout。
- 保存原文基线：编辑前后用 `git diff` 或等价的文本差异检查，确认原有正文、代码行、注释、TODO、FIXME、链接和图片引用没有丢失。
- 不要因为编码显示异常就改写内容；先确认实际编码。

### 2. 设计 Markdown 层级

优先使用以下层级：

```text
# 文件主题
## 开篇速记卡 / 背景 / 总览
## 一、核心章节
### 1. 章节内的知识点
### 2. 另一个知识点
## 二、下一个核心章节
```

- 每个文件通常只保留一个一级标题；如果原文没有一级标题，可以补充一个能概括文件主题的标题。
- 用二级标题划分主要知识点、功能模块或执行阶段。
- 用三级标题拆分同一知识点中的步骤、语法、分支或代码片段。
- 不主动使用四级及更深标题；需要更细时使用加粗小标签、列表或说明段落。
- 原有标题文字应保留。若需要调整标题级别，在原文字前增加章节编号或上层标题即可，不要任意改写原标题。
- 可补充“开篇速记卡”“分类索引”“一句话总结”“执行流程”等导航内容，但必须与原文清楚分隔。

### 3. 拆分和解释代码

遇到长代码块时，按代码职责拆分，例如：

1. 准备数据或类型声明。
2. 定义接口、函数或类。
3. 实现核心逻辑。
4. 处理条件分支、递归或异常。
5. 调用函数、创建实例或启动流程。

拆分规则：

- 每个代码片段都使用完整且成对的 Markdown 围栏，例如 ` ```ts `、` ```js ` 或 ` ```text `。
- 代码行、缩进、注释、字符串、标点和 TODO 必须原样保留；不要为了“好看”自动格式化代码。
- 只在代码块之间补充解释，说明输入、输出、类型收窄、执行顺序和关键 API。
- 如果同一行必须与相邻代码一起才能表达语义，则保持在同一个代码块中。
- 拆分后不得重复执行会产生副作用的代码；说明性片段可以标明它们来自同一段原始代码。
- 不要把代码改成另一种实现，也不要偷偷修复原代码中的潜在问题；如确有必要，只用说明指出风险。

### 4. 添加适量学习辅助内容

可以根据原文补充以下内容：

- 速记卡、术语对比表、类型符号速查表。
- 代码块前的目的说明和代码块后的逐段解释。
- 函数参数、返回值、分支条件、递归调用或类继承关系的流程说明。
- “注意”“提示”“警告”等 Obsidian callout，但不要把补充内容伪装成用户原文。
- 结尾的一句话总结，帮助复习本篇主题。

补充内容应简洁、准确，并以原文实际出现的概念为依据。不要凭空添加业务逻辑、API 行为或未出现的结论。

## 内容保护规则

### 必须保留

- 原有普通文本、中文标点和个人表达。
- 所有代码、代码注释、TODO、FIXME、链接和图片嵌入。
- Obsidian 内部链接（如 `[[页面名]]`）和图片语法（如 `![[图片.png]]`）。
- 原有表格、列表、引用和 callout 的信息内容。

### 可以新增

- 一级、二级、三级标题及章节编号。
- 解释性段落、列表、对比表、流程图文本和总结。
- 为原本没有语言标注的代码围栏补充语言标识，但不要修改代码本身。

### 不要做

- 不要删除、改写、翻译、润色或合并原文句子。
- 不要修改代码变量名、逻辑、格式、注释或执行结果。
- 不要把用户的 TODO/FIXME 当作授权直接修复。
- 不要把整篇笔记重写成脱离原文的教程。
- 不要为多个文件创建不必要的额外文档或资源文件。

## 完成前检查

编辑完成后逐项检查：

1. 每个文件是否有清晰的一级主题标题。
2. 主要章节是否使用二级标题，章节内拆分是否使用三级标题。
3. 是否出现四级或更深标题；如有，改为加粗标签或列表。
4. 所有代码围栏是否成对闭合，语言标注是否合理。
5. 原文代码、注释、TODO、链接和图片是否仍然存在。
6. 新增解释是否与原代码一致，是否明确区分于原文。
7. 是否存在意外的空白、乱码、重复代码或 Markdown 语法错误。
8. 查看最终差异，确认修改范围只包含用户指定的笔记和必要的结构补充。

## 输出方式

完成后简要说明：

- 哪些文件已整理。
- 使用了怎样的标题层级和代码拆分方式。
- 是否保留了原文内容。
- 做过哪些结构和 Markdown 完整性检查。
