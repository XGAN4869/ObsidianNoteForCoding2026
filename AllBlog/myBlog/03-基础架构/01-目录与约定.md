# 01 · 目录与约定

> 这一节是"软性"的，但**比写代码更重要**。
> 目录理顺了，**后面 100 倍快**。

---

## 一、为什么"目录约定"很重要

新手最容易做的事：

```
随手写代码 → 写完能用 → 不管
再写代码 → 又随手放 → 还是能用
3 个月后 → 项目变成屎山 → 自己都看不懂
```

**目录约定 = 提前想好"将来怎么找到东西"**。

## 二、目录回顾

我们在 `01-方案/04-项目目录结构.md` 里设计好了结构，再列一遍：

```
src/
├── app/              路由（URL = 文件夹结构）
├── components/       你的组件库
│   ├── pixel/        像素原子组件
│   ├── layout/       布局组件（导航、底部、主题切换）
│   ├── blog/         博客专用
│   ├── capsule/      时光胶囊专用
│   ├── todo/         代办清单专用
│   └── home/         首页专用
├── lib/              工具函数（读文件、格式化日期）
├── types/            TypeScript 类型定义
└── hooks/            自定义 React Hooks
```

## 三、什么算"组件"，什么不算

### 组件长这样

```tsx
// src/components/pixel/PixelButton.tsx
export function PixelButton({ children, ...props }: PixelButtonProps) {
  return (
    <button className="border-2 border-fg px-4 py-2" {...props}>
      {children}
    </button>
  );
}
```

**判断标准**：
- [ ] 复用 ≥ 2 次？
- [ ] 有清晰的 props 输入？
- [ ] 自己负责一段 UI？
- [ ] **不是直接 copy 自某页面**？

3 个 ✅ = 抽组件。

### 不算组件（直接写在 page.tsx 里就行）

- 页面专属的 hero 区
- 一次性的图标
- 临时调试用的 div

## 四、组件命名规范

| 类型 | 命名 | 例子 |
| --- | --- | --- |
| **像素原子组件** | `Pixel*` | `PixelButton`、`PixelCard` |
| **布局组件** | 描述位置 | `Navbar`、`Footer`、`ThemeToggle` |
| **业务组件** | 描述业务 | `PostCard`、`TodoItem` |
| **页面** | `page`（固定） | `app/posts/page.tsx` |
| **布局** | `layout`（固定） | `app/layout.tsx` |
| **Hook** | `use*` | `useTheme`、`useLocalStorage` |
| **工具函数** | 动词 / 名词 | `formatDate`、`getPosts` |
| **类型** | 名词 | `Post`、`Todo` |
| **常量** | `UPPER_SNAKE_CASE` | `MAX_TITLE_LENGTH = 100` |

**为什么像素组件叫 `Pixel*`？**
- 一眼看出"这是像素风的"
- 跟 lucide / shadcn 的 `Button` 区分
- 别人写 `import { Button } from 'lucide-react'` 不会冲突

## 五、文件命名规范

| 类型 | 规范 | 例子 |
| --- | --- | --- |
| **React 组件** | 大驼峰 | `PixelButton.tsx` |
| **Hooks** | camelCase，`use` 开头 | `useTheme.ts` |
| **工具函数** | camelCase 或 kebab-case | `formatDate.ts` 或 `format-date.ts` |
| **类型定义** | 大驼峰 | `Post.ts` |
| **配置文件** | 小写 + 点开头 | `.eslintrc.json` |
| **CSS** | kebab-case | `globals.css` |
| **MDX 文章** | kebab-case + `.mdx` | `hello-world.mdx` |

> 新手常问：组件文件名是 `PixelButton.tsx` 还是 `pixel-button.tsx`？
>
> **业界两派都有**。React 官方文档用 `PascalCase`，我们跟官方走。

## 六、注释规范

### 文件头注释

```tsx
/**
 * PixelButton - 像素风按钮
 *
 * 用法：
 *   <PixelButton onClick={...}>点我</PixelButton>
 *
 * 设计规则：
 *   - 硬边，无圆角
 *   - hover 阴影缩小，active 偏移
 */
```

### 函数注释

复杂函数**必须写注释**，尤其是**为什么这么写**，不是"做什么"：

```tsx
// ✅ 好的注释：解释"为什么"
/**
 * 用 localStorage 持久化主题。
 * 不用 cookie 因为：cookie 会被发到服务器，没必要。
 */
function saveTheme(theme: Theme) {
  localStorage.setItem('theme', theme);
}

// ❌ 坏的注释：复述"做什么"
// 把主题存到 localStorage
function saveTheme(theme: Theme) {
  localStorage.setItem('theme', theme);
}
```

### 段落分隔

```tsx
// ============ 数据加载 ============

async function loadPosts() {
  // ...
}

// ============ 渲染 ============

export default function PostList() {
  // ...
}
```

**超过 100 行的文件**，加这种分隔线。

### TODO 注释

```tsx
// TODO: 加上标签过滤
// FIXME: 这里在暗色模式下文字看不清
// HACK: 临时方案，等 Next.js 15.1 修了再改
// NOTE: 重要，不要删
```

**配合 Todo Tree 插件**会高亮。

## 七、Commit 规范（Conventional Commits）

每次提交**必须带前缀**：

| 前缀 | 含义 | 例子 |
| --- | --- | --- |
| `feat:` | 新功能 | `feat: 加上时光胶囊模块` |
| `fix:` | 修 bug | `fix: 暗色模式下文字看不清` |
| `style:` | 改样式（不影响功能） | `style: 像素按钮加 hover 效果` |
| `refactor:` | 重构代码（不改功能） | `refactor: 把 CapsuleCard 拆成小组件` |
| `docs:` | 改文档 | `docs: 更新 README 安装步骤` |
| `test:` | 加测试 | `test: 给 formatDate 加单元测试` |
| `chore:` | 杂项 | `chore: 升级 Next.js 到 15.1` |
| `perf:` | 性能优化 | `perf: 给图片加 lazy load` |

**例子**：

```bash
git commit -m "feat: 时光胶囊列表页"
git commit -m "fix: 暗色主题切换闪屏问题"
git commit -m "style: 按钮 active 时偏移 2px"
```

## 八、Import 顺序

```tsx
// 1. React / Next.js
import { useState } from 'react';
import type { Metadata } from 'next';

// 2. 第三方库
import { format } from 'date-fns';

// 3. @/ 别名（项目内部）
import { PixelButton } from '@/components/pixel';
import { formatDate } from '@/lib/date';

// 4. 相对路径（同目录或子目录）
import { PostMeta } from './PostMeta';

// 5. 样式（必须最后）
import './styles.css';
```

**为什么这么排？**
- 依赖关系清晰：先看"用了哪些外部的"
- 不容易循环引用

## 九、Props 设计原则

### 1. 只接"必要的" props

```tsx
// ✅ 好：只接一个变体
function PixelButton({ variant = 'default', children }: Props) { }

// ❌ 差：接一堆 CSS 类，让用户传 Tailwind class
function PixelButton({ className, bgColor, borderColor, children }: Props) { }
```

**为什么？** 组件内部管样式，外部不操心。

### 2. 命名要"语义化"

```tsx
// ✅ 好
<PixelButton onClick={handleClick}>保存</PixelButton>
<PixelButton disabled>不可点</PixelButton>

// ❌ 差
<PixelButton color="red" size="big" bg="white">保存</PixelButton>
```

### 3. 必填项要"破坏性地"提示

```tsx
type Props = {
  /** 用户 ID（必填） */
  userId: string;
  /** 头像 URL（可选，没传用默认） */
  avatarUrl?: string;
};
```

TypeScript 会在你忘传 `userId` 时报错。

### 4. boolean props 加 `is` / `has`

```tsx
type Props = {
  isLoading?: boolean;
  hasError?: boolean;
  isDisabled?: boolean;
};
```

## 十、文件大小铁律

| 文件类型 | 上限 | 拆法 |
| --- | --- | --- |
| **页面文件** (`page.tsx`) | 200 行 | 拆组件 |
| **组件文件** | 150 行 | 拆小组件 / 抽 hook |
| **工具函数** | 100 行 / 函数 | 拆函数 |
| **配置** | 50 行 | 一般不用拆 |

**超过就拆**。这是**死规定**，不要讲条件。

## 十一、怎么避免"屎山"

| 习惯 | 说明 |
| --- | --- |
| **先写注释再写代码** | 哪怕一行也行 |
| **每个 commit 只做一件事** | 不要"fix + feat + style" 一起提交 |
| **删掉没用的代码** | 不要 `// 旧的实现` 留着 |
| **用 git stash 暂存** | 不要让工作区永远有未提交代码 |
| **每完成一个模块就 commit** | 一周下来 10+ 个 commit |
| **重要决策写进 commit message** | "为什么选 SQLite 而不是 JSON" |
| **看到 `any` 立刻改** | TypeScript 的 `any` = "我没想清楚" |

## 十二、目录的"演化路径"

> 新手最容易踩的坑：**预先优化目录**。

### ❌ 错误示范

```
一开始就建：
/services/
/repositories/
/controllers/
/useCases/
/dtos/
/factories/
```

**这种过度工程化 = 4 天写 100 个空文件夹 + 0 行业务代码**。

### ✅ 正确示范

```
第 1 天：
src/app/page.tsx         ← 一行 "Hello"
src/components/PixelButton.tsx

第 3 天：
src/lib/posts.ts         ← 读博客文章

第 7 天：
src/components/blog/PostCard.tsx

第 14 天：
src/lib/db/              ← 真要换数据库了，才建
src/types/index.ts       ← 类型多了，才集中
```

**原则**：**先用着，**疼了再拆**。

## 十三、目录自检清单

> 每完成一个模块，看一眼：

- [ ] 这个文件**应该放在哪个目录**？（不是凭感觉）
- [ ] 这个组件**应该被复用吗**？（2+ 次才抽）
- [ ] 这个工具函数**值得独立吗**？（复杂逻辑才独立）
- [ ] 这个 hook **算 hook 吗**？（用 React API 才是 hook）
- [ ] 文件名**符合规范**？（大驼峰 / camelCase / kebab-case）
- [ ] 文件**没超 200 行**？
