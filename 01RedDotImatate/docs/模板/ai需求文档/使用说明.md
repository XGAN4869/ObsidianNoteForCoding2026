# 需求评审与前端方案模板

提炼自[首页需求评审](../首页/首页需求评审.md)与[首页前端方案](../首页/首页前端方案.md)，用于新页面、功能模块或已有功能改造。

## 1. 复制与填写

1. 在 `docs/<模块>/` 复制两份模板，分别改名为 `<模块>需求评审.md`、`<模块>前端方案.md`，同步修改标题和相互链接。
2. 先填写需求依据、需求卡、已确认规则与验收条件，再确定当前最小闭环。
3. 依据相关源码填写状态归属、数据链路、实现选择与验证方法。未读源码、未运行验证的内容如实标记。
4. 当前闭环确定后，再按需补文件输入输出。只填与当前任务相关的内容；不适用的表格行、分支和可选章节直接删除。
5. 后续只更新变化的决定、规则和验证结果；保持规则与验收有唯一维护位置。

模板入口：

- [需求评审模板](需求评审模板.md)：为什么做、做什么、业务怎样运行、如何验收、哪些事项还没决定。
- [前端方案模板](前端方案模板.md)：状态放哪里、数据怎么流、按什么条件选实现、如何证明方案可行。

## 2. 保留原文的写法

| 原则 | 填写方式 |
| --- | --- |
| 业务与实现分开 | 业务规则、运行规则、行为 AC、业务未决项只在需求评审维护；方案引用相应编号 |
| 确认与建议分开 | 有用户确认依据才写“已确认”；AI 推荐写“建议”，不能代写人工评审结论 |
| 事实与验证分开 | 源码存在、源码缺口已确认、原型已验证、行为已验收分别记录 |
| 两棵树用途不同 | 需求树拆“做什么”；技术树表达“满足什么条件，就采取什么实现” |
| 从最小闭环开始 | 写清起点、成功结果、失败反馈与恢复；后续未决项只阻塞受影响单元 |
| 复用有依据 | 查清现有能力是否满足当前契约，再决定直接复用、扩展或新增 |
| 验收能观察 | 使用“给定条件 → 执行操作 → 预期结果”，覆盖正常、异常与恢复 |
| 参数有来源 | 首页原文的条数、距离、比例、缓存策略是该模块决定，不自动成为新模块默认值 |

项目内使用时以 [AGENTS.md](../../AGENTS.md) 为准。模板不复制整份工程规范，避免规则分叉；跨项目使用时替换规范入口。

## 3. 完成一轮文档的检查

- [ ] 当前用户问题、目标、范围与最小闭环明确。
- [ ] 业务规则有来源，建议没有被写成已确认。
- [ ] 当前闭环的关键未决项明确，后续事项没有扩大当前范围。
- [ ] 需求拆分树与技术决策树分工清楚，没有把普通执行顺序伪装成选择条件。
- [ ] 状态归属、模块输入输出与复用依据能支持当前方案。
- [ ] 验收覆盖正常、异常、恢复；技术验证写明方法、证据和真实状态。
- [ ] 文档相互链接正确；人工结论、实现进度与验收结果没有被提前填写为通过。

## 4. 后续给 AI 的复用提示词

```text
请参考 docs/模板/需求评审模板.md 和 docs/模板/前端方案模板.md，
为【模块名】整理需求评审与前端方案。

原始需求：【粘贴需求】
设计或资料：【填写路径或链接，没有则写无】
已有确认：【填写用户已决定的规则，没有则写暂无】
当前范围：【填写本次最小目标和目标平台】
输出目录：docs/【模块名】/

先读 AGENTS.md，再按当前任务读取相关资料与直接依赖源码。
沿用已有确认，明确事实、建议、待确认和待验证，不虚构接口或完成证据。
需求文档维护业务规则、运行规则、行为验收和业务未决项；
方案文档维护状态归属、数据流、技术决策和可行性证据。
先拆一个包含正常、异常和恢复的最小闭环，再按需展开实现。
不适用的模板内容删除，不照搬首页专属的数字、算法或缓存策略。
本轮只整理文档，不修改业务代码。
```
