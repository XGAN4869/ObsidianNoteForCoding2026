# 瀑布流卡片测量：SelectorQuery 与 ResizeObserver

> 项目背景：uni-app + Vue 3，目标为 H5、App-vue 和微信小程序。当前按页获取数据，每页 20 条；标题自然占一行或两行，图片通过成品比例提前占位。

## 面试时怎么回答

我们的首页是跨端瀑布流，每批卡片布局前只需要测量一次，所以使用 `uni.createSelectorQuery()`，批量获取新增卡片的真实尺寸，再按最短列增量追加。测量区复用正式卡片的宽度和样式，测量期间不下载封面、头像，结束后移除临时节点。

选择它主要考虑跨端能力和当前交互需求，并没有测出它一定比 `ResizeObserver` 更快。`ResizeObserver` 更适合浏览器中元素尺寸会持续变化的场景，例如内容展开、容器宽度变化。它是事件驱动的，也支持用一个 observer 观察多个元素，不能理解成持续轮询或必然高开销。[ResizeObserver 说明](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver)

## 1. 两种 API 怎么选

| 对比项 | uni.createSelectorQuery | ResizeObserver |
| --- | --- | --- |
| 使用方式 | 主动选择节点，在需要时执行尺寸查询 | 观察 DOM 元素，获取初始尺寸及后续尺寸变化通知 |
| 当前需求 | 每个新批次排版后读取一次，适合 | 可以实现首次测量，但需要观察、收集结果和取消观察 |
| 尺寸变化 | 需要主动再次查询 | 可以自动响应被观察元素的尺寸变化 |
| 跨端边界 | 使用 uni-app 的节点查询能力，具体支持范围按平台确认 | 浏览器 DOM API，不能直接在所有 uni-app 平台的普通 setup 中复用 |

`selectAll` 可以选中一批节点，`exec` 统一执行已登记的查询；它返回布局信息，但不是持续监听器。[uni-app 节点查询文档](https://uniapp.dcloud.net.cn/api/ui/nodes-info.html)

H5 可以按浏览器能力使用 `ResizeObserver`。App-vue 的逻辑层与视图层分离，操作视图 DOM 通常通过 `renderjs` 等视图层方案；`renderjs` 不支持微信小程序，因此换用浏览器 API 会增加平台适配工作。也不能把 App-vue 的处理方式直接套到 nvue。[uni-app renderjs 文档](https://uniapp.dcloud.net.cn/tutorial/renderjs.html)

## 2. 当前测量流程

```text
获取新一页数据
→ measuringItems 暂存本批数据
→ 隐藏区按实际列宽渲染卡片
→ nextTick 后提交一批节点查询
→ 返回卡片宽高和间距，全部使用 px
→ 分页确认成功，按 ID 去重后的新卡片进入最短列
→ 清空测量区
```

- `measuringItems` 是让模板渲染临时卡片的响应式数组，不是正式列表。
- `CardMeasurement.cards` 保存数据与尺寸的对应关系；`gap` 是间距探针的实测宽度，探针与列间距引用同一个样式令牌。
- 卡片外壳的实测高度包含封面、标题、作者行、内边距和边框；卡片间距单独累计，不能重复相加。
- 一行标题占一行，两行占两行，超过两行截断；不再使用固定两行占位或 `比例 × 100 + 50`。
- 测量放在注入分页层的 loader 内，测量失败则本次分页失败，旧内容和游标保留；成功后由页面提交对应的列布局。

`nextTick` 等待 Vue 视图更新，它不等于所有平台的绘制、异步字体和图片都已经稳定。首次查询需要保证页面节点已经就绪；当前通过封面比例占位、固定头像尺寸和本地字体降低后续尺寸变化，App／小程序仍需验证实际渲染时序。

## 3. 当前方案的性能取舍

| 做法 | 目的 | 成本或限制 |
| --- | --- | --- |
| 每次只渲染本批测量卡片 | 限制临时节点数量，不为测量重新挂载历史列表 | 本批卡片仍要经历一次额外的组件创建、样式计算和布局 |
| selectAll 后统一 exec | 避免逐张卡片串行等待查询回调 | 批量调用不等于零通信，也不保证底层只发生一次布局或一次桥接 |
| 测量阶段只读尺寸，分列后再统一提交视图 | 避免逐张读尺寸、改布局、再读下一张 | 查询布局信息仍有成本；nextTick 也不会消除布局计算 |
| 相同卡片组件、相同列宽 | 保证测量高度与正式渲染一致 | 复用完整组件比纯占位节点重，但手写简化版模板容易尺寸失真 |
| 测量卡片不请求封面和头像图片 | 避免测量区重复发起业务图片请求、增加图片解码负担 | 图片占位比例必须正确，不能依赖下载完成后才确定高度 |
| finally 清空临时数组 | 测量结束后移除临时组件及其引用 | 释放引用不代表内存立即归还，实际回收由运行时决定 |
| shallowRef + 批次替换 | 无需为整条 Feed 建立深层响应式代理 | 仍有数组复制、遍历和渲染成本；直接改内部字段也不会自动触发更新 |

浏览器中反复交替修改样式和读取布局可能触发多次强制同步布局。应把布局读取集中处理，并把相关写入集中处理，避免循环中读写交错。[浏览器布局与 layout thrashing](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)

隐藏区仍然需要计算布局才能得到真实高度，不能称为“隐藏后没有渲染成本”。当前用隐藏和裁剪避免展示及撑高页面；使用 `display: none` 则无法得到用于正常排版的卡片高度。

## 4. ResizeObserver 的性能也要正确理解

- 它不是定时器轮询，不会因为存在一个 observer 就每帧无条件执行业务回调；初始观察与尺寸变化才会产生通知。
- 一个 observer 可以观察多张卡片，不需要为每张卡片各建一个实例；通知也可以批量处理。
- 回调已经带有尺寸信息，通常不需要再次逐个读取布局。
- content box 与 border box 的口径不同。计算整张卡片高度时，应选取包含 padding、border 的合适口径，不能把默认 `contentRect.height` 直接当成总高度。
- 回调中如果持续改变被观察元素的尺寸，可能形成“尺寸变化 → 回调 → 再变化”的循环。应只处理确有变化的结果，避免无条件修改尺寸；组件卸载时取消观察。[ResizeObserver 尺寸和循环说明](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver)
- 浏览器专用实现可以先观察、拿到首批结果后取消观察；这也是一次性测量的可行方案。因此不能仅凭“持续监听”四个字断定它更慢。[浏览器 ResizeObserver 实践](https://web.dev/articles/resize-observer)

如果未来支持正文展开、异步内容插入或容器宽度变化，当前“一批测一次”的前提就会改变，需要重新评估持续观察或明确事件触发的重测。已有卡片高度改变时，也应修正后续位置；不能永久沿用旧高度。

## 5. 增量追加还有哪些开销

设历史数据有 N 条，新批次有 M 条，列数为 C。

- **最短列选择**只遍历新批次，成本约 O(M × C)。首页固定两列，这部分约为 O(M)。
- **旧卡片不重新分列**保证旧卡片的列归属稳定，但不代表浏览器完全不做布局或 Vue 完全不做列表比较。
- **当前 useWaterfall 会复制旧列数组**，因此追加仍有 O(N) 的旧引用复制成本，不是整个追加流程都只有 O(M)。
- **当前分页去重也会读取旧列表 ID**，追加列表时同样创建新数组，历史数量变大后需要结合实际数据量评估。
- **当前还没有窗口化**，正式卡片节点随累计数据增加。增量算法解决了换列跳动问题，没有解决长列表的节点数量、图片资源和内存增长问题。

优先保证当前每批测量准确、旧卡片不跳动；累计数据量明显增加后，性能重点应转向窗口化与资源管理，而不是仅替换测量 API。

## 6. 怎么证明性能，而不是凭感觉

两种方案对比时，应固定设备、发布构建、卡片内容、列宽、图片缓存状态和列表规模。比较一次性预测量与持续尺寸监听时，还要说明两者承担的功能是否一致。

| 指标 | 观察内容 |
| --- | --- |
| 测量耗时 | 从提交测量数据到获取整批尺寸，包含视图更新及查询等待 |
| 本批可见耗时 | 从接口数据返回到新卡片实际呈现；不能只计 JS 分列循环 |
| 布局与脚本耗时 | H5 用浏览器性能记录查看 Layout、脚本任务和读写交错；其他端用对应工具验证 |
| 滚动表现 | 触底时有无停顿、跳位或反复加载，旧卡片位置是否稳定 |
| 节点与内存 | 测量区是否清理，正式列表增长后节点数、内存、图片资源是否持续增长 |
| 重复测量 | 图片完成加载是否改变占位高度，容器宽度变化后是否需要重测 |

可以分 20、200、1000 条等不同规模重复记录，关注典型值和较慢批次；不要用一次 H5 开发预览代表 App 真机性能。

当前取得的是功能证据：H5 验证了一行／两行标题高度不同、20 → 40 条追加后旧卡片位置不变、45 条末页和临时节点清理正常。尚未完成两种 API 的耗时、帧表现、内存对比，也没有 App／微信小程序真机性能数据，因此不宣称“更快了多少”。
