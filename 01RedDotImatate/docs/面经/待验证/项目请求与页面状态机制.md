# 项目请求与页面状态机制

本文只整理当前负责范围内的模块：

- 首页发现流、关注流和双列布局：`src/pages/index`、`src/composables/homepage`
- 笔记详情、图片画廊和视频生命周期：`src/pages/note`、详情相关 composable 与工具

发布笔记、草稿同步、上传和发布幂等属于其他模块，本篇不把它们当作自己的实现经验。

## 一、统一 HTTP 请求封装

有。统一入口是 [src/api/request.ts](../../src/api/request.ts)。页面和组件不直接调用 `uni.request`，而是由 `src/api/modules/*` 暴露业务函数，例如：

```ts
// src/api/modules/feed.ts
const page = await get<FeedPageVO>('/feed/discover', params, {
  showError: false,
  retryOnUnauthorized: false,
  parseResponse: parseJsonPreservingIntegers
})
```

请求层统一负责：

- 拼接 App/H5 的接口地址。
- 注入 access token。
- 统一超时，默认 `15000ms`。
- 处理 HTTP 状态码和业务 `code`。
- 将错误转换成 `ApiError`，区分网络、超时、HTTP 和业务错误。
- 对 401 尝试刷新 token，并只重放原请求一次。
- 控制是否由全局 toast 反馈错误；首页和详情把 `showError` 关掉，由页面展示局部错误。
- 对需要保留 long 精度的接口，用 `parseResponse` 在解析前处理原始 JSON。

请求层的职责是“通用请求能力”，它不负责首页空态、详情失效文案或业务页面布局。

## 二、页面四态：Loading、Success、Empty、Error

### 1. 首页信息流：四态比较完整

首页状态主要在 [src/composables/homepage/useCursorFeed.ts](../../src/composables/homepage/useCursorFeed.ts) 和 [src/composables/homepage/useHomeFeed.ts](../../src/composables/homepage/useHomeFeed.ts) 中维护，在 [HomeFeedView.vue](../../src/pages/index/components/HomeFeedView.vue) 中展示。

| 状态 | 代码位置 | 表现 |
| --- | --- | --- |
| Loading | `useCursorFeed.ts` 的 `loading`、`isInitialLoading`、`isLoadingMore`、`isRefreshing` | 首屏显示“正在加载”，翻页或刷新保留旧内容并显示加载反馈 |
| Success | `useHomeFeed.ts` 的 `view.columns`、`hasItems` | `HomeFeedView.vue` 渲染两列 `HomeNoteCard` |
| Empty | `useHomeFeed.ts` 的 `empty`，条件是没有条目且没有更多数据 | `HomeDiscoverFeed.vue` 展示“暂无内容”；关注流展示关注空态和推荐作者 |
| Error | `useCursorFeed.ts` 的 `error`、`errorPhase`，`HomeFeedError.vue` 展示 | 首屏错误显示错误占位和重新加载；翻页失败保留旧列表，在底部提供重试 |

这里的一个关键点是：**翻页失败不应该把成功列表清空**。所以首页实际上还区分了“无内容的首屏错误”和“已有内容后的局部错误”。

### 2. 详情页：有 Loading、Success、Error，Empty 不是独立状态

详情状态在 [src/pages/note/index.vue](../../src/pages/note/index.vue)：

- `loading`：显示“正在加载笔记”。
- `note` 有值：显示正文、媒体和互动区域，属于 Success。
- `failure`：由 `classifyNoteFailure()` 区分网络、登录失效、删除、下架、审核、私密和不可访问。
- `error`：显示页面错误描述和重新加载按钮。

详情没有“正常返回但内容为空”的独立 Empty 状态。服务端返回明确不可读状态时，页面会清理旧的 `note`，展示对应失效占位。面试时应说：**首页做了完整四态；详情采用 Loading / Success / Error 与业务失效状态，当前没有单独的 Empty 语义。**

## 三、请求缓存

当前负责模块没有通用 HTTP 响应缓存。

现有的“保留”容易和缓存混淆：

- 首页两个流各自保留组件实例中的 `items`、游标和列布局。切换 Tab 时是复用内存中的当前实例，不是把响应写入本地缓存。
- [useHomeFeed.ts](../../src/composables/homepage/useHomeFeed.ts) 的 `initialized` 只防止同一组件重复加载首屏，不是 HTTP 缓存。
- [useNoteImageGallery.ts](../../src/composables/useNoteImageGallery.ts) 缓存图片尺寸，避免同一张图片重复调用 `uni.getImageInfo`；它缓存的是媒体元数据，不是接口响应。
- 详情页返回后会重新调用 `getNoteDetail()` 核实内容状态，没有使用详情长期缓存。

因此，面试中应回答：**当前没有统一请求缓存层；有组件生命周期内存状态和图片尺寸缓存，但没有按 URL、参数、过期时间管理的 HTTP cache。**

如果以后做缓存，可以按“请求方法 + URL + 序列化参数 + 账号”作为 key，并设置过期时间；涉及权限和详情可见性时，切账号、登出和状态失效都要清理。

## 四、自动重试

当前有一种自动重试，位置在 [src/api/request.ts](../../src/api/request.ts)：

```text
请求返回 401
  → 用 refresh token 刷新 access token
  → 刷新成功，重放原请求一次
  → 再次失败或没有 refresh token，清理登录态并跳登录页
```

这属于“鉴权恢复后的单次重放”，不是网络错误无限重试。

首页和详情的网络失败目前是手动重试：

- 首页由 `HomeFeedView.vue` 的“重新加载/重试”按钮触发 `feed.retry()`。
- 详情由 `src/pages/note/index.vue` 的 `statusClick()` 或错误区域按钮触发 `loadDetail()`。
- `useCursorFeed.ts` 的 `retry()` 只是重新执行失败阶段，也不是自动定时重试。

当前没有“网络失败后自动重试 2 次、指数退避、只对幂等 GET 重试”的通用策略。若以后增加，应该默认只对 GET/HEAD 或明确幂等请求重试，避免把 POST 写操作重复发送。

## 五、请求去重

当前有几层去重，但要说清它们分别去重什么。

### 1. 首页分页请求锁

位置：[src/composables/homepage/useCursorFeed.ts](../../src/composables/homepage/useCursorFeed.ts) 的 `requestLocked`。

同一个分页实例正在请求时，再次触发 `loadInitial`、`loadMore` 或 `refresh` 会直接返回，不会并发发出第二个相同阶段的请求。这解决了重复触底和重复下拉造成的并发请求。

### 2. 首页首屏初始化保护

位置：[src/composables/homepage/useHomeFeed.ts](../../src/composables/homepage/useHomeFeed.ts) 的 `initialized`。

切换回已经加载过的发现流或关注流时，不会再次请求首屏。切账号时通过组件 `key` 重建实例，避免把旧账号的列表继续复用。

### 3. token 刷新请求合并

位置：[src/api/request.ts](../../src/api/request.ts) 的 `refreshPromise`。

多个接口同时收到 401 时，共用同一个 refresh 请求，避免并发刷新把 refresh token 轮换多次。

### 4. 图片元数据请求去重

位置：[src/composables/useNoteImageGallery.ts](../../src/composables/useNoteImageGallery.ts) 的 `pendingImages` 和 `dimensions`。

同一张图片正在读取尺寸或已经读取过时，不重复调用 `uni.getImageInfo`。

这不是“全局请求去重”。例如两个不同页面同时请求同一个详情接口，目前没有一个全局 promise map 自动合并它们。

## 六、AbortController

当前负责模块没有真正使用 `AbortController`，也没有把取消信号传到 `uni.request`。

现有代码采用“忽略旧结果”的保护：

- 详情页 [src/pages/note/index.vue](../../src/pages/note/index.vue) 用 `batch` 判断请求批次；旧批次返回时不再写入当前页面。
- 详情页用 `disposed` 阻止页面卸载后的回调提交。
- 首页 [useHomeFeed.ts](../../src/composables/homepage/useHomeFeed.ts) 也用 `disposed` 阻止组件卸载后的结果进入列表和布局。
- 图片画廊用 `metadataVersion` 让旧的图片尺寸回调失效。

区别是：

- `AbortController` 是真的取消底层请求，减少网络和解码工作。
- `batch/disposed` 是请求仍可能完成，但页面不再消费结果。

面试可以这样回答：**当前项目没有 AbortController；使用批次号、组件卸载标记和版本号做结果隔离，先保证旧响应不污染新状态。**

## 七、幂等性

在你负责的首页信息流和详情/媒体模块中，目前主要是只读 GET：

- `GET /feed/discover`
- `GET /feed/follow`
- `GET /note/{id}`
- 图片元数据读取

这些模块没有负责创建或修改业务资源，因此没有实现自己的幂等 key、版本号更新或状态机写入。

需要注意：请求层的 401 重放不是业务幂等方案。它只是在 token 刷新后再次读取同一个请求；你的模块主要是 GET，所以风险较低。若将来你负责点赞、收藏或关注等写接口，才需要单独设计：

- 状态明确设置：`PUT /note/{id}/like` 携带 `liked: true`，重复请求仍是 true。
- 幂等 key：一次用户操作生成 key，重试复用同一个 key。
- 状态机：未点赞 → 已点赞，已经是已点赞时重复请求不再增加计数。

发布笔记和草稿的 `idempotentKey` 属于其他模块，本篇不把它算成你的实现。

## 八、乐观更新

当前负责模块没有真正的乐观更新。

乐观更新是：用户点击后先立即改本地 UI，等接口成功；失败时回滚，结果不确定时再核实服务端。

首页目前是请求成功后才提交新的分页列表和布局；详情页也是详情请求成功后才设置 `note`。它们是“请求确认后更新”，不是乐观更新。

如果以后在你的详情模块增加点赞/收藏，可以把状态拆成：

```text
confirmed：服务端确认的 liked / collected / count
pending：当前正在提交的操作
error：失败后的回滚或待核实状态
```

不要只写一个 `isLiked` 就认为完成了乐观更新，因为超时不代表服务端一定失败，可能需要重新读取权威状态。

## 九、面试版总结

我负责的首页和详情模块使用统一请求封装：页面通过 `src/api/modules/*` 调用 `src/api/request.ts`，请求层统一处理 token、超时、业务错误和 401 刷新重放。首页在 `useCursorFeed`、`useHomeFeed` 和 `HomeFeedView` 中实现了 Loading、Success、Empty、Error 四态，详情页在 `pages/note/index.vue` 中实现 Loading、Success、Error 和业务失效占位，暂时没有单独 Empty。

当前没有通用 HTTP 缓存、AbortController、网络自动重试、全局请求去重、幂等写入或乐观更新。已有的是：分页请求锁、初始化保护、refreshPromise 合并 token 刷新、图片尺寸读取去重，以及用 batch/disposed/version 丢弃旧响应。由于我负责的模块主要是只读 GET，所以暂时重点是状态隔离和失败恢复；如果以后加入写接口，再补幂等 key、版本号、状态机和乐观更新。
