# 幂等性与修改接口

## 一、什么是幂等性

幂等性指：同一个业务操作执行一次或执行多次，最终业务结果相同。

它解决的是“请求结果不确定”时的重复提交问题：客户端可能超时，用户可能连续点击，网络层可能重试，或者服务端已经成功但响应没有回到客户端。

例如用户点击“保存草稿”后请求超时。客户端无法判断服务端到底有没有保存成功。如果直接再发一次，可能产生两条草稿；如果接口具备幂等性，重试只会得到同一个业务结果。

幂等性不等于“请求只能发送一次”。请求仍然可能到达多次，关键是服务端要保证同一个业务操作不会重复产生业务副作用。

还要区分：

- `GET` 通常设计成幂等：重复读取不会新增数据。
- `PUT` 通常天然适合幂等：把资源设置为某个确定状态，重复设置结果相同。
- `DELETE` 通常可以设计成幂等：第一次删除成功，之后再次删除返回“已删除”或“目标不存在”，不能重新产生副作用。
- `POST` 通常不是幂等的：重复发布、重复支付、重复创建都可能生成多条记录，所以需要额外的幂等方案。

## 二、先看项目里哪些接口需要考虑

项目统一通过 `src/api/request.ts` 发请求，页面不直接调用 `uni.request`。请求层负责鉴权、刷新 token、超时和错误转换，但它没有自动解决业务重复提交问题。

当前代码里比较典型的修改接口有：

| 代码 | 接口 | 风险 |
| --- | --- | --- |
| `src/api/modules/node.ts` | `POST /note` 发布笔记 | 超时后重试可能产生两条笔记；当前没有发布幂等 key |
| `src/api/modules/node.ts` | `POST /note/draft` 新建草稿 | 自动保存重试可能重复创建；当前请求体已有 `idempotentKey` |
| `src/api/modules/node.ts` | `PUT /note/draft/{id}` 更新草稿 | 目标由草稿 ID 唯一确定，重复写入同一份内容通常可幂等；仍要考虑旧版本覆盖新版本 |
| `src/api/modules/node.ts` | `DELETE /note/draft/{id}` 删除草稿 | 可按资源 ID 设计成重复删除安全 |
| `src/api/modules/settings.ts` | `PUT /settings` 修改单个开关 | 当前只提交被修改的字段；重复设置同一个布尔值结果相同 |
| `src/api/modules/profile.ts` | `PUT /user/profile` 修改资料 | 重复提交同一份资料结果相同，但并发编辑可能互相覆盖 |
| `src/api/modules/follow.ts` | `POST /follow/{targetUserId}`、`DELETE /follow/{targetUserId}` | 关注和取消关注必须按最终关系处理，不能因为重复请求把状态切换两次 |

## 三、方案一：版本号机制（乐观锁）

### 1. 原理

每条可修改数据带一个 `version`。客户端读取到版本 `7`，修改时携带 `id` 和 `version: 7`。服务端更新时只允许：

```text
UPDATE note_draft
SET content = ?, version = version + 1
WHERE id = ? AND version = 7
```

如果影响行数为 `0`，说明别人已经先修改过，客户端手里的版本过期，服务端返回冲突。这样可以避免“旧页面最后保存，把新页面的内容覆盖掉”。

### 2. 对应项目里的例子：更新草稿

现有代码在 `syncNoteDraft` 中根据 `remoteDraftId` 选择：

- 没有远程 ID：`POST /note/draft`
- 有远程 ID：`PUT /note/draft/{id}`

这已经能保证“更新哪条草稿”是明确的，但还没有看到 `version` 字段。假设用户在手机 A 和电脑 B 同时打开同一份草稿：

1. A、B 都读取 `version = 7`。
2. A 保存成功，服务端变成 `version = 8`。
3. B 仍拿着 `version = 7` 保存。
4. 没有版本校验时，B 会把 A 的修改覆盖掉；有版本校验时，B 会收到冲突，页面可以提示“草稿已在其他设备更新，请重新读取”。

请求可以扩展成：

```ts
await updateNoteDraft(draft.remoteDraftId, {
  ...body,
  version: draft.version
})
```

服务端成功后返回新版本，客户端再写回本地草稿。

### 3. 适用场景

版本号适合“修改已有资源”的接口：草稿、个人资料、设置、笔记编辑。它主要解决并发覆盖问题，也能把过期更新明确暴露给用户。

它不能单独防止“首次创建重复”。例如两个完全相同的 `POST /note` 都没有旧版本可以比较，创建接口仍需要幂等 key。

## 四、方案二：唯一业务流水号（幂等 key）

### 1. 原理

客户端为一次业务操作生成唯一 ID，并在整个重试过程中复用它：

```text
idempotencyKey = deviceId + operationId
```

服务端为这个 key 建唯一约束或幂等记录：

```text
key                  status       result
draft-local-abc-001  succeeded    remoteDraftId = 18
```

处理流程通常是：

1. 第一次收到 key，记录“处理中”并执行业务写入。
2. 业务成功，保存 key 和最终结果。
3. 同一个 key 再次到达，直接返回第一次的结果，不再创建新数据。
4. 如果第一次失败，要根据失败类型决定允许重试还是保留失败结果。

### 2. 对应项目里的例子：新建草稿

项目的 `DraftNote` 有本地 `id`，同步草稿时已经把它作为：

```ts
idempotentKey: draft.id
```

这正是幂等 key 的现成例子。`syncNoteDraft` 的注释也明确说明：自动保存和手动保存同时发生、弱网重试时，不能让后端落下两条草稿。

但是这个方案成立有一个前提：后端必须对 `idempotentKey` 建唯一约束，并在重复请求时返回原来的远程草稿 ID。仅仅把字段发给后端、而后端不保存和检查它，并不能产生幂等性。

### 3. 对应项目里的反例：发布笔记

当前发布流程是：

1. 上传图片和视频。
2. 生成或确认封面。
3. 调用 `POST /note`。

如果第 3 步服务端已经创建笔记，但客户端因为超时没有拿到响应，用户再次点击发布，当前代码没有一个贯穿整次发布的幂等 key，后端可能生成第二条笔记。

更稳妥的做法是页面进入一次发布流程时生成 `publishOperationId`，重试时保持不变：

```ts
await publishNoteRequest({
  ...payload,
  idempotencyKey: publishOperationId
})
```

后端按 `(userId, idempotencyKey)` 建唯一约束，并保存第一次成功返回的 `noteId`。客户端重试时拿到同一个 `noteId`，就不会重复发布。

### 4. 适用场景

幂等 key 最适合“创建型”或副作用明显的 `POST`：发布笔记、发送消息、提交评论、生成订单、上传后确认。它也可以用于任何需要客户端重试的写操作。

幂等 key 必须有作用域，通常至少包含用户或账号维度；否则不同用户碰巧使用同一个 key，可能被错误地当成同一个业务操作。

## 五、方案三：状态机控制

### 1. 原理

服务端只允许合法状态迁移，已经完成的状态不能再次执行同一个副作用：

```text
editing  -> publishing -> published
editing  -> failed
failed   -> publishing
```

例如“发布中”只能进入“已发布”一次。重复收到“确认发布”时，如果资源已经是 `published`，就直接返回已发布结果，不能再次创建或扣款。

状态机的重点不是简单判断一个布尔值，而是限制“从哪个旧状态到哪个新状态”，并在数据库更新时把旧状态放进条件里：

```text
UPDATE note
SET status = 'published'
WHERE id = ? AND status = 'publishing'
```

### 2. 对应项目里的例子：草稿状态

项目的本地草稿有：

```ts
type DraftStatus = 'editing' | 'failed'
```

远程草稿也有 `status`，`syncNoteDraft` 会把本地状态映射为后端状态码：

```ts
status: draft.status === 'failed' ? 1 : 0
```

这为状态机提供了基础，但当前前端并没有完整实现“发布中 / 已发布”的状态迁移，也不能仅靠前端的 `status` 防止并发请求。真正的状态迁移必须由后端在事务和条件更新中保证。

### 3. 对应项目里的例子：关注关系

用户页根据 `profile.following` 决定调用关注还是取消关注：

- `false -> true`：`POST /follow/{targetUserId}`
- `true -> false`：`DELETE /follow/{targetUserId}`

这就是一个简单的关系状态机。重复点击时，页面已有 `followPending` 锁，避免同一时刻连续发送；服务端仍应校验当前关系：

- 关注接口只有在“未关注”时执行创建关系。
- 已经关注时重复请求，返回当前已关注或幂等成功。
- 取消关注接口只有在“已关注”时删除关系。
- 已经取消时重复请求，返回当前未关注或幂等成功。

如果只在前端判断 `following`，两个设备同时操作仍可能产生竞态，所以后端的唯一键 `(followerId, targetUserId)` 和状态条件仍然必要。

## 六、三种方案怎么选

| 场景 | 首选方案 | 原因 |
| --- | --- | --- |
| 创建笔记、发送消息、提交评论 | 幂等 key | 没有旧资源版本，必须识别“这是同一次创建” |
| 更新草稿、编辑资料、修改设置 | 版本号；必要时叠加幂等 key | 防止旧页面覆盖新页面；重试时还可以识别同一次保存 |
| 关注、取消关注、发布状态、删除状态 | 状态机 + 数据库唯一约束 | 只有合法的状态迁移才能产生副作用 |
| 删除草稿 | 资源 ID + 状态机 | 重复删除不应再次产生副作用，已删除可返回幂等成功 |

实际项目通常组合使用，而不是三选一：

```text
保存草稿 = idempotencyKey 防重复创建
         + version 防并发覆盖
         + status 防止非法状态迁移
```

## 七、面试时可以这样回答

幂等性不是让请求只能发一次，而是让同一个业务操作重复到达时不会重复产生副作用。修改接口我会先看资源是否已有版本：有版本就用乐观锁，更新时带旧版本，版本不匹配就返回冲突；创建型接口没有旧版本，就由前端生成唯一业务幂等 key，后端记录并复用第一次结果；涉及发布、删除、关注这类明确阶段的操作，再用状态机限制合法迁移。项目里新建草稿已经有 `idempotentKey`，更新草稿适合补 `version`，发布笔记的 `POST /note` 目前还需要补发布级幂等 key，关注关系则需要前端 pending 锁配合后端唯一约束和状态判断。
