# 首页首屏缓存与后台刷新

## 面试版结论

首页使用的是“本地首屏快照 + 后台刷新”，也可以称为轻量的 stale-while-revalidate：

1. 进入首页时先读本地快照，快照有效就立即展示，减少白屏和首屏等待。
2. 展示缓存后继续请求服务端最新首屏，不让缓存长期代替真实数据。
3. 服务端返回成功后替换当前列表、游标和瀑布流布局，并覆盖本地快照。
4. 后台刷新失败时保留已经展示的缓存内容，只在列表底部显示局部错误和重试入口。

## 具体代码位置

### 1. 缓存 key

位置：[src/constants/index.ts](../../src/constants/index.ts)

```ts
HOME_FEED_CACHE: 'ys:home-feed-cache'
```

它只是 key 的前缀，真正使用时会继续拼接账号和流类型：

```text
ys:home-feed-cache:guest:discover
ys:home-feed-cache:guest:following
ys:home-feed-cache:123:discover
ys:home-feed-cache:123:following
```

这样做是为了防止用户退出登录或切换账号后，看到上一个账号的首页内容。

### 2. 缓存的读写和后台刷新

位置：[useHomeFeed.ts](../../src/pages/index/feed/composables/useHomeFeed.ts)

关键结构：

- `FeedCacheSnapshot`：缓存时间、列表、下一页游标、是否还有更多、推荐作者。
- `FEED_CACHE_TTL`：当前有效期为 30 分钟。
- `hydrateCache()`：读取、校验并恢复快照。
- `ensureLoaded()`：决定先显示缓存还是直接请求网络。
- `fetchFeed()` 成功后：当 `cursor === null` 时写回最新首屏缓存。

首页组件传入缓存 key：

```ts
useHomeFeed({
  type: 'discover',
  cacheKey: `${accountKey}:discover`,
  measure: notes => list.value!.measure(notes)
})
```

## 完整时序

```text
首页组件 mounted
→ feed.ensureLoaded()
→ initialized = true
→ 读取 ys:home-feed-cache:{账号}:{流类型}
→ 校验 savedAt、30 分钟有效期、list 是否为数组
→ 有效：恢复 items / nextCursor / hasMore / recommendedAuthors
→ 先测量缓存卡片并立即渲染
→ void load('refresh') 后台请求最新首屏
→ 请求成功：测量新卡片、替换列表和布局、写回缓存
→ 请求失败：保留缓存列表，底部显示错误和重试
```

如果没有有效缓存，`ensureLoaded()` 会直接走 `load('initial')`，页面显示正常 Loading 状态，等网络请求结束后再进入 Success、Empty 或 Error。

## 为什么能提升首屏速度

普通流程是：

```text
进入首页 → 等接口 → 等测量 → 显示卡片
```

缓存流程是：

```text
进入首页 → 读本地 → 测量本地快照 → 先显示卡片
                         ↓
                   后台请求最新数据
```

本地存储读取不需要网络往返，因此用户会更快看到上一次成功的首页。网络请求仍然会继续执行，所以缓存只是首屏占位和快速恢复，不是永久数据源。

## 缓存恢复时为什么仍要测量

缓存只保存业务数据和游标，不保存卡片的最终布局高度。标题和正文摘要可能是动态一行或两行，字体、屏宽和版本变化也可能影响卡片高度。

因此恢复缓存后仍然要调用 `measure()`：

```text
缓存 list
→ HomeFeedView 隐藏测量区
→ HomeFeedView.measure 批量读取真实卡片高度
→ useWaterfall 重建两列
```

测量失败时不会丢掉缓存，`useHomeFeed` 会使用 3:4 卡片高度兜底，保证缓存仍能浏览；后台刷新成功后再用新数据和新测量结果校准。

## 需要注意的边界

| 边界 | 当前处理 |
| --- | --- |
| 缓存超过 30 分钟 | 忽略缓存，直接请求网络 |
| 缓存数据格式异常 | 忽略缓存，直接请求网络 |
| 缓存存在但后台刷新失败 | 保留缓存内容，显示局部错误，不把页面清空 |
| 切换账号 | key 带账号 ID，组件 key 变化时重建 feed 实例 |
| 发现流和关注流 | 使用不同的 `discover/following` key，列表和游标隔离 |
| 缓存为空列表 | 仍可恢复游标和空态，但最终是否显示 Empty 由当前状态决定 |
| 服务端快照版本变化 | 由 `fetchFeed` 和 `SnapshotResetError` 触发整体替换，不能把新旧快照混在一起 |
| 从详情返回 | 首页实例按流保存滚动位置。详情确认的更新按 ID 回写已加载卡片和有效首屏快照，保留原游标和缓存时间 |

当前实现没有主动删除过期 storage，只是在读取时忽略过期快照。后续如果需要控制本地空间，可以在发现过期时调用 `removeStorage`，但这不是首屏正确性的前提。

## 面试时怎么回答

我在首页使用了本地首屏快照来优化首屏体验。缓存 key 由账号和流类型组成，避免串账号；快照包含保存时间、列表、游标、hasMore 和推荐作者，当前 TTL 是 30 分钟。进入首页后先校验并恢复缓存，测量卡片高度后立即展示，再后台请求最新首屏。后台刷新成功就整体替换并更新缓存，失败则保留已有内容，只显示局部错误。这样首屏不依赖网络才能出现，同时服务端数据仍然最终会覆盖缓存。需要注意的是，缓存保存的是数据快照，不保存布局高度，所以恢复后仍要重新测量瀑布流卡片。
