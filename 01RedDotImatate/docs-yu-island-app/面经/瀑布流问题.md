## 瀑布流排版算法采纳
- 用增量追加，而不是一左一右，不然有的列图片会过长，有的过短，这个是看卡片的宽度和高度的
    初始：只有 A、B
    - A：列 0（列 0 总高 = 10）
    - B：列 1（列 1 总高 = 12） 列状态：`col0:[A(10)], col1:[B(12)]`
    触底，拿到新一批：`[C,D]` 只遍历 C、D，旧 A、B 不动
    - C：找最短列 → 列 0（10）塞进去，col0=10+9=19
    - D：现在最短是列 1（12），塞进去，col1=12+10=22 最终布局： col0: [A,C] 总高 19 col1: [B,D] 总高 22
    ✅ 旧卡片 A、B 还在原来的列，位置不变，用户不会看到内容跳来跳去
- 其次判断高度有失真问题，不能只计算图片比例要计算整张卡片的比例

测量 API 的选择、隐藏渲染成本和长列表性能，见 [卡片测量与 ResizeObserver](./卡片测量与ResizeObserver.md)。

## 虚拟滚动 vs 普通滚动：测量与性能的取舍

**普通滚动**（页面滚动 / `scroll-view` 都算）不需要任何高度测量：节点交给浏览器排版，滚动交给内核处理。代价是节点全量存在——列表越长，内存、样式计算、图片资源越多，滚动和触底越容易卡。页面滚动比 `scroll-view` 少一层容器，性能略好，但两者都是"全量渲染"。

**虚拟滚动**只渲染可视区附近的节点，节点数恒定，但必须自己算出每个条目占的位置：

- 固定高度：`index × itemHeight` 直接算，不需要 measure；
- 不定高度：必须 measure（`SelectorQuery` / `ResizeObserver` / 预留占位），并缓存高度；图片加载、字体、展开收起改变高度时还要更新缓存和后续偏移；
- 瀑布流更麻烦：位置依赖前面所有条目的高度，缓存错了会重叠、留空洞或滚动跳位。

所以不是"虚拟滚动一定更好"，而是用测量的复杂度和跳位风险，换节点数和内存。数据量小时普通滚动更简单；无限信息流累计到几百上千条后，性能重点才转向窗口化。当前项目还没做窗口化，正式卡片节点随累计数据增长（见 [卡片测量与 ResizeObserver](./卡片测量与ResizeObserver.md) 第 5 节）。
