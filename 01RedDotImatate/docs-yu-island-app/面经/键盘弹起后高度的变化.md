# 键盘弹起后高度的变化

参考链接：https://www.cnblogs.com/Lotos/p/18034579

> 项目背景：uni-app App-vue，详情页评论输入弹层。详情页在 `src/pages.json` 配置了 `softinputMode: "nothing"`（方案 3，手动接管键盘布局）。

## 面试时怎么回答

Android 键盘弹起后 WebView 窗口怎么变，取决于 Activity 的 `softInputMode`：

- `adjustResize`：系统把可视区域缩小，WebView 窗口高度变小，`onResize` / `uni.onWindowResize` 会触发。可以用「宽度不变、高度变小」判断键盘弹起，用「高度恢复」判断键盘收起。
- `adjustPan`：窗口尺寸不变，只是把页面整体往上平移，保证输入框可见。**resize 不会触发**，任何依赖窗口高度变化的键盘判断都会失效，只能听 `uni.onKeyboardHeightChange`。
- `nothing`：不做调整，键盘可能直接盖住输入框。

所以「键盘弹起会触发 resize」不是平台通用结论，它只在你选择了 `adjustResize` 时成立。把 UI 行为建立在窗口高度变化上，等于隐式依赖这个配置；配置一换，代码不会报错，只会静默失效。

## 1. 三种 softinputMode 对比

| 模式 | 窗口高度 | 是否触发 resize | 页面表现 | 能否靠 resize 判断键盘 |
| --- | --- | --- | --- | --- |
| `adjustResize` | 变小 | 是 | WebView 可布局区域减去键盘区域，底部固定元素自然浮在键盘上方 | 可以，需配合宽度判断 |
| `adjustPan` | 不变 | 否 | 整个页面内容上移，让聚焦的输入框露出来 | 不能 |
| `nothing` | 不变 | 否 | 键盘覆盖内容，输入框可能被挡住 | 不能 |

`plus` 类型定义里的原始说明：

- `adjustPan`：弹出软键盘时 Webview 窗口自动上移，以保证当前输入框可见；
- `adjustResize`：自动调整 Webview 窗口大小（屏幕区域减去软键盘区域），同时自动滚动 Webview 保证输入框可见；
- `nothing`：不做任何调整（软键盘可能覆盖输入框）。

参考：[HTML5+ Webview 文档](http://www.html5plus.org/doc/zh_cn/webview.html)、[uni-app pages.json 配置](https://uniapp.dcloud.net.cn/collocation/pages.html)

## 2. resize 和键盘高度事件不是一回事

| 信号 | 触发条件 | 能回答的问题 | 局限 |
| --- | --- | --- | --- |
| `onResize` / `uni.onWindowResize` | 窗口尺寸变化 | 窗口变高还是变矮 | 分不清是键盘、旋转还是分屏；`adjustPan` 下不触发 |
| `uni.onKeyboardHeightChange` | 键盘高度变化 | 键盘具体多高、是否收起（`height === 0`） | 不决定页面是否 resize；H5 不支持，需按平台条件编译 |
| `uni.getWindowInfo()` | 主动调用 | 调用那一刻的窗口尺寸 | 不是事件，不会持续通知；调用时机不对会拿到旧值 |

用 resize 推断键盘时，必须同时满足两个条件：

1. 宽度不变：排除横竖屏旋转、分屏、折叠屏展开；
2. 高度比打开输入框前小：排除其它 resize 原因。

高度恢复后再判定键盘收起。这套判断的本质是「猜」，不是平台明确告诉你键盘状态，所以：

- 只在 `adjustResize` 下成立；
- iOS 键盘弹起通常不改变 WebView 窗口高度，这套判断在 iOS 上同样不成立；
- 页面配置改成 `adjustPan` 后，resize 分支永远进不去，表现是键盘收起了但弹层/状态没复位。

## 3. 和 `adjust-position` 的区别

`input` 的 `adjust-position`（uni-app 内置属性）控制的是「输入框聚焦时，是否让页面自动上推」，它不改变窗口是否 resize：

- `adjust-position: true`（默认）：由平台自动滚动/上推，保证输入框可见；
- `adjust-position: false`：关闭自动上推，页面位置自己负责。

即使设置了 `adjust-position: false`，`adjustResize` 下窗口高度该变小还是会变小；`adjustPan` 下窗口也仍然不会 resize。不要把「关掉自动上推」当成「窗口不会变化」。

两种方案里 `adjust-position` 的实际取舍：

- **`adjustResize`（聊天页）**：`adjust-position` 开不开影响都不大。窗口已经被系统压缩，输入栏天然在键盘上方；列表要贴底就自己滚动（`scroll-into-view` / `scrollToBottom`），不依赖 uni 的自动上推。
- **`nothing` + 覆盖键盘（详情页评论弹层）**：必须 `adjust-position="false"`，干掉 uni 的自动滚动。输入框在 fixed 弹层里、位置由 `bottom: keyH` 控制，自动上推会再叠一层位移，和手动偏移打架，表现为抖动。

## 4. 本项目的情况

- 详情页在 `src/pages.json` 配置 `"softinputMode": "nothing"`，评论输入框设置 `:adjust-position="false"`，键盘高度由 `uni.onKeyboardHeightChange` 维护到 `keyH`，弹层自己设 `bottom: keyH`（方案 3）。
- 页面里的 `onResize` 只用于重新测量正文折叠行数（`measureContent`），不再参与键盘判断。
- 旧实现依赖 `adjustResize` 的窗口挤压；切到 `nothing` 后，任何基于窗口高度变化推断键盘状态的代码都会静默失效。

如果页面改成 `adjustPan` 或 `nothing`：

- 窗口高度不变，基于 resize 的键盘/弹层状态判断全部失效；
- 底部固定弹层是否还能露出来取决于页面平移，不能按 `adjustResize` 的布局假设继续写；
- 键盘状态应改用 `uni.onKeyboardHeightChange`，并按键盘高度手动偏移输入区。

## 5. 容易踩的坑

- 在 H5 上验证调整模式没有意义：H5 没有 Android 的 `softInputMode`；iOS Safari 的键盘还可能只改变 `visualViewport`，不改变布局视口高度。
- 不能只看 `onResize` 有没有触发就判断键盘；旋转、分屏、字体缩放也会触发 resize。
- 真机验证要覆盖不同 Android ROM 和输入法，模拟器行为不能代表全部设备。
- 依赖隐式平台配置的代码，至少要在配置和代码两处互相注明，避免以后有人改 `softinputMode` 时找不到受影响的地方。

## 6. App 端四种键盘布局组合

只针对 App：小程序没有 `softinputMode`；H5 不支持 `uni.onKeyboardHeightChange`。

| 方案 | 配置 | 系统行为 | 适用场景 |
| --- | --- | --- | --- |
| 1 自动上推 | `adjustPan` + `adjust-position="true"` | 不压缩 WebView，页面整体上移，框架保证输入框可见 | 简单表单，不用自己算键盘高度 |
| 2 挤压 | `adjustResize` + 默认 `adjust-position` | WebView 高度被压缩，页面跟着缩小 | 普通滚动表单；底部弹窗容易受挤压影响 |
| 3 完全手动 | `nothing` + `adjust-position="false"` + `onKeyboardHeightChange` | 系统不推不挤，键盘直接盖在页面上 | 小红书式底部评论弹窗，自己设置 `bottom: keyH`、`max-height` |
| 4 半手动 | `adjustPan` + `adjust-position="false"` + `onKeyboardHeightChange` | 系统仍保留自动上推能力，和手动位移叠加 | 不推荐：安卓上容易双重位移、抖动 |

选型速记：

- 简单表单 → 方案 1；
- 普通滚动表单 → 方案 2；
- 底部弹出评论框、双层输入、不想被系统推 → 方案 3；
- 方案 4 不要用，自动上推和手动偏移会打架。

### 监听注册放在哪

- `onLoad` 是页面生命周期，页面级逻辑用它；`onMounted` 是组件生命周期，键盘监听写在组件里时用它。
- 组件内注册的监听要在 `onBeforeUnmount` 解绑，避免组件销毁后回调还在改状态。
- 不要为了省一个 import 把组件里的逻辑塞进页面根文件的 `onLoad`，会把页面的职责和组件的职责混在一起。

> 项目现状：详情页已切到方案 3 —— `softinputMode: "nothing"`、输入框 `adjust-position="false"`、`onKeyboardHeightChange` 维护 `keyH` 给弹层做偏移，组件卸载时解绑监听。

### 为什么 `nothing` 还要 `virtualKeyboard.overlaysContent = true`

`softinputMode` 和 WebView 内核的焦点滚动是两层机制，`nothing` 只关了第一层：

- `softinputMode: "nothing"` = **不让 Android 系统帮你挪 WebView 窗口**：Activity 不缩窗口，也不平移页面。
- 但新版 WebView 内核（Chromium）自己还有一套焦点滚动：输入框聚焦时仍会滚动可视视口、按需重新布局，保证输入框可见。这个配置管不到内核层，所以只写 `nothing`，页面仍可能被内核推走或抖一下。
- `navigator.virtualKeyboard.overlaysContent = true`（VirtualKeyboard API）告诉内核：键盘直接盖在内容上，不要改视口尺寸，也不要替页面滚动。布局完全交给 `onKeyboardHeightChange` + 自己的 `bottom: keyH`。

两者必须一起用：前者关掉系统窗口调整，后者关掉内核的自动滚动。

**这行必须放进 renderjs。** 这是最容易翻车的点，也是本项目踩过的坑：

- App-vue 的逻辑层和视图层是两个 JS 环境。普通 `<script setup>` 跑在逻辑层，那里的 `navigator` 不是 WebView 的 `navigator`，`'virtualKeyboard' in navigator` 永远 false——不报错，但完全没效果，页面照样被内核推。
- `<script module="xxx" lang="renderjs">` 跑在视图层 WebView 里，拿到的才是真正的 Chromium `navigator.virtualKeyboard`，改的才是 WebView 自己的键盘/视口策略。所以「逻辑层 API + 视图层行为」不能指望在同一个 `onMounted` 里配齐。
- renderjs 只在 app-vue 和 H5 可用，小程序不支持。

用 `'virtualKeyboard' in navigator` 先做能力检测，是因为该 API 只在较新的 Android WebView 内核提供，旧内核没有这个对象。

两个补充：

- `overlaysContent` 是 document 级的，app-vue 所有页面共用一个 WebView。离开详情页要置回 `false`，否则其它依赖系统 resize 的页面（如聊天页）输入栏会被键盘盖住。
- renderjs 在 H5 也会执行。H5 没有 `uni.onKeyboardHeightChange` 那套手动偏移，进入覆盖模式后输入栏会被挡住；H5 是发布目标时要按平台条件编译。

### 为什么说这是「Chromium 内核」的问题

这里的 "Chrome" 指 Chromium 内核，不是 Chrome 浏览器。App-vue 的页面本质是 WebView 里跑的网页，Android 上用的是 Android System WebView（厂商可能换皮，底层都是 Chromium/Blink）。这件事涉及三层，别混：

- `softinputMode`：**原生 Activity 层**的窗口策略（Java 侧），决定系统要不要缩窗口、平移窗口；
- 键盘弹出后 WebView 内部怎么响应 IME：**Chromium/Blink 内核层**——visual viewport 缩放、聚焦元素滚动都在这一层，`softinputMode` 管不到；
- `navigator.virtualKeyboard`：Chromium 实现的标准 Web API（Chrome 94+，WebView 内核版本对应），用来告诉内核「键盘覆盖内容，别缩放、别替页面滚」。所以能力检测判断的是内核有没有这个对象。

对照其他端：

- iOS 的 WebView 是 WKWebView（WebKit）：既没有 Android 的 `softinputMode`，也没实现 VirtualKeyboard API，`'virtualKeyboard' in navigator` 直接 false，这段天然跳过；
- 小程序没有 WebView 内核这个概念（双线程 + 原生组件），renderjs 也不可用；
- nvue 是原生渲染，整条 WebView 链路都不存在。

同一份代码在不同 Android 设备上 WebView 版本不同（老内核没有这个 API），所以必须能力检测。真机确认内核版本：页面里打 `navigator.userAgent`，一般能看到 `Chrome/xxx` 和 `wv` 标记。

## 7. 对应源码

- `src/pages.json`：详情页 `app-plus.softinputMode: "nothing"`。
- `src/pages/note/index.vue`：`<script module="keyboardViewport" lang="renderjs">` 在视图层设置 `navigator.virtualKeyboard.overlaysContent = true`；`onResize` 只重新测量正文折叠高度，与键盘无关。
- `src/pages/note/media/components/comment.vue`：底部评论弹层，输入框 `adjust-position="false"`，`onMounted` 注册 `onKeyboardHeightChange`、`onBeforeUnmount` 解绑。键盘高度监听属于逻辑层；`virtualKeyboard` 那行属于视图层，不能放在这里。
