## 一、这一阶段要解决什么问题

**具体需求：**

1. 本地图片和 CSS 引用的资源，在开发与生产 App 中都能找到。
2. 图片失败有反馈，恢复后能显示，不把路径错误误判为组件故障。
3. 一个实际使用的图标在联网、首次离线和缓存后离线时的行为可解释。
4. Tailwind、SCSS 与 TDesign 的颜色来源和单位关系清楚。
5. 结论来自实际产物与手机验证，不仅是配置中写了某个值。

**项目效益：** 在开发业务页面前，先识别图片丢失、字体联网依赖、颜色冲突、尺寸不一致等基础问题，减少后面逐页面补救。

**最终交付：** 一份资源路径表、一份单位/颜色对照、一组失败恢复及离线记录，以及是否需要修改现有方案的结论。没有问题时，可以保留现有配置。

**本阶段不重复做：** 已有组件库与样式工具的安装接入、基础代码规范、手绘图标制作、完整业务页面、全量换肤、图片压缩平台或资源 CDN。

## 三、官方资料怎么用：先区分普通 Vite 和 uni App

### V2.02：CSS url() 与图片失败，分别定位和恢复

**具体需求：** 验证样式资源的路径重定位，同时确认图片组件失败反馈有实际效果。

**操作 B：失败与恢复。**

1. 保留一张正常图片作为对照，另一实例指向一个确定不存在的路径。
2. 观察失败文案、占位区域、页面高度和调试信息；CSS 背景失败不一定有可见提示，不能和 AppImage 的反馈混为一谈。

### V2.04：测单位、查颜色，确认现有样式实际一致

**具体需求：** 给已有单位换算与语义色建立证据，先确认问题，再做最小调整。

**操作 A：单位。**

1. 用 w-[200rpx] 的元素作对照，记录本页有效窗口宽度 W。
2. 按 rpx 的 750 宽基准推算该对照的逻辑尺寸：200 × W / 750。例如 W=375 时为 100 个逻辑 px；不把手机物理像素当逻辑 px。
3. 对 px-4、gap-2、text-sm 各选一处，检查本次 App CSS 的实际规则、变量与最终计算值。
4. 使用 App 调试器、元素测量能力或可比较的截图记录结果；必要时通过页面就绪后的 selector query 获取区域尺寸。
5. 有第二种窗口宽度时再对照；仅在一台手机测过，就写“一台”，不声称所有机型一致。
6. 如果输出保留 rem/calc()，继续检查根字号和最终尺寸，不因字符串没有 rpx 就直接判错；也不能因为配置有 rem2rpx:true 就直接判对。

前述尺寸推算以普通手机窗口及当前默认计算规则为前提；若项目另有 rpx 计算配置，应以实际规则为准。单位定义与换算参考 [uni-app 官方样式说明](https://uniapp.dcloud.net.cn/tutorial/syntax-css.html#尺寸单位)。

**操作 B：颜色。**

1. 对照 Tailwind 的 danger、SCSS 的 danger 与 TDesign 的错误色阶。
2. 先确认它们是相同语义还是不同场景。相同语义才统一事实来源；不同场景应明确名称与用途，不把整个色阶替换成一个值。
3. 本阶段不重新决定品牌色，不引入完整暗色主题或生成 design token 工具。
4. 修改必要颜色后，在实际使用该颜色的组件/测试区域复测；没有使用到的值不声称已显示验证。

**项目效益：** 后续页面不因同名变量来源不同而出现尺寸或颜色漂移。

- [ ] **验收：** 至少一个 rpx 对照和一个 Tailwind 间距有输入/产物/实测记录；danger 差异有处理结论。

### V2.05：一个真实图标，验证字体联网与离线

**具体需求：** 确认当前依赖是否能满足预期离线行为；源码有远程字体不等于已经证明离线一定失败。

6. 若产品确实要求首次离线也可用，而当前方案不满足，才按许可和包版本选择必要字体格式/图标资源本地化，并在项目层覆盖；不要改 node_modules。
