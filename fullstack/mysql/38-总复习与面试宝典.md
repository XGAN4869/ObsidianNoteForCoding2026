## 38.2 50 道面试题详解

### 基础 SQL（1-15题）

**题 1：WHERE 和 HAVING 的区别是什么？**

WHERE 在分组前过滤行，HAVING 在分组后过滤组。WHERE 不能使用聚合函数，HAVING 可以。WHERE 作用于原始数据行，HAVING 作用于 GROUP BY 后的组结果。执行顺序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT。

```sql
-- WHERE：过滤原始行
SELECT dept_id, COUNT(*) FROM employees WHERE salary > 10000 GROUP BY dept_id;

-- HAVING：过滤分组后的组
SELECT dept_id, COUNT(*) FROM employees GROUP BY dept_id HAVING COUNT(*) > 5;
```

**题 2：DELETE、TRUNCATE、DROP 的区别？**

| 特性 | DELETE | TRUNCATE | DROP |
|------|--------|----------|------|
| 类型 | DML | DDL | DDL |
| 删除内容 | 行（可 WHERE） | 所有行 | 整表（结构+数据） |
| 回滚 | 可回滚 | 不可回滚（隐含COMMIT） | 不可回滚 |
| 触发器 | 触发 | 不触发 | 不触发 |
| 自增计数 | 保留 | 重置 | N/A |
| 速度 | 慢（逐行日志） | 快（回收空间） | 快（元数据） |
| 空间回收 | 不释放 | 释放 | 释放 |

**题 3：CHAR 和 VARCHAR 的区别？**

CHAR(N) 是定长字符串，始终占用 N 个字符的存储空间。VARCHAR(N) 是变长字符串，实际占用 = 数据长度 + 1-2 字节长度前缀。CHAR 适合固定长度的编码（如 ISO 国家代码、MD5 哈希），VARCHAR 适合可变长度文本（如姓名、地址）。CHAR 最大 255 字符，VARCHAR 最大 16383 字节（实际受行大小限制）。CHAR 会自动截断尾随空格（PAD_CHAR_TO_FULL_LENGTH 模式下），VARCHAR 保留尾随空格。

**题 4：UNION 和 UNION ALL 的区别？**

UNION 会去重（内部使用临时表 + DISTINCT 排序），UNION ALL 保留所有行。当确定不存在重复行或重复可接受时，应该使用 UNION ALL（性能更好）。

```sql
-- UNION ALL：更快，不排序不去重
SELECT name FROM current_employees
UNION ALL
SELECT name FROM former_employees;

-- UNION：更慢，排序 + 去重
SELECT name FROM current_employees
UNION
SELECT name FROM former_employees;
```

**题 5：LEFT JOIN、RIGHT JOIN、INNER JOIN 的区别？**

- INNER JOIN：只返回两个表中匹配的行（交集）
- LEFT JOIN：返回左表所有行，右表无匹配的填 NULL
- RIGHT JOIN：返回右表所有行，左表无匹配的填 NULL
- CROSS JOIN：笛卡尔积（无 ON 条件）

**题 6：COUNT(*)、COUNT(1)、COUNT(col) 的区别？**

- COUNT(*) 和 COUNT(1)：完全等价，统计所有行数（包括 NULL 行）。优化器将 COUNT(1) 内部转换为 COUNT(*)。
- COUNT(col)：统计 col 列非 NULL 的行数。
- 性能：COUNT(*) 和 COUNT(1) 性能相同。MyISAM 对 COUNT(*) 有优化（存储了总行数），InnoDB 需要扫描索引。
- InnoDB 下 COUNT(*) 会选择最小的二级索引进行扫描。

**题 7：ON 和 WHERE 在 JOIN 中的区别？**

ON 是 JOIN 条件，决定如何匹配两表的行。WHERE 是整体过滤条件，在 JOIN 完成后过滤。对于 INNER JOIN，ON 和 WHERE 效果相同（优化器等价处理）。对于 LEFT/RIGHT JOIN，ON 和 WHERE 效果不同：ON 中的条件不影响左表（保留左表所有行），WHERE 中的条件会过滤所有结果行（可能排除左表行）。

```sql
-- LEFT JOIN：ON 不减少左表行
SELECT * FROM users u LEFT JOIN orders o
  ON u.id = o.user_id AND o.status = 'paid';

-- LEFT JOIN：WHERE 减少左表行（效果类似 INNER JOIN）
SELECT * FROM users u LEFT JOIN orders o
  ON u.id = o.user_id
WHERE o.status = 'paid';
```

**题 8：子查询和 JOIN 如何选择？**

现代 MySQL（5.6+）对子查询进行了大量优化（自动转换为 semi-join、materialization），许多子查询已经与 JOIN 等效。但一般建议：当查询只需要一个表的列时用子查询，需要多个表的列时用 JOIN。关联子查询在数据量大时性能差，应考虑改写为派生表或 JOIN。

**题 9：EXISTS 和 IN 的区别？**

多数情况下优化器会做等价转换。EXISTS 对子查询结果为 large 的场景更优（找到第一个匹配就停止），IN 对子查询结果为 small 的场景更友好。MySQL 8.0 对 IN 子查询优化（semi-join）后差异大大缩小。

**题 10：GROUP BY 和 DISTINCT 的区别？**

DISTINCT 用于去重，GROUP BY 用于分组聚合。在某些情况下它们可以达到相同结果。DISTINCT 本质上是 GROUP BY 所有 SELECT 列的特例。MySQL 内部实现上，DISTINCT 和 GROUP BY 使用相同的优化路径，性能差异很小。

**题 11：LIMIT 深分页为什么慢？如何优化？**

LIMIT 1000000, 10 需要扫描并丢弃前 100 万行。优化方法：（1）覆盖索引 + 延迟关联；（2）游标分页（基于 ID 的 "WHERE id > ?"）；（3）限制最大页数；（4）搜索引擎方案（Elasticsearch）。

**题 12：隐式类型转换如何导致索引失效？**

MySQL 将字符串和数字比较时，会把字符串转为数字。例如 `WHERE phone = 13800138000`（phone 是 VARCHAR），会触发隐式转换导致索引失效。应写为 `WHERE phone = '13800138000'`。

**题 13：ORDER BY 如何利用索引？**

当 ORDER BY 的列顺序与索引左前缀匹配时，MySQL 可以利用索引排序避免 filesort。例如 INDEX(a,b,c)，`ORDER BY a,b,c` 可以利用索引排序。如果 WHERE 中有 a=1 AND b=2，然后 ORDER BY c，也可以利用索引。

**题 14：SQL 语句的执行顺序是什么？**

FROM → ON → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT。理解执行顺序对查询优化至关重要。

**题 15：MySQL 有哪些类型的 JOIN？**

INNER JOIN（内连接）、LEFT JOIN（左外连接）、RIGHT JOIN（右外连接）、CROSS JOIN（交叉连接/笛卡尔积）、NATURAL JOIN（自然连接）、STRAIGHT_JOIN（强制左表为驱动表）。MySQL 不直接支持 FULL OUTER JOIN，但可以用 LEFT JOIN UNION RIGHT JOIN 实现。

### 索引（16-25题）

**题 16：B+Tree 索引的结构特点是什么？为什么 MySQL 使用 B+Tree 而不是 B-Tree？**

B+Tree 特点：（1）所有数据存储在叶子节点；（2）非叶子节点只存储键值；（3）叶子节点通过双向链表连接；（4）所有叶子节点在同一层。

B+Tree vs B-Tree：（1）B+Tree 非叶子节点不存储数据，单个节点可存更多键，树更矮；（2）B+Tree 叶子节点有链表，范围查询效率高（一次寻路，顺序遍历）；（3）B+Tree 的所有查询最终都到叶子节点，查询时间稳定 O(logN)。

**题 17：聚簇索引和二级索引的区别？**

聚簇索引（Clustered Index）：数据存储顺序与索引顺序一致。InnoDB 将数据和主键索引存在一起（数据即索引）。一个表只能有一个聚簇索引。

二级索引（Secondary Index）：叶子节点存储的是索引列+主键值。通过二级索引查询时，先找到主键值，再通过主键索引找到完整行数据（回表）。

```text
二级索引查找过程：二级索引 → 获取主键值 → 聚簇索引 → 获取完整行
覆盖索引：二级索引包含了所有需要的列 → 不需要回表
```

**题 18：什么是覆盖索引？它如何提升性能？**

覆盖索引是查询所需的所有列都包含在索引中，不需要回表。EXPLAIN 的 Extra = "Using index" 表示使用了覆盖索引。优势：（1）减少磁盘 I/O（不需要回表）；（2）减少 Buffer Pool 占用；（3）对 COUNT(*) 查询尤其有效。

**题 19：复合索引的左前缀原则是什么？举例说明。**

复合索引 (a, b, c) 的索引顺序是：先按 a 排序，a 相同按 b 排序，b 相同按 c 排序。要利用索引，查询条件必须从 a 开始。`WHERE a=1 AND b=2` 能用索引；`WHERE b=2` 不能用索引；`WHERE a=1 AND c=3` 能使用 a 列（但 c 不能）；`WHERE a=1 AND b>2 AND c=3` 能使用 a,b 列（范围后的 c 失效）。

**题 20：哪些操作会导致索引失效？（列举 5+ 种）**

1. 对索引列使用函数：`WHERE YEAR(created_at) = 2024`
2. 隐式类型转换：`WHERE varchar_col = 123`
3. LIKE 前导通配符：`WHERE name LIKE '%keyword'`
4. OR 连接无索引列：`WHERE indexed_col=1 OR unindexed_col=2`
5. 负向操作符：`!=`, `<>`, `NOT IN`, `NOT EXISTS`
6. 复合索引中范围查询中断：`WHERE a=1 AND b>10 AND c=5`
7. 在索引列上做运算：`WHERE id + 1 = 100`

**题 21：EXPLAIN 的 type 字段有哪些值？从小到大（性能从好到差）排列。**

system > const > eq_ref > ref > fulltext > ref_or_null > index_merge > unique_subquery > index_subquery > range > index > ALL。

- const：主键等值查询（最多一行）
- eq_ref：JOIN 中被驱动表的主键/唯一键等值查找
- ref：非唯一索引等值查找
- range：索引范围扫描
- index：全索引扫描（full index scan）
- ALL：全表扫描（full table scan）

**题 22：EXPLAIN 的 Extra 字段有哪些常见值？各代表什么？**

- Using index：覆盖索引（无需回表）-- 好
- Using where：Server 层对存储引擎返回的行进行额外过滤
- Using index condition：索引下推（ICP）-- 好
- Using filesort：需要额外排序 -- 可能需要优化
- Using temporary：需要临时表 -- 通常需要优化
- Using join buffer：JOIN 缓冲区不够用
- Impossible WHERE：WHERE 条件总是 false
- Select tables optimized away：MIN/MAX 直接通过索引获取

**题 23：什么是索引下推（Index Condition Pushdown / ICP）？**

MySQL 5.6+ 的特性。将 WHERE 条件中可以由索引判断的部分，下推到存储引擎层处理，减少回表次数。Extra = "Using index condition" 表示使用了 ICP。

```sql
-- INDEX(name, age)
SELECT * FROM users WHERE name LIKE '张%' AND age > 30;
-- 无ICP：通过索引找到所有 name LIKE '张%' 的行 → 全部回表 → Server过滤age
-- 有ICP：通过索引找到 name LIKE '张%' → 在索引中检查age>30 → 仅匹配的行回表
```

**题 24：如何选择索引的列和列顺序？**

选择列：WHERE 条件中经常用到的列、JOIN 的关联列、ORDER BY 和 GROUP BY 的列。

选择顺序：（1）等值条件列排前面，范围条件列排后面；（2）选择性高的列排前面（选择性 = DISTINCT值数/总行数）；（3）考虑查询频率，频率最高的查询应被索引覆盖。

**题 25：什么是前缀索引？为什么和如何使用？**

前缀索引只索引字符串列的前 N 个字符，节省索引空间。`CREATE INDEX idx_email_prefix ON users(email(10))`。需要选择合适的前缀长度：既足够区分数据，又不过长。使用 `SELECT COUNT(DISTINCT LEFT(col, N))/COUNT(*) FROM table` 来评估选择性。

### 事务与锁（26-35题）

**题 26：事务的 ACID 特性分别是什么？**

- Atomicity（原子性）：事务中所有操作要么全成功要么全失败。通过 Undo Log 回滚实现。
- Consistency（一致性）：事务前后数据保持一致状态。由其他三个特性共同保证。
- Isolation（隔离性）：并发事务间互不干扰。通过锁 + MVCC 实现。
- Durability（持久性）：已提交的事务数据永久保存。通过 Redo Log 实现。

**题 27：MySQL 的四种事务隔离级别是什么？各解决了什么问题？**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 默认 |
|---------|------|-----------|------|------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | |
| READ COMMITTED | 解决 | 可能 | 可能 | |
| REPEATABLE READ | 解决 | 解决 | 可能(大部分解决) | InnoDB默认 |
| SERIALIZABLE | 解决 | 解决 | 解决 | |

- 脏读：读到其他事务未提交的数据
- 不可重复读：同一事务两次读取同一行，返回的数据不同
- 幻读：同一事务两次范围查询，返回的行数不同

InnoDB 的 REPEATABLE READ 通过 MVCC + Next-Key Lock 大大减少了幻读（但仍存在极端场景）。

**题 28：MVCC 的原理是什么？InnoDB 如何实现 MVCC？**

MVCC（Multi-Version Concurrency Control）允许多个事务看到数据的不同版本。

InnoDB 实现：（1）每行数据有两个隐藏列：DB_TRX_ID（最近修改的事务ID）和 DB_ROLL_PTR（指向 Undo Log 的回滚指针）；（2）Undo Log 形成版本链；（3）ReadView（快照）在事务开始时创建（RR级别）或每次读取时创建（RC级别）；（4）ReadView 通过判断事务ID的可见性，确定看到哪个版本。

**题 29：什么是快照读和当前读？**

- 快照读（Snapshot Read）：读取数据的快照版本，不加锁。普通 SELECT 是快照读。
- 当前读（Current Read）：读取最新版本并加锁。SELECT ... FOR UPDATE、SELECT ... LOCK IN SHARE MODE、UPDATE、DELETE 都是当前读。

```sql
-- 快照读（无锁）
SELECT * FROM accounts WHERE id = 1;

-- 当前读（加锁）
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- 排他锁
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;  -- 共享锁
```

**题 30：InnoDB 有哪些锁类型？**

- 行级锁：Record Lock（记录锁）、Gap Lock（间隙锁）、Next-Key Lock（临键锁 = 记录锁 + 间隙锁）
- 表级锁：意向共享锁（IS）、意向排他锁（IX）
- 行锁模式：共享锁（S）、排他锁（X）
- 其他：AUTO-INC 锁（自增锁）

Next-Key Lock 是 InnoDB 的默认行锁算法，锁定索引记录和它之前的间隙，用于在 REPEATABLE READ 级别下防止幻读。

**题 31：什么是死锁？如何预防和排查？**

死锁是两个或多个事务相互等待对方持有的锁，形成循环等待。

排查：（1）SHOW ENGINE INNODB STATUS 查看 LATEST DETECTED DEADLOCK 部分；（2）设置 innodb_print_all_deadlocks=ON 将死锁信息写入错误日志。

预防：（1）按相同顺序访问资源；（2）缩短事务（锁持有时间越短越好）；（3）使用低隔离级别（RC 可减少间隙锁）；（4）添加合理的索引（减少锁范围）。

**题 32：乐观锁和悲观锁的区别？各适用于什么场景？**

- 乐观锁：假设冲突很少，操作时不加锁，只在更新时检查版本号（CAS）。适合读多写少场景。
- 悲观锁：假设冲突频繁，操作前先加锁。适合写多冲突高的场景。

```sql
-- 乐观锁（版本号）
UPDATE products SET stock = stock - 1, version = version + 1
WHERE id = ? AND stock >= ? AND version = ?;

-- 悲观锁
SELECT stock FROM products WHERE id = ? FOR UPDATE;
UPDATE products SET stock = stock - 1 WHERE id = ?;
```

**题 33：InnoDB 的 Redo Log 和 Undo Log 分别是什么作用？**

Redo Log：（1）记录数据页的物理修改；（2）保证持久性（崩溃恢复）；（3）WAL 机制：先写 Redo Log，后刷数据页；（4）循环写（固定大小）。

Undo Log：（1）记录数据修改前的版本；（2）支持事务回滚；（3）支持 MVCC（提供历史版本）；（4）Purge 线程异步清理。

**题 34：Binary Log（Binlog）和 Redo Log 的区别？**

| 特性 | Binlog | Redo Log |
|------|--------|----------|
| 所属层级 | Server 层 | InnoDB 引擎层 |
| 记录内容 | 逻辑 SQL / 行变更 | 物理页修改 |
| 主要用途 | 复制、PITR | 崩溃恢复 |
| 写入方式 | 追加写 | 循环写 |
| 文件大小 | 自动切换（max_binlog_size） | 固定大小 |

**题 35：什么是两阶段提交（Two-Phase Commit）？**

MySQL 使用两阶段提交确保 Binlog 和 Redo Log 的一致性：（1）Prepare 阶段：写入 Redo Log，标记为 prepare 状态；（2）写入 Binlog；（3）Commit 阶段：Redo Log 标记为 commit 状态。这样确保崩溃恢复时，可以通过检查 Binlog 来确定事务是否应该提交。

### 性能优化（36-45题）

**题 36：InnoDB 的 COUNT(*) 为什么慢？如何优化？**

InnoDB 不支持行数缓存（MyISAM 可以）。因为 MVCC 的存在，不同事务看到的不同行数。COUNT(*) 必须扫描索引。优化：（1）统计近似值用 information_schema.TABLES 的 TABLE_ROWS；（2）用计数器表维护计数；（3）业务上只显示近似值。

**题 37：如何优化大表分页？**

方法一（覆盖索引+延迟关联）：`SELECT t1.* FROM t t1 JOIN (SELECT id FROM t ORDER BY id LIMIT 1000000, 20) t2 ON t1.id = t2.id`。

方法二（游标分页）：`SELECT * FROM t WHERE id > last_id ORDER BY id LIMIT 20`。

方法三：限制最大页数 + 结合搜索引擎方案。

**题 38：ORDER BY + LIMIT 如何优化？**

如果 ORDER BY 列有索引且匹配左前缀，可以利用索引排序（无 filesort）。当 WHERE + ORDER BY + LIMIT 组合时：如果 WHERE 等值 + ORDER BY 匹配索引左前缀，Extra 不出现 filesort。如果 WHERE 范围 + ORDER BY 匹配索引，也可以利用索引排序。

**题 39：为什么 SELECT * 不好？**

（1）无法使用覆盖索引（必须回表）；（2）传输无用数据（网络开销）；（3）排序和临时表的开销更大；（4）破坏表的封装（新加列影响现有查询）；（5）无法利用索引优化器可能选择错误。

**题 40：innodb_buffer_pool_size 应该设多大？为什么重要？**

专用数据库服务器：物理内存的 50%-70%。Buffer Pool 缓存了数据页和索引页，是 InnoDB 最重要的性能参数。太小则频繁磁盘 I/O，太大则 OS SWAP。通过 `SHOW STATUS LIKE 'Innodb_buffer_pool_read%'` 计算命中率，应保持 >99%。

**题 41：EXPLAIN 中 Using temporary 和 Using filesort 是什么意思？需要优化吗？**

Using filesort：MySQL 无法利用索引排序，需要额外的排序操作。Using temporary：MySQL 需要创建临时表来处理查询（通常是 GROUP BY 或 DISTINCT）。两者同时出现通常意味着查询需要优化（加索引）。单独出现且数据量小可以接受，大表必须优化。

**题 42：慢查询优化的标准流程是什么？**

（1）从慢查询日志/监控发现慢 SQL；（2）使用 EXPLAIN 分析执行计划；（3）定位瓶颈（全表扫描？filesort？temporary？）；（4）优化（加索引/改查询/改表结构）；（5）EXPLAIN 验证优化效果；（6）实际执行时间对比；（7）生产灰度验证。

**题 43：如何做 JOIN 优化？**

（1）确保被驱动表的 JOIN 列有索引；（2）驱动表应该小（优化器通常自动选择）；（3）尽量减少 JOIN 前的数据量；（4）使用合适的数据类型（JOIN 列类型相同）；（5）考虑在 JOIN 前用子查询减少数据量；（6）避免笛卡尔积。

**题 44：innodb_flush_log_at_trx_commit 参数的含义和选择？**

0：每秒刷 Redo Log，最快但崩溃丢 1 秒数据。
1：每次 commit 都刷，最安全（ACID 持久性）但最慢。
2：每次 commit 写入 OS，每秒刷磁盘。MySQL 崩溃不丢，OS 崩溃丢 1 秒。

选择：金融/订单场景选 1；大多数互联网业务可选 2（需保证 OS 不 crash）。

**题 45：MySQL 8.0 相比 5.7 有哪些重要新特性？**

（1）窗口函数（ROW_NUMBER, RANK, DENSE_RANK, LAG/LEAD）；（2）CTE 和递归 CTE；（3）降序索引；（4）原子 DDL；（5）不可见索引；（6）角色管理；（7）caching_sha2_password 默认认证；（8）JSON 增强（JSON_TABLE, JSON_ARRAYAGG 等）；（9）CHECK 约束真正生效；（10）默认字符集 utf8mb4。

### 架构与设计（46-50题）

**题 46：数据库读写分离的架构是什么？如何应对复制延迟？**

架构：Master 处理写操作，Slave(s) 处理读操作。通过中间件（ProxySQL）或应用层路由实现。

应对复制延迟：（1）刚写入后的读强制走 Master；（2）版本号/token 跟踪（Redis 缓存 "刚写入" 的 key）；（3）监控 Seconds_Behind_Master，延迟过高时切回 Master 读；（4）业务上容忍短暂不一致。

**题 47：数据库分库分表有哪些策略？各有什么优缺点？**

垂直拆分（按业务模块）：user_db, order_db, product_db。优点：清晰、易管理。缺点：跨库 JOIN 困难。

水平拆分（按数据行）：user_0-user_7，按 user_id % 8。优点：扩展性好。缺点：跨片查询复杂、全局唯一 ID 生成困难、事务跨分片不可用。

分表：单表数据量过大（>5000 万行）时将一张表拆为多张相同结构的物理表。

**题 48：分区的类型有哪些？各适用于什么场景？**

RANGE（按范围）：时间序列数据（订单按年/月）
LIST（按列表）：离散分类数据（按国家/地区）
HASH（按哈希）：均匀分布（按 user_id 哈希）
KEY（按 MySQL 内部哈希）：类似 HASH，适用于非整型列

**题 49：GTID 复制相比传统复制有什么优势？**

GTID 每个事务有全局唯一 ID。优势：（1）故障切换时自动找位置（不需要手动指定 binlog 文件+位置）；（2）简化复制拓扑变更；（3）复制错误时可以精确定位到事务；（4）更可靠的数据一致性保证。

**题 50：如何设计一个高可用的 MySQL 架构？**

（1）主从复制（1 主 + N 从）保证数据冗余；（2）读写分离提升读性能；（3）自动故障切换（Orchestrator / MHA / InnoDB Cluster）；（4）定期备份 + binlog PITR；（5）监控告警（PMM / Prometheus + Grafana）；（6）连接池 + 限流保护；（7）缓存层（Redis）减少数据库压力；（8）最终：MySQL Group Replication + InnoDB Cluster 实现原生高可用。
