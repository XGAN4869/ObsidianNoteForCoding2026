## 一句话先看懂整条链路

  

这个定位模块的完整流程其实是：

  

1. 页面初始化，恢复上次车辆定位状态

2. 父组件统一维护定位相关数据

3. 子组件只负责展示“人员模式 / 车辆模式”

4. 如果切到车辆模式，先加载车辆列表

5. 用户选车后，提交“开启车辆定位”

6. 扫码打卡时，再根据后端返回的分界时间判断当前应该继续定位还是关闭定位

7. 页面退出时把关键状态缓存起来，下次再回来做回显

  

如果你能把上面 7 步讲顺，这块业务你就真的懂了。

## 第一段：页面一进来，先不是点按钮，而是先把状态准备好

  

这一段对应知识点：

  

- `1. 数据统一管理`

- `4. 派生数据使用 computed`

- `7. 初始化与回显逻辑分离`

  

代码位置：[index.vue](/E:/Work1/hzlt/Private/614/travel-web/sites/uniapp/src/packageAttendance/attendance/index.vue:115)

  

```vue

const accountStore = useAccountStore();

const vehicleOptions = ref(buildVehicleSelectOptions([]));

const selectedVehicle = ref(null);

const vehicleActive = ref(false);

const vehicleLoading = ref(false);

const vehicleSubmitting = ref(false);

const loadedVehicleDriverId = ref('');

  

const displayUserName = computed(() => (

  accountStore.accountRealName

  || accountStore.accountInfo?.realName

  || accountStore.accountInfo?.accountName

  || accountStore.accountInfo?.name

  || '用户'

));

  

const personLocationTarget = computed(() => resolvePersonLocationTarget(

  accountStore.accountInfo,

  accountStore.isTempWorker

));

```

  

### 这里在做什么

  

页面刚进来，先把“整个定位模块真正要记住的状态”统一放在父组件。

  

这些状态分别表示：

  

- `vehicleOptions`

  当前车辆下拉数据

- `selectedVehicle`

  当前选中的车辆

- `vehicleActive`

  当前是不是车辆定位中

- `vehicleLoading`

  车辆列表是否在加载

- `vehicleSubmitting`

  车辆开关定位是否在提交

- `loadedVehicleDriverId`

  当前司机的车辆列表有没有加载过

  

### 为什么这一步很重要

  

因为后面的所有逻辑都依赖这些状态：

  

- 子组件展示靠它

- 校验靠它

- 提交靠它

- 回显靠它

  

如果这些状态不统一放在父组件，而是东一块西一块，后面定位流程一定会乱。

  

### 这一段怎么体现 1 和 4

  

这里有一个最关键的区分：

  

- `ref` 保存的是“原始状态”

- `computed` 保存的是“根据原始状态算出来的展示值或业务值”

  

比如：

  

- `selectedVehicle` 是原始状态，因为用户确实选了一辆车

- `displayUserName` 是派生数据，因为它是从多个字段兜底算出来的

- `personLocationTarget` 也是派生数据，因为它不是后端原样给你的，而是你前端加工出来的定位对象

  

你以后手撕任何页面，第一步都先分清这两个层次。

## 第二段：页面进入时先恢复数据，退出时再保存数据

  

这一段对应知识点：

  

- `1. 数据统一管理`

代码位置：[index.vue](/E:/Work1/hzlt/Private/614/travel-web/sites/uniapp/src/packageAttendance/attendance/index.vue:159)

  

```vue

onLoad(() => {

  const cache = uni.getStorageSync(VEHICLE_STATE_KEY)
```

### 这里在做什么

- 从缓存里拿上次状态

- 恢复车辆列表

- 恢复选中的车

- 恢复车辆定位状态

- 把这些关键状态再存回去

  

### 为什么要单独讲这段

  

因为很多新手会把“初始化”和“回显”混在一起。

  

其实它们是两层：

  

1. 父组件负责初始化

   也就是“把旧数据拿回来”

2. 子组件负责回显

   也就是“把拿回来的数据展示到界面上”

  

这就是 `初始化与回显逻辑分离` 的真正意思。

因为这里形成了稳定契约：

  

- 输入永远是 `props`

- 输出永远是 `emits`

  

只要这个契约清楚，组件就不会乱。

  

你手撕时也可以固定这样想：

  

1. 父组件是“业务指挥中心”

2. 子组件是“展示和交互面板”

## 第四段：人员模式和车辆模式切换，本质是一个小状态机

  

这一段对应知识点：

  

- `2. 模板绑定保持一致`

- `4. 派生数据使用 computed`

- `5. 字段联动使用 watch`

- `6. 校验规则集中管理`

  

代码位置：[AttendanceLocationSelector.vue](/E:/Work1/hzlt/Private/614/travel-web/sites/uniapp/src/packageAttendance/attendance/components/AttendanceLocationSelector.vue:136)

  

```vue

const currentMode = ref(PERSON_MODE);

const selectedVehicleValue = ref('');

  

const submitDisabled = computed(() => props.submitting || !currentVehicle.value);

const personDisplayText = computed(() => props.personalName || props.personLabel || '未获取到人员账号');

  

function selectPersonMode() {

  if (shouldBlockPersonModeSwitch(props.vehicleActive)) {

    emit('personBlocked');

    return;

  }

  

  currentMode.value = PERSON_MODE;

  emit('modeChange', PERSON_MODE);

}

  

function selectVehicleMode() {

  if (props.isTempWorker) {

    return;

  }

  

  currentMode.value = VEHICLE_MODE;

  emit('modeChange', VEHICLE_MODE);

}

```

  

### 这里在做什么

  

这块不是单纯切 tab，而是在维护一个“模式状态机”。

  

当前只有两种模式：

  

- `person`

- `vehicle`

  

切模式时不是无脑切，而是带业务规则：

  

- 如果当前车辆定位还开着，不能切回人员模式

- 如果当前是临时工，不能进入车辆模式

  

### 这里体现了什么

  

先看 `computed`：

  

- `submitDisabled`

  是根据“是否提交中 + 是否选中车”算出来的

- `personDisplayText`

  是根据姓名和账号兜底出来的

  

再看校验：

  

- `shouldBlockPersonModeSwitch(props.vehicleActive)`

  就是在集中做业务限制

  

也就是说，模式切换不是 UI 问题，而是“UI + 状态 + 规则”共同决定的。

## 第五段：为什么这里要有那么多 `watch`

  

这一段对应知识点：

  

- `5. 字段联动使用 watch`

- `7. 初始化与回显逻辑分离`

  

代码位置：[AttendanceLocationSelector.vue](/E:/Work1/hzlt/Private/614/travel-web/sites/uniapp/src/packageAttendance/attendance/components/AttendanceLocationSelector.vue:229)

  

```vue

watch(

  () => props.selectedVehicle,

  (vehicle) => {

    const nextValue = String(vehicle?.licensePlate || '').trim();

  

    if (selectedVehicleValue.value !== nextValue) {

      selectedVehicleValue.value = nextValue;

    }

  

    if (nextValue || props.vehicleActive) {

      currentMode.value = VEHICLE_MODE;

    }

  },

  { immediate: true }

);

```

  

### 这里在做什么

  

父组件一旦恢复了缓存，或者重新设置了 `selectedVehicle`，子组件不能装作不知道。

  

这时候就要用 `watch` 做联动：

  

- 父组件选中的车变了，子组件的 picker 选中值也同步变化

- 父组件说当前已经在车辆定位，子组件就自动切到车辆模式

- 页面重新进入时，子组件能根据父组件状态自动回显

  

### 为什么不用 `computed`

  

因为这里不仅仅是“算一个值”，还要：

  

- 改变子组件内部状态

- 触发模式切换

- 必要时清空选择

  

这就是典型的 `watch` 场景。

  

### 这类联动你要会总结

  

这个子组件里至少有 4 类联动：

  

1. `props.selectedVehicle` 变了，更新 `selectedVehicleValue`

2. `props.isTempWorker` 变了，强制回到人员模式

3. `vehicleOptions` 变了，如果原来选中的车没了，就清空

4. `props.vehicleActive` 变了，决定是否保留车辆模式和选中值

  

所以你以后看到多个 `watch`，不要觉得乱，要先问：

  

“它是不是在做字段联动和回显同步？”

  

如果是，那通常就是合理的。

## 第六段：车辆列表不是直接拿来就用，要先做规则加工

  

这一段对应知识点：

  

- `3. 配置常量单独抽离`

- `4. 派生数据使用 computed`

- `6. 校验规则集中管理`

  

代码位置：[attendance-location-options.js](/E:/Work1/hzlt/Private/614/travel-web/sites/uniapp/src/packageAttendance/attendance/attendance-location-options.js:20)

  

```js

export function resolveDriverId(accountInfo = {}) {

  return normalizeValue(accountInfo?.vehicleEntities?.[0]?.driverId);

}

  

export function resolvePersonLocationTarget(accountInfo = {}, isTempWorker = false) {

  return {

    entityId: isTempWorker

      ? normalizeValue(accountInfo?.phone)

      : normalizeValue(accountInfo?.user),

    type: 2,

  };

}

  

export function buildVehicleSelectOptions(vehicles = []) {

  const vehicleOptions = (Array.isArray(vehicles) ? vehicles : [])

    .map(normalizeVehicle)

    .filter(Boolean)

    .map((vehicle) => ({

      label: vehicle.licensePlate,

      value: vehicle.licensePlate,

      vehicle,

    }));

```

  

### 这里在做什么

  

这里把“接口原始数据”和“页面真正要用的数据”拆开了。

  

它解决了 3 件事：

  

1. 司机 ID 从哪里取

2. 人员定位目标到底取哪个字段

3. 车辆接口返回的数据如何变成 picker 需要的 `label/value`

  

### 为什么这一步一定要抽文件

  

如果这些规则都写在页面里，会出现两个问题：

  

1. 页面里到处都是 `accountInfo?.xxx?.yyy`

2. 一旦字段改名，你要全页面搜着改

  

抽到单独文件后，页面只关心：

  

- 我要司机 ID

- 我要人员定位对象

- 我要车辆 options

- 我要提交 payload

  

这就是 `配置常量单独抽离` 更深一层的意义：

  

不是只抽“常量字符串”，而是把规则和映射抽成独立模块。

这一段对应知识点：

  

- `1. 数据统一管理`

- `6. 校验规则集中管理`

  

代码位置：[index.vue](/E:/Work1/hzlt/Private/614/travel-web/sites/uniapp/src/packageAttendance/attendance/index.vue:315)

  

```vue

async function loadVehicleOptions(force = false) {

  if (accountStore.isTempWorker) {

    vehicleOptions.value = buildVehicleSelectOptions([]);

    return;

  }

  

  const driverId = resolveDriverId(accountStore.accountInfo);

  

  if (!driverId) {

    vehicleOptions.value = buildVehicleSelectOptions([]);

    return;

  }

  

  if (!force && loadedVehicleDriverId.value === driverId) {

    return;

  }

  

  vehicleLoading.value = true;

  

  try {

    const vehicles = await apiGetCars({ driverId }, false);

    vehicleOptions.value = buildVehicleSelectOptions(vehicles);

    loadedVehicleDriverId.value = driverId;

  } finally {

    vehicleLoading.value = false;

  }

}

```

  

### 这里在做什么

  

用户切到车辆模式后，父组件才决定要不要加载车辆。

  

这个函数里有 4 层判断：

  

1. 临时工直接没有车辆列表

2. 没有司机 ID 也没有车辆列表

3. 当前司机的车辆已经加载过就不重复请求

4. 真正满足条件后才发接口

  

### 这一段为什么非常值得学

  

因为这就是标准的“前置校验 + 异步加载 + 缓存复用”写法。

  

新手常见错误是：

  

- 一切模式就立刻无脑请求

- 不判断临时工

- 不判断有没有司机 ID

- 不判断是否已经加载过

  

而这里写法很稳，说明作者在控制无效请求。

## 第八段：开启车辆定位，真正的业务顺序是什么

  

这一段对应知识点：

  

- `6. 校验规则集中管理`

- `8. 提交流程固定规范`

- `1. 数据统一管理`

  

代码位置：[index.vue](/E:/Work1/hzlt/Private/614/travel-web/sites/uniapp/src/packageAttendance/attendance/index.vue:440)

  

```vue

async function handleSubmitVehicle(vehicle) {

  const vehiclePayload = buildVehicleStatusPayload(vehicle || selectedVehicle.value, 1);

  

  if (!vehiclePayload) {

    showToast('请选择运营车辆');

    return;

  }

  

  if (vehicleSubmitting.value) {

    return;

  }

  

  result = await submitVehicleLocationFlow({

    vehiclePayload,

    startVehicleLocation,

    saveVehicleStatus: async(payload) => {

      vehicleSubmitting.value = true;

      return apiModifyCarStatus(payload, true);

    },

    stopVehicleLocation: () => stopAttendanceLocation(),

  });

}

```

  

### 这里在做什么

  

开启车辆定位并不是一个动作，而是三步：

  

1. 先校验有没有车、是不是重复提交

2. 先尝试开启定位能力

3. 再把车辆状态提交给后端

  

如果只看页面函数，你会觉得长。

但如果你按“流程步骤”去看，就很清楚。

  

### 这一步为什么要先开定位再调后端

  

因为如果先告诉后端“车辆定位开启了”，但手机实际上没有定位权限，那状态就假了。

  

所以这里的顺序必须是：

  

1. 本地先确认定位能开

2. 确认能开后，再保存后端状态

  

这就是业务正确性。

## 第九段：为什么提交流程要单独拆成 flow 函数

  

这一段对应知识点：

  

- `8. 提交流程固定规范`

- `6. 校验规则集中管理`

  

代码位置：[attendance-vehicle-submit.js](/E:/Work1/hzlt/Private/614/travel-web/sites/uniapp/src/packageAttendance/attendance/attendance-vehicle-submit.js:1)

  

```js

export async function submitVehicleLocationFlow(options = {}) {

  const {

    vehiclePayload,

    startVehicleLocation,

    saveVehicleStatus,

    stopVehicleLocation,

  } = options;

  

  const locationStarted = await startVehicleLocation(vehiclePayload);

  

  if (!locationStarted) {

    return {

      locationStarted: false,

      vehicleSaved: false,

    };

  }

  

  try {

    await saveVehicleStatus(vehiclePayload);

  

    return {

      locationStarted: true,

      vehicleSaved: true,

    };

  } catch (error) {

    await stopVehicleLocation?.();

    throw error;

  }

}

```

  

### 这里在做什么

  

这个 flow 把“车辆定位开启”做成了一个固定模板：

  

1. 先执行第一步副作用

   `startVehicleLocation`

2. 第一步没成功就直接结束

3. 第一步成功才走第二步提交

   `saveVehicleStatus`

4. 第二步失败时执行补偿回滚

   `stopVehicleLocation`

  

### 这一段是整篇最值得背的

  

因为这就是标准的异步提交流程模板：

  

1. `校验`

2. `开始动作`

3. `保存结果`

4. `失败回滚`

5. `最终收尾`

  

以后你写提交、支付、授权、上传、切换状态，都能套这套思路。

## 第十二段：时间比较规则被单独抽出去，是为了让判断更清晰

  

这一段对应知识点：

  

- `3. 配置常量单独抽离`

- `6. 校验规则集中管理`

  

代码位置：[attendance-clock-location.js](/E:/Work1/hzlt/Private/614/travel-web/sites/uniapp/src/packageAttendance/attendance/attendance-clock-location.js:7)

  

```js

export function getClockLocationCompareInfo(separateTime, currentTime) {

  const separateSeconds = parseClockTimeToSeconds(separateTime);

  const currentSeconds = parseClockTimeToSeconds(currentTime);

  

  return {

    separateTime,

    currentTime,

    separateSeconds,

    currentSeconds,

    isAfterSeparateTime: separateSeconds < currentSeconds,

  };

}

  

export function resolveClockLocationTargetAction(separateTime, currentTime, options = {}) {

  const { vehicleActive = false } = options;

  const { isAfterSeparateTime } = getClockLocationCompareInfo(separateTime, currentTime);

  

  if (isAfterSeparateTime) {

    return vehicleActive ? 'stop-vehicle' : 'stop-person';

  }

  

  return vehicleActive ? 'keep-vehicle' : 'start-person';

}

```

  

### 这里在做什么

  

这里把“时间比较”和“动作决策”从页面里抽了出来。

  

逻辑其实很简单：

  

- 如果当前时间已经晚于分界时间

  就关闭定位

- 如果当前时间还没到分界时间

  就继续定位或开启定位

  

但是因为还要结合 `vehicleActive` 判断，所以最终动作会分成 4 种：

  

1. `stop-vehicle`

2. `stop-person`

3. `keep-vehicle`

4. `start-person`

  

### 为什么单独抽出来是好事

  

因为这类判断一旦写在页面里，很快就会变成一大串 if else。

  

抽出去后，页面只看结果：

  

- 你告诉我下一步动作是什么

- 我负责执行它

  

这就是“判断”和“执行”的职责分离。

### 这里在做什么

  

关闭车辆定位也不是一句 `stop()` 就完事。

  

它同样有固定顺序：

2. 没拿到就直接拦住

3. 调后端更新车辆状态为关闭

2. 本地运行时要不要停

3. 页面状态要不要清空

4. 缓存要不要更新

  

这就是完整思路。

## 第十四段：把 1-8 真正串成一条线

  

如果你还是觉得 1-8 容易散，可以直接背这一条主线：

  

1. `先做数据统一管理`

   父组件先把定位模块要记住的状态都收口。

2. `再保持模板绑定一致`

   父组件传 `props`，子组件抛 `emits`，明确谁管业务、谁管展示。

3. `再把配置和规则抽离`

   司机 ID、人员定位对象、车辆 options、提交 payload、时间判断都单独放工具文件。

4. `再把派生数据改成 computed`

   用户名、人员定位目标、当前选中车辆、按钮禁用态、状态文案都从已有状态计算。

5. `再用 watch 做字段联动`

   父组件恢复数据后，子组件自动回显；模式变化后自动同步展示。

6. `再集中写校验规则`

   临时工不能切车辆模式、没车不能提交、重复提交要拦、没定位对象要拦。

7. `再拆开初始化和回显`

   父组件负责拿旧状态，子组件负责把旧状态显示到界面。

8. `最后按固定规范写提交流程`

   校验 -> 开启定位 -> 保存后端 -> 失败回滚 -> 统一收尾。

  

这才是这 8 条真正的串联方式。

## 第十五段：你以后手撕时，固定按这个顺序写

  

### 第 1 步：先写业务流程，不要先写页面

  

先用中文列出来：

  

1. 页面进来要恢复什么

2. 用户会点哪些按钮

3. 每个按钮成功后会发生什么

4. 每个按钮失败后要怎么收尾

  

### 第 2 步：再列原始状态

  

问自己：

  

- 哪些值是页面必须记住的

- 哪些值会影响多个动作

- 哪些值要跨页面进出保留

  

这些才放 `ref/reactive`。

  

### 第 3 步：再列派生状态

  

问自己：

  

- 这个值是不是根据别的值算出来的

  

如果是，就尽量用 `computed`，不要重复存。

  

### 第 4 步：拆父子组件职责

  

问自己：

  

- 哪些逻辑必须由父组件处理

- 子组件是不是只负责展示和抛事件

  

### 第 5 步：抽公共规则函数

  

把下面这类东西抽出去：

  

- 字段归一化

- options 转换

- payload 组装

- 时间比较

- 动作决策

  

### 第 6 步：补字段联动

  

问自己：

  

- 父组件状态变化后，子组件要不要同步

- 切模式后，要不要刷新列表

- 数据失效后，要不要自动清空

  

这时候才写 `watch`。

  

### 第 7 步：最后写异步提交流程

  

固定顺序：

  

1. 前置校验

2. 开始动作

3. 调接口提交

4. 失败回滚

5. 收尾提示

  

### 第 8 步：最后检查边界

  

这块业务至少要检查：

  

- 临时工

- 没司机 ID

- 没车辆

- 定位权限拒绝

- 接口失败

- 重复点击

- 页面退出后重进
