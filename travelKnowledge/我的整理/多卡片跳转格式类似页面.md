## 第 2 步：列表初始化、刷新、分页，全部围绕一个 fetch 函数收口

这一段重点体现的是：

- `8. 提交流程固定规范`

## 第 5 步：创建提交时，字段校验、参数清洗、loading、成功回调，是一条标准提交流程

  

核心函数是 `handleSubmit`，[ComplaintCreateForm.vue:124](E:/Work1/hzlt/Private/614/travel-web/sites/uniapp/src/packageOther/customer-complaint/ComplaintCreateForm.vue:124)。

  

这段逻辑非常适合背下来：

3. 校验 `contact` 是否为空。

## 第 12 步：详情成功后，不是直接操作列表，而是通过 storage 标记回页刷新

## 把 1-8 再映射回整条主链路

  

如果你觉得上面逻辑很多，可以直接按下面这套“知识点在流程里的落点”去记。

  

### 1. 数据统一管理

  

出现位置：

  

- 列表页把 `complaintList / pager / loading / activeTab` 分开管

- 创建页把 `formData / deptOptions / selectedDeptIndex / submitLoading` 分开管

- 详情页把 `currentComplaint / records / formData / previewImageUrl / 多个 loading` 分开管

  

一句话理解：

  

同一类数据只放一个地方，不让“表单数据、展示数据、loading 数据、配置数据”搅在一起。

  

### 2. 模板绑定保持一致

  

出现位置：

  

- 列表页模板只读 `activeTab / complaintList / loading / finished`

- 创建页输入统一读写 `formData.xxx`

- 详情页模板主要读 `displayComplaint / records / 各种 computed 状态`

  

一句话理解：

  

模板只绑定状态，不承担复杂业务计算。

  

### 3. 配置常量单独抽离

  

出现位置：

  

- `COMPLAINT_LIST_REFRESH_KEY`

- `COMPLAINT_CREATE_ORDER_PERMISSION`

- `COMPLAINT_STATUS`

- `PENDING_CLOSE_STATUS_NAMES`

- `FINISHED_STATUS_NAMES`

- `COS_CONFIG`

  

一句话理解：

  

凡是会重复出现、带业务含义、以后可能变的值，都不要散落在逻辑里。

  

### 4. 派生数据使用 `computed`

  

出现位置：

  

- 列表页 `finished`

- 创建页 `selectedDeptName`

- 详情页 `displayComplaint / complaintId / hasFinalResult / dialogStatus / latestResultRecord / isProcessingStatus / baseInfoList / showComplaintProcessingPermissionMask`

  

一句话理解：

  

能从已有数据算出来的值，就不要再手动维护一份状态。

  

### 5. 字段联动使用 `watch`

  

出现位置：

  

- 详情弹窗里 `props.complaint -> currentComplaint`

- `complaintId -> resetForm + fetchRecords`

  

补充理解：

  

- 创建页虽然没写 `watch`，但 `handleDeptChange -> assignedDeptId -> selectedDeptName` 也是联动思维

  

一句话理解：

  

当一个字段变化会带来“重新拉接口、重置表单、同步副本”这种副作用时，用 `watch` 或明确的事件链来处理。

  

### 6. 校验规则集中管理

  

出现位置：

  

- 创建页：`handleSubmit`

- 详情页普通保存：`handleSaveRecord`

- 详情页结案提交：`handleSubmitResult`

- 详情页底层公共校验：`validateComplaintId + submitRecord`

  

一句话理解：

  

把校验集中在提交入口附近，不要把规则拆得到处都是。

  

### 7. 初始化与回显逻辑分离

  

出现位置：

  

- 列表首次加载、回页刷新、下拉刷新、上拉分页分开，但都走统一 fetch

- 详情页先吃路由参数，再拉完整详情

- 返回列表时通过 storage 标记触发刷新

  

一句话理解：

  

初始化、回显、刷新，三件事要分清入口，但可以共用底层函数。

  

### 8. 提交流程固定规范

  

出现位置：

  

- 创建提交 `handleSubmit`

- 附件上传 `uploadSelectedImage`

- 普通保存 `handleSaveRecord -> submitRecord`

- 结果提交 `handleSubmitResult -> submitRecord`

  

固定模板：

  

1. 防重

2. 校验

3. 组装参数

4. 打开 loading

5. 调接口

6. 成功回填/刷新

7. 失败提示

8. finally 收尾

## 如果你自己手写这类页面，正确顺序应该是什么

  

不是先写模板，也不是先写接口，而是按下面顺序：

  

1. 先拆业务阶段。

先确认页面有几段流程：列表、创建、详情、记录、上传、提交、回刷。

  

2. 再定数据模型。

先把列表数据、表单数据、详情数据、记录数据、loading、配置常量分清。

  

3. 再定模板绑定。

模板只绑定状态名，不直接写复杂逻辑。

  

4. 再抽常量。

把状态枚举、权限码、刷新 key、上传配置这类固定值先抽掉。

  

5. 再写派生值。

哪些值能从原始数据推出来，就写成 `computed`。

  

6. 再写字段联动。

哪些字段变化后要重置、回显、重拉数据，就写 `watch` 或事件联动。

  

7. 再写初始化和回显。

首次进入怎么拉、回页怎么刷、详情怎么补数据。

  

8. 再写校验。

先字段校验，再业务校验，再防重校验。

  

9. 最后写提交流程。

把真正的提交逻辑收口，避免同类接口写多份。

  

你可以把它背成一句固定话术：

  

先拆流程，再定状态；先统一绑定，再抽常量；先写派生和联动，再做初始化和回显；最后再补校验和提交。

  

## 一句话总结

  

`customer-complaint` 这套代码的本质，不是“页面很多”，而是“它把一条完整客诉流转链路拆成了状态、派生、联动、回显、校验、提交 6 个层次”；你以后手写业务页，只要也按这条顺序搭骨架，1-8 这套方法自然就会落到代码里。
