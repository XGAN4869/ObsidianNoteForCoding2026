# role 页面按逻辑顺序梳理

  

结论：`role` 页面本质上是一个“左侧选角色，右侧配权限，最后统一提交”的权限配置页，真正重要的不是某一个按钮怎么写，而是整条链路怎么把 `1. 数据统一管理` 到 `8. 提交流程固定规范` 串成一套稳定模型。

  

## 先看文件分工

  

先不要一上来就盯着 `index.vue`，这页其实是 4 个文件一起配合的。

  

- [index.vue](E:\Work1\hzlt\Private\614\travel-web\sites\web\src\pages\system\role\index.vue:88)

  负责页面入口、接口调用、源数据管理、初始化、回显、提交。

- [role-tree-state.js](E:\Work1\hzlt\Private\614\travel-web\sites\web\src\pages\system\role\role-tree-state.js:1)

  负责把角色列表加工成左侧树结构。

- [role-permission-state.js](E:\Work1\hzlt\Private\614\travel-web\sites\web\src\pages\system\role\role-permission-state.js:1)

  负责把权限数据加工成右侧权限树，并封装勾选联动规则。

- [PermissionMenuNode.vue](E:\Work1\hzlt\Private\614\travel-web\sites\web\src\pages\system\role\PermissionMenuNode.vue:84)

  负责递归渲染单个菜单节点，以及这个节点下面的按钮权限、隔离权限、弹窗权限。

  

这一层就已经体现了 `1. 数据统一管理`、`2. 模板绑定保持一致`、`3. 配置常量单独抽离`、`7. 初始化与回显逻辑分离` 的思想：

  

- 页面只做页面该做的事。

- 树结构加工单独放工具文件。

- 权限联动单独放工具文件。

- 递归模板单独放子组件。

  

如果全部塞进一个文件，后面根本没法维护。

  

## 第一段逻辑：页面先把“源数据”和“派生数据”分清楚

  

这一步是整页最重要的基础，也是 `1` 和 `4` 的核心。

  

文件：[index.vue](E:\Work1\hzlt\Private\614\travel-web\sites\web\src\pages\system\role\index.vue:121)

  

```vue

const roleList = ref([]);

const activeRoleId = ref('');

const activeRoleTreeValue = ref([]);

const expandedRoleTreeKeys = ref([]);

const roleTreeKeyword = ref('');

const roleTreeFilter = ref(null);

const activeMenuId = ref('');

const menuPermissionList = ref([]);

const expandedPermissionTreeKeys = ref([]);

  roleList.value.find((role) => String(role.id) === String(activeRoleId.value)),

const roleTreeData = computed(() => buildRoleTree(roleList.value));

const flatMenuPermissionList = computed(() => flattenMenuPermissionList(menuPermissionList.value));

```

  

这里一定要分清两类数据：

  

### 1. 源数据

  

这些是真正要存下来的状态：

  

- `roleList`

- `activeRoleId`

- `menuPermissionList`

- `expandedRoleTreeKeys`

- `expandedPermissionTreeKeys`

- `roleTreeKeyword`

  

这些数据是“输入”，后续逻辑都围着它们转。

  

### 2. 派生数据

  

这些不是存出来的，而是根据源数据算出来的：

  

- `currentRole`

- `currentRoleName`

- `currentDataScope`

- `roleTreeData`

- `flatMenuPermissionList`

  

这就是 `4. 派生数据使用 computed` 的标准写法。

  

你可以记一句固定话术：

  

“先把最小源数据存下来，再把所有展示态、选中态、统计态通过 `computed` 派生出来，避免一份数据维护多份副本。”

这里在做三件事：

- 把树节点 `value` 的命名规则固定住。

- 把角色树和权限树的节点标识统一格式化。

  

为什么一定要这么做？

  

因为树组件、展开逻辑、选中逻辑，最终都依赖稳定的 `value`。  

如果这里今天是数字，明天是字符串，后天又拼接别的前缀，后面所有联动都会乱。

  

所以 `3` 不是“把常量拿出去这么简单”，本质上是在定义这页的数据契约。

## 第八段逻辑：右侧权限节点为什么能递归展开，因为子组件只负责一个 menu

  

这一段要理解 [PermissionMenuNode.vue](E:\Work1\hzlt\Private\614\travel-web\sites\web\src\pages\system\role\PermissionMenuNode.vue:96) 的职责。

  

```vue

<permission-menu-node

  v-for="child in menu.children"

  :key="child.id"

  :menu="child"

  :expandedKeys="expandedKeys"

  @menuChange="(targetMenu, checked) => $emit('menuChange', targetMenu, checked)"

  @nodeToggle="(targetMenu) => $emit('nodeToggle', targetMenu)"

/>

```

  

子组件做的是“一个菜单节点的最小闭环”：

  

1. 先显示菜单本身。

2. 如果菜单被勾选，再显示它的权限分组。

3. 如果有子菜单，再递归渲染子菜单。

4. 自己不存全局状态，只把事件往外抛。

  

这也在呼应 `1. 数据统一管理`：

  

- 全局状态还是在父组件。

- 子组件只负责局部展示和局部交互。

  

这是一种非常典型的组件拆分方式，面试里很好讲。

- 主动点击触发的联动，用事件函数更直接。

- 纯联动规则，收口到 `role-permission-state.js` 更稳定。

- `watch` 只适合那种“字段变化后系统必须自动执行副作用”的场景。

- 监听 `activeRoleId` 自动拉权限

- 监听 `currentRole.dataScope` 做额外提示或限制

```js
    activeRoleTreeValue.value = [getRoleNodeValue(roleId)];

    await getRolePermission(roleId);

    await permissionStore.fetchPermissionInfo(true);

    MessagePlugin.success('保存成功');

  } catch (error) {

    MessagePlugin.error('保存失败');

  }

};

```

  

固定规范一定要按顺序看：

  

1. 前置校验：有没有当前角色。

2. 组装 payload：把页面状态收口成后端需要的数据。

3. 调保存接口。

4. 本地先同步当前角色缓存，避免页面展示立刻失真。

5. 重新拉当前角色权限详情，保证后端结果和前端回显一致。

6. 刷新 `permissionStore`，保证全局权限体系同步。

7. 最后统一给成功或失败提示。

  

为什么这套顺序不能乱？

  

因为这页保存影响的不只是当前页面，还影响全局权限。  

如果你只调接口不刷新 store，可能页面保存成功了，但整个系统里的权限判断还是旧的。  

所以这个提交流程其实是在处理三层同步：

  

- 当前页面同步

- 当前角色回显同步

- 全局权限缓存同步

  

## 把 1-8 串成一条真正的开发顺序

  

如果你以后自己手写这种页面，不要按“1 到 8 分开背”，而是按下面这个真实开发顺序背。

  

### 第 1 步：先定源数据和常量

  

这里对应：

- `1. 数据统一管理`

- `3. 配置常量单独抽离`

  

先想清楚：

  

- 页面最少需要存哪些状态

- 树节点 `value` 怎么命名

- 枚举值怎么定义

  

### 第 2 步：把接口返回统一成前端自己的模型

  

这里对应：

- `1. 数据统一管理`

- `7. 初始化与回显逻辑分离`

  

先 `normalize`，再建模，别让模板直接吃后端原始数据。

  

### 第 3 步：能算出来的状态全部改成 computed

  

这里对应：

- `4. 派生数据使用 computed`

  

比如：

  

- 当前角色是谁

- 左侧树结构

- 右侧权限扁平列表

- 全选/半选状态

- 当前节点权限统计

  

### 第 4 步：模板只做绑定，不做复杂业务

  

这里对应：

- `2. 模板绑定保持一致`

  

模板只负责：

  

- 展示

- 绑定

- 触发事件

  

不要让模板自己处理接口兼容、树结构加工、复杂判断。

  

### 第 5 步：把联动规则收口到工具函数

  

这里对应：

- `5. 字段联动使用 watch`

  

更准确地说，这一页学到的是：

  

- 能用事件驱动就别滥用 `watch`

- 联动规则最好用纯函数封装

- 父子菜单、按钮级联、全选半选，都放到统一工具层

  

### 第 6 步：初始化和回显拆开

  

这里对应：

- `7. 初始化与回显逻辑分离`

  

固定拆法就是：

  

- 初始化拉列表

- 选中角色

- 拉权限详情

- 应用权限回显

  

### 第 7 步：提交前统一校验和收口

  

这里对应：

- `6. 校验规则集中管理`

  

不管页面是不是传统表单页，提交入口一定要统一处理：

  

- 是否可提交

- 数据类型是否统一

- 权限 id 是否统一收集

- 错误提示是否统一出口

  

### 第 8 步：提交后做完整同步闭环

  

这里对应：

- `8. 提交流程固定规范`

  

保存不是结束，真正完整的是：

  

- 接口保存

- 本地更新

- 当前页面回刷

- 全局 store 回刷

- 成功失败提示

  

## 前端小白可以直接背的固定顺序思路

  

以后遇到这种管理后台页面，你就按这套顺序想：

  

1. 这页最小源数据是什么。

2. 哪些是接口原始数据，哪些要先 `normalize`。

3. 页面展示结构要不要做前端二次建模。

4. 哪些状态应该用 `computed` 算，不应该手动存。

5. 模板该绑定什么，哪些逻辑绝不能写进模板。

6. 哪些联动是事件驱动，哪些场景才值得用 `watch`。

7. 初始化、回显、提交能不能拆成三个独立流程。

8. 提交时怎么统一校验、统一组 payload、统一回刷。

  

## 一句话总结

  

这页最值得学的不是“树怎么渲染”，而是“先统一数据模型，再用 `computed` 和工具函数把联动规则收口，最后用固定提交流程把页面状态、接口状态、全局权限状态同步起来”。
