## 一句话结论

这套审批单据已经有“前端领域模型”的雏形，但现在模型分散在多个文件里：列表卡片、详情接口、详情字段、流程时间线、撤回重提、申请弹窗分别维护。后续重构不要把所有单据强行做成一个万能组件，而是整理成“单据注册表 + 数据适配器 + 保留复杂弹窗自定义”的结构。

### 4. 审批详情弹窗负责“拉详情 + 渲染详情 + 审批/撤回”

文件：`sites/web/src/pages/approval/components/ApprovalDetail.vue`

拉详情：

```js

    fetchedDetail.value = null;
    return;
  }

  if (!apiFn) {
    fetchedDetail.value = null;
    return;
  }

  try {

    fetchedDetail.value = res?.data || res;
  } finally {
    loading.value = false;
  }

```

这个 function 是干嘛的：根据当前单据的 `bizType` 找详情接口，再根据 `id` 拉完整详情。

小白应该怎么模仿：

1. 先判断关键参数有没有。
2. 再根据类型找接口。
3. 再处理 loading。
4. 成功后保存详情。
5. 最后一定关闭 loading。

详情字段和流程：

```js
const displayFields = computed(() => {
```

审批提交：

### 5. `packages/tool/src/approval/detailFields.js` 是详情字段领域适配层

这个文件专门做一件事：把不同单据的原始详情数据，转成前端详情页能渲染的数据。

核心入口：

```js
export const buildApprovalDetailFields = (bizType, detail = {}, options = {}) => {
  const {
    labelSuffix = '：',
    objectMode = true,
  } = options;

  if (objectMode && bizType === 'purchase_apply') {
    return buildPurchaseApplyObject(detail);
  }

  if (objectMode && bizType === 'complaint_close') {
    return buildComplaintCloseObject(detail);
  }

  return buildRowDetailFields(bizType, detail, labelSuffix);
};
```

这个 function 是干嘛的：外部只传 `bizType + detail`，它内部决定用哪种单据字段生成方式。

它接收什么数据：

- `bizType`：单据类型，比如 `expense_daily`、`position_feedback`。
- `detail`：后端详情接口返回的数据。
- `options`：控制返回结构，比如返回对象还是行数组。

它返回什么结果：

- 普通单据返回 `label/value` 行数组。
- 采购申请、客诉结案这种复杂单据可以返回结构化对象。

为什么它像领域模型：它不是单纯格式化字符串，而是在表达“某种单据有哪些字段、字段从哪里取、怎么显示金额/图片/明细”。

### 6. `packages/tool/src/approval/flow.js` 是审批流程领域适配层

这个文件负责把后端流程 `workflowConfig` 转成前端时间线可渲染数据。

核心入口：

```js
export const buildApprovalFlows = (detail = {}, bizType = detail?.bizType || '') => {
  const config = detail?.workflowConfig;
  const fixedInitiatorName = fixedInitiatorNameMap[bizType || detail?.bizType];

  if (!Array.isArray(config) || !config.length) {
    return fixedInitiatorName
      ? [{ name: fixedInitiatorName, initiator: getInitiator(detail), desc: `发起人：${getInitiator(detail) || '申请人'}`, time: detail?.createTime || '', statusClass: 'done', status: 'done', statusText: '已完成', state: 'done' }]
      : [];
  }

  const currentIdx = getApprovalCurrentWorkflowIndex(detail);
  const firstUnapprovedIdx = config.findIndex((node) => !node.isAudit);
  const isPositionFeedback = (bizType || detail?.bizType) === 'position_feedback';

  const flowList = config.map((node, idx) => {
    const flowState = getFlowState({ detail, node, idx, currentIdx, firstUnapprovedIdx });
    const nodeOperated = isNodeOperated(node);

    return {
      name: node.name || node.intoName || `节点${idx + 1}`,
      approver: getNodeCandidateApprover(node),
      actualApprover: nodeOperated ? getNodeActualApprover(node, nodeOperated) : '',
      status: flowState.state,
      statusText: flowState.statusText,
      statusClass: flowState.statusClass,
      evidenceList: isPositionFeedback && nodeOperated ? getPositionFeedbackEvidenceList(processPayload) : [],
      time: nodeOperated ? getNodeTime(node) : '',
    };
  });
};
```

这个 function 是干嘛的：把后端复杂流程节点，统一整理成页面时间线需要的节点数组。

它中间做了哪几步：

1. 先拿到 `workflowConfig`。
2. 根据 `bizType` 找发起人文案。
3. 算当前待审批节点下标。
4. 逐个处理流程节点。
5. 计算节点状态，比如已同意、待审批、不同意、未开始。
6. 提取候选审批人、实际审批人、审批意见、时间。
7. 岗位反馈特殊处理凭证图片和处理结果。

值得保留：这是当前项目里最接近“领域服务”的代码。它把流程规则从页面里抽出来了。

## 为什么说它能重构成领域模型

这里的“领域模型”不是后端 DDD 那种实体、聚合、仓储，而是前端项目里更实用的：

```txt
单据类型 bizType
  -> 列表展示规则
  -> 详情接口
  -> 详情字段规则
  -> 审批流程规则
  -> 创建/编辑弹窗
  -> 创建/编辑提交规则
  -> 撤回/重提规则
```

所以它不是“所有单据都写成一样”，而是“所有单据都注册到同一张地图里”。

## 具体可以改进的地方

### 改进 1：建立一个单据注册表，先收拢分散的映射

现在分散的位置：

- `approvalDisplay.js`：`approvalBizTypeConfig` 管列表卡片。
- `approvalDetailApi.js`：`detailApiMap` 管详情接口。
- `withdrawResubmit.js`：`withdrawnResubmitDialogMap` 管撤回重提弹窗。
- `flow.js`：`fixedInitiatorNameMap` 管流程发起人文案。
- `detailFields.js`：`builders` 管详情字段。
- `index.vue`：模板里挂了所有申请弹窗，还手写打开逻辑。

建议先做“收拢”，不要一上来重写。

示例代码仅供参考，需要你手动复制到项目中。

### 改进 2：申请弹窗不必统一成一个组件，但打开流程可以统一

现在 `index.vue` 里有很多弹窗：

```vue
<DailyReimburse ... />
<PurchaseReimburse ... />
<CardRepair ... />
<MaterialReceiveDialog ... />
<MaterialReturnDialog ... />
```

这些弹窗不一样是正常的。采购申请有明细表，物料领用有库存校验，员工录入复用组织模块，它们不适合硬塞进同一个万能表单。

更合理的做法：

- UI 复杂的弹窗继续保留独立组件。
- 打开弹窗、设置模式、传入回显数据、提交成功刷新列表这些动作统一。

示例代码仅供参考，需要你手动复制到项目中。

```js
// 只统一“打开哪个弹窗”，不统一“弹窗内部怎么画”
function openDocumentDialogByBizType(bizType, detail = null) {
  const config = approvalDocumentRegistry[bizType];
  if (!config) return;

  const dialogKey = config.dialogKey;

  // 有 detail 表示重提/编辑，没有 detail 表示新建

```

这个 function 的固定写法：

1. 先根据 `bizType` 找配置。
2. 再拿到对应 `dialogKey`。
3. 再判断是新增还是编辑。
4. 最后打开弹窗。

### 改进 3：把回显逻辑和提交参数整理抽出来

日常报销里有 `fillForm`：

```js
const fillForm = (detail = {}) => {

  form.applicantId = detail.applicantId || detail.accountId || detail.createBy || '';
```

这是典型的“接口字段不统一，前端做兼容回显”。这类代码可以抽成单据适配器。

- 回显适配：后端详情怎么填到表单。
- 提交适配：表单怎么变成后端参数。

### 改进 5：减少 `packages/tool/src/approval` 和 `sites/web/shared/approvalUtils.js` 的重复

现在有两个地方都在做类似事情：

- `packages/tool/src/approval/flow.js` 有 `getApprovalCurrentWorkflowIndex`、`isLastApprovalWorkflowNode`、岗位反馈处理结果和凭证提取。
- `sites/web/src/pages/approval/shared/approvalUtils.js` 也有 `getCurrentWorkflowIndex`、`isLastWorkflowNode`、岗位反馈处理结果和凭证提取。

这类重复会带来一个问题：以后修一个流程规则时，你不知道该改哪边。如果只改一边，PC 和移动端或者不同页面可能表现不一致。

建议：

- 纯数据方法尽量放到 `packages/tool/src/approval`。
- Web 页面只保留和 Web 强相关的内容，比如 COS 上传配置、预览 URL、组件状态。

### 改进 6：把校验规则集中管理

现在校验散在不同组件里，比如：

- `Daily.vue` 校验报销人、金额、事由、附件。
- `Purchase.vue` 校验采购报销信息和报销类型。
- `CardRepair.vue` 校验补卡类型、日期、原因。
- `ApprovalDetail.vue` 校验审批意见、岗位反馈处理结果、凭证。

短期这样能跑，长期问题是：同一种规则不容易复用，也不容易测试。

可以先不做复杂表单引擎，只做简单的 `validateXxxForm`。

## 如果按阶段重构，建议这样做

### 第一阶段：只整理，不大改

目标：让新人能快速找到单据规则。

可以做：

- 新建 `approvalDocumentRegistry.js`。
- 先收拢 `title`、`dialogKey`、`detailApi`、`canWithdraw`。
- 不动弹窗组件内部。
- 不动 `packages/tool/src/approval` 的字段和流程构造。

风险低，收益高。

### 第二阶段：把详情规则统一走 registry

目标：同一个 `bizType` 的列表、详情、流程都能从同一个入口找到。

可以做：

- `buildApprovalCard` 从 registry 读取 `title/buildCardContent`。
- `ApprovalDetail.vue` 从 registry 读取 `detailApi`。
- `withdrawResubmit` 从 registry 读取 `canWithdraw/canResubmit/dialogKey`。

### 第三阶段：抽申请弹窗适配器

目标：保留不同弹窗 UI，但统一“回显、校验、提交参数”。

可以做：

- 每个弹窗建立 `toForm`、`validate`、`toPayload`。
- 先从 `Daily.vue` 和 `Purchase.vue` 开始，因为它们结构相似。
- 物料和员工类弹窗先不要急着动，因为它们业务更重。

### 第四阶段：处理重复工具

目标：PC 和全端共用规则只维护一份。

可以做：

- 对比 `packages/tool/src/approval/flow.js` 和 `sites/web/src/pages/approval/shared/approvalUtils.js`。
- 把纯数据工具沉到 `packages/tool/src/approval`。
- Web 侧只 import，不重复实现。

## 小白应该怎么读这套代码

如果你不是这块代码的作者，建议按这个顺序读：

1. 先看 `sites/web/src/pages/approval/index.vue`，理解页面有哪些弹窗和入口。
2. 再看 `approvalDisplay.js`，理解列表卡片是怎么从后端数据变出来的。
3. 再看 `approvalDetailApi.js`，理解每个 `bizType` 对应哪个详情接口。
4. 再看 `ApprovalDetail.vue`，理解详情弹窗怎么拉详情、怎么审批、怎么撤回。
5. 再看 `packages/tool/src/approval/detailFields.js`，理解每种单据详情字段怎么生成。
6. 最后看 `packages/tool/src/approval/flow.js`，理解审批流程时间线怎么生成。

这个顺序比直接从某个弹窗组件开始读更舒服，因为你先知道全局地图，再看局部细节。

## 举一反三：同类 function 的固定写法

### 1. 拉详情 function

固定顺序：

1. 判断 `id/bizType` 是否存在。
2. 根据 `bizType` 找接口。
3. 开 loading。
4. 调接口。
5. 保存数据。
6. 关 loading。

### 2. 回显 function

固定顺序：

1. 接收后端详情 `detail`。
2. 用多个备用字段兜底，比如 `applicantId || accountId || createBy`。
3. 把类型转换好，比如金额转 Number。
4. 把附件、下拉、特殊字段单独处理。

### 3. 提交 function

固定顺序：

1. 防重复提交。
2. 校验必填和业务限制。
3. 组装接口参数 `payload`。
4. 调接口。
5. 成功提示、关闭弹窗、通知父组件刷新。
6. finally 里恢复提交状态。

### 4. 字段构造 function

固定顺序：

1. 接收 `bizType + detail`。
2. 根据 `bizType` 找 builder。
3. 每个 builder 返回统一结构。
4. 图片、金额、明细数组用专门工具处理。

## 最后记一句

这套审批单据不要理解成“一堆弹窗”，而要理解成“一批不同业务单据，共用列表、详情、流程、审批动作，每个单据用配置和适配器描述自己的差异”。
